## 四、遗漏清单（运行时频率硬编码，还没改）

### 🔴 遗漏 #1（最重要）：UI 进程主循环 tick 仍是 30Hz

- **位置**：`App/MissionConsole.swift:6035`
- **代码**：`timer.schedule(deadline: .now(), repeating: 1.0 / 30.0, leeway: .nanoseconds(0))`
- **作用**：此 DispatchSourceTimer 驱动 `DriveState.shared.tick()`（`:6057` `DispatchQueue.main.async { state.tick() }`）。`DriveState.tick()`（`AuroraDriveApp.swift:6843`，注释"每帧推进（30Hz）...完整决策管线：CoreML推理→置信度→状态机→控制量→录制"）是 **UI 进程的驾驶主循环**。
- **问题**：背景只改了引擎进程（`--engine`）的 `EngineMain.engineTickHz=20`（`EngineMain.swift:1023` `repeating: 1.0/EngineMain.engineTickHz`=1/20），但 **UI 进程的 tick 还硬编码 1/30**。若驾驶循环跑在 UI 进程（非 `--engine` 模式），实际驾驶频率仍是 30Hz，与 20Hz 定档直接矛盾。
- **判断依据**：`MissionConsole.swift` 内 grep `EngineMain` 零命中 → UI 进程不读 `engineTickHz`，该 timer 是独立硬编码。
- **建议**：改成 `1.0 / 20.0`，或改为读 `EngineMain.engineTickHz`（需 UI 进程能访问；当前未引用）。注释 `:6036/6044/6045/6052` 写"45Hz"也需同步（代码本是 30Hz，注释已先于代码漂移）。
- **风险提示**：该 timer 在 `isDriving||isRecording` 时全速跑、待机时 `idleSkip<8` 降到 ~5.6Hz（`:6046-6056`）。改 20Hz 后待机分频比仍成立（20/8=2.5Hz），但注释 `:6052` "45Hz/8≈5.6Hz" 需重算。

### 🔴 遗漏 #2：自车运动模型 typicalDt 仍是 1/30

- **位置**：`Inference/EgoMotionModel.swift:269`
- **代码**：`let typicalDt = 1.0 / 30.0`
- **作用**：自车运动模型期望 dt，用于偏差检测 `:270` `let dtDeviation = abs(dt - typicalDt) / typicalDt`。
- **问题**：tick 改 20Hz 后实际 `dt=1/20=0.05`，`typicalDt` 仍 0.0333 → `dtDeviation = |0.05-0.0333|/0.0333 = 50%`，会误触发偏差告警/降级。背景已点名"准备改成 1/20"，**当前未改**。
- **建议**：改 `1.0 / 20.0`。注释 `:265-266`（"45Hz 下偏离 33%"）同步更新。

### 🟡 遗漏 #3：生产 tick() 内运行时 dt 仍是 1/30

- **位置**：`App/AuroraDriveApp.swift:7084`
- **代码**：`let dt = 1.0 / 30.0`
- **作用**：生产 `DriveState.tick()` 内的物理计算 dt，喂给 `motionPredictor.ingest(dtSeconds: dt)`（`:6680`）、`motionPredictor.predict(dtSeconds: dt)`（`:6684`）、光流/加速度/状态机。
- **问题**：必须与 tick 频率一致，否则速度/加速度换算全错。背景已点名"准备改成 1/20"，**当前未改**。注释 `:7080-7083`（"tick 是 30Hz"）同步过时。
- **建议**：改 `1.0 / 20.0`。注意：本条与遗漏 #1 耦合——若 #1（UI tick）改 20Hz 而本 dt 仍 1/30，则 tick 间隔(50ms) 与 dt(33ms) 不一致，物理积分错乱。**两者必须同时改**。

### 🟡 遗漏 #4：MotionPredictor 默认 dt 仍是 1/30（次要）

- **位置**：`Inference/MotionPredictor.swift:163`（`lastIngestDt` 默认值）、`:263`（`ingest(dtSeconds:)` 默认参数）
- **代码**：`private var lastIngestDt: Double = 1.0 / 30.0` / `func ingest(detections:, dtSeconds: Double = 1.0 / 30.0)`
- **作用**：API 默认值。
- **现状**：运行时唯一调用方 `AuroraDriveApp.swift:6680` 显式传 `dtSeconds: dt`，默认值**被覆盖、不生效**。自检路径（`runMotionSelfTest`）也显式传 dt。
- **建议**：同步改 `1.0 / 20.0`（防御性，避免未来调用方忘传 dt 时引入 30Hz 假设）。不影响当前运行时。

### 🟡 遗漏 #5：LaneFallback.stabilityFrames 注释基于 30Hz（有兜底）

- **位置**：`Inference/LaneFallback.swift:106`
- **代码**：`var stabilityFrames: Int = 6`，注释 `:98` "约 0.2s @30Hz"
- **作用**：车道兜底稳定性门（连续一致帧数门槛）。
- **现状**：该门为**双条件**——帧数达标 **或** 时间窗 `stabilityWindowSeconds=0.2`（`:111`）达标，取先到者。时间窗用真实经过时间，帧率无关。tick 改 20Hz 后，6 帧=0.3s，但时间窗 0.2s 会先达标，**实际门宽不变**。
- **建议**：可按 20Hz 重算（0.2×20=4 帧）使注释与代码自洽；或保留 6 依赖时间窗。注释 `:98-101` 过时需更新。影响小。

### 🟢 遗漏 #6：PerfSelfTest TickBench 预算（边界，建议评估）

- **位置**：`App/PerfSelfTest.swift:907`
- **代码**：`let budget = 1.0 / 30.0`
- **作用**：TickBench 单帧时间预算（`:908` `while ... < secs` 内 `if spent < budget` 节流）。注释 `:857` "驱动：30Hz RunLoop（与生产同构）"。
- **问题**：自检声称"与生产同构"，生产改 20Hz 后同构性破裂。
- **建议**：若要自检反映 20Hz 生产节拍，改 `1.0/20.0`；若作为更严压力基准（30Hz 预算更紧）可保留，但注释需改为"压力基准"。需产品决策。

## 八、结论

### 必须改的运行时硬编码（遗漏）

| 优先级 | 位置 | 现状 | 目标 |
|---|---|---|---|
| 🔴 P0 | `MissionConsole.swift:6035` | `1.0/30.0`（UI tick） | `1.0/20.0`（背景漏报） |
| 🔴 P0 | `AuroraDriveApp.swift:7084` | `1.0/30.0`（生产 dt） | `1.0/20.0` |
| 🔴 P0 | `EgoMotionModel.swift:269` | `1.0/30.0`（typicalDt） | `1.0/20.0` |
| 🟡 P1 | `MotionPredictor.swift:163,263` | `1.0/30.0`（默认值） | `1.0/20.0`（防御性） |
| 🟡 P2 | `LaneFallback.swift:106` | `6`（@30Hz 注释） | 重算或依赖时间窗+更新注释 |
| 🟢 P3 | `PerfSelfTest.swift:907` | `1.0/30.0`（基准预算） | 评估是否改 1/20（需决策） |

### 关键耦合警告

**遗漏 #1（MissionConsole UI tick）与 #3（AuroraDriveApp dt）必须同时改**：
- 若只改 dt=1/20 而 UI tick 仍 30Hz → tick 间隔 33ms 但 dt 按 50ms 积分，物理错乱。
- 若只改 UI tick=20Hz 而 dt 仍 1/30 → tick 间隔 50ms 但 dt 按 33ms 积分，同样错乱。
- 两者必须同步到 1/20。

### 最重要发现

**`MissionConsole.swift:6035` 是背景清单未覆盖的运行时 30Hz 硬编码**，它驱动 UI 进程的完整驾驶决策管线。这是本次审计最有价值的发现。
