## 二、逐条审计结论

### 1. `holdDuration` 覆盖范围 ✅ 已覆盖 5 个驾驶键，但只覆盖 5 个

| 键 | keyCode | 用于 | 覆盖 |
|---|---|---|---|
| A（左转） | 0 | steer | ✅ |
| D（右转） | 2 | steer | ✅ |
| W（油门） | 13 | throttle | ✅ |
| S（刹车/倒车） | 1 | brake | ✅ |
| Space（手刹） | 49 | brake | ✅ |
| **Shift（极速/boost）** | 56 | — | ❌ **未录** |
| **F/E（交互）** | 3 / 14 | — | ❌ 未录（非驾驶控制，可接受） |
| **Z（切视角）** | 6 | — | ❌ 未录（非驾驶控制，可接受） |

**问题 1 后果**：`Shift` 是**驾驶相关**控制（`ControlEngine` 的 `.boost`，
`applyCommand` 之外由限速/极速逻辑使用）。专家模式下真人按住 Shift 加速，
**这个意图完全没进标签**。模型学不到"该不该加速"。
- 严重度：🟡 中（不影响 steer/throttle/brake 三通道正确性，但少了 boost 维度）
- 状态：**已验证**（grep 确认 `recordFrameIfNeeded` 只读 5 个 keyCode）

### 2. `RecordLabelMapper` 数学 ✅ 正确闭环

| 项 | 实现 | 与推理端闭环 |
|---|---|---|
| 输出范围 | steer ∈ [-1,1]、throttle/brake ∈ [0,1] | ✅ 与 `ControlCommand` 一致 |
| 满刻度 | 0.6s（30Hz ≈ 18 帧） | ✅ 覆盖"轻点→满打"手感区间（`:4120` 注释） |
| steer 方向 | `ratio(D) − ratio(A)`，左负右正 | ✅ 与 `applyCommand:7917`（steer>0.1 → steerRight）一致 |
| brake 合成 | `max(ratio(S), ratio(Space))` | ✅ 与 `applyCommand:7932`（brake>0.3 或手刹）一致 |
| **死区** | 标签连续无死区；推理端 `steer>0.1` / `throttle>0.3` / `brake>0.3` | ⚠️ **见问题 2** |

**问题 2：标签无死区，推理端有死区 → 训练/推理分布错配**
`applyCommand:7916-7937`：`|steer| ≤ 0.1` 视为不转向、`throttle ≤ 0.3` 视为不给油。
但专家标签是连续的（按住 0.05s 就出 0.083 的 steer）——**模型会学到 [0, 0.1] 区间的
"微小转向"标签，而这些值在推理端被当作 0 丢弃**。等于让模型去拟合一个它自己不会执行的动作。
- 严重度：🟡 中（不会崩，但训练目标与执行器语义不一致）
- 状态：**已验证**（两侧代码都读过）
- 建议：要么录制端加同款死区（`<0.1 → 0`），要么推理端去掉死区（**推荐前者**，改动小且不改执行行为）

### 3. 专家模式下 AI 是否真的不注入 ✅ 已确认（且有两道门）

```swift
7385: let mayInjectKeys = isDriving && !expertMode && !controlDisabled
7391: if !mayInjectKeys { ... reset + releaseSpeedLimitBrake() ... }
7609: } else if expertMode || controlDisabled {
7615:     releaseAllIfNeeded()          // 只发松键，不发按鍵
7620: } else {
7621:     applyCommand(currentCommand)  // ← 唯一真注入路径
```

**结论**：专家模式下**不走 `applyCommand`**，且每帧 `releaseAllIfNeeded()` 保证 AI 键全松。
标签纯来自真人物理键 ✅。另有夹具硬开关 `benchSuppressAllInjection`（生产恒 false）。
- 严重度：无问题
- 状态：**已验证**

### 4. 引擎模式下专家标签能否产出：**代码路径通了，且有非零实测样本（P0 降级）**

**链路真相**（三个事实叠加）：

| 事实 | 证据 |
|---|---|
| ① 引擎模式是**默认路径**（UI 启动即 spawn `--engine`） | `EngineClient.swift:328-330` |
| ② UI 进程在引擎模式下 `tick()` **提前 return**，不跑 `recordFrameIfNeeded()` | `AuroraDriveApp.swift:6858-6864` |
| ③ 引擎进程**自己也跑 `DriveState.tick()`**（30Hz DispatchSource），且它的 `EngineClient.shared.isActive == false` → **不早退**，会走到 `recordFrameIfNeeded()` | `EngineMain.swift:766, 792-800, 1162`；`isActive` 只在 `EngineClient.connect` 里置 true（`:199`），引擎进程不连自己 |

**所以：引擎模式下真正写盘的是引擎进程的 `recordEngine`**（与 T3 修复一致）。

**keyboardMonitor 在引擎进程里**：
```swift
// EngineMain.swift:1162  EngineGlobals.state?.startDriving()
// AuroraDriveApp.swift:6237  keyboardMonitor.start()   // 引擎进程也调
```
监听**确实启动了** ✅。全局键盘监听 `NSEvent.addGlobalMonitorForEvents` 对后台进程
**可以**收到全局事件（只要有辅助功能权限），引擎进程的权限状态代码里看不到确证——
**但有一份决定性的实测数据**：

> **`data/raw_clips/clip_20261010_133453/controls.csv`（2026-10-10 录制）**：
> 91 帧，其中 **90 帧标签非零**（steer 合计 13.37 / throttle 合计 9.12 / brake 合计 12.51）。
> 典型行：`t=0.0327, frame=1, steer=0.1490, throttle=0.1003, brake=0.1404`

**这说明引擎进程的标签计算路径是通的、能产出非零标签**。此前 5 个 clip 标签全零
（`dataset_v2.py:39` 记录）的原因最可能是：**那些是 AI 模式（非专家模式）录制，
且模型未输出决策（currentCommand = .idle = 0,0,0）**，而非 keyboardMonitor 失效。

**⚠️ 但仍有一个无法从数据区分的点**：2026-10-10 这个 clip 是**专家模式**还是
**AI 模式**？CSV 和 meta.json 都没记 expertMode 标志。
- 若是专家模式 → keyboardMonitor 在引擎进程**确证可用** ✅
- 若是 AI 模式 → 非零值是模型输出，**不证也不伪** keyboardMonitor 可用性

**结论（修正后）**：
- 路径已验证（引擎 tick 不早退 + 调 keyboardMonitor.start）
- 旧 clip 全零的最可能解释是 AI-mode-idle，不是 keyboardMonitor 失效
- keyboardMonitor 在引擎进程是否可靠工作，**仍需一次明确的专家模式实测确证**
  （但风险已从"🔴 高危（疑似全废）"降为"🟡 需确证但已有非零证据"）
- 严重度：🟡 中（**降级**；不再是"数据全废"级别）
- 状态：**部分验证**（路径 + 非零样本已验证；专家模式确证仍缺）

### 5. 录制触发时机 ✅ 帧与标签同帧

`recordFrameIfNeeded()` 在 `tick()` 的**同一帧内**读取：
- `currentScreenImage`（本帧画面，`:6750` 附近赋值）
- `keyboardMonitor.holdDuration(...)`（**实时读**，同一帧）

**没有"先推帧后算标签"的错位** ✅。三个调用点（`:7052` 待机 / `:7429` 限速刹车早退 / `:7634` 主路径）
都在本帧上下文里，`image` 与标签同帧。
- 严重度：无问题
- 状态：**已验证**

### 6. 背压丢帧对标签的影响 ⚠️ 帧连续但**时间戳跳变**

`RecordEngine.appendFrame` 的背压（`RecordEngine.swift:381-390`）：
```swift
guard pending <= Self.maxPendingWrites else { return }   // 丢帧
let idx = frameCount; frameCount += 1                     // 帧号不入队 → 保持连续
```

| 项 | 行为 | 影响 |
|---|---|---|
| 帧号 | **连续**（丢帧时不自增） | ✅ 训练端不会读到缺失的 jpg |
| `t_sec` | 用 `Date().timeIntervalSince(start)` 实时算 | ⚠️ **丢帧会造成时间戳跳变**（如 0.033 → 0.100） |
| 标签 | 与所存帧同帧 | ✅ 标签本身准 |
| 时序模型 | 8 帧窗口 | ⚠️ 跳变处 dt 异常 → accel 估计失真（`dataset_v2.py` 已实测踩过 dt=0.0011s 问题） |

**结论**：丢帧**不污染标签**（帧与标签同帧落盘），但会让**时间序列的 dt 不均匀**，
对 8 帧时序 + accel 特征有影响。`maxPendingWrites = 1` 已在 2026-10-05 收紧，实测丢帧率低。
- 严重度：🟢 低
- 状态：**已验证**
