# 目的地来源结论 —— 游戏数据流里到底有没有「目的地」

> 结论日期：2026-10-03
> 结论一句话：**没有。游戏包里不存在目的地字段。路径必须由客户端自己算。**
> 所以「巡路搬好」（寻路）这件事，**必须**在 AuroraDrive 这边实现，等游戏给答案是等不到的。

---

## 一、为什么必须先查这件事

动手写寻路之前，有一个分岔口：

| 若游戏数据流里**有**目的地 | 若**没有** |
|---|---|
| 直接读包里的目标坐标 → 零算法成本<br>只需做「坐标 → 折线」的呈现 | 必须自带路网图 + 规划算法<br>工作量差一个数量级 |

这个判断决定了整个方案的所有权，所以先查、查实、留下证据再动手。

---

## 二、取证据的方法（可复现）

样本：`tools/reverse/samples/` 下 4 个抓包

| 文件 | 大小 |
|---|---|
| `idle.pcap` | 644 B |
| `move2.pcap` | 1264 B |
| `move_burst.pcap` | 102400 B |
| `turn.pcap` | 4536 B |

环境里**没有** `tshark`、**没有** `scapy`，故用 Python 手工解析 pcap：
24 字节全局头 + 每记录 16 字节头 + IPv4/TCP 载荷提取。
（`--proto-selftest` 另有 6 项失败，与硬编码流 IP `43.144.211.30` 有关，属**既存**问题，不在本次范围。）

对全部 **292 个 TCP 载荷**做了两件事：

1. **逐字节枚举**：按方向和长度归类，确认协议构成
2. **全字段扫描**：在 76 字节移动包里做 608 bit 的滑动扫描，找「看起来像浮点」的位置
3. **字符串扫描**：ASCII + UTF-16 双编码，搜 `target / goal / dest / marker / navi / route / waypoint / mission / quest / 目标 / 导航 / 路径 / 终点 / 目的`

## 三、实测结果

### 3.1 载荷构成（292 个）

| 方向 | 长度 | 个数 | 内容 |
|---|---|---|---|
| c2s | 4 B | 79 | `30000000`（心跳/握手） |
| c2s | 48 B | 79 | 上行包 |
| **s2c** | **76 B** | **79** | **移动包**（就是它） |
| 其余 | — | — | 商店/背包类（见下） |

### 3.2 76 字节移动包的字段

```
[ 56 字节固定前缀 ] + [ 20 字节尾 ]
```

608 bit 全扫描后，**只有**这些位置能解释为合理浮点：

| bit 偏移 | 常量/字段 | 说明 |
|---|---|---|
| 204 | `10240` | 恒定不变 |
| **498** | **X1** | 坐标 1 |
| **509** | **Y1** | 坐标 1 |
| **562** | **X2** | 坐标 2 |
| **573** | **Y2** | 坐标 2 |

> 这四个偏移已固化在 `CoordinateCapture.swift`：
> `kProtoBitX1=498, kProtoBitY1=509, kProtoBitX2=562, kProtoBitY2=573`，
> 合法长度 `kProtoLengths=[72,76]`，前缀 `protoMovePrefix` 56 B。

### 3.3 关键判别：X2/Y2 **不是**目的地

这是最容易误判的一步。**若 X2/Y2 是目的地，那么车在移动时它应该不动**（目标不动）。

实测：**X1/Y1 与 X2/Y2 沿同一条直线同步滑动，且差值恒定。**

→ 同一辆车、**相邻两帧**（30 Hz），不是「车 + 目的地」。

若它是目的地，会出现「车拐弯而 X2/Y2 不动」的现象 —— 四份 pcap（含 `turn.pcap`）里**一次都没有**。

### 3.4 字符串扫描：0 命中

对全部 292 个载荷做 ASCII + UTF-16 双编码扫描，
关键词 `target / goal / dest / marker / navi / route / waypoint / mission / quest / 目标 / 导航 / 路径 / 终点 / 目的`
→ **0 命中**。

命中的字符串**全是**商店/背包业务字段，例如：

```
StoreBrandItemSalesVolumeRecord
StoreBrandItemRepertoryItemRecord
StoreBrandIncomeRecord
food_material_00xx
Item_113#2
```

### 3.5 附带确认：我们一直在用的坐标是对的

顺带验证了既有实现：`decodeProtoMove`（`CoordinateCapture.swift:441-456`）
读的正是 bit 498/509（与 562/573），与实测一致 —— 现有定位链路没有读错字段。

## 四、结论与架构含义

**协议是「服务端权威位置」型：服务端只下发你在哪，不下发你要去哪。**

因此：

- 路径规划**必须**客户端做 → 这正是 `models/route_graph.json` + `Sources/AuroraDrive/App/RouteGraph.swift` 存在的理由
  （拓扑已修复：**664 节点 / 932 边 / 断头 36（5.4%）**，「2026-10-07 实测」；
  此前 612/825、断头 118（19.3%），同一对起终点 7.450 km/47 弯 → **5.781 km/30 弯**）
- 70~120 ms 的网络定位更新率**只够画自车**，不足以驱动逐帧转向 ⇒ 转向判断要由本地路网提供（见 `导航算法选型表.md`）
- 将来若要做「自动开到某点」，目标点**只能**由用户/AI 指定，不能指望从包里读

---

## 五、这条结论的边界（别过度推广）

以下**未被证实**，不要当成结论用：

- 只覆盖了 4 个 pcap / 292 载荷。**未**覆盖副本、副本过场、多人同屏、任务追踪激活态
  —— 存在一种可能：目的地只在**接了任务并开启追踪**时才下发。
  但当前样本里连一个字段位都找不到，说明即便有也是**新增包**而非现有包的新字段。
- 未抓取 `30031` 端口（那是坐标包）之外的其他端口流量
- 未做长时段（>1 分钟）连续抓包，可能漏低频包

**若要推翻本结论**，最小实验：接一个带追踪的任务，边开车边抓包，
比对是否出现**新的包类型**（长度或端口不在上表内）。
在此之前，按「无目的地」设计是唯一有证据支撑的选择。
