# 地图分类与合并（聚类）说明

> 生成时间：2026-10-03
> 涉及代码：`Sources/AuroraDrive/App/MarkerTaxonomy.swift`、`MarkerCluster.swift`、`MapWiring.swift`、`MissionConsole.swift`
> 涉及数据：`models/marker_taxonomy.json`、`models/map_icons/`、`models/FINAL_complete_map_database.json`（只读）

本文回答三个问题：**分类怎么做的、合并（聚类）怎么做的、为什么这么做**。
所有数字都是实测，不是估算；每条结论都附了复现命令。

---

## 一、要解决的问题

原地图被用户评为「烂得离谱」，具体三条：

1. **没有分类** —— 5677 个标记只有 19 种 `type`，UI 上用 `kind` 上色，
   语义上完全不同的东西（怪物、商店、宝箱、传送点）混在一起，看不出主次。
2. **分类做错了** —— 满屏「计程车站」。根因是两个独立的 bug：
   - `MissionConsole.swift` 里硬编码 `if m.kind == "waypoint" { Text(m.name) }`，
     而 100 个 `waypoint` 里有 **80 个叫「计程车站」**（另 10 个「快速旅行点」、
     10 个 `Taxi Stop`），于是整张图都在喊「计程车站」。
   - `电话亭` 的 `type` 写的是 **`phone-booth`（连字符）**，而旧代码只匹配
     `"phone_booth"`（下划线），导致这 17 个点掉进 `default` 分支，
     和普通地标同色 —— 用户根本认不出这是电话亭。
3. **卡** —— 原实现用 `ForEach(..., limit: 400)` 画标记，每帧重建最多 400 个
   SwiftUI 子视图。实测 **18.92 ms/帧**，已超 60fps 的 16.67 ms 预算。
   而且 `limit: 400` 意味着 5677 个点里有 5277 个**永远看不到**。

## 二、分类：7 组语义词表

### 2.1 分组定义

| 组 id | 中文名 | 数量 | 占比 | 默认开 | 颜色 |
|---|---|---:|---:|:---:|:---|
| `explore` | 探索度 | 2434 | 42.9% | ✓ | `#4CC9FF` |
| `resource` | 资源 | 964 | 17.0% | ✓ | `#34E5AA` |
| `monster` | 怪物 | 725 | 12.8% | ✗ | `#FF5468` |
| `shop` | 商店 | 677 | 11.9% | ✗ | `#FFB648` |
| `landmark` | 地标 | 502 | 8.8% | ✗ | `#A98BFF` |
| `service` | 服务 | 269 | 4.7% | ✗ | `#8EE0FF` |
| `travel` | 传送点 | 106 | 1.9% | ✓ | `#FFFFFF` |
| | **合计** | **5677** | 100% | | |

> 覆盖率 **100%**，零兜底条目（`check_taxonomy.py` 会验证 `:fallback` 计数为 0）。

`monster` 默认**关**是刻意的：参考实现 maante 默认把怪物打开，
但本项目的用途是「找地方去」，725 个怪物点默认铺满只会再次变成噪声。

### 2.2 匹配优先级：`type` → `icon` → `name`

这一条是踩过坑才定下来的，**必须写清楚**。

初版把 `icon` 放在 `type` 前面，结果 129 个 `type=currency`（魔术师的馈赠）
因为图标名是 `magicline_256` 而被归进「服务」。**覆盖率仍是 100%**，
所以纯看覆盖率完全发现不了这个错误 —— 这正是「覆盖率会骗人」的实例。

修正后 `type` 是权威判据，`icon`/`name` 只在 `type` 缺失或无法判定时兜底。
`check_taxonomy.py` 里为此加了 8 条语义回归探针，把这个结论**锁死**：

```
✓ currency 全归「资源」            — 964 个
✓ magicline_256 全归「资源」（曾是「服务」）— 129 个
✓ 计程车站 全归「传送点」          — 80 个
✓ phone-booth 全归「服务」         — 17 个
✓ waypoint+tower 全归「传送点」    — 106 个
✓ monster+boss 全归「怪物」        — 725 个
✓ shop 全归「商店」                — 677 个
✓ 无兜底条目                       — 0 个
```

### 2.3 产物

- **`models/marker_taxonomy.json`**（371 KB）
  schema：`{schema:1, source, total:5677, groups:[7], categories:[18], byMarker:{5677}}`。
  `byMarker` 以标记 **id** 为键（不用数组下标 —— 下标会随数据源增删整体错位）。
  category id 形如 `travel:type:waypoint`，取 `:` 前的前缀即组 id。
- **`models/map_icons/`** —— 150 个 `.webp`（600 KB）。
  缺 2 个（`YH_UI_Mapicon_109`、`icon-poi`，影响 7 个标记），回落成默认圆点。
  下载脚本 `tools/roadnet/download_icons.sh` 幂等（已存在且非空则跳过）。
  macOS 原生解码 webp（`NSImage(contentsOfFile:)` 实测可用），无需第三方库。

### 2.4 生成与门禁

```bash
# 生成词表（--check 只校验不落盘）
tools/ayolom/.venv/bin/python tools/roadnet/build_taxonomy.py --out models/marker_taxonomy.json

# 独立门禁（重读两个文件交叉验证，含 8 条语义回归）
tools/ayolom/.venv/bin/python tools/roadnet/check_taxonomy.py
```

门禁固化基线 `EXPECT_GROUPS = {explore:2434, resource:964, travel:106, monster:725,
shop:677, service:269, landmark:502}`、`EXPECT_TOTAL=5677`，组数偏移即为失败。

### 2.5 缺词表时的降级（硬性要求）

`MarkerTaxonomy` 加载失败 ⇒ `groups=[]`、`loaded=false`，
**不崩、不空白**，UI 回落旧的 `kind` 配色，且隐藏筛选条。

实测（`mv models/marker_taxonomy.json /tmp/`）：

```
[TAXONOMY] ✗ 词表文件不存在：.../models/marker_taxonomy.json —— 地图将回落旧配色
[MC-MAP] saved=true path=/tmp/aurora_mc_map_online.png 标记=5677 定位=已锁定
退出码=0
```

**一个关键顺序约束**：词表必须在**解析标记之前**就绪。
标记的 `group`/`groupLabel` 是在解析时一次性写入的（避免每次访问都查表），
若词表晚到，所有标记的 `group` 都是 `nil` → 地图回落成一片同色，
而词表文件明明存在。这种「数据对了但没生效」最难排查，故在
`MapDatabase.ensureLoaded()` 和 `ensureLoadedSyncLegacy()` 里都先调
`MarkerTaxonomy.ensureLoadedSync()`。

## 三、合并（聚类）

### 3.1 为什么需要合并

用户原话是「一大堆一大堆会变得非常卡」，且「也没有真正的合并」。
实测压缩效果（中心 = 地图中心，52 屏幕 px 格）：

| 视野 | 视野内标记 | 聚团数 | 压缩比 |
|---:|---:|---:|---:|
| 120 m | 18 | 14 | 1.3× |
| 300 m | 54 | 41 | 1.3× |
| 1200 m | 888 | 224 | 4.0× |
| 3000 m | 4870 | 302 | 16.1× |
| 6000 m | 5635 | 109 | 51.7× |
| 12000 m | 5677 | 38 | 149.4× |

**关键结论：单一 52px 规则在全 120 m ~ 12 km 区间都成立，不需要按 zoom 分级。**
最坏情况 3000 m 档约 302 个团，Canvas 画 300 个圆约 0.2 ms，远在预算内。

> 复现：`tools/ayolom/.venv/bin/python -c` 用
> `mapX = x/100 × 13056`、`pxPerMeter = 13056 / (13056/(A*100)) = 1.6395` 复算。
> 注意标记的 `x/y` 是**归一化百分比（0~100）**，直接映射到地图像素，
> **不经校准矩阵** —— 校准矩阵只用于自车世界坐标，两者别混。

### 3.2 格边长为什么用「屏幕像素」而非「地图像素」

```
格边长（地图像素） = (52 / 视野屏幕宽度) × 视野地图像素
```

这样屏幕上每个格子的**视觉大小恒定**（52 px），与 maante 的
`maxClusterRadius: 52` 同源。若用固定地图像素格，放大时格会变稀疏
（近处该合并的没合并），缩小时整片糊成一坨。

### 3.3 代表点优先级

一团里选谁当代表：

```
传送点 > 探索度 > 资源 > 商店 > 服务 > 怪物 > 地标
```

理由：用户看地图主要为「去哪」，传送点/资源是决策目标；
地标数量大且信息量低，不该抢掉一个传送站的显示位置。
可用 `AURORA_MAP_CLUSTER_PRIORITY` 覆写成逗号分隔的组 id 顺序。

同优先级时取**离形心最近**的点（视觉更居中）。

### 3.4 视觉语言

- 未成团（count==1）：4px 圆点，组色
- 成团（count>1）：柔光外圈 + 实心圆 + 白字 `+N`，
  半径 `4 + 2.2×ln(count)`，封顶 13 px（避免某个 300 团的点把地图糊死）
- 半径 < 7px 时不画 `+N`（会糊成一坨黑点），改为靠大小表达

### 3.5 过滤顺序：**必须先过滤再聚类**

若先聚类再过滤，团的 `count` 会包含被隐藏组的成员，
用户看到「+12」点开只有 3 个 —— **数字骗人比没数字更糟**。

过滤逻辑在 `MarkerClusterer.filter(_:enabledLabels:)` **只有一份实现**，
`MissionConsole` 直接调用它。全链路统一用**中文名（groupLabel）**比较：
筛选条的 state 存的是中文名，地图上画的也是中文名，只有一处口径；
若改成用组 id 比较就需要 UI 层做 id↔名转换，两边一旦不同步就会出现
「点了没反应」。

词表缺失（`groupLabel == nil`）时**无条件通过** —— 不能因为分类坏了就让地图空掉。

### 3.6 又一个自查出来的 bug：`AURORA_MAP_DEFAULT_GROUPS` 只认中文名

文档与脚本里自然想写组 **id**（`travel` 比「传送点」更稳，不受中文改动影响），
但初版 `defaultOnGroups` 只是把逗号分隔的字符串**原样透传**，
从不把 id 翻译成中文名 —— 因为标记的 `groupLabel` 是「传送点」，
永远匹配不上 `travel`。

实测：`AURORA_MAP_DEFAULT_GROUPS=travel` → **过滤后 0 个标记**，
地图直接空白。这种错很隐蔽：不崩、不报错、日志里「可见组: travel」
看起来还挺正常。

修后 id 与中文名双通道都可用（可混写）：

```
AURORA_MAP_DEFAULT_GROUPS=travel
   → 可见组: 传送点     888 → 22 个，21 团

AURORA_MAP_DEFAULT_GROUPS=travel,怪物
   → 可见组: 传送点,怪物  888 → 98 个，60 团
```

两者都不匹配的 token 被**忽略**（不报错）—— 环境变量写错不该让地图空白。

## 四、性能：实测数据与一个真实的 bug

### 4.1 基准方法

`--mc-map-bench --iters N` 在**同一个进程里**跑三种模式各 N 轮：

| 模式 | 说明 |
|---|---|
| `.none` | 不画标记层 —— 量出底图基线 |
| `.legacy` | 旧的 `ForEach(limit: 400)` |
| `.canvas` | 新的 `Canvas + 聚类` |

同进程对比是必须的：跨进程时底图裁切缓存状态、JIT 预热都不一样，不公平。
所以 `LargeMapCanvas` 的 `markerMode` 由参数传入，环境变量只在 `.auto` 时生效。

每轮把视口平移 0.5px **强制重新渲染** —— 否则 `ImageRenderer` 直接命中
`nsImage` 缓存，测出 `0.000 ms` 这种假数（第一版就踩了这个坑）。

### 4.2 结果

```
── 视野 1200 m（默认档，标签不显示，因门槛 400 m）──
① 仅底图（基线）   平均 13.58 ms · p50  9.53 · p95 11.56
② ForEach 旧路径   平均 45.28 ms · p50 45.35 · p95 45.63
③ Canvas+聚类 新路径 平均 14.94 ms · p50 14.75 · p95 16.75
   标记层增量：旧 31.69 ms → 新 1.36 ms（23.4× 提速，省 30.34 ms）

── 视野 300 m（标签全开，最坏情况）──
① 仅底图（基线）   平均  9.95 ms · p50  7.85 · p95  9.12
② ForEach 旧路径   平均 12.84 ms · p50 12.63 · p95 14.55
③ Canvas+聚类 新路径 平均  9.69 ms · p50  9.65 · p95 10.14

60fps 预算 16.67 ms → 1200m ✓ · 300m(标签全开) ✓
```

> ⚠️ **诚实边界**：离屏 `ImageRenderer` 的耗时**不等于**真机合成器耗时
> （真机有 GPU 合成、图层缓存、脏区重绘）。上表用于**相对对比**，
> 不宣称真机绝对 60fps。

### 4.3 排障中抓到的真实 bug：`ProcessInfo.environment` 被逐点读取

换成 Canvas 后第一次实测，**新路径反而比旧路径慢 6 倍**
（321.94 ms vs 53.82 ms）。这与「Canvas 比 ForEach 快」的微基准完全矛盾，
必须查清楚，不能糊过去。

分段计时（`AURORA_MAP_CLUSTER_TRACE=1`）定位到聚类函数本身：

```
[CLUSTER-TRACE] 取点 0.05 · 过滤 0.25 · 聚类 120.04 ms  (888 → 541 → 264 团)
[CLUSTER-TRACE] 取点 0.08 · 过滤 0.69 · 聚类 209.85 ms  (1420 → 819 → 364 团)
```

**541 个点、120 ms** —— 荒谬。单独测 `ProcessInfo.processInfo.environment`
单次读取的耗时：

```
600 次 ProcessInfo.environment 读取: 18.9 ms  (0.032 ms/次)
```

macOS 上它**每次都要重建整个环境字典**。而 `rank()` 在两个循环里逐点调用
（主循环 541 次 + 代表点选择又一遍，约 1100 次），
1100 × 0.032 ms ≈ **35 ms**，加上 `clusterPx`/`priority` 本身也是每次重读环境，
累积到 120 ms 完全对得上。

**修法**：`clusterPxCached` / `priorityCached` 用 `static let` 只读一次；
`rank` 预计算成 `[String: Int]` 表供循环查；排序改用预排序键。

修后：

```
[CLUSTER-TRACE] 聚类 0.35 ms  (888 → 541 → 264 团)
```

**聚类 120 ms → 0.35 ms（快约 340 倍）**，整帧 321.94 ms → 23.75 ms。

> 这个 bug 最难发现的地方：代码逻辑完全正确、结果也对，**只是慢**。
> 教训：任何「在循环里读环境变量/读文件/建字典」的写法都要当成性能嫌疑，
> 尤其是在热点路径上被随手封成计算属性的。

### 4.4 另一个自查出来的错：基准自己漏测了标签

第一版基准只跑 1200 m 视野，但**标签门槛是 400 m** —— 也就是
`drawLabels` 在 1200 m 时直接 `return`，一个标签都不画。
若就此宣称「标记层 1.36 ms」，等于把最贵的一步（标签，实测 ~32.7 µs/个）
完全漏掉，是假结论。故基准加跑 300 m 档（标签全开），实测整体 9.69 ms，仍在预算内。

### 4.5 标签预算怎么来的

标签成本实测约 **32.7 µs/个**（线性）：

| 标签数 | 耗时 |
|---:|---:|
| 0 | 0.68 ms |
| 400 | 13.77 ms |

预算 16.67 ms ⇒ 最多约 488 个；预算 8 ms ⇒ 约 223 个。
故取硬上限 **200**（≈6.5 ms），留余量给底图/折线/自车图标。
可用 `AURORA_MAP_MAX_LABELS` 覆写。

**标签选取规则**（含一个自查出来的设计缺陷修正）：

初版白名单只有 `travel/shop/service`，但其中 shop(677) 与 service(269)
**默认关闭**，只有 travel(106) 默认开，而 travel 仅占 1.9%。
实测默认视图 300 m 视野下，靠白名单能显示的标签只有 **约 1 个** ——
200 个预算几乎全浪费，用户依旧「看不出这些点是什么」，
**这恰恰就是要修的那个抱怨**。

现规则：

1. 未被聚团（团已用 `+N` 表达，再标名字会叠字）
2. 视野 ≤ 400 m（`AURORA_MAP_LABEL_SPAN_M` 可调）—— 拉远了名字糊成一片
3. **传送点必标**（用户决策目标，仅 106 个，不会挤掉别人）
4. 其余点平等竞争剩余预算，**按离视野中心由近及远**
5. **悬停的标记无视以上全部，始终显示**（用户主动看的东西必须有反馈）

## 五、UI 变化

### 5.1 分类筛选条（地图左上）

7 个 chip，每个用**组色**（与地图上的点颜色一一对应，
看到一片琥珀色就能一眼找到「传送点」chip），带该组数量。
右侧显示当前可见标记数。三个快捷按钮：`全部 / 默认 / 清空`。

默认开启「传送点 + 探索度 + 资源」，实测 1200 m 视野下可见 **819** 个
（全开是 888+，因为默认组已覆盖绝大多数）。

### 5.2 悬停提示

`onContinuousHover` 每帧给位置 → 找屏幕距离 < 12px 的最近团 → 显示
`ClusterTooltip`：团显示「N 个标记」+ 按组分解（最多 4 组）+ 代表点名字；
单点显示名字 + 组名。

用 `onContinuousHover` 而不是 `onHover`：后者只给「进入/离开」，
定位不到鼠标具体在哪，无法知道悬停的是哪个团。

## 六、环境变量汇总（全部加法，默认安全）

| 变量 | 默认 | 作用 |
|---|---|---|
| `AURORA_MARKER_TAXONOMY` | `models/marker_taxonomy.json` | 词表路径 |
| `AURORA_MAP_DEFAULT_GROUPS` | `传送点,探索度,资源` | 默认开启组（中文名或 id，逗号分隔） |
| `AURORA_MAP_CLUSTER_PX` | `52` | 聚类格边长（屏幕 px，8~400） |
| `AURORA_MAP_CLUSTER_PRIORITY` | `travel,explore,resource,shop,service,monster,landmark` | 代表点优先级 |
| `AURORA_MAP_LABEL_SPAN_M` | `400` | 标签视野门槛（米） |
| `AURORA_MAP_MAX_LABELS` | `200` | 标签数量硬上限 |
| `AURORA_MAP_LEGACY_MARKERS` | `0` | `1` = 回退旧 `ForEach` 路径（A/B） |
| `AURORA_MAP_FILTER_BAR` | `1` | `0` = 隐藏筛选条 |
| `AURORA_MAP_SPAN_M` | — | 覆写视野（仅出图核对用） |
| `AURORA_MAP_NO_MARKERS` | `0` | `1` = 完全不画标记层（排障二分） |
| `AURORA_MAP_CLUSTER_TRACE` | `0` | `1` = 打印聚类分段耗时 |
