### 2.1.2 Step [1/4] environment check — libpcap detection (a documented past bug)

`run.sh:26-39`. Two former predicates are recorded as **always-false since macOS 11**, so they were
necessarily false-negatives:
1. `ls /usr/lib/libpcap*` — all system libraries moved into the dyld shared cache, no on-disk files

2. `brew list libpcap` — libpcap ships with macOS and is never installed via brew.

Current predicate (`run.sh:32-39`) is a 3-way `||`:
- `[ -f "$BIN_SRC" ] && dyld_info -linked_dylibs "$BIN_SRC" | grep -q libpcap` — only possible after a
  prior build produced a binary;
- `dyld_info -exports /usr/lib/libpcap.A.dylib` — succeeds via dyld shared cache even without a file;
- `ls /usr/lib/libpcap*` — last-resort fallback.
The `[ -f "$BIN_SRC" ] &&` guard is explicitly there because predicate ① needs a build product that
does not exist on a clean tree, so ② is the fallback (`run.sh:31`).
Failure text names the consumer and a dead implementation: `CoordinateCapture.swift` needs it;
`legacy/NetworkPacketCapture.swift` is the deprecated one (`run.sh:37`).

### 2.1.4 Step [3/4] build

`run.sh:73-93`.

### 2.1.5 Step [4/4] sign + deploy — the SIGKILL / Code-Signature-Invalid incident

`run.sh:95-106`. Comment at `run.sh:96-101` documents the root cause chain:
macOS pages process text **on demand**, so a running instance keeps reading pages from disk. The old
deploy did `cp` **in place over the same inode**; the kernel then read a mix of old and new pages,
CDHash verification failed, and the kernel killed the process (reported as Taskgated Invalid
Signature, seen in 9/10 DiagnosticReports).

Current sequence:
```

## 2.3 Build serialization — `scripts/build-lock.sh`

Reason it exists (`build-lock.sh:6-17`): SwiftPM is whole-module; concurrent edits + concurrent
`swift build` produce `error: input file '.../AuroraTheme.swift' was modified during the build`, and
one broken file blocks **everyone** because compilation is per-module. Called an "infrastructure
defect", not an individual mistake. Second, less obvious reason: concurrent benchmarking. Measured
claim at `:15-17` — 3 agents running `--mc-map-bench --iters 200` simultaneously at ~85% CPU each
drove loadavg to 5.15 on 8 cores, at which point any timing number is incomparable; therefore
**long tasks (selftests / benches / gate collection) must also hold the lock**, not just builds.

Interface (`build-lock.sh:19-23`, dispatch at `:140-146`):
```
bash scripts/build-lock.sh acquire "阶段A验收"   # exit 3 if not acquired
bash scripts/build-lock.sh release
bash scripts/build-lock.sh status
bash scripts/build-lock.sh run "原因" -- <cmd...>
```
Env knobs: `AURORA_BUILD_LOCK` (default `${TMPDIR:-/tmp}/aurora-build.lock`, `:37`),
`AURORA_BUILD_LOCK_STALE_MIN` (default 15, `:38`), `AURORA_LOCK_OWNER_PID` (owner pid override,
`:65`, `:102`).

Design decisions with their stated reasons (`:29-33`):
- `mkdir` is the atomic primitive because macOS `bash` 3.2 has **no `flock` command** (`:30`).
- Lock dir carries an `owner` file with `pid`, `time`, `host`, `user`, `reason`, `cwd`
  (written `:64-71`; fields read by `_owner_field` at `:48-51`).
- Stale locks are **reported, never auto-deleted**, twice: age ≥ STALE_MIN prints a staleness verdict
  but says "但**不自动删**（万一真的还在跑）" (`:91-94`); and if the recorded pid is gone it prints
  `rm -rf` instructions rather than executing them (`:87-90`).
- `release` refuses to remove a lock owned by a different pid (`:102-106`, returns 1).
- `run` acquires, executes `"$@"`, releases, returns the command's rc (`:129-138`) — note it releases
  via plain sequential call, not a `trap`, so a `set -e` abort inside the wrapped command would skip
  the release. The recommended in-script pattern uses `trap 'bash scripts/build-lock.sh release' EXIT`
  (`:26-27`). `UNVERIFIED:` whether a wrapped-command crash in practice leaves stale locks — not
  reproduced this session.

Lock usability caveat: because `age` is computed from the lock dir's birth time via
`stat -f %B` (`:57`), and `mkdir` timestamps are not preserved across copies, a copied/restored lock
dir could read as fresh. `UNVERIFIED:` not tested.

# SEC-03 — DUAL PROCESS / IPC / SINGLETON LOCK / ENGINE HANDOVER

Read from `Sources/AuroraDrive/Core/EngineMain.swift` (2395 lines; header, run(), shutdown, socket
server, globals) and `Sources/AuroraDrive/Core/EngineClient.swift` (1121 lines, all key regions).
Line numbers are real.

## 3.1 Two processes, one binary

The project is **two long-lived processes sharing one executable**. There is no separate engine
binary in `Package.swift`; `AuroraDrive` is one executableTarget (`Package.swift:77-79`) and the mode
is selected by argv.

| aspect | detail | evidence |
|---|---|---|
| UI process | normal SwiftUI app, `@main AuroraDriveLauncher` | `EngineMain.swift:7` |
| engine process | same binary invoked with `--engine` | `EngineMain.swift:5`, `EngineClient.swift:404` |
| dispatch point | `@main AuroraDriveLauncher` splits at the very front of the process, **before** SwiftUI is touched | `EngineMain.swift:7-9` |
| engine never touches | SwiftUI, window creation, `NSApp.run()` | `EngineMain.swift:7-8` |
| TCC inheritance | permissions inherited through the process chain (parent already authorised → no prompt) | `EngineMain.swift:9` |
| engine entry | `static func run() -> Never` | `EngineMain.swift:1077` |

Consequence of sharing the binary: the engine process contains the entire SwiftUI/AppKit code and the
whole `DriveState`; it simply never enters the UI run loop. It builds its own `DriveState()`
(`EngineMain.swift:1234`) from the same class code (stated "照搬主程序组装（同一份类代码）" at
`EngineMain.swift:19`). Any state that lives only in a SwiftUI `@State` is therefore **absent** in the
engine process — this is the root cause of several "works locally, broken in engine mode" bugs
(see 3.8).

## 3.2 UI-side startup ladder — `EngineClient.startup()`

`EngineClient.swift:231-270`.

```
if AuroraFlags.uiLocal:  wantsEngineMode=false; return     :232-237   (AURORA_UI_LOCAL=1)
wantsEngineMode = true                                     :238
if tryConnect(): activate(); return                        :240-243   (health engine already there)

Key design point: **connection attempt happens before spawn**. If a healthy engine is already
listening (from a previous UI session, or the engine outlived the UI), the new UI attaches to it
instead of starting a second one (`EngineClient.swift:8-9`). All failures degrade to local mode with
`isActive == false`; the UI keeps working on its own code path (`EngineClient.swift:14`).

`activate()` (`:272-280`) sets `isActive=true`, `isConnected=true`, stamps `lastHeartbeat`,
`attachShm()`, then calls `onActivated?()` so the UI can push its current display mode / upscale state
to the freshly attached engine (`:278-279`).
`tryConnect()` (`:286-322`) builds `sockaddr_un`, guards `pathBytes.count <= sun_path` size
(`:294-296`), `connect`, installs a `DispatchSource.makeReadSource` on the fd (`:313-318`), and
immediately sends `status` (`:320`).

Notes that matter operationally:
- The child is launched from `argv[0]` **resolved through symlinks**, not from `Bundle.main`. So a

- The child's stdout/stderr go to the **engine** log file, not the UI's. This is why engine `print` was

- `Process` inherits the environment by default. `EngineMain.swift:906-907` relies on exactly that: the

## 3.4 Socket: path, protocol version, staleness

- Path: `~/Library/Application Support/AuroraDrive/engine.sock` (`EngineMain.swift:17`, built at
  `:1189-1191`); the parent dir is created at `:1089-1090`.
- `EngineClient.protocolVersion = 3` (`EngineClient.swift:115`). Version history is inline (`:108-114`):
  1 = original `start/stop/bye/status/upscale/ping`; 2 = added `record/reloadmodel/config` plus
  heartbeat `recording/frames/proto`; 3 = shared memory gained the **mask area** and `pixelsOffset`
  moved `20480 → 28672` — an explicit layout change, so old UI reading a new engine would interpret
  mask bytes as pixels (screen garbage), hence the version bump.
- Staleness predicate: `isEngineStale = sawHeartbeat && engineProtocol != protocolVersion`
  (`EngineClient.swift:330-332`). The comment at `:324-329` records the trap: it **must** be keyed on
  `sawHeartbeat`, not `engineProtocol != 0`, because an old engine never sends a `proto` field at all,
  so `engineProtocol` stays 0 — using 0 as "unknown, not a mismatch" would precisely miss the
  "new UI × old engine" case this guard exists for (2026-09-12, measured).

### 3.4.1 Killing and relaunching a stale engine — three documented traps

`relaunchStaleEngine()` (`:345-...`); the three pitfalls are listed at `:336-343`:
1. **`bye` does not stop the engine.** It only calls `pauseDriving()` and then waits 30 s idle before
   exiting, so a real `kill` is mandatory — you cannot negotiate via `bye`.
2. **Must wait for the old process to be truly dead before `startup()`.** Otherwise `tryConnect()`
   reattaches to the old engine, producing the loop "connect → detect stale → restart → connect to
   stale again"; worse, the flock singleton makes the *new* engine `exit(0)` immediately because the
   old one still holds the lock, so the new engine cannot even start.
3. **Must reset `sawHeartbeat`**, else the mismatch predicate stays true right after restart and it
   immediately re-declares staleness.

Sequence (`:351-380+`): cancel read source, close fd, `detachShm()`, cancel connect timer (`:352-357`);
clear all version/connection state `isActive/isConnected/engineProtocol/sawHeartbeat/lastHeartbeat/
enginePID` (`:358-364`); `kill(pid, SIGTERM)` (`:366-368`); poll every 0.4 s up to 8 s, escalate to
`SIGKILL` once `waited >= 1.2` while still alive (`:369-380`); only after death does it `startup()`.
Documented restriction: only called when **not driving** — losing the engine mid-drive is more
dangerous than a version mismatch (`:344`).

## 3.5 Engine-side singleton lock — flock, not a pid file

`EngineMain.swift:1092-1105`:
```
lockPath = AppSupport/engine.lock                                :1093
lockFD = open(lockPath, O_CREAT|O_RDWR, 0o600); if <0 → exit(3)  :1094-1098
if flock(lockFD, LOCK_EX|LOCK_NB) != 0:
    log "已有引擎实例在运行（flock 失败），本进程退出"; exit(0)   :1099-1102
ftruncate(lockFD, 0); write pid + "\n"                           :1103-1105
```
Properties that must be stated explicitly:
- The lock is released by the **kernel on process exit**, so no stale-lock cleanup code exists and none
  is needed (`:1092` states "进程退出自动释放").
- A second engine exits with **code 0**, not an error code — i.e. "someone else is doing the job" is a
  normal, non-failure outcome. This is why `resumeAfterLeanRecording` (3.9) must wait for the old
  process to die before spawning; otherwise the new engine silently `exit(0)`s and the UI waits for a
  socket that will never appear.
- The pid is written into the lock file purely for post-mortem inspection; authority is the flock, not
  the contents.
- Distinct from `scripts/build-lock.sh`, which is a **build-time** `mkdir`-based lock (SEC-02 §2.3) and
  unrelated to this runtime lock.

## 3.6 Engine startup sequence — ordered, fail-fast

`run()` performs these steps in order (`EngineMain.swift:1077-1256+`):

0. `setvbuf(stdout/_IOLBF)` + `setvbuf(stderr/_IOLBF)` (`:1084-1085`). Reason at `:1078-1083`: the
   engine's stdout is redirected to a file by the parent; stdio defaults to **block buffering** (4 KB)
   when writing to a file, so every `print("[cap-deep] ...")` sat in memory and the log was empty —
   during diagnosis this was misread as "the code never ran". The UI path already set line buffering at
   `AuroraDriveApp.swift:751`; the engine path had missed it.
1. Create `~/Library/Application Support/AuroraDrive` (`:1088-1090`).
2. **flock singleton** (see 3.5).
3. **TCC self-check, fail-fast** (`:1107-1155`): `axOK = AXIsProcessTrusted()`,
   `screenOK = CGPreflightScreenCaptureAccess()`. Default predicate `axOK && screenOK`; failure →
   `exit(2)` with "权限须由父进程链继承". Bypass `AURORA_ENGINE_DIAG_SKIP_TCC=1` logs a warning and
   continues, explicitly "仅供无 TCC 环境验证非权限逻辑，正常路径禁用" (`:14-15`, `:1142-1143`).
   **Observe-only relaxation** (`:1114-1155`): under `AURORA_OBSERVE_ONLY=1` the predicate narrows to
   `screenOK` only, because that mode forces `controlDisabled = true` and therefore injects zero keys,
   making Accessibility permission useless to it while screen capture remains essential. The comment
   stresses this is **not** "skipping permission checks": the non-observe predicate is unchanged
   verbatim, and even if injection were attempted, `ControlEngine.hold()`'s own
   `guard hasAccessibilityPermission` returns early, so nothing can physically be injected (`:1132-1138`).
4. `GameModeDefender.shared.start()` (`:1157-1159`) — engine is the process that needs the audible
   dimension and repeated re-assertion (mutes audio + re-asserts every 3 s).
5. **Anti-freeze**: `ProcessInfo.beginActivity([.latencyCritical, .userInteractive,
   .idleSystemSleepDisabled])` with the token retained (`:1161-1165`; comment: must be held or the
   activity releases immediately), then `setpriority(PRIO_PROCESS, 0, -20)` (`:1166-1168`).
6. **Signal handling** (`:1170-1187`): first `signal(SIGTERM, SIG_IGN)` and `signal(SIGINT, SIG_IGN)` to
   defeat default behaviour, then a `DispatchSource.makeSignalSource` per signal on its own queue. The
   handler sets `EngineGlobals.shutdownRequested = true` and hops to main to call
   `performShutdown(reason: "signal \(sig)")`. Two-stage intentionally: the flag is visible to the tick
   loop (`:1309-1310` also performs shutdown when it observes the flag) while the main-actor call
   guarantees `releaseAll()` runs on the main actor before exit.
7. **Socket server** (`:1189-1224`): `EngineSocketServer(path:)`; three callbacks wired
   (`onLine → handleCommand`, `onClientDisconnected`, `onClientConnected`); `start()` failure →
   `exit(4)`.
8. **Shared memory** (`:1226-1230`): `EngineFrameShm()`; failure → `exit(5)`.
9. `DriveState` assembly on the main actor inside `MainActor.assumeIsolated` (`:1232-1250+`): sets
   `EngineGlobals.state = DriveState()`, then `state?.isEngineHost = true` with the reason that this
   process has no run loop (`dispatchMain`) and therefore receives no `NSEvent`, so recorded keys must
   come from the UI-forwarded `remoteKeyMask` (`:1235-1237`). It then overrides the upscale wiring
   (`:1240-1250`): the engine has no window/MTKView, so interpolation renders in the UI and the engine
   only forwards full-resolution frames through a lock-protected slot; gating closures
   `isUpscaleWanted` and `isYoloWanted` are installed to avoid doing work whose consumers are disabled
   by the mode gate (`:1248-1254`).

Exit codes are therefore a usable diagnostic ladder: `2` = TCC, `3` = cannot create lock file,
`4` = socket start failed, `5` = shm failed, `0` = another engine already running (non-error).

## 3.8 Connection-loss, reconnect window, idle exit

UI side: `readSocket()` (`EngineClient.swift:422-453`) accumulates bytes into `lineBuffer` and splits on
`0x0A` (`:428-436`); each line hops to main for `handleHeartbeatLine`. On EOF/error it **cancels the read
source synchronously on the read queue** before hopping to main (`:447-451`). The comment at `:439-446`
records the measured bug: killing the engine once produced **12+ consecutive "连接断开"** log lines,
because `read()` returning 0 left `readSource` alive, so the same EOF was re-delivered every event-loop
turn; the old code also cancelled inside an async block, which was too late. `handleConnectionLoss` is at
`:628`; `tryReconnectSoon()` (`:455-474`) polls `tryConnect` every 0.5 s and only while `isActive`
(`:456`).

Engine side: `onClientDisconnected` (`EngineMain.swift:1195-1210`):
- if `clientSaidBye`: log "UI 主动关闭（bye），引擎继续运行等待重连" — no reconnect window;
- else: log "UI 连接异常断开，进入 3 秒重连窗口" and `startReconnectWindow()`;
- **both** cases start the idle-exit countdown (`:1205-1207`).
`onClientConnected` (`:1211-1220`) cancels both windows, clears `clientSaidBye`, and sends a heartbeat
with `reason: "client-connected"` immediately (so the UI does not wait a full period for the first
heartbeat).

`startIdleExitCountdown()` (`:2336-2352`): 30 s `DispatchQueue.main.asyncAfter`; the work item re-checks
`EngineGlobals.socket?.hasClient == true` and returns if a client reattached (`:2345`), otherwise logs
"30 秒无人使用，自动退出（先释放全部按键）" and calls `performShutdown(reason: "idle-exit")`.
Rationale at `:2336-2338`: the engine is designed as resident (it can keep driving with the UI closed),
but holding resources with nobody attached is unreasonable, hence the backstop. Cancel is via
`cancelIdleExitCountdown()` (`:2354-2358`).

`pauseDriving(_:)` (`:2360-2375`) is the safety-side pause used by `bye` and watchdog timeout: sets
`isDriving=false`, `controlEngine.releaseAll()`, and **also stops recording** if running (`:2370-2373`).
The stated reason is data quality: otherwise the engine keeps recording for 30 s frames of "car stopped,
labels still the previous AI decision", and those frames get treated as valid samples by the next
training run, poisoning the imitation dataset (`:2367-2369`). Capture and inference keep running,
waiting for reconnect.

## 3.9 Handover: UI ⇄ engine yield and reclaim

This is the mechanism that lets the lean recorder take over the screen stream without fighting the
engine. Two functions, both on `EngineClient`.

### 3.9.1 Yield — `suspendForLeanRecording() -> Bool` (`:1011-1068`)

Ordered steps, each with a stated reason:
1. Cancel any pending "reclaim" poll **before** the guard (`:1012-1018`). Reason (`:1013-1015`): while
   the engine is leaving, `isActive`/`enginePID` are already empty, so a guard placed first would return
   false and skip the cancellation; the pending poll would then fire and `startup()` the engine again,
   making it contend for the same screen stream as local capture.
2. Idempotence: if `suspendedByLeanRecording` is already true, return true without re-signalling
   (`:1020-1025`). Reason: `enginePID` is already zero, so the only available pid is `suspendedPID`,
   which by then is long dead — and that pid may have been **reused by an unrelated process**, so a
   second kill would kill an innocent process. Returning true still tells the caller "remember to
   reclaim".
3. `hadPendingResume` also counts as "engine already yielded" (`:1027-1029`) — otherwise the caller would
   not record the need to reclaim and the engine would never come back.
4. Turn off the reconnect basis first: `wantsEngineMode = false`, cancel `connectTimer`
   (`:1031-1034`) — otherwise reconnect polling would immediately re-spawn the engine.
5. `sendByeSync()` before killing (`:1035-1036`) so the engine knows this is an intentional disconnect
   and does not enter its 3 s abnormal-loss window.
6. `pid = enginePID > 0 ? enginePID : suspendedPID`, then store into `suspendedPID` before zeroing
   `enginePID` (`:1037-1042`). Reason: when the reclaim flow is already in flight `enginePID` is already
   zero, and reclaim must poll "is the old engine really dead" — without the stored pid it would skip
   that wait and hit the flock `exit(0)`.
7. Tear down the local connection: cancel read source, close fd, `detachShm()`, clear
   `isActive/isConnected/enginePID/engineProtocol/sawHeartbeat/lastHeartbeat` (`:1043-1053`). Shm must
   be unmapped or the new engine would still be pointed at the old memory (`:1043`).
8. `kill(pid, SIGTERM)` and log; **15 s** backstop to `SIGKILL` (`:1054-1063`). The comment states
   SIGKILL loses the "keys were released" guarantee and is a last resort only.
9. If no pid was known, log that only the connection was dropped (`:1064-1066`).

### 3.9.2 Reclaim — `resumeAfterLeanRecording() -> Bool` (`:1084-1120`)

- Guard on `suspendedByLeanRecording`; clears it and sets `wantsEngineMode = true` (`:1085-1087`).
- Reads `suspendedPID` then zeroes it (`:1090-1092`).
- If no pid: `startup()` directly (`:1096-1099`).
- Else poll every 0.3 s, up to 8 s, for `kill(pid, 0) != 0` (old process gone) then `startup()`
  (`:1100-1119`). If it is still alive at 8 s it logs "⚠️ 旧引擎 pid=… 8 秒未退出，仍尝试拉起" and
  starts anyway.
- The reason `startup()` is re-run rather than just flipping `wantsEngineMode`: SIGTERM made the engine
  **exit the process**, so the desire to connect is not enough — `startup()` respawns it (`:1072-1074`).
- The reason for waiting out the old process (`:1076-1080`): after SIGTERM the engine still has to run
  `releaseAll → stopDriving → flushSync → exit(0)`, which takes hundreds of ms; during that time the
  socket file still exists and the flock is still held, so a new engine spawned then would `exit(0)` for
  want of the singleton lock, presenting as "the engine never comes back". The comment cross-references
  the same incident as `relaunchStaleEngine`'s trap 2.

### 3.9.3 Invariants of the handover (cross-checked against both sides)

- `bye` alone never stops the engine (3.4.1 trap 1); only `SIGTERM` does. Therefore a yield must be
  `wantsEngineMode=false` **plus** a real SIGTERM, and the reclaim must not assume the pid is gone.
- Shm must be unmapped before a new engine maps `/aurora_frame_v1`.
- Ordering is strict: cancel pending reclaim → disable reconnect → bye → remember pid → drop
  connection → SIGTERM → (later) wait for death → startup.
- Handover is refused while driving — `UNVERIFIED:` the exact guard line; the project note states it,
  and `relaunchStaleEngine` carries the same "not while driving" restriction at `EngineClient.swift:344`.

## 3.10 Shutdown — every path releases keys first

`performShutdown(reason:)` at `EngineMain.swift:2379-2394`:

    st.stopDriving()          // includes controlEngine.releaseAll()      :2383

## 3.11 Shared memory — `/aurora_frame_v1`

Declared at `EngineMain.swift:184`; `shm_open`/`shm_unlink` are bridged because Swift cannot import the
C variadic `shm_open` (fixed 3-arg version at `:43-49`, `@_silgen_name`).

Header layout is documented byte-by-byte at `EngineMain.swift:112-166`. Fields that later sections
depend on: `magic 0x41555246` ("AURF", `:113`), `version = 1` (struct version, distinct from the socket
`protocolVersion = 3`), `headerSize 4096` (`:115`), `detOffset 4096` / `detCapacity 256` / `detStride 64`
(`:116-118`), `frameWidth/Height` (`:119-120`), `generation` bumped on resolution change (`:121`),
`activePage` 0/1 double buffer ("翻转即新帧就绪", `:122`), `frameSeq` (`:123`), `timestampNs` (`:124`),
`detectionCount` (`:125`), `flags` bit0 isDriving / bit1 isStreaming (`:126`), `fpsMilli` (`:127`),
`enginePid` (`:128`), `pageSize` (`:129`), then the mask block `maskSeq/maskW/maskH/laneW/laneH/
maskFlags/maskRatio/maskPadX/maskPadY/maskSrcW/maskSrcH/maskNewW/maskNewH` (`:130-142`).

Three layered facts that are not obvious from the file header:

**(a) `maskNewW/maskNewH` were added as a bug fix, not a feature** (`:144-162`). `MaskOverlay`'s draw
guard read `metrics.newW > 0` but the protocol never transmitted `newW/newH`, so `EngineClient`
rebuilt `LetterboxMetrics` with `newW: 0` → the guard was permanently false → **in engine mode not a
single mask cell was drawn**, user symptom "只能看到检测框，看不到可行驶区域和车道线". Local mode was
fine because it reads `yolopxEngine.metrics` where `newW` is real, which is why local selftests could
never catch it. Two fixes were applied, both deliberate: ① actually transmit the values; ② remove the
draw path's dependence on `newW`, because the drawing math never used it (only
`ratio/padX/padY/srcW/srcH`). ② was necessary because ① alone would still block old clients.
Backward compatibility: the fields sit in otherwise-free header space (header is 4096 bytes, only 125
were used), so no existing field moved and old clients simply ignore them (`:161-162`).

**(b) Mask area placement forced a layout bump** (`:191-198`). Old `pixelsOffset` was exactly `20480`
(end of detection area) with no room for masks; adding them pushed the pixel area back and bumped the
socket protocol to 2 (later 3). `maskOffset = detEnd = 4096 + 256*64 = 20480` (`:198-199`),
`maskGridMax = 160` (`:199`).

**(c) Masks are bit-packed and versioned** (`:168-181`). Motivation quoted as a user requirement that
the engine must return masks and the UI draw them directly. Plain `UInt8` would be 160×160 = 25,600
bytes per mask, 50 KB for two, i.e. **1.5 MB/s of pointless copying at 30 Hz**; bit-packing gives 3,200
bytes each, 6.4 KB total — negligible. Generation-number approach (`maskSeq`): masks only change on
frames where YOLOPX produced output, and YOLOPX runs slower than tick; unconditional resend would spend
half the frames retransmitting identical data, so `maskSeq` changes trigger a resend and the UI only
parses on a new seq (`:179-181`). `EngineGlobals.maskSeq` and `lastMaskFingerprint` hold this state
(`:648-652`).

## 3.12 Engine-mode blind spots (state that exists only in the UI process)

Facts recorded in-source that constrain future work:
1. **YOLOPX does not run in engine mode** (`EngineMain.swift:22-34`). Evidence chain given:
   `DriveState.tick()` early-returns via `tickEngineMode()` when `EngineClient.shared.isActive`
   (near `AuroraDriveApp.swift:3172`), and `yolopxEngine.infer(image:)` has exactly **one** call site
   repo-wide, located **after** that return in the local-inference branch (same file `:3260`) → engine
   mode can never reach it. Consequence: mask overlay reads empty masks and `yolopxEngine.isDegraded`
   stays at its initial `true`, so `LaneFallback` does not engage. Declared "既定设计", not a defect —
   but if masks are ever wanted in engine mode, the 160×160 grid (~50 KB) must be added to the shm
   protocol and back-filled in `tickEngineMode`; **not done** (`:33-34`).
2. `DriveState.perceptionMode` is a **UI-process** property (`UNVERIFIED:` exact definition line;
   cited as `AuroraDriveApp.swift:5414` in `EngineMain.swift:890`). Nothing writes it on the engine side
   — `selectPerceptionMode` only pushes config — so the engine's `st.perceptionMode` stays at its
   initial `.ayolom` and any engine-side gate reading it is permanently A-model (`EngineMain.swift:889-895`).
   Because of that, the engine keeps its own mode value; default `"ayolom"` is justified at `:897-901`
   (the engine has no yolo26s load path at boot: `yoloEngine.loadIfNeeded()` has **zero** occurrences in
   EngineMain — this is a quoted grep result, `:898-899`).
3. Recorded keys in engine mode must come from the UI-forwarded `remoteKeyMask` because the engine has
   no `NSEvent` source (`EngineMain.swift:1235-1237`, §3.6 step 9).

## 4.1 What this layer is

`final class CaptureEngine: NSObject, SCStreamOutput, @unchecked Sendable` (`CaptureEngine.swift:98`).
A long-lived ScreenCaptureKit stream: the system pushes frames on change, memory stays flat, and one

## 4.2 Two capture modes (2026-10-08 dual-mode rework)

Header documents the user requirement verbatim and, more importantly, the **bug it fixed**
(`CaptureEngine.swift:10-27`):
- Original filter was `SCContentFilter(display:excludingWindows: [])` — the exclude array was **empty**,
  i.e. nothing excluded, so the whole display (desktop + AuroraDrive's own UI) was captured.
  Training data contaminated by the app's own windows = poisoned imitation-learning dataset (`:17-19`).
- `.fullScreen` — whole display, **excluding all own windows** (`:22`).
- `.window(id)` — `SCContentFilter(desktopIndependentWindow:)`, which inherently contains neither own UI
  nor desktop (`:23-24`).
- Runtime switching uses `SCStream.updateContentFilter(_:)` (macOS 12.3+) so there is no stream restart
  and no dropped frames (`:26-27`).

Types:
- `enum CaptureMode: Equatable, Sendable` (`:45-63`), cases `.fullScreen` (with `excludedWindowCount`
  used only for diagnostics, `:46-47`) and `.window(id: CGWindowID)` where the id is
  `SCWindow.windowID` = `CGWindowID` (`:48-49`). `isWindowMode` (`:51-54`), `label` (`:57-62`).
  Why an enum rather than a Bool is documented at `:42-44`: the requirement is a two-way choice that may
  later become multi-window, and an enum with associated values removes the illegal state
  "`isWindowMode=true` but `windowID=nil`".
- `struct CapturableWindow: Identifiable, Equatable, Sendable` (`:70-90`) — flat value snapshot for the
  UI selector: `id`, `applicationName`, `bundleIdentifier`, `title`, `width`, `height`, `isGame`, `isOwn`
  (`:72-81`), plus `displayLabel` (`:84-87`) and `sizeLabel` (`:89`). Why flat (`:66-69`): `SCWindow` is
  a system object that dies with the window; holding it in cross-process/cross-thread UI code risks a
  stale object, so the selector holds values and re-resolves by `id` when switching
  (`CaptureEngine.resolveWindow(id:)`).

## 4.4 Frame-rate control — hot update and its unverified assumption

`func setCaptureHz(_ hz: Double) async` (`:710-746`).

Flow:
1. Clamp `newHz` into `1...120`, treating non-finite as 20 (`:711`).
2. Store `targetCaptureHz = newHz` unconditionally, so a later `start()` uses it (`:713`).
3. If not capturing (or no stream/display), log "未在捕获 → 只记 targetCaptureHz，下次 start() 生效" and
   return (`:715-718`).
4. If `newHz == old`, skip `updateConfiguration` entirely (`:719-722`).
5. Primary path: build a fresh full config and `try await stream.updateConfiguration(newConfig)`, then
   `activeCaptureHz = newHz` (`:724-730`).
6. Fallback on throw: await any `pendingStopTask`, then `stop()` + `start()` (`:731-742`).

Two facts that make changing this API risky:
- **The hot update is explicitly documented as unverified** (`:686-700`). `SCStream.h:500` is quoted
  verbatim (`:668-679`) showing the Swift async signature and that `updateConfiguration` has no extra
  availability beyond macOS 12.3, so it is usable at `.macOS(.v26)` (`:680-684`). But the header says
  nothing about which fields may be updated live, and frame rate is a capture throttle that may be
  frozen at stream creation. Therefore **"`updateConfiguration` did not throw" ≠ "the frame rate really
  changed"**, and setting `activeCaptureHz` on the success path is called out as an **optimistic
  assumption** (`:689-690`).
  The author wrote a measurement plan (`:692-699`): observe `[cap-deep] 📥 帧到达 #N` (printed every 60
  frames, so ~3.0 s at 20 fps), call `setCaptureHz(45)` and see whether the interval becomes ~1.33 s, or
  more rigorously count frames in a fixed 5 s window (20 fps → ~100, 45 fps → ~225); if the hot update
  proves ineffective, the fallback must become the primary path. `UNVERIFIED:` whether this measurement
  was executed — the block still says "待批准编译后执行".
- `activeCaptureHz` is deliberately **not** assigned on the fallback path (`:743-744`): it means "actually
  in effect" and is only set by `startStream` after `startCapture` succeeds (`:530`).
- Wiring status note (`:707-709`): as of 2026-10-12 it **is** called from
  `EngineMain.applyPerceptionMode` (two sites: mode switch, and re-switch after recording ends) and from
  `tickOnce`'s emergency-sprint linkage. The newer line numbers in that comment point into `EngineMain`
  and are `UNVERIFIED:` in this session.

## 4.5 `start()` — ordering and races

`func start()` (`:438-501`):
1. Probe log with `isCapturing`, `desiredMode.label`, pid (`:439`).
2. `guard !isCapturing` — repeated calls early-return (`:440-443`).
3. Body runs in a `Task` rather than inline (`:446`).
4. **Await `pendingStopTask` before building a new stream** (`:449-466`). Rationale (`:452-460`):
   `stop()` sets `stream=nil`/`isCapturing=false` **synchronously** precisely so this guard can pass,
   but the old stream's `stopCapture()` is still running asynchronously. Starting a new capture then
   interleaves old-stop with new-start on the same SCStream subsystem; the observed symptom was the
   user-reported "停止后再选就没反应". It must be `await`, not a semaphore, because `start()` is invoked
   from the **main thread** (UI button / socket command) and a synchronous wait would freeze or deadlock
   it if the cleanup task needs main-thread progress (`:458-460`).
5. `SCShareableContent.current` (`:473-482`); on failure it emits both
   `onStatusChange(.error("获取屏幕内容失败（可能未授权）: ..."))` and `onStatusChange(.permissionDenied)`
   (`:479-480`) so the UI can distinguish an authorisation problem.
6. Display selection prefers `CGMainDisplayID()` and only falls back to `content.displays.first`
   (`:484-496`) — reason given: avoid capturing an arbitrary-order display (`:484`).
7. `await startStream(display:content:)` (`:499`).

## 4.7 Own-UI exclusion audit — a deterministic invariant instead of a pixel heuristic

`static func auditOwnWindowExclusion(content:display:excludedCount:) -> String?` (`:1076-1093`).

Design reasoning (`:1058-1072`):
- The obvious check — "look at captured pixels and decide whether our own UI is in there" — was
  **deleted**; the stated principle is "宁可漏报也不能误报", because a false positive makes the user think
  recording is broken (`:1060-1061`).
- The single root cause of "we recorded ourselves" is `excludingWindows: []`, so the check asserts the
  invariant directly: in full-screen mode, if own windows really exist on screen then the exclusion list
  **must be non-empty**, and the excluded count must be ≥ the number of own windows overlapping the
  capture region (`:1063-1067`). Called a necessary-and-sufficient check that cannot false-positive and
  exactly blocks the regression "someone changed the filter back to an empty array".
- Cost: evaluated once per `start()`/`applyMode()`, not per frame, reusing the already-obtained
  `SCShareableContent`, so zero extra system calls (`:1071-1072`).

Implementation: collects `ownWindows(in: content)`, filters to `isOnScreen && frame.intersects(display.frame)`
(`:1079-1082`); returns a specific message if the list is empty while overlapping own windows exist
(`:1083-1087`), a different message if `excludedCount < overlapping.count` (`:1088-1091`), else `nil`.
`ownUIWarningFired` makes it **once per session** (`:1095-1096`), skipped entirely in window mode because
that mode inherently cannot contain own UI (`:1100`), and `resetOwnUIWarning()` re-arms it for a new
recording (`:1110-1113`).

## 4.8 Per-frame callback — what runs on the SCStream queue

   recording is running** (`:1124`). Probes print the first 3 frames then every 60th (`:1126-1128`).
3. **The entire per-frame body is wrapped in `autoreleasepool`** (`:1130-1133`). Reason: the SCStream
   delegate callback does not get an automatic autorelease pool, and at 30 fps the per-frame temporary
   objects (`NSImage`/`CGImage`/`CGDataProvider`/`vImage`) would otherwise accumulate, causing slow memory
   growth over long runs.
4. Timing probes: `lastFrameGapMs` uses `0` for the first frame because `lastFrameTime` starts at
   `.distantPast` and would yield ~5e11 ms of fake gap (`:1137-1144`); a `defer` records
   `lastFrameWorkMs` so **failed frames still get diagnostics** (`:1146`); `updateFPS()` (`:1147`).
5. Fan-out to four optional consumers, each gated **before** its copy:
   - `onNativeFrame` — `copyNativeFrame(from:)`, a private `CVPixelBufferPool` buffer copy that copies row
     order verbatim from `src.bytesPerRow` and does not reinterpret orientation. Reason (`:1149-1154`):
     SCStream's buffer comes from a system pool and may be recycled/overwritten if the main thread is
     slow → use-after-release (garbage crop, or crash). The main thread must own its copy so it is fully
     decoupled from the SCStream lifetime.
   - `onUpscaleFrame` — gated by `isUpscaleWanted()`, `copyUpscaleFrame(from:)` must land in a private
     buffer **with an IOSurface** or downstream `CGImage` creation crashes (cited as `MG-ENG-001`)
     (`:1159-1166`). Gate-before-copy is deliberate: when interpolation/upscaling is off there is no
     consumer, so even the full-resolution copy is skipped (`:1161-1162`).
   - `onRecordFrame` — gated by `isRecordFrameWanted()`; **the copy is synchronous on captureQueue
     (≈4 MB memcpy, sub-millisecond) but JPEG encoding and disk I/O belong to the recorder's own
     background queue** (`:1168-1176`). The comment carries the incident: doing synchronous heavy work
     on this queue previously pushed `capGap` from **11 ms to 2081 ms** (`:1172`). This is a hard
     constraint for anyone touching the recorder.
   - `onYoloFrame` — CPU `vImage` downscale to `YoloEngine.inputSize` (640) at the source, so the large
     image never goes through the `大图 → NSImage → CGImage → 再缩放` chain (`:1178-1179+`); also gated by
     `isYoloWanted()`.
6. `isUpscaleWanted`, `isRecordFrameWanted`, `isYoloWanted` are all `() -> Bool` closures evaluated per
   frame, described as "完全同款模式" (`:136-138`, `:159`, `:163`, `:179`). The engine process installs
   them so work whose consumers are mode-gated away is never done (`EngineMain.swift:1248-1254`).

Summary table of the frame fan-out (`:148` and neighbours):

| closure | resolution | gated by | consumed by |
|---|---|---|---|
| `onNativeFrame` | native copy, row order preserved | always (if set) | display path |
| `onUpscaleFrame` | true full resolution | `isUpscaleWanted()` | MetalGoose interpolation/upscale |
| `onRecordFrame` | full resolution | `isRecordFrameWanted()` | lean recorder |
| `onYoloFrame` | 640×640 CPU-scaled | `isYoloWanted()` | yolo26s / optical flow |

## 4.9 Operational invariants for this layer

- One `CaptureEngine` instance serves recording **and** autodrive; changing capture config in this file
  affects all three paths (`:514-515`).
- Never do JPEG encoding, OCR, inference, or any blocking I/O on the SCStream callback queue
  (`:1170-1172`; the 11 ms → 2081 ms incident).
- `start()` after `stop()` must await `pendingStopTask`, else "stop then select again does nothing"
  (`:452-456`).
- Frame rate is dispatched at runtime; the `CMTime(value:1, timescale:45)` seen in older code is an
  upper bound / initial value, not the operating rate — this point is stated in `EngineMain.swift:724-725`.
- Window mode never falls back to full screen on a missing window; it reports an error (`:549-556`).
- Own-window exclusion is a necessary-and-sufficient invariant (`:1063-1069`); breaking it silently
  contaminates training data (`:17-19`).

## 5.1 Why a second recorder exists

Header `LeanRecordEngine.swift:4-49`. The existing `RecordEngine` "expert mode" was too heavy in the UI
process: per frame it read the keyboard, generated continuous-value labels, scaled to 640×360, and
competed with OCR / glyph / interpolation work for the main thread — in practice it slowed capture.
The user's 2026-11-03 decision (verbatim at `:9-10`) was to build a **very thin** recorder that runs
**no models at all** during recording and pushes all heavy work to offline annotation after the clip
ends.

## 5.2 What the lean recorder does — exactly two things

`:12-14`:
1. Encode the **full-resolution** frame handed over by the capture layer into JPEG and write it to disk.
2. Record a timestamp and a **key snapshot** at 15 Hz — the keys *are* the V3 training labels.

## 5.3 What it deliberately does NOT record — and why (position was removed)

`:16-26` records the reversal in the author's own words. Initially this recorder also parsed
position/heading/acceleration out of libpcap and wrote **19 columns**. The user rejected it outright
(quoted verbatim in-source, colloquial). The three reasons that were accepted as valid (`:19-25`):
- V3 learns **screen → keys**. Position is neither a model input nor a supervision signal;
  `dataset_v3`'s `REQUIRED_COLUMNS` requires only `t_sec/frame` plus 8 keys and reads **not one** of
  `x/y/z/pitch/heading/accel`.
- Position is map information for humans — a **display-layer** concern, unrelated to training data.
- Capture required locking a NIC and asking for permissions, and when it failed the columns were simply
  left blank; introducing a failure-prone, warning-emitting, maintenance-carrying external dependency
  for a column the training side never reads is a net burden.
⟹ whole column set deleted; CSV went **19 → 11 columns**; the `poseProvider` wiring was removed with it.

Also explicitly **not** recorded, because all of it is offline work (`:28-32`):
- Speed OCR — the full-screen original frame already contains the speedometer, so the `speedROINorm`
  region is cropped offline and recognised there. Therefore no separate "speedometer strip" is stored
  (the user explicitly rejected that design).
- Supersampling to 384×224 — done offline; recording keeps the original image so the input size can be
  changed and retrained.
- Coordinate tables / world model / any perception model.

## 5.4 The one hard data invariant: CSV row index ⇄ frame filename

`LeanRecordEngine.swift:34-40` states the invariant and the exact upstream reading that forces it:
`dataset_v3._build_index` computes `n_frames = len(rows)` and resolves each image as
`frames/{j:06d}.jpg` where `j` is the CSV **row order**. Therefore **CSV row j must correspond to
`frames/0000jj.jpg`**.

Failure mode if violated (`:38-40`): if frame numbers were pre-assigned on the main thread and one JPEG
encode failed and was dropped, every subsequent frame number shifts by one — the entire batch's labels
no longer match its images, **and nothing reports an error**.

Therefore: frame numbers advance only after a successful disk write; a failed write retries/drops the
frame and writes **no CSV row** (`:40`).

This invariant is defended by five separate mechanisms (all read):

1. **Number allocated in the write queue, not on the main thread** (thread model at `:42-48`:
   `start()`/`stop()` on main; `appendFrame` on captureQueue; JPEG encode + disk write + CSV append on
   the serial `writeQueue`).
2. **Generation check before taking `framesDir`/`nextFrameIndex`** (`writeFrame` at `:406-424`). A frame
   captured in an old session, if the session rotated (auto-segment = stop→start) in between, would
   otherwise be written into the new segment's directory at index 0 — a silent mismatch (`:408-411`).
3. **Image first, CSV row second** (`:447-460`): "图片已落盘，才写 CSV 行". If the CSV row fails, the
   **image is deleted** (`:450-455`) because a leftover image with no row shifts every later filename.
   Frame number does not advance, so the next frame reuses the same index (`.atomic` overwrite), meaning
   even a failed delete leaves no permanent hole.
4. **No "file exists → next index" retry branch** (`:435-441`). Two reasons: `Data.write(to:options:
   .atomic)` overwrites anyway so the branch would be dead code; and if it did run, `idx += 1` would
   leave a hole in `frames/` while the CSV row still says `idx`, breaking the hard constraint silently.
5. **`appendCSVRow` returns Bool** (`:481-529`). The comment records the earlier bug: on failure it only
   incremented a counter and returned, while `writeFrame` still advanced `nextFrameIndex` → image present,
   row missing, later indices keep advancing → the training side's "index → filename" mapping is
   off-by-N and `dataset_v3`'s `frame == i` check raises `ValueError`, making the **entire segment
   unloadable**.

Two API-level traps documented inside `appendCSVRow`:
- Uses `try handle.write(contentsOf:)` rather than `write(_:)` (`:508-511`) because
  `FileHandle.write(_:)` is non-throwing and **raises an ObjC exception** on disk-full/IO error, which
  Swift `do/catch` cannot catch → it crashes the whole app, and a mid-recording crash leaves an
  unflushed CSV, which is far worse than losing one frame.
- The handle must be force-unwrapped via `guard let handle = csvHandle` (`:513-523`), not
  `try csvHandle?.write(...)`, because optional chaining returns `true` on `nil`, letting the caller
  believe the row was written and advance the frame number while the CSV has no such line. The two
  fields are always assigned/cleared under the same lock
  (`openSession:558-559` / `closeSessionLocked`), so the state is currently unreachable — kept as a
  zero-cost defence that does not depend on that implicit invariant.

## 5.5 CSV format — 11 columns, header written once per session

Header, verbatim (`LeanRecordEngine.swift:649-650`):
```
t_sec,frame,speed_kmh,w,a,s,d,shift,space,super_brake,ultimate_brake
```
Row construction (`:497-502`), in the same column order, built by **string concatenation** rather than
`String(format:"%@…")` — stated reason (`:493-496`): `%@` relies on String→NSString `CVarArg`
bridging which can produce unpredictable output for empty or non-ASCII values, while concatenation is
deterministic and the column count is visible at a glance.

Field semantics:
- `t_sec` — `String(format: "%.5f", tSec)` where `tSec = date.timeIntervalSince(sessionStart)`
  (`:448`, `:497`).
- `frame` — the integer `idx` (`:497`).
- `speed_kmh` — **always an empty string, never `0`** (`:489-491`, `:498`). Reason: `dataset_v3` treats
  an empty string as `speed_valid=0`; writing `0` would be interpreted as "the true speed is zero",
  i.e. a wrong supervision signal. Real speed is filled in by offline OCR.
- `w,a,s,d,shift,space,super_brake,ultimate_brake` — the 8 V3 native key labels from `RawKeySample`
  (`:499-502`).

Key codes (project-wide authority, cross-referenced by other sections): A=0, D=2, W=13, S=1, Space=49,
LeftShift=56. `UNVERIFIED:` those integers were not re-derived from source in this session; they must be
pinned in the control section before being asserted.

Session file set, written by `openSession` (`:634-685`):
- `view.txt` — content = `viewLabel`, default `"TPV"` (`:119-121`, `:640-643`). Written only if absent.
  Rationale (`:636-639`): `dataset_v3` reads it only when `view_filter` is passed explicitly and
  `train_v3.py:263` currently does not pass one, so a missing file does not silently drop the segment —
  but keeping the file set identical avoids a future silent skip (which **does not error**, it just
  yields fewer samples).
- `controls.csv` — created with the header via `FileManager.createFile` (`:651`), then reopened for
  writing and seeked to end (`:654-655`).
- `frames/` — created by `makeSessionDir` (`:626-627`).
- `meta.json` — written at close (5.6).

Session state reset inside `openSession` (`:657-683`), each with its reason:
`sessionDir`, `lastClipDir`, `framesDir`, `csvHandle`, `sessionStart` (`:658-662`);
`sessionGeneration &+= 1` so in-flight old frames are discarded by the generation check (`:663-664`);
`frameCount = 0`, `writeFailureCount = 0`, `nextFrameIndex = 0` (`:665-667`);
`framesWrittenLocked = 0` — explicitly noted as the **authoritative** counter, and omitting the reset
would make segment 2's log/meta inherit segment 1's frame count (`:668-669`);
`lastFrameWidth/Height = 0` (`:670-671`); `restartedPending = false` (`:672`);
`lastAcceptedFrameTime = nil` — else the 10-minute auto-segment would drop exactly one frame at the start
of every segment because the stale timestamp blocks the first frame (`:673-675`);
`cadenceIntervals.removeAll` + `contractBreachStreak = 0` — else the new segment inherits the previous
segment's interval samples and could be stopped immediately for jitter that belonged to the old segment;
the contract is evaluated **per clip**, so the monitor must also work per segment (`:676-681`);
`lastError = nil` (`:682`).

Directory naming (`makeSessionDir`, `:602-632`): `clip_<yyyyMMdd_HHmmss>` under `clipsRoot`, matching the
repo convention — the training side scans only the `clip_` prefix and cleanup relies on lexicographic ≈
chronological order (`:609-611`). **Name collisions are never accepted** (`:612-624`): the timestamp is
second-precision and auto-segment is `stop()` immediately followed by `start()`, which necessarily lands
in the same second; `createDirectory(withIntermediateDirectories:)` does **not** error on an existing
directory, and `createFile` in `openSession` would then **truncate** the previous segment's
`controls.csv` while frames restart at `000000` — the whole segment is silently lost with no error. A
numeric suffix `_2 … _999` is appended instead; exceeding 999 returns nil (`:622`).

## 5.7 `start()` / `stop()`

`start() -> Bool` (`:234-263`), order matters:
1. `guard !isRecording else { return true }` (`:235`).
2. Disk check **on the volume actually written to** (`:237-245`): `Self.freeDiskBytes(at: clipsRoot)`
   compared against `minFreeDiskBytes` (default 2 GiB, `:117`). Explicit reason: it must not query
   `projectRoot`, because the two may be different volumes (switch recording disk / external disk /
   selftest `clipsRootOverride`); querying the wrong volume means authorising writes to disk B using
   disk A's free space, and running truly full invalidates the whole segment (`:238-239`).
   Failure message includes both the free space and the floor and states recording was refused
   (`:241-243`), returns false — it does **not** delete user data (`:116`).
3. `makeSessionDir()` else error (`:247-251`).
4. `openSession()` else error (`:252-256`).
5. Set `isRecording = true` under lock, log `▶ 开始精简录制 → <dir>（15.0 fps，段 N）` (`:258-262`).

`stop()` (`:266-295`):
1. `guard isRecording` (`:267`).
2. Set `isRecording = false` **first** (`:269-271`).
3. `writeQueue.sync { closeSessionLocked() }` (`:273-277`). Because writeQueue is serial, `sync` is
   ordered after every enqueued frame, guaranteeing the CSV handle closes **after** the last frame is
   written — otherwise tail rows are lost (`:273-274`).
4. Read `framesWrittenLocked`/`writeFailureCount` under lock and log totals (`:279-287`); if failures > 0
   it says the corresponding CSV rows were skipped to keep frame numbers paired (`:285-287`).
5. `onSegmentClosed?(closedPath)` **last** (`:288-294`), only registers the path — it must **not**
   annotate here, because auto-segment calls `stop()` then immediately `start()`, and annotating now
   would compete with the new segment's capture for CPU (`:290-291`).

## 5.8 Per-frame admission — the one-way 15 fps gate

`appendFrame(pixelBuffer:)` (`:298-343+`), called on **captureQueue**, does only "take timestamp + key
snapshot + enqueue" (`:299`). The pixel buffer is already a private copy made by
`CaptureEngine.copyRecordFrame`, so holding it until the write completes is safe — no
use-after-release (`:300-301`).

Rate limiting (`:305-330`):
- Runs **before** taking the timestamp (`:305`).
- Purpose stated precisely (`:306-312`): this is **not** compressing 20 fps down to 15. The UI process's
  capture baseline is 15 fps and the UI only calls `start()`, never `setCaptureHz` (20/45 fps are values
  the **engine process** dispatches by mode and are unrelated to this recorder's process). The gate is a
  defence against **extra pushes from SCStream**: when the picture changes violently the system pushes
  more frames, and accepting them all compresses `t_sec`, while `dataset_v3` validates
  `actual_fps = 1/median(dts)` against 15 ± 15 % (**12.75–17.25**) and raises `ValueError` — making the
  entire dataset unloadable.
- Threshold is `minGap = period * 0.9` (`:329-330`) rather than a strict `1/15`. Reason (`:314-316`):
  the true interval of a 15 fps source jitters around 66.7 ms, and pinning to exactly 66.7 ms would also
  reject normal frames, lowering the effective rate and falling below the tolerance floor.
- **Documented blind spot of a one-way gate** (`:318-327`): it only enforces "not too fast", never "too
  slow". If SCStream stalls or the system throttles and delivery drops to ~10 Hz, intervals ~100 ms pass
  the lower bound every time, `median(dts)` leaves 12.75–17.25 and `dataset_v3` raises on the whole
  segment. Rejecting slow frames cannot fix it — the next frame's reference is the last *accepted* time,
  so intervals only grow, leading to rejecting everything; and rejecting cannot turn a 10 Hz source into
  15 Hz. The correct response, and the chosen one, is to **monitor actual rate with `dataset_v3`'s own
  criterion and stop recording with an explicit reason** rather than silently producing ten minutes of
  data that cannot be loaded.
- Lock discipline (`:331-341`): the `isRecording` check and the generation read happen in **one** lock
  acquisition. If they were taken separately and a segment rotation landed between them, an old
  segment's in-flight frame would be carried into the new segment, then written to the new segment's
  `framesDir` at `nextFrameIndex=0`, overwriting `000000.jpg` — old segment loses a frame, new segment
  gains an old picture, and frame numbers remain contiguous ⇒ `dataset_v3` reports nothing. A silent
  mismatch.
- Rate-limited frames are excluded from cadence statistics because they are not representative of
  capture cadence (`:342-343`).

## 5.9 Cadence monitor — enforcing the training-side contract at record time

`noteCadenceForContract()` (`:555-598`), called per frame from `appendFrame` (`:363`).
Fields: `cadenceIntervals`, `cadenceWindow = 120`, `contractBreachStreak`, `contractBreachLimit = 45`,
`contractMinSamples = 30`, `contractFpsTolerance = 0.15` (`:196-205`). `contractBreachLimit` and
`contractMinSamples` are `var`, deliberately, so a selftest can shorten them to trigger the stop
deterministically — the same convention as `maxSegmentSeconds` (`:199`, `:114`).

Algorithm (`:556-598`): lock → require `isRecording` and `cadenceIntervals.count >= contractMinSamples`
→ compute the **median** of the intervals (even/odd aware, `:561-565`) → `actualFps = 1/medianDt`
(`:570`) → `deviation = |actualFps - fps| / fps` (`:571`) → `breached = deviation >
contractFpsTolerance` (`:572`) → streak increments on breach, resets otherwise (`:573-577`) →
unlock → require `breached && streak >= contractBreachLimit` (`:581`) → **report only at the exact
crossing moment** `streak == contractBreachLimit` (`:582-583`) since this runs every frame.

Message (`:585-587`): `实测 X.XXfps 已持续偏离 YHz 超过 ±Z%（dataset_v3 会拒载整段），已停止录制`.

Stop must be hopped to main (`:589-597`): the comment forbids calling `stop()` on the capture queue
because `stop()` contains `writeQueue.sync {}` and would block the capture queue on disk I/O — the same
incident on record (capGap 11 ms → 2081 ms). `DispatchQueue.main.async` is used, and the closure
re-checks `isRecordingSnapshot` before stopping and setting `lastError`.

## 5.10 Threading model (authoritative summary)

| context | what happens | rule |
|---|---|---|
| main thread | `start()` / `stop()`, segment rotation | `stop()` does `writeQueue.sync` drain; never call it from captureQueue |
| captureQueue (SCStream callback) | `appendFrame`: timestamp, key snapshot, rate gate, enqueue | **no JPEG encode, no disk I/O, no `stop()`** (`:44-47`) |
| writeQueue (serial) | JPEG encode, file write, CSV append, meta write, close | owns `nextFrameIndex` ordering; `stop()` drains it synchronously |
| main thread (async hop) | `frameCount` publish (because `@Observable` storage is not thread-safe) | authoritative count is `framesWrittenLocked` under `stateLock` (`:473-478`) |

## 6.4 Why the central table exists (with the measured cost it removes)

`AuroraFlags.swift:4-54`:
- Pre-refactor there was **no aggregation**: default values existed only inside each `??` expression, so
  answering "what happens if I don't set this" required reading 13 files (`:19-20`).
- **Hot-path re-reads were real and measured**: `ProcessInfo.environment[key]` costs **17.213 µs/call**
  (measured, cited `AuroraDriveApp.swift:5171`) and **0.032 ms/call** (cited `MarkerCluster.swift:75`).
  `AURORA_OCR_DEBUG` was read **3 times inside every OCR inference**; `AURORA_DISABLE_OPTICAL_FLOW` was
  read every frame (latter since fixed) — called a "typical symmetric omission" (`:21-25`).
- At 30 Hz, 17 µs × 30 = 0.5 ms/s burned for nothing (`:37-38`). `static let` is `swift_once`-guarded →
  thread-safe, evaluated once, thereafter a memory read (`:33-38`).
- Three goals: ① centralise; ② self-describe (`defaultValue` / one-line summary / `isDiagnostic` /
  `readBy`); ③ discoverable via `--flags-help` (`:27-30`).

### 6.4.1 Boolean parsing conventions — a compatibility contract

`AuroraFlags.swift:94-114`:
- `bool(_:default:)` — **only the literal `"1"` means on**; `"true"`/`"yes"` are **not** accepted.
  Reason (`:96-98`): the project's historical convention is `== "1"`
  (`AuroraDriveApp.swift:138/5334` cited); keeping it byte-identical avoids a silent behaviour change of
  the form "this used to work and now doesn't".
- `boolNotZero(_:default:)` — inverse: only `"0"` means off; unset or anything else means on. Used for
  default-on switches (`AURORA_CACHE`, `AURORA_MAP_FILTER_BAR`) (`:104-109`).
- `str` treats empty string as absent (`:111-114`); `dbl`/`int` fall back to the default on parse
  failure; `dblOpt`/`intOpt` return nil.
- Single subscript site: `raw(_:)` at `:89-92` is the **only** `environment[...]` inside the file, and
  the comment states this deliberately so that `grep -rn 'environment\[' Sources/` is a direct measure of
  how much has not been migrated (`:82-83`). `UNVERIFIED:` that grep now returns exactly the residual
  sites listed in 6.3 — not re-run as an exhaustive assertion this session.

## 6.6 Self-description contract — `--flags-help`

`AuroraFlags.swift:536-552`. `helpText()` emits, in order: a title line containing `all.count`, then one
line per switch, then one trailing statistics line. Format is **one switch per line**, and the comment
makes the assertion explicit (`:538-540`): `wc -l` must equal `all.count + 2`, so
`--flags-help | wc -l` is usable as a test assertion.

Per-line format (`:545`): `  [诊断|功能] KEY=defaultValue  — summary   ← readBy`.

`AuroraFlagSpec` (`:61-72`) requires `key`, `defaultValue`, `summary`, `isDiagnostic`, `readBy`; the
`defaultValue` doc comment states it **must** match the real code default — "不一致就是文档撒谎"
(`:64-65`). The table itself is authoritative: `:444` states "漏加等于这个开关'不存在'", i.e. a switch
missing from `all` is invisible to `--flags-help` and to the selftest.

## 6.7 CLI flags — 73 distinct, two hard registration rules

### 6.7.1 Rule 1 — a one-shot flag must be registered in `oneShotFlags` or it is silently blocked

`AuroraDriveApp.swift:950-952` declares `let oneShotFlags = [...]` (array spans `:952-1018`, **53**
distinct entries) with the stated purpose: short-lived self-check and daemon modes must not participate
in the UI lock, otherwise they mutually exclude the resident UI and either the selftest fails or the user
cannot start the GUI (`:950-951`).

The lock itself (`AuroraDriveApp.swift:763-779`): `flock(LOCK_EX|LOCK_NB)` on
`~/Library/Application Support/AuroraDrive/ui.lock`; if the file cannot be created it **allows**
startup (`:769`) rather than blocking normal use; on success it stores the fd and writes the pid
(`:770-775`); on failure `close` + false (`:777-778`).
Enforcement (`:1358-1366`):
```swift
let isOneShot = args.contains { oneShotFlags.contains($0) }
if !isOneShot, !acquireUISingleInstanceLock() {
    print("[App] 已有 AuroraDrive 实例在运行 —— 本次启动退出")
    print("      原因：两个 UI 会互抢引擎 socket（0.5s 断开重连死循环）")
    exit(0)
}
```
The reason for the lock (`:760-762`): measured 2026-09-12 — two UI instances fight over the same engine
socket, the engine serves one client, both get kicked and each enters a "disconnect → reconnect 0.5 s"
loop flooding the log. The engine side already had `engine.lock`; the UI side lacked it.

**The documented failure mode is a false green**, and the source records it recurring **four times**:
- `:982-983` — "W5 实测警告：漏登记时进程会被 UI 单实例锁挡掉却仍 exit 0 —— **假绿**。登记与分发必须同时存在。"
- `:999-1002` — "这两个自检早就有分发代码，但从未登记进本数组 —— 一旦 UI 进程在跑（持 ui.lock），
  它们会被单实例锁挡掉却仍 exit 0（**假绿**）。同款陷阱第 3 次出现。"
- `:1015-1016` — "⚠️ 登记与分发必须同时存在（本项目第 4 次踩同款假绿陷阱）。"
- `:986-990` — the mirror-image error: registering without dispatching falls through to the normal UI
  start and also exits 0 → false green.
- `:216` and `:992-998` add the same warning for `--lean-annotate`.

Consequence for verification work: a selftest that "passed" while another UI instance was running, and
whose flag was not registered, **proved nothing**. Both registration and dispatch must be verified.

## 7.1 Verification integrity — the "false green" class (highest-value pitfall)

**Invariant**: a test that reports success must actually have executed.

The `oneShotFlags` registry is a **hand-maintained array** (`AuroraDriveApp.swift:952-1018`). A
self-check flag missing from it is blocked by the UI single-instance lock and the process **exits 0**,
which reads as success. The source records this recurring **four times**:
- `:982-983` — "漏登记时进程会被 UI 单实例锁挡掉却仍 exit 0 —— **假绿**。登记与分发必须同时存在。"
- `:999-1002` — two self-checks had dispatch code for a long time but were never registered;
  "同款陷阱第 3 次出现".
- `:1015-1016` — "本项目第 4 次踩同款假绿陷阱".
- `:986-990` — the **mirror image**: registering without dispatching falls through to the normal UI
  start and also exits 0 → false green.
- `:216`, `:992-998` — same warning restated for `--lean-annotate`.

Related false-green sources recorded elsewhere in the UI file:
- `:1652` — "避免「自检用的解析逻辑和生产不一样」的假绿" (self-check parsing must not diverge from
  production parsing).
- `:1796` — proving only "load succeeded" is a false green; a closed-loop probe must use instrumentation
  counts.
- `:1991`, `:1996` — a pre-condition assertion prevents "the value is 0 because it hasn't loaded yet"
  being mistaken for a real zero.
- `:3603` — a specific item's first version was a **weak assertion (false green)** and is recorded as
  such.
- `:3856` — "硬凑一个恒真断言只会制造假绿" (padding with a tautological assertion only manufactures

Operational consequence for anyone verifying this project: confirm **both** registration and dispatch

## 7.2 Concurrency / architecture constraints

### 7.2.1 Never do heavy work on the SCStream callback queue
`CaptureEngine.swift:1170-1172` — the record-copy is synchronous on captureQueue (≈4 MB memcpy,
sub-millisecond) but "JPEG 编码与写盘由录制器丢到自己的后台队列 —— **绝不可在 captureQueue 上编码**",
with the incident cited: synchronous heavy work on that queue pushed `capGap` from **11 ms to 2081 ms**.
Restated independently in `LeanRecordEngine.swift:44-47` and again at `:589-592` (why the cadence monitor
hops to main before calling `stop()`). Three separate files state the same rule.

### 7.2.2 `stop()` must not be called from the capture queue
`LeanRecordEngine.swift:589-593` — `stop()` internally does `writeQueue.sync {}`, which would block the
capture queue on disk I/O; therefore `DispatchQueue.main.async` is used, mirroring the auto-segment path.

### 7.2.3 Socket fd must not be closed via the shared variable
`EngineMain.swift:562-566` — on new connection the old one is cancelled (`old.cancel()`), never closed by
reading `clientFD`, because cancel is asynchronous and closing the shared variable would **close the new
connection** ("绝不在这里按 clientFD 关…会误关新连接").

### 7.2.4 UI read-source must be cancelled synchronously on EOF
`EngineClient.swift:439-451` — measured: one engine kill produced **12+ "连接断开"** lines because
`read()` returning 0 left `readSource` alive and the same EOF was re-delivered every event-loop turn;
the earlier fix that cancelled inside an async block was also too late. Correct order: cancel on the
read queue, then hop to main only for state cleanup.

### 7.2.5 Handover ordering (flock makes it unforgiving)
`EngineClient.swift:1076-1080` and `:336-343` — after SIGTERM the engine still needs
`releaseAll → stopDriving → flushSync → exit(0)` (hundreds of ms); during that window the socket exists
and the flock is still held, so spawning a new engine immediately makes it `exit(0)` for want of the
singleton lock, presenting as "the engine never comes back". Two independent sites record the same trap.

### 7.2.6 Pid reuse — never re-kill a remembered pid
`EngineClient.swift:1020-1025` — `enginePID` is already zero in the idempotent path, so only
`suspendedPID` is available, and that process is long dead; **the pid may have been reused**, so a second
kill would kill an unrelated process. Return true instead.

### 7.2.7 `@Observable` storage is not thread-safe
`LeanRecordEngine.swift:473-478` — `frameCount` may only be written on the main thread via
`DispatchQueue.main.async`; the authoritative count is `framesWrittenLocked` under `stateLock`, because
at `stop()`-drain time the main-thread value may not have updated yet (`:694-696`).

## 7.3 Data-integrity constraints (training data)

### 7.3.1 CSV row index ⇄ `frames/NNNNNN.jpg` is a hard pairing
`LeanRecordEngine.swift:34-40`. Upstream cause: `dataset_v3._build_index` uses `n_frames = len(rows)` and
resolves `frames/{j:06d}.jpg` by **row order**. Violation is **silent** — labels shift and nothing errors.
Five defence mechanisms are enumerated in SEC-05 §5.4. The specific historical bug: `appendCSVRow`
returned nothing while `writeFrame` still advanced the index → whole segment unloadable
(`:481-486`).

### 7.3.2 Never write `speed_kmh = 0`
`LeanRecordEngine.swift:489-491` — empty string ⇒ `speed_valid=false`; `0` would be read as "true speed is
zero", i.e. a **wrong supervision signal**. Real speed is filled by offline OCR.

### 7.3.3 Frame-rate tolerance is enforced by the training loader, not the recorder
`LeanRecordEngine.swift:311-327` — `dataset_v3` computes `actual_fps = 1/median(dts)` and raises
`ValueError` outside **12.75–17.25** (15 ± 15 %). The recorder's own gate only enforces "not too fast";
the "too slow" case cannot be fixed by rejecting frames and is handled by monitoring and **stopping with
an explicit reason** (`:325-327`).

### 7.3.4 Never accept a session-directory name collision
`LeanRecordEngine.swift:612-624` — timestamp precision is one second and auto-segment is `stop()`
immediately followed by `start()`, so collision is guaranteed; `createDirectory` does not error on an
existing directory and `createFile` would **truncate** the previous `controls.csv`, silently losing a
whole segment.

### 7.3.5 Do not record the app's own windows
`CaptureEngine.swift:17-19` — original filter used `excludingWindows: []` (nothing excluded), so the
desktop and AuroraDrive's own UI entered the training data. The invariant assertion is now
"exclusion list must be non-empty when own windows are on screen" (`:1063-1069`), and the pixel-based
heuristic was **deleted** on the principle "宁可漏报也不能误报" (`:1060-1061`).

### 7.3.6 Never silently fall back on a missing capture window
`CaptureEngine.swift:549-556` — falling back to full screen would violate the user's explicit choice, so
it reports an error and marks the selector red instead.

### 7.3.7 Alt-tab / focus loss must not lose held keys
`YolopxEngine.swift:58` and `:63` state the fail-open red line: a fail-hard path would drop the
already-pressed keys; the design instead gives "the most conservative answer" when data is untrustworthy
rather than letting the car die. `LaneBridge.swift:175` restates the fail-open red line for mask
geometry: `isUsable` must reject short `cells` before `LaneFallback` would `SIGTRAP`.

## 7.4 Input-injection constraints (measured against the actual game)

### 7.4.1 Only `.hidSystemState` + `.cghidEventTap` works
`ControlEngine.swift:183-198` — measured: the target game's input layer reads only the HID system state
layer. `.combinedSessionState` (previously used) is ignored by the game even though system UI reacts
(keyboard visualiser lights up, system beep sounds) — symptom "UI 显示已输出 W，但游戏纹丝不动".
`.privateState` is "禁止使用". `.hidSystemState` with `.cghidEventTap` is the verified combination that
gets through.

### 7.4.2 Modifier keys only emit `flagsChanged`
`KeyboardMonitor.swift:106-118` — measured: synthesising Shift produces event type **12 = flagsChanged**
for both phases, no keyDown/keyUp. Shift is the handbrake and the precondition for super brake
(Shift+Space) and ultimate brake (Shift+Space+S) (`:111-112`). Without a `.flagsChanged` monitor,
`heldKeys` never contains 56, so `shift` is 0 for the whole recording and the three safety heads get zero
positive samples — the trained model would never pull the handbrake (`:113-115`).

### 7.4.3 Auto-repeat is ignored by this game
`ControlEngine.swift:504-507` — the game's input layer only accepts "new key down" and ignores
auto-repeat, so `autorepeat` must stay `false` for the target game.

### 7.4.4 Never inject keys in observe-only mode
`ToolRegistry.swift:405` — with `AURORA_OBSERVE_ONLY=1` input injection is refused with an explicit
message that nothing was sent. Cross-referenced by the engine's narrowed TCC predicate
(`EngineMain.swift:1132-1138`, SEC-03 §3.6).

### 7.4.5 Permission query must not pop a dialog on the hot path
`ControlEngine.swift:210-232` — two distinct bugs recorded:
- P0 (2026-09-07): the string literal `"kAXTrustedCheckOptionPrompt"` is not a valid CFString constant,
  making the options dictionary invalid, `AXIsProcessTrustedWithOptions` receiving a nil-equivalent and
  **crashing with EXC_BAD_ACCESS at 0x8**.
- 2026-09-30 correction: the earlier comment claiming "first call auto-prompts" was **wrong** — passing
  `nil` only queries and **never** prompts, which is why the app never appeared in the Accessibility list
  (no request was ever issued). Therefore two methods exist: `checkPermission()` stays pure-query
  (because the high-frequency `press`/`hold` retry path must never prompt, "否则每帧弹一次"), and
  `requestAccessibilityPermission()` prompts once at start.

### 7.4.6 Six key-ups per frame was 71 % of the frame
`ControlEngine.swift:456-485` — measured `tick.inject` p50 = **0.15 ms** of `tick.total` 0.21 ms = **71 %**,
the single largest main-thread cost, because the `expertMode || controlDisabled` branch called
`releaseAll()` every frame (6 keys × `CGEvent.post`, `ev=` counter rising ~2000 per 30 s). Fix:
`releaseAllIfNeeded()` throttles to at most once per second when `heldKeys` is empty, while `releaseAll()`
itself is unchanged ("一字未改") because it still carries the safety duty of clearing system-level stuck
keys left by a previous crashed process. Safety argument enumerated at `:473-481`; equivalence to be shown
by ABBA comparison (0.15 ms → ~0.01 ms) at `:483-485`.

## 7.5 Platform / OS constraints

### 7.5.1 Deploying a binary over its own inode kills the running process
`run.sh:96-101` — running processes page text on demand; an in-place `cp` over the same inode makes the
kernel read mixed old/new pages, CDHash verification fails, and the kernel kills the process
(Taskgated Invalid Signature). Fix: copy to a temp name and `mv` (new inode), so the old instance keeps
the old vnode.

### 7.5.2 Metal precompile needs a writable module cache
`run.sh:118-120` — metal's clang ModuleCache defaults to `/var/folders/`, which a restricted environment
rejects with `Operation not permitted`, silently failing the precompile; redirected via
`-fmodules-cache-path="$ROOT/.build/metal-cache"`.

### 7.5.3 `libpcap` presence cannot be detected by file existence
`run.sh:26-39` — system libraries moved into the dyld shared cache since macOS 11, so
`ls /usr/lib/libpcap*` is always false; `brew list libpcap` is always false because libpcap ships with
macOS. Detection now uses `dyld_info -linked_dylibs` on a build product, then
`dyld_info -exports /usr/lib/libpcap.A.dylib`.

### 7.5.4 Build exit code lost through a pipe
`run.sh:78-80` — `swift build | tail -5` swallowed the exit status so `set -e` never fired and a **failed
build was deployed and launched**; the named incident is a 2026-09-15 `bagel_spam` compile failure that
was mis-deployed. Now the full log is captured and the rc checked.

### 7.5.5 Only `"1"` means on
`AuroraFlags.swift:94-102` — the project convention is `== "1"`; accepting `"true"`/`"yes"` would create a
silent behaviour change. `boolNotZero` is the inverse for default-on switches (`:104-109`).

### 7.5.6 `static let` never re-reads the environment
`AuroraFlags.swift:40-45` — `static let` evaluates at first access, so `setenv` later has no effect. One
documented exception exists: `AURORA_EGO_CHECK` is deliberately a per-call `static var` because
`AuroraDriveApp.swift:3232` does `setenv("AURORA_EGO_CHECK", "off", 1)` and a selftest depends on it
taking effect immediately (`:238-243`).

### 7.5.7 View-state restoration hangs the process
`AuroraDriveApp.swift:1368-1372` — symptom with `open AuroraDriveUI.app` (LaunchServices / double-click):
the process spins forever — 4 threads, 0.0 % CPU, 70 MB RSS, CPU time flat for 30 s, no log, no window —
while running the same binary from a shell is fine. Fix recorded as "禁用窗口状态恢复" (2026-09-30).

### 7.5.8 stdio block buffering hides all engine logs
`EngineMain.swift:1078-1085` — redirected stdout/file output block-buffers at 4 KB, so every
`print("[cap-deep] ...")` stayed in memory and the log was empty; during diagnosis this was misread as
"the code never ran". Both stdout and stderr are set to `_IOLBF`; the UI path already did this at
`AuroraDriveApp.swift:751`, the engine path had missed it. `AuroraDriveApp.swift:782-784` states the same
rationale for the UI process.

### 7.5.9 First-frame timing probes produce astronomical values
`CaptureEngine.swift:1139-1144` — with `lastFrameTime == .distantPast`, `timeIntervalSince` yields
~5e11 ms; the first frame logs 0 instead.

### 7.5.10 Screenshot rendering must happen before the run loop
`AuroraDriveApp.swift:787-790` — headless capture must run synchronously there: it is pure offscreen
`ImageRenderer` work, and if placed in `ContentView.onAppear` there is no window, the view never lays out,
`onAppear` never fires, and the process hangs after engine init — measured **240 s without producing an
image**.

## 7.6 Performance-measurement constraints

### 7.6.1 Absolute timings are not comparable across sessions
`PerfSelfTest.swift:868-874` (read verbatim in the `runTickBench` banner, 2026-10-05 measured lesson):
same binary, same machine, measured **2–2.5× difference** around a few hours of heavy load
(opticalflow p50 2.53 ms → 6.4 ms; `infer.yolopx` 16.4 ms → 22.6 ms), unrelated to code — it is thermal /
contention state. Therefore the fixture is **only** for same-session A/B attribution (same process,
back-to-back, single variable = perception tier), and cross-binary comparison must use
`scripts/paired-ab.sh --metric tick` (alternating paired rounds).

### 7.6.2 Concurrent benchmarking invalidates all timing numbers
`scripts/build-lock.sh:14-17` — measured: 3 agents running `--mc-map-bench --iters 200` at ~85 % CPU each
drove loadavg to 5.15 on 8 cores, at which point any timing figure is incomparable. Hence long tasks
(selftests / benches / gate collection) must hold the build lock, not only `swift build`.

### 7.6.3 Re-reading the environment on a hot path costs 17–32 µs
`AuroraFlags.swift:21-25` — `ProcessInfo.environment[key]` measured at **17.213 µs/call** and
**0.032 ms/call**; `AURORA_OCR_DEBUG` was read three times inside every OCR inference and
`AURORA_DISABLE_OPTICAL_FLOW` every frame.

### 7.6.4 The 45 Hz plan was wrong and must not be retried
`EngineMain.swift:727-733` — user once asked for "720P + 45fps" and tick was raised to 45, which was
**wrong**: 45 Hz budget is 22.2 ms while measured per-frame work is yolopx letterbox 10.5 + ayolom model
10.4 + V2 8.5 + world_model 3 + flow/control/recording 2 ≈ **36.9 ms**, so yolopx alone would consume 94 %
of the budget and the game dropped to **1–2 fps** (user-measured).

### 7.6.5 Changing tick frequency with `.now()` fires an extra tick
`EngineMain.swift:814-830` — measured on a running `DispatchSourceTimer`:
`schedule(deadline: .now(), repeating:)` produced a **0 ms** interval at the switch
(`GAPS: 204,200,197,204,[0],54,50,50,...`). Even with `hold()/release()` idempotence guards and
`appendFrame` back-pressure, the extra tick still posts an async inference `Task` with no idempotence
guard and an extra `refreshHeldKeys()` keyDown round. Chosen fix: always schedule `now + 1/clamped`, i.e.
wait one full period so the switch is a clean "old period → new period" with zero extra ticks; accepted
cost is one period of delay on the first new-cycle tick (`:828-830`).

### 7.6.6 Do not trust "updateConfiguration did not throw"
`CaptureEngine.swift:686-700` — the header states nothing about which fields are live-updatable; frame
rate is a capture throttle that may be frozen at stream creation, so success is an **optimistic
assumption** with a written measurement plan. `UNVERIFIED:` plan not executed in this session.

### 7.6.7 Native Retina capture was 675 MB/s of waste
`CaptureEngine.swift:509-535` — original capture was native 2940×1912 @30fps = **675 MB/s** through the
WindowServer compositor, competing with the game for GPU bandwidth; on a fanless Air M3 this throttled the
machine and the game fell to 1–2 fps, while training stored only 640×360 JPEG and the model consumed
180×320 (24× wasted). Down to 1280-wide @20fps = 85 MB/s; overall **7.9×** reduction.

## 7.7 "Don't overstate / don't fabricate" — documentation discipline encoded in source

### 7.7.1 Comments that overstate behaviour get explicitly corrected in place
`ControlEngine.swift:220-226` — a prior comment's claim ("first call auto-prompts") is marked
"**错的**" and replaced with the measured truth. This project's convention is to keep the wrong statement
visible with a correction date rather than silently rewriting it.

### 7.7.2 Hardcoded developer paths must not exist in product code
`AuroraPaths.swift:69-89` — P-1 (2026-10-04): the source contained
`URL(fileURLWithPath: "/Users/dupi/Desktop/自动驾驶系统")`, i.e. one developer's desktop baked into the
product. Consequences recorded: it fails on any other machine **silently** (it is a fallback candidate,
so failure is invisible), and it is both a privacy problem and a "this only runs on my machine" smell.
Also records a **first failed fix**: replacing it with `homeDirectoryForCurrentUser` was rejected because
that directory contains neither `Package.swift` nor `models/`, i.e. it would be a candidate that can never
match — "兜底候选的价值在于'真的可能命中'，不是'看起来更通用'". Final approach: walk up to 6 levels from the
executable's directory, with the level count justified (`release/ → macosx/ → scratch/ → .build/ → root`
= 4, plus 2 spare).

### 7.7.3 Secrets must never be printed or persisted
`AuroraFlags.swift:146-151` — `AURORA_API_KEY` is annotated "绝不打印、绝不落盘". `PrivilegePill.swift:17-19`
— passwords are entered in-app, never hardcoded (the old implementation hardcoded `"123456"`, which
"发布版必然失效且是安全隐患"), live only in memory, cleared after use, never written to disk or logs, and the
privilege escalation is strictly limited to installing one LaunchDaemon script (`:22-26`).

### 7.7.4 No native authorisation dialogs
`PrivilegePill.swift:9-13` — user requirement (2026-09-23): never use
`do shell script ... with administrator privileges`; repeated system authorisation prompts get the app
flagged by macOS as suspicious behaviour, which is harmful to an open-source project's reputation. Both
legacy entry points are now `@available(*, deprecated)` and immediately return failure:
`BPFSetup.swift:96-99`, `PrioritySetup.swift:53-58`.

### 7.7.5 Web search must fail honestly and must not evade anti-bot measures
`WebSearch.swift:31-36` — compliance red line: no proxy pools (the proxy mentioned is the machine's own
system proxy, verified with `scutil --proxy`, not an evasion tool); read-only public pages; no CAPTCHA
bypass, no simulated login, no forged Referer, no proxy rotation. **Honesty red line**: any failure throws
`WebSearchError` and never returns a placeholder or fabricated result; not-found = `.emptyResults`,
blocked = `.blocked`, timeout = `.timeout`, and the three must be distinguishable in the UI (`:36-37`).
Error taxonomy at `:84` — "每一类都对应一次真实的实测观察，绝不合并成一句'失败了'".
`WebSearch.swift:218-221` — an independent ephemeral `URLSession` is a **performance red line**: it must not
be shared with `captureQueue` or `aurora.quest.ocr`.

### 7.7.6 Self-checks must not fabricate omissions or environment limits
`LLMSelfTest.swift:30` — unverified items are explicitly marked "未验证" and counted as failures or
flagged environment-limited, "绝不编造". `:1288` — print the actual session state and mark environment
limits instead of disguising them as a pass. `:211` — repository red line: source must not hardcode API
keys; the check scans all descriptor headers and baseURLs. `LLMBackend.swift:27` — the only literal that
looks like a key, `"public"`, is the OpenCode Zen catalog term.

### 7.7.7 Brand vs upstream attribution
`ControlEngine.swift:4-16` (2026-10-04) — the game key table (`GameKey`, near `:408`) comes from the
upstream open-source project **MaaNTE**'s actually-used key set. The upstream name is deliberately kept in
**source comments** so any key's presence can be re-verified, but the upstream name must never appear in
brand-visible strings/identifiers; the product brand is `AuroraDrive` (`App/AuroraBrand.swift`).

## 7.8 Mask/display-path pitfalls (engine vs local asymmetry)

### 7.8.1 The mask draw guard depended on a field the protocol never sent
`EngineMain.swift:144-162` — `MaskOverlay` guarded on `metrics.newW > 0`, but the protocol never carried
`newW/newH`, so `EngineClient` rebuilt `LetterboxMetrics` with `newW: 0` → guard permanently false → in
engine mode **no mask cell was drawn**; user symptom "只能看到检测框，看不到可行驶区域和车道线". Local mode
was unaffected because it reads `yolopxEngine.metrics`, which is why **local selftests could never catch
it**. Both fixes were applied (transmit the values; remove the guard's dependence on them).

### 7.8.2 Layout changes require a protocol version bump
`EngineClient.swift:108-115` — v3 added the mask area and moved `pixelsOffset 20480 → 28672`; an old UI
would read mask bytes as pixels (garbled screen). The bump exists so the version guard forces an engine
restart.

### 7.8.3 Staleness must key on "saw a heartbeat", not on "protocol != 0"
`EngineClient.swift:324-332` — an old engine never sends `proto`, so `engineProtocol` stays 0; treating 0
as "unknown, not a mismatch" would miss the exact "new UI × old engine" case the guard exists for
(measured 2026-09-12).

### 7.8.4 YOLOPX does not run in engine mode (by design, with side effects)
`EngineMain.swift:22-34` — `tickEngineMode()` early-returns, and `yolopxEngine.infer(image:)` has exactly
one call site located after that return, so engine mode can never reach it. Consequences: no `da`/`ll`
masks are produced in that process (masks arrive via shm instead), `MaskOverlay` otherwise reads empty
masks, and `yolopxEngine.isDegraded` stays at its initial `true` so `LaneFallback` does not engage.

## 7.9 Logging / resource pitfalls

`EngineMain.swift:55-58` — the engine log had **no cap**; measured 6.16 MB in a 5.71 h session

explicitly a last resort because it loses the "keys released" guarantee
(`EngineClient.swift:1058-1062`). `pauseDriving` additionally stops recording to avoid polluting the
training set with "car stopped, labels still the last AI decision" frames (`:2367-2369`).

## 8.3 Transport layer — what makes it offline-testable

`LLMTransport.swift:8-30`:
- Sends `POST {base}/chat/completions`, non-streaming and SSE streaming;
- SSE line parsing: `data:`, `[DONE]`, `delta.content`, `delta.reasoning_content`,
  `delta.tool_calls` fragment accumulation;
- Image part encoding as data URL, with **long side 1568 px, JPEG 0.8 hard limits**;
- 12 error classes, each corresponding to a real observed upstream body;
- `Task.cancel` → `.cancelled`, leaving no dangling connection.

**All parsing is pure functions** (`:19-23`): `SSEParser`, `LLMError.classify`, `LLMImageEncoder` are
stateless (no `URLSession`, no global state) specifically so `--llm-selftest` can reproduce every
criterion **without network access**.

Performance red lines (`:26-30`): network and parsing run entirely in async context (URLSession's own
delegate queue); **no `DispatchQueue.main` and no `@MainActor` anywhere in the file**; URLSession uses an
independent configuration (`LLMSessionPool`) fully separated from `captureQueue` and the panel's
`llmSession`, so capture frame rate is unaffected by LLM requests (listed as an ABBA comparison item);
reads use `URLSession.bytes(for:)` consumed byte-by-byte with **per-line flush** (minimum
first-token latency) rather than buffering the whole SSE body and splitting it.

Error taxonomy is copied from real responses, one case per observed body (`:32-44`):
`{"type":"error","error":{"type":"FreeTierError"}}` → `.gated`;
`RegionError` → `.regionBlocked`; `ModelDeprecated` + `metadata.replacement` → `.modelDeprecated`;
`ModelDeprecated` without replacement (placeholder `no-replacement-available`) → `.modelNotFound`;
`server_error`/HTTP 5xx → `.upstream`; HTTP 429 (with `Retry-After` header) → `.rateLimited`;
HTTP 401 → `.invalidKey`; `URLError.timedOut` → `.timeout`; DNS/network unreachable → `.network`;
HTTP 200 with empty content (observed on `space-bunny-free`) → `.badResponse`; `Task.cancel` → `.cancelled`.
The comment's framing rule: "逐条照抄、不自行增删分类".

`toolCall` id semantics (`:420`): in SSE fragments the `id` and `function.name` appear **only in the
first** fragment.
`timeout` semantics (`:491-493`): it is an **idle** timeout (`URLSession.timeoutIntervalForRequest` =
maximum gap between two packets), so long streaming answers are not cut mid-stream.
SSE compat mode (`:539`): some key-free endpoints return plain JSON even when `stream=true`.

## 8.4 Chat orchestration — `AgentChatService`

Header (`AgentChatService.swift:4-27`). Why the actor exists: the panel needs "user says something → show
incrementally → get final text", while underneath there is a distributed state of candidate chain ×
transport × health monitoring. Extracting the orchestration into an actor gives three benefits:
the panel need not know candidate/degradation/error-class details (UI cares only about text and a status
string); the orchestration is directly reusable by the CLI selftest (`--llm-selftest` uses the same path
as the panel); network and parsing stay inside the actor so the **main thread is never touched**.

**The bug this file fixed** (`:13-16`): before the rework, `sendUserMessage`'s free-text branch went
through `localReply()` hardcoded canned text, while the real model Q&A function `plainAnswer` existed but
**was never called by any production path**. This file *is* that missing production path.

Constants (`:100-126`):
| constant | value | reason (source) |
|---|---|---|
| `maxHistoryTurns` | **12** | prevent token explosion; overflow turns are dropped (`:107-109`) |
| `maxCandidatesPerRequest` | **4** | "4 是权衡值" — free tiers rate-limit so several escape routes are needed, but dragging one conversation into a dozen round trips is unacceptable and triggers more rate limiting (`:111-115`) |
| `deltaThrottleInterval` | **1/15 s** (≈66 ms) | some channels push one SSE chunk per token, hundreds per answer; a SwiftUI state write per chunk saturates the main thread (`:117-124`) |
| `requestTimeout` | **30 s** | idle-timeout semantics, does not truncate streaming (`:126-128`) |

Degradation semantics (`:19-23`): the candidate chain comes from `LLMHealthMonitor.candidates` and tries
**at most 4**. Full-chain failure **does not throw to the UI**: it returns empty text plus an error
string, and the panel decides to fall back to `localReply` marked 「离线回复」, so the user can tell
"model answered" from "local fallback".

Performance justification is measured and repeated across files (`:25-27`): Vision OCR p50 **33.6 ms** ≈
one entire 30 Hz frame budget, hence the project is extremely main-thread sensitive; therefore network,
SSE parsing and history trimming all run in the actor, and the `onDelta` callback is throttled to ≤15 Hz
by this layer.

## 8.8 Degradation ladder — three tiers, and why the fourth was deleted

## 8.10 Geometric fallbacks — explicitly *not* the main driver

`FallbackGuard.swift:6-30`. Two criteria provided by the user:
- Structure A — ego position: "take the largest detection box at the image centre as the ego position",
  so "is there anything directly ahead" can be answered even with the perception chain down;
- Structure B — box-overlap collision: if the centre box overlaps another vehicle's box, that is
  necessarily an avoidance/collision case, so overlap can drive emergency avoidance as a pure-geometric
  criterion with no model confidence at all.
Positioning discipline is inherited from `LaneFallback`'s four rules (`:26-31`): ① fail-open — if input is
untrustworthy (too few boxes / abnormal size) return nil and the caller keeps its original decision;
② bounded output — steering and brake are hard-limited, never full throttle; ③ multi-frame confirmation —
the same verdict must hold N consecutive frames; ④ discard sudden changes — a single anomalous frame does
not change the conclusion.

`EgoBoxFilter.swift:8-30` solves the mirror-image problem: in third person the model always boxes **the
player's own car**. Its historical incident is severe and worth quoting: ego box + the front car's box
were judged by the geometric fallback as "box overlap = collision" → output `brake 0.8` → and in this game
`brake` **is the S key, which is also reverse** → so the takeover state kept giving the user braking and
reversing (`:12-17`). The decision was made by **area**, not position, because the user stated the camera
wanders ("官方为了帅车可能会到处跑……甚至可以到最远端"), and a 10,000-real-frame measurement settled it
(`:20-28`):

| rule | own-car masking success | false-hit on real cars / frame |
|---|---|---|
| area > 2 % | **98.0 %** | 0.08 |
| area > 3 % | 97.8 % | 0.05 |
| position only (centre band + lower area) | 93.2 % | 0.06 |
| area > 3 % AND position | 93.0 % | 0.03 |

The shipped rule is the area > 2 % row (`:24`), i.e. the highest success rate was accepted together with
its slightly higher false-hit rate.

## 8.11 Segment handover — four AND conditions

`DriveSegmentController.swift:8-30` records the user's 2026-09-30 required flow: ① car approaches a map
waypoint (corner) → enter **map segment**, use map guidance to steer through; ② after the turn the
heading is skewed → **must straighten** using the map road direction; ③ after straightening, hand over to
**model/vision** for lane keeping; ④ the handover must be **confirmed to really succeed**, all four
conditions satisfied, otherwise stay in place and drive conservatively.

Verbatim requirement (`:14-17`): "判断成功标准是在那条道路里…而且已经向前行驶一段距离…而且都能拟合在道路里…
并且模型已经能正常识别到车道线，才能算准确性". The four AND conditions (`:18-22`):
1. position falls inside the target road corridor (`RoadMapPrior.isOnRoad`);
2. has actually travelled some distance (network-locate coordinate integration);
3. fitting stays inside the road for several consecutive frames (vision confidence + no jump);
4. vision can actually recognise lane lines (laneMask valid).
Why not hand over immediately after the turn (`:24-26`): at that instant the heading is still skewed and
lane lines may not be recognised yet; handing over then most likely yields no trustworthy direction and
the car swerves. Safety boundary (`:28-30`): this controller only decides **which control source** to use
and performs **no limiting**.

## 9.1 YOLOPX — the core perception asset

`YolopxEngine.swift:5-31`.
Model: `models/yolopx/yolopx3_pal8_detfp.mlmodelc` (first candidate, 8-bit palette, det precision 100 %);
candidates listed in `modelCandidates`, each probe-loaded and the next tried on failure (`:8-10`).
Exported by `tools/yolopx/export_yolopx_coreml.py`, parity-verified by
`tools/yolopx/verify_yolopx_coreml.py` (`:10-11`).

Measured output shapes (`:13-16`):
```
det  [1, 8400, 6]      cx, cy, w, h, obj_conf, cls_conf   (640-input pixel coords, NOT NMS'd)
da   [1, 2, 640, 640]  drivable-area binary logits
ll   [1, 2, 640, 640]  lane-line binary logits
```

**Three differences from `YoloEngine`(yolo26s) where any mistake fails silently** (`:18-27`):
1. Input is **letterbox** (aspect-preserving scale + 114 grey padding), **not** whole-frame stretch.
   The model was trained on BDD100K with letterbox; feeding a stretched image changes object aspect
   ratios and distorts **both** boxes and masks.
2. The `det` head is YOLOX (anchor-free) and **output is not NMS'd**; coordinates are `(cx,cy,w,h)`.
   yolo26s is NMS-free end-to-end and directly emits `(x1,y1,x2,y2)`, so this engine must do its own
   coordinate transform + NMS + grey-padding box rejection.
3. `nc = 1` — only the "car" class, all mapped to `Detection.Label.car`.

Coexistence guarantee (`:29-31`): this engine loads independently with independent buffers, does not touch
the incumbent detection chain, and can be disabled to roll back with zero impact.

## 9.2 yolo26s — a different contract, easy to confuse with YOLOPX

`YoloEngine.swift:5-25`. Model `models/yolo26s.mlmodelc` (YOLOv26s, **NMS-free end-to-end**), exported by

## 9.4 Speed OCR — dual model, three layers, honest degradation

`SpeedOCRReader.swift:4-30`. Architecture (2026-09 dual-model rework; template matching removed):
- **primary**: PP-OCRv6 full-line inference — ROI slice → grey → bilinear to 48×136 → replicate to 3
  channels → CTC decode → take the last 3 digits → confidence threshold (`:6-8`);
- **fallback**: per-digit CNN (`speed_digit_cnn_v4`) — `cropSlots` cuts 3 slots → each 90×50 → softmax per
  digit (`:9-10`);
- **switching rule** (`:11-14`): only a system-level runtime fault (inference throw / missing output)
  degrades to CNN **within the same frame** and writes `engineNotice` (orange banner in UI + orange engine
  label beside the speed). "Can't read" business diagnostics (low foreground / low confidence / short digit
  string) are **not** treated as faults and do not trigger switching. Both models failing to load writes
  `errorMessage`/`engineNotice` at `init` — never silent.
- history (`:15-17`): the earlier glyph-template matching (`speed_glyphs.json` + 0–300 enumeration
  residual) was fully replaced and deleted; `cropSlots` slot constants are still used by the CNN path.

recorded:
- generic Vision OCR has a high misread rate on the HUD's hollow digits (`"000"` → `"NTO0U"`);

- the finetuned PP-OCRv6 = official general pretraining representation + project-scene alignment;
  frozen test set (5077 images from unseen clips) **99.9803 %**; strongest generalisation
  (report referenced as `PPOCRV6_FINETUNE_REPORT.md`).

Invalid-frame pre-check (`:32-35`): loading/view-misaligned frames contain no speedometer; an
Otsu-foreground ratio below threshold marks the frame invalid and it never enters inference (preventing

## 9.6 Optical flow — OpenCV DIS, chosen by measurement

`OpticalFlowBridge.swift:4-30`. Problem statement: YOLOPX single inference is measured ≈60 ms
(148 GFLOPs against measured ANE peak 9.26 TFLOPS ⇒ 16 ms physical floor, current efficiency ≈26 %), so it
cannot reach the main loop rate; the intermediate frames must not be blind.

Same-batch ABBA measurement at 640×640 on this machine (`:13-19`), driven by the user's 「光流 ≤5ms」 red
line:
```
Apple VTOpticalFlow (VideoToolbox hardware)   10.28 ms   ✗
Vision VNGenerateOpticalFlow                   27.43 ms   ✗
OpenCV DISOpticalFlow ULTRAFAST                 1.91 ms   ✓
same, restricted to 1 core (extreme case)       3.78 ms   ✓
```
Official hardware paths are **5–14× slower**. DIS is the formal CVPR 2016 algorithm built into OpenCV's
`video` module, not custom code (`:19-21`). Accuracy (`:23`): displacement error **0.07 px**
(measured `dx = 1.930` vs ground truth 2.000 on a natural-texture image).

Threading (`:25-30`): the C layer `ad_dis_compute` is **not** thread-safe — the same ctx must not be called
concurrently — so the class serialises `compute` behind a private lock and permits calls from any thread
while serialising internally. `Vendor/OpenCVFlow/README.md` referenced for details; the build wiring
(`Package.swift:59-71`) and the static-link pitfalls are in SEC-01 §1.3.3 / SEC-02.

## 9.7 Motion prediction — α-β filter instead of Kalman

`MotionPredictor.swift:1-30`. The stale-box problem (`:5-11`): between two inferences the boxes are
**completely static** while targets move, so the car decides on stale positions.
Solution shape (user's proposal, `:13-18`): YOLOPX low-rate ground truth (~15 Hz) + optical flow
inter-frame motion vectors (measured p95 **3.7 ms**) + an α-β filter maintaining per-target position and
velocity + extrapolation between frames with correction when new observations arrive.

**Why α-β rather than Kalman** (`:20-27`), stated as an analytic argument: α-β is Kalman's closed-form
solution under a "constant-velocity model + steady-state gain". Covariance matrices are unnecessary here
because the motion model is simple (near-constant velocity, lane scenes), observation noise is relatively
stable (YOLO box jitter is measurable), and it must run every frame at 30 Hz where α-β costs two
multiply-adds versus matrix operations.

Design discipline (`:29-33`, same family as `LaneFallback`): ① fail-open — if flow is unavailable, ground
truth is stale, or a target is lost past timeout, **do not extrapolate**, return the un-predicted original
detection, "绝不编造运动"; ② predicted results are explicitly marked `isPredicted = true` so the decision
layer can down-weight them.

## 9.8 Ego motion — the missing consumer that was found by static audit

`EgoMotionModel.swift:4-30`. This file exists because of a **dead-data** finding: `OpticalFlowBridge` had
long computed `dx/dy/divergence` that had **zero readers repo-wide** (2026-09-30 static audit). Its stated
design purpose — "cross-check global motion direction" — had **never been implemented**: interface
reserved, data fed in, consumer never wired (`:7-12`). This file is that missing consumer: it turns
flow-estimated **ego motion** into a usable criterion for validating `MotionPredictor`'s target velocities
computed from box differencing (`:10-12`).

Why the model is **radial**, not translational (`:14-28`): `MotionPredictor`'s velocity comes from α-β
updates on box differences, which has an inherent weakness — when a **target is static and the ego is
moving**, it misinterprets "my own motion" as "the target is moving". The intuitive fix (subtract flow's
global median translation `dx/dy`) **is wrong**:
- ego **lateral** movement → whole image pans → `dx` describes it ✓
- ego **forward** movement → image content expands **radially toward the vanishing point** → not a
  translation ✗
When moving forward, targets near the centre barely move while edge targets fly outward — exactly what
`divergence` measures. Hence a radial expansion field is required.
Geometry (`:24-30`): vanishing point at image centre (valid when the optical axis is horizontal); for a
point at radius vector `r = (px − cx, py − cy)`, ego-motion displacement is
`u_ego = forwardRate · r_x`, `v_ego = forwardRate · r_y`.

## 9.9 Road prior — bitmap prior, heading only, never lateral

## 9.10 Corner waypoints — v1's three mistakes

`RoadCornerGuide.swift:4-30`. Why waypoints rather than pure vision (`:6-10`): lane-line vision frequently
fails or is ambiguous at corners/junctions, whereas the map is a **fixed** prior that knows where the road
bends; the user explicitly required map-guided steering where turns belong.

**Three key properties of v2, where v1 was wrong on all three and the user said so on 2026-09-30
(`:12-22`)**:
1. **Dense** — one point every ~23 m along the bend (**952 positions**), not one point per corner;
   otherwise entering from another position or lane would miss it.
2. **Bidirectional** — each position produces two records (one per approach direction, with opposite
   `turnSign`), because a bend can be driven both ways and reverse entry reverses left/right. Matching must
   select the record whose direction agrees with the ego's current heading, otherwise the wheel is turned
   the wrong way.
3. Junction data is retained (`branchCount ≥ 3`, recording branch directions) but **turning decisions do
   not yet cover junctions** (corners first); it is used only for logging and future extension.

Division of labour with the prior (`:24-29`): `RoadMapPrior` = bitmap prior (2048² road grid) →
`isOnRoad` / `roadHeadingCandidates`; `RoadCornerGuide` = waypoint set (discrete corner records) →
`cornerAhead` / `steerForCorner`. The waypoint set answers "is there a known corner ahead and which way",
the bitmap answers "am I on the road right now".

## 9.12 Confidence estimator — the dead-model equilibrium bug

`ConfidenceEstimator.swift:4-30`. E2E outputs no confidence, so this heuristic estimates it from output
history plus the current image; the score in [0,1] feeds the degradation state machine (`:5-6`).
Gating + three fused signals (`:8-22`):
0. **Link-liveness gate** — model not loaded / no result / result stale ⇒ confidence 0. Reason recorded
   (`:9-11`): the old formula computed **0.70** for a dead E2E that always outputs `idle`/constant values,
   which is above the degradation threshold 0.65, so a **dead model stayed in the end-to-end tier forever**.
1. Output consistency — smaller steer jitter over the last N frames is more trustworthy (stable model).
2. Steer extremeness — steer pinned at the limit for a long time (`|steer| > 0.95`) is treated as
   degeneration. Throttle/brake at the edge is normal driving behaviour and no longer penalised — fixing
   the defect where "healthy cruise sat at exactly 0.70, could never reach the 0.75 recovery threshold, and
   stayed stuck in the rule tier" (`:14-17`). Stable output is **not** judged as frozen, because on a
   straight road the model is *supposed* to be stable (`:17-18`).
3. Frame validity — abnormal brightness (all black / all white) ⇒ low confidence.
Design (`:24-28`): sliding window of the last N outputs with O(1) update; three signals weighted, weights
adjustable; main-thread only (synchronous with tick).

## 9.13 Lane fallback — the four disciplines

`LaneFallback.swift:4-24`. Positioning statement: this is **fallback, not main driver**; every principle
serves one goal — the fallback must never itself become the accident source (`:8-9`):
1. **fail-open** — if any input is untrustworthy (degraded / empty mask / size mismatch) return nil
   immediately and the caller keeps its original decision; never "guess a direction" (`:10-11`);
2. **bounded output** — steer correction hard-clamped (±`maxSteer`), throttle may only decrease, never
   full throttle, because the fallback cannot judge whether acceleration is safe (`:12-14`);
3. **multi-frame confirmation** — the same directional deviation must hold N consecutive frames before
   being adopted, avoiding direction flapping from single-frame mask jitter (`:15-16`);
4. **discard sudden changes** — inter-frame deviation jumps beyond a threshold are treated as anomalous
   frames and the previous valid value is retained (`:17-18`).
Pure functional style (same as `RuleController`): no side effects, unit-testable; the only internal state is
a stability counter fed per frame by the caller (`:20-22`).

`Perception/LaneBridge.swift:168-176` supplies the same fail-open red line for mask geometry: `isUsable`
only checks "dimensions positive + cells long enough" — deliberately **not** a strict `== 160` gate, which
is `LaneFallback`'s job (its guard ②). The stated reason for still needing this check: if `cells` is shorter
than `width*height`, `LaneFallback` would later `SIGTRAP`, so it must be intercepted early.

`Perception/LaneExtrapolator.swift:57` restates it for lanes themselves: on a malformed mask return `.empty`
and **never fabricate lane lines**; the malformed-input guard shares its origin with `MaskGrid.at`.

## 9.16 Pitfalls summary for this subsystem

1. **YOLOPX letterbox ≠ yolo26s stretch** — feeding the wrong preprocessor silently distorts boxes and
   masks (`YolopxEngine.swift:18-22`).
2. **YOLOPX `det` is not NMS'd and is `(cx,cy,w,h)`** — unlike yolo26s which is NMS-free `(x1,y1,x2,y2)`
   (`:23-25`).
3. **CoreML feature name `lane`, not `lane_mask`**; and never name an input `state`
   (`InferenceEngineV2.swift:32-42`).
4. **`OpticalFlowBridge`'s `dx/dy/divergence` had zero readers until `EgoMotionModel` was written** — a
   dead-data class of bug that static audit found, not tests (`EgoMotionModel.swift:7-12`).
5. **Ego motion must be radial, not translational** — subtracting global median `dx/dy` is wrong for
   forward motion (`EgoMotionModel.swift:18-28`).
6. **Road prior gives heading only** — using it for lateral offset mis-steers by metres
   (`RoadMapPrior.swift:10-12`).
7. **Corner matching must respect ego heading** — otherwise the wheel turns the wrong way on bidirectional
   records (`RoadCornerGuide.swift:16-19`).
8. **A dead E2E model scored 0.70** — above the 0.65 degradation threshold, so it never degraded; fixed by
   the liveness gate (`ConfidenceEstimator.swift:9-11`).
9. **A healthy cruise scored exactly 0.70** — could never reach the 0.75 recovery threshold and stayed
   stuck in the rule tier (`ConfidenceEstimator.swift:14-17`).
10. **Double-model switching must trigger only on system faults, not on "can't read"** — otherwise normal
    low-confidence frames churn the engines (`SpeedOCRReader.swift:11-14`).
11. **θ₀ = 332.0° is a calibrated constant, not a guess** — omitting it makes every heading off by a fixed
    rotation (`PointerHeadingReader.swift:20-26`).
12. **Engine-mode blindness**: local selftests validate a different perception path than production engine
    mode (`EngineMain.swift:22-34`).

     (`:7588-7596`): the UI process unconditionally calls `yolopxEngine.loadIfNeeded()`, so in `ayolom` tier
     `isDegraded` is permanently true (da=0 cells, ll=0 cells; engine log 121/121). The UI instance would
     `enterSprint()` locally → `takeoverActive=true`, while the engine heartbeat reports the engine's real
     state (possibly false) and `syncFromEngine` writes false back → **the banner flickers on and off**.
     Fix: in engine mode the UI instance is a **display mirror driven by heartbeat only**; only UI-local mode
     (no engine attached) feeds locally. `tickGap` is gated together for semantic clarity (`:7598-7599`).
   - `isDegraded` is only fed when `isLoaded` (`:7602-7604`): before load `isDegraded` defaults to true
     ("no model = degraded"), but that is not "degenerated while running" and must not trigger takeover.
3. **Perf instrumentation start** (`:7607-7614`): `var perfT = PerfBus.stamp()`; `tick.total` is settled with
   `defer { PerfBus.mark("tick.total", from: perfStart) }` **specifically so every return path**
   (engine mode / standby / normal driving) is counted without restructuring branches. When `AURORA_PERF`
   is unset, `stamp()` returns 0 and every `lap` short-circuits, so the whole chain costs one static bool
   per segment (`:7608-7609`).
4. **Even/odd frame phase split** (`:7616-7637`), placed "at the very front of tick" so that the
   `inferFast` path and the slow driving path **share one phase counter** and stay in the same frequency and
   phase (`:7617-7618`):
   - `detectGateA` = yolopx three-in-one (`det/da/ll`) on even frames;
   - `detectGateB` = yolo26s (detection only) on odd frames;
   - rationale (`:7620-7622`): both stopping on the same frame creates "vacuum frames"; offsetting means at
     least one net produces ground truth every frame and boxes stay continuous.
   - **2026-10-07 user decision: the `ayolom` family is not decimated** (`:7624-7629`). The E4 original
     unconditionally gated `yolopxEngine.infer`, which also halved the *default* ayolom small model to
     15 Hz — but ayolom is measured p50 **10.4 ms** on ANE (95.9 Hz; only 31 % of a 30 Hz budget), so it
     neither needs nor deserves decimation. Hence `detectGateA` is **always true for ayolom**
     (`:7637`: `decimateFallback || isAyolom || parityEven`) and the offset applies only to legacy-tier
     yolopx + yolo26s.
   - rollback switch: `AURORA_DETECT_DECIMATE=1` makes both gates always true (`:7631`, `:7634`).
5. **yolo26s tier gate** (`:7639-7642+`): before 2026-10-19 yolo26s had **no** tier gate, so in A-model tier
   it still inferred every other frame.

Consequences that must be stated plainly: tick frequency is not "the model rate" — the tick rate is
`EngineMain.engineTickHz` (15 Hz now, SEC-03 §3.4), and within a tick the *perception nets* are further
gated by tier and by frame parity. Any timing measurement that assumes "one inference per tick" is wrong in
legacy tier and wrong for yolo26s.

## 10.6 Map wiring — coordinate transform and the invisible-matrix trap

`MapWiring.swift:1-13` gives the data chain: `CoordinateCapture` packet capture → world coords (UE5 cm) →
`worldToMapPixel()` calibrated transform → map pixels (**13056×13056**) → viewport-normalised coords →
minimap/bigmap render. All of these are **derived quantities computed on the fly, never persisted or cached**
— "定位一变地图立刻跟着动" (`:11`). When the locator is not locked, `mapPixelX/Y` return the map centre
(`:39-46`) and the caller decides display based on `locatorFound` (`:12`). The pure math functions are
`nonisolated` because callers may not be on the main thread (`:24-27`, `:29`, `:34`).

**The documented near-miss** (`MapWiring.swift:52-78`): the inverse transform must **not** reuse
`CoordinateTransform.invert` (`NetworkLocator.swift:55`) because the two are **not the same matrix**:
- `MapWiring.worldToMapPixelX`: `mapX = A·wx + B·wy + TX`
- `CoordinateTransform.apply`:    `x' = a·x − b·y + tx`
The **B term has opposite sign** (`+B` vs `−b`). Numerically `B = 5.69e-08`, which for coordinates of order
1e5 differs by only ~**0.006 px** — invisible to the eye. Therefore taking the wrong inverse **does not
reveal itself**; it merely shifts every click-set destination by a tiny, constant amount. Called out as
"看不见的错"的典型：量小、恒定、永远不崩. Hence the inverse is solved strictly from MapWiring's own equations
and paired with a round-trip selftest (`--route-selftest` asserts deviation < 0.5 px).
Derivation recorded in-source (`:70-78`):
```
mapX = A·wx + B·wy + TX ;  mapY = A·wy − B·wx + TY
dx = mapX − TX ; dy = mapY − TY
[dx]   [ A   B ] [wx]
[dy] = [−B   A ] [wy]      det = A² + B²  (A≠0 always invertible)
wx = (A·dx − B·dy) / det ;  wy = (B·dx + A·dy) / det
```

### 11.1.2 Frame-rate contract — a raise, not a warning

```
src/dataset_v3.py:86   EXPECTED_FPS = 15
src/dataset_v3.py:89   FPS_TOLERANCE = 0.15
```
Reasoning recorded at `:80-85`: the deployment tick is 15 Hz (citing `EngineMain.swift:709`), and V3's
24-frame window is designed at 15 Hz = 1.6 s (`model_v3.py:274`). Recording at another rate desynchronises
"how long 24 frames cover" from deployment, so the temporal dynamics the model learns have the wrong scale —
at 10 fps, 24 frames span 2.4 s and the motion looks slower.

Validation (`:427-450`): if `expected_fps is None` or fewer than 2 rows, skip. Parse `t_sec` (a non-numeric
value raises with the clip name). Compute positive deltas only, take the **median**, then
`actual_fps = 1.0/median_dt`; if `abs(actual_fps - expected)/expected > FPS_TOLERANCE` → `ValueError` whose
message quotes the measured fps, the assumed fps, the tolerance, the design rationale, and the remedy
(`--fps 15` re-record, or pass `expected_fps=None` to disable deliberately).
Accepted band is therefore **12.75–17.25 fps**.

## 11.2 The 8 output heads and their derived labels

Head names enumerated in `src/dataset_v3.py:15-18` (and the model's forward dict, see §11.4):
```
handbrake    [B,1] 0/1   (= shift)
brake        [B,1] 0/1   (= space)
super_brake  [B,1] 0/1   (= shift ∧ space)
ultimate     [B,1] 0/1   (= shift ∧ space ∧ s)
```
**Combination consistency is validated, not assumed** (`:183-195`): if `super_brake != (shift and space)`
the loader raises naming the row and all three values; likewise
`ultimate != (shift and space and s)`. This is why those two columns are stored rather than recomputed — they
are redundant by construction, so any disagreement proves corruption.

Key semantics (user-authoritative, cross-referenced from `KeyboardMonitor.swift:111-112` and the recorder's
CSV): Shift = handbrake; Space = normal brake; Shift+Space short press = super brake; long press = ultimate
brake; S alone = reverse; S during ultimate braking = anti-rollover. `dataset_v3` encodes the derived heads
as `handbrake=shift`, `brake=space`, `super_brake=shift∧space`, `ultimate=shift∧space∧s` — i.e. **the safety
heads are Boolean functions of the three atomic keys**, which is exactly why recording raw keys is
sufficient and recording continuous values is not needed.

`intent_from_keys(w,a,s,d,shift,space)` at `:160-171` provides the intent-head label.
`risk` labels derive from the same keys (`:231-233`): `ultimate_brake` (Shift+Space+S) → **1.0** (highest
risk, actively limit-braking); `super_brake` (Shift+Space) → **0.8**; `space` or `s` (normal brake /
reverse) → **0.5**.

## 11.3 `model_v3` — structure and its paper provenance

`src/model_v3.py:1-2` — the file is marked `[TRAINING-ONLY]`: used only for offline training/export; at
runtime CoreML / the C++ inference side executes it. Header (`:3-8`) declares it the integrated
implementation of the three `docs/v3-design/` design documents (`01-backbone.md`, `02-temporal.md`,
`03-output-head.md`).

**Paper-derived mechanisms that must be preserved verbatim** (`:11-30`), from
`docs/v3-design/papers/state_aware.txt` (arXiv:2310.20650), *Addressing Limitations of State-Aware Imitation
Learning for Autonomous Driving*:
1. **State Token Propagation** (§IV.A, `:173-207`) — the ego state (`t−1` steer/throttle/brake/speed) becomes
   a special Transformer token, role-equivalent to ViT's CLS token (paper `:193`), but its content comes from
   **measured values**, not learned. Between adjacent stages **only this one state token is propagated**
   (paper `:179-181`), not the visual tokens — so every stage can "look at the image again with a new
   question".
2. **Pixel-State Attention** (§IV.B, `:208-245`) — the conv backbone's feature map is flattened into N visual
   tokens, the state token is prepended, and all do self-attention together, so every pixel attends to other
   pixels **and** to the vehicle state (paper `:236-237`). This is both the multi-stage information path and
   the source of built-in interpretability.
3. Coarse-to-fine multi-stage (§III / §IV.D), continuing past the read window.

`V3Config` at `:329-330`; `num_hi_frames: int = NUM_HI_FRAMES` (`:342`); total-frame property
`num_hi_frames + num_lo_frames` (`:384`); validation that `num_hi_frames ≥ 1` and `num_lo_frames ≥ 0`
(`:438-439`).
Reparameterization: `def reparameterize()` (`:506`, `:1103`) folds training-time branches into the deployment

## 11.4 `train_v3` — supervision is raw keys, and model selection is macro recall

`src/train_v3.py:4-9` states the design premise in terms of the user's requirement (「模型直接输出标签，不要油门」):
V3's supervision target **is the raw keys** (`w/a/s/d/shift/space`) expanded into 8 heads; the data flow is
`controls.csv(pure keys) → dataset_v3 → 8 head targets → V3Loss`. **No continuous
(steer/throttle/brake)-to-key conversion exists anywhere in this file.**

Relationship to v2 (`:11-19`): reuses `build_adamw_optimizer` (no weight decay on BN/bias) and
`CosineWithWarmup` from `train_v2.py` — existing implementations, not re-invented — but does **not** reuse
the v2 data pipeline, because v2 reads continuous values and v3 reads pure keys; the target semantics differ.

**CCM is explicitly disabled during training** (`:21-29`), with the measured evidence quoted in-source:
`V3Model.forward` returns keys `['brake','confidence','handbrake','horizontal','intent','risk','super_brake',
'ultimate','vertical']` — **no `ccm`** — and `V3Loss` computes the CCM term only when both `ccm_pred` and
`ccm_target` are passed, otherwise it **silently skips** (no error, no trace). Therefore training passes
`enable_ccm=False` explicitly so that "CCM not enabled" is a **stated decision** rather than a silently
skipped configuration. Enabling requires wiring a ccm output into forward first (a training-only branch).

**Model selection must not use overall accuracy** (`:30-35`), with the measured justification: a trivial
"always output W" solution already scores **80.8 %** overall accuracy while never predicting class S even
once. Therefore the script selects the epoch by **macro recall** (arithmetic mean of per-class recall)
and logs per-class recall plus the confusion-matrix diagonal.

Usage (`:37-44`): inspect distribution first (`python3 src/dataset_v3.py --stats data/raw_clips`) to decide
class weights rather than hand-filling them; then
`python3 src/train_v3.py --clips data/raw_clips --epochs 30 --batch-size 8`; a smoke run uses 2 epochs and a
small batch.

## 11.8 Training-pipeline pitfalls

1. **Wrong class name**: `V3KeyDataset`, not `V3ClipDataset` (`dataset_v3.py:257`) — importing the wrong
   symbol fails at import time.
2. **Wrong FPS is fatal, not cosmetic**: `expected_fps` mismatch raises and rejects the whole clip
   (`:442-448`); the recorder's 15 Hz gate exists to satisfy this (SEC-05 §5.8).
3. **Empty `speed_kmh` is meaningful**: empty ⇒ `speed_valid=0`; `0` would be read as a true zero speed
   (`LeanRecordEngine.swift:489-491`).
4. **`skip_all_zero` can empty the dataset** and raises rather than returning zero samples (`:400`).
5. **Derived brake heads are validated against atomic keys**, so corruption surfaces as a `ValueError` with
   all three values printed (`:183-195`).
6. **CCM silently does nothing unless enabled** — `V3Loss` skips it without error when the predict/target pair
   is absent (`train_v3.py:21-29`).
7. **Overall accuracy is a trap**: a constant-W model scores 80.8 % (`train_v3.py:30-33`) — select on macro
   recall.
8. **`lane`/`dets` are zero-filled**, so those branches cannot learn from current recordings
   (`dataset_v3.py:275-277`) — a stated open item, not a hidden one.
9. **CoreML feature names ≠ Python parameter names**, and `state` is renamed by coremltools
   (`InferenceEngineV2.swift:32-42`).
10. **Export script wins over model source** for the on-disk contract (`InferenceEngineV2.swift:14-17`).
11. **`config.py` is simulation config**, not vehicle runtime parameters — do not quote its numbers as
    deployed behaviour.

## 12.3 Traffic is bursty — NIC probing takes many rounds

## 12.4 Locate freshness — four tiers, and why 18 s

`CoordinateCapture.swift:1738` defines `enum PoseTier` (cases `:1739-1742`):
```
case live      // ≤ liveWindow (default 18s)  : full function
case recent    // ≤ recentWindow (default 40s ≈ 2–3 periods) : UI normal, decision down-weighted
case stale     // ≤ staleWindow (default 90s) : UI marks "stale", decisions do not trust it
case lost      // > staleWindow : UI marks "no locate"
```
Thresholds: `poseFreshWindow = 18.0` (`:848`), `poseRecentWindow = 40.0` (`:1747`, ≈2.6 × 15 s periods),
`poseStaleWindow = 90.0` (≈6 periods). `.live` is **exactly** the pre-existing `poseFreshWindow` so old
behaviour is preserved verbatim while two wider tiers are added (`:1747-1748`).

Why 18 s and not 12 s (`:818`, `:842-846`): the game's **real coordinate period is 15 s** (2026-09-30 final
measurement), so a 12 s window expired on every cycle and produced **location flicker**; 18 s = 15 s period +
3 s margin, and 18 s is only 3 s more than 15 s so the "stale position" perception impact is negligible.
The tier system removed the flicker without creating "ghost positions", because `stale`/`lost` are
down-weighted, `lost` is explicitly labelled "no locate" in the UI, and the `hasRecentTraffic` pre-gate
remains (`:1735-1738`).

API: `readWithTier(live:recent:stale:) -> (tier, pose?, ageSeconds?)` (`:1753`), lock-protected, returning
`.lost` with nil pose only when there has never been a sample.

## 12.6 Key semantics — the user-authoritative contract

Key codes (`ControlEngine.swift:48-53`):
```
throttle   = 13   // W
brake      = 1    // S
steerLeft  = 0    // A
steerRight = 2    // D
handbrake  = 49   // Space
boost      = 56   // Left Shift
```
`Action` enum (`:34-40`): `throttle`, `brake`, `steerLeft`, `steerRight`, `handbrake` (+ boost mapping).
Semantics (user-confirmed, recorded at `KeyboardMonitor.swift:111-112` and encoded in `dataset_v3`):
| gesture | meaning |
|---|---|
| Shift | **handbrake** |
| Space | normal brake |
| Shift+Space (short press) | super brake |
| Shift+Space (long press) | ultimate brake |
| S alone | reverse |
| S during ultimate braking | anti-rollover |
This table is why the training targets are Boolean functions of atomic keys
(`dataset_v3.py:15-18`, SEC-11 §11.2) — `handbrake=shift`, `brake=space`, `super_brake=shift∧space`,
`ultimate=shift∧space∧s`.
**The dangerous overlap**: in this game `brake` **is the S key, which is also reverse** — recorded as the
cause of a real incident where the ego-box fallback output `brake 0.8` and the car kept braking *and*
reversing (SEC-08 §8.10, `EgoBoxFilter.swift:12-17`).

## 12.7 Injection layer — three independent constraints

`ControlEngine.swift:183-198`: the event source must be `.hidSystemState`, and the tap `.cghidEventTap`.
Measured basis: the target game's input layer reads only the HID system state layer;
`.combinedSessionState` is ignored by the game even though system UI reacts; `.privateState` is banned.
`ControlEngine.swift:504-507`: `autorepeat` must stay `false` because the game ignores auto-repeat events and
only accepts "new key down".
`MouseController.swift:10-19`: identical strategy — `CGEventSource(stateID: .hidSystemState)` and
`.cghidEventTap` — with a coordinate warning recorded from a near-miss:
- CGEvent mouse coordinates are **global display coordinates in points**, origin at the **main display's
  top-left**, y growing downward — same orientation as screenshot pixels, differing only by
  `backingScaleFactor` (2× on Retina);
- `NSScreen.frame` uses **bottom-left AppKit coordinates** — the two must not be mixed;
- conversion: `CGEvent point = screenshot pixel / backingScaleFactor` (main display case).

Hold/press/release bookkeeping (`:361-390`): `press` posts down then up; `hold` is idempotent via
`guard !heldKeys.contains(keyCode)` before posting down and inserting; `release` only posts up if the key is
in `heldKeys`; every entry point guards `hasAccessibilityPermission` (`:357`, `:371`).
`releaseAll()` (`:436-443`) unconditionally posts key-up for **all six mapped keys** and clears the set — it is
deliberately not conditional, because it also carries the safety duty of clearing **system-level stuck keys
left by a previously crashed process** (`:468-471`). The throttled per-tick variant `releaseAllIfNeeded()`
(`:486-496`) skips redundant sweeps when nothing is held and a sweep happened within the last second, without
changing `releaseAll` semantics (SEC-07 §7.4.6).

## 12.9 Game Mode suppression — measured, and countered in two ways

`GameModeDefender.swift:4-18`. Measured 2026-09-13: after the game enters full-screen Game Mode, AuroraDrive's
auxiliary frame rate holds ~30 fps for about **40 s**, then `gamepolicyd` suppresses it to single digits. The
lesson recorded: a one-off setup at launch (nice value, activity assertion) is **not enough** — it is
progressively suppressed.
Two complementary measures:
1. **Silent audio (the `audible` dimension)** (`:8-15`): Apple documents "it isn't audible" as one of App
   Nap's criteria, and audio playback is an independent exemption; Game Mode plausibly uses the same
   dimension. The CoreAudio audio thread runs at **realtime priority without root**, which bypasses the
   earlier blocker "realtime threads need root". Implemented as an `AudioQueue` loop emitting zero samples;
   it needs no `NSApplication`, so the **engine process can use it too**.
2. **Persistent re-assertion** (`:16-18`): re-claim every 3 s rather than once.
Engagement: `GameModeDefender.shared.start()` at `EngineMain.swift:1157-1159`, with the stated reason that the
engine is the process doing detection and therefore needs the audible dimension and continuous re-assertion
most.
Related: `ProcessInfo.beginActivity([.latencyCritical, .userInteractive, .idleSystemSleepDisabled])` plus
`setpriority(PRIO_PROCESS, 0, -20)` in the engine (`EngineMain.swift:1161-1168`, SEC-03 §3.6).

## 12.10 Privilege escalation — in-app only, one action only

## 12.11 Safety invariants — consolidated

Because this list is the part a maintainer must never break, it is restated here as one block with pointers:

1. **Every exit path releases all keys before exiting**; SIGKILL is a last resort precisely because it loses
   that guarantee. `EngineMain.swift:20`, `:2377-2394`; `EngineClient.swift:1058-1062`.
2. **Observe-only (`AURORA_OBSERVE_ONLY=1`) refuses all injection** at three independent layers: engine TCC
   predicate narrowed to screen-only (`EngineMain.swift:1132-1138`), UI `controlDisabled=true`
   (`AuroraDriveApp.swift:6886-6896`), and `ToolRegistry` guard ① (`ToolRegistry.swift:26-27`, `:405`).
   Even if injection were attempted, `ControlEngine.hold()`'s permission guard returns early
   (`EngineMain.swift:1136-1138`).
3. **No injection without Accessibility permission**, and the permission query must never prompt on the hot
   path (`ControlEngine.swift:210-232`, SEC-07 §7.4.5).
4. **Handover/engine restart is refused while driving** — losing the engine mid-drive is more dangerous than a
   protocol mismatch (`EngineClient.swift:344`; the handover pair in SEC-03 §3.9).
5. **Recorded keys must be released, not inferred**: the engine has no `NSEvent` source, so it uses the
   UI-forwarded `remoteKeyMask` (`EngineMain.swift:1235-1237`).
6. **Stuck detection is independent of the model** — the car not moving triggers intervention even if the
   model is confident (`DegradeStateMachine.swift:12-13`).
7. **Fallbacks are fail-open and bounded**: never guess a direction, never full throttle, require N-frame
   confirmation, discard sudden jumps (`LaneFallback.swift:10-18`; `FallbackGuard.swift:26-31`;
   `MotionPredictor.swift:29-33`; `LaneBridge.swift:168-176`).
8. **Rule tier never brakes automatically and never reverses on its own** (`RuleController.swift:157`, `:164`).
9. **Recording must never be corrupted silently**: CSV row ⇄ image pairing, no `speed_kmh=0`, no name-collision
   reuse, stop with an explicit reason on frame-rate breach (SEC-05 §5.4, §5.8–5.9).
10. **Permissions are inherited through the process chain**, and TCC self-check fails fast at startup
    (`EngineMain.swift:107-1155`, exit code 2).
11. **Never click anything labelled login globally**, to avoid clicking another app's login button
    (`AIAgentPanel.swift:703`); never press F1–F12 because the game cannot receive macOS system function keys
    (`AIAgentPanel.swift:305`).
12. **No synthetic network traffic, no proxy pools, no CAPTCHA evasion**; search tools fail honestly
    (`WebSearch.swift:31-36`, SEC-07 §7.7.5).
