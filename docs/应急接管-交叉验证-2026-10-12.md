## 2. 🔴 跨进程一致性（致命缺陷 · 核心结论）

### 2.1 两个进程各有一个 `EmergencyTakeover` 实例

```swift
// EmergencyTakeover.swift:48
static let shared = EmergencyTakeover()   // ← 每进程一个单例，不是跨进程共享
```
`EmergencyTakeover.swift:36` 注释**自承**：「**双进程注意**：@MainActor 隔离；双进程（UI + engine）各有独立实例。」

**⟹ UI 进程和引擎进程各持一份状态，互不可见。**

### 2.2 两个实例的喂入与消费

| 进程 | `noteTickGap` 喂入 | 状态消费方 | 实际效果 |
|---|---|---|---|
| **引擎进程** | `AuroraDriveApp:6881`（`tick()` 最前，早退**之前**） | `EngineMain:1174` 读 `effectiveTickHz` → `setTickHz` | ✅ **冲刺/让位真实生效** |
| **UI 进程** | `AuroraDriveApp:6881`（同一份代码） | `MissionConsole:708` 读 `takeoverActive` → 横幅 | ❌ **永不触发** |

### 2.3 为什么 UI 实例永不触发

**关键**：UI 进程的 `tick()` 在 `:6918` 有 `if EngineClient.shared.isActive { tickEngineMode(); return }` 早退。

```
【UI 进程】
  tick() → :6865 tickGapMs = 实测间隔
         → :6881 noteTickGap(tickGapMs)     ← 喂到了（ET-4 特意放在早退前 ✅）
         → :6918 isActive=true → tickEngineMode(); return
```
- UI 的 tick 由 `MissionConsole:6035` 的 **20Hz 定时器**驱动 → 间隔 **≈50ms**
- `EmergencyTakeover.takeoverTickGapMs = 80.0`（`:65`）→ **50ms < 80ms，永不掉拍**
- `noteModelDegraded` 也喂了（`:6884`），但 `yolopxEngine.isLoaded` 在 UI 进程**是否加载**决定其效果——**即使触发，改的也是 UI 实例**，UI 实例的 `effectiveTickHz` **无人消费**（UI 进程不跑 tick 定时器调 `setTickHz`）

**⟹ UI 实例的 `takeoverActive` 恒为 `false`。**

### 2.4 引擎→UI 状态回传：字段发了，没人读

**`EngineMain.swift:1845`（heartbeat）已包含**：
```swift
{"type":"heartbeat",...,"takeover":\(et.takeoverActive),"userHolding":\(et.userHoldingKey),"reason":"..."}
```
**但 `EngineClient.swift` 里 `grep '"takeover"'` → 零命中**（我实测）。
**且 `tickEngineMode()`（`:6519-6560` 全文读过）无任何 takeover 相关代码。**

**⟹ 引擎的 `takeoverActive=true` 发出去了，UI 收不到、也不解析。**

### 2.5 ET-6 早已推荐了修复方案，但实现没采纳

`docs/应急接管审计-跨进程与让位-2026-10-12.md`：
- §3：「shm `maskFlags` 能加 bit 传 takeoverActive？✅ **bit4 空闲**；引擎设位 + UI 加一行即可」
- §3 末尾：「**给 ET-4 的指引（UI 横幅读状态）**：`if takeoverActive { flags |= 16 }` // bit4」
- 并警告：「如果 takeoverActive 状态变了但掩码没变（maskSeq 不变），UI **不会重读 flags** → 横幅延迟」

**⟹ ET-3（横幅）与 ET-4（接线）都没有采纳 ET-6 推荐的任一方案**（shm bit4 或 heartbeat 字段消费），而是让 UI 横幅直接读**本进程实例** → 链断。

### 2.6 判定

> **🔴 跨进程一致性：实现不成立。**
> **引擎进程内功能闭环（45Hz 冲刺 / 5Hz 让位 / 20Hz 巡航都真实生效），但 UI 横幅永不显示 → 用户看不到任何提示。**
> **ET-4 的 diff 注释（`AuroraDriveApp.swift` 新增段）自己写明了这点**：
> 「· 引擎进程 → 该实例控制 `setTickHz`（让位后降到 5Hz 省 CPU）
>  · UI 进程 → 该实例控制横幅显示」
> —— **作者知道有两个实例，但没意识到 UI 实例收不到触发信号。**

**修复方向（供 Lead 决策，我不改代码）**：
| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐，ET-6 已给）** | 引擎 heartbeat 的 `takeover`/`userHolding` 字段 → `EngineClient` 解析 → `tickEngineMode()` 回填 UI 实例 | **字段已在发**，只需加消费方；改动最小 |
| B | shm `maskFlags` bit4 | ET-6 已警告 maskSeq 门控会导致延迟 |
| C | UI 进程订阅 socket config 广播 | 需新增通道 |

## 3. `noteUserKeyDown/Up` 状态守卫（Lead 第②条）

### 3.1 实现
```swift
// :136
func noteUserKeyDown() {
    if sprinting { enterYield() }        // 只在冲刺态响应
}
// :144
func noteUserKeyUp() {
    if userHoldingKey { enterCruise() }  // 只在让位态响应
}
```

### 3.2 Lead 担心的漏洞：「用户按键时若还没进冲刺态，会被忽略？」

**分两种情形**：
| 情形 | 是否进 sprinting | 按键是否被忽略 | 判定 |
|---|---|---|---|
| **tickGap 掉拍触发** | `enterSprint()` 设 `sprinting=true` | 否（冲刺态按键→让位 ✅） | ✅ 正常 |
| **模型降级触发** | `noteModelDegraded` → `enterSprint()` **也设 `sprinting=true`** | 否（同上） | ✅ 正常 |
| **巡航态（无触发）用户按键** | `sprinting=false` | **是，被忽略** | ⚠️ **设计如此**（巡航态无需让位） |

**⟹ Lead 担心的"模型降级路径按键被忽略"不成立**——两条触发路径都经 `enterSprint()` 设了 `sprinting=true`。

### 3.3 但发现一个真实时序风险 ⚠️

**跨进程延迟**：UI 监听按键 → socket → 引擎处理（`EngineMain:1685`）。
```
用户按键 → KeyboardMonitor 回调（UI 进程）
        → sendCommand("config", ["takeover":true])   ← socket 往返
        → 引擎收到 → noteUserKeyDown()
```
**如果用户按键时引擎**尚未**进入 sprinting（例如掉拍检测刚累计到第 2 帧）** → `noteUserKeyDown` **被静默丢弃** → 用户按了但没让位 → **且无任何提示**。

**严重度**：P1（不是致命，但会导致"按了没反应"的用户困惑）。

## 4. 频率冲突（Lead 第③条）

### 4.1 两层防线（ET-5 的实现）

**第一层：源头 guard**（`EngineMain:809`）：
```swift
guard !EmergencyTakeover.shared.takeoverActive else {
    return (false, "应急接管进行中（\(Int(...effectiveTickHz))Hz）：档位频率暂不应用（应急优先），结束后自动恢复")
}
```
**第二层：tickOnce 兜底**（`EngineMain:1174`）：
```swift
let wantHz = EmergencyTakeover.shared.effectiveTickHz   // 每 tick 读
```

### 4.2 判定 ✅

| 场景 | 结果 |
|---|---|
| 应急中用户切档 | 源头 guard 拒绝，ack `ok:false` + 明确 detail → **UI 知情** ✅ |
| 应急结束 | `enterCruise()` 设 `effectiveTickHz=20` → `tickOnce` 读到 20 → `setTickHz(20)` ✅ **自动恢复** |
| 频率互相覆盖？ | **不会**：应急期间档位应用被源头拦截；应急结束后 tickOnce 以 `effectiveTickHz` 为准 |

### 4.3 ⚠️ 但 ack `ok:false` 的语义可能让 UI 误判

`applyPerceptionMode` 返回 `(false, "应急接管进行中...")` → ack `ok:false`。
**风险**：UI 若把 `ok:false` 当"配置失败"（而非"暂缓"），可能弹错误提示或回滚开关 → **用户看到"切档失败"的误导信息**。

**ET-5 已在 `:1706` 加了回显**（`applied["takeover"]`），但**档位本身的 `ok:false` 语义未区分"失败"与"暂缓"**。
**严重度**：P2（需确认 UI 侧如何处理 `ok:false`）。

## 5. 状态机逻辑走查

### 5.1 主路径（巡航→冲刺→让位→巡航）

| 转换 | 代码 | 判定 |
|---|---|---|
| 巡航→冲刺（掉拍） | `noteTickGap`:116-120（3 帧 >80ms） | ✅ 可走通 |
| 巡航→冲刺（降级） | `noteModelDegraded`:130 | ✅ 可走通 |
| 冲刺→让位 | `noteUserKeyDown`:138 | ✅ 可走通 |
| 让位→巡航 | `noteUserKeyUp`:146 | ✅ 可走通 |
| 冲刺→巡航（35s 超时） | `noteTickGap`:106-110 | ✅ 可走通 |

### 5.2 35 秒超时 ✅
```swift
if sprinting {
    if let start = sprintStart, Date().timeIntervalSince(start) >= 35.0 { enterCruise() }
    return
}
```
**但注意**：超时检查**只在 `noteTickGap` 被调用时**执行。若冲刺期间 tick 仍在跑 → 每帧都调 → ✅ 超时能生效。
**⚠️ 若 tick 完全停摆**（引擎卡死）→ `noteTickGap` 不被调用 → **超时永不触发** → 卡在 45Hz。**严重度 P2**（tick 停摆是极端场景）。

### 5.3 ⚠️ 发现状态卡死风险（P1）

**场景**：冲刺期间用户**一直按住**受控键。
```
冲刺 → 用户按下 → enterYield（hz=5, userHoldingKey=true）
     → 用户一直不松手
     → noteTickGap 第 102 行 `if userHoldingKey { return }` 直接返回
     → 35s 超时检查**被跳过**（因为 `if sprinting` 分支都进不去）
     → **永远停在 5Hz**
```
**分析**：这是**有意设计**（用户接管期间不干预），且 5Hz 是省 CPU 的（把算力让给用户），**对用户是安全的**。
**但**：`takeoverActive` 仍为 `true` → 若横幅能显示，会一直显示"已接管"；用户松手才回巡航。
**判定**：**P1 但可接受**（用户主动接管期间保持 5Hz 合理），需在文档中说明"用户不松手则一直 5Hz"。

### 5.4 状态归零检查 ✅
`enterCruise()`（`:174-182`）重置全部 6 个字段（`sprinting`/`takeoverActive`/`userHoldingKey`/`sprintStart`/`consecutiveMisses`/`effectiveTickHz`）→ **无残留** ✅
