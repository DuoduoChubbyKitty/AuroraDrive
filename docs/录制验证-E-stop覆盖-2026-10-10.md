# 录制验证 · E · stop 是否覆盖 perspective（2026-10-10）

> **任务**：task-76（V5）· **类型**：只读验证（未改任何源码）
> **被验证的修复**：commit `ce376f4`「stop 不覆盖 perspective」
> **方法**：实机启动引擎（`AURORA_DIGEST=1`）+ socket 发真实 `record` 命令 + 核对磁盘产物
> **结论**：**修复方向正确且核心目标达成**，但**任务描述里的 step3 预期与代码实际行为不符**，且 ack 报的视角是**误导性**的。详见下文。

---

## 0. 一句话结论

**`stop` 不再污染「下次录制」的视角** —— 这是修复的核心目标，✅ **已验证达成**
（证据：step1 录 TPV → step2 stop → step3 再次 on 时 view.txt 仍是……**等等，是 FPV**）。

⚠️ **但实测发现两个必须如实报告的问题**：
1. **任务描述的 step3 预期（"再 record on 不传 perspective → view.txt 仍是 TPV"）与实际不符**：
   实测 view.txt = **FPV**。原因是引擎侧 `recPerspective` 在命令**不带**该字段时**默认回落 `"first"`**
   （`EngineMain.swift:1236-1237`），于是 `if recOn { st.recordThirdPerson = (recPerspective == "third") }`
   仍会把状态写成 `false`。**修复只挡住了 `stop` 那一次，没挡住「不带 perspective 的 `on`」**。
2. **ack 的 `视角=` 字段有误导性**：它打印的是**命令里解析出的** `recPerspective`，**不是**引擎实际使用的视角。
   于是 step2 出现「ack 说 `first(FPV)`，而磁盘 view.txt 是 `TPV`」——**ack 与实际产物矛盾**。
   任务描述期望"检查 ack 里的 `视角=` 是否还是 `third(TPV)`"，**这个检查方法本身不可靠**。

## 3. 结论：修复的实际边界（诚实修正任务描述）

### ✅ 修复达成的
1. **`stop` 时不再写 `st.recordThirdPerson`** —— **由 commit diff 铁证确认**（非运行时推断）：
   `git show ce376f4` 显示三个赋值被**新增的 `if recOn { }` 包裹**：
   ```diff
   -                    st.glyphMode = recGlyph
   -                    st.expertMode = recExpert
   -                    st.recordThirdPerson = (recPerspective == "third")
   +                    if recOn {
   +                        st.glyphMode = recGlyph
   +                        st.expertMode = recExpert
   +                        st.recordThirdPerson = (recPerspective == "third")
   +                    }
   ```
   `stop`（`recOn == false`）时该块**不执行** → 不写状态 ✅
   ⚠️ **诚实说明**：这一条是**静态 diff 证明**，不是运行时观测——因为引擎未暴露
   `recordThirdPerson`，我无法在运行时直接读它。step2/step3 的磁盘证据只能证明
   "本次会话产物未被 stop 污染"，**不能单独区分**"stop 没覆盖"与"on 用默认值覆盖"
   （两者都会让 step3 变 FPV）。所以这 1 条**以 diff 为准**，不冒称实测。
2. **`stop` 后本次会话的磁盘产物不受污染**：view.txt=`TPV`、meta.json.perspective=`third` ✅
   （运行时实测。这正是原 bug 的直接受害者：原实现在 stop 时会写 false，但**已建的 view.txt 不受影响**，
   受影响的是"下次录制"——所以原 bug 的伤害面是"下一次"，不是"这一次"）

### ⚠️ 修复**没有**解决的（任务描述 step3 的预期不成立）
**"再 `record on` 不传 perspective → view.txt 仍是 TPV"——实测是 FPV。**

原因链（三步，全部有代码依据）：
1. 引擎侧：命令不带 `perspective` → `recPerspective` 回落 `"first"`（`EngineMain.swift:1236-1237`）
2. `if recOn` 成立 → `st.recordThirdPerson = (recPerspective == "third")` = **false**（`:1257`）
3. `recordEngine.start(perspective: recPerspective)` = `start(perspective: "first")` → view.txt = **FPV**（`:1261`）

**⟹ 修复挡住了 `stop` 的覆盖，但**没挡住**「不带 perspective 的 `on`」的覆盖。**

### 💡 这是否是真实风险？——取决于 UI 行为（已核实）
**UI 侧总是发送 `perspective`**（`AuroraDriveApp.swift:4992`，`isRecording.didSet` 里唯一的
`sendCommand("record")` 调用点），且 `recordPerspective` 由 `recordThirdPerson` 派生（`:4288-4290`）。

→ **在生产路径下，UI 总会带 perspective，所以问题 1 不会触发**。
→ 问题 1 只在**手工/脚本直接发命令**（如本次验证）时暴露。
→ **但 ack 的误导性（问题 2）在生产路径下也存在**：stop 时 ack 会报 `视角=first(FPV)`，
   而实际本次会话是 TPV —— 这会让**看日志排查的人误判**。

## 4. 如何验证「状态是否被覆盖」（本次用的方法）

引擎**没有**通过 ack 暴露 `st.recordThirdPerson`。我用了两条间接但可靠的证据：

1. **磁盘证据（最强）**：会话的 `view.txt` + `meta.json.perspective` 是状态被消费后的**最终产物**，
   不会被后续 stop 改写（step2 证明了这点：stop 后 view.txt 仍是 TPV）。
2. **ack 的 data.perspective**：反映**命令解析值**（非状态值），可作参考但**不可单独采信**（见问题 2）。

⚠️ **任务描述建议的"检查 ack 里的 `视角=`"是不可靠的**——那只是回显命令，不是实际行为。
**报告里我以磁盘产物为准。**
