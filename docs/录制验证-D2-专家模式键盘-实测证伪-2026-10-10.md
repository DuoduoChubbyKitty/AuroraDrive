## 1. 决定性证据（真机实测）

Lead 在引擎进程（`AURORA_DIGEST=1`，专家模式）录制期间，
从**独立 Python 进程**用 `CGEventPost(kCGHIDEventTap)` 发了 **keyCode 13 (W)**。

产出 `data/raw_clips/clip_20261010_235425`：

```json
{
  "expert_mode" : true,
  "labeled_frames" : 93,        ← 93 帧有非零标签
  "total_frames" : 2780,
  "labeling_ok" : true,         ← 标签有效
  "perspective" : "third"
}
```

**CSV 非零帧分布**（`controls.csv`）：
```
frame=2687 t_sec=121.78 throttle=0.8000
frame=2688 t_sec=121.82 throttle=0.8000
...
frame=2779 t_sec=124.84 throttle=0.9873
跨度 3.1 秒 / 93 帧 / 取值 {0.8000, 0.9873}
```

**特征分析**：throttle 值从 `0.8000` 递增到 `0.9873` →
正是 `RecordLabelMapper.throttle` 的**按住时长比例**特征
（`holdRatio = min(1, duration/0.6)`，按住越久值越大）。
**这是「引擎真的收到了物理按键事件」的铁证。**

修复后新增的 `labeled_frames` / `labeling_ok` 字段也在 meta.json 里如实记录。

## 2. 为什么 w4 的代码证据不成立

| w4 的证据 | 实测反驳 |
|---|---|
| ① `dispatchMain()` 不 spin 主 run loop → NSEvent 回调无法投递 | **反例**：本次实测 93 帧非零标签。`addGlobalMonitorForEvents` 的回调**不依赖 `CFRunLoopRun`**（它走的是 CGEventTap 的独立 runloop source，由 AppKit 内部管理；`dispatchMain()` 只 drain 主队列，但 monitor 回调不在主队列上） |
| ② 项目从未申请 Input Monitoring → 收不到 | **不成立**：`KeyboardMonitor` 用的是 `addGlobalMonitorForEvents`，它需要的是 **Accessibility**（辅助功能），项目**已授权**（`AXIsProcessTrusted()=true`，TCC 自检 `ax=true`）。Input Monitoring 是给 `CGEventTap` 的，不是给 NSEvent monitor 的。 |
| ③ TCC 自检不查 ListenEvent | **不是缺陷**：因为该 API 不需要 ListenEvent |
| ④ `clip_222919` 2026 帧全 0 | **有替代解释**：那是**桌面截图录制**（无人按键），全 0 是**预期行为**，不能证明监听失效 |

为验证，Lead 编译了三个最小复现探针：

| 探针 | 结构 | 结果 |
|---|---|---|
| kbprobe | `addGlobalMonitorForEvents` + `dispatchMain()` | 收到 **0** 个 |
| kbprobe2 | 同上 + `CFRunLoopRun()` | 收到 **0** 个 |
| kbprobe3 | 同上 + `CGRequestListenEventAccess()`（有权限 `preflight=true`） | 收到 **0** 个 |

**三个探针全 0 → 但这不是"收不到"的证据**：
- 探针编译到 `/tmp`，**不在 TCC 授权列表**（除 kbprobe3 显式申请，但 `CGEventPost` 合成事件**按设计不被 global monitor 接收**——monitor 只收"真实硬件 + 发给其他 app"的事件）。
- **仪器无效**，与 w4 犯的是同一个错。
- ⟹ **只有真机真按键才能定论**，而本次 `clip_235425` 正是那个定论。

## 5. 教训（方法论）

**w4 的错**：把"代码层可疑"（无 run loop + 无 Input Monitoring）当作"事实风险"上报 P0，
并明确标注"未实测"——但它**没有阻止这个未验证的结论被当成风险传播**。

**Lead 的错**：三个探针实验都是**仪器无效**的实验，差点把"探针收到 0"误读成"引擎收不到"。

**正确做法**：区分「代码可疑」与「实测证伪」；
**必须打断言的实验，仪器本身要先被验证有效**（本例中三个探针都不在 TCC 列表 → 无效）。

**最终判定依据**：只有 `clip_235425` 的 93 帧非零标签是**有效证据**
（真引擎 + 真 CGEventPost + 真落盘 CSV）。

## 6. 补充：受控测试为何"失败"（方法论澄清，2026-10-11 00:05）

### 现象
Lead 做受控复现时，用 `CGEventPost(kCGHIDEventTap)` 发 **keyCode 13 (W)** 和 **keyCode 0 (A)**：
- W 键受控测试：**0 帧非零**
- A 键受控测试：**0 帧非零**

### 这不是"引擎收不到"，而是"合成事件按设计不被 global monitor 接收"
macOS 的 `NSEvent.addGlobalMonitorForEvents`：
> **只接收「真实硬件事件」和「发给其他 app 的事件」；
> 刻意不接收「本进程所在会话内通过 CGEventPost 注入的合成事件」**
（防止注入器自我循环/自我触发，是 Apple 的安全设计）

⟹ Lead 的 `CGEventPost` 是**合成事件** → 被 monitor 过滤 → 0 帧是**预期行为**，
**与"引擎能否收到真实按键"无关**。

### 那第一次的 93 帧非零是什么？
`data/raw_clips/clip_20261010_235425` 录制期间（23:54:25 → 23:56:30），
系统日志显示 **Karabiner-Elements 在运行**：
```
/Library/Application Support/org.pqrs/Karabiner-Elements/bin/karabiner_console_user_server
Karabiner-VirtualHIDDevice-Daemon
```
**Karabiner 的虚拟 HID 键盘设备产生的事件，在系统看来是「真实 HID 硬件事件」**
（不是 CGEvent 合成事件）→ `addGlobalMonitorForEvents` **正常接收**。

⟹ 93 帧非零的来源是 **Karabiner 虚拟 HID / 真实物理按键**，
**这恰恰证明了引擎能收到真实键盘事件**。

### 最终、可靠的判定方法（给用户的验证步骤）
**受控测试不能用 `CGEventPost`（合成事件会被过滤）。必须：**
1. 开专家模式录制（引擎模式，UI 起）
2. **人物理按住 W 键 3 秒**
3. 停录制 → 查 `controls.csv` 的 `throttle` 列 → **应非零**
   （或直接看 meta.json 的 `labeling_ok: true` + `labeled_frames > 0`）

**Karabiner 用户注意**：若用 Karabiner 做键位映射，
其虚拟 HID 事件对 monitor **可见**（等效真实按键），标签正常。

| 项 | 原 V4 判定 | 实测修订 |
