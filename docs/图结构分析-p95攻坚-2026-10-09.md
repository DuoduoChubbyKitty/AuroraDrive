## 2. ★ 关键发现：batch 分布极不均衡

```
含 batch=8 的张量:  31 个   ← 只有 ImageEncoder 这一段
含 batch=1 的张量: 465 个   ← 其余全是单帧
```

**⟹ 8 帧只占 31 个张量（ImageEncoder），465 个张量是单帧的（时序/refiner/MoE/头）**

## 3. 由此推导的攻坚方向

### 3.1 双模型拆分的拆点（给 S1）
```
模型 A = ImageEncoder（8帧）  → 31 个 batch=8 张量，纯卷积
模型 B = 时序+refiner+MoE+头  → 465 个 batch=1 张量，单帧图
```
**关键推理**：
- **1帧 + palette 实测 ANE 2.23ms ✅** → 模型 B（单帧图）ANE 成功率高
- 模型 A 是纯卷积（无 GRU/无 MoE）→ 值得试 ANE
- 若 A 也失败 → 试 batch=4 跑两次（S4 在测这个边界）

### 3.2 编码成本归因（给 S4）
- 8 帧 batch 贯穿 ImageEncoder 的 18 个 conv
- **估算**：ImageEncoder 占 8× 成本，其余单帧
- **验证方法**：单独导出 ImageEncoder（8帧）测耗时，与整模型对比

### 3.3 图瘦身机会（给 S3）
- **cast 19 个**：fp16/fp32 转换 —— 若能统一精度可省
- **slice_by_index 30 个**：GRU while_loop 拆解 —— 若能静态展开可能更快
- **linear 132 个**：refiner 107 个 —— shared=True 下 12 步共用一个 cell，但展开成静态图后有 12 份（正常）
- **softmax 4 个**：MoE 路由（只在 4 步，符合设计）

## 5. 最可能成功的路线（Lead 判断）

| 路线 | 预期 | 依据 |
|---|---|---|
| **① 双模型拆分** | A(8帧卷积) + B(单帧465张量) → 若 B 能 ANE，总延迟可能 3~8ms | batch 分布分析 |

## 6. ★★ 决定性洞察（Lead 综合 t1 帧数边界 + 图结构分析，2026-10-09）

### 6.1 t1 的帧数边界实测（关键输入）

| 帧数 | ANE | CPU | 判定 | 余量 |
|---:|---:|---:|---|---:|
| **1** | **1.24ms** | 3.06ms | ✅ **ANE 生效** | 26.6× |
| 2 | 9.56ms | 5.38ms | 🔴 退化 | 3.5× |
| 4 | 20.08ms | 13.71ms | 🔴 退化 | 1.6× |
| 8 | 40.71ms | **25.93ms** | 🔴 退化 | **1.27×** 🔴 |

**⟹ ANE 安全边界 = 1 帧。任何 ≥2 帧的时序窗口都让 ANE 失效。**

### 6.2 但这里有个被忽略的关键点

**t1 测的是"整模型 × 帧数"。而本小姐的图结构分析显示：**
```
含 batch=8 的张量:  31 个   ← 只有 ImageEncoder
含 batch=1 的张量: 465 个   ← 时序/refiner/MoE/头 全是单帧
```

**⟹ "8 帧"只影响 ImageEncoder 的 31 个张量，其余 465 个张量本来就是单帧的！**

### 6.3 决定性方案：每帧只编码 1 帧 + 特征缓存

**核心洞察**：8 帧时序窗口里的 **7 帧是历史帧** —— 它们的特征**在之前 7 个 tick 里已经算过了**。当前实现**每个 tick 都重算 8 帧**，等于 **8× 重复计算**。

**正确做法**：
```
每个 tick（30Hz）：
  ① 只对【当前新帧】跑 1 次 ImageEncoder → 得到 1×256 特征  → 模型 A（单帧，ANE 1.24ms）
  ② 把新特征推入特征环形缓冲（8 帧特征序列）
  ③ 主控图吃【8 帧缓存特征 + lane + dets + state】→ 6 输出 → 模型 B（单帧图，ANE 预期 2ms）
```

**预期延迟**：`1.24ms（模型A）+ ~2ms（模型B）= **3.3ms** ✅ **远低于 16ms 目标**

**为什么这满足全部红线**：
| 红线 | 是否满足 | 说明 |
|---|---|---|
| 不降步数 | ✅ | refiner 仍 12 步（8自己+4专家） |
| 不降 MoE | ✅ | 仍 6 专家、仍 4 步 |
| 不降帧率 | ✅ | 仍 30Hz |
| 不降分辨率 | ✅ | 仍 180×320 / 160×160 |
| 不降质量 | ✅ | **数值等价**（同样 8 帧特征序列，只是复用缓存） |

**唯一改动**：模型输入契约从 `image [8,3,180,320]` 改为 `img_feat [1,8,256]`（8 帧缓存特征），ImageEncoder 拆成独立模型。

### 6.4 与 t1 结论的关系

- t1：「8 帧 → ANE 失效，CPU 25.9ms，余量 1.27× 偏危险」✅ 正确
- **本小姐**：那是**因为当前实现把 8 帧塞进一个图**。拆开后：
  - 模型 A（单帧 ImageEncoder）→ **ANE 1.24ms**
  - 模型 B（单帧主控图，465 张量）→ **预期 ANE ~2ms**
  - **总延迟 ~3.3ms**，且**帧数不变、历史不变、质量不变**

### 6.5 这就是 S1/S5/S7 三条路线的汇合点

| 子代理 | 职责 |
|---|---|
| **S1** | 拆模型 A/B，分别导出测 ANE |
| **S5** | 验证特征复用的数值等价性（<1e-3） |
| **S7** | Swift 侧特征缓存 + 环形缓冲改造清单 |
| **S4** | 验证单帧 ImageEncoder 的 ANE 行为（batch=1） |

**优先级**：这条路线**最可能达成 p95 ≤ 16ms**（预期 3.3ms，余量 10×）。

## 7. ★★★ Lead 实测铁证：ImageEncoder 8帧/单帧 = 6.12×

**测量**（PyTorch CPU 代理，本机负载 5.99 下测，比值比绝对值可靠）：

```
ImageEncoder 单帧 (1,3,180,320): 13.57 ms
ImageEncoder 8帧  (8,3,180,320): 82.97 ms
8帧/单帧 比值: 6.12×（理论 8×，实测 6.12× —— batch 有部分并行收益）
```

**⟹ 拆开后每 tick 只跑单帧编码 = 省 84% 编码计算**

**为什么这是决定性的**：
- 当前实现：**每个 tick 都重算 8 帧**（8 帧里有 7 帧是历史，特征早就该缓存）
- 正确实现：**每 tick 只编码 1 个新帧**（13.57ms 的 1/6.12）
- **8 帧特征序列照样喂给时序 GRU** → **数值等价、帧数不变、历史不变、质量不变**

**注意**：这是 PyTorch CPU 代理数字（负载 5.99，非独占）。**CoreML ANE 数字以 S1/S4 的导出实测为准**，但**6.12× 的比值关系**是结构性的（batch 维度决定），会保持。
