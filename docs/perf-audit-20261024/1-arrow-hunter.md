# 小地图箭头朝向「时准时不准」根因排查

- 排查人：arrow-hunter（性能/正确性诊断）
- 日期：2026-10-24
- 性质：**只读审计**。未改任何源码、未 build、未启停 App 进程、未跑 `--pointer-selftest`。
- 证据口径：所有 `file:line` 指向当前工作区源码；所有实测数字均为**离线复刻判据**在给定帧集上跑出，已单独标注"未测"的项。

---

## 1. 结论一句话

**根因是「静默回退」：`read()` 一旦返回 nil，`MissionConsole.swift:2044` 的 `bodyHeadingDeg ?? locatorHeading` 会把箭头瞬间换成「视角朝向」（UE5 ControlRotation，与身体朝向是两个不同的物理量），而且视觉上**没有任何区分**——同一根 `Capsule`、同一个颜色；叠加「置信度算了却从不参与门控」（`PointerHeadingReader.swift:114` 的契约无人执行），于是一次漏检/误检就是一次 100°+ 的角度跳变，而读成功时误差只有 0.16° 量级。所谓「准的时候真准、不准的时候烂到离谱」，正是**离散状态切换**的特征，不是精度渐变。**

置信度：**高**（机制本身）；触发频率：**中**（取决于画面内容与驾驶状态，见 §2）。

### 2.1 关键量级：这不是「单帧闪一下」，而是可持续数秒~数分钟的持续错值

交接笔记在真游戏 1500 帧上实测过：**t=210s 那 300 帧命中率 0.0%**，原因是那 300 帧**打开了大地图**，小地图箭头在画面里根本不存在（经看图确认，`docs/指针朝向-交接笔记.md:230,234-235`）。

300 帧 @30fps = **连续 10 秒**。这 10 秒里 `read()` 每一帧都返回 nil → `bodyHeadingDeg = nil` → 箭头**全程渲染视角朝向**（`MissionConsole.swift:2044`）。用户把大地图开着、进菜单、或者小地图被别的窗口盖住——只要这个状态持续多久，箭头就错多久，且**外观与正常箭头完全一致**。

这正好对上用户的描述：
- 「准的时候真准」= 正常驾驶、画面里有箭头 → 跳变中位 **0.16°**（`交接笔记:236`）。
- 「不准的时候烂到离谱」= 箭头不存在/画面不是游戏 → 整段持续输出**另一个物理量**（视角朝向），不是抖动、不是渐变，是**离散切换**。

所以 M1 不是"偶发瑕疵"，而是**有明确、可复现触发场景的整段失效**。这也解释了为什么离线帧集上的检测指标漂亮（那些帧全是正常驾驶画面），而用户在真机上有强烈体感——**两者测的根本不是同一批场景**。

### 2.2 补充发现：注释与代码不符（会误导后续排查）

`App/AuroraDriveApp.swift:7383-7385` 注释写：

> 「待机时 `bodyHeadingDeg` 不刷新，罗盘箭头回退 `locatorHeading`（视角朝向）」

**这与代码不符**：`bodyHeadingDeg` 在停车时**没有被置 nil**（全仓写入点仅 `6767/7397/7400`），因此待机时箭头不会"回退视角"，而是**冻结在最后一次驾驶时的身体朝向**。只有「从未驾驶过」时才是真回退。这个差异对验收方法影响很大：待机实验看到的既可能是冻结值、也可能是回退值，取决于之前有没有开过车。

## 3. 复现方法

### 3.1 复现 M1（回退视角朝向，最核心）

最直接：让 `read()` 必然返回 nil，然后观察箭头是否变成"跟着相机转"。

1. 停用模型（**只改文件名，不改源码**）：
   ```bash
   mv models/tiny_arrow_v2.mlmodelc models/tiny_arrow_v2.mlmodelc.off
   ```
2. 启动 App，进入驾驶，用鼠标拖视角（不改车身朝向）。
3. 预期现象：侧栏读数显示「无指针」，但**小地图上的箭头仍然在动，且与视角同步**——因为它渲染的是 `state.locatorHeading`（`MissionConsole.swift:2044`）。箭头本体没有任何"这是回退值"的视觉标记。
4. 恢复：
   ```bash
   mv models/tiny_arrow_v2.mlmodelc.off models/tiny_arrow_v2.mlmodelc
   ```

> 该实验同时验证 M2：整个过程中 `conf` 一栏根本不显示（走 `无指针` 分支），说明门控压根不存在。

### 3.2 复现 M3（待机冻结）

1. 驾驶 10 秒以上（确保 `bodyHeadingDeg` 已被写入）。
2. 按停（`stopDriving` → `App:6446`），**不要重启 App**。
3. 原地大幅转视角。
4. 预期现象：箭头**完全不动**（冻结在最后一次驾驶朝向），而光束（`locatorHeading`，`:2037`）照常转 —— 两者夹角越拉越大。这**不是**"回退视角"，是"冻结"。
5. 对照组：冷启动 App **不驾驶**，直接在驾驶位前转视角 → 此时才是真回退（箭头跟着光束一起转）。

### 3.3 复现 M4（非游戏画面误检）

1. 把游戏设成**窗口化**，或把任意一个浅色/金色调的窗口拖到屏幕**左上角**覆盖小地图区域。
2. 保持驾驶态，观察箭头读数。
3. 预期现象：侧栏**不显示「无指针」**，`conf` 可能仍 0.7+，但箭头指向明显错误的角度。这是 `PointerHeadingReader.swift:66-74` 记录的行为（436/449 帧仍选出块，实测出现过 104°）。

### 3.4 复现 M5（档位跳变，需精确构造）

不改源码的前提下难以稳定复现；建议用离线脚本确认（见 §5.2 的复刻脚本思路）：构造 area 在 78~82 之间、fill≈0.80 的箭头贴图，喂给 `judge` 逻辑，观察是否在同一形状上因面积 1~2 像素抖动而在"通过/拒绝"之间翻转。

### 3.5 现场取证（不改代码，用户日常跑就能拿到）

在真机上抓三个数就能判定当前命中的是哪条机制。建议临时用 `AURORA_PERF=1` 启动，`tick.pointer` 通道会统计指针段耗时；重点看 `Journey`/日志里是否出现「无指针」。更省事的办法是直接看 UI：

- 侧栏显示 `无指针` 且箭头跟着光束转 → **M1**（回退）。
- 侧栏显示 `箭头 xx°` 但角度明显错误 → **M4**（误检）或 **M5**。
- 停之后箭头不动 → **M3**（冻结）。

## 4. 修复建议（按「改动最小、风险最低」排序）

| 优先级 | 改动 | 具体做法 | 是否影响画质/精度 |
|---|---|---|---|

## 5. 我排除了哪些方向（附证据）

### 5.1 已由委派方排除，我未重复验证

- 480×312 缩略帧 vs 1280×832：120 帧角度差 max 5.09°，无一帧 >10° → **排除**。
- `.cpuAndNeuralEngine` / 推理耗时 0.087ms → **排除**（不是性能问题，是正确性问题）。
- "只算小地图区域"优化：新旧二进制逐字节相同 → **排除**。

### 5.2 我自己排除的

**① 检测层在干净游戏帧上不脆弱（排除"judge 太松把噪声当箭头"作为**主**机制）**

我用 Python 逐项复刻了 `PointerHeadingReader.swift:622-787` 的 `locateArrow` + `judge`（8 邻域连通域、area 二次缩放、aspect/fill/holeFrac/sharpen/rcv 五项判据、`minimapCenterIn720p` 选块），在三个给定帧集上跑：

| 帧集 | 尺寸 | 判据通过率 | 每帧候选块数 | 选中块到实测圆心距离 |
|---|---|---|---|---|
| `/tmp/nte_vid/full720seq` | 1280×720 | **120/120 (100%)** | min=1 / p50=1 / max=1 | p50=2.0px，max=2.3px |
| `/tmp/ptr_equiv/prod832` | 1280×832 | **120/120 (100%)** | 1 | p50=2.3px，max=2.5px |
| `/tmp/ptrtest_480/real480` | 480×312 | **120/120 (100%)** | 1 | p50=1.0px，max=1.3px |

关键量（生产档 normal 阈值）：`rcv` 实测 **0.25~0.35**（阈值 0.12，余量 2~3 倍）；`sharpen` 实测 **5.2~6.8**（阈值 4.8，**最紧，余量仅约 8%~40%**）；fill 0.52~0.58（阈值 0.42~0.78，居中）；aspect 1.08~1.15（阈值 1.8，宽松）。

尺度鲁棒性复测（同一批 720p 帧逐级降采样，复刻判据）：1280×720 → 960×540 → 854×480 → 640×360 → 480×312 → 426×240 → **320×180 全部 120/120 通过**。

模糊敏感性（prod832 加高斯模糊）：r=1.0px 仍 120/120（sharpen min 5.90），**r=2.0px 仍 120/120**（sharpen min 4.94）。→ 轻微模糊/重采样不足以让判据崩掉，`sharpen` 虽有最小余量但不是当前主因。

结论：**在"画面确实是游戏、且箭头存在"的前提下，检测层几乎不失败**。所以 nil 的来源更可能是「画面里没有箭头」（大地图/菜单/M1 场景）与「画面不是游戏」（M4），而不是判据本身太松。

**② 选块圆心/缩放算错 → 排除**

`minimapCenterIn720p = (101.5, 86.9)`（`PointerHeadingReader.swift:210`，2026-10-23 已从错误的 ROI 中心改正）。实测三个帧集选中块距该圆心 1.0~2.5px，且**每帧只有 1 个候选块**——选块逻辑根本没被行使，不存在"选错块"的空间。

顺带核实生产帧形态：`prod832` **不是** 720 内容 + 黑边（顶部 56 行 mean=110.9、max=255，有真实内容），而是 1470×956 显示器整屏等比缩放到 1280×832（1470/1280=1.148 vs 956/832=1.149，**两轴比例一致**）。虽然代码用 `sy = 832/720 = 1.156` 做 ROI 换算（口径不严谨），但实测箭头质心落在 (99.7, 100.7)、预测圆心 (101.5, 100.4)，**误差 2.3px**，未造成问题。

**③ `headingOffsetDeg = 332.0` 系统性偏差 → 排除（作为间歇性根因）**

常量偏移只会造成**恒定**误差。实测跳变中位 0.16°（`docs/指针朝向-交接笔记.md:220-240`，4 个有效窗口 1175 个相邻帧对）——若常量错 20°，跳变中位仍是 0.16°，但绝对值全偏。用户描述是"时准时不准"，与常量偏差的签名不符。残余不确定度 ±4.4° 值得记录，但不是本 bug。

**④ 跨 0°/360° 换算 → 未发现证据，排除**

`PointerHeadingReader.swift:454-457`：`atan2(s,c)` → 加偏移 → `truncatingRemainder` → 负数加 360，是完整归一化。显示侧 `rotationEffect(.degrees(...))`（`MissionConsole:2044`）接受任意角度且**不做角度插值/最短路径动画**，因此没有"跨零度插值绕远路"的问题。全链路未发现按区间分支的逻辑。

**⑤ 模型路径在引擎子进程里找不到 → 排除**

`AuroraPaths.projectRoot()`（`Core/AuroraPaths.swift:41-107`）优先用 `#filePath` 编译期绝对路径上溯 4 级，其次 cwd、可执行文件目录及其上溯 6 级，与进程启动方式无关；且 `models/tiny_arrow_v2.mlmodelc` 存在于项目根。引擎与 UI 是同一二进制、同一份解析逻辑，不会一个找到一个找不到。

**⑥ 引擎模式与 UI 本地模式"两个 pointerReader 打架" → 不存在（但另有 M6）**

UI 在引擎模式下于 `App:7122-7127` `tickEngineMode(); return` 早退，**本地 `pointerReader` 根本不会执行**；引擎进程跑完整 `tick()` 后每 3 帧发一条 `pointer` 消息（`EngineMain.swift:1497-1510`），UI 在 `EngineClient.swift:433-439` 解析并写 `engineBodyHeading`，再由 `App:6767` 同步。**同一时刻只有一个数据源**，不存在双写竞争。唯一相关缺陷是 M6（回落时不清空陈旧值），且本次采样日志中未观测到心跳超时事件。

## 7. 一句话给用户

箭头本身（检测+模型）很准，问题在于**它有一次"悄悄换成视角朝向"的后门**——换过去时箭头外观一模一样，你看到的就是一根乱转的箭头，而不是"没读数"。这条后门在三种情况下会被打开：读指针失败、画面不是游戏、以及车停着（此时冻结在旧值）。这三条都能在 §3 复现。
