### 改动 1：`captureCursor = false`（修复假光标 BUG）

**位置**：`Vendor/MetalGoose/Engine/GooseUpscaler.swift:54-61`

**改动**：
```swift
public func configureInterpolation() {
    let settings = CaptureSettings.shared
    settings.scalingType = .off
    settings.aaMode = .off
    settings.frameGenMode = .interpolation
    settings.frameGenMultiplier = 2
    settings.captureCursor = false          // ← 新增
    engine.updateSettings(settings)
}
```

**为什么**：`Stubs.swift:15` 的 `MouseConstraintManager.currentCursorFraction()` **硬编码返回 `(0.5, 0.5)`**，而 `CaptureSettings.captureCursor` 默认 `true` → **画面正中永远有一个不跟随鼠标的假箭头**。

**影响链**：
```
settings.captureCursor = false
  → GooseEngine.swift:1821  next.captureCursorEnabled = false
  → GooseEngine.swift:1203  if config.captureCursorEnabled { ... }   // 不进入
  → 不再调用 drawSyntheticCursor
```

**⚠️ 会破什么**：
- **真光标是否还在？** → ✅ **在**。`CaptureEngine.swift:218` 已设 `config.showsCursor = true`（SCStream 捕获真光标）
- **`CaptureSettings` 持久化** → 改动会写入 UserDefaults（`didSet { store(...) }`），下次启动保持 `false` ✓

**验证**：
1. 开插帧 → 看画面正中是否还有假箭头
2. 移动鼠标 → 真光标仍可见
3. `--upscale-selftest` 通过

**回滚**：删掉那一行。

**收益**：修复用户可见的视觉 BUG（插帧开启时必现）。

### 改动 7：`publish` 的 CGContext → memcpy（引擎最大热点）

**位置**：`Sources/AuroraDrive/Core/EngineMain.swift:220-247`

**实测证据**：`sample <engine_pid> 8` 显示 **`tickOnce` 的 14 个样本 100% 在 `publish`**：
| 位置 | 样本 | 占比 |
|---|---|---|
| `:241` `ctx.draw(img)` | 8 | **57.1%** |
| `:238` `CGContext(data:)` | 3 | **21.4%** |
| 编译器生成 | 3 | 21.4% |
| **`DriveState.tick()`** | **0** | **0%** |

**改动**：
```swift
} else if let img = image {
    let w = img.width
    let h = img.height
    if w > 0, h > 0, w <= EngineFrameShm.maxWidth, h <= EngineFrameShm.maxHeight {
        let pageSize = w * h * 4
        if pageSize != currentPageSize {
            currentPageSize = pageSize
            generation += 1
            storeU32(32, generation)
            storeU64(72, UInt64(pageSize))
        }
        let active = base.load(fromByteOffset: 36, as: UInt32.self)
        let writePage = active == 0 ? 1 : 0
        let dest = base.advanced(by: EngineFrameShm.pixelsOffset + writePage * currentPageSize)

        // ★ 优化：CGImage 底层已是 32BGRA premultipliedFirst（CaptureEngine 用
        //   CGDataProvider 零拷贝包装，CaptureEngine.swift:407-409），格式与目标完全一致
        //   → 直接 memcpy。原 CGContext.draw 会走完整 CG 绘制管线 + 像素格式转换 +
        //   Alpha 混合（实测占引擎主线程 78.6%）。
        if let data = img.dataProvider?.data, let src = CFDataGetBytePtr(data) {
            let srcBPR = img.bytesPerRow
            let copyBytes = w * 4
            if srcBPR == copyBytes {
                memcpy(dest, src, copyBytes * h)                  // 紧凑布局：一次 memcpy
            } else {
                for r in 0..<h {                                   // 有行填充：逐行
                    memcpy(dest.advanced(by: r * copyBytes),
                           src.advanced(by: r * srcBPR), copyBytes)
                }
            }
            storeU32(24, UInt32(w))
            storeU32(28, UInt32(h))
            storeU32(36, UInt32(writePage))
        } else {
            // ★ 兜底：dataProvider 不可读时回退原 CGContext 路径（功能零损失）
            let cs = CGColorSpaceCreateDeviceRGB()
            let bitmapInfo = CGImageAlphaInfo.premultipliedFirst.rawValue
                | CGBitmapInfo.byteOrder32Little.rawValue
            if let ctx = CGContext(data: dest, width: w, height: h,
                                   bitsPerComponent: 8, bytesPerRow: w * 4,
                                   space: cs, bitmapInfo: bitmapInfo) {
                ctx.draw(img, in: CGRect(x: 0, y: 0, width: w, height: h))
                storeU32(24, UInt32(w))
                storeU32(28, UInt32(h))
                storeU32(36, UInt32(writePage))
            }
        }
    }
}
```

**⚠️ 必须保持的 4 条不变量**：
| # | 不变量 | 破坏后果 |
|---|---|---|
| ① | 像素格式 = `premultipliedFirst + byteOrder32Little` | UI 侧颜色错乱（红蓝互换） |
| ② | `bytesPerRow = w*4`（紧凑） | 图像斜切/错行 |
| ③ | 写入"非活动页" | 画面撕裂 |
| ④ | 写完像素后才翻页（`offset 36`） | 同上 |

**⚠️ 为什么安全**：
- **UI 侧读者**：`EngineClient.swift:508-517`，按 `w*4` + `premultipliedFirst + byteOrder32Little` 读 → **与源格式一致** ✓
- **`ctx.draw(img, in: CGRect(0,0,w,h))`** 的**目标尺寸 = 源尺寸** → **无缩放** → **纯格式转换**
- **源已是目标格式** → **转换是恒等** ✓

**⚠️ 验证清单**：
1. 画面正常（无花屏/斜切）
2. 颜色正确（红色元素仍是红色）
3. **`sample <engine_pid> 8` → `publish` 占比应从 ~100% 降到 <20%**
4. 帧率仍 30fps（引擎日志 `seq` 差）
5. `--speed-selftest` / `--yolo-selftest` 通过
6. 插帧路径正常（若开启）

**回滚**：把 `if let data = img.dataProvider...` 改成 `if false`（走兜底分支）。

**收益**：**引擎 CPU -78.6%**（实测驱动）。

## §12 预览框卡顿优化 + 掩码可见性修复（2026-09-27 第二轮）

**用户反馈**：「感觉没有车到线，我只能看到检测框」「预览框巨卡」

### 12.1 主线程每帧开销：3.831ms → 0.675ms（降 82%）

| 项 | 改前 | 改后 | 手段 |
|---|---|---|---|
| `convertToGray` | 0.639 ms | **0.040 ms** | 消除每像素整数除法（同尺寸快路径） |
| 光流 DIS | 1.700 ms | **0（移出主线程）** | 移到 `captureEngine.onYoloFrame` |
| 掩码绘制 | 1.192 ms | **0.375 ms** | 行跨度合并（含新增车道线描边） |
| 检测框绘制 | 0.300 ms | 0.300 ms | 未动 |
| **合计** | **3.831 ms** | **0.675 ms** | 占 33.33ms 预算 11.5% → **2.0%** |

**后果**：
- 光流移出主线程后，主线程不再被 2.3ms/帧的感知计算占用。
  用户实测 `tickGap` 曾达 45ms（>33.33ms 即掉拍），此项直接缓解。
- 灰度快路径是**数学等价**（同尺寸时除法恒等于 x），输出逐位相同。
- 行跨度合并经 7 种形态逐像素比对，覆盖面积完全一致（几何等价）。
- ⚠️ 光流相关成员改为 `nonisolated(unsafe)`，访问点收敛到 captureQueue 单线程
  （与既有 `pendingYoloFrame` 同一手法）。

### 12.2 光斑 blur 实测（首次量化）

用户要求保留光斑视觉（空间感光斑是明确的功能要求，不得缩减），故取
**零视觉改动**方案。

| 视口 | p50 | p95 | 占 33.33ms |
|---|---|---|---|
| 800×450 | 2.13 ms | 143 ms | 6.4% |
| 1200×675 | 2.93 ms | 5.25 ms | 8.8% |
| 1470×956 | **4.20 ms** | 6.90 ms | **12.6%** |

**确认它是预览框里单项最贵的绘制**（此前只有注释断言、从未被量过）。

**手段**：`.drawingGroup()` 栅格化缓存。半径 60、blob 尺寸/位置/透明度/
动画曲线全部不变，视觉逐像素一致。

**后果 / 尚未验证**：`.drawingGroup()` 的实际收益需在真实 UI 上复测
（离线夹具无法完全复现 SwiftUI 合成路径）。**若收益不明显需回退** ——
它本身也有一点内存代价（额外一张离屏纹理）。

### 12.3 掩码可见性：分层塌陷解耦

**根因**：单一 `isDegraded` 同时控制两层掩码显示。车道线是细目标
（前景占比 1.3~2.6%，天然贴近下限），它一塌陷就把可行驶区也压暗到
`0.18 × 0.35 = 0.063` —— 用户看到的现象是"什么都没有"。

**改动**：
- `YolopxEngine` 新增 `laneDegraded` / `drivableDegraded`
- `MaskOverlay` 分别调暗
- 协议 v3 flags 加 bit2 / bit3
- **决策层 `isDegraded` 语义完全不变**

**后果**：车道线塌陷不再连坐可行驶区。旧引擎不发新位 → 恒为 0 →
两层都不压暗（**安全方向**：偏亮而非偏暗）。

### 12.4 自检补真实推理（关键）

**问题**：`--yolopx-selftest` 打印 `可行驶占比: 0.00%` 但**从未调用过
`engine.infer()`** —— 那是字段初值。整个项目对"掩码能不能出来"没有证据。

**改动**：加 A2 节，用真实异环行车画面跑完整推理。

**结果**：
```
检测框 9 个 / 可行驶占比 26.19% / 车道线占比 8.042%
网格前景格数: da=3772 ll=1158 (共 25600 格)
降级判定: 否
```
**模型一直是好的**，问题全在显示层。这条证据把排查方向从模型侧纠回显示侧。

### 12.5 验证状态

- 自检：`yolopx` 46/46、`opticalflow` 7/7、`motion` 15/15 全通过
- 位打包：9/9 单格探针精确定位（生产读写逐格无损）
- 共享内存布局：区域不重叠 ✓，物理边界门防 SIGSEGV ✓
- 引擎侧新增诊断插桩：每 5 秒输出 yolopx 加载状态/推理帧数/掩码格数
- ⚠️ **真机驾驶验证仍缺失**（掩码只在 `isDriving` 时绘制，需用户点「开始驾驶」）

## §13 紧急回退：`drawingGroup()` 与光流位置（2026-09-28）

**用户反馈**：「一开自动驾驶就卡得离谱，卡到逆天，基本不能动」

### 13.1 根因：我上轮加的两处改动都是净负面

| 改动 | 我当时的理由 | 实际后果 | 处置 |
|---|---|---|---|
| 光斑加 `.drawingGroup()` | 离线测到 blur 是预览框最贵绘制，栅格化可缓存 | **主线程 1402/1402 样本卡在离屏纹理重建** | **已移除** |
| 光流移到 `captureQueue` | "后台线程，挪走省主线程时间" | 该队列是 SCStream 采样队列（queueDepth=3），拖慢帧消费 | **已移回主线程** |

### 13.2 证据：真实堆栈采样（`sample <pid> 3`）

```
1402/1402 主线程样本：
  CA::Transaction::commit()
    → CA::Layer::display_if_needed
    → RBLayer displayWithBounds
    → RB::DisplayList::render
    → RenderState::RootTexture::make_texture()      ← 1110 样本
  并出现 FilterStyle<RB::Filter::GaussianBlur>::draw
```

**机理**：`.drawingGroup()` 把子树渲染进离屏纹理，而外层 `.offset` 动画每帧移动位置
→ 纹理每帧失效重建 → 从"一次高斯卷积"变成"离屏合成+卷积+再合成，且纹理每帧重建"。

### 13.3 指标对比

| 指标 | 修复前 | 修复后 |
|---|---|---|
| UI 待机 CPU | 30.5% | **6.9%** |
| `CA::Transaction::commit` | 1402/1402 样本 | 6 |
| `RootTexture::make_texture` | 1110 样本 | **0** |
| `GaussianBlur FilterStyle` | 主因 | **0** |
| 引擎 `capWork` | 11ms → **2081ms**（雪崩） | 恢复正常 |
| 引擎 `tickGap` | 33ms → **17044ms** | 恢复正常 |
| 系统 load | **171** | 3~7 |

### 13.4 保留的有效优化（未回退）

| 项 | 收益 | 验证 |
|---|---|---|
| `convertToGray` 消除逐像素除法 | 0.639ms → **0.040ms**（快 16 倍） | 数学等价 |
| 掩码行跨度合并 | 1.192ms → **0.375ms** | 7 种形态逐像素面积一致 |
| 分层塌陷解耦（da/ll 独立调暗） | 车道线塌陷不再连坐可行驶区 | 自检 + 协议 bit2/bit3 |

### 13.5 关键教训

1. **离线微基准不能替代真实 UI 堆栈采样。** CIGaussianBlur 夹具里没有 SwiftUI 的
   离屏合成语义，测不出 `drawingGroup()` 的代价，还给了我"有据可依"的错觉。
   改渲染路径后**必须** `sample <pid>` 验证。

2. **`drawingGroup()` 只适合内容与位置都稳定的子树。** 有动画/位移时比不加还慢。

3. **"后台线程"不等于"空闲线程"。** 挪计算前必须确认那条队列承载什么；
   屏幕采集/音频采集/网络收包的采样队列上只应做最少工作。

4. **性能数据必须在真实输入分布上取。** 我的「光流 1.7ms」是在合成块状图上测的；
   真实游戏画面（纹理梯度 8.58 vs 合成 2.51）实测只要 **0.96ms**——
   错误的前提导致了一系列错误决策。

5. **改完必须实测，不能只靠推理。** 本次两处改动我都有"理论依据"，
   但都没在真实场景验证，结果双双是负优化。

## §14 【汇总】被实测推翻的优化方案（2026-09-29 归集）

> **为什么单列这一节**：`性能审计笔记.md` 的「§356 执行总结」里有一张**极有价值的表**——
> 「**清单改法被实测推翻的（重要）**」，记录了 5 个**看起来合理、实测却是负收益或有风险**的改动。
> 但它埋在 28,012 行笔记的第 27,990 行，**几乎不可能被翻到**。
> **本节的方案都是"别再做"的清单**——每个想优化本项目的人应该先读它。

| # | 原清单改法 | 声称收益 | **实测结论** | 处置 |
|---|---|---|---|---|
| **#6** | `ConsoleCard` 加 `.compositingGroup()` | 「视觉零影响」 | **1px 边框+文字边缘亚像素变化 1.89%，可感知**（基线噪声仅 0.0069%）；主画面/卡片主体零差异；UI 重绘仅 **1.875 Hz** → **收益≈0、代价>0** | ❌ **回滚** |
| **#17** | `hit.sort` 加长度判断 | 「省 3,460 次比较」 | **sort 顺序是显示语义**（近处优先）→ 跳过排序会**破坏顺序** | ❌ **跳过** |
| **#20** | `regionLabel` 改存储属性 + tick 更新 | 「省 5677 次遍历 × 10Hz」 | **tick 是 30Hz，会把遍历从 1.875Hz 提到 30Hz（重 16 倍）** | ✅ **改用更优方案**：`regionName` **格缓存**（-99% 遍历）★比原清单方案更好 |
| **#24** | `ObstacleOverlay` 加 `drawingGroup()` | 「Canvas GPU 合成」 | **Canvas 本身已是位图渲染** → drawingGroup **无收益反加一次拷贝** | ❌ **跳过** |
| **#23** | `ForEach` 用 `id: \.offset` 替代索引 | 「消除索引反模式」 | **rows 文本可能重复 → 稳定 id 有 duplicate id 崩溃风险**；offset 对每次重建的数组**是正确做法** | ❌ **跳过** |

### 从这 5 项提炼的方法论（★ 务必记住）

1. **"省了 N 次操作"不等于"省了时间"** —— 必须先确认**该路径的真实触发频率**。
   #20 的教训最典型：清单按 10Hz 估算，实际 tick 是 30Hz，**方向完全反了**。
2. **"视觉零影响"必须用像素级 diff 验证**，不能靠肉眼。
   #6 的 1.89% 亚像素变化 —— 靠"我觉得看不出来"是发现不了的（基线噪声 0.0069%，差 274 倍）。
3. **有些"反模式"是刻意的** —— `ForEach` 的 offset、`Canvas` 不加 drawingGroup，
   在本项目的具体约束下**才是正解**。改之前先问"原来的写法是不是有理由"。
4. **排序可能是语义，不是冗余** —— `hit.sort` 的近处优先是**显示需求**，
   不是性能负债。**把语义当性能问题优化，是危险的一类错误。**

> **交叉引用**：这 5 条与 `pitfalls.md` 的 §21（`drawingGroup()` 用在会动的子树上）、
> §22（"后台线程"≠"空闲线程"）同源 —— 都是「**理论依据充分但实测为负**」的案例。
> 项目里这类记录的价值极高：**它们阻止后人重犯同样的错误**。
