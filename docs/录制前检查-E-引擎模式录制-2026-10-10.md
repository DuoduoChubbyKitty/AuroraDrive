# 录制前检查 · E · 引擎模式录制链路审计（2026-10-10）

> **任务**：task-68（R5）· **类型**：只读审计（未改任何产品代码，未跑 build）
> **问题**：引擎模式（默认路径）下录制到底在哪个进程做、标签从哪来、UI→引擎参数是否完整下发
> **结论先行**：**链路是通的**（5 个疑点全部排除），**但发现 3 个真实风险**，其中 1 个是**静默数据错误**级

---

## 0. 一句话结论

引擎模式下**真正写盘的是引擎进程**（这一点是对的，注释与代码一致）；
UI 的 `recordFrameIfNeeded()` 确实永不执行（符合设计，不是 bug）；
引擎进程的帧源（`onFrame`）与录制逻辑（`tick`→`recordFrameIfNeeded`）**都真的在跑**——
但存在 **① 专家模式标签在引擎进程恒为 0（静默错误）**、**② watchdog 杀引擎丢了 `flushSync`**、
**③ UI 与引擎的 `isRecording` 状态可能不一致** 三个风险。详见 §6。

## 1. 审计问题逐条回答

### 问题 1：引擎侧录制实现——引擎进程里有没有跑 `recordFrameIfNeeded()` 等价逻辑？

**答：有，而且是同一份代码。**

关键链条（每一环都有代码依据）：

| 环 | 证据 |
|---|---|
| 引擎进程建自己的 `DriveState` | `EngineMain.swift:766` `EngineGlobals.state = DriveState()` |
| 引擎 30Hz 定时器调 `tick()` | `EngineMain.swift:790-796` `DispatchSource.makeTimerSource` → `EngineMain.tickOnce()` |
| `tickOnce` 调 `st.tick()` | `EngineMain.swift:894-896` `st.tick()` |
| `tick()` 在引擎进程**不会**提前 return | `AuroraDriveApp.swift:6860` `if EngineClient.shared.isActive` —— 见下方论证 |
| 正常分支末尾调 `recordFrameIfNeeded()` | `AuroraDriveApp.swift:7634`（§7 行驶录制） |

**为什么引擎进程不提前 return**（这是审计的核心，必须论证而非假设）：
- 提前 return 的条件是 `EngineClient.shared.isActive == true`（`:6860`）
- `isActive` **只在 `EngineClient.activate()` 里置 true**（`EngineClient.swift:199`）
- `activate()` 只在 `EngineClient` 的**连接成功回调**里被调（`:167` / `:184` / `:574`）
- 而 `EngineClient` 是**每进程独立单例**（`EngineClient.swift:49` `static let shared = EngineClient()`）
- **引擎进程从不调用 `EngineClient.shared` 的连接方法**（grep `EngineMain.swift` 全文，
  对 `EngineClient` 的引用只有 2 处：`:24` 注释、`:1461` 复用 `EngineClient.protocolVersion` 常量）
- 全仓 `EngineClient.shared.startup()` 只在 `AuroraDriveApp.swift:209` 调用（UI 路径）

**⟹ 引擎进程里 `EngineClient.shared.isActive == false`（恒为该单例的初始值）
⟹ `tick()` 不提前 return ⟹ 正常走到 `:7634` 的 `recordFrameIfNeeded()`。**

### 问题 2：引擎进程的帧源（`currentScreenImage`）是通的吗？

**答：通。**（这条是任务描述没点名、但我审计时发现必须验证的——否则问题 1 的"走到了"是空转）

`recordFrameIfNeeded()` 的守卫是 `if isRecording, let image = currentScreenImage`
（`AuroraDriveApp.swift:7764`）。若 `currentScreenImage` 在引擎进程恒 nil，**即使 tick 走到了也录不进帧**。

| 环 | 证据 |
|---|---|
| `currentScreenImage` 由 `pendingFrame` 喂 | `AuroraDriveApp.swift:6880` `currentScreenImage = latest` |
| `pendingFrame` 由 `captureEngine.onFrame` 闭包写 | `AuroraDriveApp.swift:5960-5968` |
| `onFrame` 接线在 `DriveState.init()` 内（**不是** UI 专属） | `:5886` 是 `init()`，`:5960` 在其函数体内 |
| 引擎进程执行 `DriveState()` → 同样执行 `init()` → 同样接线 | `EngineMain.swift:766` |
| `onFrame` 在 `--engine` 守卫**之外** | `:5934` 的 `if !CommandLine.arguments.contains("--engine")` 块在 `:5940` 闭合，`:5960` 在其后 |

**⟹ 引擎进程的帧源是通的**（唯一注意：`captureEngine.start()` 需被调用，见 `EngineMain.swift:784` 仅诊断开关下自动启动；生产靠 UI 的 `start` 命令 → `startDriving()` → `captureEngine.start()`，见 `AuroraDriveApp.swift:6238`）。

### 问题 3：专家模式标签从哪来？`keyboardMonitor` 在引擎进程启动了吗？

**答：`keyboardMonitor` 是 `DriveState` 的成员（`AuroraDriveApp.swift:5621`），引擎进程有自己的实例；
但 `keyboardMonitor.start()` 只在 `startDriving()` 里调（`:6237`）——而 `startDriving()` 
在引擎进程**会被调**（`case "start"` → `EngineMain.swift:1162`）。**

⚠️ **但这里有一个真实问题**：`KeyboardMonitor` 依赖**物理键盘事件监听**（CGEventTap / NSEvent）。
引擎进程是**后台进程（无 UI/无窗口）**，能否收到物理键盘事件**未经实测验证**。
→ 若收不到，`holdDuration(keyCode:)` 恒返回 0 → **专家模式录出的标签全是 0**（静默错误）。
→ 详见 §6 风险 1。

### 问题 4：UI→引擎的录制参数下发是否完整？

**答：完整。四个字段一一对应。**

| UI 发送（`AuroraDriveApp.swift:4986-4993`） | 引擎接收（`EngineMain.swift:1223-1230`） | 用途 |
|---|---|---|
| `on: Bool` | `recOn` | 开/关 |
| `glyph: Bool` | `recGlyph` | 字模模式 → `glyphMode` |
| `expert: Bool` | `recExpert` | 专家模式 → `expertMode` |
| `perspective: String` | `recPerspective`（经 `normalizePerspective` 归一） | 视角 first/third |

**无遗漏**。且引擎侧对 `perspective` 做了归一化防御（非法值回落 `first`，不因字符串拼错整场失败）。

### 问题 5：CSV 写入路径与 UI 是否同一个？

**答：同一个 `data/raw_clips/`（`RecordEngine.swift:144-148`，用 `AuroraPaths.projectRoot()` 定位）。**

- 普通录制：`data/raw_clips/clip_<yyyyMMdd_HHmmss>/`（含 `frames/` + `controls.csv` + `view.txt` + `meta.json`）
- 字模模式：`data/glyph_clips/clip_<ts>/frames/`（隔离，不写 CSV）
- 两侧都用 **同一个 `AuroraPaths.projectRoot()`**，与进程无关 → **不会出现"UI 写 A 目录、引擎写 B 目录"的分裂**

### 问题 6：停止时完整性 —— `stop()` 有 fsync + meta.json 吗？watchdog 杀引擎会丢数据吗？

**`stop()` 本身是健壮的**（`RecordEngine.swift:261-330`）：
- ✅ `csvHandle?.synchronizeFile()`（fsync）+ `closeFile()`（`:267-271`，注释明确写了这是 P1 修复）
- ✅ `writeQueue.sync` 排在已入队的 `appendFrame` 写块之后 → 不丢尾部
- ✅ `meta.json` 后台异步写（含 `perspective`，`:311-325`）
- ✅ `flushSync()` 提供"等队列排空"能力（`:333+`）

**`performShutdown()` 也调了 `flushSync()`**（`EngineMain.swift:1540`），注释说明：
> `stop()` 里的 meta.json 是 writeQueue.async 写的，紧接着 exit(0) 会在元信息落盘前杀掉进程 → 录制会话缺 meta.json。这里等队列排空。

⚠️ **但 watchdog 的 30 秒 idle-exit 路径我确认它走 `performShutdown`**（`:1501` `EngineMain.performShutdown(reason: "idle-exit")`），
**所以 idle-exit 是安全的**。→ 见 §6 风险 2（另一条被杀路径）。

## 5. 我额外验证的（任务未点名但影响结论成立的）

1. **`currentScreenImage` 在引擎进程是否为 nil** —— 若 nil，则"引擎有录制逻辑"是空转。
   已证实 `onFrame` 接线在 `DriveState.init()` 内（非 UI 专属），引擎进程同样接线 → 帧源通。
2. **`isActive` 在引擎进程的值** —— 这决定了 tick 是否早退。已证实引擎进程从不调 `EngineClient` 连接，
   且 `EngineClient.shared` 每进程独立 → `isActive` 恒为初始 `false`。
3. **`--engine` 守卫的边界** —— `onFrame` 接线在守卫块**外**（`:5940` 闭合，`:5960` 在后），
   所以引擎进程不会被跳过。

## 6. ⚠️ 发现的风险（3 个，按严重度排序）

### 🔴 风险 1（静默数据错误）：专家模式在引擎进程可能录出**全 0 标签**

**依据**：
- `recordFrameIfNeeded()` 的专家分支用 `keyboardMonitor.holdDuration(keyCode:)` 取真人按键时长
  （`AuroraDriveApp.swift:7766-7774`）
- `keyboardMonitor` 是 `DriveState` 成员，引擎进程有自己的实例，且 `startDriving()` 会 `start()` 它
  （`:6237`）
- **但 `KeyboardMonitor` 依赖系统级键盘事件监听（CGEventTap/NSEvent）**。引擎进程是后台进程
  （`EngineMain.run()`，注释明确"不触碰 SwiftUI"），**能否收到物理键盘事件未经实测**

**后果**：若引擎进程收不到键盘事件 → `holdDuration` 恒 0 → `RecordLabelMapper.steer/throttle/brake`
映射出的标签**全为 0** → 专家演示数据集**整场废掉**（而且**不报错**，文件照常写、帧数照常涨）。

**建议**：录制前**必须实测**一次"引擎模式 + 专家模式"录一小段，
检查 `controls.csv` 的 steer/throttle/brake 是否有非零值。若全 0，则专家模式必须走 UI 进程或改用其他标签源。
**这是本次审计最重要的发现——它是静默的，靠看日志/帧数发现不了。**

### 🟡 风险 2（可能丢尾部数据）：非 idle-exit 的进程退出路径

已证实 **idle-exit（30s watchdog）走 `performShutdown` → 有 `flushSync`** ✅。

但引擎还有**其它退出路径**需确认是否都经过 `performShutdown`：
- `:713` `performShutdown(reason: "signal \(sig)")` ✅ 经过
- `:811` `performShutdown(reason: "tick-detected")` ✅ 经过
- **`exit(5)`（`:762`，共享内存创建失败）** ❌ **不经过** —— 但此时录制尚未开始，无影响
- ⚠️ **`SIGKILL`（kill -9）** —— 无法被捕获，`flushSync` 不会执行 → **CSV 尾部与 meta.json 会丢**
  （`synchronizeFile` 只在 `stop()` 里调；若引擎被 SIGKILL，缓冲区里未 flush 的行丢失）

**建议**：确认实际部署中谁会 `kill -9` 引擎；若有，考虑周期性 fsync（如每 N 帧或每 5 秒）。

### 🟡 风险 3（状态不一致窗口）：UI 与引擎的 `isRecording` 是两个独立变量

- UI：`DriveState.isRecording`（`AuroraDriveApp.swift`）
- 引擎：`EngineGlobals.state.isRecording`（**另一个 `DriveState` 实例**，`EngineMain.swift:766`）
- 两者靠 socket 命令 + ack 同步（`:1267` `sendHeartbeat(reason: "record-ack")`）

**风险**：若命令丢失/超时/引擎重启，UI 可能显示"录制中"而引擎并未录（或反之）。
代码里已有"宽限期 + 双保险"缓解（`:1266-1267` 注释），且 ack 的 `ok` 以**引擎实际状态**为准
（`:1274` `ok: st.isRecording == recOn`，不谎报）——这个设计是好的。

**建议**：录制前 UI 应显示**引擎 ack 回来的**状态（而非本地开关值），并核对心跳里的
`recording` 字段（`:1461` 心跳已含）与 `frames` 是否在增长。
