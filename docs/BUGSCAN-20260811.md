## 0. 速览结论

**整体健康度：架构骨架是对的（@MainActor + 后台串行队列 + finish 模式已基本成型），但"数据真相"没有进决策闭环——真实车速从未接入（M9 吃模拟速度、卡死判据和脱困判据都吃模拟速度）、E2E 输入疑似垂直翻转、捕获缓冲存在生命周期竞争，当前状态是"UI 完整、决策半真"，不能作为安全自动驾驶使用。**

**最该先修的 3 个：**
1. **P0-1 速度链路接入**（用户核心痛点：speedKmh 只进 UI 和日志，vehicle_state[0]/卡死判据/脱困退出判据全部吃模拟速度）
2. **P0-2 E2E 输入垂直翻转确认与修复**（可能是"M9 不能开、纯规则能开"现象的真正根因）
3. **P0-4 前台应用校验 + 注入安全**（当前无校验，注入键可能发给 AuroraDrive 自身或错误 App）

## 2. P0/P1 根因分析与重构方案

### P0-1 速度链路断裂（核心痛点，先修）
**根因**：SpeedOCRReader 接入后，只补了"显示"层（DriveState.speedKmh 计算属性 + 日志），决策层三处仍吃 tick() 里的模拟速度 `speed`：
- `inferenceEngine.infer(speedKmh: speed)`（:596）/ assist（:597）→ vehicle_state[0] 是假速度；
- `degradeStm.update(speedKmh: speed)`（:642）→ 卡死判据；
- `escapeController.update(speedKmh: speed)`（:681）→ 脱困退出判据。
模拟速度 `speed += (target-speed)*0.06 + random` 自证自洽：目标默认 86km/h，首帧即 >5km/h，stuckSeconds 永远清零 → **卡死检测与脱困档在真实使用中从未生效过**。用户抱怨"卡死不动也不脱困"即此因。

**重构方案**（结构化）：
1. `DriveState` 新增 `private var lastGoodSpeed` 与 `effectiveSpeed` 计算：
   `speedOCR.lastResultTime 距今 <0.5s && speedOCR.speedKmh >= 0 → speedOCR.speedKmh；否则 lastGoodSpeed`（首帧无 OCR 用 0）。
2. tick() 中所有 `speed` 决策引用替换为 `effectiveSpeed`（infer ×2、状态机、脱困）；`speedValid = OCR 新鲜` 传入状态机。
3. DegradeStateMachine.update 增加 `speedValid: Bool`：速度未知时 stuckSeconds 不累计、不触发/不退出 .recover。
4. EscapeController 退出判据用 effectiveSpeed（>8km/h），超时后不再自动重开（见 B06）。
5. 模拟速度仅保留为 OCR 缺失时的运动学回退（加速度模型），删除随机抖动。

### P0-2 E2E 输入疑似垂直翻转
**根因**：`CGContext.draw(cgImage, in:)` 在非翻转 bitmap context 中把图像按 CG 坐标（原点左下）写入内存，行 0 = 画面底部；CoreML 按行 0 = 顶部读 → 模型看到上下颠倒画面。InferenceEngine.preprocessImage（E2E/assist 全部推理）与 YoloEngine.draw（慢路径）均未做 y 翻转。生产 YOLO 走 CaptureEngine 的 `CIContext.render` 直通（CIContext 自动处理方向）→ 不翻转 → 与"M9 不能开、纯规则能开"现象吻合。
**注意**：此结论为经典 CG 行为推演，需对拍确认（--yolo-selftest 的 /tmp/yolo_swift_input.png 若与源图一致则无翻转；最稳妥是与 Python 端同图对比 CHW dump）。
**重构方案**：确认后，在 preprocessImage 与 draw 中绘制前加 `context.translateBy(x: 0, y: CGFloat(H)); context.scaleBy(x: 1, y: -1)`；或全部统一为 CIContext.render(to: CVPixelBuffer)（与直通同语义，消灭双路径分叉）。

### P0-3 捕获缓冲生命周期竞争
**根因**：
- `onNativeFrame` 传的是 SCStream 回调里的 CVPixelBuffer，经 DispatchQueue.main.async 延迟到主线程才 cropROI；回调返回后系统可能已复用该缓冲 → use-after-release/花屏/崩溃。
- `onYoloFrame` 双缓冲轮换仅保证"下一帧写另一块"；主线程 memcpy 延迟超过 1 帧时，captureQueue 会重写同一块缓冲与 memcpy 并发 → 撕裂帧。
**重构方案**：在 captureQueue 内同步完成"拷贝/裁剪/缩放"到自持 CVPixelBufferPool 缓冲（memcpy 约 0.5MB，微秒级），再派发主线程只做引用传递；彻底消除跨队列裸缓冲共享。

### P0-4 前台应用无校验
**根因**：CGEvent 注入是系统级，事件只分发到前台应用；代码只把 front= 写日志（:707-708 注释自己承认），没有任何拦截。游戏被 AuroraDrive 自身或其它窗口遮挡时，WASD/空格注入到错误应用（空格可能触发 AuroraDrive 按钮）。
**重构方案**：tick() 注入前校验前台进程（`NSWorkspace.shared.frontmostApplication?.bundleIdentifier/localizedName` 匹配游戏），不匹配则跳过注入、状态机照跑、UI 显示"游戏未在前台，按键已暂停"；后续可升级 postToPid 精确投递。

### P1-5 专家模式顶键（B05）
**根因**：expertMode/controlDisabled 分支每帧 `releaseAll()` 对所有映射键发合成 keyUp（releaseAll 设计为"无条件清理"），真人物理按住的键在 HID 状态层被标记释放 → 游戏认为键已松开；专家录制标签（按住时长）失真。
**重构方案**：ControlEngine 拆分 `heldAIKeys`（AI 注入集）与 `heldKeys`（显示集）；释放只针对 heldAIKeys；物理键永不合成 keyUp。expert/disabled 分支改为"零注入"而非"注入释放"。

### P1-6 脱困超时失效（B06）
**根因**：EscapeController 超时后 phase=.done、isEscaping=false；tick() 的 `.recover` 分支每帧 `if phase == .done { enter() }` 无条件重开 → 超时保护永远不生效，真卡死时无限倒车循环。
**重构方案**：tick 记录前一帧 mode，仅在 `上一帧 != .recover && 本帧 == .recover` 时 enter()；EscapeController 增加 timeoutEscalated 状态（全停 + UI 告警），由状态机决定是否继续尝试。

### P1-7 状态机一致性（B07/B09）
**根因**：卡死判据吃假速度（同 P0-1）；warmingUp 只查 M9；状态机用上帧置信度决策（step3 先于 step4）。
**重构方案**：接 effectiveSpeed + speedValid；warmingUp 覆盖两引擎；把置信度更新移到状态机之前（先感知→置信度→状态机→输出，消除一帧滞后）；recover 成功按 m9Live/health 回梯而非直跳 .e2e。

### P1-8 生命周期竞态（B08）
**根因**：start()/stop() 都包 Task，无取消/世代机制；start 的 await 未完成时 stop 直接 return，随后 start 完成 → 停驶后 capture 仍运行、isCapturing=true。
**重构方案**：CaptureEngine 引入 `generation: Int`，start 捕获当前代，完成前检查代是否过期；stop 自增代并使 in-flight start 落空；或改 async/await 串行状态机。
