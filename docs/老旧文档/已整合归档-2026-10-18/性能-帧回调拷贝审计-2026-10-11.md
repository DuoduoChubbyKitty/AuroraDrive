## 0 · 结论速览

| 项 | 数值 |
|---|---|
| 抓屏源帧 | 1280×832 @45fps = **182.8 MB/s**（`CaptureEngine.swift:439-440`） |
| **每帧拷贝总量（全开）** | **7.78 MB/帧 = 349.9 MB/s**（是抓屏本身的 **1.9 倍**） |
| 每帧拷贝总量（自动驾驶，无插帧） | 3.71 MB/帧 = **167.1 MB/s**（抓屏的 91%） |
| 每帧拷贝总量（仅 UI） | 0.59 MB/帧 = 26.4 MB/s（抓屏的 14.5%） |
| 每帧 CPU（vImage+memcpy） | 0.55–0.60 ms（45fps 下占 **2.5–2.7% 单核**） |

**三个最重要的发现**：
1. 🔴 **`inferFast` 存在重复拷贝**：帧回调已把源缩放到 640×640 池化缓冲（`CaptureEngine.swift:978`），`YoloEngine.inferFast` 收到后又 `memcpy` 一份到私有缓冲（`YoloEngine.swift:314-317`）——**同一份数据拷两遍**，白费 **70.3 MB/s**（占自动驾驶总拷贝的 42%）。
2. 🔴 **`copyUpscaleFrame` 是最大单项**：每帧整帧 4.06 MB = **182.8 MB/s**，等于把抓屏数据再搬一遍。**但有门禁**（`isUpscaleWanted()` 在拷贝前求值）——插帧关闭时 = 0。
3. 🟡 **门禁覆盖不全**：5 个拷贝点里**只有 1 个有门禁**（upscale）；其余 4 个注册即每帧执行，无"当前用不到就跳过"的判断。

## 1 · 逐帧拷贝清单（行号 / 大小 / 条件）

| # | 位置 | 操作 | 每帧字节 | 带宽@45fps | 触发条件 | 门禁 |
|---|---|---|---|---|---|---|
| ① | `CaptureEngine.swift:932` → `:1124` | `copyNativeFrame`：源 → ROI 池（102×42 memcpy） | 17,136 B（16.7 KB） | 0.74 MB/s | `onNativeFrame != nil`（OCR 常开） | ❌ 无 |
| ② | `CaptureEngine.swift:940` → `:1197` | `copyUpscaleFrame`：源 → 全分辨率池（整帧 memcpy） | **4,062,464 B（4.06 MB）** | **182.8 MB/s** | `onUpscaleFrame != nil && isUpscaleWanted()` | ✅ **有** |
| ③ | `CaptureEngine.swift:952-978` | `vImageScale_ARGB8888`：源 → YOLO 640×640 池 | 1,638,400 B（1.56 MB，写） | 70.3 MB/s | `onYoloFrame != nil`（YOLO 开） | ❌ 无 |
| ④ | `CaptureEngine.swift:1002-1024` | `vImageScale_ARGB8888`：源 → UI 480×312 池 | 599,040 B（585 KB，写） | 25.7 MB/s | **每帧无条件** | ❌ 无 |
| ⑤ | `YoloEngine.swift:314-317` → `:366` | ★**重复**：640×640 池 → 私有缓冲 memcpy | 1,638,400 B（1.56 MB） | **70.3 MB/s** | `inferFast` 收到帧即拷 | ❌ 无 |

**关键尺寸来源**（均为代码实测常量，非估算）：
- 源：`config.width = 1280`、`config.height = 1280 × aspect(0.650) = 832`（`CaptureEngine.swift:439-440`）
- ROI：`speedROINorm = (x:0.455, y:0.885, w:0.080, h:0.050)`（`:148-149`）→ 1280×0.080 = **102**、832×0.050 = **42**
- YOLO：`YoloEngine.inputSize = 640`（`YoloEngine.swift:44`）
- UI：`maxWidth = 480`（`:995`）→ 480×312

### 1.1 每帧总账

```
仅 UI 显示（不录不推理）    0.59 MB/帧 =  26.4 MB/s   （抓屏的 14.5%）
+ YOLO + OCR（自动驾驶）    3.71 MB/帧 = 167.1 MB/s   （抓屏的 91.4%）
+ 插帧（全开）              7.78 MB/帧 = 349.9 MB/s   （抓屏的 191.4%）★翻倍
```

**为什么"全开"会翻倍**：`copyUpscaleFrame`（②）把整帧**再搬一份**，量等于抓屏本身；再叠加 ③⑤ 两份 640×640 拷贝。

## 2 · 本机实测成本（vImage / memcpy）

**实测方法**：独立基准程序（`/tmp/vimgbench`，不碰仓库、不占构建锁），真 CVPixelBuffer，60 次取中位。

```
=== vImage / memcpy 每帧实测（Apple Silicon，60 次取中位）===
  vImageScale 1280×832 → 640×640      中位 0.312 ms  (min 0.310 / max 0.852)
  vImageScale 1280×832 → 480×312      中位 0.218 ms  (min 0.216 / max 0.630)
  memcpy 整帧 1280×832 (4.06MB)        中位 0.053 ms  (min 0.050 / max 0.075)
  memcpy 640×640 (1.56MB)              中位 0.020 ms  (min 0.019 / max 0.063)
```

**每帧 CPU 账**：
| 工况 | 每帧 CPU | @45fps 占单核 |
|---|---|---|
| 自动驾驶（vImage 640 + vImage 480 + memcpy 640） | 0.550 ms | **2.5%** |
| 全开（+ memcpy 整帧） | 0.603 ms | **2.7%** |

**结论**：
- **vImage 缩放是 CPU 主项**（0.53 ms/帧，占 2.4% 单核）——但它把 4.06 MB 全帧流转成 1.56 MB + 0.57 MB，**省的是下游 GPU/内存带宽**，值得。
- **memcpy 本身极快**（整帧仅 0.053 ms）→ **瓶颈不是 CPU 时间，是内存带宽**（读写 4 MB 的内存总线占用）。
- 所以优化方向应是**减少拷贝字节数**，不是"让 memcpy 更快"。

## 3 · 可省项清单（按收益排序，标注风险）

> ⚠️ 全部建议**不含降帧率/降分辨率**（用户铁律）。

### 🔴 收益 1：消除 `inferFast` 的重复拷贝 —— 省 70.3 MB/s（占自动驾驶拷贝 42%）

**现状**（两处代码）：
```swift
// ① CaptureEngine.swift:952-978 —— 已缩放进池化缓冲（每帧独立、池深度≥4）
if let pool = makeYoloBufferPool(size: size) { ... vImageScale_ARGB8888(...)
    onYoloFrame(yb)   // 送出的 yb 已是 640×640、独立缓冲、主线程强捕获
}
// ② YoloEngine.swift:313-317 —— 收到后又拷一份
if yoloInputBuffer == nil { yoloInputBuffer = Self.makePixelBuffer(size: Self.inputSize) }
guard let dst = yoloInputBuffer, Self.copyPixelBuffer(pixelBuffer, to: dst) else { ... }
```

**为什么这是纯冗余**：`CaptureEngine` 送出 `yb` 时**注释已说明**"每帧独立、池深度 ≥4，下游 `onYoloFrame` 强捕获该缓冲，直到 tick 消费 + inferFast 拷贝完才释放回池"（`:948-949`）。即 **`yb` 的生命周期已被设计成"足够下游安全使用"**——那 `inferFast` 里那次 memcpy 就是为了"防与 captureQueue 写竞争"（`:313` 注释），但池化缓冲每帧独立，**不存在写竞争**。

**建议**：`inferFast` 直接用传入的 `pixelBuffer` 做推理输入，不再拷到 `yoloInputBuffer`：
```swift
// 直接用传入的池化缓冲（它已是 640×640、每帧独立）
let dst = pixelBuffer   // 不再 copyPixelBuffer
```
**风险（中）**：需确认 `MLFeatureValue(pixelBuffer:)` 的**同步性**——若 CoreML 推理是异步持有该缓冲，而池在推理完成前复用它，会读到下一帧。**缓解**：`isInferencing` 防重叠已存在（`:312`），且池深度 ≥4；但**必须实测验证**（建议加断言：推理期间缓冲引用计数 > 0）。
**收益**：-1.56 MB/帧 = **-70.3 MB/s**。

### 🔴 收益 2：`copyUpscaleFrame` 改 zero-copy 或延迟拷贝 —— 潜在省 182.8 MB/s

**现状**（`:1197-1223`）：插帧开启时，每帧把**整帧**从 SCStream 缓冲 memcpy 到私有池（4.06 MB）。
**注释说明理由**（`:937`）："必须复制到带 IOSurface 的私有缓冲，否则下游 CGImage 创建会崩（MG-ENG-001）"。

**可省性分析**：
- 该拷贝**已有门禁**（插帧关闭 = 0），所以**只影响开了插帧的用户**。
- 用户诉求"录制/自动驾驶掉帧"发生在**不开插帧**时（插帧是显示增强，非驾驶必需）——所以**这项很可能不是用户当前症状的主因**。
- 若要优化：`MetalGoose` 若接受 `CVPixelBuffer` 直传（不要求 IOSurface），可省掉整帧拷贝；但注释明确说"会崩"，**风险高**，需先查 MG-ENG-001 的根因。

**建议**：**优先级低于收益 1**。若要动，先确认 MG-ENG-001 是否仍存在（可能已随下游改动失效）。
**收益**：最多 -4.06 MB/帧 = **-182.8 MB/s**（但仅插帧开启时）。
**风险**：**高**（历史崩溃记录）。

### 🟡 收益 3：UI 路径的 `NSImage` 包装可再省一点（收益小）

**现状**（`:1055-1061`）：`CGImage` 已零拷贝引用 `uiBuf`（`CGDataProvider` + `passRetained`，`:1034-1040` ✅ 做得好），但外面又包了 `NSImage`（`:1055`）。
`NSImage(cgImage:size:)` 本身**不拷贝位图**（只是包装），所以**这项没有可省字节**——列出仅为完整性。

### 🟡 收益 4：`copyNativeFrame` 每帧 16.7 KB —— 收益小但可零成本省

**现状**（`:932`）：`onNativeFrame` 注册即每帧拷 ROI（16.7 KB = 0.74 MB/s）。
**可省性**：**收益极小**（0.4% of 抓屏带宽），不值得动。
**但可加门禁**：若 OCR 未启用（`speedOCR` 关闭），可把 `onNativeFrame` 置 nil 从而跳过——**零成本**。检查注册方（`AuroraDriveApp.swift:6012`）是否已做。

## 4 · CVPixelBufferPool 使用审计（任务第 5 问）

| 池 | 声明 | 惰性创建 | 复用判据 | 深度 | 复用失败处理 |
|---|---|---|---|---|---|
| UI | `:301-302` | `makeUIBufferPool`（`:1094`） | `uiBufferPool != nil && width/height 匹配` | ≥4 | `guard ... else { return }`（跳过本帧） |
| YOLO | `:246` 附近 | `makeYoloBufferPool`（`:1068`） | 同上 | ≥4 | 跳过本帧直通 |
| native | `:242-244` | `nativeBufferPool`（`:1169`） | 同上 | ≥4 | `return nil` → 不回调 |
| upscale | `:305-307` | `upscaleBufferPool`（`:1228`） | 同上 | ≥4 | `return nil` → 不回调 |

**审计结论**：
- ✅ **四个池都是"惰性创建 + 尺寸匹配复用"**，不会每帧新建（尺寸稳定时命中缓存）。
- ✅ 池深度统一 `MinimumBufferCount = 4`，注释说明"主线程通常 1-2 帧在途，留余量"。
- ✅ 复用失败（池耗尽）时**优雅跳过本帧**，不崩溃。
- ⚠️ **潜在问题**：`CVPixelBufferPoolCreatePixelBuffer` 在池耗尽时会**自行扩容**（`nativeBufferPool:1168` 注释承认）——若下游持有缓冲时间过长（如 `inferFast` 又拷一份导致原缓冲延迟释放），池会持续扩容 → **内存缓涨**。这与收益 1 相关（去掉重复拷贝也能让池更快回收）。

## 5 · 已验证 vs 推测

**已验证（读真代码 + 本机实测）**：
- 5 个拷贝点的行号、字节数、触发条件（逐个读代码确认）
- 每帧总带宽（基于代码常量的确定性计算）
- vImage/memcpy 每帧耗时（**本机实测**，非估算）
- 四个池的惰性创建与复用逻辑
- 门禁覆盖情况（只有 upscale 有）
- UI 路径已零拷贝（CGDataProvider）
- `inferFast` 重复拷贝（两处代码对照确认）

**推测 / 未验证**：
- ⚠️ **收益 1 的实际可行性**：需验证 `MLFeatureValue(pixelBuffer:)` 是否同步持有——**未实测**（需真机跑 YOLO 并加引用计数断言）。这是本报告最大未验证项。
- ⚠️ **MG-ENG-001 是否仍存在**（收益 2 的前提）——未查该崩溃记录的历史
- ⚠️ **实际帧回调频率**：按 45fps 计算，但**未真机确认** SCStream 实际投递率（可能低于上限）
- ⚠️ **GPU 侧成本未测**：本报告只覆盖 CPU 拷贝；`NSImage`→SwiftUI 绘制、MetalGoose 合成的 GPU 成本未量化（超出本任务范围）

## 6 · 给 Lead 的建议（按优先级）

1. **先做收益 1**（消除 `inferFast` 重复拷贝）：省 70.3 MB/s、占自动驾驶拷贝 42%，改动小（去掉一次 memcpy），**但必须先实测验证 CoreML 是否同步持有输入缓冲**。
2. **收益 2 次之**（`copyUpscaleFrame`）：收益最大（182.8 MB/s）但**风险高**（历史崩溃记录）且**只影响插帧开启场景**——用户当前症状（不开插帧也掉帧）可能不由此引起。
3. **建议补一个运行时诊断**：把每帧实际拷贝字节数打到日志（本报告是静态计算，真机数值可能因分辨率/模式不同）。
4. **不建议动的**：`copyNativeFrame`（0.74 MB/s，收益 0.4%）、UI 路径（已零拷贝）。
