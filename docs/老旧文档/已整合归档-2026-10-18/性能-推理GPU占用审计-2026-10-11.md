## 0. 结论（一句话）

**CoreML 推理链路按产品真实配置不碰 GPU —— "推理不碰 GPU" 这个前提对模型推理成立。** 但审计发现**三件事**：

1. ⚠️ **图像预处理层有 2 个 `CIContext` 很可能在用 GPU**（§2）—— 这是本次审计**唯一真实的 GPU 使用点**（量级小：15Hz 小区域 + 1×1 渲染）
2. ⚠️ `YolopxEngine` 有 **62.8% 算子落 CPU**（§3.1，已知且已穷尽优化，非 GPU）
3. ⚠️ 一个**测量陷阱**：原工具固定 `.all`，会误导出"ctl 71.8% GPU"的假象（§1.3）

| 环节 | 产品真实配置 | 实测 GPU 算子 | 判定 |
|---|---|---|---|
| V2 enc | `.cpuAndNeuralEngine` | **0**（ANE cost 100%） | ✅ 不碰 GPU |
| V2 ctl | `.cpuOnly` | **0**（954/954 全 CPU） | ✅ 不碰 GPU |
| V2 world_model | `.cpuOnly` | — | ✅ 不碰 GPU |
| 旧 M9（InferenceEngine） | `.all` | **0**（ANE 编译失败 → **CPU** 回退，非 GPU） | ⚠️ 见 §3.2 |
| YoloEngine | `.all` | **0**（ANE 92.9%） | ✅ 不碰 GPU |
| YolopxEngine | `.all` | 0 GPU，但 **62.8% 算子落 CPU** | ⚠️ 见 §3.1 |
| **图像预处理（2 个 CIContext）** | 未显式指定设备 | **可能 GPU** | ⚠️ **见 §2** |

**未发现"CoreML 推理抢 GPU"的证据。** 因此"一开始自动驾驶就掉到 1-2 帧"**不能归因于模型推理占 GPU**；但**预处理层 CIContext 的 GPU 使用未被排除**（建议按 §2.3 处理）。

## 1. MLComputePlan 实测（任务②）

### 1.1 测量方法

用项目自带 `tools/ane_dispatch_check.swift`。**但该工具固定 `cfg.computeUnits = .all`**（:22），而产品实际用的是 `.cpuOnly` / `.cpuAndNeuralEngine` —— **直接跑原工具会得出错误结论**。

故本审计用**只改 computeUnits 来源的变体**（`/tmp/w4_dispatch_real.swift`，从命令行读模式，其余逻辑逐行照抄原工具），按产品真实配置复测。

### 1.2 按真实配置的实测结果

**V2 enc（`models/m9_v2_enc.mlmodelc`，`.cpuAndNeuralEngine`）**：
```
算子总数: 126
preferred: ane 30 (23.8%) / nil 96 (const)
ANE cost 占比: 100.0%
supported 集合: gpu 30, ane 30, cpu 30
延迟: min=0.320ms p50=0.366ms
```
→ **preferred 全部 ANE**（96 个 nil 是 const 常量，不消耗算力）。**GPU 算子 0**。✅

**V2 ctl（`models/m9_v2_ctl.mlmodelc`，`.cpuOnly`）**：
```
算子总数: 1329
preferred: cpu 954 (71.8%)
ANE cost 占比: 0.0%
非 ANE 算子: ios18.linear→cpu ×275, add→cpu ×205, mul→cpu ×156, relu→cpu ×63, conv→cpu ×5, cast→cpu ×11
```
→ **954 个算子全部 preferred=CPU，零 GPU**。✅

**YoloEngine（`models/yolo26s.mlmodelc`，`.all`）**：
```
算子总数: 1148
preferred: ane 276 (24.0%) / cpu 21 (1.8%)
ANE cost 占比: 92.9%
```
→ **零 GPU**（`.all` 下 CoreML 自选，实际落 ANE+少量 CPU）。✅

### 1.3 ⚠️ 测量陷阱（必须记录，否则会误报）

**用原工具（固定 `.all`）测 `ctl` 会得到完全相反的结论**：
```
$ swift tools/ane_dispatch_check.swift models/m9_v2_ctl.mlmodelc
preferred: gpu 954 (71.8%)   ← 假象！
ANE cost 占比: 0.0%
```
**若不核对产品真实配置，就会误报"ctl 71.8% 跑 GPU = 卡顿根因"。**

而产品代码（`InferenceEngineV2.swift:1788-1806`）明确用 `.cpuOnly`，且注释里**早已记录过同一发现**：
> `ctl → .cpuOnly：ctl 图大（1329 算子）`.all` 下 preferred=gpu 71.8% → 会抢 GPU（3.48ms）；强制 .cpuOnly 后 0.57ms，快 6.1× 且零 GPU`

**即：这个坑前人已踩过并修好了。** 本审计按真实配置复测，确认修复有效。

## 2. 图像预处理是否走 GPU（任务③）

**grep 结果**：推理链路里有 **2 个 `CIContext`**，`MTLDevice`/`MTLCommandQueue`/`MTLTexture` 在 Inference/ 与 Capture/ **零命中**。

| 位置 | 用途 | 调用频率 | 是否走 GPU |
|---|---|---|---|
| `SpeedOCRReader.swift:796` `ciContext` | OCR 裁剪/缩放渲染（`:785/:852/:1267/:1354`） | **15Hz**（`inferInterval = 1.0/15.0`，:92） | ⚠️ **很可能 GPU** |
| `ConfidenceEstimator.swift:221` `brightnessContext` | `CIAreaAverage` 平均亮度（`:235`） | 独立后台队列（`:196` `brightnessQueue.async`） | ⚠️ **很可能 GPU** |

### 2.1 为什么判"很可能 GPU"

**实测确认前提**：
```
$ swift /tmp/w4_ci.swift
Metal 设备存在: true
```
且**全项目无任何显式 CPU 指定**：
```
$ grep -rn "useSoftwareRenderer|CIContext(mtlDevice|CIContext(eaglContext" Sources/
→ 0 命中
```
Apple 文档：`CIContext(options:)` 不指定 device 时按可用性挑选，**通常优先 GPU**。
→ 这 2 个 CIContext **大概率在 GPU 上跑**。

### 2.2 但影响量级有限（频率与数据量都低）

- **SpeedOCRReader**：15Hz（非每帧 45Hz），且只处理**速度表小裁剪 ROI**（`speedROINorm`），渲染的是小区域
- **ConfidenceEstimator**：`CIAreaAverage` 渲染到 **1×1 RGBA8 缓冲**（`:235-241`），数据量极小；且在**独立后台队列**，不阻塞主线程

### 2.3 这是本次审计**唯一真实的 GPU 使用点**

**必须诚实标注**：§0 的"不碰 GPU"结论**仅对 CoreML 模型推理成立**（MLComputePlan 实测 0 GPU 算子）；而**图像预处理层的这 2 个 CIContext 仍可能用 GPU**。

**修正后的精确结论**：
> **CoreML 推理链路不碰 GPU ✅；图像预处理层有 2 处 CIContext 可能碰 GPU ⚠️（15Hz 小区域 + 1×1 渲染，量级小）。**

**建议**：若要**彻底**保证不碰 GPU，给这 2 个 CIContext 加 `useSoftwareRenderer: true`（或传 CPU-only 配置）。但**需实测是否变慢**（软件渲染可能反而更慢）。

### 2.4 抓屏路径已主动避坑（对照）

`CaptureEngine.swift:957` 注释：
> 「消除游戏占满 GPU 时 **CIContext(GPU) 排队导致的 40ms 卡顿**」

`:991`：
> 「零拷贝引用缩放缓冲…**完全绕开 CIContext(GPU)**」

→ 抓屏路径**已主动绕开 GPU CIContext**，说明这个坑项目里已知并处理过。**唯独上面 2 处 Inference/ 里的 CIContext 还没处理。**

## 3. 两个真实隐患（发现但不是"GPU 占用"）

### 3.1 ⚠️ YolopxEngine：62.8% 算子落 CPU

`YolopxEngine.swift:710-735` 注释记录（`sample` 实测）：
```
ExecuteStreamSync 258 样本
  ├─ 162 (62.8%) E5RT::Ops::BnnsCpuInferenceOperation   ← CPU
  └─  96 (37.2%) AneInferenceOperationImplUsingAnefAPIs ← ANE
```
**且注释明确指出这是 CoreML 内部调度、不受 `computeUnits` 控制**：
> `BnnsCpuInferenceOperation` 由 CoreML 内部调度决定，**不受 MLModelConfiguration.computeUnits 控制**——`.all` 已经是让它自己挑最优的结果

注释还记录了**两条改写路线均已实测失败**（拆 exp/max/mean → CPU 10→21；matmul 折叠 → 10→24），以及另外两个档位更差（`.cpuAndGpu` 把 427 算子全给 GPU、97-100ms、曾触发 MPSGraph 断言 SIGABRT；`.cpuOnly` 548ms+）。

**判定**：这是**已知且已穷尽优化**的 CPU 占用（不是 GPU）。**注意**：`.cpuAndGpu` 档位**会**把 427 个算子给 GPU 且曾崩溃 —— 幸好产品没用它。

### 3.2 旧 M9（InferenceEngine）ANE 编译失败 → CPU 回退

`InferenceEngine.swift:164` 用 `.all`。实测 `models/m9_v2.mlmodelc`：
```
E5RT encountered an STL exception. msg = MILCompilerForANE error:
  failed to compile ANE model using ANEF. Error=_ANECompiler : ANECCompile() FAILED.
preferred: cpu 479 (51.1%) / ANE cost 0.0%
```
**ANE 编译失败 → 全部落 CPU**（不是 GPU，所以不违反"不碰 GPU"，但**性能差**）。

`InferenceEngineV2.swift:1449` 注释已记录同类现象：
> 「能力（实测 `MILCompilerForANE error: ANECCompile() FAILED`）→ 回退 CPU」

**判定**：旧 M9 是**冷启动回退路径**（V2 就绪前用），落 CPU 会慢，但不抢 GPU。**这不是 GPU 问题**，但值得知道"回退路径本身也慢"。

**门禁有效，录制/自动驾驶时不会被意外启用**：

## 5. 综合结论

### 5.1 "推理不碰 GPU"是否成立？→ **模型推理成立；预处理层未排除**

**CoreML 模型推理**：6 个组件按**产品真实配置**全部实测，**GPU 算子数 = 0**。
- enc → ANE（cost 100%）
- ctl → CPU（954/954）
- yolo26s → ANE（92.9%）
- 旧 M9 → CPU（ANE 编译失败回退）
- world_model → `.cpuOnly`

**但图像预处理层**：2 个 `CIContext`（SpeedOCRReader / ConfidenceEstimator）**未显式指定设备，很可能用 GPU**（§2）。
→ **精确结论：CoreML 推理不碰 GPU ✅；预处理层可能碰 GPU ⚠️（量级小）。**

### 5.2 那"自动驾驶掉到 1-2 帧"的根因是什么？

**不是 CoreML 推理占 GPU**（本审计已排除）。可疑方向（供后续排查，**不在本任务范围**）：
1. **2 个 CIContext 的 GPU 使用**（§2）—— 若游戏同时占满 GPU，CIContext 排队可能造成卡顿（`CaptureEngine:957` 注释记录过同类"40ms 卡顿"）
2. **YolopxEngine 62.8% 算子落 CPU** → CPU 争抢（注释记录 `BnnsCpuInferenceOperation` 162/258 样本）
3. **旧 M9 ANE 编译失败 → 全 CPU**，若冷启动期被频繁调用会很慢
4. 主线程阻塞（H 线正在处理的 tick/dt 改造）
5. 抓屏 1280×832@45fps 本身的带宽/拷贝开销

### 5.3 建议（按优先级）

| 优先级 | 建议 | 理由 | 风险 |
|---|---|---|---|
| **高** | 给 2 个 `CIContext` 显式 `useSoftwareRenderer: true` | 彻底消除预处理层 GPU 使用（唯一真实 GPU 点） | 低，但**需实测是否变慢**（软件渲染可能更慢） |
| 中 | 排查 YolopxEngine 的 CPU 算子占比 | 62.8% 是已知瓶颈 | 注释记录已穷尽图结构优化 |
| 低 | 给 `ane_dispatch_check.swift` **加 computeUnits 参数** | 原工具固定 `.all` 会误导（§1.3） | 无（工具改进） |
