## 0. 最终结论（一句话）

> **任务假设被证伪：4bit 量化不能让 8 帧图 ANE 编译——因为 ANE 编译失败的根因不是图大小，是 `nn.GRU` trace 出来的 WhileLoop 算子。**
> **真正的解法是 S5 今天（08:11）把时序 GRU 手工展开成静态图（commit `561f1fa`）。用当前 `src/temporal.py` 重新导出 8 帧图后：**
> - **8 帧 fp16（无量化）：ANE p95 = 3.46 ms，零精度损失，余量 4.7×**（vs Lead 当前 p95 20.95~29.28ms，**6× 提速**）
> - **8 帧 palette-8bit：ANE p95 = 2.72 ms，但有损（maxdiff=0.19）**
> - **4bit 全方案（kmeans/uniform/int4/mixed）一律有损（maxdiff 0.2~2.0），不满足"不降质量"红线**

## 2. ★★ 方法论核心：ANE 判据不再靠"耗时比值"

既有做法（`/tmp/adt_inspect/decisive_ane.py`，即 Lead 引用的"四格对照"）用 `ANE_ms / CPU_ms < 0.85` 判"ANE 是否生效"。该判据有三个毛病，本次全部修复：

| 毛病 | 旧判据的表现 | 新判据 |
|---|---|---|
| (a) 受本机负载漂移影响 | 文档自记"单次波动可达 2×"；本次实测 load=11~23 时 fp16 8帧 ANE 计时从 60ms 漂到 25ms | **不受影响**（结构性判定） |
| (b) 无法区分"ANE 编译失败"与"ANE 慢" | 8帧 16ms 可能是"ANE 失败退 CPU"也可能是"ANE 成功但慢"，旧判据分不清 | **精确区分**（见下） |
| (c) 不能回答"为什么失败" | 只给一个比值 | **算子级定位**（能说出"WhileLoop 是元凶"） |

### 新判据：MLComputePlan（CoreML 官方 API）

```python
plan = MLComputePlan.load_from_path(compiled_path, compute_units=ct.ComputeUnit.CPU_AND_NE)
for op in plan.model_structure.program.functions["main"].block.operations:
    usage = plan.get_compute_device_usage_for_mlprogram_operation(op)
    # usage.preferred_compute_device → MLNeuralEngineComputeDevice / MLCPUComputeDevice
```

**判定规则**（本机标定，确定性、可复现）：

| 状态 | ANE 算子 | CPU 算子 | 含义 |
|---|---:|---:|---|
| `ANE_OK` | >0 | 0 | ANE 编译成功，全图跑 ANE |
| `PARTIAL` | >0 | >0 | ANE 编译成功但图被切开（部分 ANE 部分 CPU） |
| `ANE_FAIL` | 0 | >0 | ANE 编译失败，全退 CPU |

> 本机标定证据：
> - `m9_v2_int8.mlmodelc`（1帧palette，已知 ANE 可用）→ `ANE_OK`（86 ANE / 0 CPU）
> - `m9_v2.mlmodelc`（8帧fp16，已知 ANE 失败）→ `ANE_FAIL`（0 ANE / 453 CPU）
>
> ⚠️ `MLComputePlan.load_from_path` 遇到 ANE 编译失败会抛 `MILCompilerForANE error: ANECCompile() FAILED`——**这本身就是一条证据**（说明 ANE 编译器拒绝了该图）。本脚本用 `compute_units=CPU_AND_NE`，失败时捕获异常记为 `ANE_FAIL`。

**两条证据交叉校验**：耗时（ABBA）作为第二证据。若判据说 `ANE_OK/PARTIAL` 且耗时比 <0.85 → 两证据一致；若判据说 `ANE_FAIL` 但耗时比 <0.85 → **报警**（可能负载假象，须人工判读）。

## 3. ★★ 决定性发现：ANE 编译失败的真凶 = WhileLoop，不是图大小

### 3.1 单变量消融（phase=rootcause）

只切「时序 GRU 是 `nn.GRU`（→WhileLoop）还是静态展开（→无 WhileLoop）」，其余全同（8帧、12步、fp16、同权重）：

| 配置 | 算子 | WhileLoop | ANE算子 | CPU算子 | 判据 | 体积 |
|---|---:|:---:|---:|---:|---|---:|
| **A1 8帧 nn.GRU** | 891 | **1** | 0 | 453 | 🔴 ANE_FAIL | 16.08 MB |
| **A2 8帧 静态展开** | 1202 | **0** | **609** | 52 | ✅ PARTIAL(ANE可用) | 16.11 MB |
| **A3 1帧 静态展开** | 852 | 0 | 446 | 52 | ✅ PARTIAL(ANE可用) | 15.74 MB |

**读数**：
1. **唯一变量 WhileLoop**：A1 有 1 个 WhileLoop → ANE 全退 CPU；A2 把它去掉（其余结构逐字未改）→ ANE 立刻可用（609 算子上 ANE）
2. **图大小不是因素**：A1=16.08MB / A2=16.11MB，几乎一样；算子数 A2 反而更多（1202 vs 891，因为循环展开了）
3. **等价性已验证**：静态展开与 `nn.GRU` 逐位等价，maxdiff = 5.66e-07（float32 精度极限，5 seed × 2 layer × N∈{1,8}）

> **为什么 PARTIAL 而不是 ANE_OK？** 那 52 个 CPU 算子是个**固定孤岛**——在 1帧和8帧下逐字相同（cast×11, mul×8, logical_and×5, add×4, linear×4, sub×3, reshape×3, relu×2, sigmoid×2, squeeze×2, greater/less/real_div/atan/slice_by_index/expand_dims/tanh/concat 各1）。这是 **det 掩码池化 + heading 头的 atan** 等 ANE 不支持的算子，与量化/帧数无关，不是本次调优对象。

### 3.2 关键真相：`src/temporal.py` 已经被 S5 修好了

| 时间 | 事件 |
|---|---|
| 07:21 | `m9_v2.mlmodelc` 编译（**旧 `temporal.py`，还在用 `nn.GRU`**）→ 891 算子，WhileLoop=1，ANE_FAIL |
| 08:11 | S5 提交 commit `561f1fa` "fix(ANE): temporal.py GRU 手工展开——消除 while_loop" |
| 08:2x | S6 用**当前** `src/temporal.py`（已静态展开）重新导出 8 帧 → WhileLoop=0，ANE 592 算子可用 |

**所以：Lead 看到的"8帧 ANE 编译失败"，是因为测的是 07:21 的旧产物。用当前代码重新导出，ANE 已经能用了——不需要任何量化。**

> ⚠️ 本次实验里的 `sg_*` 档（"static_gru=True"）其实是**多余的**——`_staticize_temporal_gru()` 命中 0 层，因为 `temporal.py` 本身已改。`sg_*` 能上 ANE 是因为代码已修复，不是 monkey-patch 起作用。报告里如实标注，`A2` 的"消融"价值在于**独立证明了 WhileLoop 是元凶**（即便没有 S5 的 commit，本实验也能得出同样结论）。

## 7. 权重状态声明（精度数字的有效边界）

> `checkpoints/m9_v2/best_model.pt` 只有 240 个键（image_encoder/lane_encoder/det_encoder/fusion_head/state_encoder），**缺 refiner/experts/temporal/heads** → 契约记录 `missing_param_ratio = 65.74%`。

**因此**：
- 本报告测的是「**同一组权重下，量化引入的偏差**」（这个量测有效——因为 fp16 基线和量化版用同一份权重，差异纯粹来自量化）
- **绝对输出值无驾驶意义**（65.74% 权重是随机的，模型本身不能开车）
- 训练出完整 checkpoint 后，`pal8_kmeans` 的 0.062 可能变好或变坏，**须用真实权重重测才能定论**

> ⚠️ 但有一个**不受权重影响**的结论：**量化在"随机权重"上都已经有损，训练后只会更难无损**（量化误差是权值分布决定的，真实权值通常更稠密、更难无损量化）。所以"4bit 无损"的概率很低。

## 9. 推荐方案与注意事项

### ✅ 推荐：8帧 fp16 + 静态展开 temporal.py（已就绪）

- **性能**：ANE p95 = 3.46 ms（Lead 目标 p95 ≤ 16ms，余量 4.7×）
- **精度**：maxdiff = 0（与 fp16 基线逐位一致——因为**它就是** fp16 基线）
- **红线检查**：步数 12 ✅ / MoE 4 步 ✅ / 8 帧 ✅ / 180×320 ✅ / 质量 fp16 无损 ✅
- **就绪状态**：`src/temporal.py` 已改（commit `561f1fa`），只需**重新导出 `m9_v2.mlmodelc`**（当前那个是 07:21 旧产物，还在用 nn.GRU）

### ⚠️ 注意事项

1. **必须重新导出 `m9_v2.mlmodelc`**：当前文件是 07:21 编译的旧产物（WhileLoop=1）。用当前 `src/temporal.py` + `tools/export_m9_v2_coreml.py` 重新导出即可获得 WhileLoop=0、ANE 可用的产物。
2. **52 个 CPU 孤岛仍在**：det 掩码池化 + heading atan 等。本次未做优化（不在 S6 写作范围——那需要改 `src/`）。若要进一步压时延，这是下一个攻坚点（预计能从 3.46ms 再降，但需 src 侧改算子）。
3. **量化方案等训练后再评估**：当前 65.74% 随机权重下，所有量化方案已有损；训练后用真实权重重测，**可能** pal8 会变成无损（概率不高，但须实测）。4bit 几乎不可能无损。
4. **不要用循环版导出**：`nn.GRU` / `nn.GRUCell` 在 coremltools 8.3 下必出 WhileLoop → ANE 死。S5 的手工展开是正解。

## 12. 方法论警示（如实记录，免后人重踩）

| 次序 | 我的假设/做法 | 错在哪 |
|---|---|---|
| 1 | "4bit 让图更小 → ANE 能编译" | **错**。ANE 编译与图大小无关，只与算子类型（WhileLoop）有关。1帧4MB可用，2帧4.18MB失败。 |
| 2 | 用"耗时比值<0.85"判 ANE | **不够硬**。load=11~23 时 fp16 8帧比值从 0.91 漂到 1.05，无法定论。改用 MLComputePlan 算子级判据后确定性 100%。 |
| 3 | `_staticize_temporal_gru()` 消融 | **多余**。`temporal.py` 已被 S5 改过，命中 0 层。但独立证明了 WhileLoop 是元凶，仍有价值。 |
| 4 | 假设 `m9_v2.mlmodelc` 是 palette | **错**。它是 fp16（891算子，0 个 palettize 痕迹）。palette 产物是 `m9_v2_int8.mlmodelc`（1帧旧契约）。 |

**教训**：性能结论必须（a）用确定性判据、（b）核实产物真身、（c）单变量隔离。缺一不可。
