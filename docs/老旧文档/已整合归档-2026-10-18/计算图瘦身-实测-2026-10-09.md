## 0. 测量工具的三次踩坑（必须先交代，否则结论不可信）

本报告的结论高度依赖测量工具的可靠性。本人在搭实验台时连续踩了三个坑，每一个都会导致**完全相反的结论**，故先如实交代：

### 坑 A：`contextlib.redirect_stderr` 抓不到 CoreML 的 C++ 日志
第一版用 `redirect_stderr` 检测 ANE，**所有**变体都报 `ane_ok=True`（包括实际失败的基线）。
根因：`redirect_stderr` 只换掉 Python 的 `sys.stderr` 对象，**抓不到 CoreML/Espresso 在 C++ 层直接写 fd 2 的日志**。
→ 修法：最终用**子进程级**捕获（`subprocess.run(capture_output=True)`），子进程退出时的 flush 也能被完整捕获。

### 坑 B：同一进程加载多个模型 → 全部变慢 2.1×
第一版在**同一进程**里加载 7 个模型一起 ABBA 测，结果基线从 36.9ms 抬到 78.9ms，**所有模型都慢了一倍**。
根因：CoreML/Espresso 把多个模型一起加载后，各自的计算计划互相挤占 ANE/GPU 资源。
→ 修法：每个模型在**自己的子进程**里加载+测量，进程退出后资源彻底释放。

### 坑 C：死子图证明必须固定 `torch.manual_seed`
第一版没固定 seed，`load_state_dict(strict=False)` 后缺失的 96 个键保持 build 时的随机初始化。两次 build 随机数不同 → 对比出的 maxdiff（no_refiner=1.29、no_moe=2.79、no_temporal=0.85）**全是随机权重差异**，跟"删了哪个子图"毫无关系。
→ 修法：固定 `torch.manual_seed(0)` 后，所有变体在缺失权重上逐位一致，唯一变量就只剩被删的子图。修正后 maxdiff 全部归零。

**这三个坑共同说明**：性能测量里"看起来快了"或"看起来无损"经常是测量工具在骗自己。本报告所有数字都经过修正后的协议复测。

## 2. RepVGG 重参数化是否彻底（方向 2）

**结论：✅ 彻底折叠，无残留。**

```
rbr_1x1        出现    0 次
rbr_3x3        出现    0 次
rbr_identity   出现    0 次
rbr_reparam    出现   72 次   ← 18 个 RepVGGBlock × (3×3 conv + bias)
```

`src/model_v2.py` 的 `RepVGGBlock.reparameterize()` 把三分支（3×3 + 1×1 + identity）数学等价合并成单个 3×3 卷积并 `del` 训练分支。导出脚本走「训练态构建 → load → reparameterize」流程（坑 6），导出的图里**只有 `rbr_reparam` 一条单路 3×3**，无 1×1 / identity 残留。

**此项无可瘦身**——已经折叠到极限了。

## 3. MoE 6 专家"全算再加权"（方向 3）

**结论：无解（如任务所述如实报告），但有个更深的发现。**

### 3.1 软路由是"全算再加权"

`IterationRefiner.forward` 的 MoE 实现（`src/model_v2.py:1146-1155`）：
```python
expert_out = torch.zeros_like(refined)
for e in range(self.num_experts):           # 6 个专家全部前向
    w = expert_weights[:, e:e+1]            # 软权重
    expert_out = expert_out + w * self.experts[e](refined)
```
6 个专家**全部计算**再按 softmax 权重加权求和。这是 Lead 拍板要的"可微软路由"——argmax 硬路由不可微，训练梯度传不过去，且 coremltools 会把 argmax/gather 降级成 `select`（照样全算）。**这条路确实无解**，方向 3 如实报告。

### 3.2 更深的发现：MoE 的 `expert_out_proj` 权重从未训练

| 参数 | checkpoint 里有？ | 值 |
|------|------------------|-----|
| `refiner.refiner_proj.weight` | ❌ 缺失 | **全零**（零初始化，`model_v2.py:1101`） |
| `refiner.expert_out_proj.weight` | ❌ 缺失 | **全零**（零初始化，`model_v2.py:1090`） |

→ MoE 专家输出经过 `expert_out_proj`（零矩阵）→ **贡献恒为 0**。即"6 专家全算再加权"的加权结果再乘零矩阵 = 0，**整条 MoE 支路对当前 checkpoint 是死代码**（见 §4 数值证明）。

⚠️ 这是 checkpoint 不完整（缺 96 键 / 65.7% 随机初始化）导致的，**不是设计缺陷**。等 checkpoint 训练完整后 MoE 会真正生效。但**当前**它确实是死代码，删掉它数值无损（§4 已证）。

## 4. 「死子图」无损性证明（方向 1/3/4 的前置）

**方法**：对同一个已训练模型，固定 `torch.manual_seed(0)` 后逐个子图做"替换前 vs 替换后"前向对比，覆盖 6 个边界用例。maxdiff == 0.0 即逐位相同——比 <1e-3 更强的无损证据。

| 替换 | worst maxdiff（6 用例） | 证明 |
|------|----------------------|------|
| 去掉整个 refiner（12步GRU+4步MoE） | **0.000000e+00** | refiner_proj + expert_out_proj 全零 → 贡献=0 |
| 去掉 MoE（保留 12步GRU） | **0.000000e+00** | expert_out_proj 全零 → 专家支路贡献=0 |
| 去掉时序编码器 | **0.000000e+00** | temporal_proj 全零 → 时序修正=0 |

**三个子图对当前 checkpoint 都是死代码**，删掉数值逐位相同。这是因为 checkpoint 缺这些模块的权重，而它们的"出口投影"（refiner_proj / expert_out_proj / temporal_proj）都是零初始化。

> ⚠️ 这些是"当前无损"，不是"永远无损"。等 checkpoint 训练完整、这些投影学到非零权重后，删它们就会改变输出。但**当前**确实可删。

### 4.1 GRU 展开的数学等价性（方向 4 的数值验证）

`_UnrolledGRU`（静态展开 8 帧）vs `nn.GRU`（while_loop）：

```
fp32 数学等价性 maxdiff = 5.96e-07   ← float32 精度极限（eps·2）
ref 范围 = [-2.25, 2.16]
相对误差 = 2.8e-07
```

→ 静态展开与 while_loop 在 fp32 下**逐位等价**（差值在机器精度内）。CoreML 里的差异来自 fp16 舍入，不是展开本身引入的。

## 5. 时序 GRU while_loop → 静态展开（方向 4）★ 决定性发现

### 5.1 现象：ANE 编译失败

`ct.models.MLModel("models/m9_v2.mlpackage", compute_units=.all)` 推理时：
```
E5RT encountered an STL exception.
msg = MILCompilerForANE error: failed to compile ANE model using ANEF.
      Error=_ANECompiler : ANECCompile() FAILED.
```
ANE 编译失败 → CoreML 静默回退 CPU → p50 26.95ms（实测）。

### 5.2 根因：`while_loop` 把整个图踢出 ANE

通过**消除变量**隔离定位：

| 变体 | while_loop | 算子 | ANE | p50 | p95 |
|------|-----------|------|-----|------|------|
| V0 baseline（旧源码） | 1 | 538 | ❌ | 42.34ms | 204.28ms |
| V1 去整个 refiner（while_loop 仍在） | 1 | 187 | ❌ | 44.84ms | 136.08ms |
| V2 去 MoE（while_loop 仍在） | 1 | 382 | ❌ | 48.01ms | 105.99ms |
| **V3 去时序（while_loop=0）** | **0** | 499 | **✅** | **5.10ms** | **7.68ms** |
| V4 GRU 展开（while_loop=0） | 0 | 661 | ✅ | 4.29ms | 6.50ms |
| **V7 当前源码**（while_loop=0） | **0** | 644 | **✅** | **3.33ms** | **5.90ms** |

**关键对比**：
- V1 把算子砍到 **187**（比 V3 的 499 少 62%），但只要 while_loop 在 → 44.84ms（ANE 仍失败）
- V3 把算子留在 **499**，只是去掉 while_loop → 5.10ms（ANE 成功）

**算子数从 538 砍到 187 没有任何收益，去掉 1 个 while_loop 却换来 8.3× 提速。** 这是本报告最重要的发现。

### 5.3 机理：为什么 while_loop 这么贵

CoreML 的 `while_loop` 是动态循环算子，ANE 编译器无法对动态循环做静态调度。只要图里有**一个** while_loop，ANE 编译器就会**放弃整张图**，把所有算子派给 CPU/GPU。时序 GRU 的 while_loop 体里有 28 个算子，8 帧循环展开后相当于 224 个运行时算子——但问题不在算子数，而在"动态循环"这个结构本身让 ANE 拒收整图。

### 5.4 验证：ANE 确实在用（不只是没报错）

用 `compute_units` 对照测（V7）：
```
ALL      p50= 3.33ms   ← ANE 生效
CPU_ONLY p50=45.73ms   ← 强制 CPU
```
`.all` 比 `.cpuOnly` 快 **13.7×** → ANE 确实在跑，不只是"没报错"。

### 5.5 现状：已被 S5/Lead 修复

`src/temporal.py` commit `561f1fa`（2026-10-09 08:11，S5 用 `MLComputePlan` 实测发现）已把 `nn.GRU` 改成手工展开的 `_StrictGRUCell`×8，消除 while_loop。本报告是**独立交叉验证**：用 V7（当前源码）复测，ANE 成功、p95 5.90ms，与 S5 结论一致。

## 6. 权重去重 `deduplicate_weights`（方向 6）

**结论：无对象可去——权重本来就不重复。**

### 6.1 API 现状
`ct.optimize.coreml.deduplicate_weights` 是 **coremltools 9.x 的 API**，本机 8.3 没有。但 8.3 的 MIL pass pipeline 里有默认 pass `common::const_deduplication`（在 frontend/default/backend 三个阶段各跑一次），转换完成时重复常量**已经被自动折叠**。

### 6.2 实测：0 重复权重
```
models/m9_v2.mlmodelc/model.mil:
  BLOBFILE 引用数 = 113
  互不相同的 offset = 113   ← 重复引用数 = 0
```

### 6.3 "权重复用"≠"权重重复"
本模型的 `refiner_proj` 被 16 个 linear 算子引用、`cells.0.h_r` 被 12 个 linear 引用——这是"**同一个 const 张量被多个算子共享**"，本来就是**一份存储**，不存在冗余副本。去重无对象可去。

**此项无可瘦身。**

## 7. FusionHead / 辅助头冗余（方向 5）

**结论：有真冗余，但收益极小（<0.1ms），不值得改。**

### 7.1 risk_head 的 det_feat 重复拼接
`src/risk_head.py:261`：当 `det_feat.dim()==2` 且 `det_pool=='max_mean'` 时：
```python
return torch.cat([det_feat, det_feat], dim=1)   # [B, 2D]，第二份是第一份的复制
```
MIL 里对应 `x_cast_fp16 = concat(..., det_feat_cast_fp16, det_feat_cast_fp16, ...)`，即 **128 维重复**。理论上可以只存一份、把 fc1 对应列求和——但 fc1 是 `[769, 128]` 的常量权重，这个"求和"会被 coremltools 常量折叠掉，**运行时不省算子也不省时间**。

### 7.2 各头 MACs 占比
```
image_encoder    8.0087 GMACs    99.5%
refiner          0.0365 GMACs     0.5%
lane_encoder     0.0039 GMACs     0.0%
fusion_head      0.0004 GMACs     0.0%
temporal_encoder 0.0003 GMACs     0.0%
risk_head        0.0001 GMACs     0.0%
heading_head     0.0001 GMACs     0.0%
```
辅助头加起来 <0.01 GMACs，即使全删也省不了可测量的时间。**此项不值得改。**

## 11. 对 Lead 的建议

1. **while_loop 已修复**（S5 commit 561f1fa）→ V7 当前源码 p95 **5.90ms**，远低于 16ms 目标，余量 2.7×。**这条线已达标**。
2. **死子图去冗余**（V6）还能再压到 p95 5.40ms，但这是"当前无损"（依赖 checkpoint 不完整）。若 checkpoint 会继续训练，不建议采纳；若当前 checkpoint 就是最终版，可采纳。
