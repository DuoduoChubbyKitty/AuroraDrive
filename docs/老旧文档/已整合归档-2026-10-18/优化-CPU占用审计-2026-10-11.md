## 1 · Q1：UI 帧无条件生成（重点审计）

### 1.1 现状确认

`CaptureEngine.swift:1151-1227`：帧回调里 `vImage` 缩放到 480×312 → `CGDataProvider` 零拷贝 → `CGImage` → `NSImage` → `onFrame?(nsImage, cgImage)`。**无门禁，每帧无条件执行**。

### 1.2 消费者清单（grep + read 逐个核实）

| 消费者 | 行号 | 条件 | 门控后是否安全？ |
|---|---|---|---|
| `pendingFrame` 写入 | `AuroraDriveApp.swift:5993-5994` | `onFrame` 回调（captureQueue） | 闭包注册即每帧 |
| `currentScreenImage` + `currentFrameCG` 赋值 | `:6906-6907` | tick 消费 pendingFrame | **tick 每帧读** |
| **V2/M9 推理输入** | **`:7090`** | `if let cg = currentFrameCG { inferenceEngineV2.infer(image: cg, ...) }` | ❌ **驾驶必需** |

| 流推流 | `:6907` | `if isStreaming, let cg = latestCG` | ✅ 已有门禁 |

### 1.3 P3 门控公式的错误

P3 建议：`needUIFrame = isPanelVisible || isRecording || isStreaming || isDriving`

**实测发现**：`currentFrameCG` 在 `:7090` 被读作 **V2/M9 推理输入**（`inferenceEngineV2.infer(image: cg, ...)`）。P3 公式**包含了 `isDriving`**，所以驾驶时不会关——**公式本身不危险**，但**遗漏了 shm publish**（`EngineMain.swift:1142` 无条件读 `st.currentFrameCG`，即使 UI 进程不看，发 nil 也无害）。

### 1.4 正确的门控

```swift
// 帧回调里，UI 路径（:1001 起）可加：
let needUIFrame = isDriving || isStreaming || isRecording || (AuroraFlags.questOCR && isPanelVisible)
guard needUIFrame else { return }   // 纯待机时跳过 vImage 480px + CGImage + NSImage
```

**省什么**：待机时 vImage 480px 缩放（0.218ms）+ CGDataProvider/CGImage/NSImage 创建。不影响驾驶、不降帧率、不降分辨率。

**风险**：`isDriving` 变化瞬间——从 false→true（用户点"开始驾驶"）的第一帧，若 `onFrame` 还没开始写 `pendingFrame`，`currentFrameCG` 为 nil → tick 里 `if let cg` 跳过推理。但这只是**冷启动一帧延迟**，下一帧即恢复。与现有"冷启动 V2 timelineReady<2 回退 M9"机制一致。

### 1.5 ⚠️ 频率口径冲突（如实标注）

代码现状（grep 结果）：
- `EngineMain.swift:661` `engineTickHz` —— **已是 `static var = 20.0`**（非我 task-80 留的 45；后续被改成 20）

## 2 · Q2：三处 vImage 缩放能否合并

### 2.1 三者对比

| 路径 | 源尺寸 | 目标尺寸 | 缩放方式 | 核/语义 |
|---|---|---|---|---|
| YOLO | 1280×832 | 640×640 | `vImageScale_ARGB8888` | **拉伸**（不保宽高比） |
| UI | 1280×832 | 480×312 | `vImageScale_ARGB8888` | **等比**（保宽高比） |
| YOLOPX | CGImage | 640×640 | **CGContext**（`drawLetterbox`） | **letterbox**（等比+灰边 114） |

### 2.2 为什么不能合并

1. **YOLOPX 不用 vImage**：`YolopxEngine.swift:1531-1568` `drawLetterbox` 用 CGContext 路径。**vImage 版已实测证伪**（`:1536-1559`）——切换后检测框 9→6、可行驶区 26.19%→22.53%，**功能性回退**。根因是采样核不同（`kCGInterpolationMedium` vs `vImageScale`，最大像素差 49/255）。
2. **YOLO 拉伸 vs UI 等比**：语义不同。YOLO 训练在拉伸图上（640×640 直接拉伸），UI 要保宽高比显示。
3. **先缩到中间尺寸再复用**：三个目标的**宽高比处理**不同（YOLO 不保、UI 保、YOLOPX 保+灰边），中间尺寸满足不了三者，反而多一次缩放。

**结论**：P8 说的对，不能简单合并。**三者各自缩放是语义正确的**。

## 3 · Q3：extractMask 成本

### 3.1 实现（`YolopxEngine.swift:1264-1320`）

- 输入：`MLMultiArray [1,2,640,640]`（da 或 ll，fp16/f32 按 dtype 分派）
- 算法：逐像素 argmax → 4×4 多数表决下采样 → 160×160 网格
- 复杂度：O(640²) = 409,600 次/掩码，两个掩码 = 819,200 次/帧
- 纯 CPU，无 GPU/ANE 参与

### 3.2 是否重复计算

调用点（`:1020-1022`）在**推理 completion handler 内**（异步队列），对 da + ll 各调一次。无重复。

### 3.3 降级时是否白跑

```
:906  guard !isInferencing else { return }   // 上一帧没跑完就跳过
```
降级（YOLOPX 没加载/没出结果）时 `isInferencing` 不会置 true → 不进入推理 → completion 不触发 → `extractMask` **不被调用**。✅ 不白跑。

## 5 · Q5：isInferencing 跳帧率

### 5.1 逻辑（`YolopxEngine.swift:906`）

```swift
guard !isInferencing else { return }   // 防重叠：上一帧没跑完就跳过
```

标准 guard-skip：上一帧推理未完成 → 本帧跳过。**跳帧后 tick 用上一次的 lastResult**（已确认：tick 读 `yolopxEngine.detections` / `yolopxEngine.laneMask`，这些是上次 `finish()` 写的，不会 nil）。

### 5.2 跳帧率

- `minInferenceIntervalMs` 默认 0（`:943` 注释：固定间隔会变额外瓶颈，已关闭）
- 所以跳帧纯靠 `isInferencing`：服务 183ms、tick 间隔 50ms（20Hz）→ ~67% 的 tick 被 skip
- 服务 183ms、tick 间隔 33ms（30Hz）→ ~82% 的 tick 被 skip
- **这是正常的**（yolopx legacy 本来就是 12Hz 级别的模型，30Hz tick 自然会跳大部分）

### 5.3 跳帧后 tick 行为

tick 里读 `yolopxEngine.detections` / `yolopxEngine.laneMask`——这些是上次 `finish()` 写的旧值。**不会 nil**（引擎启动后第一帧推理完成后就有值）。驾驶决策用"最近一次 YOLOPX 结果"是设计预期，不是 bug。
