## 1. 🔴 画面变形（重点标注，任务要求的第 6 项）

### 1.1 代码事实

`RecordEngine.swift:566-591`（`resizeAndEncodeJPEG`）：
```swift
566: private func resizeAndEncodeJPEG(image: NSImage, size: CGSize) -> Data? {
567:     guard let cgImage = image.cgImage(forProposedRect: nil, context: nil, hints: nil) else { return nil }
569:     guard let context = CGContext(
570:         data: nil,
571:         width: Int(size.width),      // 640
572:         height: Int(size.height),    // 360
...
579:     // 绘制（保持比例填充，可能裁切，与 UI 显示一致）   ← ★ 注释说"保持比例"
580:     context.interpolationQuality = .high
581:     context.draw(cgImage, in: CGRect(origin: .zero, size: size))   ← ★ 实现是"填满"
```

**🔴 注释与实现不符**：
- 注释：「保持比例填充，可能裁切」
- 实现：`context.draw(cgImage, in: CGRect(origin: .zero, size: size))` —— 把**整个源图拉伸填满**目标矩形
  - `CGRect(origin:.zero, size: size)` 的宽高**就是目标尺寸**，没有做 aspect-fit 计算
  - **既没有保持比例，也没有裁切** → **纯拉伸变形**

### 1.2 变形量化（实测推算）

`targetSize`（`RecordEngine.swift:31`）：`CGSize(width: 640, height: 360)`

| 项 | 值 |
|---|---|
| 源（抓屏输出） | **1280×832**（3:2，来自 2560×1664 屏按比例缩放） |
| 目标（录制帧） | **640×360** |
| 源 aspect | 1280/832 = **1.5385** |
| 目标 aspect | 640/360 = **1.7778** |
| **X 缩放** | 640/1280 = **0.5000** |
| **Y 缩放** | 360/832 = **0.4327** |
| **各向异性** | **1.1556 → 差 15.6%** |

**物理效果**：
- 屏幕上的**正圆 → 录制帧里变成椭圆**（宽高比失真 1.156）
- **水平方向被额外压扁 15.6%**

### 1.3 变形链全貌（多环节核对）

| 环节 | 尺寸 | aspect | 变形 |
|---|---|---|---|
| ① 屏幕原生 | 2560×1664 | 1.5385 | （基准） |
| ② SCStream 抓屏输出 | **1280×832** | 1.5385 | ✅ 等比（Lead 已修，按屏比例算） |
| ③ **RecordEngine 录制帧** | **640×360** | **1.7778** | **⚠️ 非等比 +15.6%（唯一变形环节）** |
| ④ dataset_v2 训练输入 | 320×180 | 1.7778 | ✅ 等比（③④ 一致，不再累积） |

**结论**：**变形 100% 由 `RecordEngine` 的 640×360 引入**，且**会写进训练数据**。

### 1.4 影响面

| 影响 | 说明 |
|---|---|
| **训练数据画面变形** | 模型学到"被压扁 15.6% 的世界" |
| **训练/推理不一致** | 推理时输入是 `currentFrameCG`（180×320，从 1280×832 缩放）——**需核实推理侧是否同样变形** |
| 车道线/检测框几何 | 归一化坐标不受影响（都是比例），但**形状**变了 |

> ⚠️ **关键补充**：`dataset_v2.py:811-812` 会**再 resize 到 180×320**（aspect 1.7778）→ **与 640×360 等比，不再累积变形**。所以**变形只在 ③ 引入一次**。

### 1.5 建议（不违反"不降分辨率"铁律）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 改 `targetSize` 为 **640×416**（保持 1.5385） | 分辨率微增（640×416 > 640×360），**不降分辨率** ✅ |
| **B** | 保持 640×360，但改 `context.draw` 为 **aspect-fit + 裁切**（裁掉左右或上下多余） | 会**丢失画面边缘**（裁切），但不变形 |
| **C** | 保持 640×360，用 **letterbox**（加黑边） | 画面有黑边，训练数据含黑边 |
| **D** | 把抓屏输出改成 **16:9**（如 1280×720） | 但那会让 SCStream letterbox → 归一化坐标错位（Lead 已否决） |

**我的建议**：**方案 A**（`targetSize` 改 640×416）—— 唯一"不降分辨率、不变形、不丢画面"的方案。

> ⚠️ **但改 targetSize 会让 `dataset_v2` 的 180×320 输入变成非等比**（640×416 → 320×180 会是 -13.5% 变形）。
> **完整修法**：`targetSize = 640×416` **且** `dataset_v2.image_size` 同步改 `(208, 320)`（保持 1.5385）。
> **或者**：接受训练输入为 16:9，让 `targetSize` 也 16:9 —— 但这需要抓屏就输出 16:9（与方案 D 冲突）。
> **⟹ 这是一个需要跨线（Swift 录制端 + Python 训练端）协同的决策，建议 Lead 统一裁定。**

### 1.6 ⚠️ 重要澄清：训练与推理**相互一致**（不是不一致）

**审计发现推理侧也有同样的拉伸**（`InferenceEngineV2.swift:3016`）：
```swift
context.draw(cgImage, in: CGRect(x: 0, y: 0, width: width, height: height))
//                                  ↑ width=320, height=180（填满，非 aspect-fit）
```

**两条路径的变形对照**：

| 路径 | 源 aspect | 目标 | 目标 aspect | 变形 |
|---|---|---|---|---|
| **推理**（`V2ImagePreprocessor`） | 1.5385 | 320×180 | **1.7778** | **+15.6%** |
| **训练**（`RecordEngine` → `dataset_v2`） | 1.5385 | 640×360 → 320×180 | **1.7778** | **+15.6%** |

**结论**：
- ✅ **训练与推理的输入 aspect 完全相同（都是 1.7778）→ 相互一致，功能上自洽**
- ⚠️ **但两者都相对真实世界变形了 +15.6%** → **几何失真**（车道线角度、物体宽高比、消失点位置都不对）
- ⟹ **不是"训练/推理不一致"的 bug，而是"共同失真"的质量问题**

> 📌 **这意味着**：模型不会因为变形而"训练推理对不上"，但会**学到一个被压扁的世界**——
> 例如 45° 的车道线在输入里显示为约 50°；正方形目标变成 1.156:1 的长方形。
> **对纯端到端模型可能影响有限**（它只需学到一致的映射），**但对几何敏感的辅助任务（车道线曲率/角度）会有系统性偏差**。

**修法建议（两处必须同步改，否则会引入真正的不一致）**：
1. `RecordEngine.targetSize`：640×360 → **640×416**
2. `dataset_v2.DEFAULT_IMAGE_SIZE`：`(180, 320)` → **`(208, 320)`**
3. `InferenceEngineV2.imageHeight/imageWidth`：180×320 → **208×320**（**并且模型需重新导出**，因为 CoreML 图里烘死了输入 shape）

> ⚠️ **第 3 条代价大**（要重新训练/导出模型）。**因此更务实的方案可能是**：
> **接受 16:9 变形**，但**在文档里明确记录**这一几何失真，避免后续有人误以为输入是"真实比例"。

## 2. 每帧录制的完整成本链

### 2.1 主线程部分（`appendFrame`，`RecordEngine.swift:466-490`）

| 步骤 | 成本 | 说明 |
|---|---|---|
| `guard isRecording` 等检查 | ~0 | 纯判断 |
| `pendingLock.lock/unlock` ×2 | ~0 | 短临界区 |
| `frameCount += 1` / `labeledFrameCount` | ~0 | 计数 |
| `writeQueue.async { [weak self, image] }` | ~0 | **仅入队**（`image` 是引用捕获，**不拷贝**） |

✅ **主线程总成本 ≈ 0**（重活全在后台）。这也是实测 `record=0.133ms` 的原因（其中含少量调度开销）。

### 2.2 后台部分（`writeQueue` 串行队列，`:495-520`）

| 步骤 | 实测成本 | 拷贝点 |
|---|---|---|
| ① `image.cgImage(forProposedRect:)` | **0.003 ms** | ⚠️ 若 NSImage 内部非 CGImage 会重绘；当前是 CGImage 构造 → 无拷贝 |
| ② `CGContext(...)` 创建 640×360 位图 | 含在③ | 分配 640×360×4 = **921 KB** |
| ③ `context.draw(cgImage, in: ...)` | **0.091 ms** | ✅ **唯一实质拷贝**（源 1280×832 → 目标 640×360） |
| ④ `context.makeImage()` | 含在③ | 包装（不拷贝像素） |
| ⑤ `NSBitmapImageRep(cgImage:)` | ~0 | 包装 |
| ⑥ `representation(using:.jpeg, 0.9)` | **0.488 ms** | JPEG 编码（CPU） |
| ⑦ `jpgData.write(to:, options:.atomic)` | **0.149 ms** | 写盘（atomic = 写临时文件 + rename） |
| ⑧ `autoreleasepool` 包裹 | — | ✅ 已做（P1 修复） |
| **合计** | **≈ 0.73 ms/帧** | |

### 2.3 实测编码路径对照（30 次，源 1280×832 → 640×360 q0.9）

| 方案 | p50 | p95 | 产物 |
|---|---|---|---|
| **A 当前**：`CGContext.draw` + `NSBitmapImageRep.jpeg` | **0.579 ms** | 0.667 | 15656 B |
| **B ImageIO**：`CGContext.draw` + `CGImageDestination` | **0.529 ms** | 0.590 | 15656 B |
| **C vImage**：`vImageScale_ARGB8888` + `CGImageDestination` | 0.920 ms | 1.045 | 15639 B |
| D 仅 `CGContext.draw`（不编码） | 0.091 ms | 0.156 | — |
| E 仅 `NSBitmapImageRep.jpeg`（1280×832 源尺寸） | 1.507 ms | 1.531 | 44381 B |

**结论**：
- ✅ **B（ImageIO）比当前快 8.6%**（0.529 vs 0.579 ms）—— 微小但稳定
- ❌ **C（vImage）更慢**（0.920ms）—— vImage 的高质量重采样 + buffer 转换开销 > CGContext.draw
- 📊 **编码占 84%**（0.488/0.579），缩放只占 16%（0.091）

### 🔴 关键结论：**录制不是卡顿主因**

- **record 只占 4.3%** 的 tick 分段

> **⟹ 录制链路的 CPU 成本极低，1-2 帧的根因应在别处**（如抓屏 192MB/s 的 GPU/内存带宽、或磁盘 I/O 竞争）。

## 4. 写盘成本

| 项 | 值 |
|---|---|
| 写盘目录 | `data/raw_clips/` → **内置盘** `/dev/disk3s1`（228Gi，54Gi 可用） |
| 单帧大小 | **42,457 B（41.5 KB）**（1280×832 q0.9 实测；640×360 约 15.7 KB） |
| 45fps 写入量 | 45 × 41.5KB ≈ **1.87 MB/s**（若 640×360 则约 0.7 MB/s） |
| **单帧写盘 `.atomic`** | **0.149 ms** |
| 单帧写盘非 atomic | **0.056 ms** |
| 45 帧连续写（模拟 1 秒） | p50 **7.176 ms** / p95 9.209 ms |

✅ **写盘成本极低**（1.87 MB/s 对内置 SSD 是零头）。
💡 **可优化**：`.atomic` → 非 atomic 可省 **0.093 ms/帧**（约 62%），但**失去崩溃安全**（半写文件风险）。**不建议为这点收益牺牲原子性**。

## 5. 背压阈值分析

**当前值**（`RecordEngine.swift:131`）：
```swift
private static let maxPendingWrites = 1
```

**逻辑**（`:478-490`）：
```swift
guard pending <= Self.maxPendingWrites else { return }   // 待处理 >1 就丢帧
let idx = frameCount
frameCount += 1        // ← 丢帧时【不】自增
```

### ⚠️ 逻辑陷阱（重要发现）

**丢帧时 `frameCount` 不自增** → **帧号仍连续** → **无法用帧号连续性判断是否丢帧**！

**验证**（实测 3 个 clip）：
```
clip_20261010_232125: 帧号跳变次数=0  ✅ 连续
clip_20261010_231825: 帧号跳变次数=0  ✅ 连续
```
→ 但这**不能证明无丢帧**。

**用 `t_sec` 间隔判断**（唯一可靠方法）：
| clip | n | t 间隔 p50 | 理论 45fps | >50ms 次数 |
|---|---:|---:|---:|---:|
| clip_20261010_232125 | 165 | **33.4 ms** | 22.2 ms | 1 |
| clip_20261010_231825 | 210 | **33.4 ms** | 22.2 ms | 0 |
| clip_20261010_231614 | 150 | **33.4 ms** | 22.2 ms | 6 |

**33.4 ms = 30fps** —— 这些 clip 是 **45Hz 改造前**录的（最新 clip 02:04，45Hz 二进制 02:49）→ **符合预期**。
✅ **未发现 45Hz 下的丢帧证据**（但也没有 45Hz 录制样本，见 §7）。

### 背压阈值评价

| 项 | 评价 |
|---|---|
| `maxPendingWrites = 1` | **偏严**（只要有一帧在写就丢下一帧） |
| 设计意图 | 封顶内存（防 NSImage 在队列堆积） |
| 实测影响 | 后台 0.73ms/帧 << 22.2ms 帧间隔 → **正常不会触发** |
| 风险 | 磁盘卡顿时会**静默丢帧**（且帧号连续，难发现） |

💡 **建议**：`maxPendingWrites` 提到 **2~3**（内存代价：2~3 张 1280×832 NSImage ≈ 8.5MB，可接受），降低突发丢帧风险。

## 7. 优化空间汇总

| # | 优化项 | 预期收益 | 风险 | 建议 |
|---|---|---|---|---|
| **O1** | **修画面变形**（640×360 → 640×416） | **质量**（非性能） | 需同步改 `dataset_v2.image_size` | 🔴 **强烈建议**（见 §1.5） |
| O2 | 编码改 ImageIO（`CGImageDestination`） | **0.050 ms/帧**（8.6%） | 极低 | ⚪ 可选（收益小） |
| O3 | 写盘 `.atomic` → 非 atomic | 0.093 ms/帧 | 失去崩溃安全 | ❌ 不建议 |
| O4 | `maxPendingWrites` 1 → 2~3 | 降低突发丢帧 | 内存 +8.5MB | 🟡 建议 |
| O5 | vImage 缩放 | **负收益**（-59%） | — | ❌ 否决（实测更慢） |

### ⚠️ 关于"1-2 帧"根因的判断

**从实测数据看，录制链路（4.3% tick + 3.3% 单核后台）不足以造成 1-2 帧。**
可能的真实根因（**未验证，需进一步测量**）：
1. **抓屏 192 MB/s 的带宽竞争**（SCStream → WindowServer）
2. **磁盘 I/O 与抓屏/推理竞争**
3. **`inject` 分支的 18.77ms 尖峰**（日志里有 `inject=18.77/18.77` 的 p95 尖峰）
4. 录制时**额外的内存压力**（NSImage 队列）

**建议**：用 `--tick-profile` 在**录制中**采集完整分段，定位真实瓶颈。
