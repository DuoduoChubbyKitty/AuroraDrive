## 1 · 验证 ①：24 步是否真在 CoreML 图里 ✅

### 1.1 方法：按权重名统计（最硬判据）

不靠字符串匹配代码，而是**转换后在 CoreML 图里数算子**。

```bash
./.venv-yolo26/bin/python3 -c "... build_model(enable_refiner=True, refiner_steps=24) → ct.convert → 统计 linear"
xcrun coremlc compile /tmp/w1_s24.mlpackage /tmp/
python3 -c "re.findall(r'linear\(([^)]*)\)', model.mil) → 统计 weight 名"
```

**输出（原始）**：
```
linear 权重名去重数: 17
出现次数最多的（前10）:
  refiner_cells_0_h_z_weight_to_fp16    26
  refiner_cells_0_h_r_weight_to_fp16    26
  refiner_cells_0_h_n_weight_to_fp16    26
  refiner_cells_0_x_z_weight_to_fp16     3
  ...
```
（`shared=True` 时 GRU 三门的 hidden 投影各被 24 步复用；26 = 24 步 + FusionHead/step_head 侧的 2 处引用）

**判定**：refiner 的 GRU 门权重（`h_r/h_z/h_n`）**各出现 26 次** —— 这正是 `shared=True` 下"单一 GRU 单元展开为 24 个静态算子"的定义。**无 refiner 时为 0 次**（对照实验见 1.2）。

### 1.2 对照实验（证明不是幻觉）

| 模型 | `refiner_cells_0_*_weight` 出现次数 |
|---|---|
| `enable_refiner=False` | **0** |
| `refiner_steps=24` | **87**（3 门×24 + proj×24 + x_r/x_z/x_n×3 + …） |

### 1.3 算子数随步数线性扩展（第二重证据）

| steps | linear | sigmoid | tanh | 总 op |
|---|---|---|---|---|
| 1 | 31 | 4 | 2 | 387 |
| 8 | 77 | 18 | 9 | 543 |
| **24** | **445** | **50** | **25** | **2066** |

**24 步 vs 1 步：linear 14.4×、sigmoid 12.5×、tanh 12.5×** —— 与展开 24 个单元相符（非 24× 是因为 FusionHead 等固定算子被共同计入分母）。

### 1.4 `while_loop = 0` ✅（方案二核心目标达成）

```
while_loop 算子数: 0   ← 需求 §1：方案二要求"无 while_loop，ANE 友好"
```

> ⚠️ **但 w5 的"假绿防线第二环"对 24 步 refiner 语义不匹配**：它检查 `while_loop` 或原生 `gru` 算子，而 24 步是**展开的 linear**，两者都不匹配 → 若只看该防线会误报"时序被剪掉"。实测 w5 脚本已**额外加了 24 步专项检测**（见 §7），故最终没误报。

## 2 · 验证 ②：24 步是否真在用（非偷懒）✅

### 2.1 零初始化状态下 step1 == step24 == fused（**这是设计预期，不是偷懒**）

```
=== 零初始化（未训练）===
inter 步数: 24
step1 == fused:  True
step24 == fused: True
step1 vs step24 maxdiff: 0.00e+00
```
理由：`refiner_proj` 零初始化 → 每步 `delta = proj(h) = 0` → `refined = fused + 0`。**这是需求 §2.3 明确要求的"不破坏旧行为"**，不能当成偷懒证据。

### 2.2 模拟训练后（`refiner_proj` 非零）：step1 ≠ step24 ✅

```
=== 模拟训练后（refiner_proj / expert_out_proj 非零）===
inter 数: 24
step1  vs step24 steer maxdiff: 0.007066
step dict keys (step1):  ['steer','throttle','brake','expert_weights','route_logits']
step dict keys (step8):  ['steer','throttle','brake','lane_offset','expert_weights','route_logits']
step dict keys (step16): ['steer','throttle','brake','ttc','expert_weights','route_logits']
```

**判定**：
1. 24 步确实产生**逐步不同的输出**（step1 vs step24 差 7.07e-03），24 步机制有效。
2. **逐步监督的字段裁剪正确**：`lane_offset` 只在第 8 步出现、`ttc` 只在第 16 步出现，其余步只有三主输出 —— 与需求 §3.2 规格一致。
3. `expert_weights` / `route_logits` 每步都有（MoE 软路由，可微）。

### 2.3 关于早期版本的"逐步修正量饱和"

早期版本（`nn.GRUCell`，参数量口径不同）实测逐步修正量在 step1 后饱和（0.4487→0.4815）。
最新版引入 MoE 软路由与独立 `step_head` 后，step 间差异由 **step_head 的三主输出**承载（0.00707），
**饱和问题不再直接适用**。**训练后应复验"逐步递减监督"是否真让第 8/16/24 步产生有区分度的输出** —— 当前为模拟权重，不能判定。

## 3 · 验证 ③：零初始化逐位一致 ✅

### 3.1 ⚠️ 首次测量踩坑（记录以免后人误判）

首次测「无 refiner vs 1 步 refiner」得到 **maxdiff=0.48**，看似零初始化失效。**根因**：两次 `M2Model(...)` 是**独立随机初始化**，权重本就不同——差异来自随机权重，不是 refiner。

### 3.2 正确方法：同一份权重对比

```python
m_full = M2Model(enable_refiner=True, refiner_steps=24)  # 构建一次
m_no = copy.deepcopy(m_full); m_no.refiner = None        # 克隆权重后关掉 refiner
```

**输出（原始）**：
```
无refiner vs 24步refiner（同一权重）三输出差: ['0.00e+00', '0.00e+00', '0.00e+00'] → maxdiff 0.0  ✅
无refiner vs 1步refiner （同一权重）三输出差: ['0.00e+00', '0.00e+00', '0.00e+00'] → maxdiff 0.0  ✅
```

**判定**：零初始化真实生效，**逐位一致**（不是"接近"）。

## 4 · 验证 ④：参数量 —— ⚠️ 需求文档估算严重错误

### 4.1 实测（`reparameterize()` 后，非 deploy）

| 配置 | 总参数 | refiner 参数 | INT8 理论 |
|---|---|---|---|
| 无 refiner | 3,394,505（3.395M） | 0 | 3.237 MB |
| **shared 24 步** | **8,717,012（8.717M）** | ~5.32M | **8.313 MB** |
| independent 24 步 | 44,963,540（44.964M） | ~41.57M | 42.881 MB |
| shared 1 步 | 8,717,012（8.717M） | ~5.32M | 8.313 MB |

> 注：`shared` 的 1 步与 24 步参数量**相同**（共享同一 cell，步数不影响参数量，只影响图规模）—— **符合预期**。

### 4.2 实际 INT8 导出（palette kmeans gs=1，实测落盘）

| 配置 | 参数 | **INT8 实际大小** | ≤10MB |
|---|---|---|---|
| shared | 8.717M | **8.027 MB** | ✅ 余量 1.25× |
| independent | 44.964M | **42.838 MB** | ❌ **超 4.3 倍** |

### 4.3 ⚠️ 与需求文档的偏差（必须上报）

| 项 | 需求文档 §1 | 实测 | 偏差 |
|---|---|---|---|
| shared INT8 | 3.51 MB | **8.03 MB** | **2.3×** |
| independent INT8 | 6.90 MB | **42.84 MB** | **6.2×** |

**根因分析**：
- 文档 `+0.14MB` / `+3.39MB` 的增量估算，**没有按实际 `feat_dim=512, hidden=512` 计算**。单个 GRU 单元 = 6 个 `Linear(512,512)`（3 门 ×(x_proj+h_proj)）= **1,574,400 参数 = 1.50 MB INT8**，×24 = 36 MB，这才是 independent 的真实量级（实测 42.8MB，另含 MoE 专家与 step_head）。
- 文档很可能按 `hidden=128` 或只算了 `weight_hh` 一相。
- **实际实现用的是 `_StrictGRUStep`（手工展开）**，参数量与标准 GRUCell 同量级（w7 注释也已更新为"shared ≈1.57M / indep 38M 超 10MB 7 倍"）。

**结论**：**independent 模式在本模型尺寸下不可用**（42.8MB ≫ 10MB），需求文档"独立 6.90MB 仍 ≤10MB"的退路**不成立**。**shared 是唯一可行解**，且其 8.03MB 体积余量已从文档预期的 2.85× 收窄到 **1.25×**。

## 8 · 附：24 步的真机耗时（我实测，供性能评估）

| steps | CPU_AND_NE | ALL | CPU_ONLY |
|---|---|---|---|
| 1 | 0.549 ms | 0.552 ms | 1.705 ms |
| 8 | 1.502 ms | 1.601 ms | 1.970 ms |
| **24** | **3.699 ms** | **3.552 ms** | **2.380 ms** |

**两个重要观察**：

1. **24 步耗时 3.5~3.7 ms**，是需求文档预估「1~2ms」的 **~2×**。总预算 12.4 + 3.7 ≈ 16.1ms → **62Hz**（余量 2.1×，仍可接受，但比文档的 69Hz 保守）。
2. ⚠️ **24 步下 `CPU_AND_NE(3.699ms)` 比 `CPU_ONLY(2.380ms)` 还慢** —— 且编译期出现
   ```
   E5RT: MILCompilerForANE error: failed to compile ANE model ... ANECCompile() FAILED
   ```
   （**steps=1/8 无此警告，仅 steps=24 出现**）
   **含义**：需求 §1「方案二 → 无 while_loop → ANE 友好」的论断**未获实测支持**。24 步展开后 ANE 编译失败并回退 CPU，此时 `.all`/CPU_AND_NE 反而比纯 CPU 慢（多一次失败的 ANE 尝试开销）。
   **建议**：上线前确认 Swift 侧 `computeUnits` 选择（项目既有结论是 `.all`，但那是针对旧模型的），**24 步模型建议复测 `.cpuOnly` 是否更快**。

## 11 · 给 Lead 的三条决策建议
