# 车头朝向鉴定 · pose.4 到底是"车头朝向"还是"相机朝向"

> 日期：2026-10-08 · 鉴定人：w2-transport（抓包线监督）· 结论：**pose.4 = 相机朝向（ControlRotation），不是车体朝向**
>
> ⚠️ 与 `docs/换代约束通告-2026-10-08.md:122`（"Lead 亲查"段）的结论**相反**——
> 该段引用的证据（CoordinateCapture.swift:445）讲的是**位置 X1/X2**，
> 不构成 rotation 语义的证明。本报告给出 6 条独立证据链。

---

## 一、结论先行

| 问题 | 答案 |
|---|---|
| `pose.4` 的来源 | `rotation.yaw`（`toPose()`，`CoordinateCapture.swift:215-228`）|
| 这个 `rotation` 是谁的 | **玩家的 ControlRotation（= 相机/视角朝向）**，不是车体 Actor 的 |
| 包里有没有第二个 rotator（车体的） | **没有**。移动块结构是 `time + accel + location + ControlRotation`，只有这一个 rotator |
| `pose.4` 被覆盖了吗 | 是。`NetworkLocator.swift:555-562` 在有位移时用 `atan2(dx,dy)`（运动方向）覆盖 |
| 对 R2 的影响 | **⛔ 不该加 `carHeading = pose.4`**——那等于把相机朝向贴上"车头"标签。真车头只能从**运动方向**（atan2 覆盖逻辑）估计，或另找包 |

## 二、证据链（6 条，前 3 条决定性）

### 证据 1【决定性】：上游 MaaNTE 原注释写明 "compressed control rotation"

`MaaNTE/agent/custom/action/Navi/nte_coordinate_api.py:1-7`（模块 docstring，逐字）：

> "The game serializes client movement as a bit-packed timestamp, acceleration,
> location and **compressed control rotation**."

`nte_coordinate_api.py:66`（`_rotator` docstring）：

> "Read **FRotator::SerializeCompressedShort** (Pitch, Yaw, Roll)."

`nte_coordinate_api.py:96`（`_has_valid_rotation` 注释）：

> "**ControlRotation** serializes pitch and yaw, while roll is normally omitted by the client."

**语义**：UE5 的 `ControlRotation` 是 `APawn::GetControlRotation()`——即**玩家控制器的视角旋转**。
UE5 官方文档明确：ControlRotation 是相机（对玩家 Pawn）的旋转。在 UE5 的移动同步协议里
（`FRepMovement` 不含 rotator，旋转经 `CharacterMovement` 的 control rotation 通道同步），
移动块尾部跟的是控制（相机）旋转。

### 证据 2【决定性】：上游自己的字段命名就是 camera_pitch / camera_heading

`MaaNTE/agent/custom/action/Navi/coordinate_position.py:246-247`（消费端，逐字）：

```python
camera_pitch = float(pose[3])
camera_heading = float(pose[4])
```

`:165-166` 的成员命名 `_last_camera_pitch / _last_camera_heading`、`:241/271/302` 全部
传给 `camera_heading=` 参数。**上游作者（读得懂协议的人）把 pose.4 叫"相机朝向"**。

本项目移植时沿用了这个语义：`NetworkLocator.swift` 的 `NetworkLocationResult` 字段名
也是 `cameraPitch / cameraHeading`（`NetworkLocator.swift:556-566`，`locate()` 返回值）。

### 证据 3【决定性】：仓库既有 MAA 深度文档早已判定"基于相机朝向"

`docs/文档库/Maa深度/MAA深度文档_架构篇.md:337`（逆向笔记，逐字）：

> "4. 计算 compass heading（**基于相机朝向**）"

`docs/文档库/Maa深度/MAA深度文档_完整版.md:395`：

> `rotation, _ = _rotator(payload, cursor)  # control rotation`

### 证据 4：本仓库 `toPose()` 的变量名与算法就是"视线方向"

`Sources/AuroraDrive/Capture/CoordinateCapture.swift:215-228`：

```swift
let viewDir: Vec3 = (cos(pitchRad) * cos(yawRad), cos(pitchRad) * sin(yawRad), sin(pitchRad))
```

变量名 `viewDir`（视线方向）——按 yaw/pitch 构造**视向量**再投影到北/东。这是标准的
"视线方位角"算法；车体朝向没有 pitch（车不会抬头 90°），而 `hasValidRotation` 反而
**要求 `|pitch| ≤ 90.001`**（`:197`）——相机才会大 pitch，车体不会。

### 证据 5：`locate()` 的 atan2 覆盖逻辑本身就是"rotation 不等于运动方向"的补偿

`Sources/AuroraDrive/Locate/NetworkLocator.swift:555-562`（精确行号）：

```swift
555:        var heading = pose.4                      // ← rotation.yaw（相机朝向）
556:        if let last = lastLocPos {
557:            let dx = Double(point.0) - last.x
558:            let dy = Double(point.1) - last.y
559:            if dx * dx + dy * dy > 16 {           // ← 有位移（>2m）
560:                heading = (atan2(dx, dy) ...      // ← 用运动方向覆盖
```

**写这段代码的人已经意识到** rotation 与运动方向不一致：静止时用相机朝向（无位移可判），
移动时用实际位移方向（运动方向估计）。若 rotation 真是车头，这个覆盖只会引入误差——
它的存在恰恰说明 rotation 不是车头。

### 证据 6：实测样本——turn.pcap（转向对照）与移动样本的 rotation 无变化

用**真实 Swift 解码器**（`UE5Decoder`，从 `CoordinateCapture.swift` 原样抽取，
非复刻）直连 4 个 pcap 样本（`tools/reverse/samples/`）：

| 样本 | 解出的 rotation (P, Y, R) | 说明 |
|---|---|---|
| `turn.pcap`（玩家转向） | **无候选**（该样本包长 76，走的是 protobuf 双记录路径，findCandidates 不扫这种布局） | 无法从此样本判 yaw 变化 |
| `move2.pcap`（移动） | `(0.00, -160.39, 0.00)` | yaw 恒 -160.39 |
| `move_burst.pcap`（连续移动） | `(0.00, +76.60, 0.00)` / `(0.00, -160.39, 0.00)` | 两帧位移不同但 yaw 各不同 |

**解读（如实标注：样本有限，此条是弱证据）**：move_burst 里两个移动块的 yaw
（+76.60 与 -160.39）相差 236°——若是同一辆车连续行驶的车头朝向，两帧（间隔 <15s）
不会差这么多；更符合"**玩家中途转了视角**"或"两个候选本就是不同对齐位"的解释。
⚠️ 样本太少且 turn.pcap 未能解码（见"未验证"段），此条不单独作为结论依据，
仅与证据 1-3 互洽。

## 三、对"Lead 亲查"段的反驳

`docs/换代约束通告-2026-10-08.md:122-144` 称"抓包解出的 rotation 是【角色/玩家】的"，
引用证据为 `CoordinateCapture.swift:445`。核实结果：

1. **`:445` 讲的是位置**：该处注释是"新协议解码：从 protobuf 封装移动包里取出**世界坐标**…
   角色移动时 **X1/X2** 每包同步变化"——证明的是**位置字段**跟角色走，
   对 rotation 语义零证据。
2. **"角色/玩家"与"相机"并不等价**：第三视角下玩家转动鼠标，**相机绕车转而车头不变**
   （用户实测：heading 跟视角走、车头没变）。ControlRotation 跟随的正是前者。
3. 该段称"pose.4 本来就是车头朝向，只是被 atan2 覆盖"——**方向反了**：
   atan2 覆盖（运动方向）才更接近车头；被覆盖的 pose.4 才是相机朝向。

## 四、给 R2 的明确建议

1. **⛔ 停手，不要加 `carHeading = pose.4`**。那会把相机朝向标签成"车头"，
   与用户实测（"heading 跟视角/运动方向走"）方向相反，且与上游命名
   （camera_heading）冲突。
2. **✅ 真车头的可得路径**（按可信度排序）：
   - **运动方向估计**（现有 atan2 覆盖逻辑）：移动时即是车头方向的合理近似。
     若要单独字段，建议命名 `motionHeading`（如实：它是运动方向，不是车头）。
   - **另找车体 rotator 的包**：UE5 的 `FRepMovement`（车辆物理同步）**不含 rotation**，
     但**载具（WheeledVehiclePawn）有独立的 replication 通道**——需要新一轮抓包
     （车辆静止转视角 vs 原地转向的对照实验）才能定位。这是唯一能拿到**真车头**的路。
3. **✅ 若 R2 的目标是修"heading 跟视角走"**：正确修法是**把运动方向估计提到
   主路径**（现有覆盖逻辑已是如此），并考虑**运动方向平滑**（车头不会瞬变，
   可加 EMA/角度插值），而不是给 pose.4 换名字。
4. **✅ 命名规范**：`cameraHeading` 这个名字本来就对（上游同名），别改成 carHeading；
   需要运动方向字段时用 `motionHeading`，需要真车头时先做抓包对照实验。

## 六、未验证项（如实标注）

| 项 | 状态 | 说明 |
|---|---|---|
| turn.pcap 的 rotation | **未验证** | 该样本走 protobuf 双记录布局（72/76 字节，前缀固定），findCandidates 的位扫描不覆盖此布局；需扩展解码器才能读出转向时的 yaw 变化 |
| 包里是否存在车体 rotator（在**其他**包类型里） | **未验证** | 本报告只扫了 TCP 30031 的 4 个样本；UDP 移动 RPC（30212/30160）未采样。**不能排除**载具通道在别的包里——若要真车头，这是下一步抓包方向 |
| ControlRotation 与车头的**固定偏移** | **未验证** | 若游戏相机是"车后跟随"模式，yaw 相差一个常量偏移 + 弹性延迟；偏移量需实测标定（静止车辆转视角实验） |
| move_burst 两候选是否同源 | **未验证** | +76.60 与 -160.39 两个 yaw 可能来自不同对齐位（假候选），也可能是同源两帧；需连续帧对照 |

## 七、一句话结论

**pose.4 是相机朝向（玩家 ControlRotation），上游与本项目的历史文档、字段命名、
算法变量名三处一致证实；真车头不在现有抓包字段里，R2 若加 `carHeading = pose.4`
等于贴错标签——应停手回报，改用运动方向估计（motionHeading）或发起新一轮抓包
定位载具 rotator。**
