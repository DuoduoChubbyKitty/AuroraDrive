## 0. 大小换算基准（★ 用户明确要求 INT8 部署）

> **用户 2026-10-08 明确**：「我说是 INT8 体积，我要的是 INT8，并不是那种（FP16）」

| 精度 | 每参数字节 | **10MB 能装** |
|---|---|---|
| FP32 | 4 B | ≈ 2.5M 参数 |
| FP16 | 2 B | ≈ 5M 参数 |
| **INT8（★ 本项目目标）** | **1 B** | **≈ 10M 参数** |

**⟹ 按 INT8 口径，10MB 能装约 1000 万参数** —— 余量比 FP16 口径大一倍，
原版 RepVGG-A0（8.0M）**按 INT8 算只有约 8MB，是合规的**！

**参照物（本项目实测）**：
- 现有 M9 主驾驶模型 = **15MB**（FP16；按 INT8 约 7.5MB）
- `game_assist_control` = **7.6MB**，且有 `game_assist_control_int8.mlpackage` 变体
- M2 新写的 `model_v2.py` = 2,759,000 参数 → **INT8 ≈ 2.8MB**（✅ 远低于 10MB）

## 3. 多模态融合结构（关键——本项目必须自己搭）

| 结构 | 用途 | 参数量 |
|---|---|---|
| **PointNet** | 变长集合编码（→ **检测框分支**） | 极小（几层 MLP，<0.1M） |
| 小 CNN | 车道线掩码编码 | 极小（3 层卷积，<0.5M） |
| MLP | 状态向量编码 | 可忽略（<0.01M） |

**为什么这些够用**：检测框是"几个框"、车道线是"160×160 二值图"、状态是"4 个数"——**信息量远小于图像**，不需要大网络。

## 4. ★ 推荐 Top 3（针对 ≤10MB + 多模态 + 30Hz + 自己训练）

### 🥇 方案 A：★ **原版 RepVGG-A0 + 多模态头**（INT8 下最合适）
- 图像骨干：**原版 RepVGG-A0（8.0M / INT8 ≈ 8.0MB）**
- 车道线/检测框/状态分支：合计 <0.5M
- **合计 ≈ 8.5M → INT8 ≈ 8.5MB** ✅（贴边但合规）
- **优点**：表达力最强（8M 参数 vs ShuffleNet 2.3M）、与项目现有风格完全一致、
  **推理时可重参数化成纯 3×3 卷积（速度优势）**
- **缺点**：贴 10MB 边缘，量化到 INT8 后精度损失需验证

### 🥈 方案 B：M2 已实现的 RepVGG-A0 轻量变体（**已落地，余量最大**）
- 图像骨干：RepVGG-A0 瘦身版（**2.76M / INT8 ≈ 2.8MB**）
- + 多模态分支
- **INT8 ≈ 3.3MB** ✅✅ 余量 6.7MB
- **优点**：**已写好**（`src/model_v2.py`）、省下的 6.7MB 可用于加深融合头/提高输入分辨率
- **缺点**：骨干表达力被削到 1/3

### 🥉 方案 C：MobileNetV3-Small / ShuffleNetV2 0.5x（**最省 + 有预训练**）
- MobileNetV3-Small（2.5M / INT8 ≈ 2.5MB）或 ShuffleNetV2 0.5x（2.28M / INT8 ≈ 2.3MB）
- **优点**：有官方 ImageNet 预训练、CoreML 友好、极省
- **缺点**：表达力弱、hard-swish 在 CoreML 上可能略慢

### ★ INT8 口径下的选型建议
| 场景 | 推荐 |
|---|---|
| **要最强表达力** | 方案 A（原版 RepVGG-A0，8.5MB 贴边） |
| **要快速验证流程** | 方案 B（M2 已实现，3.3MB，先跑通） |
| **要最省/最快** | 方案 C（ShuffleNetV2 0.5x，2.3MB） |

**建议路线**：先用 **方案 B（已落地）** 跑通训练→导出→部署全流程，
再换 **方案 A（原版 RepVGG-A0）** 对比精度——反正 INT8 下 8.5MB 也合规。

## 5. 核心结论

1. **INT8 下 10MB 极其宽裕** —— 能装 10M 参数，几乎所有轻量骨干都合规
2. ✅ **原版 RepVGG-A0（8.0M）按 INT8 只有 ≈8.0MB —— 合规**
   （FP16 口径下它是 16MB 才超；M9 的 15MB 是 FP16 部署的后果）
3. **自动驾驶专用网络**：PilotNet 太小且不收车道线/检测框；
   TransFuser 等远超 10MB 且输入是 LiDAR/多摄像头 —— 不能用，只能借鉴融合思想
4. **多模态分支本身很轻**（PointNet + 小 CNN + MLP 合计 <0.5M）—— 瓶颈在图像骨干
5. **M2 的 `model_v2.py` 已符合约束**（INT8 ≈2.8MB / 五路输入）—— 可直接用
6. **★ 真正的新瓶颈不是大小，而是**：
   - **INT8 量化后的精度损失**（尤其车道线这种细结构）
   - **多模态融合的表达力**（怎么让车道线真的影响 steer）

## 6. 未验证项（诚实标注）

2. 若训练后发现精度不够 → 换 ShuffleNetV2 0.5x 骨干再试（省 1.5MB，可用于加深融合头）
3. **实测三个骨干在 M3 上的推理耗时**（`--perf-selftest` 同口径），再定最终选型
