## 一、审计方法

对 `Sources/AuroraDrive/` 执行 ripgrep：

| 模式 | 命中量 |
|---|---|
| `1\.0\s*/\s*30\|1\.0\s*/\s*45\|1\.0\s*/\s*20` | 16（30）+ 3（20）+ 0（45） |
| `targetFps\|typicalDt\|stabilityFrames` | 20 |
| `30Hz\|45Hz\|20Hz` | 153 |
| `timescale:\|minimumFrameInterval` | 4 |
| `tickHz\|captureHz\|engineTickHz\|forPerceptionMode` | 20 |

对每处命中 read 上下文，判定分类。分类口径：

- **运行时**：随 tick 频率生效的代码值（定时器间隔、物理 dt、稳定性门），必须与 20Hz 一致。
- **自检基线**：固定测试 dt，用于可复现性，**不应**跟随生产帧率。
- **非频率**：数字 30/45/20 与频率无关（角度、秒、数量、归一化）。
- **抓屏侧**：画面流帧率，与 tick 解耦，保持档位映射（ayolom→45 / legacy→20）。
- **注释**：无运行时影响，过时可择机清理。

## 四、遗漏清单（当前仍未迁移的运行时频率硬编码）

### 🔴 遗漏 #1：MotionPredictor.ingest 方法默认参数仍是 1/30（field 已迁移、method 漏改）

- **位置**：`Inference/MotionPredictor.swift:265`
- **当前值**：`func ingest(detections: [Detection], dtSeconds: Double = 1.0 / 30.0)`
- **不一致点**：同文件 `:165` 字段 `lastIngestDt` **已改** `1.0/20.0`（注释"定档 20Hz"），但 `:265` 方法默认参数仍是 `1.0/30.0`。**field 迁移了、method 签名漏改**——典型的不一致残留。
- **当前运行时影响**：小。运行时唯一调用方 `AuroraDriveApp.swift:6680` `motionPredictor.ingest(detections: observed, dtSeconds: dt)` 显式传 `dt`（=1/20），默认值被覆盖、不生效。自检路径也显式传 dt。
- **为何要改**：API 表面一致性。未来调用方若忘传 `dtSeconds`，会静默用 1/30 引入 30Hz 假设，与 tick 20Hz 不符。
- **建议**：改 `1.0 / 20.0`，与 `:165` 字段对齐。

### 🟡 遗漏 #2：UI 进程主循环 tick 仍是 1/30（条件性）

- **位置**：`App/MissionConsole.swift:6035`
- **当前值**：`timer.schedule(deadline: .now(), repeating: 1.0 / 30.0, leeway: .nanoseconds(0))`
- **作用**：此 DispatchSourceTimer 驱动 `DriveState.shared.tick()`（`:6057` `DispatchQueue.main.async { state.tick() }`）。`DriveState.tick()`（`AuroraDriveApp.swift:6843`）含完整决策管线。
- **条件性严重性**（已核代码事实，非推测）：
  - **引擎连上（常态）**：`DriveState.tick()` 在 `:6883` `if EngineClient.shared.isActive { tickEngineMode(); return }` **早退**，只拉取引擎回传数据显示，**不跑本地推理/物理**。此时 `:7084 dt=1/20` 不被执行，该 30Hz timer 只决定 UI 刷新节拍——改不改不影响驾驶正确性。
  - **UI 本地模式 / 引擎未连**：`isActive=false`，tick 不早退，走到 `:7084 dt=1/20`。此时 **timer 30Hz（间隔 33ms）与 dt 1/20（50ms 积分）直接打架** → 速度/加速度换算错 50%。这是 UI-local 下的真活 bug。
- **判断依据**：`MissionConsole.swift` 内 grep `EngineMain` 零命中 → UI 进程不读 `engineTickHz`，该 timer 是独立硬编码。`AuroraDriveApp.swift:6883` 的 `isActive` 分流闸已 read 坐实。
- **背景覆盖情况**：背景清单只点了引擎进程（`EngineMain`）的 `engineTickHz=20`，**未提 UI 进程这条独立 tick**。属背景未覆盖的遗漏点。
- **建议**：改 `1.0 / 20.0`，或改为读 `EngineMain.engineTickHz`（UI 进程当前未引用，需评估可见性）。注释 `:6036/6044/6045/6052` 写"45Hz"也需同步（代码本是 30Hz，注释已先于代码漂移）。待机分频比 `idleSkip<8`（`:6046-6056`）改后仍成立（20/8=2.5Hz）。
- **决策归属**：是否把 UI-local 也纳入 20Hz 一致性要求，属产品决策；本审计只标注事实。

### 🟡 遗漏 #3：LaneFallback.stabilityFrames 注释基于 30Hz（有兜底）

- **位置**：`Inference/LaneFallback.swift:106`
- **当前值**：`var stabilityFrames: Int = 6`，注释 `:98` "约 0.2s @30Hz"
- **现状**：该门为**双条件**——帧数达标 **或** 时间窗 `stabilityWindowSeconds=0.2`（`:111`）达标，取先到者。时间窗用真实经过时间，帧率无关。tick 改 20Hz 后 6 帧=0.3s，但时间窗 0.2s 先达标，**实际门宽不变**。
- **影响**：小。仅注释 `:98-101` 过时。
- **建议**：可按 20Hz 重算（0.2×20=4 帧）使注释自洽，或保留 6 依赖时间窗 + 更新注释。

### 🟢 遗漏 #4：PerfSelfTest TickBench 预算（边界，建议评估）

- **位置**：`App/PerfSelfTest.swift:907`
- **当前值**：`let budget = 1.0 / 30.0`
- **作用**：TickBench 单帧时间预算。注释 `:857` "驱动：30Hz RunLoop（与生产同构）"。
- **问题**：自检声称"与生产同构"，生产改 20Hz 后同构性破裂。
- **建议**：若要自检反映 20Hz 节拍，改 `1.0/20.0`；若作更严压力基准（30Hz 预算更紧）可保留，但注释改为"压力基准"。需产品决策。

## 八、结论

### 仍需处理的运行时频率硬编码（按当前代码）

| 优先级 | 位置 | 当前值 | 目标 | 性质 |
|---|---|---|---|---|
| 🔴 P1 | `MotionPredictor.swift:265` | `ingest(dtSeconds: = 1.0/30.0)` | `1.0/20.0` | field 已改、method 默认参数漏改（不一致残留） |
| 🟡 P2 | `MissionConsole.swift:6035` | `repeating: 1.0/30.0` | `1.0/20.0` | UI tick；引擎连上时无害，UI-local 下与 dt 1/20 打架 |
| 🟡 P3 | `LaneFallback.swift:106` | `stabilityFrames = 6`（@30Hz 注释） | 重算或依赖时间窗+更新注释 | 有时间窗兜底，影响小 |
| 🟢 P4 | `PerfSelfTest.swift:907` | `budget = 1.0/30.0` | 评估是否改 1/20 | 自检基线，需决策 |

### 关键事实（代码实证，非推测）

1. **引擎进程 tick 与 dt 现已自洽**：`EngineMain.swift:1022-1024` timer = 1/20；其驱动的 `DriveState.tick()` 在 `isActive=false`（引擎进程不调 `EngineClient.startup()`，`EngineMain` 内对 `isActive`/`startup` 唯一命中是 `:24` 注释）时不早退，走到 `:7084 dt=1.0/20.0`——**timer 20Hz 与 dt 1/20 一致**。引擎这条主路径已无频率打架。

2. **`AuroraDriveApp.swift:7084 dt=1/20` 的喂给链已对齐**：`:7196 updateMotionPipeline(dt: dt)` → `:6680 ingest(dtSeconds: dt)` + `:6684 predict(dtSeconds: dt)`，全用同一份 1/20。

3. **唯一明确的残留不一致**：`MotionPredictor.swift` —— `:165 lastIngestDt` 已 1/20，但 `:265 ingest` 方法默认参数仍 1/30。这是 field/method 迁移不同步，属遗漏 #1。

4. **UI 进程 tick 的条件性**（遗漏 #2）：`MissionConsole.swift:6035` 的 1/30 在引擎连上（常态）时只驱动 `tickEngineMode()` 显示拉取，不碰 `:7084`；仅在 UI-local/引擎未连时才与 dt 1/20 打架。是否纳入 20Hz 一致性，属产品决策。
