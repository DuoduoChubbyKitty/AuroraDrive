### 1.2 算子数（从 `model.mil` grep `= op_name(` 统计）

| 模型 | 算子数 | 主要算子构成 | computeUnits |
|---|---|---|---|

**关键**：V2 的 ctl 有 **954 个计算算子全跑 CPU**（`.cpuOnly`），是旧 M9（64 个）的 **14.9 倍**。虽然历史实测说 cpuOnly 反而比 .all 快 6.4×（`:1802` 注释 + `docs/双模型cpuOnly完胜`），但那是在**无竞争的基准环境**下测的。

**当前 grep 结果**：
```

$ grep -c "logical_and" models/m9_v2_ctl.mlmodelc/model.mil → 0
```
→ **两个阻断算子已被移除**（GRU 改手工展开，risk_head 布尔运算改写）。但 ctl 仍是 `.cpuOnly`——**没改回 `.all` 尝试 ANE**。这是一个可优化点（见 §4）。

## 2 · 每帧推理工作量

### 2.1 infer 调用链（`InferenceEngineV2.swift`，双模型路径 `:2260-2310`）

```
infer() → inferenceQueue.async {
  ① preprocessImage(cgImage → MLMultiArray [1,3,180,320])     ← CPU
  ② encModel.prediction(image → feat[256])                     ← ANE (0.36ms)
  ③ featBufferPush(feat) + snapshot([8×256])                   ← CPU
  ④ makeSplitProvider(feat_seq + lane + dets + det_mask + state) ← CPU
  ⑤ ctlModel.prediction(feat_seq+inputs → steer/throttle/brake+aux) ← CPU (0.54ms)
  ⑥ runWorldModel(fused+action+det_feat+state → next_fused)    ← CPU (可选)
  ⑦ Task { @MainActor in finish() }                            ← 回主线程释放门
}
```

**每帧推理次数**：**2 次**（enc + ctl）+ **1 次可选**（world_model）= **2-3 次 CoreML prediction 调用**。

旧 M9 是 **1 次** prediction（单模型、单帧）。V2 多了 1-2 次。

### 2.2 preprocessImage 成本（`:3010-3050`）

```swift
// 逐像素双重循环：180×320 = 57,600 次迭代，每次写 3 个 plane
for y in 0..<height {
    for x in 0..<width {
        ptr[outIdx]                 = Float32(pixelData[pixelIdx])      // R
        ptr[planeSize + outIdx]     = Float32(pixelData[pixelIdx + 1])  // G
        ptr[planeSize * 2 + outIdx] = Float32(pixelData[pixelIdx + 2])  // B
    }
}
```

**172,800 次写入/帧**（57,600 × 3 plane）。这是 **Python 风格的逐像素循环**——vImage 一步就能做完（`vImageConvert_420ARGB8888ToPlanarF` 或 `vImageTablewiseInterpolation`），但当前实现没用。

采样证据：`preprocessImage` 在 `/tmp/cap_sample2.txt` 中占 ~87 样本（在 `closure #2 in InferenceEngineV2.infer` 内部）。

## 3 · 延迟来源分解

### 3.1 历史实测（来自 `docs/双模型cpuOnly完胜-2026-10-09.md` + `docs/Lead-多模型ANE派发-2026-10-09.md`）

| 组件 | p50 延迟 | 出处 |
|---|---|---|
| enc（ANE） | 0.36ms | `Lead-多模型ANE派发:11` |
| ctl（cpuOnly） | 0.54ms | `双模型cpuOnly完胜:12` |
| **enc+ctl 串联** | **0.83ms** | `双模型cpuOnly完胜:3` |
| world_model | 未单独测 | — |
| 旧 M9（.all→CPU 回退） | ~1.17ms | `INT8导出与实测`（M2 基线） |

**矛盾**：V2 串联 p50=0.83ms，远低于用户报的 100+ms。→ **瓶颈不在模型推理**。

### 3.2 真实采样分析（`/tmp/cap_sample2.txt`，2026-10-11 17:39，UI 进程 pid 61827）

采样对象是** UI 进程**（父进程 61783 是引擎）。UI 进程不跑 V2 推理（那是引擎进程的事），但采样仍揭示了系统级瓶颈：

| 热点 | 样本数 | 含义 |
|---|---|---|
| **ANE** | 65,194 | ANE 硬件调用（CoreML 推理栈，跨所有线程） |
| **caulk** | 38,191 | CoreML 编译/调度框架 |
| **semaphore_wait_trap** | 17,078 | 大量线程在等信号量 |
| E5RT | 7,500 | CoreML 执行流 |
| YolopxEngine | 2,826 | YOLOPX 推理 |
| closure #2 in InferenceEngineV2.infer | ~966（含子帧） | V2 推理闭包 |
| preprocessImage | ~87 | V2 预处理 |
| runWorldModel | ~47 | 世界模型 |
| QuestPanelReader.ingest | 105（主线程） | **OCR 占了主线程 Top 1** |

**主线程 Top 1 是 `QuestPanelReader.ingest`（105 样本）**——Vision OCR 在主线程的 dispatch block 里跑。虽然注释说它节流 0.7s，但**每次命中仍占主线程 ~33ms**（VNImageRequestHandler）。

### 3.3 V2 的结构性延迟：MainActor 门释放依赖

**`InferenceEngineV2.swift:1240-1290` 的关键注释**（逐字摘要）：

> `infer()` 完成后，`isInferencing` 的释放通过 `Task { @MainActor }` 回到主线程做。
> **若主线程被 >33ms 的长任务占住，推理门会延迟释放** → 表现为"推理帧率掉一档"。
> 真实 30Hz tick 模式（帧间让出 MainActor）：10/10 帧全部成功提交。

**这就是 100ms 延迟的最可能根因**：
1. 引擎进程的 tick 跑在主线程
2. tick 里有 **Quest OCR（33ms）** + **vImage 缩放（0.5ms）** + **shm publish** + **其他**
3. 如果主线程被 OCR 或其他长任务占 >33ms → V2 的 `isInferencing` 门延迟释放 → 下一帧 `guard !isInferencing` 跳过 → **帧率掉档**
4. 用户感知到的"100ms 延迟" = 门延迟 + OCR 阻塞 + 帧掉档的累积

**但这只是推断**——采样是 UI 进程的，**没有引擎进程的实时采样**（`/tmp/p5_sample_ENGINE_LIVE.txt` 是 03:22 的旧数据）。**标为未验证**。

## 4 · 可优化项（按收益排序，不改帧率/分辨率）

### 🔴 收益 1：preprocessImage 改 vImage（省 ~87 样本 + 消除 172,800 次循环）

**现状**：`:3010-3050` 逐像素 Python 风格循环。
**改法**：用 `vImageConvert_ARGB8888toPlanarF` 或 Accelerate 的 buffer-to-planar 转换，一步完成 BGRA→CHW float32。
**收益**：消除 57,600 次迭代 × 3 plane 的 CPU 循环。采样显示 ~87 样本。
**风险**：低（纯计算替换，输出 shape 不变）。

### 🔴 收益 2：ctl 改回 `.all` 尝试 ANE（潜在省 CPU 0.54ms/帧）

**现状**：`ctlCfg.computeUnits = .cpuOnly`（`:1802`）。历史原因是 ANE 被 `while_loop`/`logical_and` 阻断 → 改 cpuOnly 比回退更快。
**现状已变**：grep 确认两个阻断算子**已移除**（`:while_loop=0 :logical_and=0`）→ **ctl 可能现在能上 ANE 了**。
**改法**：把 ctl 从 `.cpuOnly` 改成 `.cpuAndNeuralEngine`，跑 `MLComputePlan` 验证 ANE 占比。
**收益**：如果 ANE 可用，2772 个算子从 CPU 移到 ANE → 释放 CPU 给 tick 其他工作。
**风险**：中（ANE 可能仍部分失败 → 需实测；且 `.all` 可能让 GPU 抢占）。

### 🟡 收益 3：world_model 降频（省 ~47 样本）

**现状**：`:2232`/`:2309`/`:2393` 三个调用点，**每次 ctl 推理成功后都跑** world_model。
**改法**：world_model 预测的是"下一帧 fused"（缓存供下帧预填充），不是必需——可以隔帧或隔 3 帧跑。
**收益**：省 1 次 CoreML prediction 调用 + CPU。
**风险**：低（预填充缓存延迟一帧，不影响主输出）。

### 🟡 收益 4：Quest OCR 不占主线程（省主线程 105 样本）

**现状**：采样显示 `QuestPanelReader.ingest` 占主线程 105 样本（VNImageRequestHandler ~33ms/次）。
**现状代码**（`AuroraDriveApp.swift:6920`）：`if AuroraFlags.questOCR, let cg = currentFrameCG { questPanel.ingest(cg) }`——在 tick 里调。
**改法**：OCR 已有内部异步队列，但 `ingest` 的 dispatch block 最终落在**主线程的 dispatch queue**上。改到独立低优先级队列。
**收益**：释放主线程 33ms/次 → V2 的 `isInferencing` 门更快释放。
**风险**：低（OCR 结果延迟无害，它不是驾驶控制路径）。

## 5 · ANE 是否跑不动？

**用户怀疑**：「ANE 的性能可能不足以跑动那个了」

**证据**：
- enc 走 ANE（`.cpuAndNeuralEngine`），历史实测 ANE 占比 100%、p50=0.36ms → **ANE 跑得动 enc**
- ctl 走 CPU（`.cpuOnly`），**不是因为 ANE 跑不动**，而是因为**历史上有 `while_loop`/`logical_and` 把它踢出 ANE**——但这两个算子现已移除
- 采样中 ANE 65,194 样本——ANE 确实在大量工作（enc + 可能还有其他模型），没有"跑不动"的迹象

**判定**：ANE 不是"跑不动"，是 **ctl 主动选择了 CPU**（因历史原因，且没在算子修复后重新尝试 ANE）。

- **tick（含 V2 infer 的调度）只有 0.02-1.42ms**

- V2 的 enc+ctl 历史实测 p50=0.83ms，也不是瓶颈

1. 用户体感的"主驾模型延迟"实为 **YOLOPX 感知链路的延迟**（它在驾驶链路里，用户不易区分是哪个模型）

## 8 · 修正后的可优化项

### 🔴 收益 5（新增，最高优先级）：降级时跳过 YOLOPX 推理

**证据**：日志 37 次 `da=0格 ll=0格 降级=true 耗时=82.8ms`——降级状态下 YOLOPX 仍每帧全速推理，产出空掩码。
**收益**：待机/降级时省 82.8ms/次 × 推理频率。
**风险**：低（降级时结果本就没人用；需确认"降级"判据不会误判正常帧）。


### 7.4 ★ 根因确认：YOLOPX 的降级是"事后判定"，不是"事前门禁"

**推理入口（`YolopxEngine.swift:898-906`）—— 无任何降级检查**：
```swift
guard enabled else { reset(); return }
guard isLoaded, let modelRef = model else { loadIfNeeded(); return }
guard !isInferencing else { return }        // 防重叠
// ← 这里没有 isDegraded 检查
```

**降级标志是推理之后才设的**（`finish()`，`:1059-1062`）：
```swift
if let error {
    errorMessage = error
    isDegraded = true          // 出错即降级 → 但本帧已经跑完了
    return
}
```
→ `isDegraded` 是**结果**，不是**门禁**。它只影响"决策层是否采信掩码"，**不影响"是否推理"**。

**调用方（`AuroraDriveApp.swift:7216-7219`）也无降级门禁**：
```swift
// YOLOPX 三合一：独立推理（自己的 letterbox 输入…）。
// 偶数帧门（detectGateA）；与 yolo26s 奇数帧错开，互不干扰。
// 停用 yolopxEngine.enabled 即完全退出。
if detectGateA {
    yolopxEngine.infer(image: cg)     // ← 唯一门禁是"偶数帧"，与降级无关
}
```

**⟹ 闭环结论**：日志里 37 次 `da=0格 ll=0格 降级=true 耗时=82.8ms` 的成因是——
1. `detectGateA`（偶数帧）触发 → 调 `yolopxEngine.infer`
2. 推理**无条件执行**（82.8ms）
3. `finish()` 里才判定 `isDegraded = true`（因为掩码全 0）
4. 下一帧重复 1-3 → **降级状态下持续全速烧 CPU**

**可优化**：在 `:7216` 的 `if detectGateA` 里加降级短路（例如 `&& !yolopxEngine.isDegraded`，但要加"每 N 秒重试一次"避免永久停摆——因为降级可能因场景变化恢复）。
**收益**：待机/降级时省 82.8ms × ~10Hz = **~828ms/s 的 CPU**（占单核 83%！）。
