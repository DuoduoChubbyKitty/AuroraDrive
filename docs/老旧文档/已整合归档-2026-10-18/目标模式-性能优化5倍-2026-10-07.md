## 目标（Objective）

把 AuroraDrive 的**运行时 + 未运行时性能消耗降低 5 倍**（即优化到当前的 **20%**）。
**用任何办法**，但必须满足下面全部约束。

**双口径都要降 5 倍**：
- **运行时**：驾驶中的引擎 CPU / tick 耗时 / 各推理子系统耗时
- **未运行时**：UI 空闲态 CPU / 内存占用 / 后备存储膨胀

## 三、5 倍目标的可达性分析（Lead 实测判断）

**要降 5 倍（到 20%），必须动结构，不能靠微优化。**

| 子系统 | 当前 p50 | 目标（1/5） | 可行性判断 |
|---|---|---|---|
| **infer.yolopx** | 22.647ms | **4.53ms** | ⚠️ **难**。yolopx 是重模型；要么换更小模型，要么降频，要么换算力单元 |
| **infer.yolo26s** | 14.065ms | **2.81ms** | ⚠️ **难**。同上 |
| infer.m9 | 4.099ms | 0.82ms | ⚠️ 难（但 p95 10.46ms 说明有长尾可削） |
| infer.assist | 3.509ms | 0.70ms | ⚠️ 难 |
| **opticalflow** | 6.171ms | **1.23ms** | ⚠️ 难（光流本身是密集计算） |
| **tick.loop** | 6.275ms | **1.26ms** | ✅ **可能**（tick 本身是调度逻辑，主要被光流吃掉） |
| **引擎 CPU** | 59.2% | **11.8%** | ✅ **最可能**（推理降频/条件触发能大幅降） |
| UI 空闲 CPU | 3.9% | 0.78% | ✅ **可能**（停掉无意义轮询/渲染） |
| UI RSS | 121MB | 24MB | ⚠️ 难（模型/缓存占用） |

**Lead 的判断**（⚠️ 2026-10-07 修订：加入"不降质量/不降帧率/不降分辨率"约束后，难度大幅上升）：

| 目标 | 在"不降质量"约束下的判断 |
|---|---|
| **引擎 CPU 5×** | ⚠️ **变难**。原本靠"推理降频"最容易达成，但**降频=降帧率被禁止**。现在只能靠：①消除重复计算 ②复用预处理 ③减少分配/拷贝 ④流水线并行（不减少计算量但省 CPU 空转） |
| **tick.loop 5×** | ⚠️ **变难**。原本靠"削光流精度"，现在必须**同样精度下把光流算得更快**（算法等价优化/并行化/SIMD） |
| **单模型推理 5×** | ❌ **基本不可能**（FLOPs 固定，`.all` 已是最快档位）——除非常规手段（模型重写/算子融合） |
| **UI 空闲 CPU 5×** | ✅ **最可能达成**（这一块**停掉无意义轮询是纯赚**，不涉及任何质量牺牲） |
| **UI RSS 5×** | ⚠️ **难**（模型权重硬占用；但底图分块加载可能有大幅回收） |

**⚠️ 诚实声明（重要）**：
- 5 倍是**激进目标**；在"不降质量"约束下，**部分项物理上可能达不到**
- **必须报告实际能达到的倍数**，不许编数字。"用任何办法"不等于"允许造假"
- **若某子系统的唯一达成路径是降质量 → 如实说明"不可达"，不要偷偷降**
- **优先做满 A 档（零牺牲）**：复用/缓存/去重/折叠/停无意义工作——**这些做满可能就有 1.5-3×**

## 四、允许的手段 + ★ 交换率判据（用户 2026-10-07 明确要求）

### 4.0 ★★ 核心判据：先看"交换率"，再谈手段

用户原话：
> 「可以让他少干活，就是**可以不降质量的少干活**。比如说各种**复用**，各种**缓存**，
> 各种**内存复用**，各种**折叠**什么的。而且还可以**降低极低的质量**，可以降低
> **非常小质量**这样那种就可以降低**非常少的质量**来换取**极高的性能提升**。
> 但是性能提升**必须是巨大的**。如果是**很小小性能提升，直接否决**，必须是提升巨大性能。
> 而且**牺牲极低**。」

**翻译成可执行规则（三档）**：

| 档 | 质量影响 | 性能要求 | 判定 |
|---|---|---|---|
| **A 档** | **零牺牲**（输出逐字节等价） | 有提升即可 | ✅ **无条件做** |
| **B 档** | **极低牺牲**（人眼/下游不可感知） | **必须巨大提升**（建议 ≥2×，即省 ≥50% 时间） | ✅ 做，但**必须给质量对照证据** |
| **C 档** | **任何明显牺牲**（分辨率↓/帧率↓/精度回退） | 即使提升大 | ❌ **一律否决** |

**B 档的"巨大"与"极低"量化建议**（待用户最终确认）：
- **巨大**：该子系统耗时 **降低 ≥50%**（= 提升 ≥2×）；**若只降 10-20% → 直接否决**，不要交
- **极低**：下游指标**无可测退化**（如检测框数不变、坐标误差在原有阈值内、无新增误检）
- **必须附证据**：改前/改后的质量对照数据（不是"感觉没差"）

### 4.1 A 档手段（零质量牺牲，优先做满）★★★

1. **复用 / 去重（算过的不再算）**
   - 同一帧被多个子系统重复预处理？（letterbox/缩放/灰度转换是否各做一遍）
   - yolopx 与 yolo26s 是否对同一帧重复做相同的预处理？
   - 地图查询是否重复计算同一结果（`map.isOnRoad` 已 0.000ms，但看 tick 里是否有重复调用）

2. **缓存（结果缓存 / 中间结果缓存）**
   - 模型输出的后处理（NMS/解码）是否可缓存
   - 地图瓦片/路网查询的 LRU 命中率
   - 光流结果是否被多处置信复用（算一次，多处读）

3. **内存复用（不重新分配）**
   - `CVPixelBuffer` / `MLMultiArray` 是否每帧新建？（池化复用）
   - 大数组是否反复 malloc/free
   - **注意**：❌「预分配 tempBuffer」已被实测否决（慢 20%）——要区分"预分配缓冲"与"复用已有对象"

4. **折叠 / 融合（等价变换）**
   - 多次遍历合并为一次遍历
   - 重复的坐标换算/矩阵乘法合并
   - 循环内不变量外提

5. **消除无用计算**
   - 算了但没人读的输出
   - 关闭的开关仍在跑的代码路径
   - **注意**：❌「去掉 PSA」「输出端压缩」已被否决（非瓶颈 / 瓶颈在主干）

6. **UI 空闲态：停掉无意义工作** ★★★（这一块通常**纯赚**，不涉及质量）
   - 3.9% CPU 空闲态说明有周期性任务（轮询/渲染）
   - 查：LLM 健康探活（60s）、地图瓦片预取、Timer、不可见视图刷新
   - **已实测**：LLM 探活是自适应的（空闲 60s 单探）

### 4.2 B 档手段（极低牺牲换巨大提升，需证据）★★

1. **计算图融合 / CoreML 编译优化**（通常数值等价或差异极小）
   - `xcrun coremlcompiler` 的优化选项
   - **注意**：`.all` 档位已实测最快，别动

2. **多模型共享主干**（若两个检测网确实算了两遍相同的东西）
   - yolopx + yolo26s 都是检测网 → 共享 backbone 可省一份主干计算
   - **但这是改模型结构**，必须给精度对照

3. **数据结构/内存布局优化**（如 SoA vs AoS、对齐、避免装箱）
   - 通常零牺牲，若引入微小数值差异则归 B 档

4. **降分辨率类**（**仅当满足 B 档交换率**）
   - ⚠️ **不是默认允许**！必须证明：降分辨率后**下游无可测退化** + 耗时**降 ≥50%**
   - 例：光流 6.171ms 是 tick.loop 的全部 → 若能降分辨率且下游无退化，才有资格谈
   - **若下游有退化（检测框减少、坐标漂移）→ 归 C 档，一律否决**

### 4.3 内存优化（未运行时）

1. **模型按需加载 / 卸载**（当前 4 个模型常驻）—— 注意不能影响推理延迟
2. **缓存上限**（地图瓦片 LRU 已有，检查容量）
3. **底图分块加载**（13056² 整张解码可能占几百 MB）
4. **日志缓冲**（dlog 已有优化：热路径 0.000ms）

### 4.4 未运行时

1. **二进制体积**（13.3MB → 可 strip/裁剪）
2. **`.build` 938M** → 可清中间产物（但不影响运行时）

### 4.5 ⛔ 明确禁止（C 档，用户点名）

- ❌ **降分辨率**（除非满足 B 档交换率且有下游无退化证据）
- ❌ **降帧率**（推理频率、UI 刷新率）
- ❌ **明显降质量**（检测精度、坐标精度、画面质量）
- ❌ **小提升换任何牺牲**（"提升 10% 但精度掉一点" → **直接否决**）

## 五、必须遵守的纪律

1. **★ 先过交换率判据**（见 §4.0）：
   - **A 档**（零牺牲 + 任何提升）→ 做
   - **B 档**（极低牺牲 + **提升 ≥50%**）→ 做，**必须附质量对照证据**
   - **C 档**（明显牺牲）→ **一律否决**，不管提升多大
   - **小提升（<50%）换任何牺牲 → 直接否决，不要提交**
2. **先测后改**：任何改动前先跑 `--perf-selftest` 拿基线，改后再跑，**ABBA 对照**
3. **不许重试 13 项否决清单**
4. **不许因为"看着超了"就放松阈值**（本项目已有教训）
5. **精度优先**：任何有质量影响的优化**必须给出对照数据**（如 letterbox vImage 的 9→6 回退就是反面教材）
6. **数字必须实测**：用 `--perf-selftest` / `--tick-profile` / `ps` 等可复现命令
7. **达不到就如实报告实际倍数**，不许编
8. **环境一致**：对比时保证负载相近（记录 `uptime` 负载值）

### 5.1 🔴 测量纪律（血泪教训：并行测量 = 测不准）

**实测证据（2026-10-07 14:5x）**：8 个代理并行跑 `--perf-selftest` 时，
同一份"基线"三次测量结果**互相矛盾**：

| 轮次 | tick.loop p50 | 引擎 CPU | 提交次数 | 说明 |
|---|---|---|---|---|
| a | 2.634ms | 32.9% | 211（21.1Hz） | |
| b | **18.121ms** | 15.7% | **84（8.2Hz）** | max 2882ms ← 被抢占 |
| c | 9.987ms | 40.7% | 210（20.9Hz） | |

**三组差 7 倍**，根因：系统负载 **26.23**（8 核 → 3.3× 超载），
且**同时有 2 个 `AuroraDriveUI` 实例在跑**（互相抢引擎 socket）。

**规则（必须遵守）**：
1. **同一时刻只能有一个性能测量在跑** —— 测量前 `pkill -f AuroraDriveUI` 清干净
2. **测量前检查负载**：`uptime` 的 load 必须 **< 8**（8 核）才可信；否则等
3. **禁止在别人测量时启动自己的测量**（会同时污染两边的数据）
4. **ABBA 对照**：A/B/A/B 四轮，看 A 与 A、B 与 B 是否一致（差异 >10% → 环境不稳，重测）
5. **记录负载值**：每轮测量都把 `uptime` 写进报告，让别人能判断可信度
6. **性能优化是串行工作**：8 个方向可以并行**改代码/写分析**，
   但**测量必须排队**（用 `scripts/build-lock.sh` 之外的单独测量锁，或人工协调）

**推论**：`--perf-selftest` 的「引擎进程 CPU」在超载环境下**完全不可信**
（a=32.9% / b=15.7% / c=40.7%，而 Lead 静默测得 59.2%）。
**必须空载复测**。
