## 0. 摘要（TL;DR）

M9-V2 是**五输入**端到端模型（旧 M9 是两输入），输入 `image / lane / dets / det_mask / vehicle_state[8]`，
输出 `steer / throttle / brake`。本引擎**独立成文件**、靠开关切换，旧引擎一字未动。

**三件最值得说的事**：

1. **修了 Lead 核实的两个既有 bug**（`vehicle_state` 6 维只用了 2 维；`speedKmh=-1` 未判 `speedValid` 就归一化）。
2. **顺带发现了两个**上游文档/契约的**真实冲突**（见 §4）——curvature 归一化量纲不一致、heading 一词两义。
3. **车道线几何是真算的**（二次拟合 → 曲率/朝向/横向偏移），不是硬编码占位；并加了三层抗退化保护（含 INT8 量化会把车道线打没的实测结论）。

## 1. 新增了什么

`InferenceEngineV2.swift` 的核心组件：

| 组件 | 职责 |
|---|---|
| `V2InputContract` | 单一常量表：CoreML 特征名 / 尺寸 / 维度。**特征名是 `lane` 不是 `lane_mask`**（最易踩坑点） |
| `V2Config` | 可调参数集中定义（采样带、退化阈值、标定基准） |
| `LaneMaskSnapshot` | `MaskGrid` 的 Sendable 值快照（跨 actor 安全，可离线单测） |
| `LaneGeometry` + `LaneGeometryEstimator` | 车道线几何：二次拟合 → 曲率/朝向/横向偏移，**无状态纯函数** |
| `V2FeatureBuilder` | 五路纯特征构造（8 维 state / 20×12 dets / det_mask / lane），**无 CoreML 依赖，可离线单测** |
| `InferenceEngineV2` | `@MainActor` 引擎：异步推理、复用缓冲、优雅降级、PerfBus 埋点 |

### 1.1 五路输入构造

- **image `[1,3,180,320]`**：与旧引擎同算法（缩放 → RGBA → CHW → vDSP 归一化）。
- **lane `[1,1,160,160]`**：来自 `yolopxEngine.laneMask`（MaskGrid），转 0/1 二值。⛔ **只放车道线，不掺 drivableMask**（契约红线）。
- **dets `[1,20,12]`**：`Detection` → 12 维编码（`x,y,w,h,onehot4,conf,speed,heading,age`），**置信度降序**填前 20 槽，空槽全 0 + `det_mask` 置 0。
- **det_mask `[1,20]`**：1=有效框。
- **vehicle_state `[1,8]`**：`speed, accel, heading, heading_rate, curvature, lateral_offset, steer_angle, ego_visible`。

### 1.2 输出

`steer / throttle / brake`，转成 `InferenceResult`（与旧引擎**完全兼容**）。

## 2. 两个既有 bug 怎么修的

### bug 1 · `vehicle_state` 6 维里 3 维恒常量（`InferenceEngine.swift:431-436`）

**症状**：`curvature`/`sin(heading)`/`reserved` 恒 0，`cos(heading)` 恒 1 → 6 维只用了 2 维。

**修法**：`LaneGeometryEstimator` 从车道线掩码**真算**曲率与朝向。
- 逐行找车道线连续段 → 左右分组 → 二次拟合 `centerX = a·s² + b·s + c`
- 由系数导出一阶（朝向）/二阶（曲率），喂进 `vehicle_state[2]` 与 `[4]`

**关键诚实点**：无有效车道线时，几何**整体作废**（valid=false，三量全 0），对应 `model_v2.py` 的"全零=未知"语义——**绝不编造几何量**。

### bug 2 · `speedKmh=-1` 未判 `speedValid`（`SpeedOCRReader.swift:157`）

**症状**：`speedKmh` 读不到时为 **-1**，直接归一化会把负速度喂进模型。

**修法**：`V2FeatureBuilder.buildVehicleState` 以 `speedValid` 为**硬门**：
- `speedValid=false` → speed 填 0（**且 accel 也填 0**，因为速度不可信时它的导数同样不可信）
- `speedValid=true` → 按 `speed/120` 归一化并 clamp

## 4. 顺带发现的两个契约冲突（需决策）

### 4.1 ⚠️ curvature 归一化量纲不一致

- **训练侧**（`src/dataset_v2.py:64`）：`curvature_x5 = clip(curvature * 5, -1, 1)` —— curvature 是**物理量（1/米）**，参考基准 0.2 米⁻¹。
- **本引擎**：只能从**像素**估计曲率（游戏不给物理曲率遥测），`curvatureReference = 0.02` 是**像素⁻¹**。
- **矛盾**：两者差一个"像素↔米"的比例因子，**数值分布很可能与训练分布不匹配**。

**结论**：曲率的**符号**（左弯/右弯）可靠，**绝对大小**待标定。接线上车做端到端验证前必须补标定。已如实写进代码注释（CALIBRATION-PENDING）。

### 4.2 ⚠️ heading 一词两义

- **M1 文档的 heading**：`NetworkLocator.locatorHeading`，世界坐标系绝对方位角，**单位是度**（`NetworkLocator.swift:310`）。
- **本引擎的 heading**：车道线视觉朝向（相对车头指向的角度，弧度），完全不同的量。
- **风险**：若将来有人把 `locatorHeading`（度）直接喂进 `vehicle_state[2]`（期望 /π 弧度），会得到完全错误的角度。

**结论**：本引擎只消费"车道线视觉朝向"，代码注释已明确与 `locatorHeading` 区分。若接 `locatorHeading`，必须"度→弧度 + 世界系→车身系"两次变换。

## 5. 车道线几何的抗退化保护（三层）

来源：Lead 补充情报——项目既有实测 `tools/yolopx/export_yolopx_coreml.py:58-64`：**INT8 量化把车道线正像素占比从 1.30–1.80% 打到 0.13–0.21%（约 10×）**，而 `yolopxEngine.laneMask` 的来源可能就是 INT8 的。

| 层 | 保护 | 依据 |
|---|---|---|
| 第 0 层 | 前景格数 < `minLanePixels`(30) → 整体无效 | INT8 会把车道线打到只有 33~54 格（正常 333~461 格） |
| 第 1 层 | 有效行数 < `minLaneRows`(6) → 整体无效 | 碎片行拟合不出可信曲线 |
| 第 2 层 | 单侧车道线 → heading/curvature 保留、**lateralOffset 置 0** | 单侧的中心是补出来的，不能反映车在车道里的相对位置 |
| 第 3 层 | 离群行剔除 + 重拟合（2.5×中位残差） | 单侧行补出的中心混进双侧样本会污染拟合 |

**第 3 层来自一次真实 bug**：自检时发现弯曲车道线在远端越出画面被裁 → 该行变成单侧 → 补出的中心与整体趋势偏离 → **曲率符号翻转**（右弯算成负值）。稳健化后再拟合符号恢复正确。
