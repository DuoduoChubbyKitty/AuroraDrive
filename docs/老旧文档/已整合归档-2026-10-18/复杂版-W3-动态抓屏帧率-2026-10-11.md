## 1. API 可用性论证（官方头文件原文）

### 1.1 签名（`SCStream.h:500`）

```objc
/*!
 @abstract updateConfiguration:completionHandler:
 @param streamConfig the requested content filter to be updated
 @param completionHandler the handler to be called when the function completes
 @discussion this method will update the stream configuration for a content stream.
     A completion handler will be called when the update is complete with an error
     denoting if the update has failed.
*/
- (void)updateConfiguration:(SCStreamConfiguration *)streamConfig
          completionHandler:(nullable void (^)(NSError *_Nullable error))completionHandler
          NS_SWIFT_ASYNC_NAME(updateConfiguration(_:))
          NS_SWIFT_NAME(updateConfiguration(_:completionHandler:));
```

**Swift 签名推导**：
- `NS_SWIFT_ASYNC_NAME(updateConfiguration(_:))` → Swift async 版本为
  **`func updateConfiguration(_ config: SCStreamConfiguration) async throws`**
- `completionHandler` 的 `NSError *` 参数 → Swift 的 `throws`
- 参数是 `SCStreamConfiguration`（非 Optional，无 `nullable`）→ **必须传完整 config**

### 1.2 availability

`SCStream.h` 中：
```objc
API_AVAILABLE(macos(12.3), macCatalyst(18.2))
@interface SCStream : NSObject
```
`updateConfiguration` 方法本身**无额外 `API_AVAILABLE` 标注** → 继承类级 **macOS 12.3**。
本项目 `Package.swift`：`platforms: [.macOS(.v26)]` → **远高于要求，可用** ✅

### 1.3 ⚠️ 头文件未保证的部分

头文件只说 "update the stream configuration"，**未明示哪些字段支持热更**。
`minimumFrameInterval` 是**采集节流参数** —— 有可能：
- 建流时固化，热更时被**忽略**（静默无效）
- 或热更成功但不重建采集管线 → 帧率不变

⟹ **这是本实现的已知弱点**，见 §4.1。

```swift
static func makeStreamConfiguration(configHz: Double, display: SCDisplay) -> SCStreamConfiguration {
    let config = SCStreamConfiguration()
    // …width/height/scalesToFit 逻辑**逐字不变**…
    let safeHz = max(1.0, min(120.0, configHz.isFinite ? configHz : 45.0))
    let tscale = max(1, Int(safeHz.rounded()))
    config.minimumFrameInterval = CMTime(value: 1, timescale: CMTimeScale(tscale))  // ← 参数化
    // …pixelFormat/queueDepth/showsCursor **逐字不变**…
    return config
}
```
`start()`（`:458`）改为：
```swift

```

**为什么抽成静态**：`start()` 首次建流与 `setCaptureHz` 热更**共用同一份**配置逻辑，

**⚠️ 分辨率逻辑保持不动**（任务要求）：
- `targetW = 1280`、`height` 按屏幕宽高比算（3:2 → 832）
- `scalesToFit = false`（无 letterbox、坐标不错位）

### 2.5 `setCaptureHz(_:) async`（`:657`，新增）

```swift
func setCaptureHz(_ hz: Double) async {
    let newHz = max(1.0, min(120.0, hz.isFinite ? hz : 45.0))
    let old = targetCaptureHz
    targetCaptureHz = newHz
    print("[cap-deep] setCaptureHz(\(newHz)) 旧值=\(old) isCapturing=\(isCapturing)")

    guard isCapturing, let stream = stream, let display = currentDisplay else {
        // 未在捕获 → 只记 targetCaptureHz，下次 start() 生效
        return
    }
    guard newHz != old else { return }   // 频率未变 → 不做无谓 updateConfiguration

    // ① 热更路径（优先，不闪帧）
    let newConfig = Self.makeStreamConfiguration(configHz: newHz, display: display)
    do {
        try await stream.updateConfiguration(newConfig)
        activeCaptureHz = newHz
        return
    } catch {
        print("[cap-deep] ❌ updateConfiguration 失败: \(error) → 回退重启流")
    }

    // ② 回退路径：停止 + 重启（复用 pendingStopTask 竞态防护）
    if let pending = pendingStopTask {
        await pending.value
        pendingStopTask = nil
    }
    stop()
    start()   // 内部 await pendingStopTask + 读新 targetCaptureHz 建流
}
```

**三条分支**：
| 场景 | 行为 |
|---|---|
| 未在捕获 | 只写 `targetCaptureHz`，下次 `start()` 自动用上 |
| 频率未变 | 直接返回（不做 `updateConfiguration`） |
| 已在捕获 + 频率变 | ① 热更 → 失败则 ② stop+start 回退 |

## 3. `updateConfiguration` 失败时的回退方案

**回退链**：`updateConfiguration` 抛错 → `stop()` + `start()`

**竞态防护**（复用 task-C 的 `pendingStopTask` 模式）：
1. 回退前先 `await pendingStopTask`（等上一次 stop 的异步清理完成）
2. `stop()` 同步置 `isCapturing=false` + `stream=nil`，异步做 `stopCapture()` + 清池
3. `start()` 内部**也会** `await pendingStopTask`（已有的防护）→ 避免"旧流 stopCapture 与新流 startCapture 交错"

**代价**：回退会**闪一帧**（stop→start 之间有间隙），但**保证帧率最终生效**
（比"静默不改"安全 —— 用户以为切了、实际没切是最糟的）。

**为什么保留热更优先**：官方 API 存在且无版本限制；成功则零闪帧。
即使热更"静默无效"（不抛错但不生效），**回退路径也能兜住**（只要它抛错）。

## 4. ⚠️ 诚实标注（3 项未验证）

### 4.1 `minimumFrameInterval` 能否热更生效 —— **未验证**

**依据**（`SCStream.h:500` 原文）：头文件只说 "update the stream configuration"，
**未明示**哪些字段可热更。`minimumFrameInterval` 是采集节流参数，**有可能被建流时固化**。

**⟹ 本实现的弱点**：`updateConfiguration` **不抛错 ≠ 真的生效**。
成功路径直接置 `activeCaptureHz = newHz` 是**乐观假设**（已在代码注释标注）。

**实测方案（待编译解冻后执行）**：
1. 启动引擎，看 `[cap-deep] 📥 帧到达 #N` 打印频率（默认每 60 帧一次）
   —— 45fps 下应约 **1.33s 一次**（60/45）
2. 调 `setCaptureHz(30)`，再看间隔
   —— 生效应约 **2.0s 一次**（60/30）；**不变 → 热更无效**
3. 更严谨：固定 5s 窗口数帧数（45fps → ~225 帧；30fps → ~150 帧）
4. **若确认热更无效** → **回退路径必须成为主路径**（总是 stop+start），
   或改为"先热更、再按 `measuredCaptureHz` 校验、不符则重启"

**已为此提供工具**：新增的 `measuredCaptureHz`（§2.3）就是为这个验证而加。

### 4.2 🔴 收益存疑（w6 反证审计发现，Lead 转告）

w6 反证审计实测：
```
yolopx p50 = 32.8ms（11 个独立样本，>22.2ms 的占 100%）
→ 45Hz 到达间隔 22.2ms < 服务时间 32.8ms → 队列饱和
→ 产出率被服务时间锁定（~30.5Hz）
```

**推论**：若 45Hz 下 yolopx 产出率不变，则 **45fps 抓屏（比 30fps 多 50% 数据）可能是白费带宽**。

**⚠️ 这不是本次实现能解决的** —— 是**收益评估**问题。需 W7 实测"45Hz 下实际产出率"才能定论。

## 6. 我自己复查时抓到并修掉的两处

### 6.1 `var config` → `let config`（`:458`）
抽取函数后 `config` **不再被重新赋值**（原内联版本也没有），用 `var` 会产生编译警告。

### 6.2 回退路径删掉 `activeCaptureHz = newHz`
**初版错误**：
```swift
stop()
activeCaptureHz = newHz   // ❌ 设在流真正重启之前
start()
```
**问题**：`activeCaptureHz` 是**"已生效"**语义，但此处流还没建起来。
若 `start()` 失败（权限/窗口消失等），这个值就**说谎**了。

**修法**：删除该行，只由 `startStream` 成功路径（`:530`）设置。
```swift

// activeCaptureHz 待 startStream 成功后由那里设置
```
