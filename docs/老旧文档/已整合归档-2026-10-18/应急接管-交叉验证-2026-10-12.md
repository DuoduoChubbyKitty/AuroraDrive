## 2. 跨进程一致性（★ ET-9 已修 · 原 P0 已消除）

> **⚠️ 重要时间线**：本报告初稿（13:2x）核实到「UI 实例永不触发 → 横幅永不显示」的 P0 缺陷。

> 本节已按**修复后**的代码重写。**原 P0 不再成立。**

### 2.1 两个进程各有一个实例（前提不变）

```swift
// EmergencyTakeover.swift:48
static let shared = EmergencyTakeover()   // ← 每进程一个单例，不是跨进程共享
```
`EmergencyTakeover.swift:36` 注释自承：「**双进程注意**：@MainActor 隔离；双进程（UI + engine）各有独立实例。」

**⟹ UI 和引擎各持一份状态。这是 ET-9 要解决的问题根源。**

### 2.2 为什么需要 ET-9（问题的成因，仍然成立）

```
【UI 进程】tick() → :6881 noteTickGap(实测间隔)
                  → :6918 isActive=true → tickEngineMode(); return   ← 早退
```
- UI tick 由 `MissionConsole:6035` 的 **20Hz 定时器**驱动 → 间隔 **≈50ms**
- `takeoverTickGapMs = 80.0`（`EmergencyTakeover:65`）→ **50ms < 80ms → 永不掉拍**
- **⟹ UI 实例自己永远算不出 `takeoverActive=true`**

### 2.3 ★ ET-9 修复链：5/5 闭环（逐环核实）

| 环 | 位置 | 代码 | 判定 |

| ② **EngineClient 解析** | `EngineClient.swift:432-433` | `if let v = obj["takeover"] as? Bool { engineTakeoverActive = v }` | ✅ |
| ③ **切主线程同步** | `EngineClient.swift:436-439` | `DispatchQueue.main.async { EmergencyTakeover.shared.syncFromEngine(takeover:userHolding:) }` | ✅ |

| ⑤ **横幅读状态** | `MissionConsole.swift:708` | `else if EmergencyTakeover.shared.takeoverActive` | ✅ |

**⟹ 引擎的 `takeoverActive=true` → heartbeat → UI 实例 → 横幅显示。链通。**

**ET-9 的设计决策（我核实认可）**：
- `syncFromEngine` **只写显示状态**（`takeoverActive`/`userHoldingKey`），**不写** `effectiveTickHz`（`EmergencyTakeover:174-175` 注释明说"UI 进程不控制频率"）→ **UI 实例只做显示镜像，不自己算** ✅ 干净

### 2.5 ⚠️ ET-9 残留问题 1（P1）：UI 进程仍在本地喂 `noteModelDegraded`

**核实**：`AuroraDriveApp.swift:6881-6885`（**同一份 tick() 代码，两进程都跑**）：
```swift
EmergencyTakeover.shared.noteTickGap(tickGapMs)
if yolopxEngine.isLoaded {
    EmergencyTakeover.shared.noteModelDegraded(yolopxEngine.isDegraded)
}
```

**风险链**：
```
UI 进程若加载了 yolopx 且 isDegraded=true
  → noteModelDegraded(true) → UI 实例 enterSprint()
  → UI 实例 takeoverActive=true（本地自设）
  → 横幅显示
  → 但如果引擎侧实际未进入冲刺 → 下个 heartbeat 回传 false
  → syncFromEngine 把它写回 false → 横幅消失
  → 引擎再发 true（若真降级）→ 又显示
  ⟹ 横幅闪烁
```

**⚠️ 但需注意**：`noteTickGap` 的 UI 侧不会触发（50ms < 80ms），**只有 `noteModelDegraded` 这条路径**可能让 UI 自进冲刺。
**关键未知**：**UI 进程是否加载 yolopx**（`yolopxEngine.isLoaded`）——若 UI 不加载模型，此风险不存在。
**我的核实**：`:6282-6284` 只看到 `inferenceEngine.loadIfNeeded()` / `inferenceEngineV2` / `assistEngine`——**未见 `yolopxEngine.loadIfNeeded()`**；且引擎模式下 UI 的推理本应不跑 → **倾向"UI 未加载 yolopx"→ 风险低**。
**但未能 100% 确认**（未跑 app，无法验证 `isLoaded` 运行时值）→ **标注 P1 待确认**。

**建议（供 Lead 决策）**：UI 进程**不该**喂 `noteModelDegraded`——因为 ET-9 已确立"UI 实例只做显示镜像"的设计。
最小修法：`if !EngineClient.shared.isActive { noteModelDegraded(...) }`（引擎模式下 UI 不喂）。
**这不在我写作用域，仅建议。**

### 2.6 ⚠️ ET-9 残留问题 2（P2）：heartbeat 1Hz 延迟

`EngineMain:1839-1841` 注释自承：

### 2.7 ⚠️ ET-9 残留问题 3（P2）：`sprinting` 未同步

`syncFromEngine` 只同步 `takeoverActive`/`userHoldingKey`（`EmergencyTakeover:170-176`），**不同步 `sprinting`** → UI 实例的 `sprinting` 恒为 `false`。
**当前无害**（我核实 `MissionConsole` 只读 `takeoverActive`/`userHoldingKey`，不读 `sprinting`）。
**风险**：若未来 UI 代码依赖 `sprinting`，会读到错值。**P2（文档记录）**。

### 2.8 判定

## 3. `noteUserKeyDown/Up` 状态守卫（Lead 第②条）

### 3.1 实现
```swift
// :136
func noteUserKeyDown() {
    if sprinting { enterYield() }        // 只在冲刺态响应
}
// :144
func noteUserKeyUp() {
    if userHoldingKey { enterCruise() }  // 只在让位态响应
}
```

### 3.2 Lead 担心的漏洞：「用户按键时若还没进冲刺态，会被忽略？」

**分两种情形**：
| 情形 | 是否进 sprinting | 按键是否被忽略 | 判定 |
|---|---|---|---|
| **tickGap 掉拍触发** | `enterSprint()` 设 `sprinting=true` | 否（冲刺态按键→让位 ✅） | ✅ 正常 |
| **模型降级触发** | `noteModelDegraded` → `enterSprint()` **也设 `sprinting=true`** | 否（同上） | ✅ 正常 |
| **巡航态（无触发）用户按键** | `sprinting=false` | **是，被忽略** | ⚠️ **设计如此**（巡航态无需让位） |

**⟹ Lead 担心的"模型降级路径按键被忽略"不成立**——两条触发路径都经 `enterSprint()` 设了 `sprinting=true`。

### 3.3 但发现一个真实时序风险 ⚠️

**跨进程延迟**：UI 监听按键 → socket → 引擎处理（`EngineMain:1685`）。
```
用户按键 → KeyboardMonitor 回调（UI 进程）
        → sendCommand("config", ["takeover":true])   ← socket 往返
        → 引擎收到 → noteUserKeyDown()
```
**如果用户按键时引擎**尚未**进入 sprinting（例如掉拍检测刚累计到第 2 帧）** → `noteUserKeyDown` **被静默丢弃** → 用户按了但没让位 → **且无任何提示**。

**严重度**：P1（不是致命，但会导致"按了没反应"的用户困惑）。

## 4. 频率冲突（Lead 第③条）

### 4.1 两层防线（ET-5 的实现）

**第一层：源头 guard**（`EngineMain:809`）：
```swift
guard !EmergencyTakeover.shared.takeoverActive else {
    return (false, "应急接管进行中（\(Int(...effectiveTickHz))Hz）：档位频率暂不应用（应急优先），结束后自动恢复")
}
```
**第二层：tickOnce 兜底**（`EngineMain:1174`）：
```swift
let wantHz = EmergencyTakeover.shared.effectiveTickHz   // 每 tick 读
```

### 4.2 判定 ✅

| 场景 | 结果 |
|---|---|
| 应急中用户切档 | 源头 guard 拒绝，ack `ok:false` + 明确 detail → **UI 知情** ✅ |
| 应急结束 | `enterCruise()` 设 `effectiveTickHz=20` → `tickOnce` 读到 20 → `setTickHz(20)` ✅ **自动恢复** |
| 频率互相覆盖？ | **不会**：应急期间档位应用被源头拦截；应急结束后 tickOnce 以 `effectiveTickHz` 为准 |

### 4.3 ⚠️ 但 ack `ok:false` 的语义可能让 UI 误判

`applyPerceptionMode` 返回 `(false, "应急接管进行中...")` → ack `ok:false`。
**风险**：UI 若把 `ok:false` 当"配置失败"（而非"暂缓"），可能弹错误提示或回滚开关 → **用户看到"切档失败"的误导信息**。

**ET-5 已在 `:1706` 加了回显**（`applied["takeover"]`），但**档位本身的 `ok:false` 语义未区分"失败"与"暂缓"**。
**严重度**：P2（需确认 UI 侧如何处理 `ok:false`）。

## 5. 状态机逻辑走查

### 5.1 主路径（巡航→冲刺→让位→巡航）

| 转换 | 代码 | 判定 |
|---|---|---|
| 巡航→冲刺（掉拍） | `noteTickGap`:116-120（3 帧 >80ms） | ✅ 可走通 |
| 巡航→冲刺（降级） | `noteModelDegraded`:130 | ✅ 可走通 |
| 冲刺→让位 | `noteUserKeyDown`:138 | ✅ 可走通 |
| 让位→巡航 | `noteUserKeyUp`:146 | ✅ 可走通 |
| 冲刺→巡航（35s 超时） | `noteTickGap`:106-110 | ✅ 可走通 |

### 5.2 35 秒超时 ✅
```swift
if sprinting {
    if let start = sprintStart, Date().timeIntervalSince(start) >= 35.0 { enterCruise() }
    return
}
```
**但注意**：超时检查**只在 `noteTickGap` 被调用时**执行。若冲刺期间 tick 仍在跑 → 每帧都调 → ✅ 超时能生效。
**⚠️ 若 tick 完全停摆**（引擎卡死）→ `noteTickGap` 不被调用 → **超时永不触发** → 卡在 45Hz。**严重度 P2**（tick 停摆是极端场景）。

### 5.3 ⚠️ 发现状态卡死风险（P1）

**场景**：冲刺期间用户**一直按住**受控键。
```
冲刺 → 用户按下 → enterYield（hz=5, userHoldingKey=true）
     → 用户一直不松手
     → noteTickGap 第 102 行 `if userHoldingKey { return }` 直接返回
     → 35s 超时检查**被跳过**（因为 `if sprinting` 分支都进不去）
     → **永远停在 5Hz**
```
**分析**：这是**有意设计**（用户接管期间不干预），且 5Hz 是省 CPU 的（把算力让给用户），**对用户是安全的**。
**但**：`takeoverActive` 仍为 `true` → 若横幅能显示，会一直显示"已接管"；用户松手才回巡航。
**判定**：**P1 但可接受**（用户主动接管期间保持 5Hz 合理），需在文档中说明"用户不松手则一直 5Hz"。

### 5.4 状态归零检查 ✅
`enterCruise()`（`:201-209`）重置全部 6 个字段（`sprinting`/`takeoverActive`/`userHoldingKey`/`sprintStart`/`consecutiveMisses`/`effectiveTickHz`）→ **无残留** ✅
