## 二、改动清单（仅 `EngineMain.swift`）

### 2.1 `engineTickHz`：`static let` → `static var`

```swift
// 改前：static let engineTickHz: Double = 30.0
// 改后：
static var engineTickHz: Double = 30.0          // 默认仍 30（保持既有行为）
nonisolated(unsafe) private static var lastAppliedTickHz: Double = 0.0
```

`engineTickHz` 全文件引用点核实（任务第 4 条要求）：
- `EngineMain.swift:967`（tickTimer 初始 schedule）← 唯一代码引用
- `AuroraDriveApp.swift:7065` ← **仅注释**（"见 EngineMain.engineTickHz 的长注释"），不受影响
- 新增的 `setTickHz` / `currentTickHz` 读它

### 2.2 `setTickHz(_:)`：动态重调度

```swift
@MainActor static func setTickHz(_ hz: Double)
```
- 非有限/≤0 → 忽略 + 日志（性能参数，坏值不崩）
- 钳制 5~120Hz
- **防抖**：与 `lastAppliedTickHz` 差 <0.01 就 return（避免 UI 每 tick 重发 config 抖动调度）
- 用 `engineTicker?.schedule(deadline:repeating:leeway:)` **重复调用**重调度
  （`DispatchSourceTimer` 官方支持，不必 suspend/reload）

### 2.3 ⚠️ deadline 用 `now + 一个完整周期`（消除 0ms 双触发）

**Lead 实测发现的副作用**：直接 `schedule(deadline: .now(), ...)` 会在切换瞬间
多触发一次 tick（间隔 0ms）：
```
GAPS: 204,200,197,204,[0],54,50,50,...
```

**本小姐独立复现并验证修法**（实验代码 `/tmp/t93/timer_test.swift`，真跑 5Hz→20Hz 切换）：
```
【方案B deadline.now()】
  全部间隔: 205,200,200,200,200,[0],55,48,50,50,52,...
  最小间隔: 0ms   ⚠️ 有双触发
【方案A deadline.now() + 1周期】
  全部间隔: 195,204,197,204,207,[80],37,64,43,44,48,...
  最小间隔: 33ms  ✅ 无双触发
```

**采纳方案 A**，理由（不只是"照 Lead 说的"）：

副作用评估（三条路径逐条查过）：
| 路径 | 是否幂等 | 依据 |
|---|---|---|
| 按键注入 `hold()/release()` | ✅ **幂等** | `ControlEngine.swift:377` `if heldKeys.contains(keyCode) { return }`；`:386` release 同理 |
| 录制 `appendFrame` | ✅ **背压保护** | `RecordEngine.swift:478` `guard pending <= maxPendingWrites else { return }` |
| **异步推理投递** | ❌ **无幂等守卫** | `tickOnce` 里 `Task { @MainActor in ... }` 每次 tick 都投递一个新任务 |
| **`refreshHeldKeys()`** | ❌ 无守卫（刻意如此） | `ControlEngine.swift:415` 每控制周期重发 keyDown（项目**需要**这个事件流）|

⟹ 有两处没有幂等保护。虽然"多投递一次推理"在 45Hz 下大概率无害（结果会被下一帧覆盖），
但**与其论证"无害"，不如彻底消除不确定性**：等一个完整周期再起跑，
切换点变成干净的「旧周期 → 新周期」。

**代价**：切档后首个新周期晚到 `1/clamped` 秒（30→45Hz 晚 ~22ms，45→30Hz 晚 ~33ms）。
一次性的、方向正确（新频率的首帧本就该等一个周期），且 `engineTickHz` 立即更新用于诊断回显。

### 2.4 `tickHz(forPerceptionMode:)`：档位 → 频率单一映射点

```swift
"ayolom"           → 45.0
"legacy" | "yolopx" → 30.0
其他                → nil（不猜）
```

### 2.5 `applyPerceptionMode(_:isRecording:)`：录制中**延后**而非拒绝

**设计决策 + 理由**（Lead 要求写清）：

| 方案 | 行为 | 问题 |
|---|---|---|
| **拒绝** | 录制中收到切档 → 记日志"不切" → 频率**永远不变** | ❌ **静默失败**：用户以为切了。且模型档已由 `yolopxEngine` 切了、只有 tick 频率没跟上 → 两者不一致。用户必须"停止录制 → 再切一次" |
| **延后**（✅ 采纳） | 录制中 → 挂起 (`pendingTickHz`) → **停止录制时自动补切** | 用户意图最终满足，且录制会话内频率**恒定**（不破坏帧率语义）|

⟹ **选延后**：既守住"录制中不切"的硬约束，又不丢用户意图。

### 2.6 接线点

1. `run()` 的 timer 装配段：`resume()` 后调 `noteInitialTickHz(engineTickHz)` 登记初始频率
2. `case "config"`：读 `obj["perceptionMode"] as? String` → `applyPerceptionMode(mode, isRecording: st.isRecording)`
3. 录制停止分支（`else if !recOn, st.recordEngine.isRecording`）：`stop()` 后调 `flushPendingTickHz()`

## 三、线程安全论证（Lead 要求）

| 项 | 分析 |
|---|---|
| **tickTimer 在哪个队列** | `DispatchQueue(label: "aurora.engine.tick", qos: .userInteractive)`（`EngineMain.swift:878`）——timer 的 **eventHandler 在该队列**执行，但 handler 内部 `DispatchQueue.main.async { MainActor.assumeIsolated { tickOnce() } }`，即**真正工作在主线程** |
| **setTickHz 从哪调用** | `case "config"` 的 `DispatchQueue.main.async { MainActor.assumeIsolated { ... } }` 块内 → **主线程**。故 `setTickHz` 标 `@MainActor` 与调用点一致 |
| **`schedule()` 重调度线程安全吗** | ✅ GCD 的 `DispatchSourceTimer.schedule` 本身线程安全（内部同步）。收敛到主线程是为了保证 `engineTickHz` / `lastAppliedTickHz` 的**读-改-写原子性**，避免与读它的诊断路径竞争出旧值 |
| **`engineTicker` 为何 `nonisolated(unsafe)`** | 既有声明（`:919`），与 `engineHeartbeat` 同模式；只在 `run()` 装配段与 `setTickHz` 访问，两处都在主线程 |
| **`pendingTickHz` 为何 `nonisolated(unsafe)`** | 只在 `applyPerceptionMode` / `flushPendingTickHz` 里读写，两者都是 `@MainActor` → 实际单线程。标 `nonisolated(unsafe)` 是**沿用该文件既有静态变量的模式**（与 `engineTicker` 一致），语义上等价于"主线程独占" |
| **`run()` 非 `@MainActor` 却用 `assumeIsolated`** | ✅ 与既有约定一致：`run()` 内已有 **10+ 处** `MainActor.assumeIsolated`（`:884/902/917/937/977/986/996/1347/1360/1372`），我新增的那处（timer 装配段）与 `:937/986` 同一区域、同一线程前提 |
