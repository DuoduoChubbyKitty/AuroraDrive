# 性能 · 变化检测/分块复用方案评估 — 2026-10-11

> **任务 task-89（P6）**：评估用户提出的「分块变化检测 / 无变化不刷新」方案
> **用户原话**：
> > "把画面分成一个个微小的框框，框框有变化了内容立马变，没变化就不变"
> > "检测像素是否有变化，无变化就不截屏，只用旧像素，但每两三秒刷新一次"
> **方法**：读 SDK 头文件（官方语义）+ 实测成本 + 风险量化
> **约束**：只读研究 + 只写报告，**未改任何源码**

---

## 0. 一句话结论

**想法方向正确，但系统已免费提供了更好的实现——用户想要的"没变就不重算"由 `SCFrameStatusIdle` 原生支持。**

| 判断项 | 结论 |
|---|---|
| 能不能做 | ✅ **能做，但不需要自己实现分块比对**——`.idle` 是系统免费的"画面没变"信号 |
| 能省什么 | ⚠️ **省不到想省的地方**：分块比对发生在**收到帧之后**，省的是编码/写盘（CPU），**省不了抓屏（GPU）** |
| 按字面实现的代价 | ❌ **反而更慢**：全帧比对实测 **6.81ms**，占 45Hz 预算（22.2ms）的 **30.7%** |
| "2-3 秒刷新"风险 | 🔴 **高危**：横向 1.0 m/s 时 2-3 秒偏移 **2-3 米**（车道宽仅 3.5 米）→ 必压线 |
| 是否违反用户铁律 | ❌ "2-3 秒不刷新" **等价于降帧率**，违反"不降帧率"铁律 |

## 1. ★ 关键突破：`SCFrameStatusIdle` 就是用户想要的信号

### 官方头文件原文（`SCStream.h:35-52`）
```objc
/*!
 @typedef SCFrameStatus
 @abstract SCFrameStatus denotes the status of frame sample buffer.
 @constant SCFrameStatusComplete new frame was generated.
 @constant SCFrameStatusIdle new frame was not generated because the display did not change.
 @constant SCFrameStatusBlank new frame was not generated because the display has gone blank.
 @constant SCFrameStatusSuspended new frame was not generated because updates haves been suspended
 @constant SCFrameStatusStarted new frame that is indicated as the first frame sent after the stream has started.
 @constant SCFrameStatusStopped the stream was stopped.
*/
typedef NS_ENUM(NSInteger, SCFrameStatus) {
    SCFrameStatusComplete, SCFrameStatusIdle, SCFrameStatusBlank,
    SCFrameStatusSuspended, SCFrameStatusStarted, SCFrameStatusStopped
} API_AVAILABLE(macos(12.3), macCatalyst(18.2));
```

**`SCFrameStatusIdle` 官方语义**：「**new frame was not generated because the display did not change**」
—— 翻译：**因为画面没有变化，所以没有生成新帧**。

**这正是用户要的「检测到没变化就不重算」，而且由系统在 GPU 层面免费完成**（比任何 CPU 分块比对都早、都准、都便宜）。

### 怎么拿到这个信号
`SCStream.h:390-395`：
```objc
typedef NSString * SCStreamFrameInfo NS_TYPED_ENUM;
/*!
 @key SCStreamFrameInfoStatus
 @abstract The key for the CFDictionary attached to the CMSampleBuffer that denotes the frames SCFrameStatus
 */
extern SCStreamFrameInfo const SCStreamFrameInfoStatus API_AVAILABLE(macos(12.3), ...);
```
→ 从 `CMSampleBuffer` 的 attachments 里取 `SCStreamFrameInfoStatus` 即可。

### 项目现状：**没读这个信号**（改进空间）
实测 grep：
```bash
$ grep -rn "SCFrameStatus\|SCStreamFrameInfo" Sources/ --include=*.swift
（无命中）
```
`CaptureEngine.swift:895` 的 `didOutputSampleBuffer` 回调里**只检查了 `sampleBuffer.isValid`**（:903），
**完全没读 `SCStreamFrameInfoStatus`** → 系统免费给的变化信号被丢弃了。

**这意味着**：用户想省的那部分（画面没变时的重复工作），**接入成本极低**（读一个 attachment 键），
且**不需要自己写分块比对**。

## 2. 分块比对的实际收益（实测数据）

### 2.1 实测成本（1280×832 帧，与 45Hz 抓屏配置一致）
```bash
$ ./.venv-yolo26/bin/python3 -c "numpy 模拟比对成本"
帧尺寸: 1280×832 = 1,064,960 像素, 4.06 MB
  全帧逐像素比对:      6.812 ms/帧
  分块(64×64)比对:     0.496 ms/帧  (260 块)
  降采样(1/8)比对:     0.161 ms/帧
参照：45Hz 预算 = 22.2ms/帧
  → 全帧比对占预算 30.7%
```

**关键**：用户说"检测**像素**是否有变化"——按字面实现（逐像素）要 **6.8ms**，
**占掉 45Hz 预算的 30.7%**，为了省一点 CPU 先花掉三成预算，**净收益为负**。
即使用分块（0.5ms）或降采样（0.16ms），也只是"不算太亏"。

### 2.2 省的是哪一环？（这是方案的致命问题）
```
SCStream（GPU 抓屏）──推流──→ didOutputSampleBuffer（CPU 回调）
                                      │
                                      ├─ copyNativeFrame（CPU 内存拷贝）
                                      ├─ copyUpscaleFrame（CPU 内存拷贝）
                                      ├─ vImage 缩放（CPU）
                                      └─ 录制编码/写盘（CPU）
```
**分块比对只能放在"收到帧之后"**（箭头右边）——此时：
- ❌ **抓屏（GPU）已经发生了**：`SCStream` 是推流模式，帧已经采完并送达
- ✅ 能省的只有：后续的**内存拷贝 / 缩放 / 编码 / 写盘**（CPU 侧）

**所以用户"无变化就不截屏"的期望达不到**——GPU 抓屏该做还是做了。
真正能省 GPU 抓屏的只有 `.idle`（系统层面根本不生成新帧）。

### 2.3 有没有"按需拉帧"的 API？
**有**：`SCScreenshotManager`（`SCScreenshotManager.h:137`）：
```objc
@abstract captureSampleBufferWithFilter:configuration:completionHandler:
@discussion this method takes a screenshot using the filter and configuration passed in
            and returns it as a CMSampleBuffer
```
这是**真正的按需拉帧**（调用一次抓一张），不是推流。
**但它不适合本项目**：
- 每帧一次异步调用 → 45Hz 下调用开销 + 延迟不确定
- 推流模式的优势（稳定 45fps、与 `CVPixelBufferPool` 复用）会丢失
- 与"不降帧率"铁律冲突（按需拉帧的时序由调用方决定，易抖动）

## 3. 「2-3 秒刷新一次」的风险量化

### 3.1 纵向（前进距离）
```
车速 60 km/h = 16.67 m/s
  1 秒 → 前进 16.7 米
  2 秒 → 前进 33.3 米
  3 秒 → 前进 50.0 米
```
2-3 秒内车辆前进 **33-50 米**——这期间画面**不可能真的没变**（场景已完全不同），
所以"2-3 秒不刷新"在高速下**本身就是错误假设**。

### 3.2 横向（偏移风险，更致命）
```
横向速度 0.1 m/s × 2s = 0.20 米  （压线需 35.0 秒）
横向速度 0.3 m/s × 2s = 0.60 米  （压线需 11.7 秒）
横向速度 0.5 m/s × 2s = 1.00 米  （压线需  7.0 秒）
横向速度 1.0 m/s × 2s = 2.00 米  （压线需  3.5 秒）★
横向速度 1.0 m/s × 3s = 3.00 米  （车道宽仅 3.5 米）
```
**标准车道宽 3.5 米**。横向速度 1.0 m/s（轻微跑偏）时：
- 2 秒偏 2.0 米 → **已过半条车道**
- 3 秒偏 3.0 米 → **接近压线**

### 3.3 结论：这违反用户自己的铁律
用户明确要求「**不降帧率**」。而"2-3 秒才刷新一次"= 有效帧率降到 **0.33-0.5 Hz**，
**等价于降帧率**（且降得极狠）→ 直接违反铁律。

**更危险的是**：直道匀速时画面变化确实小，但**车道偏移正是"小变化"**——
恰恰是变化检测最容易漏掉、而自动驾驶最不能漏的信息。

## 4. 其他"不采集就知道变了没"的办法（评估）

| 方法 | 可行性 | 说明 |
|---|---|---|
| **`SCFrameStatusIdle`** | ✅ **最佳** | 系统免费提供，GPU 层面判断，无额外成本（§1） |
| `CGWindowListCopyWindowInfo` 窗口元数据 | ⚠️ 有限 | 只能看窗口尺寸/位置/owner，**游戏内画面变化检测不到**（窗口没动但车在跑） |
| 游戏自身渲染帧率探测 | ❌ 不可行 | macOS 无公开 API 读取其他进程的渲染帧率 |
| `SCScreenshotManager` 按需拉帧 | ⚠️ 不推荐 | 可行但丢失推流稳定性（§2.3） |

## 5. 明确结论

### ✅ 能做，且应该做——但不是用户说的做法

**推荐方案（最小改动、最大收益）**：
在 `CaptureEngine.swift:895` 的 `didOutputSampleBuffer` 里**读 `SCStreamFrameInfoStatus`**：
```swift
// 伪码（不是实际改动，仅示意）
if let attachments = CMSampleBufferGetSampleAttachmentsArray(sampleBuffer, ...),
   let status = attachments[SCStreamFrameInfoStatus] as? Int,
   status == SCFrameStatus.idle.rawValue {
    // 画面没变 → 复用上一帧，跳过拷贝/缩放/编码（省 CPU）
    return   // 或复用缓存帧
}
```
**收益**：画面静止时（菜单/暂停/加载）跳过整条 CPU 处理链，**零额外成本**（系统已算好）。

**⚠️ 但要注意触发条件（实测推断）**：`.idle` 只在**画面真的完全不变**时触发。
游戏运行中帧在持续生成——实测帧到达日志：
```
$ grep "帧到达" /tmp/engine_ctrl.log
[cap-deep] 📥 帧到达 #1   status=valid
[cap-deep] 📥 帧到达 #60  status=valid
[cap-deep] 📥 帧到达 #120 status=valid
[cap-deep] 📥 帧到达 #180 status=valid
[cap-deep] 📥 帧到达 #240 status=valid
[cap-deep] 📥 帧到达 #300 status=valid
```
帧号连续递增（每 60 帧打点一次，30fps 下约 2 秒），说明**抓屏在持续产出新帧**。
→ 结论：**这个优化只在菜单/暂停/加载画面有效**，对游戏主循环（真实驾驶场景）帮助有限。
（严格说：`.idle` 帧是否仍会到达回调需实测确认——SCK 文档说"未生成新帧"，
 可能连回调都不触发；无论哪种，**游戏运行时都不省**。）

### ❌ 不能做（会伤害正确性）

| 方案 | 为什么不能做 |
|---|---|
| 自实现逐像素比对 | 6.81ms/帧，占 45Hz 预算 30.7%，**净收益为负** |
| "2-3 秒刷新一次" | 横向 1 m/s 时偏 2-3 米（车道 3.5 米）→ 必压线；且**等价降帧率，违反用户铁律** |
| 按需拉帧替代推流 | 丢失 45fps 稳定性，时序抖动 |

### 核心洞察（给用户的一句话）
> 您想要的"没变就不重算"，**系统已经在 GPU 层面免费做了**（`SCFrameStatusIdle`）——
> 但它只在**画面真的完全静止**时触发（菜单/暂停），游戏跑起来就不触发。
> 自己再做一层分块比对，**省的是 CPU 而抓屏 GPU 已经花了**，且逐像素比对反而吃掉三成帧预算。
> 而"2-3 秒刷新"在 60km/h 下会偏出车道，**正是"会开出车道线"的翻版**。
