## 1. ★ 查证 1：`SCStream.updateConfiguration` 的真实性

**任务要求**：「`SCStream.updateConfiguration(_:)` 真的存在吗？签名是什么？（**查官方头文件 `SCStream.h`**）」

### 证据（官方头文件原文）

文件：`$(xcrun --show-sdk-path)/System/Library/Frameworks/ScreenCaptureKit.framework/Headers/SCStream.h`
（本次：`/Volumes/项目依赖/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/.../SCStream.h`，34,011 bytes）

**第 494-500 行原文**：
```objc
/*!
 @abstract updateConfiguration:completionHandler:
 @param streamConfig the requested content filter to be updated
 @param completionHandler the handler to be called when the function completes
 @discussion this method will update the stream configuration for a content stream. 
             A completion handler will be called when the update is complete with an 
             error denoting if the update has failed.
*/
- (void)updateConfiguration:(SCStreamConfiguration *)streamConfig 
          completionHandler:(nullable void (^)(NSError *_Nullable error))completionHandler 
    NS_SWIFT_ASYNC_NAME(updateConfiguration(_:)) 
    NS_SWIFT_NAME(updateConfiguration(_:completionHandler:));
```

### 结论

| 项 | 结论 |
|---|---|
| 方法是否存在 | ✅ **存在**（头文件 500 行，非 deprecated） |
| Swift 调用名 | `updateConfiguration(_:)`（async，由 `NS_SWIFT_ASYNC_NAME` 指定）<br>或显式 `updateConfiguration(_:completionHandler:)` |
| 入参 | `SCStreamConfiguration`（含 `width`/`height`/`minimumFrameInterval` 等，见 `SCStream.h:212/217/222`） |
| 错误 | completion handler 带 `NSError`（**W3 可据此判断切换失败**） |

**→ W3「用 updateConfiguration 动态切抓屏配置」在 API 层面可行。**
⚠️ **待 W3 落地后审查**：① 是否正确处理 `NSError`（失败时状态是否回滚）
② 是否在**正确的队列**上调用（SCStream 有线程/队列要求）

## 2. ★ 查证 2：`DispatchSourceTimer.schedule` 重复调用能改频率吗

**任务要求**：「`DispatchSourceTimer.schedule` 重复调用真的能改频率吗？（**查 Apple 文档/头文件确认**）」

**方法说明**：Apple 在线文档为 JS 渲染（`web_fetch` 只拿到壳），SDK 里 libdispatch 头文件本次未定位到。
故改用**本地实测**——对这类 API 语义问题，可运行实验比文档更硬。

### 实验代码（`/tmp/timer_test.swift`）

```swift
let timer = DispatchSource.makeTimerSource(queue: q)
timer.setEventHandler {
    counter += 1
    if counter == 4 {
        timer.suspend()
        timer.schedule(deadline: .now(), repeating: 0.05, leeway: .nanoseconds(0))  // 20Hz
        timer.resume()
    }
    ...
}
timer.schedule(deadline: .now(), repeating: 0.2, leeway: .nanoseconds(0))  // 5Hz
timer.resume()
```

### 实测输出（原始）

```
总触发次数: 12
间隔(ms):  205, 199, 196, 0, 55, 48, 50, 46, 54, 46, 54
早期2间隔合计: 404ms（期望≈400ms）
改后2间隔合计: 100ms（期望≈100ms）
✅ 结论：suspend → schedule → resume **确实能改频率**
```

### 结论

| 项 | 结论 |
|---|---|
| 重复 `schedule` 能改频率吗 | ✅ **能**，但**必须先 `suspend()`，改完再 `resume()`** |
| 直接对 running timer 调 `schedule` 会怎样 | ⚠️ **未实测**（本次只测了 suspend 路径）。W2 若直接改，需补测 |
| 副作用 | ⚠️ **发现一个 0ms 间隔**（输出里第 4 个间隔 = 0）→ `schedule(deadline: .now())` 会**立即多触发一次**。W2 若在切档时这样做，会有**一次额外 tick**——需评估是否有害（如双帧/重复注入） |

**→ W2「setTickHz 用 schedule 改频率」在 API 层面可行，但有三个待审点**：
1. 是否正确用 suspend/resume 包裹（否则可能崩溃或行为未定义）
2. 是否在 timer 的**所属队列**上调用（`DispatchSourceTimer` 的 suspend/resume 不是线程安全的，必须同队列）
3. 那个 **0ms 额外 tick** 是否被处理（可能造成切档瞬间双触发）
