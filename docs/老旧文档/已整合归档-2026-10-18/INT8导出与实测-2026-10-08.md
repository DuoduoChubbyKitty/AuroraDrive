## 1 · 为什么是 palette 而不是 linear int8（都有实测）

本报告对 **5 种方案**做了同权、同输入的全量对比（真权重 `checkpoints/m9_v2/best_model.pt`）：

| 方案 | 体积 | 最差偏差 | no_dets 偏差 | lane 细线 w1 | 分布内翻转 |
|---|---|---|---|---|---|
| fp16（基线） | 5.796 MB | 2.83e-03 | 2.83e-03 | 8.33e-05 | 0 |
| **palette kmeans gs=1** | **2.963 MB** | **5.59e-03** | **5.59e-03** | **8.33e-05** | **0** |
| palette kmeans gs=2/8/32 | 2.963 MB | 4.7–5.6e-03 | 4.7–5.6e-03 | 8.33e-05 | 0 |
| palette uniform gs=1 | 2.963 MB | 8.10e-02 ❌ | 8.10e-02 | 5.29e-03 | 0 |
| linear int8 | 2.963 MB | 1.04e-01 ❌ | 1.04e-01 | 1.55e-03 | 0（分布内）/ 5% 分布外 |

**关键判据（三种方案的真差距，不在汇总表的"最差偏差"里，而在细结构）**：

合成车道线扫描（1 / 2 / 3 / 6 像素宽）下：
```
palette kmeans:  w1=8.33e-05  w2=8.33e-05  w3=2.44e-03  w6=1.80e-03
fp16     (基线):  w1=8.33e-05  w2=8.33e-05  w3=4.88e-04  w6=6.40e-04
uniform:          w1=5.29e-03  w2=5.29e-03  w3=3.22e-02  w6=2.52e-02   ← 细线差 63× 于 palette
linear:           w1=1.55e-03  w2=1.55e-03  w3=1.17e-02  w6=8.45e-03   ← 细线差 19× 于 palette
```
**1~2 像素细线上，palette 与 fp16 输出逐位同值（8.33e-05）**；而 uniform / linear 在细线上塌陷 19–63 倍。这正是项目内 `tools/yolopx/export_yolopx_coreml.py:60-63` 记录的「INT8 全量化把车道线正像素打掉 10×」的**同一失效模式**——**uniform/linear 会毁车道线，palette（kmeans）+ 关键头保 fp16 不会**。

> ⚠️ 重要区分（用户经验已验证）：那条「打掉 10×」的记录指的是 **`export_yolopx_coreml.py:59` 的 INT8 全量化**（linear/uniform，权重+激活都量化）。**本项目实际在产线跑的是 `models/ayolom/ayolom_n_int8.mlmodelc`（3.8MB），配方 = palette kmeans + det 头保 fp16**，两者不是一回事。本报告实测支持这一区分。

## 2 · 「参照系」方法论（本次最重要的方法学结论）

**只看绝对 maxdiff 会得出错误结论。** 例：`no_dets`（空检测框）工况。

- t1-train 报告「真权重 INT8 下 no_dets 用例 steer 偏 0.0943，是 normal 的 59×」—— 这个数字本身对，但**结论方向错了**。
- 独立复现的真相（同权、同输入）：
```
PyTorch 自身 normal → no_dets 的 steer 跨度 = 1.16397   ← 模型本身特性（无检测框时会大幅变化）
  fp16       量化误差 0.00283 = 模型自身跨度的  0.24%
  palette    量化误差 0.00559 = 模型自身跨度的  0.48%   ← 推荐
  linear8    量化误差 0.10449 = 模型自身跨度的  8.98%   ← t1 撞到的就是方案劣化
```
**`no_dets` 工况下模型自己就会跳 1.16**，量化误差只是它的 ~0.5%。**正确参照系是「量化误差 ÷ 模型在该工况下的输出跨度」，不是绝对差值。** linear int8 之所以差，是因为它在这一跨度上引入了 8.98% 的额外失真。

## 3 · 符号翻转：分布内 0，分布外才有（决定选型的关键补充）

t1 报告 palette 在 120 组随机扫描上有 **1.7% 符号翻转**（fp16 0%）。本报告补齐口径：

| 输入口径 | palette gs=1 翻转率 | 最差偏差 |
|---|---|---|
| **分布内：40 帧真实截图帧**（训练同源） | **0 / 40 = 0.00%** | 5.13e-03 |
| 真实帧 image/lane + 随机 dets | **0 / 120 = 0.00%** | 4.15e-02 |
| 真实帧 + 全零 dets（真实无检测场景） | **0 / 20 = 0.00%** | 4.90e-03 |
| 分布外：纯随机 image（torch.rand 图） | 1~6 / 120 = 0.8%~5.0% | 4.55e-01 |

**根因已定位：翻转由「随机的图像本身」驱动，不是 lane/dets。**
- 分布外翻转样本里，`fp16 始终与 PyTorch 一致`（差 0.004~0.012），只有 palette 偏 0.13~0.46 —— 是量化对训练分布外随机图失配。
- 定位实验：真实帧 + 随机 dets → 0 翻转；纯随机图 + 全零其余 → 仍有翻转。**随机图（torch.rand）的像素统计与真实截图完全不同**，真实帧 steer 稳在 [0.069, 0.104]（跨度 0.0345），随机图跨度 0.11 且横跨 0 点附近。

**结论：真实部署喂的一定是真实截图（分布内），分布内 0 翻转。** t1 的 1.7% 出自分布外伪输入，不是部署风险。

> **关于与 t1 的"口径差异"（客观记录，非对错之分）**：双方数字都没错，错的是"用什么输入测量化"。t1 的 120 组扫描用的是随机初始化分布，本报告的 40 真实帧 + 120 真实图混合是部署分布。**量化偏差必须用部署分布来测**——这是本文的方法学结论，也请 t1 以真实帧口径复核（Lead 已安排交叉验证）。

## 4 · 体积与性能（工程实测）

### 体积（.mlpackage 落盘后 `du` 实测）

| 产物 | 总大小 | 权重净重 | 判据 |
|---|---|---|---|
| `models/m9_v2_int8.mlpackage` | **2.963 MB** | 2.917 MB | ✅ ≤10MB |
| `models/m9_v2_int8.mlmodelc`（xcrun 编译） | **3.0 M** | — | ✅ |
| fp16 基线 `m9v2_fp16_gs32.mlpackage` | 5.796 MB | 5.752 MB | 对照 |

参数量口径：**部署态（reparameterize 后）3,014,659（3.01M）**；训练态多分支 3,301,987（3.30M）。INT8 理论下限 = 3.01M / 1MB ≈ 2.88 MB，实测 2.963 MB（含元数据 + 保 fp16 的 lane/fusion 头），合理。

### 真机耗时（coremltools 本机跑，5 轮 × 100 次取中位，两次独立复测）

| 方案 | CPU+ANE 中位 | ALL 中位 | CPU_ONLY 中位 | 冷启动（首次） |
|---|---|---|---|---|
| fp16 | 0.795–0.893 ms | 0.825–1.497 ms | 4.036–6.001 ms | 2.0–9.4 ms |
| **palette gs=1** | **0.759–0.880 ms** | **0.762–0.993 ms** | 4.131–6.979 ms | 1.9–2.0 ms |
| palette gs=32 | 0.933–1.018 ms | 0.815–0.992 ms | 4.057–5.306 ms | 2.0–3.2 ms |
| linear int8 | 0.914–1.016 ms | 0.797–1.036 ms | 5.580–8.127 ms | 1.9–2.6 ms |

**INT8 不比 FP16 慢**（CPU+ANE 下 palette 甚至略快）。30Hz（33ms 预算）余量 **37–43×**。`computeUnits=.all` 与项目既有结论一致（是 Swift 侧运行时配置，导出脚本不写死）。

> 注：这是**结构性能**（与 M2 用随机权重测 1.17ms 同一性质）——真实模型性能取决于推理负载，但量化前后**相对**结论（INT8 不更慢）是稳定的。

## 5 · 两个隐蔽的实现坑（修掉后才有上面的数字）

### 坑 A · 「保 lane/fusion 头」会静默失效（前缀匹配永远匹配不到 lane）

`fusion_head_*` 权重在 MIL 里保留语义名（`fusion_head_fc1_weight_to_fp16`）→ 前缀匹配 ✅。
**但 lane 分支的权重名是 `const_2 / const_4 / const_6`（无语义）** → 前缀匹配永远命中 0 个，**"保 lane 头"变成静默失效的空操作**（模型照样全量化，细线照样可能塌，还自以为保护了）。

修法：**从 lane 输入出发做数据流追踪**（lane_to_fp16 → max_pool → conv(const_2) → relu → conv(const_4) → … → reduce_mean → lane_feat），实测命中 10 个算子。这才是真「保 lane」。

### 坑 B · M2 脚本的自删 bug（`tools/export_m9_v2_coreml.py:518`）

旧代码 `--out` 传 `.mlpackage` 结尾时，`mlpackage == mlmodelc` 同路径 → **先 save 后 rmtree 自删**，仍打印「✓ 转换完成/源模型已保存」→ 假报成功（实测 exit=6、盘上无文件）。
已修（同为 T2-INT8 任务交付）：路径去重 + 落盘存在性断言 + 先验证再打印。实测 `--out xxx.mlpackage` 现在正常产出 5.8M + 额外编译出 .mlmodelc。

## 6 · group_size 对 M9-v2 无影响（与 yolopx 结论不同，如实记录）

`tools/yolopx/exp_quant_palette.py:18-24` 实测 yolopx「gs=32 会静默跳过 ~70% 张量」。**M9-v2 上不成立**：

| group_size | 体积 |
|---|---|
| 1 / 2 / 8 / 32 | **全部 2.963 MB**（逐字节同体积） |

原因：M9-v2 的卷积/线性层通道数都能被 32 整除（架构不同），故 gs=32 不会触发"跳过不整除张量"。**结论：M9-v2 上 gs 无关紧要，选 gs=1 仅因为它是 per-channel 等价物、语义最干净，不套用 yolopx 结论。**

## 7 · 数据前提（必须读，否则误读上面的偏差数字）

> 权重 `checkpoints/m9_v2/best_model.pt` 由 t1-train 产出（2026-10-08）：
> **3 epoch / 129 帧桌面截图 / steer-throttle-brake 全 0 标注 / lane_supervised_frac=0.0（车道分支从未被监督）**。

**含义**：权重数值真实（非随机），但**语义无意义**——车道分支没被监督过，模型没学到"跟车道线"。
- ✅ **量化偏差数字有意义**（量化是结构性的，与权重语义无关）
- ❌ **模型效果结论不可解读**（"这个模型能不能开"不在本报告范围）

模型无检测框时 steer 会大幅变化（§2 的 1.16 跨度）就是**训练数据全 0 标注**的自然结果，不是缺陷、也不是量化问题。

## 9 · 落地策略：palette 首选 + fp16 兜底开关

选型不是"二选一"，而是**双档并存 + 运行时一键回退**：

| 档位 | 产物 | 触发条件 |
|---|---|---|
| **首选** | `models/m9_v2_int8.mlpackage`（2.963 MB） | 默认（用户要的 INT8） |
| **兜底** | fp16 版（5.796 MB，同脚本 `--scheme fp16`） | 若某真实工况出现量化异常（如针对性翻转），一键切回 |

兜底开关在 Swift 侧 `InferenceEngineV2` 的模型路径选择处实现（本次任务范围外，已把产物与结论交给 W6/Swift 侧）。加这个开关的**理由**：palette 在分布内 0 翻转、但分布外伪输入仍有 0.8~5%，兜底档给"万一遇极端输入"留了逃生门，成本只是多一个 5.8MB 文件。
