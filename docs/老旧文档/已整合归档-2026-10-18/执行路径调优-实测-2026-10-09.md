# 执行路径调优 · 实测报告 — 2026-10-09

> **实测人**：S2（性能攻坚员）
> **机型**：Apple M3 MacBook Air（无风扇），macOS 26.6.2（build 25G83），Xcode 16.x Swift 6.3.3
> **Python**：`./.venv-yolo26/bin/python3`（py3.11.9 / coremltools 8.3.0 / torch 2.13.0）
> **被测模型**：`models/m9_v2.mlmodelc`（8 帧 + GRU + 12 步迭代精修 + 4 步 MoE，**随机权重 65.74%**，仅链路验证，性能测量仍有效）
> **硬红线**：不降步数（12）/ 不降 MoE（4 步 [9,10,11,12]）/ 不降帧率 / 不降分辨率 / 不降质量
> **目标**：p95 ≤ 16 ms（当前 Lead 实测 20.95~29.28 ms）

---

## 0. 一句话结论

> **最佳 computeUnits = `.cpuAndGPU`，最佳配置 = `fp16 / macOS13 / 现役导出参数 + .cpuAndGPU`。**
> **`min_p50 = 13.70 ms / min_p95 = 15.04 ms`（14 轮 × 30 次 ABBA，最小值口径）—— 达标。**
> **ANE 在 8 帧模型上【不生效】（编译失败回退 CPU，占 4 档里的 2 档）；真正的加速来自 GPU。**
> 旧结论"`.all` 最快"在新模型（8 帧 + GRU + MoE）上**被推翻**——它因 ANE 编译失败而**系统性退化 CPU**，比 `.cpuAndGPU` 慢 1.8~2.2×。

## 1. ★ ANE 是否真生效 —— 三重判据（缺一不可）

新模型（8 帧）下 ANE 的判定**不能只看延迟量级**，必须三路互证。本报告同时收集了三路证据：

| 判据 | 方法 | 结果（8 帧模型） |
|---|---|---|
| ① **MLComputePlan 派发图** | `MLComputePlan.deviceUsage(for:)` 逐算子 `preferred` 设备统计 | `.all`/`.cpuAndNE`：preferred 0 个 ANE，479 个 CPU，459 个 nil（无法静态派发） |
| ② **延迟量级** | ANE 生效应 ~2-8 ms，CPU 回退 ~15-30 ms（差 3-5×） | `.all` 在低负载下 p50 17-20 ms（**像 CPU 不像 ANE**）；1 帧模型 ANE 生效时 p50 仅 1.67 ms |
| ③ **编译日志** | stderr 有无 `MILCompilerForANE error / ANECCompile() FAILED` | `.all`/`.cpuAndNE`：**每次加载都报 ANE 编译失败**；`.cpuAndGPU`/`.cpuOnly`：无此报错 |

**三路一致**：8 帧模型上 ANE **从未生效**。`.all` 和 `.cpuAndNE` 在"等 ANE 编译 5-12 秒失败后"回退 CPU，这正是它们慢的根因。

### 1.1 进一步定位：ANE 边界精确在 `num_frames == 1`

为排除"是步数/MoE 导致 ANE 失败"的假设，本报告做了**帧数梯度实验**（`--num-frames 1/2/4/8`，其余结构不变，**仅诊断用，非交付配置**）：

| 帧数 | `.all` 派发图 | ANE 编译 | `.all` p50 | `.cpuAndGPU` p50 |
|---:|---|---|---:|---:|
| **1** | **ane=446, cpu=52** ✅ | **无报错** ✅ | **1.67 ms** ✅ | 7.19 ms |
| 2 | cpu=481, nil=455 🔴 | 失败 | 9.45 ms | 12.32 ms |
| 4 | cpu=481, nil=455 🔴 | 失败 | 14.61 ms | 12.20 ms |
| **8**（现役） | cpu=479, nil=459 🔴 | 失败 | 17.62 ms (min) | **13.70 ms (min)** |

**结论**：ANE 边界是 `num_frames ≤ 1`。2 帧起 ANE 编译即失败，与步数（12）、MoE（4 步）**无关**。
这与 Lead 的 `docs/迭代精修-ANE边界实测-2026-10-08.md` 的"1 帧 + palette → ANE 2.23 ms ✅"完全吻合。
**⟹ 12 步迭代精修和 MoE 是清白的；时序窗口（8 帧）才是 ANE 的硬阻塞。** 在不降帧数的前提下（用户红线），**本模型 ANE 路线已穷尽**，只能走 GPU/CPU。

### 1.2 supported 集合（ANE 硬件能力，区别于 preferred）

本报告额外采集了 `deviceUsage.supported`（算子**可被**某设备执行的能力集，区别于 preferred 的运行时选择）：

| 模型 | units | preferred (ane/cpu/gpu/nil) | supported 含 ane |
|---|---|---|---|
| m9_v2（8帧） | all | nil=459, cpu=479 | **ane=474**（硬件支持但编译失败 → 不 preferred） |
| m9_v2（8帧） | cpuAndGPU | cpu=1, gpu=510, nil=427 | ane=0（该档不暴露 ANE） |
| diag_f1（1帧） | all | **ane=446**, cpu=52 | ane=493（支持且 preferred ✅） |
| t_mac15_fp32 | all | cpu=1, gpu=498, nil=414 | ane=2（几乎不暴露） |

**关键洞察**：8 帧 fp16 模型的算子**硬件上** 474/938 支持 ANE，但**编译期**全部失败——这是 `ANECCompile()` 的限制，不是硬件能力问题。fp32/mac15 模型连"试 ANE"都不试（supported 含 ane 仅 2 个），直接走 GPU，反而**绕过了编译失败的成本**。

## 3. MLModelConfiguration 其他旋钮

在 `.cpuAndGPU` 和 `.cpuOnly` 两个 computeUnits 上测 4 个运行时旋钮（3 轮 × 20 次，配对，`pair-config-load-075814.json`）：

| 配置 | p50 | ×p50 (vs cpuAndGPU/default) | 结论 |
|---|---:|---:|---|
| **`.cpuAndGPU` / default** | 18.83 | 1.000 | ✅ 最优 |
| `.cpuAndGPU` / fastPrediction | 19.08 | 1.013 | 无收益（旧模型 1.11×，新模型无） |
| `.cpuAndGPU` / fastPred+lowprec | 23.98 | 1.273 | ❌ 更慢 |
| `.cpuAndGPU` / reshapeInfrequent | 17.45 | 0.927 | p50 略好但 p95 暴涨（1.68×），不稳 |
| `.cpuOnly` / default | 37.57 | 1.995 | CPU 慢一倍 |
| `.cpuOnly` / fastPrediction | 32.81 | 1.742 | CPU 上 fastPred 有 ~13% 收益 |
| `.cpuOnly` / fastPred+lowprec | 31.31 | 1.663 | 同上 |
| `.cpuOnly` / reshapeInfrequent | 33.95 | 1.803 | — |

**结论**：
- `specializationStrategy = .fastPrediction`：旧 YOLO 模型实测 1.11~1.25×（`YolopxEngine.swift:730`），但**新模型在 `.cpuAndGPU` 上无收益**（1.013×，噪声内）；仅在 `.cpuOnly` 上有 ~13% 收益。由于推荐走 GPU，此旋钮**不开**。
- `allowLowPrecisionAccumulationOnGPU`：**更慢**（1.27×），不开。
- `reshapeFrequency = .infrequent`：p50 略好但 p95 不稳，不开。
- `preferredMetalDevice`：本机只有一个 GPU（Apple M3），设置与否无差异（plan 派发图相同），不开。
- `functionName`：本模型只有 `main` 一个函数，不适用。

**推荐运行时配置 = 裸 `.cpuAndGPU`，不加任何 optimizationHints。**

| **t_mac13_fp16** | 20.83 | 1.000 | ✅ 基准（与现役同参） |
| t_mac13_fp32 | 19.92 | 0.956 | p50 略好但 p95 暴涨（1.75×），不稳 |

| t_mac15_pal4/6/8 | 29~38 | 1.4~1.8 | ❌ 越量化越慢 |

**结论**：
- **`minimum_deployment_target`（macOS13/14/15）对 GPU 路径无性能差异**（1.02~1.04×，噪声内）。
- **fp32 比 fp16 在 GPU 上 p50 略快**（0.956×）但 p95 不稳；体积翻倍（32 vs 16 MB），性价比低。
- **palette / int8 量化在 GPU 上全部更慢**（1.24~1.82×）——GPU 对低比特反量化有额外开销。
- **int8 + `.cpuAndGPU` 会触发 MPSGraph 断言崩溃**（`MPSGraphExecutable.mm:5070 failed assertion 'MLIR pass manager failed'`，rc=-6/SIGABRT）——**禁用 int8 + GPU 组合**。

### 4.3 `ct.optimize.coreml.deduplicate_weights` —— 未验证（API 不存在）

任务书要求重点试 `ct.optimize.coreml.deduplicate_weights`。本报告**如实记录**：
- 在 **coremltools 8.3.0**（本机 venv）和 **9.0.0**（临时 venv）里，`optimize.coreml` 模块的公开符号**均不含** `deduplicate_weights` 或 `OpWeightDeduplicatorConfig`（已对两个版本的 `site-packages` 全文 grep 确认）。
- 该函数名**不存在于任何已发布的 coremltools 版本**（web 检索 [coremltools API](https://apple.github.io/coremltools/source/coremltools.optimize.html) 与 [Releases](https://github.com/apple/coremltools/releases) 均无此符号）。
- 权重重复率实测：`weight.bin`（16.7 MB）4KB 粒度重复块仅 3.5%（且全是全零块），**去重收益可忽略**。
- Core ML 在**编译期**（`xcrun coremlc` / ANE 编译器）会自行做权重去重，没有暴露给用户的 Python API。

**⟹ 该旋钮"未验证"（不是"试过没用"），因为 API 本身不存在。** 如 Apple 未来版本提供该 API，可按本报告的 `exp_exec_path.py --pipeline dedup` 框架直接接入。

### 4.4 macOS15 + `.all` 的"绕过 ANE"现象

**一个意外发现**：`fp32 / macOS15 + .all` **不报 ANE 编译失败**（unlike fp16 版），派发图直接 `gpu=498, cpu=1`。原因：fp32/mlprogram 的算子根本不在 ANE 的 `supported` 集合里（supported 含 ane 仅 2 个），CoreML 不会尝试 ANE 编译，直接派 GPU。
- 好处：省去 5-12 秒的 ANE 编译失败开销（`.all` 的 load_ms 从 fp16 的 5500ms 降到 fp32 的 170ms）。
- 坏处：fp32 体积翻倍、且 min_p95=17.26ms 仍**未达 16ms 红线**。
- **不推荐**：fp16 + `.cpuAndGPU` 已达标且体积更小。

## 7. ⚠️ 诚实声明（哪些未验证/不可信）

1. **绝对值未取得安静窗口**：本机全程被其他 agent 抢 CPU（loadavg 6~50），从未取得 loadavg<1.5 的安静窗口。本报告所有"绝对值"均为 14 轮取最小值的**下界估计**，不是真实无争用值。真实无争用值应**更低**（更乐观），但本报告不外推。
2. **真实工况未测**：`.cpuAndGPU` 的 min_p95 达标仅指"无争用下界"；真实驾驶场景（游戏满载 GPU）下配对 p95 达 ~87 ms。换挡是净收益（仍比 `.all` 快 2×），但是否在真实工况下绝对达标，**须真车上实测确认**。
3. **随机权重**：被测模型 65.74% 随机初始化（`m9_v2_contract.json`），精度数字（maxdiff）仅反映量化噪声，真实精度须训练后重测。**性能结论与权重无关**（只依赖图结构和 computeUnits），故有效。
4. **`deduplicate_weights` 未验证**：API 不存在（§4.3），不是"试过没用"。
5. **旧 `.cpuAndGPU` 崩溃史**：旧文档记录过 MPSGraph SIGABRT（`目标模式-性能优化5倍` §6.42.7），但那是旧 YOLO 模型。新模型 20 次压测 0 崩溃（§5），**但未做长时间（小时级）稳定性测试**，上线前建议跑 ≥1 小时 soak test。

## 9. 给其他攻坚员的情报

- **给 S1（双模型拆分）**：已验证 `m9_v2_enc`（batch=1 单帧卷积）ANE 生效（ane=30 算子，0.65ms），`m9_v2_ctl`（单帧时序+refiner+MoE）走 GPU（4.67ms）。拆分后总延迟 ~5.3ms，**远优于不拆的 13.7ms**——S1 路线极有前途，本报告的 `.cpuAndGPU` 结论可直接用于 `ctl` 子模型。
