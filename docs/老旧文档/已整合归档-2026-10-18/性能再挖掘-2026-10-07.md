## 方向一：预处理复用

### 1.1 yolopx vs yolo26s 是否各自做一遍？

**现状证据（结论：目标形式不同，不可合并；且已错开帧）：**

- **yolo26s 慢路径** `YoloEngine.draw`（`Sources/AuroraDrive/Inference/YoloEngine.swift:716`）是「整帧**非等比拉伸**到 640×640」（`ctx.draw(in: 全幅)`，注释 L21 明写「不做 letterbox，与训练端一致」）。
- **yolopx** `YolopxEngine.drawLetterbox`（`Sources/AuroraDrive/Inference/YolopxEngine.swift:1531`）是「等比缩放 + 114 灰边 letterbox」，训练端要求逐位对齐（L20-21）。
- 两者**目标像素形式不同**（拉伸 vs letterbox），输出**不能共用一个预处理缓冲**——合并会破坏其一与训练端对齐，属降质量，A 档红线。

**再叠一层：生产主路径根本不走慢路径 draw。** yolo26s 的主力是 `inferFast` 直通（`AuroraDriveApp.swift:6642` + `CaptureEngine.swift:369` 的 `vImageScale_ARGB8888` 源头统一缩放），慢路径 `YoloEngine.infer`（走 `draw`）只在 `fastPathActive==false` 或直通超时 >1s 时兜底（`AuroraDriveApp.swift:6808-6811`）。

**再加一层：P1 检测网降频已把两网错开帧。** `AuroraDriveApp.swift:6582-6586`：`detectGateA`（yolopx）= 偶数帧、`detectGateB`（yolo26s）= 奇数帧。同帧**不会同时**做 yolopx letterbox + yolo26s 拉伸。lead 担心的「同一帧预处理重复做」在错开后已不存在。

**结论：无可改 A 档点。**

### 1.2 附加发现：M9 与 assist 同帧重复 180×320 预处理（记录，不改）

`AuroraDriveApp.swift:6783-6785`：同一 tick 同一 `cg` 分别喂给两个 `InferenceEngine` 实例——

```swift
inferenceEngine.infer(image: cg, ...)   // m9_mono
assistEngine.infer(image: cg, ...)      // game_assist_control
```

两者都走 `InferenceEngine.preprocessImage`（`InferenceEngine.swift:445`）：各自对同一 `cg` 做一次 `CGContext.draw` 缩放到 180×320 + RGBA→CHW 双循环 + `vDSP_vsdiv` 归一化，并各自 `[UInt8](repeating:0, count: 180*320*4)` 新建 230KB 中间缓冲（L451，每帧 ×2 引擎）。

**为什么不动：**
- 收益微小：180×320 是低分辨率，双循环仅 5.76 万像素/引擎，中间 Array 分配在 autoreleasepool 内。
- 侵入大：两个 `MLModel` 各自独立实例、各自 `reusableImageBuffer`，共享 image 预处理需跨引擎重构 provider 构造与缓冲生命周期，风险 > 收益。
- 与 lead 点名范围（yolopx vs yolo26s）不符，属新发现但达不到「明确可改 + 收益达标」。

## 方向二：内存池复用

**现状证据（结论：已全部到位）：**

| 原生帧 / YOLO / UI / 插帧缓冲区 | 四个 `CVPixelBufferPool`，惰性创建、尺寸不变时复用、停捕获时置 nil | `CaptureEngine.swift:122-141, 459-640` |

**结论：无每帧 new 的 CVPixelBuffer/MLMultiArray 残留，池化已彻底，无可优化点。**

## 方向三：后处理管线（det 解码 / argmax 之外的数据搬运）

**现状证据（结论：已向量化/整块拷贝，很彻底）：**

- **yolo26s**：`YoloEngine.parse`（`YoloEngine.swift:750`）输出仅 [1,300,6]，300 行下标读，量小无优化动力。
- **yolopx det 解码**：`parseDetections`（`YolopxEngine.swift:1125`）已用 `fastRowsStrided`（L1433）按真实 strides 整块拷出 8400×6，避免 8400×5 次 `readML` 下标读（注释明确这是历史性能坑、已修）。
- **掩码提取**：`extractMask`（`YolopxEngine.swift:1264`）已按 dtype 显式分派 `Float16/Float32` 直接指针（L1291-1304）+ 4×4 多数表决下采样；`smoothMask`（L1364）已向量化写。
- **NMS/**：`iouXYXY` 标 `@inline(__always)`（L1245）。

**结论：后处理数据搬运已无低效下标读 / 逐元素除法残留，无可优化点。**

## 方向四：地图查询去重

**现状证据（结论：无同帧重复）：**

- `isOnRoad` 生产路径**仅一处**（`AuroraDriveApp.swift:7506`，在 `segmentDecisionForRule` 内），每 tick 一次；实现是 `worldToGrid` + 1 格容差（最多 3×3=9 cells 位图读），微秒级（`RoadMapPrior.swift:210-222`）。
- `cornerAhead` / `junctionAhead` / `chooseExit` 在同一 tick 内由 `DriveSegmentController.update` 的 `switch segment` **分段互斥**（`DriveSegmentController.swift:141-150`），不会出现「同一帧对同一坐标重复查同一 API」。
- `cornerAhead` 本身已从「全量线性扫描 31.4ms」优化为「3×3 索引格 + 方向/前方锥过滤」亚毫秒（`RoadCornerGuide.swift:355-392`），且进弯前/过弯阶段逻辑与 `steerForCorner` 分离，无冗余重查。

**结论：无去重空间，无可优化点。**
