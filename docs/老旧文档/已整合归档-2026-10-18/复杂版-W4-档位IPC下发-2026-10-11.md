## 1. ⚠️ 一个必须澄清的发现：Lead 给的类型说法有误

任务描述写「value 必须是 `"ayolom"`/`"legacy"`（与 `PerceptionModelFamily` 的 rawValue 一致）」——**后半句不成立**。实测源码：

| 类型 | 定义位置 | rawValue 实测 |
|---|---|---|
| `PerceptionMode`（**`perceptionMode` 属性的实际类型**） | `YolopxEngine.swift:203` | `.ayolom = "A 模型"` / `.legacy = "26S + 光流 + YOLOPX"` |
| `PerceptionModelFamily` | `YolopxEngine.swift:173` | `.yolopx` / `.ayolom`（**没有 `"legacy"`**） |

**两个类型的 rawValue 都不是 `"ayolom"`/`"legacy"`**：
- `PerceptionMode.rawValue` 是**中文显示名**（用于 UI 卡片标题）
- `PerceptionModelFamily.rawValue` 是 `"yolopx"`/`"ayolom"`

**因此我没有直接用任何 rawValue**，而是按协议约定**显式映射**：
```swift
perceptionMode == .ayolom ? "ayolom" : "legacy"
```
这样：
- ✅ 满足 Lead 的硬约束（key=`perceptionMode`，value=`"ayolom"`/`"legacy"`）
- ✅ **不改动任何枚举定义**（`PerceptionMode`/`PerceptionModelFamily` 都可能有其他用途，改 rawValue 会波及 UI 显示与日志）
- ✅ W2 按协议字符串取值即可，无需知道 Swift 类型细节

**请 Lead 转告 W2**：引擎侧直接比较字符串 `"ayolom"` / `"legacy"`，**不要**尝试映射回 `PerceptionModelFamily.rawValue`（那是 `"yolopx"`）。

**为什么改 `selectPerceptionMode` 而不给 `perceptionMode` 加 `didSet`**：
1. `perceptionMode` 是 `var`（`:5400`），当前**无 didSet**；加 didSet 会在**初始化赋默认值**时也可能干扰（虽 `didSet` 不在 init 中触发，但语义上"属性被写入"≠"用户切档"）
2. `selectPerceptionMode` 是**注释明确标注的「UI 选择器唯一入口」**（`:5402`），语义精确
3. 与现有代码风格一致（同文件其他配置项均用显式推送函数，如 `setUpscaleEnabled`）

## 3. 协议兼容性论证（老引擎收到未知字段会不会崩）

**结论：不会崩，完全向后兼容。**

**引擎侧解析方式**（`EngineMain.swift` `case "config":`，逐行实测）：
```swift
let cSport = obj["sport"] as? Bool
let cCtrlDisabled = obj["controlDisabled"] as? Bool
...
let cDigest = obj["digest"] as? Bool
// 每个字段都是「可选取值 + if let 才赋值」
if let v = cSport { st.sportMode = v }
if let v = cDigest { st.digestMode = v; ... }
```

**论证**：
1. `obj["perceptionMode"]` 在**老引擎里根本不会被读取**（代码里没这一行）→ 未知 key 被 JSON 反序列化后的字典**直接忽略**，零影响
2. 即使 W2 加了读取，写法也是 `as? String` 可选取值 → 类型不符/字段缺失都安全
3. **反向兼容**：新 UI + 老引擎 = 字段被忽略，其他 8 个字段照常生效 ✅
4. **老 UI + 新引擎**：引擎读不到 `perceptionMode` → `nil` → 保持默认档位，不崩 ✅

**关键**：这个通道是**增量字段**设计（`[String: Any]` 字典 + 逐字段可选解析），天生向后兼容。项目里 `digest` 字段就是同样的先例（后来加的，老引擎照样跑）。

## 4. UI 侧 tick 频率（任务第 4 项：只报告，不改）

**观察到的事实**：
- 本次改动**只下发档位**，未改任何 tick 频率
- 任务描述提到"UI 侧 tick 是固定 30（W1 在改）"
- 引擎按档位切频率是 **W2/W3 的活**（`case "config"` 里读 `perceptionMode`）

**若 UI 侧也要跟着档位变频率，方案建议（供 Lead 决策，我未实施）**：

| 档位 | 建议 tick | 理由 |
|---|---|---|
| `ayolom` | **45Hz** | A-YOLOM 在 ANE p50 10.4ms → 95.9Hz，45Hz 只占 47% 预算（`YolopxEngine.swift:196`） |
| `legacy` | **30Hz** | 旧三件套含光流外推，YOLOPX 单帧 183ms 跑不到高频（`:238` 注释） |

**但有两个前置问题需要 W1/H 线确认**：
1. UI 侧 tick 与引擎 tick 是**两个独立循环**，UI 侧频率只影响画面显示/交互，**不影响引擎推理频率**
2. 若 UI 侧真要变频率，`Timer.schedule` 的 `repeating` 需重建（现有 timer 是固定值）
3. **风险**：UI 侧频率变化会影响 `dt` 计算 → 需同步检查 `dt` 的取值处（H2 在改）

**结论**：档位 → 频率的映射**应由引擎侧（W2/W3）实现**，UI 侧保持固定频率更安全（UI 只是显示层）。若 Lead 要求 UI 也变速，建议单独派任务。
