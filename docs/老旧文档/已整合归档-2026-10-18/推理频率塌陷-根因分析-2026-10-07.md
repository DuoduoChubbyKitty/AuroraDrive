## 0. 摘要（TL;DR）

**根因：不是降频、不是丢帧、不是队列阻塞，而是 yolopx 单次推理的绝对耗时在游戏负载下从空载的 ~68ms 涨到 128ms（p50）/ 306ms（p95）/ 最高 961ms，而推理链路是「串行队列 + 防重叠门 + 完成后下一 tick 才排下一次」—— 出结果频率被锁死在 `1 / (单次耗时 + 半拍量化 ≈16.7ms)`，实测拟合中位误差仅 10.6%。2.6~3.0 Hz 就是这个倒数，不是任何降频或丢帧机制的产物。**

三条独立证据互相咬合：

| # | 证据 | 位置 |
|---|---|---|
| E1 | **算术闭环**：观测到单次推理 295–360ms → 倒数 = 2.78–3.39 Hz，与塌陷值 2.4–3.0 Hz 重合 | `性能实测...md:4513` |
| E2 | **真机现场**：游戏内日志逐段可算出 **2.40–2.60 Hz** 的真实区间；`耗时=378.2ms` → 1/0.3782 = **2.64 Hz** | `data/perf-2026-10-02/engine-game-partial.log:13772-13804` |
| E3 | **捕获与 tick 全程健康**：塌陷窗口内 `tickGap` p50=33ms（30Hz 正常）、`capGap` p50=51ms，**主循环没塌** | 同日志，见 §3.2 |

**⟹ 塌陷发生在「单帧推理耗时」这一层，不在其上游（捕获）或下游（tick/队列）。**

**排除的假设**（均有反证）：
- ❌ 捕获降帧（H-Capture）：`capGap` 游戏内 p50=35ms，未塌陷 → §3.2
- ❌ 队列串行阻塞 / `isInferencing` 白扔：无效提交成本已降到 ~0.04ms，且实测提交 241 次 / 完成 120 次的比例与「1/68.9ms 上限」一致 → §3.3
- ❌ App Nap：`nice=-20` + activity token 全程持有，日志无被压制记录 → §3.5
- ⚠️ 热降频：**部分成立但非主因**（详见 §3.4 —— 内存压力 Heavy + swap 5.9GB 是更可疑的放大因子）

## 2. 核心机制：`完成即排下一次` + `防重叠门`

### 2.1 代码事实

yolopx 的推理入口有一道**防重叠门**，保证同一时刻只有一帧在推理队列里：

```
Sources/AuroraDrive/Inference/YolopxEngine.swift:894
guard !isInferencing else { return }   // 防重叠：上一帧还没跑完就跳过
...
Sources/AuroraDrive/Inference/YolopxEngine.swift:952
isInferencing = true
```

队列是**串行**的：

```
Sources/AuroraDrive/Inference/YolopxEngine.swift:442-445
private let inferenceQueue: DispatchQueue = {
    let env = ProcessInfo.processInfo.environment["AURORA_INFER_QOS"]
    let qos: DispatchQoS = (env == "interactive") ? .userInteractive : .userInitiated
    return DispatchQueue(label: "com.aurora.yolopx", qos: qos)
}()
```

### 2.2 由此推出的频率上限（纯逻辑，无需实测）

tick 以 30Hz 调用提交。设单次推理耗时 `T`：

- 若 `T < 33.3ms`：每 tick 都能提交并完成 → 出结果频率 = **30 Hz**（受 tick 限）
- 若 `T > 33.3ms`：推理期间所有提交被 `isInferencing` 门丢弃，只有**推理完成后的下一个 tick** 才能提交新帧 → 出结果频率 = **1 / (T + 量化延迟)**

**量化延迟的来源**：推理在某个 tick 的提交上启动；它完成时**不在 tick 边界上**，必须等下一个 30Hz tick 才会发起新提交。因此下一次启动平均等半拍（**16.7ms**），最坏等满拍（33.3ms）。

⟹ **精化模型：`频率 ≈ 1 / (T + 16.7ms)`**

**这是本次分析的第一个决定性推理**：一旦 `T > 33.3ms`，出结果频率就与 tick 频率**解耦**，由 `T` 主导。

**用真机数据验证三个候选模型**（§3.1 的 1143 组配对）：

| 模型 | 中位相对误差 | 误差<25% 占比 |
|---|---|---|
| `Hz = 1/T` | 18.9% | 72.3% |
| **`Hz = 1/(T + 16.7ms)`（半拍量化，预期）** | **10.6%** | **87.3%** |
| `Hz = 1/(T + 33.3ms)`（满拍量化，最坏） | 9.2% | 84.1% |

**⟹ 精化模型把中位误差从 18.9% 降到 10.6%，误差<25% 的窗口从 72.3% 升到 87.3%。**
**⟹ 这不仅确认了 `频率 = 1/耗时` 的定性关系，还确认了「量化延迟」这一具体机制的存在（否则 `1/T` 就该是最优拟合，而不是明显更差）。**

### 2.3 项目自己已经测到过这个现象

```
Sources/AuroraDrive/Inference/YolopxEngine.swift:451-453
/// 【为什么需要】基线实测：yolopx **提交 241 次 / 完成 120 次** ——
///   一半提交被 isInferencing 门白扔。单次 68.9ms > tick 预算 33.3ms，
///   "每 tick 触发"只是让它在两次结果之间**空转争抢 CPU**。
```

**验算**：241 次提交对应约 8 秒（241/30）；120 次完成 / 8s = **15 Hz**；而 1/68.9ms = **14.5 Hz**。**完全吻合** —— 这从项目自己的数据反向证实了 `频率 = 1/T` 定律。

### 2.4 曾经的错误修法与教训（重要，勿重蹈）

同文件记录了一次**导致 61% 掉频**的失败优化：

```
Sources/AuroraDrive/Inference/YolopxEngine.swift:456-461
/// 【⚠️ 为什么默认 0 = 关闭 —— 实测教训】
///   曾默认设 90ms，ABBA 实测 yolopx **12.75 Hz → 5.02 Hz（掉 61%）**，
///   **违反 R1 红线**。根因：节拍是基于"上次完成时刻"的**固定间隔**，
///   而空载推理比游戏里快得多 —— 固定间隔反而成了**额外瓶颈**，
///   把"能跑多快"硬压到"间隔多大"。
```

**⟹ 这条教训同时证明了两件事**：
1. 频率确实由「单次耗时 + 排程语义」共同决定（改排程立刻改频率）；
2. **任何基于固定间隔的节拍器都是错的修法** —— 只会让负载下更慢。

**`total` = 2.20ms**（tick 预算 33.3ms），`yoloFast` 仅 0.19ms（即提交开销）。

**⟹ tick 主线程侧毫无压力。队列无堆积（因为 `isInferencing` 门根本不让堆积 —— 它直接丢，而不是排队）。**

**⚠️ 语义澄清**：这里的「丢帧」不是 bug，是**设计**。队列深度实际为 1（串行 + 门），所以「提交 241 / 完成 120」的 50% 丢弃率是 `1/T` 语义的必然结果，不是缺陷。

**证据 B —— GPU 功率与 P 核频率在游戏段确实不同**：

空载硬件基线（`00-idle-baseline-raw.txt`）：

**⚠️ 但无法断定这是热降频还是正常 DVFS**：本次采集数据中**未包含 `thermal` 字段的时序**，无法区分「热墙」与「功耗墙/正常调频」。→ **列入待验证**，见 §4 步骤 4。

**⚠️ 关键反证 —— 热降频不能解释全部现象**：
塌陷段 `耗时=378.2ms` 而 20 分钟后（16:42 段）同一进程在**同样游戏内**恢复到 `耗时=53.5–68.5ms`、频率 12.8–14.8 Hz：

**⟹ 如果是纯热降频，恢复需要分钟级降温；而这里是「负载一变（游戏静置/暂停）耗时立刻回到 53ms」。**
**⟹ 结合 §3.1 的 62.8% CPU 算子事实，「CPU 争抢」是比「热降频」更自洽的解释。**

## 5. 结论

### 5.1 根因判定

| 假设 | 判定 | 置信度 | 关键证据 |
|---|---|---|---|
| **单次推理耗时暴涨（`1/T` 锁频）** | ✅ **成立·主因** | **高** | `engine-game-partial.log:13772-13804` 逐行算术吻合；`性能实测...md:4513` |
| CPU 算子争抢（62.8% 算子在 CPU） | ✅ 成立·机制 | 中高 | `YolopxEngine.swift:710-716`；恢复速度与负载同步（§3.4） |
| 内存压力 Heavy + swap 5.9GB | ⚠️ 疑似放大因子 | 中 | `01-game-partial-164351.txt`；项目自己也列为待查（`:4653`） |
| 热降频 | ⚠️ 部分成立，非主因 | 低（未验证） | 缺 thermal 时序；且恢复速度反驳纯热降频（§3.4） |
| ANE 带宽争抢 | ⚠️ 未验证 | — | 本次无 ANE 带宽数据 |
| 捕获降帧 | ❌ 证伪 | 高 | `capGap` p50=35ms（§3.2） |
| 队列堆积 / 白扔提交 | ❌ 证伪 | 高 | 无效提交 0.04ms；`total`=2.2ms（§3.3） |
| App Nap | ❌ 证伪 | 高 | `/tmp/aurora_defender.log`；`nice=-20`（§3.5） |
| `nice=-20` 未生效（原 H3） | ❌ 证伪 | 高 | 同上（§3.6） |

### 5.2 一句话根因

> **yolopx 单次推理耗时在游戏负载下从 ~68ms 涨到 150–400ms，而推理链路是「串行队列 + 防重叠门 + 完成即排下一次」，出结果频率被严格锁定为 `1/单次耗时`。2.6~3.0 Hz 就是这个倒数，不是任何降频或丢帧机制的产物。**
>
> **修法方向（本报告不实施）**：不是调节拍器（已实测掉 61%，`YolopxEngine.swift:456-461`），而是**降低单次耗时**或**改并行语义**。前者受限于 62.8% 的 CPU 算子（CoreML 内部调度，已证伪所有 computeUnits 替代方案）；后者意味着放弃端到端单模型的时序一致性 —— **属于设计决策，需用户拍板**。
