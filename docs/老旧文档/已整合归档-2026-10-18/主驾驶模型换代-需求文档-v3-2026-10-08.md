## 0. 一句话目标（用户原话校准后）

> **车道线只是兜底。核心是让模型「开得快、开得对、开得好」——最快最好的车手，不是跟在车道中间的乖宝宝。**

---

## 1. 核心诉求（按优先级）

### 1.1 开得快（第一优先）

- **走线优化（racing line）**：入弯外切 → 弯心 → 出弯外切，走最宽弧度，不是贴车道中心
- **前瞻 / 未来多步预测**：看前面弯道提前松油、提前打方向，不是到弯口才刹车
- → 车道中心保持**不是**目标（那是最慢的走法），**切最佳线路才是**

### 1.2 开得对（第二优先）

- **极限控制三档**：油门、强力刹车（Shift）、手刹（空格），在正确时机分档使用
- **漂移 / 反打救车**：推过头了会反打、会松油

### 1.3 开得好（第二优先，并列）

- **救车能力**：判断"我操作要失控了"→ 反打/松油/重刹
- **主动接管**：模型自己判断"我没法处理好"→ 明确让用户接管（不是硬着头皮开）

### 1.4 车道线 = 兜底（降级定位）

- 不是主驾驶依据，是**主策略失效 / 看不清时**的兜底安全网
- 与前代 `LaneFallback` 语义一致：`fail-open`，平时不主导

## 2. 训练数据要什么（用户新问题的答案）

### 2.1 检测框能不能输入？训练数据里有没有？

| 问题 | 答案 |
|---|---|
| 模型能输入检测框吗？ | ✅ **能**。`model_v2.py` 已有 `dets[20,12]` 分支 |
| 现在训练数据里有检测框标注吗？ | ❌ **没有**。录制只存 `t_sec,frame,steer,throttle,brake` 五列 |

**结论**：检测框**能输入**，但**录制时必须补存**。有两条路：
- **A（推荐）**：录制时**实时落盘检测框**（用 yolopx det 头当天跑，边录边存）
- **B（备选）**：先录图像，事后**离线补算**检测框（`backfill_detections`，169ms/帧，10万帧≈4.7h）

### 2.2 训练数据的完整字段清单

| 字段 | 必存? | 说明 |
|---|---|---|
| 图像帧 | ✅ | 第三视角（追尾） |
| steer / throttle / brake | ✅ | **必须非零**（旧数据全 0 = 废） |
| **检测框** | ✅ | 新模型核心输入，录制时补存 |
| **车道线掩码** | ✅ | 兜底用，录制时补存或离线补算 |
| **速度 / 加速度** | ✅ | 新模型状态输入 |
| **第 N 帧时序** | ✅ | 加时序后要存连续帧 |

### 2.3 数据采集要求

- **视角**：第三视角（追尾），不是 FPV（旧数据全 FPV，作废）
- **弯道占比**：≥ 40%（治"只会直走"）
- **无辅助线场景**：× 掺 ≥10%（防模型学游戏辅助线而非真实路况）
- **量级**：阶梯实验测，10/30/60/120min 四档（详见 `docs/数据量与可学习性实验-2026-10-08.md`）

## 3. 架构改造需求（一次改到位，不返工）

> 背景：GAP 架构 bug（分不清左右）已由 w7 在修；时序和加大要一起做。

### 3.1 时序能力（用户明确要求）★ 必做

- **吃前 N 帧**（建议 4~8 帧），不是只看当前一帧
- 结构：LSTM / GRU / 时序卷积（3D Conv / Causal Conv），待选型实测
- 为什么：单帧模型帧间会抖、决策缺上下文；时序让决策连贯 + 能预测

### 3.2 骨干加大（用户问"变大有没有帮助"）

**结论：变大有用，但不能只硬堆骨干。**

| 做法 | 帮助 | 说明 |
|---|---|---|
| 纯加胖 RepVGG（2.76M→8M） | ⚠️ 有限 | 单帧看一张图，瓶颈是缺时序不是缺容量 |
| **加时序 + 适度加大骨干** | ✅✅ 巨大 | 时序特征需要容量消化；两者配合才有效 |
| 加深度（不是宽度） | ✅ 有帮助 | 感受野更大，看更远 |

**预算**：INT8 ≤10MB 硬约束。当前 3.01M 参数（2.96MB），加时序 + 加到 RepVGG-A0（8M）+ 新头，总量预算约 8~9M → INT8 8~9MB，**仍 ≤10MB**。

### 3.3 新能力（按提升巨大排序）

| # | 能力 | 提升 | 说明 |
|---|---|---|---|
| 1 | **未来多步预测**（MPC 式前瞻） | 🥇 巨大 | 预测未来 0.5s/1s 偏离/碰撞，转弯跟车救车都靠它 |
| 2 | **时序融合** | 🥇 巨大 | 吃前 N 帧，决策连贯不抖 |
| 3 | **风险分 + 主动接管** | 🥈 大 | 模型判断"我不行"→ 松手让用户接管（现有的 confidence 字段是空的） |
| 4 | **TTC 碰撞时间** | 🥈 大 | 检测框 + 自车速度 → 物理先验，重刹救车 |
| 5 | **速度条件化** | 🥉 中 | 同样画面 30→120km/h 给不同油门（验证模型对速度敏感） |
| 6 | **驾驶意图条件化** | 🥉 中 | 直行/左转/右转/靠边/掉头，任务切换不乱 |

### 3.4 明确不要的（别碰）

| 项 | 原因 |
|---|---|
| ✗ attention 注意力机制 | M6 实测否决：yolopx PSA 静态 3.9% 却烧 72% 墙钟，33ms 预算里是确定风险 |
| ✗ 车道中心保持头 | 用户明确：车道线只是兜底，"开得快"要走最佳线不是贴中心 |

## 8. 追加：冷启动分布要求（w5 发现，2026-10-08）

### 问题：零填充不是中性的

GRU 有 bias，**零输入仍会推进隐状态**（Lead 实测：全零输入输出范数 = 11.31，非零）。

**含义**：推理启动头几帧（环形缓冲未填满）等于注入"若干步内容为零的历史"，与训练稳态分布不一致。

**实测**：全 8 帧 vs 后 5 帧有效，输出差 **0.445**。

### 两条要求（写进训练与推理）

| # | 要求 | 归属 |
|---|---|---|
| ① | **有效帧 < 2 时退回单帧模式**（避免纯噪声注入） | w3（Swift 侧门控） |
| ② | **训练时有效帧数分布要覆盖推理冷启动分布** ← **更重要** | 训练侧（数据/训练脚本） |

**② 的具体做法**（本小姐建议）：
- 训练时对每条样本**随机截断历史长度**（如 1~8 帧随机），并在前方零填充
- 这样模型见过"1 帧有效 / 3 帧有效 / 8 帧有效"各种情况，不会因冷启动分布偏移而失稳
- 参考 w5 实测占比（**随机权重下，非结论**）：1 帧 16.9% / 3 帧 42.5% / 8 帧 34.5%

### 合同契约 JSON（w5 裁决）

**采纳"常量表 + W8 离线交叉校验"，不做启动时读 JSON**：
- 理由（w5）：引入运行时文件依赖 = 多一个启动失败点；离线 diff 就能拿满跨语言对齐的价值，零运行时风险
