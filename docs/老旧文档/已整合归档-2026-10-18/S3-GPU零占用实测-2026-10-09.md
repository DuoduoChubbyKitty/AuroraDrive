# S3 · GPU 零占用实测报告 — 2026-10-09

> 实测人：S3（性能攻坚员）
> 目的：验证 Lead 导出的 `models/multi_split/` 9 模型串联方案**推理全程零 GPU 占用**，
>       并用 Swift `MLComputePlan` 给出算子级派发证据 + 真机延迟数据。
> 工具：`tools/gpu_usage_check.swift`（本报告新增，合一脚本）
> 纪律：**延迟全部用 Swift 测**（coremltools Python 对 <1ms 模型完全失真）；
>       **GPU 判定必须用 MLComputePlan**（Swift 侧算子级 preferred/supported 证据）。

---

## 0. 最终结论（一句话）

> **✅ 铁律满足：9 个模型全链路 GPU preferred 算子数 = 0，零 GPU 占用。**
> **串联 p50 = 1.98ms，p95 = 2.30ms，max = 2.40ms**（n=320，8轮×40次）。
> 等效 434.8 Hz，30Hz 预算余量 **14.35×**。
> 最优 computeUnits 分配：enc=`.cpuAndNeuralEngine`，其余 8 个全 `.cpuOnly`。
> **反直觉关键**：chunk5/chunk6（MoE）走 `cpuOnly` 比 `all`/`cpuAndNE` **快 5.1×**。

## 2. GPU 零占用证据（MLComputePlan 算子级派发）

`MLComputePlan.load(...).deviceUsage(for:)` 逐算子统计 `preferred` / `supported`。
判定口径：**只要没有任何算子 preferred=gpu，即 GPU 未被任何算子选中**。

### 2.1 全链路派发汇总（串联实测配置：enc=cpuAndNE，其余=cpuOnly）

| 模型 | 总算子 | preferred 分布 | supported 集合 | cost% ane/cpu/gpu | GPU 算子 |
|---|---:|---|---|---:|---:|
| enc | 126 | ane=30, nil=96 | cpu=30, ane=30 | 100 / 0 / 0 | **0** ✅ |
| tf | 327 | cpu=192, nil=135 | cpu=192 | 0 / 100 / 0 | **0** ✅ |
| chunk1 | 89 | cpu=69, nil=20 | cpu=69 | 0 / 100 / 0 | **0** ✅ |
| chunk2 | 89 | cpu=69, nil=20 | cpu=69 | 0 / 100 / 0 | **0** ✅ |
| chunk3 | 89 | cpu=69, nil=20 | cpu=69 | 0 / 100 / 0 | **0** ✅ |
| chunk4 | 89 | cpu=69, nil=20 | cpu=69 | 0 / 100 / 0 | **0** ✅ |
| chunk5 | 347 | cpu=225, nil=122 | cpu=225 | 0 / 100 / 0 | **0** ✅ |
| chunk6 | 347 | cpu=225, nil=122 | cpu=225 | 0 / 100 / 0 | **0** ✅ |
| head | 130 | cpu=69, nil=61 | cpu=69 | 0 / 100 / 0 | **0** ✅ |
| **合计** | **1613** | — | — | — | **0** ✅ |

> **说明**：`nil` = 无 preferred 设备的算子（常量折叠 / 形状变换 / 无计算语义的辅助节点），
> 不参与设备竞争，也绝不会落到 GPU。
> **enc 特殊**：126 算子中 30 个计算算子 preferred=ane，且 ANE cost 占比 100%——
> 即 enc 的全部计算都被 ANE 承接，无 CPU 回退。

### 2.2 结论

- **9 模型、1613 个算子，preferred=gpu 的数量为 0。** 铁律满足。
- supported 集合中也**没有 gpu**——不仅没被选中，连"可被 GPU 执行"的候选都没有。
  这是比"preferred 非 gpu"更强的证据。
- enc 是唯一上 ANE 的模型（符合设计），其余 8 个全部 CPU。

## 3. 逐模型 3 档 computeUnits 延迟对比

命令：`swift tools/gpu_usage_check.swift --per-model --rounds 8 --iters 40`
（每档预热 5 次，正式采样 80 次取分位；单位 ms，格式 `p50/p95`）

| 模型 | `.all` | `.cpuOnly` | `.cpuAndNE` | 最优 | MoE |
|---|---:|---:|---:|---|---|
| **enc** | **0.33 / 0.38** | 1.37 / 1.60 | **0.33 / 0.38** | all=cpuAndNE | — |
| tf | 0.12 / 0.14 | 0.15 / 0.16 | 0.13 / 0.16 | all | — |
| chunk1 | 0.05 / 0.07 | 0.05 / 0.05 | 0.05 / 0.05 | ≈持平 | — |
| chunk2 | 0.06 / 0.06 | 0.05 / 0.06 | 0.05 / 0.07 | ≈持平 | — |
| chunk3 | 0.05 / 0.06 | 0.05 / 0.06 | 0.05 / 0.06 | ≈持平 | — |
| chunk4 | 0.05 / 0.06 | 0.05 / 0.05 | 0.06 / 0.06 | ≈持平 | — |
| **chunk5** | 0.71 / 0.81 | **0.14 / 0.16** | 0.74 / 0.81 | **cpuOnly** | ✓ |
| **chunk6** | 0.77 / 0.82 | **0.14 / 0.15** | 0.77 / 1.02 | **cpuOnly** | ✓ |
| head | 0.07 / 0.08 | 0.09 / 0.09 | 0.08 / 0.10 | ≈持平 | — |

### 关键解读

1. **enc**：`.all` 与 `.cpuAndNE` 完全相同（0.33ms），说明 `.all` 下 CoreML 自动把 enc
   派给 ANE；而 `.cpuOnly` 强压到 CPU 后 **慢 4.2×**（1.37ms）。→ enc 必须给 ANE。
2. **chunk5/6（MoE）**：`.cpuOnly` 0.14ms，而 `.all`/`.cpuAndNE` 高达 0.71–0.77ms，
   **cpuOnly 快 5.1×**。原因：这两个模型的 MLComputePlan preferred 虽为 CPU，
   但 `.all`/`.cpuAndNE` 会触发 CoreML 尝试 ANE 分区编译 / 额外调度开销，
   而纯 linear+MoE 的小图在 CPU 上直接跑最划算。
3. **chunk1–4 / head**：三档基本持平（0.05–0.09ms），说明这批小 linear 图
   设备切换开销可忽略；但从"零 GPU"铁律与最小绝对延迟出发，仍统一选 `.cpuOnly`。

> **注**：`--per-model` 的 `.all` 档同时输出 MLComputePlan：chunk5/6 的 GPU preferred 算子 = 0，
> 即"`.all` 慢"并非因为用了 GPU，而是 ANE 分区编译尝试的开销。**GPU 全程未被选中。**

## 4. chunk5 / chunk6（MoE）专项

### 4.1 节点数口径澄清

- Lead 口径（Torch `jit.inlined_graph` 节点数）：chunk5/6 ≈ **828 节点**（含 MoE 分支展开）。
- 本报告口径（CoreML 转换后 MLComputePlan 算子数）：chunk5/6 = **347 算子**
  （计算算子 225 + 辅助/常量 122）。
- 两者不矛盾：828 是导出前的 Torch 图节点，347 是 CoreML 优化/融合后的实际执行算子。
  判定 GPU 必须用后者（CoreML 执行图）。

### 4.2 三档性能（重点）

**chunk5：**
| computeUnits | p50 | p95 | max |
|---|---:|---:|---:|
| `.all` | 0.714 | 0.810 | 0.817 |
| **`.cpuOnly`** | **0.140** | **0.164** | 0.444 |
| `.cpuAndNE` | 0.740 | 0.809 | 0.827 |

**chunk6：**
| computeUnits | p50 | p95 | max |
|---|---:|---:|---:|
| `.all` | 0.765 | 0.823 | 0.863 |
| **`.cpuOnly`** | **0.144** | **0.155** | 0.386 |
| `.cpuAndNE` | 0.775 | 1.018 | 1.052 |

- 两模型 **GPU 派发算子 = 0**（`.all` 档 MLComputePlan 实测）。
- **`cpuOnly` 比 `all`/`cpuAndNE` 快 5.1×**，且 p95 更稳（0.16ms vs 0.82ms）。
- 结论：chunk5/6 **必须显式配置 `.cpuOnly`**，交给 `.all` 会自动尝试 ANE 反而变慢。

## 7. 工具与复现

### 7.1 `tools/gpu_usage_check.swift`（本次新增）

合一脚本，四件事一次做完：编译 mlpackage→mlmodelc、串联跑 N 次、
逐模型 MLComputePlan 派发检查、延迟分位测量。

```bash
# 串联实测（含派发图）
swift tools/gpu_usage_check.swift --pipeline --rounds 8 --iters 40

# 逐模型 3 档 computeUnits 对比
swift tools/gpu_usage_check.swift --per-model --rounds 8 --iters 40

# 两者都跑
swift tools/gpu_usage_check.swift --pipeline --per-model
```

参数：`--rounds`（默认8）、`--iters`（默认40）、`--warmup`（默认5）。

代码复用：MLComputePlan 派发遍历来自 `tools/ane_dispatch_check.swift`；
确定性 LCG 输入构造与计时分位来自 `tools/exp_exec_bench.swift`。

### 7.2 判定方法说明（为什么必须这样测）

- **为什么用 Swift 测延迟**：coremltools Python 的 `predict()` 每次要做
  numpy→MLMultiArray 转换，对 <1ms 的小模型开销主导，数字完全失真。
- **为什么用 MLComputePlan 判 GPU**：延迟数字无法直接证明"没碰 GPU"
  （CPU 慢也可能是调度问题）。`deviceUsage(for:)` 给出的是 CoreML 编译期
  确定的**算子级设备归属**，是"零 GPU"的硬证据。
  本报告同时看 `preferred`（实际选择）和 `supported`（候选集合）。
