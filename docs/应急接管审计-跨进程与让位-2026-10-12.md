## 1. tickGapMs 在引擎进程无条件赋值 ✅

### 证据
`AuroraDriveApp.swift:6845-6849`（`DriveState.tick()` 最开头）：
```swift
func tick() {
    // 诊断：tick 实际间隔（>33ms = 主线程掉拍/被卡；配合 capGap/capWork 定位延迟）
    let tickNow = Date()
    tickGapMs = tickNow.timeIntervalSince(lastTickTime) * 1000
    lastTickTime = tickNow
```

**关键**：这两行在 `tick()` 的**最前面**，**不受任何 `guard isDriving` 或模式分支影响**——
引擎进程 `tickOnce()`（:1131）调 `st.tick()` → 必经此处 → `tickGapMs` 在引擎进程也被赋值。

`tickGapMs` 定义于 `AuroraDriveApp.swift:5480`：
```swift
var tickGapMs: Double = 0
```
是 `DriveState` 的实例属性——两个进程各有一份 `DriveState`（引擎 :988、UI 本地），
各自独立赋值。引擎进程的 `tickGapMs` 反映引擎 tick 实际间隔。

### 给 ET-3 的指引
> 在 `DriveState.tick()` 里（:6848 之后）调 `EmergencyTakeover.shared.noteTickGap(tickGapMs)`。
> 两个进程都会执行这行，但只有引擎进程的 `setTickHz` 生效（UI 进程的 EngineMain 没跑 tick 定时器）。
> **无需 IPC**——这是 Lead 已确认的方案 A。

## 2. releaseAll() 签名 + 让位实现建议

### 证据
`ControlEngine.swift:436-448`：
```swift
func releaseAll() {
    let allMappedKeys: [CGKeyCode] = [
        keyMap.throttle, keyMap.brake,
        keyMap.steerLeft, keyMap.steerRight,
        keyMap.handbrake, keyMap.boost,
    ]
    for keyCode in allMappedKeys {
        postKeyEvent(keyCode: keyCode, keyDown: false)
    }
    heldKeys.removeAll()
    lastFullReleaseAt = CACurrentMediaTime()
}
```
- **签名**：`func releaseAll()` —— 无参数，无返回值
- **行为**：对 6 个映射键各发一次 `keyUp`（`CGEvent.post(tap: .cghidEventTap)`），清 `heldKeys`
- **可达性**：引擎进程 `EngineGlobals.state?.controlEngine` → `st.controlEngine.releaseAll()`
  （:1819 已有调用先例：`st.controlEngine.releaseAll()`）

### AI 注键 vs 用户按键（前提确认）
`ControlEngine.swift:537` `event.post(tap: .cghidEventTap)` —— AI 用 `CGEvent.post` 系统级注入。
用户物理按键走真实键盘 HID → 两者在 macOS 上是**不同的输入路径**，但 `CGEvent.post(keyUp)`
是**全局的**——会对系统全局发 keyUp，**包括用户正在按住的键**。

### 让位实现建议（给 ET-4/ET-5 的指引）

**一次性 releaseAll 不够**——下一帧 tick 会 `applyCommand` 重新按下去。

推荐：**持续抑制 applyCommand + 一次 releaseAll**：
```
让位触发时：
  ① st.controlEngine.releaseAll()         ← 一次性释放所有 AI 注键
  ② 设标志位 st.takeoverActive = true     ← 持续抑制
  ③ tick() 里：if takeoverActive { 跳过 applyCommand }  ← 不再发新 keyDown
  ④ setTickHz(5)                           ← 降频让出 CPU
松手时：
  ⑤ st.takeoverActive = false              ← 解除抑制
  ⑥ setTickHz(回原档)                      ← 提回频率
```

**为什么不用 `releaseAllIfNeeded()`（:486）**：那是节流版，语义是"同秒内已清扫就跳过"，
让位场景需要**立即**释放、且**持续**不注入——节流版的设计目标是性能优化，不是让位语义。

### releaseAll 误伤风险
`releaseAll` 对 6 键发全局 keyUp。如果用户正按着 W（throttle），AI 发 W 的 keyUp 会让系统认为 W 被释放。
**但这正是让位的语义**——AI 不再控制，用户接管。用户松手后重新按即可。
**风险可控**：让位期间 `applyCommand` 被抑制（③），不会重新发 keyDown。

## 3. shm maskFlags 能加 bit 传 takeoverActive ✅

### 证据
**引擎侧设位**（`EngineMain.swift:105` + `:279-286`）：
```
协议布局偏移 104: maskFlags u32
  bit0 = isDegraded     ✅ 已用（:286 if isDegraded { flags |= 1 }）
  bit1 = 掩码有效         ✅ 已用
  bit2 = lane 降级       ✅ 已用
  bit3 = drivable 降级   ✅ 已用
  bit4 = 空闲            ← 可加 takeoverActive
```

**UI 侧读位**（`EngineClient.swift:696-700`）：
```swift
if maskReadable, maskSeq != engineMaskSeq {
    engineMaskSeq = maskSeq
    let flags = base.load(fromByteOffset: 104, as: UInt32.self)
    engineMaskDegraded = (flags & 1) != 0          // bit0 ✅ 被读
    engineLaneDegraded = (flags & 4) != 0           // bit2 ✅ 被读
    engineDrivableDegraded = (flags & 8) != 0       // bit3 ✅ 被读
    let maskValid = (flags & 2) != 0                // bit1 ✅ 被读
```

**UI 侧确实在读 maskFlags**——bit0/1/2/3 全被解析。bit2/bit3 是后加的分层降级标志
（注释说"旧引擎不发这两个位 → 恒为 0 → 安全降级方向"），**有加 bit 的先例**。

### 给 ET-4 的指引（UI 横幅读状态）
```
引擎侧（EngineMain publishMasks）：
  if takeoverActive { flags |= 16 }              // bit4 = takeoverActive

UI 侧（EngineClient.swift:700 附近）：
  engineTakeoverActive = (flags & 16) != 0      // 读 bit4
  // 旧引擎不发 bit4 → 恒为 0 → false（安全降级方向，同 bit2/3 先例）
```
改动范围：`EngineMain.publishMasks`（设位）+ `EngineClient`（读位）+ `EngineFrameShm` 协议注释。
**不需要新 IPC 通道**——shm 已是引擎→UI 的状态回传通道。

### ⚠️ 限制
shm 掩码区只在 `maskSeq` 变化时才重读（:696 `if maskSeq != engineMaskSeq`）。
如果 takeoverActive 状态变了但掩码没变（maskSeq 不变），UI **不会重读 flags** → 横幅延迟。
**建议**：takeover 状态变更时强制 bump 一次 maskSeq，或单独加一个不受 seq 门控的 flags 字段。

## 4. KeyboardMonitor 跨进程：引擎进程收不到物理按键 ❌

### 证据
**KeyboardMonitor 实现**（`KeyboardMonitor.swift:41-57`）：
```swift
func start() {
    keyDownMonitor = NSEvent.addGlobalMonitorForEvents(matching: .keyDown) { ... }
    keyUpMonitor = NSEvent.addGlobalMonitorForEvents(matching: .keyUp) { ... }
}
```
依赖 `NSEvent.addGlobalMonitorForEvents`——这是 **AppKit API**，需要主 run loop 在 spin。

**引擎进程不 spin 主 run loop**（`EngineMain.swift:8` + `:1117`）：
```
//  不创建窗口、不跑 NSApp.run()，在纯后台进程里运行完整驾驶闭环。
...
dispatchMain()   // 永不返回
```
`dispatchMain()` 只跑 dispatch queue 的回调，**不 spin NSRunLoop** →
`NSEvent.addGlobalMonitorForEvents` 的回调**不会被调度**。

**RecordEngine.swift:110-118 已确认这个限制**（w4-tools V4 验证发现）：
```
//   `KeyboardMonitor`（`NSEvent.addGlobalMonitorForEvents`），而引擎进程主循环
//   是 `dispatchMain()`（**不 spin 主 run loop**），且项目**从未申请 Input
//   Monitoring** 权限 → **极可能收不到物理按键**。
```

**KeyboardMonitor 是 DriveState 属性**（:5646），引擎进程构造了 DriveState（:988），
**但从未调用 `keyboardMonitor.start()`**（grep EngineMain.swift 无 `keyboardMonitor` 引用）。

### 4.3 这对让位方案意味着什么

让位需要"用户按键 → AI 停注键"。但**引擎进程收不到用户物理按键**——
如果让位触发依赖引擎进程感知键盘，**现有架构做不到**。

### 可行的替代方案（给 ET-4/ET-5 的指引）

**方案 A（推荐）：UI 进程监听键盘 → socket 通知引擎**
- KeyboardMonitor 在 UI 进程已工作（:5016/6262 `keyboardMonitor.start()`）
- UI 侧检测到用户按键 → `EngineClient.sendCommand("config", extra: ["takeover": true])`
- 引擎侧 `case "config"` 加 `takeover` 字段 → 设 `st.takeoverActive = true` + `releaseAll()` + `setTickHz(5)`
- 松手 → `sendCommand("config", extra: ["takeover": false])` → 引擎解除抑制 + 提回频率
- **优点**：复用现有 socket config 通道（:1571），无需新 IPC
- **缺点**：UI→引擎 socket 有延迟（心跳 5s 间隔，config 是即时的但非零延迟）

**方案 B：引擎进程申请 Input Monitoring + 用 CGEventTap 替代 NSEvent**
- `CGEventTapCreate` 不依赖 NSRunLoop，可在 dispatchMain 下工作
- 但需申请 Input Monitoring 权限（项目从未申请过）→ 用户需手动授权
- **缺点**：引入新权限依赖，用户体验变差

**推荐方案 A**：已有 socket config 通道，改动最小，不引入新权限。
