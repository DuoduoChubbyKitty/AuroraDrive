# 性能 · 抓屏实测（P5 · 2026-10-11）

> **任务**：task-88（P5）· **类型**：只读实测（**未改任何源码**）
> **方法**：`AURORA_DIGEST=1` 启动 app，真实采样 CPU/GPU，`sample` 抓热点，对比抓屏开/关
> **结论**：**抓屏的真实成本已量化**——engine 进程 CPU **+76.3pp**（0.3% → 76.6%）、
> RSS **+210MB**（37MB → 247MB）、UI CPU **+20.8pp**、GPU **+8.5pp**。
> ⚠️ **`powermetrics` 无权限**（需密码），GPU 数据改用 `ioreg` 免密读取。

---

## 0. 一句话结论

**抓屏（1280×832@45fps）开启后，主成本在 engine 进程：CPU 从 0.3% 涨到 76.6%（+76.3pp）、
RSS 从 37MB 涨到 247MB（+210MB，**5.7 倍**）；UI 进程 CPU 从 0.8% 涨到 21.6%。**
GPU 占用只增加 8.5pp（59.6% → 68.1%），说明**瓶颈在 CPU 侧（图像搬运/转换/推理），不在 GPU 渲染**。

## 4. ★ 抓屏的真实成本（差值 = 状态 B − 状态 A）

| 指标 | 状态 A（抓屏关） | 状态 B（抓屏开） | **差值（真实成本）** | 倍数 |
|---|---|---|---|---|
| **engine CPU (p50)** | 0.3% | **85.2%** | **+84.9 pp** | 284× |
| **engine CPU (mean)** | 0.30% | 76.62% | **+76.3 pp** | 255× |
| **engine RSS** | 37.0MB | **247.4MB** | **+210.4 MB** | **6.7×** |
| **UI CPU (mean)** | 0.78% | 21.61% | **+20.8 pp** | 28× |
| **UI RSS** | 139.5MB | 150.5MB | **+11.0 MB** | 1.08× |
| **GPU Device% (mean)** | 59.6% | 68.1% | **+8.5 pp** | 1.14× |

### 三条关键结论

1. **抓屏的主成本在 engine 进程的 CPU**（+76~85pp），**不在 GPU**（仅 +8.5pp）。
   → 优化方向应是**减少 CPU 侧的图像搬运/转换**，而不是优化 GPU 渲染。

2. **engine RSS 涨 210MB（6.7 倍）** —— 这是**内存**问题：抓屏缓冲 + 推理模型 + 共享内存。
   ⚠️ MacBook Air 16GB，247MB 单进程可接受，但**6.7 倍增长值得关注**。

3. **UI 进程 CPU 也涨 20.8pp** —— UI 不是"纯显示"：它要收引擎推来的帧并绘制。
   与 §5 热点（`vImage`/`CABackingStoreCollect_`）吻合。

### ★ 热点解读（本次实测最有价值的发现）

**ENGINE 进程（抓屏主战场）—— 三大开销**：

| 热点 | 采样数 | 含义 |
|---|---|---|
| `vImage` 缩放族：`vVertical_Scale_ARGB_8888_Accelerate_64x16`(446) + `vHorizontal_Scale_...`(380) + `argb32_sample_rectilinear_argb32`(321) + `resample_horizontal/vertical`(140+118) | **1405** | **图像缩放**（抓屏 1280×832 → 模型输入尺寸） |
| `YolopxEngine.extractMask` | **465** | 车道线掩码提取（后处理） |
| `vConvert_ARGB8888toPlanarF_CV_vec` | **223** | ARGB→Planar Float 格式转换（喂模型） |
| `EngineFrameShm.writeMask` | 96 | 掩码写共享内存（跨进程传输） |
| `libBNNS` 两处 | 241+176 | CoreML/BNNS 推理 |

**→ 结论：engine 侧 CPU 主要花在「图像缩放 + 格式转换 + 掩码提取」，即经典的
CPU 图像处理管线，不是推理本身。**

**UI 进程 —— 几乎全是 `vImage` 格式转换**：
`vLookupTable_Planar16WithClipping`(44) + `vUnpremultiplyData_RGBA8888_CV_vec`(43)
+ `vLookupTable_Planar8toPlanar16`(26) + `vPremultiplyData_RGBA8888_CV_vec`(18)
+ `vMatrixMultiply_Planar16S_27_vec`(15) + `AnyToAnyBlockInternal`(11)
+ `vConvert_Planar16Q12toARGB8888_vec`(11) = **168**
加上 `read`(4858，从 socket 读帧) → **UI 的成本是"收帧 + 像素格式转换 + 绘制"**。

> ✅ 本次 sample **在驾驶中抓取**（engine CPU 90~105% 时），**不是空闲态**——
> 这是对上一版报告缺口的修正。上一版 sample 在 stop 之后执行，栈顶全是等待类，无参考价值。
> `vConvert_Planar16FtoPlanarF_vec`——**可作参考但受干扰污染，不作为结论**。

## 9. 复现步骤（只读）


## 10. 对下一步优化方向的建议（基于实测）

1. **优先优化 engine 进程的 CPU**（+76~85pp 是最大项）——不是 GPU。
2. **UI 侧的 `vImage` 格式转换**（§5 三个函数）值得查：像素格式转换能否在引擎侧一次做完，
   避免传到 UI 再转？
3. **engine RSS +210MB** 需要关注（16GB 机器上可接受，但要防长期增长）。
4. ⚠️ **不要在 GPU 上做优化**——实测只占 8.5pp 增量，收益空间小。
