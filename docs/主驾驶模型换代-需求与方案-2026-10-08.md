## 0. 摘要（TL;DR）

用户说 M9「残废：只会直走、不会跟车道线、会开出车道线、不训练就停在原地不输出」。
**本次侦察把这句话拆成了三个互相独立的根因，全部拿到硬证据**：

| # | 根因 | 一句话 | 关键证据 |
|---|---|---|---|
| **R1** | **当前部署的"M9"根本不是 M9** | `models/m9_mono.mlmodelc` 的 `generatedClassName` 是 **`game_assist_control_fpv`** —— 它是 FPV 游戏辅助模型被复制改名而来 | `models/m9_mono.mlmodelc/metadata.json` |
| **R2** | **训练数据是「macOS 桌面截图」，不是游戏画面** | `data/raw_clips/` 全部 129 帧经逐帧目视 = 桌面 + AuroraDrive 自己的窗口；5 个 clip 的 `controls.csv` **标签全为 0.0000** | 见 §2.2 目视取证 + 命令输出 |
| **R3** | **数据管线在默认参数下直接抛异常，训不出东西** | `MonoClipsDataset(skip_zero_label=True)`（默认）在现有数据上抛 `RuntimeError: 所有 clip 帧均被过滤` | `src/mono_dataset.py:168,196,206` + 实跑输出 |

**⟹ 三个根因叠加，正好逐条解释用户观察到的现象**（§2.4 有对照表）。
**⟹ 关键含义：本次换代的第一优先级不是"换骨干"，而是"先让录制产出可训练的数据"。**
换骨干（M2 已做）解决的是容量与输入接口，**不解决数据**。

**另外五个必须先摆到台面上的事实**：

1. **视角标签与实际内容不符**：`view.txt` 全部写着 `FPV`，但录制调用点是**硬编码** `perspective: "first"`（`AuroraDriveApp.swift:4921`、`AIAgentPanel.swift:894`），
   而用户实际玩的是**第三视角**（`AuroraDriveApp.swift:7250` 原话：「用户玩的是**第三视角**」）。**标签是录制器自己填的常量，不是从画面判定的** → §5。
2. **模型体积超约束**：现有 M9 架构 `M9MonoModel` = **8,651,283 参数 → FP16 ≈ 16.5MB**，超用户 10MB 硬约束（`docs/换代约束通告-2026-10-08.md`）。M2 新写的 `src/model_v2.py` = 2.76M / 6.2MB 合规。
3. **车道线与检测框录制时根本没落盘**（§4.4）—— 新模型的两路核心输入**在历史数据里不存在**。
   已有代理实现离线伪标签补救（`src/dataset_v2.py:914,966`），**但伪标签不能替代录制端落盘**。
4. **🔴 heading 单位存在真实口径冲突**（§3.4）：`NetworkLocator` 产出**度**（`NetworkLocator.swift:310`），
   而模型契约隐含**弧度**。**直接接入会得到完全错误的角度。**
5. **状态维度存在 8 vs 10 分叉**（§3.4）：`src/model_v2.py:212` = 8 维（入模），
   `src/dataset_v2.py:107` = 10 维（落盘），靠 `src/train_v2.py:372` 的 `map_state()` 桥接。

**⟹ 关于既有进展的定位**：`src/model_v2.py`（模型）、`src/dataset_v2.py`（数据集）、`src/train_v2.py`（训练）
三件套**已在本次侦察期间由其他代理落地**（均为工作区未提交状态）。
**M1 不重复造轮子** —— 本文件的输入规格建议改为「**复核 + 补缺口**」形式（§3.6），
并**新增了 3 条它们尚未覆盖的风险**（heading 单位、dets 口径分叉、伪标签上限）。

## 2. 现状体检：M9 为什么"残废"

### 2.1 R1 —— 部署的"M9"是 FPV 游戏辅助模型，不是 M9

**证据链**：

```
$ python3 -c "import json;d=json.load(open('models/m9_mono.mlmodelc/metadata.json'));print(d[0]['generatedClassName'])"
game_assist_control_fpv
```

`models/m9_mono.mlmodelc/metadata.json` 的 `generatedClassName` = **`game_assist_control_fpv`**，
而 `models/game_assist_control.mlmodelc/metadata.json` 的 `generatedClassName` = `game_assist_control_int8`。
两者**都是 `game_assist_control` 系列**，**都不是** `src/model.py` 里的 `M9Model`/`M9MonoModel` 类名。

**为什么会这样** —— 这是**设计如此**的"训练完一键热替换"：

```swift
// Sources/AuroraDrive/App/AuroraDriveApp.swift:6192
let names = ["game_assist_control_fpv.mlmodelc", "game_assist_control.mlmodelc",
             "game_assist_control_fpv.mlpackage", "game_assist_control.mlpackage"]
...
let dst = modelsDir.appendingPathComponent("m9_mono.\(src.pathExtension)")
try FileManager.default.copyItem(at: src, to: dst)
```

`deployTrainedModel()`（`AuroraDriveApp.swift:6189-6233`）把**训练产出的 FPV 模型复制成 `m9_mono.*`**，
再由 `InferenceEngine(modelFileName: "m9_mono")`（`InferenceEngine.swift:135`）加载。

**⟹ 结论（高置信度）**：所谓"M9 主驾驶模型"在运行时的实际身份 = **`game_assist_control_fpv`**。
M9（`M9Model`，10 摄像头 + 2 激光雷达 + 13,318 维融合头，`src/model.py:12`）**从来没有被部署到这个位置**。
它的 ONNX 残骸 `models/m9_mono.onnx` 停留在 **Jul 26 15:07**，而 mlmodelc 是 **Sep 12 22:14** —— 相差 48 天，二者无关。

**这条纠正了 Lead 简报里的一个隐含前提**：任务书写"当前 M9 接口 `image [1,3,180,320]` + `vehicle_state [1,6]`" ——
接口 shape 是对的（`InferenceEngine.swift:10-14`），但**它描述的其实是 game_assist 模型的接口**，
不是 `src/model.py` 里 M9 的接口（M9 是 10 路图像 + 点云）。**换代时要换掉的是这个 FPV 模型的角色**。

### 2.2 R2 —— 训练数据是桌面截图，且标签全零（决定性证据）

**表头（录制器写的）**：

```
$ head -3 data/raw_clips/*/controls.csv
==> data/raw_clips/clip_20260825_182145/controls.csv <==
t_sec,frame,steer,throttle,brake
0.0106,0,0.0000,0.0000,0.0000
```

**5 个 clip 的表头完全一致**（`t_sec,frame,steer,throttle,brake`），
即全部命中 `src/mono_dataset.py:84` 的 **`v1_old`** 分支，`vehicle_state` 被**零向量填充**（`src/mono_dataset.py:119`）。

**标签全零（逐 clip 求和）**：

```
$ for f in data/raw_clips/*/controls.csv; do awk -F, 'NR>1{s+=$3;t+=$4;b+=$5;n++} END{printf "n=%d sum_steer=%.4f sum_throttle=%.4f sum_brake=%.4f\n",n,s,t,b}' "$f"; done
clip_20260825_182145: n=23 sum_steer=0.0000 sum_throttle=0.0000 sum_brake=0.0000
clip_20260825_182147: n=12 sum_steer=0.0000 sum_throttle=0.0000 sum_brake=0.0000
clip_20260922_003025: n=2  sum_steer=0.0000 sum_throttle=0.0000 sum_brake=0.0000
clip_20260922_003027: n=22 sum_steer=0.0000 sum_throttle=0.0000 sum_brake=0.0000
clip_20260922_003029: n=70 sum_steer=0.0000 sum_throttle=0.0000 sum_brake=0.0000
```

**去重后唯一值**：`cat data/raw_clips/*/controls.csv | grep -v "^t_sec" | awk -F, '{print $3"|"$4"|"$5}' | sort -u`
→ **只有一行 `0.0000|0.0000|0.0000`**。

**画面真实内容（目视取证，这是最关键的一条）**：

M1 对 5 个 clip 各取 3 帧（共 15 帧）拼图目视，**全部 15 帧显示的是 macOS 桌面**：
- 壁纸、顶部菜单栏、Dock、右上角状态栏图标
- **AuroraDrive 自己的控制面板窗口**（左侧「AURORA 面板」、右侧参数栏、中间地图）
- 部分帧里 AuroraDrive 窗口本身是主体，游戏窗口根本不在画面内

**帧尺寸**：全部 640×360（`sips -g pixelWidth -g pixelHeight` → `640 × 360`），
与 `RecordEngine.swift:31` 的 `targetSize = CGSize(width: 640, height: 360)` 一致。

**为什么录到的是桌面而不是游戏** —— 抓屏范围是**整块显示器、不排除任何窗口**：

```swift
// Sources/AuroraDrive/Capture/CaptureEngine.swift:229
let filter = SCContentFilter(display: display, excludingWindows: [])
```

配合 `config.showsCursor = true`（`CaptureEngine.swift:227`），
只要录制时游戏不在前台 / 被 AuroraDrive 窗口盖住 / 压根没启动，**录到的就是桌面**。

**为什么标签全零** —— 标签来源只有两条，当时都不成立：

```swift
// Sources/AuroraDrive/App/AuroraDriveApp.swift:7441-7458
if expertMode {
    recSteer = RecordLabelMapper.steer(leftHeld: keyboardMonitor.holdDuration(keyCode: 0), ...)
    ...
} else {
    recSteer   = currentCommand.steer
    recThrottle = currentCommand.throttle
    recBrake   = currentCommand.brake
}
```

- **非专家模式**：录 `currentCommand`（AI 自己的决策）。没在开车 → `currentCommand` 恒 0 → **全零**。
- **专家模式**：录真人按键按住时长（`RecordLabelMapper`，`AuroraDriveApp.swift:4090-4119`）。没按键 → 全零。

**⟹ 用户原话"之前那些数据只是纯走直线什么都不给的"得到完整解释**：
不是"走了直线但没转弯"，而是**标签一个都没写进去**（全 0），画面**连游戏都不是**。

**冗余度**：129 帧中唯一帧只有 **90** 帧（`md5` 去重），有 **26 帧完全重复**同一张图。

### 2.3 R3 —— 数据管线在默认参数下直接抛异常

`MonoClipsDataset.__init__` 默认 `skip_zero_label=True`（`src/mono_dataset.py:168`），
过滤逻辑在 `:196`，过滤干净后抛异常于 `:206`：

```python
# src/mono_dataset.py:196
if skip_zero_label and row["steer"] == 0.0 \
        and row["throttle"] == 0.0 and row["brake"] == 0.0:
    continue
# src/mono_dataset.py:206
raise RuntimeError(f"所有 clip 帧均被过滤（skip_zero_label={skip_zero_label}）")
```

**实跑验证**：

```
$ /usr/local/bin/python3.11 -c "from src.mono_dataset import MonoClipsDataset; MonoClipsDataset('data/raw_clips')"
RAISED: RuntimeError -> 所有 clip 帧均被过滤（skip_zero_label=True）

$ ... skip_zero_label=False
[MonoDataset] 加载 129 样本，来自 5 个 clip （全部视角，有效控制帧 0）
len= 129
labels all zero? True
```

注意日志里的 **`有效控制帧 0`** —— 这是 `src/mono_dataset.py:209-211` 自己打印的统计。

**⟹ 结论**：**用当前数据根本走不到训练循环**。要么抛异常，要么用 `skip_zero_label=False`
硬训 129 个全零标签帧 —— 后者等价于教模型「无论看到什么，输出恒 0」。
这解释了用户说的「**不训练就停在原地不输出**」的另一半：即使"训练成功"，学到的也是恒零。

### 2.4 三个根因 ↔ 用户现象对照表

| 用户原话 | 对应根因 | 机理 |
|---|---|---|
| 「只会直走」 | **R2 + R3** | 训练标签全零 → 模型学到恒零输出；推理端 `throttle` 却恒 ≈0.94（见 §2.5），低速下表现为直行 |
| 「不会跟车道线」 | **R1 + 架构** | 部署的是 game_assist 模型，**输入里根本没有车道线通道**（只有 `image` + `vehicle_state`，`InferenceEngine.swift:10-11`）；车道线只走 `LaneFallback` 规则兜底，不进模型 |
| 「会直接开出车道线」 | **R2 + R3** | 模型对画面内容不敏感（§2.5 实测 steer 极差仅 0.006），无法从画面学到"该转弯" |
| 「不训练就停在原地不输出」 | **R3** | 数据管线抛异常 → 训练根本没跑成 → 没有新模型产出 → `deployTrainedModel()` 找不到源文件直接 `return false`（`AuroraDriveApp.swift:6194-6197`） |

### 2.5 模型实际行为实测（部署权重）

M1 用 `checkpoints/game_assist_control_fpv/best_model.pt`（即 `m9_mono.mlmodelc` 的来源）
在**真实录制的 70 帧**上逐帧推理：

```
$ /usr/local/bin/python3.11 (build_m9_mono + load_state_dict(strict=False) → missing:0 unexpected:0)
testing 70 frames, state=speed0.5/curv0/h0/limit0.5
  steer:    min=-0.0676 max=-0.0616 std=0.0014
  throttle: min=0.9431 max=0.9444 std=0.0003
  brake:    min=0.0616 max=0.0624 std=0.0002
```

**⟹ 输出几乎是常量**：70 帧画面变化下，steer 极差仅 **0.006**、throttle 极差 **0.0013**。
模型对画面**基本不响应** —— 这与"标签全零、数据是桌面"完全自洽。
（注：这 70 帧是桌面截图，属于**分布外输入**，此处测的是"输出不敏感"这一现象本身。）

**状态输入的影响**（同一帧、改 vehicle_state）：

```
zero-state (curv=0,h=0)    steer=-0.0695 throttle=0.9399 brake=0.0627
speed0.5 limit0.5          steer=-0.0676 throttle=0.9431 brake=0.0624
speed0.3 curv=1            steer=-0.1069 throttle=0.9436 brake=0.0589
```

**⟹ 状态通道确实有梯度响应**（curv 从 +1 到 −1，steer 从 −0.107 变到 −0.028），
说明"接收角度/曲率"这条路径在架构上是通的、且权重真的学到了东西。
**这是对需求⑤（加加速度/角度输入）的正面证据**：状态分支有效，值得保留并加强。

### 2.6 状态输入现状：接口在，但值是硬编码的

```swift
// Sources/AuroraDrive/Inference/InferenceEngine.swift:431-436
arr[0] = NSNumber(value: speedNorm)          // speed_norm [0,1]
arr[1] = NSNumber(value: 0.0)                // curvature*5（无遥测→0）
arr[2] = NSNumber(value: 0.0)                // sin(heading)（无遥测→0）
arr[3] = NSNumber(value: 1.0)                // cos(heading)（无遥测→1）
arr[4] = NSNumber(value: limitNorm)          // speed_limit_norm [0,1]
arr[5] = NSNumber(value: 0.0)                // reserved
```

**6 维里 3 维（curvature / sin(heading) / cos(heading)）被硬编码为常量**（`:432-434`）。
即**模型现在收不到任何"角度"信息** —— 需求⑤目前是**未满足**状态。

**但数据源是存在的**（见 §3.5），只是没接进来。

## 3. 新模型输入规格建议

### 3.0 总原则

1. **每条输入都必须有「缺失/降级」的合法表示**（真实驾驶里车道线全丢、前方无车是常态）。
   M2 的 `src/model_v2.py` 已按此设计（`_zero_like` 早退，`src/model_v2.py:110-117`）—— **复核通过，建议沿用**。
2. **可行驶区域（drivableMask）绝对不进模型** —— 用户明确要求，且 M2 已在 `src/model_v2.py:118-121` 写成契约红线。
3. **所有输入必须在训练侧与推理侧用同一份归一化契约**，并把契约写进导出脚本。
   （历史教训：`InferenceEngine.swift:404` 记录了"前三维超出训练分布 60~8000 倍 → 恒输出 steer=-1/throttle=1"的事故。）

### 3.1 输入①：图像（第三视角）

| 项 | 建议值 | 依据 |
|---|---|---|
| shape | `[1, 3, 180, 320]` Float32 CHW | 沿用 `InferenceEngine.swift:10`；`models/*/metadata.json` 实测输入 |
| 归一化 | `[0,1]` | `InferenceEngine.swift:10`、`src/mono_dataset.py:29` |
| 色彩 | RGB（不是 BGR） | `src/mono_dataset.py:228` `im.convert("RGB")` |
| 分辨率是否提高 | **建议维持 180×320，先不动** | 提高分辨率直接线性推高 ImageEncoder 耗时（占模型 90%，`src/model_v2.py:68`），30Hz 预算会被吃掉。**若实测车道线细节不足，再考虑 240×426** |

✅ **宽高比已核对，图像分支无需 letterbox**：现有录制是 **640×360**（`RecordEngine.swift:31`），
训练侧 resize 到 180×320（`src/mono_dataset.py:227-228`）。
640/360 = 1.778，320/180 = 1.778，**两者同为 16:9，等比缩放无变形**。

🔴 **但车道线/检测框与图像是「三套不同坐标系」，这是融合前的硬伤**：

| 数据 | 坐标系 | 依据 |
|---|---|---|
| 图像（录制帧） | 640×360 等比 → 180×320 | `RecordEngine.swift:31`、`src/mono_dataset.py:227-228` |
| `MaskGrid`（车道线） | **letterbox 640 空间，含 114 灰边**，stride = 640/160 = 4 | `YolopxEngine.swift:20-21,40,262-263` |
| `Detection`（检测框） | **原帧归一化 [0,1]，已剔除灰边** | `YoloEngine.swift:21-22`（非等比拉伸）、`RuleController.swift:40-43` |

⚠️ 注意两个感知引擎的预处理**并不一致**：
`YolopxEngine` 是 **letterbox（等比 + 灰边）**（`YolopxEngine.swift:20-21` 明确「**不是**整帧拉伸」），
而 `YoloEngine` 是 **整帧非等比拉伸**（`YoloEngine.swift:21-22` 明确「不做 letterbox」）。

**⟹ 结论**：把 `MaskGrid` 与 `Detection` 直接 concat 会错位（M6 实测**最多 46 格 / 184px**）。
**这一条已由 M6 的专项文档深入处理，本文件不重复展开** —— 见
[车道线检测框输入编码方案-2026-10-08.md](车道线检测框输入编码方案-2026-10-08.md)（M6 产出）。
M1 的复核结论：**M6 关于"裁掉灰边后 `Detection` 零换算直接可用"的推导成立**，
且该结论**优先于本文件的 §3.2/§3.3 编码细节**。

### 3.2 输入②：车道线掩码（对应需求①）

**建议编码**：`lane [1, 1, 160, 160]` Float32 二值 {0,1}。

| 项 | 值 | 依据 |
|---|---|---|
| 来源 | `YolopxEngine.laneMask` | `Sources/AuroraDrive/Inference/YolopxEngine.swift:375` |
| 类型 | `MaskGrid`（`width`/`height`/`cells: [UInt8]`，行优先，0=背景 1=前景） | `YolopxEngine.swift:45-52` |

**为什么 1 通道而不是 2 通道（左右车道线分开）**：
- 现状 `MaskGrid` 是**单张二值图**，左右线没有分开存储（`YolopxEngine.swift:48` `cells: [UInt8]`，无通道维）。
- 若要左右分离，需要改 `extractMask` 的 argmax 逻辑（`YolopxEngine.swift:1265-1346` 附近），**属于 Swift 侧改动，超出本次侦察范围**。
- **建议**：先按 1 通道做（M2 方案）。若训练后发现"分不清该往哪边偏"，再升级为 2 通道 —— 但那是**感知侧改造**，不是模型侧。

⚠️ **车道线质量风险（重要，见 §7 R-2）**：
`YolopxEngine` 有 `laneDegraded` 标志（`YolopxEngine.swift:397`），
且车道线刷新率被 P1 降频拖到约 8~15Hz、带 1~2 帧 EMA 滞后（`docs/车道线外推-蓝图-2026-10-07.md` §1.2）。
**训练时用的是"最终掩码"，推理时也是同一份** —— 这一点是自洽的。
但**退化帧要不要喂给模型、还是喂全零**，必须在训练侧与推理侧**取同一个策略**，否则分布不一致。

### 3.3 输入③：检测框（对应需求②）

**建议编码**：`dets [1, N, 12]` + `det_mask [1, N]`，固定槽位 **N=20**，空槽补 0。

⚠️ **与 M6/M3 的口径分叉（M1 侦察期间发现）**：
- `src/model_v2.py`（M2 模型）用 **`dets [1, N, 12]`**（每框 12 维，含 label one-hot 与 conf），`src/model_v2.py:512-524`。

🔴 **发现一个真实的口径冲突（heading 单位）—— 接 heading 前必须先解决**：

```swift
// Sources/AuroraDrive/Locate/NetworkLocator.swift:310
let heading = (atan2(eastDot, northDot) * 180.0 / .pi + 360.0).truncatingRemainder(dividingBy: 360.0)
//                                                                  ↑ 产出「度」，范围 [0,360)
```

```swift
// Sources/AuroraDrive/Inference/InferenceEngine.swift:433-434
arr[2] = NSNumber(value: 0.0)                // sin(heading)（无遥测→0）
arr[3] = NSNumber(value: 1.0)                // cos(heading)（无遥测→1）
```

`NetworkLocator` 产出的 heading 是**度**（`[0,360)`），
而 `InferenceEngine` 的 sin/cos 契约隐含**弧度**。
`src/dataset_v2.py:75-79` 已明确标注这是「**真实存在的口径冲突**」并提供
`heading_unit="auto"|"rad"|"deg"` 参数（auto 规则：`max|heading| > 2π+eps` → 判为度）。

**⟹ 结论**：**把 `locatorHeading`（度）直接塞进 sin/cos 会产生完全错误的角度**
（例如 heading=90° 会被当 90 rad 算 sin）。
**这是 M1 独立发现、且 M3 也独立标注的同一个坑 —— 高置信度，必须显式指定 `heading_unit="deg"`。**

**关于"当前角度"的语义澄清（重要）**：
用户说「当前角度」，有**三种可能解释**，本项目里对应**三个不同的量**：
1. **车辆朝向（heading）** —— `locatorHeading`，世界坐标系绝对方位角（`NetworkLocator.swift:270,299-311`），**单位是度**。
2. **转向角（steer_angle）** —— 当前前轮转角。**本项目没有这个数据源**（`src/train_v2.py:385` 明确标 `✗ 无 → 0`）。
3. **曲率（curvature）** —— 轨迹弯曲程度。**本项目也没有实时数据源**（`InferenceEngine.swift:432` 硬编码 0）。

**⟹ 建议**：先接 **heading（有源，需转弧度）**，并**明确告诉用户"转向角/曲率游戏不给"**。
如果用户要的是转向角，那是**不可得**的 —— 这属于要跟用户澄清的需求歧义，**不要自己猜**。

**关于加速度数据源（关键发现）**：

```swift
// Sources/AuroraDrive/App/AuroraDriveApp.swift:4651-4655
// 同包加速度：坐标系未实测确认，只做如实展示，不参与控制。

```

- 数据源 = `NetworkLocator` 通过 **`ws://127.0.0.1:9004`** 的位姿桥接（`NetworkLocator.swift:23`、`:411`），
  从游戏 C2S 移动包解出，**约 8Hz**（`AuroraDriveApp.swift:4649`）。
- ⚠️ **坐标系未实测确认、单位只是"推测"**（`:4651-4652` 原文），且**当前"不参与控制"**。
- **⟹ 建议**：加速度接进模型前，**必须先做一次坐标系与单位的实测标定**（直线加速 vs 转向时的符号/量级）。
  **这是 M1 标「未验证」的一条** —— 直接把推测值喂给模型有重演 `InferenceEngine.swift:404` 事故的风险。
- ⚠️ **补充**：`src/dataset_v2.py` 的 `accel` 是**从 `speed_kmh` 逐帧差分算出的**
  （`src/dataset_v2.py:70`「逐帧差分算出的加速度」），
  而**运行时**的 `accel` 来自 9004 端口的游戏物理包。**两者是不同来源、不同噪声特性** ——
  训练用差分、推理用物理包，**存在分布不一致风险**（标「未验证」）。

### 4.2 结论：**完全不够，且不是"量"的问题，是"质"的问题**

**不能用的原因（按严重度排序）**：

1. 🔴 **标签全零** —— 129 帧无一条有效监督信号。**这是致命的，不是"少"而是"没有"。**
2. 🔴 **画面内容错误** —— 录的是桌面/工具窗口，不是游戏画面。**分布与推理时完全不同。**
3. 🔴 **没有状态字段** —— 需求⑤要的加速度/角度，v1 格式里一个都没有。
4. 🟠 **无弯道** —— 用户原话「纯走直线什么都不给」（`docs/换代约束通告-2026-10-08.md`）。
5. 🟠 **视角标签不可信** —— 硬编码 `"first"`（§5.1），无法用于 TPV/FPV 路由。
6. 🟡 **量级过小** —— 129 帧（唯一 90）对任何 CNN 都是杯水车薪。M2 模型 3.26M 参数，
   90 张唯一图训练必然过拟合。

### 4.3 缺什么（按优先级）

| # | 缺的东西 | 为什么必须 | 落点 |
|---|---|---|---|
| **1** | **游戏真实画面 + 非零控制标签** | 唯一能让模型学到"画面→控制"的东西 | 录制链路修复（§4.4） |
| **2** | **弯道样本** | 用户明确要求；直行数据训不出转向能力 | 录制时人为走弯道 |
| **3** | **状态字段落盘** | 需求⑤的前提；否则训练侧只能填零 | 扩 `controls.csv` 表头 |
| **4** | **正确的视角标签** | 第三视角 vs 第一视角模型不能混 | 录制时传对 `perspective` |
| **5** | **车道线/检测框的"同步快照"** | 现在**完全没有落盘** | 见 §4.4 ⚠️ |
| **6** | **量级** | 至少数百~数千帧有效样本 | 多次录制 |

| 方案 | 实现 | 位置 |
|---|---|---|
| **车道线离线补算** | `backfill_lane_masks()` —— 用 yolopx 的 **`ll` 车道线头**对录制帧跑一遍，落盘 `{clip}/lane_mask/{frame:06d}.png` | `src/dataset_v2.py:914-929` |
| **检测框离线补算** | `backfill_detections()` —— yolopx `det` 头 + NMS | `src/dataset_v2.py:48`（docstring 引用） |

**M1 对该方案的复核意见（3 条，其中 1 条是明确警告）**：

1. ✅ **方向正确** —— 用已有感知模型对历史帧回灌，避免了"必须重录才有 lane/dets"的死锁。
2. ✅ **可行驶区域被显式丢弃** —— `src/dataset_v2.py:927` 明确「**`da`（可行驶区域）头被显式丢弃**」，
   符合用户需求③。**复核通过。**
3. 🔴 **但它产出的是「伪标签」，不是真值** —— `src/dataset_v2.py:929` 自己承认：
   「⚠️ 这是**伪标签**（yolopx 预测），不是人工标注，存在域偏差，训练时建议给较低权重。」
   **⟹ 关键推论**：用伪标签训出的模型，**上限就是 yolopx 的车道线质量**（见 §7 R-2：`laneDegraded`、
   8~15Hz 刷新、1~2 帧 EMA 滞后）。
   而且**当前录制帧是桌面截图**（§2.2），对桌面跑 yolopx **只会得到垃圾掩码**。
   **⟹ 伪标签方案只有在「画面本身是对的（真实游戏第三视角）」的前提下才有意义。**

**⟹ M1 的最终建议**：
- **短期**：用 `backfill_*` 让管线跑通（验证代码路径、做端到端冒烟测试），**但不要用现有数据训正式模型**。
- **长期（正式训练）**：**必须在录制端实时落盘 lane/dets**，理由有二：
  ① 避免伪标签的域偏差；② 运行时模型看到的是**当帧真实掩码**，训练就该用同一份。
- **落盘方案建议**（录制端，三选一）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 扩 `controls.csv`** | 加 `lane_rle` 列（160×160 二值游程编码）+ `dets_json` 列 | CSV 变宽；RLE 约 1~3KB/帧，70 帧 ≈ 200KB，可接受；解析要写 RLE 编解码 |
| **B. 每帧存 PNG 掩码** | `frames/000000_lane.png`（160×160 1-bit PNG ≈ 400B） | 文件数翻倍；但最直观、最易调试、无需编解码 |
| **C. 存 sidecar JSONL** | `perception.jsonl`，每行 `{frame, lane_rle, dets:[...]}` | 与 CSV 解耦，不影响既有解析；但多一个文件要对齐 |

**M1 建议**：**方案 B（PNG 掩码）+ 方案 C 的变体** ——
掩码存 PNG（`_lane.png`）、检测框存 JSONL。理由：**可目视检查**（调试价值极高，
本次侦察就是靠目视才发现"录的是桌面"），且不破坏既有 CSV 解析。
⚠️ 注意 `src/dataset_v2.py:937` 已采用 `{clip}/lane_mask/{frame:06d}.png` 的命名 ——
**若采用方案 B，建议与它保持一致，避免两套缓存目录**。

⚠️ **未验证**：`RecordEngine` 是否能拿到 `laneMask`/`detections`。
它在 `AuroraDriveApp` 的 tick 里被调用（`AuroraDriveApp.swift:7438`），
而 `yolopxEngine.laneMask` 与 `yoloEngine.detections` 在同一作用域内可访问 —— **大概率可行，但 M1 未验证 tick 内的实际可见性**。

### 4.5 录制链路还有两个"录不到"的坑

1. **抓屏范围是整块显示器**（`CaptureEngine.swift:229` `excludingWindows: []`）——
   录制时应确保**游戏在前台且不被 AuroraDrive 窗口遮挡**，否则重现 §2.2 的桌面截图。
   更稳的做法：改用 `SCContentFilter(desktopIndependentWindow:)` 只抓游戏窗口 —— **属于 Swift 侧改造**。
2. **`maxClipsPerKind = 10` 自动删旧 clip**（`RecordEngine.swift:41`）——
   只保留最近 10 个 clip。**录满 10 个后继续录会静默删掉最旧的**，
   若想攒大批数据必须先调大这个常量。
3. **`clearRawClips()` 训完即删**（`AuroraDriveApp.swift:6235-6251`）——
   部署成功后**清空 `data/raw_clips/` 下所有 `clip_` 目录**。
   ⚠️ **若在数据攒够前误触发一次训练部署，全部录制数据会被清掉**。

## 5. 第三视角对数据的要求（对应需求⑥）

### 5.1 现有录制是哪个视角？—— **标签说是 FPV，但标签本身不可信**

**标签侧**：

```
$ for f in data/raw_clips/*/view.txt; do echo "$f => $(cat $f)"; done
clip_20260825_182145/view.txt => FPV
clip_20260825_182147/view.txt => FPV
clip_20260922_003025/view.txt => FPV
clip_20260922_003027/view.txt => FPV
clip_20260922_003029/view.txt => FPV
```

**但这个标签是录制器按调用参数硬编码写的，不是从画面判定的**：

```swift
// Sources/AuroraDrive/Capture/RecordEngine.swift:166-168
// 写视角标签，供训练端 _clip_view 过滤（first→FPV, third→TPV）
let viewLabel = (perspective == "first") ? "FPV" : "TPV"
try? viewLabel.write(to: sessionDir.appendingPathComponent("view.txt"), ...)
```

**而两个调用点都写死 `"first"`**：

```swift
// Sources/AuroraDrive/App/AuroraDriveApp.swift:4921
recordEngine.start(perspective: "first")
// Sources/AuroraDrive/Agent/AIAgentPanel.swift:894
recorder.start(perspective: "first")
```

**⟹ 结论**：
- `view.txt` 里的 `FPV` **只是"调用时传了 first"的记录，不代表画面真的是第一视角**。
- **实际上画面连游戏都不是**（§2.2 目视：是桌面），所以"是哪个视角"这个问题**对现有数据无意义**。
- **但标签机制本身是对的**（`third` → `TPV`），**只是没人传过 `third`**。
- 训练侧 `MonoClipsDataset(view_filter=...)` 依赖这个标签做过滤（`src/mono_dataset.py:181-186`），
  `_clip_view()` 读 `view.txt` 或 `clip.json`（`src/mono_dataset.py:57-75`）。
  ⚠️ 注意 `clip.json` **不存在于任何 clip**（`ls data/raw_clips/clip_*/clip.json` → 空），
  只有 `view.txt` 和 `meta.json`（`meta.json` 里的 `perspective` 字段是**目录名前缀**，不是视角，
  见 `RecordEngine.swift:226-228` —— 这是个容易混淆的命名）。

### 5.2 用户实际玩的是第三视角（需求⑥的依据）

```swift
// Sources/AuroraDrive/App/AuroraDriveApp.swift:7250
//   用户玩的是**第三视角**。模型会把**自车本身**当成一个检测框，
```

并且代码里有**三处**专门处理"第三视角自车入框"的逻辑
（`AuroraDriveApp.swift:1163`、`:4169`、`:5496`、`:7250`），
以及 `EgoBoxFilter` 整个类型（`Sources/AuroraDrive/Agent/EgoBoxFilter.swift`）。
**⟹ 用户玩第三视角是高置信度事实**（代码注释 + 专门设计的剔除器 + 实测标定数据）。

**⟹ 结论：现有 `view.txt = FPV` 与用户实际视角（第三视角）矛盾。**
这解释了为什么 `deployTrainedModel()` 要"优先 FPV 专用模型"
（`AuroraDriveApp.swift:6184` 注释：「当前录制为 FPV 视角」）——
**这个注释的前提是错的**，录制从来就是第三视角（或干脆是桌面）。

### 5.3 第三视角对数据的具体要求

| # | 要求 | 说明 |
|---|---|---|
| **1** | **必须重录** | 现有数据无论视角还是内容都不可用（§2.2）。**不是"要不要重录"的问题，是"必须重录"。** |
| **2** | 录制时传 `perspective: "third"` | 让 `view.txt` 写 `TPV`（`RecordEngine.swift:167`）。当前调用点硬编码 `"first"`，**需改**（Swift 侧）。 |
| **3** | **自车框必须在决策层剔除后喂模型** | `EgoBoxFilter`（阈值 4%，`EgoBoxFilter.swift:63`）。第三视角特有，FPV 无此问题。 |
| **4** | 画面构图需覆盖"追尾视角"特有元素 | 自车车尾、更大的近景地面、更小的远景。**模型要能容忍自车占据画面下 1/4。** |
| **5** | 训练/推理必须同视角 | 视角变了，画面统计分布全变。**绝不能混用 TPV/FPV 数据训同一个模型**（除非做视角条件化）。 |
| **6** | 建议保留视角分类器或显式路由 | `src/train_game_assist.py:50-58` 有 `ViewClassifier`（MobileNetV3-Small 三分类 TPV/FPV/MENU）。⚠️ 但 `AuroraDriveApp.swift:6150` 注释称「视角分类器已移除」，**两者矛盾，标「未验证」**。 |

### 5.4 重录的最低可行清单（建议）

1. 游戏切**第三视角**（用户当前设置，无需改）。
2. 确保**游戏在前台**、AuroraDrive 窗口不遮挡游戏画面（或改造抓屏为窗口级）。
3. 录制时 `perspective: "third"`。
4. **走弯道**（左右各若干次），不要只直行。
5. **扩 `controls.csv`**：加 `speed_kmh, heading, curvature, accel_x, accel_y`（§3.4 数据源）。
6. **落盘 lane + dets**（§4.4，**前置阻塞项**）。
7. 目标量级：**建议 ≥ 30 分钟有效驾驶、≥ 5000 帧**（含弯道）。⚠️ **这是 M1 的经验建议值，非实测推导**。

## 6. 输出规格

**建议沿用现有三头，不改**（改动收益低、破坏面大）：

| 输出 | shape | 激活 | 范围 | 依据 |
|---|---|---|---|---|
| `steer` | `[1,1]` | `tanh` | `[-1, 1]`，左负右正 | `InferenceEngine.swift:13`；`src/model_v2.py:116` |
| `throttle` | `[1,1]` | `sigmoid` | `[0, 1]` | `InferenceEngine.swift:14` |
| `brake` | `[1,1]` | `sigmoid` | `[0, 1]` | 同上 |

**理由**：
1. **Swift 侧零改动** —— `InferenceResult`（`InferenceEngine.swift:36-41`）与
   `ControlCommand` 的对接、按键注入映射（`AuroraDriveApp.swift:7468` 附近）全部复用。
2. **与训练标签语义天然对齐** —— `RecordLabelMapper`（`AuroraDriveApp.swift:4090-4119`）产出的
   就是 steer∈[-1,1]、throttle/brake∈[0,1]。
3. **M2 已经这么定了**（`src/model_v2.py:116`）。

**⚠️ 但要提醒一个语义坑**：本游戏里 **`brake` 就是 S 键，兼作倒车**
（`AuroraDriveApp.swift:7257-7258` 原文：「本游戏里 **brake 就是 S 键，兼作倒车**」）。
即输出 `brake` 高 ≠ "减速"，而是"挂倒挡"。
**这是策略层要处理的语义，不是模型输出规格的问题**，但**训练标签的语义必须与此一致**，
否则模型会学出"该减速时输出倒车"。**建议在文档与训练脚本里显式标注这条。**

**不建议的输出扩展**（明确排除）：
- ❌ 不做轨迹点/waypoint 输出（用户没要求，且标签体系不支持）。
- ❌ 不做可行驶区域分割输出（用户明确排除）。
- ❌ 不加"置信度"第四头（Swift 侧已有 `ConfidenceEstimator.swift` 独立算）。

## 7. 可行技术路线（3 条，各带代价）

### 路线 A：修数据 → 训 M2 模型（**推荐**）

**做法**：按 §4.4/§5.4 修录制链路（落盘 lane+dets+状态、传 `third`、确保游戏在前台），
录 ≥5000 帧含弯道数据，用已落地的 `src/model_v2.py`（2.76M / FP16 6.2MB）训练，
导出 CoreML，走既有 `deployTrainedModel()` 热替换。

| 维度 | 评估 |
|---|---|
| **模型** | `src/model_v2.py` **已存在且合规**（6.2MB < 10MB）✅ |
| **输入** | 完全覆盖需求①~⑥（含 `ego_visible`，无 drivable）✅ |
| **Swift 侧改动** | 中等：`InferenceEngine` 加 lane/dets/state 输入通道 + `RecordEngine` 落盘 + N=20 截断 |
| **数据需求** | **高**：必须重录，且必须先修落盘（§4.4） |
| **主要代价** | **工期压在"修录制链路 + 攒数据"上**，不在模型上 |
| **主要风险** | 车道线质量（§7 R-2）、加速度标定（§3.4） |
| **为什么推荐** | 复用 M2 已完成的模型工作，避免重复劳动；输入契约已对齐；体积合规 |

### 路线 B：先做「纯视觉 + 状态」最小闭环，车道线/检测框二期接入

**做法**：先用 `image + state(8维)` 训一版（砍掉 lane/dets 分支），
把"能开、能转弯、能跟线"跑通，**二期**再加 lane/dets。

| 维度 | 评估 |
|---|---|
| **优点** | **绕开 §4.4 的落盘阻塞**（lane/dets 不用落盘）；数据只需画面+标签+状态，录制改动最小；**能最快验证"第三视角纯视觉能不能开"**（正好对应用户需求④"可以自己纯视觉判断"） |
| **缺点** | 不满足需求①②（车道线/检测框），**只是过渡态**；二期接入时模型要重训 |
| **Swift 改动** | 小：只需扩 `controls.csv` 表头 + 传 `third` |
| **主要风险** | 纯视觉在第三视角下能否稳定跟线**未知**（用户需求④的原始疑问） |
| **适用** | **若 §4.4 落盘改造被卡住，这条路是唯一能往前走的** |

⚠️ **注意**：路线 B 与用户需求① ② 冲突，**只能作为过渡，不能作为交付**。
但它的价值在于：**用最小成本先回答"第三视角纯视觉可行性"这个最大未知**（§8 R-1）。

### 路线 C：换更小骨干（ShuffleNetV2 0.5x）+ 全输入

**做法**：把 `src/model_v2.py` 的 `ImageEncoder`（RepVGG-A0 轻量变体，2.76M）
换成 **ShuffleNetV2 0.5x（2.28M / 4.73MB）** 或 **MobileNetV3-Small（2.5M / 5.0MB）**
（`docs/骨干网络候选清单-2026-10-08.md` §1）。

| 维度 | 评估 |
|---|---|
| **优点** | 体积更小（4.73MB，留更多余量）；ShuffleNetV2 为移动端设计，ANE 友好 |
| **缺点** | **需要重新验证**：特征维度变化 → `FusionHead` 输入维度变 → 训练/导出全链路重跑；`RepVGG` 的重参数化优势（推理时融合为纯 3×3）丢失，需要新的部署路径 |
| **收益** | **边际**：M2 已经 6.2MB，离 10MB 上限还有 3.8MB 余量，**换骨干的收益不足以抵消风险** |
| **建议** | **暂不做**。除非路线 A 实测发现"6.2MB 仍太大"或"RepVGG 在 ANE 上耗时超标"。 |

### 路线对比小结

| | A（修数据+M2） | B（纯视觉最小闭环） | C（换骨干） |
|---|---|---|---|
| 满足需求①~⑥ | ✅ 全部 | ❌ 缺①② | ✅ 全部 |
| 数据阻塞（§4.4） | **被阻塞** | 绕开 | 被阻塞 |
| Swift 改动 | 中 | 小 | 中 |
| 体积 | 6.2MB ✅ | ~5MB ✅ | 4.7MB ✅ |
| 推荐度 | ⭐⭐⭐ **主路线** | ⭐⭐ **过渡/探路** | ⭐ **暂缓** |

**M1 建议**：**A 为主线，B 作为 A 被数据落盘卡住时的并行探路**。
两条路线**共享前 3 步**（传 `third` + 扩表头 + 确保游戏前台），
**分叉点只在"要不要落盘 lane/dets"** —— 所以**先做共享部分，不会浪费**。

## 8. 风险与未知

| # | 风险 / 未知 | 严重度 | 说明 | 缓解 |
|---|---|---|---|---|
| **R-1** | **第三视角纯视觉可行性未知** | 🔴 高 | 用户需求④「可以自己纯视觉判断」是**一个待验证的假设**，不是已知结论。市面上无可用第三视角自驾模型（用户原话，`docs/换代约束通告-2026-10-08.md`）。第三视角下自车占据画面下方、远景被压缩，**纯视觉能否稳定判断转向未知** | 路线 B 快速验证；先录少量数据做小规模实验 |
| **R-2** | **车道线掩码质量与刷新率** | 🔴 高 | `laneDegraded` 标志存在（`YolopxEngine.swift:397`）；刷新率被降到约 **8~15Hz** 且带 1~2 帧 EMA 滞后（`docs/车道线外推-蓝图-2026-10-07.md` §1.2）。模型输入是"滞后的车道线" | 训练/推理用**同一份掩码**（自洽）；在数据里保留 `laneDegraded` 标志让模型知道质量 |
| **R-3** | **加速度坐标系/单位未标定** | 🟠 中高 | `AuroraDriveApp.swift:4651-4652` 原文：「坐标系未实测确认」「单位**推测** cm/s²」。直接喂给模型有重演 `InferenceEngine.swift:404` 事故（超分布 60~8000 倍 → 恒输出 steer=-1）的风险 | **接进模型前必须实测标定**（直线加速/转向的符号与量级） |
| **R-4** | **lane/dets 未落盘** | 🔴 高 | §4.4。**没有这两路快照，新模型无法训练**。已有离线伪标签补救（`src/dataset_v2.py:914,966`），但伪标签有域偏差且上限 = yolopx 质量 | 录制端实时落盘（建议 PNG+JSONL）；伪标签仅用于冒烟测试 |
| **R-4b** | **伪标签方案的隐含上限** | 🟠 中高 | §4.4 第 3 条。`src/dataset_v2.py:929` 自认伪标签有域偏差。且**对现有桌面截图跑 yolopx 只会得到垃圾掩码** | 伪标签只在"画面正确"的前提下有意义；正式训练必须用真值 |
