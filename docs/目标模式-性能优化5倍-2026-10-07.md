## 目标（Objective）

把 AuroraDrive 的**运行时 + 未运行时性能消耗降低 5 倍**（即优化到当前的 **20%**）。
**用任何办法**，但必须满足下面全部约束。

**双口径都要降 5 倍**：
- **运行时**：驾驶中的引擎 CPU / tick 耗时 / 各推理子系统耗时
- **未运行时**：UI 空闲态 CPU / 内存占用 / 后备存储膨胀

## 二、🚫 红线：13 项已实测否决的优化（**不得重试**）

| 方向 | 实测结果 |
|---|---|
| 档位 `.all` → `.cpuAndNeuralEngine` | ❌ `.all` 更快（183 vs 204.6ms） |
| 档位 `.cpuAndGPU` | ❌ 慢 60%（278.5ms） |

| 输出端压缩（砍两张掩码） | ❌ 瓶颈在主干卷积，非搬运 |

## 三、5 倍目标的可达性分析（Lead 实测判断）

**要降 5 倍（到 20%），必须动结构，不能靠微优化。**

| 子系统 | 当前 p50 | 目标（1/5） | 可行性判断 |
|---|---|---|---|
| **infer.yolopx** | 22.647ms | **4.53ms** | ⚠️ **难**。yolopx 是重模型；要么换更小模型，要么降频，要么换算力单元 |
| **infer.yolo26s** | 14.065ms | **2.81ms** | ⚠️ **难**。同上 |
| infer.m9 | 4.099ms | 0.82ms | ⚠️ 难（但 p95 10.46ms 说明有长尾可削） |
| infer.assist | 3.509ms | 0.70ms | ⚠️ 难 |
| **opticalflow** | 6.171ms | **1.23ms** | ⚠️ 难（光流本身是密集计算） |
| **tick.loop** | 6.275ms | **1.26ms** | ✅ **可能**（tick 本身是调度逻辑，主要被光流吃掉） |
| **引擎 CPU** | 59.2% | **11.8%** | ✅ **最可能**（推理降频/条件触发能大幅降） |
| UI 空闲 CPU | 3.9% | 0.78% | ✅ **可能**（停掉无意义轮询/渲染） |
| UI RSS | 121MB | 24MB | ⚠️ 难（模型/缓存占用） |

**Lead 的判断**：
- **引擎 CPU 5 倍（59.2% → 11.8%）**：**最可能达成**——核心手段是**推理条件触发**（不是每帧都跑 4 个模型）
- **tick.loop 5 倍**：**可能**（削光流 + 事件驱动）
- **单模型推理 5 倍**：**很难**（模型计算量固定；除非换模型或换硬件单元）
- **内存 5 倍**：**很难**（模型权重占大头）

⚠️ **诚实声明**：5 倍是**激进目标**。若某子系统物理上做不到，**必须报告实际能达到的倍数**，不许编数字。**"用任何办法"不等于"允许造假"**。

## 四、允许的手段（按性价比排序）

### 4.1 结构性优化（可能达 5 倍）

1. **推理条件触发 / 自适应降频** ★★★
   - 不是每帧都跑 4 个模型；按需触发（如：车道保持稳定时降频）
   - 已有基础设施：`DegradeStateMachine` 三档（e2e/yolo/rule）
   - **历史证据**：推理频率塌陷（2.6~3.0 Hz）→ 说明降频机制存在但有问题，要先修塌陷

2. **多模型共享主干 / 剪枝** ★★
   - yolopx + yolo26s 都是检测网，能否共享 backbone？
   - 模型大小：`ayolom_n_int8.mlmodelc` / `yolo26s.mlmodelc`

3. **计算图融合 / CoreML 优化** ★★
   - 用 coremlcompiler 的优化选项
   - **注意**：`.all` 档位已实测最快，别动

4. **光流降分辨率 / 稀疏光流** ★★
   - 当前 `opticalflow` 6.171ms
   - 若只用于运动预测兜底，可降精度

5. **UI 空闲态：停掉无意义工作** ★★★
   - 3.9% CPU 空闲态说明有周期性任务（轮询/渲染）
   - 查：LLM 健康探活（60s）、地图瓦片预取、Timer
   - **已实测**：LLM 探活是自适应的（空闲 60s 单探）

### 4.2 内存优化

1. **模型按需加载 / 卸载**（当前 4 个模型常驻）
2. **缓存上限**（地图瓦片 LRU 已有，检查容量）
3. **日志缓冲**（dlog 已有优化：热路径 0.000ms）

### 4.3 未运行时

1. **二进制体积**（13.3MB → 可 strip/裁剪）
2. **`.build` 938M** → 可清中间产物（但不影响运行时）

## 五、必须遵守的纪律

1. **先测后改**：任何改动前先跑 `--perf-selftest` 拿基线，改后再跑，**ABBA 对照**
2. **不许重试 13 项否决清单**
3. **不许因为"看着超了"就放松阈值**（本项目已有教训）
4. **精度优先**：任何降精度的优化必须给出精度对照（如 letterbox vImage 的 9→6 回退）
5. **数字必须实测**：用 `--perf-selftest` / `--tick-profile` / `ps` 等可复现命令
6. **达不到就如实报告实际倍数**，不许编
7. **环境一致**：对比时保证负载相近（记录 `uptime` 负载值）
