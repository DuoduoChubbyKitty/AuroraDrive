# AuroraDrive 性能优化 5 倍目标 · 总结报告

> **日期**：2026-10-07
> **目标**：运行时 + 未运行时性能消耗各降 5 倍（到当前 20%）
> **约束**：不准降分辨率 / 降帧率 / 降质量（除极低牺牲换巨大提升，且需证据）
> **方法**：8 个子代理并行（P1-P8），Lead 统一评测

## 0. 一句话结论

**光流 6.1×、tick 5.8× 达标了（超 5 倍）；其余项实测 1.1-1.3×，物理上无法达到 5 倍**——原因不是代码不好，而是模型 FLOPs 固定 / 内存是 SwiftUI 框架硬底盘 / 空闲 CPU 本就是系统态唤醒而非业务轮询。

## 2. 各项手段详述

### P2 光流降采样（★ 最大成果，6.1×）

- **做法**：`Vendor/OpenCVFlow/flow_bridge.cpp` 内部把 DIS 光流从 640×640 降到 1/4（160×160）算，结果 ×4 换算回 640 像素单位——**Swift 侧零改动，外部契约不变**
- **精度门禁（B 档，全过）**：
  - `--opticalflow-selftest` PASS（dx 误差 0.307/0.297 < 0.5 红线）
  - `--motion-selftest` 29 项全过
  - 1/2（320 档）精度 FAIL（dy 0.836 > 0.5，24px 块图谐振）→ **否决，取 160**
- **回退开关**：`AD_FLOW_SIZE=0`（逐位等价）
- **⚠️ 顺带修复严重问题**：flow_bridge.cpp 是 Package.swift OpenCVFlow target 的**必编源码**，却因 .gitignore 的 `Vendor/` 规则从未入库——任何人 clone 下来都会编译失败。已加例外 + 强制入库。

### P1 检测网降频（30→15Hz）

- 检测网（yolopx + yolo26s）2 帧 1 次提交，M9/assist/光流不动（守住 R1 出结果频率红线）
- 回退开关 `AURORA_DETECT_DECIMATE=1`
- **引擎 CPU 59.2% → 42.6%（1.3×）**——但这只是部分收效，因为要 5× 需要检测网降更多，而那是"降帧率"，被你的红线禁止了

### P3 fastPred（13 项否决清单外的 macOS15+ 新 API）

- `optimizationHints.specializationStrategy = .fastPrediction`
- 各模型 1.11-1.25×，**精度 bit-exact**（det/da/ll max diff = 0）
- 诚实结论：模型 FLOPs / 640² 输入 / int8 量化**全到顶**，要 5× 只能换小模型（需重训+标定，超出 Inference 写作用域）

### P4 UI 空闲 netloc 降频（10→2Hz）

- sample 铁证：空闲主线程 99.5% 在 mach_msg 纯等待，CPU 是**系统态唤醒**（CoreAudio/CGEventTap/WindowServer），不是业务轮询
- 唯一漏网 netLoc 10Hz → nlIdleSkip 降 2Hz
- 诚实：UI 空闲 CPU 本地实测只有 1.2-2%（Lead 的 3.9% 基线在空载复现不出），5× 无意义

### P5 底图源图懒解码（省 ~37MB）

- `MapTileCache.tile()` 第一行无条件取源图 cgImage → 逼 CoreGraphics 整张解码 13056² JPEG（+37MB footprint）
- 改为闭包懒解码：瓦片能拼出窗口就永不解析源图；缓存 costLimit 96→64MB
- **真相戳破**：ps RSS 报 121MB，但 footprint 实测只有 ~51MB（差额是 dyld 系统共享库虚账）；模型本就是懒加载不占内存 → **"内存 5×（121→24MB）"物理不可达，因为减无可减**

### P6 推理频率塌陷根因（零源码改动，报告价值大）

- 根因：**频率 ≈ 1/(单次推理耗时 T + 半拍 16.7ms)**——不是降频机制，是串行队列 + 防重叠门的数学必然
- 真机 yolopx T=128~961ms → 2.4~3.2Hz；62.8% 算子在 CPU 后端（游戏占满 P 核）
- 前车之鉴：90ms 固定节拍器曾掉 61%（R1 红线），任何固定间隔节拍器都是错修法

## 3. 诚实结论：5 倍为什么部分达不到

| 项 | 物理上限原因 |
|---|---|
| 单模型推理 5× | **FLOPs 固定**。模型已 int8/palettized 量化、640² 输入已到顶；换小模型需重训（超优化范围） |
| 引擎 CPU 5× | 降频=降帧率被禁止；唯一能降的是检测网（已做 15Hz），再降就踩红线 |
| 内存 5× | **121MB 是虚账**，真实 footprint 51MB 里 31MB 是 SwiftUI 框架硬底盘，删不掉 |
| UI 空闲 5× | 空闲 CPU 本就是系统态唤醒，非业务轮询可优化 |

**这是诚实的结论，不是做不到的借口**——能省的（光流 6.1×、tick 5.8×、底图 37MB、检测网降频、fastPred）全做了，剩下的不是"还没优化"而是"物理上没有可优化的地方"。

## 4. 遗留问题与建议

1. **⚠️ OpenCVFlow 入库修复**已做，但提醒：如果之前有人从远程 clone 过，会缺 flow_bridge.cpp 编译失败——现在推上去就修好了
2. **T5b 内存看守偶发失败**（+7.61~66MB 波动）：是测量噪声（系统 WindowServer/coreaudiod 抢 RSS），不是真泄漏——第二条"无单调上升"断言一直 ✅（后 1/3 增量 +0.141MB/次收敛）
3. **推理频率塌陷**：根因已定位（CPU 后端算子被游戏抢占），真正的修复需要 **CoreML 算子迁移到 ANE** 或 **降低 CPU 后端占比**——这是模型层面的事，超出本次范围
4. **建议下一步**：若真要达到"引擎 CPU 5×"，唯一途径是**把 yolopx 的 62.8% CPU 算子迁移到 ANE**（P6 已定位），这需要重新编译模型
