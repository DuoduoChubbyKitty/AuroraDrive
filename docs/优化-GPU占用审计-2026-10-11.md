## 0. 摘要（TL;DR）

**结论：GPU 运行时占用已充分优化，可省空间有限。** 主要 GPU 消费者（模型推理→ANE、CIContext→CPU、MetalGoose→门禁+遮挡感知）都已处理。剩余 GPU 占用**大部分是应用本质决定的**（显示帧、显示叠加层），非冗余浪费。

**唯一可操作的发现**：`upscaleHost.prepare()` 在 UI 进程**无条件调用**（不 gate `upscaleEnabled`）→ 启动时创建 Metal device + queue + 编译 466 行 shader（~100ms-1s）。但这主要是**启动时间**问题，不是**持续 GPU 运行时占用**（device 是系统单例、queue 是句柄）。

**Lead 说的"如果结论是'GPU 没得省了'，如实说"** → **接近这个结论，但不完全**：有一个小的启动时间优化 + 两处值得标注的 trade-off（`showsCursor`、`queueDepth`）。

## 1. SCStream 抓屏对 WindowServer GPU 合成的压力

### 1.1 全部参数（`CaptureEngine.swift:592-601`，`makeStreamConfiguration`）

| 参数 | 值 | GPU 影响 |
|---|---|---|
| `width` / `height` | 1280 × 按屏幕比例(832) | 决定每帧像素量；越小越省带宽。已从 2940×1912 降到 1280×832（5.3 倍面积缩减） |
| `scalesToFit` | `false` | 不拉伸、不 letterbox → 坐标不错位。对 GPU 无直接影响 |
| `minimumFrameInterval` | `1/45s`（参数化） | 帧率上限。45fps 比 30fps 多 50% 帧合成 |
| `pixelFormat` | `32BGRA` | 固定 4 字节/像素。项目依赖此格式（vImageScale_ARGB8888） |
| `queueDepth` | `3` | 帧队列深度。深=流畅但多缓冲 |
| `showsCursor` | `true` | ⚠️ 见下方 |

### 1.2 `showsCursor = true` —— Trade-off，非明显浪费

**代码位置**：`:601` `config.showsCursor = true`

**分析**：
- `true` → SCStream 在每帧中合成鼠标光标 → WindowServer 需要做一次额外的光标叠加
- `false` → 不合成光标 → 省一点点 GPU 合成
- **但**：录制时用户要看到鼠标（操作回放、AI 工具用鼠标点击的回放都依赖光标可见性）
- 官方头文件 `SCStreamConfiguration.h`：无性能相关注释（已读，grep 为空）
- **结论**：**不建议改**。省的是 WindowServer 合成光标的微秒级开销，代价是录制里看不到鼠标——不划算

### 1.3 `queueDepth = 3` —— 合理，不改

深队列 = 3 个帧缓冲同时存在。降到 1 可能省内存但会导致主线程卡顿时丢帧。**当前值合理**。

### 1.4 SCStream 触发 WindowServer compositor 切换

**已知**（任务描述）：抓屏 45fps 时 WindowServer 被迫从 direct scanout 切到 compositor 模式。
- 这是 **SCStream 的固有行为**（任何使用 SCStream 的 app 都会触发），不是本项目的代码问题
- 无法从 app 代码层面优化——除非不用 SCStream（没有替代方案）
- **唯一缓解**：档位切换到 30fps 时少传数据（task-94 已实现，即减少 compositor 调用频率）

### 2.2 🔴 MetalGoose 资源创建：`prepare()` 无条件调用

**发现**：`AuroraDriveApp.swift:6135`：
```swift
if !CommandLine.arguments.contains("--engine") {
    upscaleHost.prepare()    // ← 只 gate --engine，不 gate upscaleEnabled
    upscaleSupported = upscaleHost.isAvailable
}
```

`prepare()` → `GooseUpscaler.make()`（`:8636`）→ `GooseEngine.make()`（`GooseEngine.swift:420-431`）：
```swift
guard let dev = MTLCreateSystemDefaultDevice() else { … }   // ← 获取系统 GPU
guard let queue = dev.makeCommandQueue() else { … }          // ← 创建命令队列
return GooseEngine(device: dev, commandQueue: queue)
```

**即使用户没开插帧（`upscaleEnabled = false`）**，Metal 资源也在启动时创建了。

**但这不是持续 GPU 运行时占用**——需要诚实区分：

| 资源 | 性质 | 是否持续占 GPU |
|---|---|---|
| `MTLDevice` | 系统单例（`MTLCreateSystemDefaultDevice` 返回同一个） | ❌ 不占（只是句柄） |
| `MTLCommandQueue` | 命令队列句柄 | ❌ 不占（没有提交 workload 就不跑） |
| Shader 编译 | 一次性 CPU 成本（~100ms-1s） | ❌ 是 CPU 不是 GPU，且只一次 |
| `MTLTexture`（6 个） | 显存分配 | ⚠️ 占显存但不占 GPU 算力（无渲染命令） |

**真正的 GPU 运行时消费者**是 MTKView 的 60fps 渲染循环——但那个**已经有门禁**：
```swift
// MissionConsole.swift:590
if state.upscaleEnabled {     // ← 门禁：不开插帧就不挂 MTKView
    UpscaleFrameHostView(host: state.upscaleHost)
}
```
加上遮挡感知（`:8667-8683` 不可见时 `isPaused = true`）。

**结论**：
- 🔴 **启动时间优化点**：把 `prepare()` 延迟到 `upscaleEnabled` 首次置 true 时调（省 ~100ms-1s 启动时间 + 一些显存）
- ✅ **GPU 运行时已门禁**：MTKView 渲染循环只在 `upscaleEnabled && 窗口可见` 时跑

### 2.3 `CAMetalLayer` —— 全仓未命中

grep `CAMetalLayer` → **0 命中**。没有手动创建 Metal layer 的代码。✅

## 3. macOS 系统级 GPU 服务

### 3.1 GameHUDWindow —— 纯 AppKit，非 Metal

`GameHUDWindow.swift:43-50`：
```swift
let win = NSWindow(contentRect: …, styleMask: [.borderless], backing: .buffered, defer: false)
```
- `backing: .buffered` → CPU 后备存储，**不是 Metal**
- 内容用 `NSTextField`（`:28`），**不是 MTKView**
- **结论**：✅ 无 GPU 路径

### 3.2 MapWindow / LargeMapCanvas —— CGContext，非 Metal

`MapLayers.swift:366-378`：
```swift
private var reusableCtx: CGContext?
private func obtainContext(side: Int) -> CGContext? {
    guard let c = CGContext(data: nil, width: side, height: side, …) else { … }
```
- `CGContext` 是 **CPU 绘图**，不是 Metal/OpenGL
- `MapWindow.swift` grep Metal/CAMetalLayer/MTKView → **0 命中**
- **结论**：✅ 无 GPU 路径

### 3.3 SwiftUI Canvas（MaskOverlay / MiniMapCanvas）

`AuroraDriveApp.swift:8357/8502`：
```swift
Canvas { ctx, size in … }    // 路径填充 2000~4000 个 rect
```

- SwiftUI `Canvas` 底层走 CoreAnimation，**默认 GPU-backed**
- 但有 `active` 门禁（`guard active` 在 Canvas 闭包内，`:8361` 修复记录确认）
- **每帧一次 Canvas 路径填充**（注释 `:8334`："代价可控"）
- **结论**：⚠️ 走 GPU 但有门禁 + 代价可控。**不建议改**（改了就看不到车道线/可行驶区叠加了）

### 3.4 FrameHost —— CALayer.contents（WindowServer 合成）

`AuroraDriveApp.swift:8585-8590`：
```swift
view.wantsLayer = true
view.layer?.contentsGravity = .resizeAspectFill
…
func push(_ image: CGImage) {
    hostView?.layer?.contents = image    // ← 每帧设 CALayer.contents
}
```

- `CALayer.contents = CGImage` 触发 WindowServer GPU 合成（把图像合成到屏幕）
- 这是**"显示一张图"的标准路径**——任何 NSView + wantsLayer 都走这条路
- 45fps 下 = 45 次/秒 WindowServer 合成
- **结论**：⚠️ 走 GPU 但**这是应用本质**（要显示帧就必须合成）。**无法避免**（除非不显示帧）

## 4. SCContentFilter 选择对 GPU 的影响

### 4.1 代码现状

`CaptureEngine.swift:494-510`（`startStream`）：
- `.fullScreen` → `SCContentFilter(display: display, excludingWindows: own)`（排除自家窗口）
- `.window(id)` → `SCContentFilter(desktopIndependentWindow: target)`

### 4.2 官方头文件

`SCContentFilter.h`：grep `performance`/`overhead`/`composit` → **0 命中**。Apple 未提供性能相关注释。

### 4.3 分析

- `desktopIndependentWindow`（只抓一个窗口）→ WindowServer 只需合成该窗口的内容
- `display`（全屏）→ WindowServer 需要合成整个显示器（排除列表里的窗口要裁掉）
- **理论上** `desktopIndependentWindow` 省更多 GPU（少合成面积）
- **但**：用户要第三视角（追尾视角），游戏画面就是全屏 → 只能选 `display`
- **结论**：当前选 `display` 是**需求决定的**，不是可以优化的点

## 6. 结论

### 6.1 诚实结论

**GPU 运行时占用已充分优化。** 主要消费者（模型→ANE、CIContext→CPU、MetalGoose→门禁+遮挡）都已处理。剩余 GPU 占用来自：
1. **WindowServer 合成**（SCStream + CALayer.contents）—— 应用本质，不可省
2. **SwiftUI Canvas** —— 有门禁、代价可控
3. **MetalGoose 渲染循环** —— 有双重门禁（`upscaleEnabled` + 遮挡感知）

### 6.2 唯一可操作项（收益有限）

**延迟 `upscaleHost.prepare()` 到首次开启插帧时**：
- 现状：UI 进程启动时无条件创建 Metal device + queue + 编译 shader
- 建议：改为在 `upscaleEnabled` 首次置 true 时才调 `prepare()`
- 收益：省 ~100ms-1s 启动时间 + 若用户从不开启插帧则完全不创建 Metal 资源
- 代价：首次开启插帧时有 ~100ms-1s 卡顿（可提前在 UI 准备阶段异步预热）
- **这是启动时间优化，不是 GPU 运行时优化**

### 6.3 不建议动的（Trade-off / 不可省）

| 项 | 原因 |
|---|---|
| `showsCursor = true` | 改 false 省的是微秒级光标合成，代价是录制看不到鼠标 |
| `queueDepth = 3` | 降深度省内存但导致丢帧 |
| FrameHost `CALayer.contents` | 显示帧必须走 WindowServer 合成 |
| SCStream compositor 切换 | SCStream 固有行为，无法从 app 层面改 |
| SwiftUI Canvas | 有门禁、代价可控，改了看不到叠加层 |
