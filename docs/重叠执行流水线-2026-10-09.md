## 0. 一句话结论（先说最反直觉的那条）

> **重叠执行流水线不建议实施 —— 实测它不赚，反而可能亏。**
> **真正该做的是「特征缓存 + 拆分」（S1 已落地）：p95 = 5.99ms，余量 2.67×，已达标。**
>
> 重叠方案在 5 次复跑中收益为 **-22.8% / +33.1% / +0.3% / +17.7% / +4.3% / -6.2%**，
> 均值 ≈ 0，且**代价确定**：端到端输出延迟 **+1 帧 = +33.3ms**。
> 用"确定的 33ms 延迟"换"均值为 0 的临界路径收益"，对实时驾驶控制环是**坏账**。

## 2. 机理：为什么特征缓存是「数学恒等」而不是「近似」

### 2.1 关键代码事实

```
src/model_v2.py:1416        img_feat = self.image_encoder(image)
src/model_v2.py:440-521     ImageEncoder = Conv/BN/ReLU/RepVGG + AdaptiveAvgPool2d + flatten
```

`ImageEncoder` 是**纯卷积 + 全局平均池化**：
- **无** BatchNorm 的 batch 统计（`eval()` 态用 running stats，与 batch 无关）
- **无** LayerNorm、**无** attention、**无** 任何跨样本算子

⟹ batch 维**完全独立**，故对任意帧 `f_i`：

```
encode(cat([f_1..f_8]))  ≡  cat([encode(f_1)..encode(f_8)])
```

这是**恒等式**，唯一差异来源是浮点累加顺序（fp32 舍入），量级 ~1e-7。

### 2.2 与「8 帧窗口」语义的关系（重要：不影响时序）

时序信息由 `TemporalEncoder`（GRU，`src/temporal.py:229`）处理，它吃的是
**编码后的 8×256 特征序列**，而不是原图。所以缓存特征**不改变**喂给 GRU 的输入内容
—— GRU 看到的仍是"最近 8 帧的特征，最老在前"。**时序能力完整保留。**

> ⚠️ 这正是任务书里 `V2InputContract` 注释（`InferenceEngineV2.swift:122-132`）记载的
> 「最初设想 `history_feats [1,8,256]`，但发现鸡生蛋：256 维是 ImageEncoder 中间层输出，
> CoreML 静态图不暴露中间层 → Swift 侧算不出来」。
> **本方案的解法：不取中间层，而是把 ImageEncoder 单独导出成一个模型**
> （`m9_v2_enc`），它的**输出**就是那 256 维 → 鸡生蛋问题消解。

## 3. 实测 A/C：特征缓存数值等价性（两层验证）

### 3.1 验证一：PyTorch fp32（`tools/exp_pipeline_equiv.py`）

方法：把 `model.image_encoder` 临时替换为"返回预计算特征"的桩，保证除 `img_feat` 来源外
**代码路径完全一致**（seq_mode 判定、GRU、refiner、fusion、三个辅助头全不变）。

```
── 训练态(RepVGG多分支) ──  权重: missing=96 unexpected=0
  ① 图像特征 [8,256]   maxdiff = 0.000e+00
  ② 端到端 6 输出      maxdiff = 0.000e+00
       steer/ throttle/ brake/ confidence/ risk/ car_heading  全部 diff=0.000e+00
── 部署态(reparameterized) ──
  ① 图像特征 [8,256]   maxdiff = 0.000e+00
  ② 端到端 6 输出      maxdiff = 0.000e+00
  ⟹ 判定：✅ 数值等价（判据 maxdiff < 1e-3）
```

### 3.2 验证二：**真实 CoreML 部署产物**（`tools/exp_pipeline_coreml_equiv.py`）

这一层更硬：E1/C8/F8 是**三个独立 palette INT8 量化**的模型，
量化误差可能让"拆分"与"不拆"产生差异。在真实产物上比对：

```
  输出                      F8（当前）        E1→C8（新）        diff  判定
  steer               0.98779297      0.98779297   0.000e+00  ✓
  throttle            0.00000000      0.00000000   0.000e+00  ✓
  brake               0.00000411      0.00000411   0.000e+00  ✓
  confidence          0.00000000      0.00000000   0.000e+00  ✓
  risk                0.00000000      0.00000000   0.000e+00  ✓
  car_heading        -1.18847656     -1.18847656   0.000e+00  ✓

  ⟹ 最大偏差 0.000e+00  vs 判据 1e-3  →  ✅ 拆分等价（部署产物级验证通过）
```

**结论：maxdiff = 0，远优于 Lead 要求的 <1e-3。** 这是严格恒等，不是"够用的近似"。

## 4. 实测 B：重叠执行流水线到底赚不赚（**核心裁决**）

### 4.1 实验设计（`tools/exp_pipeline_overlap.swift`）

同一批模型、同一台机器、同一进程内**交错测量**三种模式：

| 模式 | 语义 | 临界路径 | 输出延迟 |
|---|---|---|---|
| `serial-tick` | S1 现状：同队列 `enc(帧N)` → `ctl(帧N)` | `enc + ctl` | 0 帧 |
| `overlap-pipe` | 双队列并行 `enc(帧N)` ∥ `ctl(帧N-1)` | `max(enc, ctl)` | **+1 帧（+33.3ms）** |

### 4.2 实测结果（6 次独立复跑）

| 复跑 | serial p95 | overlap p95 | 收益 |
|---|---:|---:|---:|
| 1 | 14.71 | 18.08 | **−22.8%** |
| 2 | 10.71 | 7.16 | +33.1% |
| 3 | 7.31 | 7.29 | +0.3% |
| 4 | 7.44 | 6.12 | +17.7% |
| 5 | 16.51 | 15.80 | +4.3% |
| 6 | 12.33 | 13.09 | −6.2% |

**收益在 −22.8% ~ +33.1% 之间乱跳，均值 ≈ 0。**

### 4.3 为什么重叠不赚 —— 机理

```
MLComputePlan 逐算子派发（exp_exec_bench --plan 1）：
  m9_v2_enc: {ane: 30,  nil: 96}          ANE cost 100.0%
  m9_v2_ctl: {ane: 421, cpu: 53, nil: 335} ANE cost 88.9% / CPU 11.1%
```

**两个模型都在 ANE 上跑。** ANE 是**单一硬件单元**，两个并发推理请求只是在
**抢同一个单元的时间片** —— 总吞吐不变，反而多了两次调度/同步开销。

> 重叠流水线的经典收益前提是「两段跑在**不同**硬件资源上」（如 CPU ∥ GPU）。
> 本项目不满足该前提，故"用并发换延迟"这条路**在硬件层面就不成立**。

### 4.4 代价是确定的，收益是不确定的

即使重叠在最好情况下赚 33%，它也要付：

- **端到端输出延迟 +1 帧 = +33.3ms**（30Hz）。这对驾驶控制环是**安全性代价**：
  从"看到障碍"到"输出控制量"的闭环多了一整帧。
- 代码复杂度：双缓冲、跨队列同步、帧序错位、`generation` 防过期结果要重做一遍。

**在串行 p95 已达 5.99ms（余量 2.67×）的前提下，这笔交易没有任何理由做。**

## 5. 真实成本账（Swift 原生测量，非 Python 代理）

> ⚠️ **测量环境警告**：测试期间本机 load average 在 **12 ~ 53** 之间波动，
> 有 5 个其它 agent 的 Python 进程各占 ~90% CPU。**绝对 ms 不可比**，
> 故本报告一律采用：① Swift 原生路径（无 numpy 转换开销）
> ② min-of-N（受争抢影响最小的统计量）③ 同进程同时刻的**比值**。
> **所有 p95 达标判定建议在空载机器上复测确认。**

### 5.1 分解（`tools/exp_exec_bench.swift`，Swift 原生）

| 组件 | ANE p50 | ANE p95 | CPU p50 | ANE cost% | 算子派发 |
|---|---:|---:|---:|---:|---|
| `m9_v2_enc`（1 帧编码） | **0.59** | 0.95 | 6.90 | **100.0%** | `{ane:30, nil:96}` |
| `m9_v2_ctl`（8 帧特征主控） | **1.60** | 5.04 | 2.51 | **88.9%** | `{ane:421, cpu:53, nil:335}` |
| **串联（每 tick）** | **2.19** | **5.99** | 9.41 | — | — |

> 末次复核（同一命令，120 样本，本机 load 仍偏高）：
> `enc` p50 0.88 / p95 2.68（cost% ane 100.0）；`ctl` p50 2.18 / p95 7.62（cost% ane 88.9）。
> **ANE 派发比例两次一致**，故结论（两个模型都上 ANE）稳固；
> 绝对 ms 的波动来自本机争抢，非模型差异。

### 5.2 引擎侧每帧开销（`tools/exp_preprocess_bench.swift`，逐位复刻引擎算法）

| 项目 | min | p50 | p95 |
|---|---:|---:|---:|
| `preprocessImage`（CGImage→CHW 180×320） | 0.187 | **0.208** | 0.317 |
| `featSeq` 装配 [8×256] | 0.000 | 0.000 | 0.000 |
| `lane` 装配 [160×160] | 0.005 | 0.005 | 0.007 |
| **合计** | 0.193 | **0.225** | 0.402 |

### 5.3 每帧总成本

```
p50: 2.19 (CoreML) + 0.225 (引擎) = 2.42 ms
p95: 5.99 (CoreML) + 0.402 (引擎) = 6.39 ms
```

**对 16ms 红线：p95 余量 2.50×　|　对 33ms 帧预算：余量 5.2×**

### 5.4 为什么不是 8×（Amdahl 账）

任务书预期"8× 提速"。实际端到端只拿到 **3.4~4.3×**，原因：

| 项 | 拆分前 | 拆分后 | 说明 |
|---|---|---|---|
| 每 tick 编码帧数 | 8 帧（batch=8 一次） | **1 帧** | ✅ 这才是 8× 的那部分 |
| 时序 GRU | 8 步 | **8 步（不变）** | ❌ 不可省，见 §6 |
| refiner | 12 步 + 4 步 MoE | **12 步 + 4 步 MoE（不变）** | ❌ 红线，不动 |
| 其他三编码器 | 有 | 不变 | — |

**编码只是总成本的一部分**，且拆分后 `ctl` 内部仍要跑完整的 8 步 GRU + 12 步 refiner。
故端到端加速必然 < 8×。**这是 Amdahl 定律的正常结果，不是实现缺陷。**

## 6. 被否决的方案：GRU 隐状态续算（诚实留痕）

### 6.1 曾经（错误地）以为这是"免费提速"

初稿推演：「GRU 是递推的 ⟹ 缓存隐状态 h，每 tick 只跑 1 步 ⟹ 零代价 O(N)→O(1)」。

### 6.2 实测证明这是**语义变更，不是等价优化**（`tools/exp_pipeline_gru_state.py`）

```
  ① 续算 vs 窗口重算（核心对照）
      窗口 GRU(x_1..x_8) = [-0.7899, -1.3875, -0.6507, -0.6503]
      续算 GRU(x_0..x_8) = [-0.7810, -1.3783, -0.6444, -0.6504]
      maxdiff = 4.613e-02   ⟹ ❌ 不等价
  ② 方法自检：手工 8 步（从零）vs te() 封装同窗口 → maxdiff = 0.000e+00 ✅（结论可信）
```

> 复跑一次得 maxdiff = 3.898e-02（特征量级 1.80）——**两次都在 4e-2 量级**，
> 远超 1e-3 判据。结论稳固：**不是等价优化**。

**根因**：现有语义是**滑动窗口**——每 tick 都拿最近 8 帧、**从 h=0 重跑 8 步**
（`src/model_v2.py:1450` `te(img_feat.unsqueeze(0), None)`，无状态传入）。
而续算带着上一 tick 的 h（含更早的帧）→ 得到 `GRU(x_0..x_8)`，窗口要的是 `GRU(x_1..x_8)`。
**两者是不同的函数复合。**

### 6.3 结论：精确的 O(1) 滑动窗口 GRU **不存在**

GRU 门控是非线性复合（`h_t = (1-z)⊙h_{t-1} + z⊙tanh(...)`），
**无法从旧状态"减去"最老帧的贡献** ⟹ 窗口语义本质上是 O(N)。

> **这条从方案里剔除**，以免 Lead 按错误前提排期。
> （若要无界历史语义，那是**重训 + 重新验收**的事，不属于性能优化。）

## 8. 什么条件下才该做重叠流水线（给 Lead 的判据）

本方案不是"永远错"，而是"**在当前硬件与预算下不划算**"。若以下条件**任一**成立，应重新评估：

1. **两段落在不同硬件上**：例如把 `enc` 强制 CPU、`ctl` 留 ANE
   （用 `MLModelConfiguration.computeUnits` 分别设置），此时并发才可能真并行。
   ⚠️ 但 `enc` 的 CPU p50 = 6.90ms，远慢于 ANE 的 0.59ms → **大概率仍不划算**，须实测。
2. **帧预算收紧到 p95 > 16ms**：若未来模型变大导致串行超标，重叠可作为最后手段。
3. **吞吐成为瓶颈**（而非延迟）：例如要同时驱动多路视频流。**当前是单路 30Hz，不适用。**

**当前建议：不做。** 串行拆分 p95 5.99ms 已满足红线，余量 2.50×。

## 9. 方法论留痕：本小姐本次踩的两个坑（如实记录）

### 坑 1：用 coremltools Python 的 A/C 比值判定 ANE，得出**错误结论**

- **错误做法**：用 `ct.models.MLModel(p, compute_units=CPU_AND_NE/CPU_ONLY)` 测 `min` 比值，
  判据 `A/C < 0.85 = ANE 生效`。
- **错误结论**：判定 `m9_v2_ctl` 的 A/C = 1.02~1.21 → "ANE 编译失败"，
  并据此给 Lead 发了一条**错误的中途报告**（已发更正）。
- **错因**：Python 侧每次 `predict()` 都要 numpy→MLMultiArray 转换，且无法设置
  `specializationStrategy` / `allowLowPrecisionAccumulationOnGPU`。
  对 1ms 级小模型，**固定开销主导**，比值失去意义。
  （`tools/exp_exec_bench.swift:4-9` 恰好记载了这个坑，本小姐没先读它。）
- **正确做法**：Swift 原生 + `MLComputePlan.deviceUsage` **逐算子派发统计** ——
  这是"ANE 到底用没用上"的**权威判据**。
  实测 `ctl` = `{ane:421, cpu:53}`，ANE cost **88.9%** → **ANE 是生效的**。

> **教训**：小模型的性能判定**必须看算子派发，不能看比值**。
> 比值会被固定开销淹没；派发统计才是事实。

### 坑 2：把"GRU 递推"误推为"可免费 O(N)→O(1)"（§6）

- **错因**：只看到"GRU 是递推的"，没核对现有语义是**滑动窗口 + 每 tick 从零重跑**。
- **纠正**：写实验实测 → maxdiff 4.6e-2 → **不等价**，从方案里剔除。

## 11. 给 Lead 的三句话

1. **重叠流水线不做** —— 实测收益均值≈0（两段都在 ANE 上，并发只抢同一单元），
   代价是 +33ms 输出延迟。**用确定的延迟换不确定的收益，是坏账。**
2. **特征缓存已由 S1 落地且经本小姐独立验证为严格恒等**（部署产物级 maxdiff = 0.000e+00）。
   每帧总成本 p95 = **6.39ms**（CoreML 5.99 + 引擎 0.40），对 16ms 红线余量 **2.50×**。
3. **判定 ANE 必须用 `MLComputePlan` 算子派发统计，不能用 Python 的 A/C 比值** ——
   本小姐在此踩坑并误报过一次，已更正。另：本机 load 12~53 波动大，
   **所有 p95 达标判定建议在空载机器上复测确认。**
