## 2. 必答问题 ②：第三视角训练需要重录吗？现有数据能用吗？

### 结论：**必须重录。现有 129 帧一帧都不能用。**

### 理由 1 — 域错误（最致命）

现有帧内容是 AuroraDrive 的 UI 界面（§1 证据 A/B/C）。第三视角模型要学的是「游戏世界 + 追尾相机下的道路/车道线/车辆」，而现有数据里连一条真实车道线都没有。这不是「视角不对」，是**内容根本不是同一个东西**。

### 理由 2 — 量级差三个数量级

| | 现有 | 参考量级 |
|---|---|---|
| 帧数 | 129 帧（唯一 91） | 见 §4.2 |
| 时长 | 6.14 秒 | — |

对比：`EgoBoxFilter.swift:19` 记录的实测分析用了 **10000 帧真游戏画面**（连续 600 帧时序跟踪定自车轨迹）。现有数据连那个规模的 **1.3%** 都不到。

### 理由 3 — 训练端硬编码只取 FPV，录了 TPV 也不会被用

`src/train_game_assist.py:364-368`：

```python
all_clips = _list_clips(_ROOT / "data" / "raw_clips")
fpv_clips = [c for c in all_clips if _clip_view(c) == "FPV"]
if not fpv_clips:
    print("[FPV] 没有 FPV 训练数据，跳过 FPV 控制模型训练")
    return None
```

`src/train_game_assist.py:376`：

```python
    view_filter="FPV",
```

**训练脚本写死了只要 `FPV` 的 clip。** 即使录出 `view.txt = TPV` 的数据，也会在 `:365` 被整个过滤掉，`:367` 直接跳过训练。

> ⚠️ 本任务禁止改代码，故此处只做**事实标注**，不提供改动。落地第三视角训练**必须**动这一处。

### 理由 4 — 磁盘上限会静默删掉新录的数据

`Sources/AuroraDrive/Capture/RecordEngine.swift:41`：

```swift
let maxClipsPerKind = 10
```

`RecordEngine.swift:260-272` 的 `pruneOldClips` 在**每次录制启动时**删除最旧的 clip，只保留最近 10 个。想靠内置录制器攒数据，**必须先调大这个常量**，否则录到第 11 段时第一段就被删了。

### 理由 5 — 即使内容对了，控制量标签也缺一半

`src/mono_dataset.py:77-83` 的格式判定：

```python

    h = [c.strip() for c in header]
    if "speed_kmh" in h and "curvature" in h:
        return "v2_new"
    return "v1_old"
```

而现有 `controls.csv` 表头是 `t_sec,frame,steer,throttle,brake` → 判为 `v1_old` → `src/mono_dataset.py:119-120` 把 `vehicle_state` **填零向量**：

```python
else:
    # 旧格式：无车辆状态，零向量填充（模型仍可从图像学习）
    row["vehicle_state"] = np.zeros(6, dtype=np.float32)
```

这与交接文档记录的 M9 弃用根因一致（`docs/文档库/神秘乱七八糟的文档/交接文档-64K手写版.md:904`）：

> **致命缺陷（换模型的根因）**：6 维里 5 维是占位 0，只有车速是真信号——模型本质上看不见路

**采集 TPV 数据时若同时想修这个问题，需要录制端产出含 `speed_kmh`/`curvature`/`heading` 的 v2 格式 CSV。** 现有两个录制器都不写这些列（见 §4.4）。

## 3. 必答问题 ③：`EgoBoxFilter` 怎么工作？

**文件**：`Sources/AuroraDrive/Agent/EgoBoxFilter.swift`（118 行）

### 3.1 要解决的问题

第三视角下，模型会把**玩家自己的车**当成障碍框标出来。这个框进入决策层会造成**实际危害**（`EgoBoxFilter.swift:8-12`）：

> ego 框 + 前车框被几何兜底判为「框叠加 = 碰撞」，输出 brake 0.8 → 而本游戏 brake 就是 S 键兼倒车，于是托管状态不停给用户刹车/倒车

历史事故记录见 `AuroraDriveApp.swift:5496-5498` 与 §5.5 删除记录。

### 3.2 判据：**只看面积，不看位置**（这是核心设计）

`EgoBoxFilter.swift:84-96`：

```swift
static func normalizedArea(of d: Detection) -> Double? {
    let a = d.width * d.height
    return a.isFinite && a >= 0 ? a : nil
}

func isEgo(_ d: Detection) -> Bool {
    guard isEnabled else { return false }
    guard let a = Self.normalizedArea(of: d) else { return false }
    return a > areaThreshold
}
```

**为什么不用位置**（`EgoBoxFilter.swift:19-28` 实测对照表）：

| 规则 | 屏蔽自车成功率 | 误伤真车/帧 |
|---|---|---|
| 面积 > 2% | 98.0% | 0.08 |
| 面积 > 3% | 97.8% | 0.05 |
| **仅位置（中心带 + 下方）** | **93.2%** | 0.06 |
| 面积 > 3% 且 位置 | 93.0% | 0.03 |

> **加位置条件反而把召回从 98% 拉到 93%** —— 因为镜头一动自车就不在「中心下方」了。

用户明确说过镜头会到处跑（`EgoBoxFilter.swift:18`）：「官方为了帅车可能会到处跑……甚至可以到最远端」。

### 3.3 阈值：4.0%（实测得出，非拍脑袋）

`EgoBoxFilter.swift:63`：

```swift
static let defaultAreaThreshold: Double = 0.04
```

实测依据（`EgoBoxFilter.swift:30-39`）：

- **自车识别方法**：连续 **600 帧时序跟踪**定自车轨迹 → 覆盖率 **88.8%**，第二名真车仅 **6.2%**，差 **14 倍**（自车是唯一「永远在画面里」的目标，不受镜头摇摆影响）
- **面积量测**：

| 目标 | 中位 | p5 | min |
|---|---|---|---|
| 自车框 | **5.57%** | 4.71% | **4.25%** |
| 真车框 | 0.17% | — | — |

两者中位相差 **33 倍**。阈值取 **4.0%**（自车下界 4.25% 再留 0.25pp 余量）→ 自车 **100%** 被屏蔽，误伤真车 **0.112 框/帧**。

**量测脚本**（可复现）：
- `tools/ayolom/measure_ego_area.py` — 面积占比实测
- `tools/ayolom/measure_ego_identity.py` — 时序刚性检验判定「哪个框是自车」

> `measure_ego_identity.py` 文件头记录了一次方法论纠错：最初把「每帧面积最大的框」当自车去评估规则，属**循环论证**，被用户当场指出。改用「覆盖率接近 100% 且抖动接近 0」的时序判据。

### 3.4 fail-open（有意为之）

`EgoBoxFilter.swift:91-95`：框面积算不出来（NaN / Inf / 负 / 零尺寸）→ **保留**，不屏蔽。

> 宁可多留一个框，不可因异常值把真车吃掉。

### 3.5 作用范围：**只作用于决策层，UI 照画全部框**

这是本项目一个刻意的双访问器设计。

| 访问器 | 行号 | 是否屏蔽自车 | 用途 |
|---|---|---|---|
| `displayDetections` | `AuroraDriveApp.swift:4177` | ❌ 不屏蔽 | **UI 画框**（用户要求看到全部框） |
| `effectiveDetections` | `AuroraDriveApp.swift:4204` | ✅ 屏蔽 | **决策层**（规则控制、运动预测、框计数） |

`AuroraDriveApp.swift:4204-4206`：

```swift
var effectiveDetections: [Detection] {
    egoBoxFilter.filter(displayDetections)
}
```

过滤器实例构造于 `AuroraDriveApp.swift:5500`：

```swift
let egoBoxFilter = EgoBoxFilter.configured
```

**下游全部自动生效**（`AuroraDriveApp.swift:4199-4201` 注释）：

> ⚠️ 下游**名字一个都没改**（`ruleController.decide`、`motionPredictor.ingest`、`boxCount`、`AutoRoadCondition` 全部照旧读本属性）—— 屏蔽对它们自动生效。

**明确不动**（`AuroraDriveApp.swift:4202-4203`）：`effectiveDetections.count → AutoRoadCondition → forceRuleMode` 那条链一个字不改，它的 70/20/10 阈值是防「游戏 bug 刷出 699000 个假框」的护栏，与自车框无关（自车每帧最多 1 个框）。

### 3.6 开关

`EgoBoxFilter.swift:70`：

```swift

```

- `AURORA_EGO_AREA=0.03` → 调阈值
- `AURORA_EGO_AREA=0` → **关闭屏蔽**（一键回滚）
- 默认 `0.04`，解析与校验收敛在 `Sources/AuroraDrive/Core/AuroraFlags.swift:219-227`（键名、默认值、`isFinite`/非负校验）

### 3.7 与训练数据的关系（**重要**）

`EgoBoxFilter` 是**运行时决策层**的补丁，**不是**数据层的修复。

它解决的是「模型输出自车框 → 决策被污染」。它**不解决**「模型为什么会输出自车框」——那需要在**训练数据**层面显式 mask 掉自车区域（`EgoBoxFilter.swift:8-9` 用户原话：「无论是什么模型，他都会标注自己车辆，我们是救不了这个办法」）。

历史调研结论（`.workbuddy/memory/2026-09-11.md`，TPV 专题）：

> **必须显式 mask 掉自车区域**（TPV 画面里有车尾/整车）。不屏蔽会同时坏三个任务：① 可行驶区域被自车挖洞 ② 自车被检测成「车辆」（把自己当障碍物）③ 车道线在自车附近断裂。**这是视角特性决定的必要预处理设计，不是补丁。**

**即：第三视角数据集的标注规范里，自车区域必须作为 mask 处理，而不是留给运行时过滤。**

#### 数据量建议

> ⚠️ **诚实标注**：项目内**没有**第三视角数据量的既定标准。以下是**推算**，非既有规范。

**推算依据**：

| 依据 | 出处 |
|---|---|
| 既有实测分析规模为 10000 帧真游戏画面 | `EgoBoxFilter.swift:19` |
| 自车轨迹判定需连续 600 帧 | `EgoBoxFilter.swift:31` |
| 单帧 640×360 JPEG ≈ 33–72 KB（实测） | `ls -la data/raw_clips/*/frames/` |
| 录制器产能：10 fps | `aurora_recorder.c:37` |
| 内置录制器产能：24 fps | `RecordEngine.swift:35` |
| 磁盘估算：30fps 约 230 GB/天 | `RecordEngine.swift:38` |

**建议量级（推算，未验证）**：

- **单场景起步**：≥ 600 帧连续（≈ 1 分钟 @ 10fps）—— 与自车轨迹判定的时序要求对齐
- **总量起步**：≥ 10000 帧（≈ 17 分钟 @ 10fps）—— 与既有实测分析规模对齐
- **磁盘占用估算**：10000 帧 × ~50 KB ≈ **500 MB**（按实测帧大小中位数）
- **若要训控制模型**：量级应显著高于 10000 帧；具体需求**未验证**，需先跑通一轮端到端再定

> 注意：10000 帧是 `EgoBoxFilter` 做**自车框统计**的规模，不是「训练一个驾驶模型」的规模。两者不可混用。真正要多少训练数据，**本项目尚无依据，标为未验证**。

### 4.3 什么场景

项目已有 8 类场景分类法可直接沿用（来源：`data/validation_clips/` 目录结构 + `_sources.csv` 的 `scenario` 列）：

| 场景 | 目录 | 现有帧数（参考） | 第三视角采集要点 |
|---|---|---|---|
| 白天城市 | `day_city` | 15 | 基准场景，车道线最清晰 |
| 白天高速 | `day_highway` | 22 | 高速车道线收敛，TPV 下近端被自车遮挡 |
| 夜间 | `night` | 16 | 低照度，车道线对比度低 |
| 雨天湿滑 | `rain_wet` | 14 | 路面反光、车道线被水膜干扰 |
| 隧道 | `tunnel` | 42 | 明暗剧变，隧道灯带 |
| 弯道 | `curve` | 18 | **TPV 下最难**，透视畸变最剧烈 |
| 拥堵 | `congestion` | 24 | 多车密集，检测框重叠 |
| 逆光低对比 | `backlight_lowcontrast` | 18 | 阳光眩光 |

> 现有帧数来自 `data/validation_clips/`，是**第一视角真实道路素材**（`_sources.csv` 的 `viewpoint` 列标为「车头视角」，来源为 Wikimedia Commons 的 CC 授权行车视频）。**它们是 FPV 数据，不是 TPV，不能直接当 TPV 训练集**，但场景分类法可以照搬。

**TPV 专属场景要求**（源自 `.workbuddy/memory/2026-09-11.md` TPV 专题，**属历史调研结论，本次未复验**）：

> 三个任务在 TPV 下难度变化：
> - **可行驶区域分割 → 变简单**（相机更高更广、路面连续、遮挡少）
> - **车辆检测 → 中等**（尺度分布变了；画面里有自车需屏蔽）
> - **车道线检测 → 变得最难，是决定性瓶颈**（相机后置高位 → 近端被自车遮挡、远端极度收敛、细长结构被压缩、弯道透视畸变更剧烈）

**因此采集应向弯道、车道线密集场景倾斜。**

### 4.4 采集时必须一并解决的三个数据格式问题

#### 问题 1：控制量标签缺 `vehicle_state`

- `src/mono_dataset.py:82`：只有表头同时含 `speed_kmh` **和** `curvature` 才判为 `v2_new`
- 现有 `RecordEngine` 写 5 列（`RecordEngine.swift:173`）：`t_sec,frame,steer,throttle,brake`
- `aurora_recorder` 写 7 列（`aurora_recorder.c:16`）：`t_sec,frame,steer,throttle,brake,handbrake,strong_brake`
- **两者都不含 `speed_kmh`/`curvature`/`heading`** → 均判为 `v1_old` → `vehicle_state` 填零向量（`mono_dataset.py:118-120`）

**后果**：模型 6 维输入里 5 维是占位 0（交接文档 `:904` 记录的 M9 弃用根因）。

**若要用 `v2_new` 格式**，需要录制端产出含 `speed_kmh, curvature, heading, speed_limit` 的 CSV。项目内 `speed_kmh` 的来源是 `SpeedOCRReader`（速度表 OCR），但**现有录制链路没有把它接进 controls.csv**。

> **未验证**：把 OCR 速度接进录制 CSV 的具体方案，本次未调研。

#### 问题 2：`view.txt` 白名单校验缺失

`.workbuddy/memory/2026-07-13.md:1715` 记录：

> **P4｜`--view` 无白名单校验**：任意字符串直写 `view.txt`；若拼错（如 `tpv` 小写），训练端 `view_filter` 过滤时会静默漏掉整个 clip。

`src/mono_dataset.py:59-63` 确实只接受大写：

```python
vt = clip_dir / "view.txt"
if vt.exists():
    raw = vt.read_text().strip().upper()
    if raw in ("TPV", "FPV", "MENU"):
        return raw
```

> 注意 `:61` 有 `.upper()`，所以小写 `tpv` 其实**能**被识别。但 `aurora_recorder.c:245` 是原样写入 `g_view`，若传入非法值（如 `TPVV`），`_clip_view` 返回 `None` → 该 clip 静默漏掉。
>
> **采集时务必用大写 `TPV`。**

#### 问题 3：目录名与 `perspective` 字段

`RecordEngine.swift:227-228` 从目录名首段取 `perspective`，因目录名是 `clip_<ts>` → `meta.json` 里恒为 `"clip"`（实测确认）。**不要依赖 `meta.json.perspective` 做视角判据，以 `view.txt` 为准。**
