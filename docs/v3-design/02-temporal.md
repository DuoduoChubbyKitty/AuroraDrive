| 项 | 结论 | 证据 |
|---|---|---|
| 推荐架构 | **3 高清(224×384) 走完整骨干 + 21 低清(112×192) 走共享骨干前 2 层 + 3 段×8 帧层级时序** | §3 |
| 端到端实测 | **p50 = 2.06ms，p95 = 3.30ms，100% 算子派发 ANE，比 CPU 快 6.7×** | §5.5 |
| 算力 | 5.19 GMACs，是「24 帧全过完整骨干」(21.67G) 的 **24.0%** | §5.2 |

| 时序结构 | **层级融合（3 段×8 帧）** 优于 24 步 unroll GRU / 24 帧 TCN / 时间维 attention | §2 / §5.4 |
| 时间位置编码 | **必须显式编码**，推荐可学习 embedding（24×D≈4.6K 参数） | §4.2 |
| 3 帧高清选帧 | **最近 3 帧（t、t−1、t−2）**，不选等间隔，理由见 §4.6 | §4.6 |
| 噪声注入 | **保留，但不能只靠它**；24 帧历史把覆盖率从 9.6% 提到 20.9%，两者互补 | §4.3 |

**一句话**：24 帧 unroll 的算力爆炸点**不在时序模块**（24 步 GRU 只有 5.36 MMACs），而在**骨干**（24 帧全过完整骨干 = 21.67 GMACs）。所以设计的关键不是把时序模块做小，而是**让低清帧不要重复付完整骨干的代价**。

## 1. 我读到了什么（论文时序相关设计）

> 精读范围：`III. OVERVIEW`(`:166-171`)、`IV.A State Token Propagation`(`:173-207`)、`IV.B Pixel-State Attention`(`:208-245`)、`IV.D Architecture and Training`(`:212-256`)、`VII. STATE TOKEN AND INERTIA PROBLEM`(`:382-395`)、`Tab. IV/V/VI/VII`。
> 另全文检索 `temporal|recurrent|sequence|history|LSTM|GRU|multi-frame|video` 确认无遗漏。

### 1.1 论文的状态 token 里装的到底是什么

论文原文（`:196-201`）：

> "The initial state token is the embedding of **steer, throttle, brake and speed at time t − 1**."
> "The initial state token is the embedding of steer, throttle, brake and speed at time t−1."

具体实现（`:223-234`）：

- 4 个标量：**speed / steer / acceleration / brake**（原文 `:223-224` 写作 "speed, steer, acceleration and brake"；`:201` 写作 "steer, throttle, brake and speed" —— 原文这两处措辞略有出入，`acceleration` 与 `throttle` 指同一路的纵向控制量，我在实现建议里按「4 标量槽位」处理，不纠结名字）
- 每个标量 lift 到 `D/4`，再 concat 成 D 维 → `xstate ∈ R^{1×D}`
- 加上可学习位置编码 `Epos ∈ R^{(N+1)×D}`
- token 序列：`z = [xstate; f¹Pv; ...; f^N Pv] + Epos`（原文公式 (1)，`:230-234`）

**关键事实：这个 token 只装 t−1 这一个时刻的 4 个数，不含任何多帧历史。** 它不是"时序编码器"，而是一个"上一时刻状态的注入点"。

### 1.2 它如何跨 stage 传播

`D. Architecture and Training`（`:212` 起）+ Fig.1 图注（`:155-158`）：

- 共享卷积骨干 → 4 个并行分支（每个高层命令一条）
- 每个分支是**多阶段 transformer encoder**（3 stage，每 stage depth=4、3 头，D=64，`:223-224`）
- **stage i 的 state token 输出，直接作为 stage i+1 的输入 state token**（`:179-181`："the i−th stage can inform stage i + 1 by taking the output of the encoder corresponding to the state token and propagating it as the new state token"）
- stage1 → 用 FFN 解出 stop/go；stage2 → 解出 steer/throttle/brake；stage3 → 仅训练期 CCM 正则
- 语义是 **coarse-to-fine**：`xstate` 每过一 stage 就被那里空间信息 enrichment 一次，语义越来越复杂（`:196-198`）

### 1.3 论文为什么认为「把状态喂给模型」会加剧 inertia

这是论文的核心论点，逻辑链是**两层**的：

**第一层：状态输入本身是必要的**（`:184-187`）
> "In principle, informing the model of the current state of the vehicle could ensure temporal smoothness and coherency... **In practice, this makes the model vulnerable to spurious correlations in the data, bringing out the inertia problem.**"

**第二层：机理是「伪相关 + 分布稀疏」**（`:26-37`、`:55-70`）
1. **伪相关**：训练数据里"低速"与"不给油"高度共现 → 模型学到 `speed≈0 ⇒ throttle≈0`。车一停（红灯/堵车），模型就再也起不来。这就是 inertia（惯性）问题，是 causal confusion 的一个特例。
2. **分布更稀**：`:33-35` 明说"the more variables are observed by the model, such as ego-velocity or previous driving commands, **the sparser the coverage of the training data gets**" —— 观测变量越多，联合状态空间的覆盖率越低，驾驶时越容易落到欠表示区域。
3. **离线/在线差距**：`:26-37` 指出在线时模型输出会影响未来输入，破坏 i.i.d. 假设；小误差累积把车带到训练时没见过的状态。

**这不是纯理论 —— 论文有实测数据**（Tab. V，`:440` 附近，惯性失败率，NoCrash Town01-NewWeather）：

| 任务 | Single Stage | Ours |
|---|---|---|
| Empty | **17%** | **1%** |
| Regular | **9%** | **1%** |
| Dense | **16%** | **6%** |

以及 Tab. VI（`:500` 起）：time-out 类失败（含 inertia）从 Single Stage 的 **17 次降到 1 次**。

**更关键的一条消融（Tab. IV，`:420` 起，Dense 任务成功率）—— 这条直接支撑我们该怎么做时序：**

| 配置 | Dense 成功率 |
|---|---|
| Single Stage（无 stop/go 阶段） | 30 |
| **w/o ST（去掉 state token）** | **20** |
| w/o S/G loss | 28 |
| w/o CCM | 28 |
| **Ours（完整）** | **50** |

**去掉 state token 掉得最多（50 → 20）**。说明「把上一时刻状态喂进模型」是这套架构最核心的收益来源 —— 而这正是时序模块要负责的事。同时也说明：光有 state token 不够，必须配合 stop/go 这类**显式的"该不该动"监督**（去掉 stop/go loss 也从 50 掉到 28）。

### 1.4 论文用什么办法解决

三板斧，缺一不可：

1. **多阶段 + stop/go 中间监督**（`:186-190`）：stage1 不产出控制量，只预测"该停还是该走"，用三路意图信号的 L1 loss（红绿灯 / 行人 / 其它车辆，`:230-234` 公式 (2)）。这让"是否移动"成为一个**显式、被单独监督**的量，而不是从 `speed≈0` 里隐含推断。原文称此"almost eradicate inertia entirely"（`:162-163`）。
2. **状态 token 传播**（`:179-181`）：stop/go 信息经 state token 传给 stage2，作为条件。
3. **对状态做噪声注入增广**（`:201-207`）：`zero mean Gaussian noise σ=0.1`（控制量，范围 [0,1]）、`σ=1`（速度，范围 [0,10]）。原文明确理由是"训练集车辆状态非均匀分布"（`Sec. VII-A`）。
   - 效果：在线成功率与离线 MAE 的 Pearson 相关性 **−0.64 → −0.92**（Fig.7，`:555` 附近）

另外还有 **CCM**（Command Coherency Module，`:246-264`）：训练期正则，用冻结的 MLP 预测 `speed(t+1)`，确保 steer/throttle/brake 三者不矛盾（原文明说 `throttle` 和 `brake` 同时 >0 是错的）。总损失 `L = λLc + κL_CCM + τL_SG`，λ=0.8、κ=0.1、τ=0.1（`:251-253`）。

### 1.5 论文的多阶段结构在时序上是怎么串起来的 —— **以及它没做什么**

**已做的（真正的时序成分只有两处）：**
1. **t−1 单步状态注入**（不是多帧）
2. **状态 token 跨 stage 传播**（这是"阶段间"的串接，不是"时间上"的串接）

**没做的（对我们极其重要）：**
- ❌ 没有帧缓冲 / 多帧历史 / 24 帧窗口
- ❌ 没有 RNN / LSTM / GRU / TCN / 时间维 attention
- ❌ 没有时间位置编码（只有**空间** token 的位置编码 `Epos`）
- ❌ 全文 "temporal" 只出现在相关工作 `:275` 的表格上标（指的是**别人的**工作，标注 `†(TEMPORAL MODELING)`）

**所以：论文无法为我们的「24 帧多帧结构」选型背书。** 论文给的是「单帧 + t−1 状态」范式；24 帧混合持续是我们的增量。§2/§3 的方案取舍**只能靠我们自己的实测**，不能引用论文当证据 —— 这一点我严格守住了。

**论文给我们的真正启示（3 条可执行）：**
1. **state token 是收益最高的一枚 token**（Tab. IV：去掉它 50→20）。我们的 24 帧历史应该设法**强化这个 token**，而不是另起一条平行支路。
2. **必须同时有"该不该动"的显式监督**（stop/go）。24 帧历史能提供运动趋势，但**不能替代** stop/go 监督（Tab. IV：去掉 stop/go loss 也从 50 掉到 28）。
3. **状态增广解决的是"分布稀疏"，不是"信息不足"**。这是我们判断要不要噪声注入的关键（见 §5.5）。

## 2. 方案对比（全部实测，M3 真机）

> 所有数字来自 `tools/v3_exp/` 下脚本的真实运行，非手算。MACs 用 forward hook 统计 Conv/Linear 的乘加次数。
> 测量口径：batch=1、FP16、`MLModel.predict`（含 Python 绑定开销约 0.1–0.3ms，故绝对值偏大，横向对比有效）。

### 2.1 时序融合结构（4 类，24 帧）

输入统一按**真实骨干输出维度**：`[1, 24, 256]` → 输出 `[1, 192]`（D=192，对齐 `01-backbone` 的 `BackboneConfig.dim`）。

| 方案 | 参数量 | MACs | 真机 p50 (ALL) | p95 | 结论 |
|---|---|---|---|---|---|
| **A 静态展开 GRU（24 步逐帧）** | 272,064 | 5.36M | 0.079ms | 0.088ms | 可用，链最长 |
| **B 4 层因果 TCN（不分层）** | 492,864 | 10.67M | 0.246ms | 0.277ms | 算力最贵，且**独立部署时 ALL 反而比 CPU 慢 4×** |
| **C 时间维 self-attention（手写 2 层 4 头）** | 284,800 | 0.15M (d=128) | 0.237ms | 0.374ms | **ALL 比 CPU 慢 3.8×**（0.237 vs 0.062）→ 不建议 |
| **★ D 层级融合（3 段×8 帧 + TCN 段间）** | 566,400 | **1.60M** | **0.062ms** | 0.065ms | **推荐**：算力仅 B 的 15%，延迟最低档 |
| **D′ 层级融合（3 段×8 帧 + GRU 3 步段间）** | 567,168 | 1.60M | **0.057ms** | 0.064ms | 同为推荐，递推链只有 3 步 |

**为什么 D 的算力比 B 低 6.7 倍？** 因为层级结构先把 24 帧压成 3 个段 token（`Conv1d(k=8, stride=8)`），之后所有段间计算只作用在 3 个 token 上，而不是 24 个。TN 层 TCN 是 4 层 × 24 步膨胀卷积，D 是 1 层段内卷积 + 2 层 × 3 步段间卷积。

### 2.2 两档分辨率的融合方式（4 种，实测 21 帧 @112×192）

| 方案 | 新增参数 | p50 | p95 | ANE | 结论 |
|---|---|---|---|---|---|
| **A 低清帧也走完整 ImageEncoder（共享权重）** | 0 | 1.573ms | 1.795ms | 100% | 特征空间最一致，但最贵 |
| B 独立 depthwise-separable 轻量编码器 | 10,784 | 0.620ms | 1.272ms | 100% | 便宜，但特征与高清**异空间** |
| **★ C 共享骨干前 3 层(stem+s1+s2) + GAP + proj** | 12,544 (proj) | 0.876ms | 1.166ms | 100% | 兼顾：权重共享 + 便宜 |
| **★ C2 共享骨干前 2 层(stem+s1) + GAP + proj** | 12,544 (proj) | **0.650ms** | **0.766ms** | 100% | **推荐**：p95 最低 |
| D 极简 patch 池化(4×4)，完全不进 CNN | 12,544 | 0.984ms | 1.423ms | **0%** | 反而更慢且 ANE 全掉 CPU → 否决 |

> **「新增参数」口径说明（避免下游对不上数）**：C/C2 的 12,544 是**推荐架构下真正新增**的参数（只有最后的 `proj`），因为它们复用高清分支已有的骨干权重。
> 若把 C/C2 当作**独立模块**测量（`06_arch_compare.py` 的做法，模块内自带一份骨干前馈层），参数量分别是 **275,440（C）** 与 **55,504（C2）** —— 差额是骨干前 1~2 层的权重。两种口径都正确，只是"这份权重算不算新增"不同；**推荐架构里算共享，只新增 12,544**。

24 帧图像侧总耗时（高清 3 帧 1.026ms + 低清 21 帧）：

| 低清方案 | 合计 p50 | 合计 p95 |
|---|---|---|
| A 完整骨干 | 2.599ms | 2.971ms |
| B dw-sep | 1.646ms | 2.449ms |
| C 前 3 层 | 1.902ms | 2.342ms |
| **★ C2 前 2 层** | **1.677ms** | **1.942ms** |

**选 C2 而非 B 的决定性理由**：B 虽然 p50 略低（0.620 vs 0.650），但它的**特征空间和 V3 的 transformer 主干不一致** —— 它是在一个全新的 depthwise 特征空间里训练出来的，而 V3 主干的 visual token 来自重参数化骨干。C2 **复用同一份卷积权重**（真正共享，参数量不重复计），低清特征天然落在与高清相同的语义空间，跨分辨率对齐不需要额外学习。同时 C2 的 p95 最低（0.766ms）。

### 2.3 层级分组拓扑：3 段×8 帧 vs 8 组×3 帧

这个选择由**用户需求的两种读法**决定，必须先讲清楚：

- **用户原话**：「每三针一针清晰的…这样子24针」→ 字面读是 **8 高清 + 16 低清**（每 3 帧 1 帧高清）
- **任务书已确认**：**3 高清(224×384) + 21 低清(112×192)**

两者都测了：

| 拓扑 | 分组 | 参数量 | MACs(估算) | 说明 |
|---|---|---|---|---|
| 拓扑甲 | 8 组 × 3 帧（1 高清 + 2 低清） | 213,888 (d=128) | — | 匹配"8 高清 + 16 低清" |
| **★ 拓扑乙** | **3 段 × 8 帧（1 高清 + 7 低清）** | 566,400 (d=192) | 1.60M | 匹配已确认的"3 高清 + 21 低清" |
| 对照 | 24 帧全展平（不分层） | 492,864 | 10.67M | 最贵 |

8 高清 + 16 低清方案的图像侧算力实测为 **10.40 GMACs**，是 3+21 方案（3.97G）的 **2.62 倍**（`01_budget.py` E 段）。**按任务书确认的 3+21 执行**；若后续用户改口要字面方案，算力需按 2.62× 重新评估。

**为什么层级结构天然适配"1 高清 + 7 低清"的段**：每组内的 1 帧高清正好作为该段的"锚点"（分辨率高、语义准），7 帧低清提供该段的运动趋势。段内卷积 `kernel=8, stride=8` 一次性把 8 帧压成 1 个段 token —— 高清锚与低清趋势在同一卷积里融合，不需要额外的对齐模块。

## 3. 选型推荐 + 理由

### 3.1 推荐架构（唯一方案）

```
输入:  image_hi [3, 3, 224, 384]      最近 3 帧高清（t, t-1, t-2）
       image_lo [21, 3, 112, 192]     前 21 帧低清（t-3 ... t-24）
       state    [1, 4]                t-1 的 steer/throttle/brake/speed（论文式）

①  高清 3 帧 ──完整 RepVGG 骨干（D=256，14×24=336 token）──> f_hi [3, 256]
②  低清 21 帧 ──共享骨干前 2 层 + GAP + proj(48→256)──> f_lo [21, 256]
③  按时间序拼: seq = [f_hi; f_lo]                    → [1, 24, 256]
④  层级时序:  段内 Conv1d(k=8, s=8) → 3 段 token
              段间 2 层因果膨胀卷积(d=1,2)           → hist [1, 192]
⑤  state token: Linear(cat[state(4), hist(192)] → 192) → x_state [1, 192]
⑥  视觉 token 序列: [x_state; 336 visual tokens] + Epos → transformer 主干
⑦  输出头: 从 x_state 解 stop/go + W/A/S/D + Shift/Space + confidence/risk
```

### 3.2 为什么是这套（5 条理由，按重要性）

1. **算力花在刀刃上**：时序模块只占 1.60M MACs，而图像侧 5.19G —— 时序部分占端到端算力 **0.03%**。把时序做复杂没有收益，把低清帧做便宜才有收益（21.67G → 5.19G，省 76%）。
2. **层级结构让递推链最短**：3 段×8 帧把 24 步递推压成 **3 步**（若选 GRU 段间）或 **2 层卷积**（TCN 段间）。递推链越短，静态展开后的图越浅，ANE 越友好，也不会有长链的数值漂移。
3. **state token 强化而非另起支路**：论文 Tab. IV 证明 state token 是最有价值的 token（去掉它 50→20）。我们不新增平行的 temporal token，而是**把 24 帧历史摘要喂进 state token 本身** —— token 数不变（不增加 attention 平方级开销），但每个 token 的信息量变大。
4. **低清走共享骨干前 2 层**：权重真共享 → 跨分辨率语义天然对齐；p95 最低（0.766ms）；新增参数只有 12.5K。
5. **全静态展开**：整图 0 个 `while_loop`，实测 100% 算子派发 ANE（§6）。

### 3.3 为什么不选其它方案

| 被否决的方案 | 否决理由（实测） |
|---|---|
| 24 步 unroll GRU（不分组） | 递推链 24 步，图中 573 个算子；虽延迟可接受（0.079ms），但作为**整图**一部分会让图更深、编译更慢。且它需要吃 24 帧逐帧特征，没有层级压缩带来的"段内融合"优势 |
| 4 层 TCN（不分层） | 10.67M MACs，是层级方案的 6.7 倍；p50 0.246ms 明显更慢；**独立部署时 ALL(0.246) 比 CPU(0.059) 慢 4 倍** |
| 时间维 self-attention | ① `nn.TransformerEncoderLayer` **coremltools 9.0 直接转换失败**（`NotImplementedError: '_transformer_encoder_layer_fwd'`）；② 手写版能导出，但 **ALL 比 CPU 慢 3.8×**（0.237 vs 0.062ms）—— 小张量在 ANE 上的搬运开销大于计算收益 |

### 4.2 时间位置编码（任务问题 2 的正面回答）

**必须显式编码，推荐可学习 embedding。**

理由：

1. **24 帧的时间间隔不均匀** —— 这是本项目既有 `TemporalEncoder` 就记录过的问题（`src/temporal.py:103-117`）：图像 30Hz、位置序列约 8Hz，帧与帧的 dt 并不一致。V3 窗口按 15Hz 算 1.6s，但实际采样若抖动，模型必须知道"这一帧离上一帧多久"。
2. **层级结构会丢绝对时间位置**：段内卷积后只剩 3 个段 token，段的顺序信息若不在输入里显式给出，卷积无法区分"这是最近的段还是最远的段"。因果卷积只保证不看未来，不保证知道远近。
3. **三种方案取舍**：
   - 可学习 embedding（24×D，D=192 → **4,608 参数**）：最灵活，推荐；
   - 正弦编码：0 参数、可外推到更长窗口，但 15Hz 固定采样下外推需求不存在；
   - 不编码：**不可接受** —— 因果卷积+段池化后，模型无法区分时间远近，等于把 24 帧当成无序集合。
4. 实现上复用论文的加法式位置编码（`:226-228` "a learnable positional embedding Epos is added to all the N+1 tokens"），只是我们的 `Epos` 同时覆盖**时间维（24 帧）**与**空间维（336 token）**。建议分开两个参数：`Epos_time [24,D]` 加到帧特征上，`Epos_space [337,D]` 加到 transformer token 上 —— 让两者的语义不混淆。

### 4.3 三个必答题（Lead 补充要求）

#### 问题 1：state token 的初始内容 —— 只装 t-1 四标量，还是装 24 帧序列？

**推荐：t-1 四标量 + 24 帧历史摘要（方案 B）。** 实测：

| 方案 | 参数量 | MACs | 评价 |
|---|---|---|---|
| A 只装 t-1 四标量（论文原样） | 640 | 512 | 最省，但浪费 24 帧信息 |
| **★ B t-1 四标量 + 24 帧历史摘要** | 17,024 | 16,896 | **推荐**：多 16K 参数换来完整历史 |
| C 24 帧完整状态序列（4→64→128 GRU） | 33,600 | 604,160 | 状态序列的**信息量**远小于视觉特征序列（4 维 vs 256 维），604K MACs 花在 4 维信号上性价比低 |

**理由**：论文的 state token 只有 4 个标量是因为它只有单帧。我们有 24 帧 × 256 维的视觉特征，其信息量比 24×4 维的状态序列高两个数量级。方案 B 把**视觉历史摘要**（192 维）与 t-1 标量拼起来，相当于给 state token 装上了"这 1.6 秒车是怎么动的" —— 正好补上论文 state token 缺失的那部分。方案 C 则把宝贵的 token 容量花在 4 维状态信号的历史上，不划算。

#### 问题 2：24 帧视觉特征怎么进 state token —— 摘要拼接 vs 独立 temporal token？

**推荐：摘要拼接（不新增 token）。** 实测 token 数增加后的 attn 算力代价（视觉 336 token、D=192、8 层主干）：

| 方案 | token 数 | 主干 attn MACs | 相对论文式 |
|---|---|---|---|
| 论文式：336 视觉 + 1 state | 337 | 1.542 G | 1.000× |
| **★ 推荐：336 视觉 + 1 state**（历史摘要并入 state token） | **337** | **1.542 G** | **1.000×** |
| 336 视觉 + 1 state + 1 temporal | 338 | 1.547 G | 1.004× |
| 336 视觉 + 1 state + 3 temporal | 340 | 1.558 G | 1.011× |
| 336 视觉 + 1 state + 8 temporal | 345 | 1.587 G | 1.029× |
| 336 视觉 + 1 state + 24 逐帧 temporal | 361 | 1.678 G | 1.089× |

**结论**：如果走独立 temporal token，**1 个 token 只增加 0.4% 算力，3 个增加 1.1%，24 个增加 8.9%** —— **token 数增加的开销在 336 个视觉 token 的基数下可以忽略**（因为 QK^T 是 O(T²)，但 T 已经是 337 量级）。

所以「算力」不是这个决策的依据，**依据是信息架构**：

- **摘要拼接（推荐）**：state token 变成"t-1 状态 + 1.6 秒历史摘要"，语义集中在一枚 token 上。论文 Tab. IV 已证明这枚 token 是收益最高的（去掉它 50→20），强化它比新增支路更符合论文的验证结果。
- **独立 temporal token**：好处是 attention 可以选择性读历史（可解释性更好），代价是要多学一套 token 的位置编码与注意力模式，且它不享受论文已验证的 state token 传播机制。

**我的推荐是「摘要拼接进 state token」**，但如果 §5.5 的数据显示历史信息量大到一枚 token 装不下（192 维 vs 340 帧特征的压缩比 96:1），可以加 **1 个独立 temporal token**（+0.4% 算力，几乎免费）作为退路。**不要加 24 个**。

#### 问题 3：有了 24 帧真实历史，还需要噪声注入吗？

**推荐：保留噪声注入，但降低权重、且不能只靠它。** 这是**有条件**的结论，依据是实测 + 论文机理：

**实测（合成数据，仅说明机理）：**

| 配置 | 状态空间占据格 | 充分覆盖格 | 物理不自洽比例（\|acc\|>0.5） |
|---|---|---|---|
| ① 单帧（无增广） | 3,153 / 32,768 (9.6%) | 2,220 (6.8%) | 7.2% |
| ② 单帧 + 论文式噪声 | 5,187 (15.8%) | 3,399 (10.4%) | **9.4%** ↑ |
| ③ **24 帧窗口（真实历史）** | **6,853 (20.9%)** | **5,029 (15.3%)** | **3.2%** ↓ |
| ④ 24 帧窗口 + 噪声注入 | 9,310 (28.4%) | 6,584 (20.1%) | 6.1% |

**三个关键读数：**

1. **24 帧历史本身就是最强的增广**：覆盖率 9.6% → **20.9%（2.2 倍）**，且**物理自洽性更好**（不自洽比例 7.2% → 3.2%）。因为它给的是真实轨迹，不是随机扰动。
2. **噪声注入用"物理不自洽"换覆盖率**：②的自洽性从 7.2% **恶化**到 9.4% —— 逐维独立加高斯噪声会造出"油门 0.9 + 速度 0 + 加速度极大"这类现实中不存在的状态。论文在单帧设定下不得不这么做（没有别的选择），但**我们有真实历史这个更优的信息源**。
3. **两者互补而非替代**：④把覆盖推到 28.4%，仍高于 ③ 的 20.9%。噪声能覆盖到真实历史**到不了**的罕见组合。

**我的判断与理由**（三条）：

- **保留，但要"小剂量"**：建议控制在论文的 **σ_ctrl = 0.05~0.1**（不放大），只在**训练期**对 `state` 输入施加，不动视觉特征。
- **不要指望它解决 inertia**：论文的机理是"训练集伪相关 + 分布稀疏"。24 帧历史解决的是**信息不足**（模型现在能看出"上一秒在加速"），不能解决**伪相关**（数据里仍然是"停了就不给油"）。所以 §1.4 的 stop/go 监督**必须保留**，这是论文验证过的抗 inertia 主手段（Tab. IV：去掉 stop/go 50→28）。
- **可关闭，做成开关**：`state_noise_sigma` 默认 0.1，训练前期开、后期可退火到 0。理由：噪声注入的收益主要在"防止过拟合到稀疏区域"，训练后期模型已见过足够多的真实历史，继续加噪反而引入不自洽样本。

**⚠️ 这条结论的数据是合成数据**（复现论文 Fig.5 的双峰 throttle + steer 近零形状），不是我们的真实采集。**真实覆盖率必须用我们的数据重算** → 见 §7 未测项。

### 4.5 空历史 / 冷启动处理

必须处理（沿用现有 `TemporalEncoder` 的 mask 惯例，`src/temporal.py:44-53`）：

- **历史不足 24 帧**：无效帧特征清零并保留位置（**不要丢帧**，丢帧会改变时间轴对齐）。
- **t-1 状态缺失**（首帧 / 状态读取失败）：填零向量。现有 `StateEncoder` 已确立"全零 = 未知"的约定（`src/model_v2.py:807-811`）。
- 校验：`image_hi` 必须恰好 3 帧、`image_lo` 必须恰好 21 帧（CoreML 固定 shape，不足用 mask，**不要改 N**）。

### 4.6 选帧策略：3 帧高清取哪 3 帧（任务问题 5）

**推荐：最近 3 帧（t, t−1, t−2）。**

| 策略 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **★ 最近 3 帧** | 与当前决策因果最相关；无需额外状态；实现最简 | 长程信息全靠低清 | **推荐** |
| 等间隔（t, t−8, t−16） | 长程覆盖好 | ①当前帧信息量最大，等间隔浪费了最近的帧；②间隔帧与当前帧差异大，跨分辨率/跨时间的特征对齐更难；③需要额外的"选哪几帧"逻辑进图 | 否决 |
| 关键帧（按运动突变选） | 理论上信息密度最高 | ①**需要动态决策**（选帧本身是动态控制流）→ 直接违反"禁止动态循环"约束；②CoreML 图必须固定 shape，动态选帧无法表达；③训练/推理选帧逻辑不一致会引入分布漂移 | **明确否决** |

**为什么"最近 3 帧"是关键设计而非妥协：**

1. **因果性**：驾驶决策主要取决于最近的运动状态。1.6 秒前的画面（t−24）价值远低于 0.2 秒前（t−3）。高清帧应该花在最有价值的时段。
2. **层级结构天然利用它**：3 段×8 帧中，**每段的第 1 帧是高清锚点**。第 1 段（最近 8 帧 t−1..t−8）含 t、t−1、t−2 三帧高清 —— 正好是"最近段信息最密"，越远越粗。这与"近处需要精细、远处只需趋势"的驾驶直觉一致。
3. **避免动态控制流**：固定取最近 3 帧，图的输入 shape 是静态的，CoreML 可导出。关键帧选择会引入动态性，与项目 `while_loop` 禁令的精神冲突。

> 注：低清帧是 112×192，分辨率为高清的 1/2（面积 1/4）。按 Nyquist，它能表达的空间频率是高清的一半 —— 对"看出车道线走向、前车位置趋势"足够，对"识别交通灯颜色、读远处标志"不够。所以**高清帧放在最近处**，也符合"最近的决策需要最细的输入"。

## 5. 算力 / 参数估算（全部实测）

### 5.1 测量方法（可复现）

- MACs：给模块挂 forward hook，累加 `Conv2d`/`Conv1d`/`Linear` 的乘加次数（batch=1）。不含 BN/激活/池化的逐元素开销。
  - ⚠️ **MACs ≠ FLOPs**：1 MAC = 2 FLOPs。本文所有"算力"都是 MACs。
- 参数量：`sum(p.numel())`。
- 延迟：`MLModel.predict` 实测，warmup 15–20 次、计时 60–100 次，报 p50/p95。
- ANE 派发：coremltools 9.0 `MLComputePlan` 逐算子查 `preferred_compute_device`。
  - ⚠️ **API 坑**：`load_from_path()` 直接吃 `.mlpackage` 会 **C++ abort**（coremltools 9.0 新布局没有 `coremldata.bin`）。必须 `ct.models.MLModel(pkg).get_compiled_model_path()` → 用 `.mlmodelc` 路径加载。第一版脚本踩了这个坑。
  - ⚠️ **设备识别坑**：`MLComputeDevice` **没有** `.type` 属性，只能按**类名**（`MLNeuralEngineComputeDevice` 等）判断。用 `getattr(dev,'type',str(dev))` 会统计出"ANE 0%"的假象。

### 5.2 图像侧算力（决定性数字）

| 配置 | MACs | 相对基线 |
|---|---|---|
| 单帧 180×320（现有基线） | 902.85 M | 1.00× |
| 单帧 224×384（V3 高清） | 1,291.27 M | 1.43× |
| 单帧 112×192（V3 低清） | 322.82 M | 0.36× |
| **24 帧全过完整骨干（180×320）** | **21,668.29 M = 21.67 G** | **24.0×** |
| **★ 混合方案：3×224×384 + 21×低清编码器** | **3,969.44 M = 3.97 G** | **18.3%（vs 24 帧全骨干）** |

**这就是"24 帧 unroll 会不会算力爆炸"的答案：会，但爆炸点不在时序模块，在骨干。**

- 24 帧全过完整骨干 = **21.67 GMACs**，是单帧的 24 倍 —— 这才是"算力爆炸"
- 时序模块（任一变体）只有 **0.15M ~ 10.67M MACs**，即单帧骨干的 **0.02% ~ 1.2%**
- 用混合分辨率 + 轻量低清编码器，图像侧从 21.67G 降到 **3.97G（18.3%）**

**推荐架构的参数量分解**（`07_hybrid_e2e.py` 实测，**hidden=192 即 §3.1/§4.1 的推荐配置**）：

| 部件 | 参数量 | 说明 |

| 时序模块（3段×8帧 + TCN段间，hidden=192） | 566,400 | 含 in_proj(256→192) + 段内/段间卷积 + LN |
| 低清分支新增（proj 48→256） | 12,544 | 复用骨干前 2 层 |
| state token（Linear 196→192） | 37,824 | |
| 历史注入 + 输出头 | 82,884 | hist_proj(192→256)=49,408 + head(256→128→3)=33,283 + state_out(192→1)=193 |
| **合计** | **3,218,804 ≈ 3.22M** | |

> 若把时序 hidden 降到 128（**不推荐**，仅为参数量下限参考），实测总参数为 **2,878,068 ≈ 2.88M**、时序模块 262,912、端到端 p50 1.801ms / p95 3.330ms（单轮 80 次口径）。两者 MACs 相同（5.19G，瓶颈在图像侧）。**推荐 hidden=192 的核心理由不是延迟**（600 次口径下 p50≈2.06ms / p95≈3.30ms，与 hidden=128 的 p95 3.33ms 基本持平），而是：① 它与 `01-backbone` 的 D=192 对齐，state token 无需再做维度转换；② 时序摘要容量翻倍，对 24 帧 × 256 维的压缩比更合理（192 维 vs 128 维）。

**关于"2-3M 预算"的口径澄清（重要）：**

任务书写"参数量预算约 2-3M"，但这是**时序模块**的预算，而上面的 3.22M 是**整个时序相关链路**（含共享骨干 2.52M）。

如果只看**时序模块自身新增参数**，按真实骨干维度（in=256, D=192）：

| 时序结构 | 参数量 |
|---|---|
| 层级 3段×8帧 + TCN段间 | 566,400 |
| 层级 3段×8帧 + GRU3步 | 567,168 |
| 24 步 unroll GRU | 272,064 |
| 4 层因果 TCN | 492,864 |

**这些数字远超"2-3M"吗？不 —— 是远低于。** 时序模块最贵也只有 567K，是 2-3M 预算的 **19% ~ 28%**。

所以真实情况是：**"2-3M" 的预算给时序模块绰绰有余，钱应该花在别处**（骨干/主干容量）。我的建议是时序模块就按 567K 落地（层级方案），**不要为了凑 2-3M 而把时序结构做复杂** —— §5.2 已证明复杂时序结构的收益极小而算力浪费大。

> 参考：现有 V2 的 `IterationRefiner(24 步 shared)` 单独就有 5,322,507 参数（24 步 × 512 隐层），比 V3 的整个时序模块贵 9.4 倍。这说明"步数多"不等于"参数量合理"。

### 5.4 时序模块四种结构对比（汇总，真实骨干维度）

## 6. ANE 风险清单

### 6.1 已实测排除的风险

| 风险 | 实测结果 | 证据 |
|---|---|---|
| `while_loop` | **0 个**。所有时序结构用 Python `for t in range(steps)` 静态展开，trace 后是普通算子序列 | 整图 228 算子无 loop |
| `nn.GRU` / `nn.GRUCell` | **不使用**。沿用 `src/temporal.py:273-307` 的 `_StrictGRUCell`（手工展开成 Linear+sigmoid+tanh+mul） | 项目已实测等价性 maxdiff 2.98e-08 |
| `nn.TransformerEncoderLayer` | **不能用** —— coremltools 9.0 直接 `NotImplementedError: '_transformer_encoder_layer_fwd'`。若需时间维 attention，必须**手写**（Linear+matmul+softmax），手写版可导出 | `02_ane_dispatch.py` / `03_ane_decisive.py` |
| 低分辨率上不了 ANE | **错**。真实 `ImageEncoder` 在 112×192 上仍 **100% ANE**（29/29 算子） | `03_ane_decisive.py` Q1 |
| 时序模块太小上不了 ANE | **整图是 100% ANE**。但**孤立小图**上 planner 会随机派给 CPU/GPU（见 §6.2 陷阱） | `07_hybrid_e2e.py` |
| 输入尺寸门槛 | 第一轮曾误判"≤160×160 上不了 ANE"，**该结论是错的**（见 §6.2） | 已推翻 |

### 6.2 ⚠️ 测量陷阱（必须写进任何后续报告，否则会误导决策）

**现象**：同样结构的时序模块，**孤立导出时**算子派发是 `{'cpu': 430}`（ANE 0%），但**拼进完整骨干后**是 `{'neuralEngine': 62}`（ANE 100%）。

**诊断实验**（`02_ane_dispatch.py` 之外的补充探测）：

| 测试对象 | 算子派发 |
|---|---|
| 3 个 Linear + LN on `[1,24,128]` | CPU 4 |
| 5 层 Linear on `[1,24,128]` | **ANE 6** |
| 3 个 Linear on `[1,1024,128]` | GPU 3 |
| 2 层 Conv1d on `[1,128,24]` | CPU 3 |
| 2 层 Conv1d on `[1,128,256]` | CPU 3 |

**结论**：`MLComputePlan` 的派发是 **planner 对每个算子的成本启发式估计**，在**极小图**上（总计算量远低于调度开销）它会随机落到 CPU/GPU，这个结果**不代表实际部署表现**。

**正确做法**：ANE 派发评估**必须在"真实部署形状的整图"上做**，不能用孤立子模块下结论。本文档所有 ANE 结论都以 `07_hybrid_e2e.py` 的整图测量为准。

**另一条佐证**：延迟实测显示，4 层 TCN 孤立部署时 `ALL(0.246ms)` 比 `CPU_ONLY(0.059ms)` **慢 4 倍**、手写 attention 慢 3.8 倍 —— 这不是"ANE 不行"，而是**小张量在 ANE 上的搬运/调度开销大于计算收益**。这反而是个真实的设计信号：**时序模块不要做重，做重了在小张量上反而更慢**。

## 8. 给下游（`model_v3.py` / `task-11`）的接口建议

```python
class TemporalModuleV3(nn.Module):
    """V3 24 帧混合时序模块（本文档推荐实现）。

    输入契约（与 task-11 的 forward 签名对齐）：
        f_hi:  [B, 3, 256]   高清 3 帧的骨干特征（时间序 t, t-1, t-2）
        f_lo:  [B, 21, 256]  低清 21 帧的骨干特征（时间序 t-3 ... t-24）
        s_t1:  [B, 4]        t-1 的 steer/throttle/brake/speed
    输出：
        x_state: [B, 192]    强化后的 state token（拼进 transformer 的 token 序列首位）
        hist:    [B, 192]    历史摘要（可选，供 aux 输出/调试）
    """
```

**三条实现纪律（都是项目踩过坑的）：**

1. **零初始化历史注入**：`hist_proj` 必须 `nn.init.zeros_()`。依据 `src/model_v2.py:1294-1306` 的 `temporal_proj` bug 记录 —— 随机初始化会让残差项范数 7.8~50 倍于主干，一上来就破坏主干行为。零初始化后起步 `fused = base + 0 = base`，与无时序模型逐位一致。
2. **不用 `nn.GRU` / `nn.TransformerEncoderLayer`**：前者 trace 出 `while_loop`（ANE 全掉），后者 coremltools 9.0 不认。用 `_StrictGRUCell` + 逐帧静态展开；注意力必须手写。
3. **固定 shape，不动态选帧**：低清必须恰好 21 帧、高清恰好 3 帧。冷启动靠 mask，不靠改 N。关键帧选择会引入动态控制流，与 `while_loop` 禁令的精神冲突。

**建议的默认超参：**

```python
TEMPORAL_GROUP = 8          # 段内 8 帧（1 高清 + 7 低清）
TEMPORAL_INTER_LAYERS = 2   # 段间 2 层因果膨胀卷积
TEMPORAL_HIDDEN = 192       # 对齐 backbone D=192
STATE_NOISE_SIGMA = 0.1     # 论文值，训练后期可退火到 0
STATE_TOKEN_INIT = "t1+hist"  # 方案 B：t-1 四标量 + 历史摘要
```
