# 08 · 人机共驾壳模式（速度三段奖励 + 壳模式安全语义）

> 本文回答两个问题：**壳模式是什么、为什么这么设计**（它退出哪些引擎、人机共驾怎么流转、
> 默认关的安全语义）；以及**速度三段奖励的精确口径**（它同时落在 Swift 在线训练器与
> Python 离线奖励模块两边，是「两边必须逐值一致」的那类契约）。

## 一、壳模式定位：只留「壳 + 训练引擎 + 速度表」

壳模式（人机共驾壳模式）是「让模型自己学着开」的使用形态：**UI 壳保留**（主界面、
状态显示、速度表读数），但**所有会替人决策/替人按键的驾驶引擎一律退出**，把驾驶权
交给 RL 策略头的采样动作（默认走 digest 影子——算键不真发，见第五节）。

进入壳模式时退出的引擎清单（叙述口径，与 `ShellModeController.start()` 的编排一致）：

- **后台自动驾驶引擎进程**（`--engine` 远程引擎）：真 kill、不重连——壳模式期间引擎
  不得再注入任何按键；
- **V3 主推理**（`InferenceEngineV3`）与**纯规则驾驶**：停止决策；
- **降级链 / V2 / 检测链**（如 degradeStm、yolo 系列）：复位、退出决策路径；
- **保留不退**：抓屏采集（训练的眼睛，绝对不能停）与**速度 OCR**（速度表是速度三段
  奖励的唯一真实信号源）。

退出这些引擎的原因很直接：壳模式期间**唯一合法的「驾驶动作」来源是策略头采样**，
任何其它引擎的按键注入都会污染「这个动作是策略选的」这一训练前提。

**停止壳模式（stop）** 按固定次序执行，其中第一步是硬不变量：

1. **立即 `releaseAll`**（硬不变量）：一进入 stop 就失效动作会话并撤销全部在途 AI 动作，
   不等训练排空——按键安全永远先于训练收尾；
2. **排空（有超时）**：帧管线与训练队列在超时上限内排空（任一超时则如实报
   `drained=false`，此时不碰训练器独占态、不存盘，宁可少存一次也不冒损坏状态的风险）；
3. **存盘**：把训练好的策略头权重原子写入存档（默认
   `Application Support/AuroraDrive/shell_head_latest.json`，可用环境变量覆盖），成功与否
   如实计入 `headSaved`。stop 结果 `(drained, headSaved)` 原样透传 UI——**不再无条件
   显示「已停止」**，排空超时/存盘失败都要让用户看见。

**退出恢复**：停止后恢复自动驾驶走 `resumeAfterLeanRecording`，它内置时序保护——
**等旧引擎进程确认退透之后**才拉起新引擎，避免新旧两个引擎进程并存、双路注入按键。
另外**录制与壳模式互斥**（双向门控）：录制开着不允许进壳模式，壳模式开着不允许开录制
——两者都要独占抓屏流与按键标签，并存会让「这个键是谁按的」不可判读。

**策略头权重的跨会话生命周期**：`存盘 > 上次存档`——只有当本次训练的权重确实存进
存档后，存档才更新；`start()` 时**优先读回存档**（`shell_head_latest.json`），读不到才
回退到导出的初始权重或随机初始化。也就是说：上一会话学到的策略头，下一次启动壳模式
时**接着用**，训练是跨会话连续的；存档读回失败也如实降级并说明，不静默装作从头开始。

## 二、人机共驾流程：示范 → 自开 → 接管即负分+示范

壳模式下的人机共驾按回合流转：

1. **人示范**：一段真人驾驶录像/实驾，作为模仿学习的正例（离线管线里 `--stage bc`
   消费的就是这类数据；在线侧真人帧同样不进策略梯度，只做示范标签）。
2. **模型自开**：策略头采样动作，默认走 digest 影子（算键不真发）；真注入需显式 live
   许可（`AURORA_RL_LIVE_ACTUATION=1`，见第五节三源合并），观测速度/车道/接管信号，
   `OnlineTrainer.collect` 逐帧收集 transition。
3. **人接管 = 强负分 + 示范**：任何一帧检测到人工接管（`tookOver == true`），
   - 该帧**不建策略 transition**（人类救援动作不是策略采样，不进策略梯度）；
   - `-takeover`（默认权重 10，六项里最大）惩罚归因到**上一条策略执行的 AI transition**，
     并把它置为真实终止、整批训练——惩罚真正进入 actor 梯度；
   - **保留人工键**：接管瞬间 AI 只撤销**自己注入的**键（`releaseAIHeldKeys(preserving:)`），
     真人此刻正按住的物理键一律保留——绝不全量 `releaseAll` 清键（那会松开人手里的
     方向/油门，等于在救援时刻制造新事故）；
   - 人接管期间的动作本身是一段新的示范数据（下一次模仿学习的素材）。

**接管怎么检测**：信号源是 `EmergencyTakeover.userHoldingKey`（真人物理按键触发的接管
状态）+ 壳模式自带的独立键盘监听，**不依赖 `isDriving`**——引擎模式/待机等「V3 是否
在控」的状态不参与接管判定，杜绝「AI 正常开、人没动却被误判接管」或反过来漏判。

这条「接管即让位 + 负分 + 示范」的语义在在线/离线两边一致：在线侧 `OnlineTrainer.collect`
的 tookOver 路径与离线侧 `reward.py` 的 `takeover_reward` / 掩码语义对齐。

## 三、速度三段奖励（精确口径 + 双语言契约）

### 3.1 口径（用户口径，2026-11-17 定稿）

速度项把「开得快不快」从单一的 0..1 线性分改为**三段**：低于 100 为负分、100–160 线性
从 0 递增到 +1、超过 160 再转负分。各段数值如下：

| 速度区间 | 公式 | 端点值 |
|---|---|---|
| `v < 100` | `-(100 - v) / 100` | v=99 ≈ -0.01（接近 0 的负）；v=0 = -1.0（最负） |
| `100 ≤ v ≤ 160` | `(v - 100) / 60` | v=100 = 0；v=130 = +0.5；v=160 = +1.0（最大正） |
| `v > 160` | `-(v - 160) / 60` | v=161 ≈ -0.0167（略负）；越高越负 |

明确常数（写在两边代码注释里，自检逐值断言）：

- **下分界 100**（`SPEED_LOW_KMH` / `RewardConfig.speedLowKmh`）
- **上分界 160**（`SPEED_HIGH_KMH` / `RewardConfig.speedHighKmh`）
- 低于 100 按差距扣、超过 160 按超出扣，两个归一化宽度分别是 100 与 60。

边界语义两点必须说清，否则两边对不上：

- **v=100 处连续**（左右两段都恰为 0）；
- **v=160 处是设计跳变**：v=160 属中间段（+1.0，甜点区上限最大正分），一旦越过 160
  立刻转负（v=161 已是小负）。这是「甜点区上限、越过即罚」的刻意设计，**不是**错误。
- `speedValid=false` 或速度非有限/为负 → 该项为 **0**（不伪造奖励，也不伪造惩罚）。
  下一帧的 decel 检查同时被 `prev_valid=false` 抑制（跨 OCR 缺口不伪造急减速，既有语义不变）。

### 3.2 双语言同源（Swift / Python 逐值一致）

同一公式同时落在两处，缺一边就是「在线训的和离线算的不是一个奖励」：

- Swift 在线侧：`OnlineTrainer.speedTerm`（`RewardConfig` 持分界常数）；
- Python 离线侧：`tools/v3_rl/reward.py` 的 `speed_term`（模块级 `SPEED_LOW_KMH` / `SPEED_HIGH_KMH`）。

两端各自有**同一组黄金值断言**（99/100/130/160/161 + speedValid=false→0）：

- Swift：`-rl-shell-selftest` 自检（`ShellModeSelfTest.run()`，见第六节）；
- Python：`tests/test_reward.py` 内 pin 分界常数 100/160，并逐值断言黄金输出。

任一语言的口径漂移都会在对应套件里立刻暴露——这是把「两边一致」从口头约定变成
可执行断言的唯一办法。

### 3.3 碰撞保护：用户选择不启用（刻意决策）

**本阶段不自动加碰撞保护。** `frameReward` 里的 collision 项保留既有实现（按观测到的
碰撞信号扣分），但**没有**任何「预测碰撞、提前刹车、自动避让」的主动保护逻辑接入
训练或驾驶链路。这是用户明确选择：壳模式阶段先验证「速度三段 + 接管惩罚」能否把策略
头带上正轨，碰撞类主动干预（及其奖励塑形）留待后续按实测数据决定。将 collision 权重
配置为 0 或极小（`RewardConfig(collision:)` / `RewardWeights(collision=...)`）即可完全
关闭该项，语义与「不启用」一致。

### 3.4 学习收益环境的速度尺度（为什么自检用 160/20）

速度三段把「低速度」从 0 分变成负分后，「学习收益」类自检（合成环境里正确动作得高分、
错误动作得低分）的环境速度必须落在**正分段**承载奖励：正确动作 160（+1.0）、错误动作
20（-0.8）。若沿用旧的 90/20，最优回报本身为负，critic 的价值目标整体为负，全局梯度
裁剪会被 critic 的巨梯度主导，策略学习被压垮——这不是阈值松紧问题，是奖励尺度问题。

## 四、训练在哪跑：实时只训策略头；骨干离线轻训是下一阶段

壳模式的在线训练**只训策略头**（trunk 两层 Linear + vertical/horizontal + value，
纯 Swift + Accelerate，CPU 即可跑）。state_token 由冻结骨干的 CoreML 旁路加速器逐帧
产出，骨干**不参与在线梯度**。

骨干（视觉 + 时序主干）的更新是**下一阶段**：离线轻训，**在 Mac 本机用 MPS 跑、不上云**
（不上云 GPU 租赁/云训练服务）。理由：骨干只需要低频轻量微调（吸收在线阶段积累的
分布漂移），MPS 的吞吐足以在停机时段完成；策略头则吃「逐帧采样、即时反馈」的实时性，
所以两者分期。本阶段（速度三段 + 壳模式接线）不含任何骨干训练代码——把「实时只训头」
写死为当前架构事实，避免读者误以为壳模式已经在动骨干。

## 五、默认关 + digest 影子先行

**默认关是安全底线**：`OnlineTrainingRuntime` 构造即 `running == false`，未显式 `start()`
前 `onFrame` 一帧都不会采样、不会 collect（自检断言：灌 200 帧后 sampledFrames 仍为 0、
无任何 PPO 指标）。启动壳模式必须显式走 `start()`（其内部还要过加速器就绪检查）。

**digest 影子先行**：策略头采样出的动作**默认在 digest（消化）模式下走影子**——执行方
照常「算键」（ControlEngine 的状态链、计数、UI 状态机全部真实推进），但**不真发**
`CGEvent`，事件不离开本进程。所以训练开着跑也不会替人按键、不会打扰系统。

**真注入（live）需要显式许可**：只有环境变量 `AURORA_RL_LIVE_ACTUATION` 为 `1` 时，
真注入才被允许；缺省（未设或非 1）一律 digest。为杜绝「三处开关各说各话」，运行时对
digest 做**三源合并**统一核算：

```
effectiveDigest = digestMode(运行时基线，默认 true)
                  || 用户开关（ControlEngine.digestMode）
                  || !liveAllowed（AURORA_RL_LIVE_ACTUATION != 1）
```

三者**任一**为真，本帧动作就走 digest——也就是「不真发键」是**多锁串联**：基线默认开、
用户开关开、或没有 live 许可，任何一条成立都压回影子。要真正把训练动作发进游戏，
必须 live 许可为真**且**基线与用户开关都为 false，缺一不可。急停/人工接管立即让位的
护栏在两种模式下都始终生效。一句话：**先在影子里学会，再放手真开**。

## 六、自检与证据

壳模式相关共两个自检入口，职责不同、flag 不同，不存在重复：

- **`-rl-shell-selftest` / `--rl-shell-selftest`**（本文配套，入口类型 `ShellModeSelfTest.run()`，
  文件名因避免并发冲突落在 `ShellModeRewardSelfTest.swift`）：纯合成数据断言——
  ① 速度三段 99/100/130/160/161 逐值对拍手算值 + speedValid=false→0，且校验
  `frameReward` 速度项 == `config.speed × speedTerm`（用非默认权重 3.0 证明乘法真实发生）；
  ② 接管帧封口（markInvalid 清空 pending、人类动作不建 transition、-takeover 落在末条
  AI 帧上）；③ 策略头 `head_state_dict` 存盘→加载回环（先证两个种子权重不同、回环后
  逐元素一致，拒绝 NaN 假绿）；④ 默认关时 200 帧 onFrame 零采样/零指标。
- **`--shell-engine-selftest`**（shell-engine 域交付，`ShellModeControllerSelfTest`）：
  壳模式 start/stop 的**编排**自测（假硬件记录调用轨迹：退引擎→退驾驶→备抓屏→起训练，
  抓屏保活、stop 恢复引擎）。

两个入口互补：前者管「奖励口径与回环语义」，后者管「引擎编排轨迹」。此外
`-rl-online-selftest`（在线 RL 循环 11 段自检）与 Python 侧
`/usr/local/bin/python3.11 tools/v3_rl/run_tests.py`（含速度三段黄金值断言，断言数下限 500）
是回归总闸。所有自检均为合成数据：不真开游戏、不真训练、不需要屏幕录制权限。

## 七、边界与诚实声明

- 壳模式的**生产接线**（tick 侧把策略头采样动作接到真注入、UI 按钮状态机）由
  shell-engine / ui-shell / runtime-fix 三个域分别交付；本文锁定的是奖励口径、训练分期、
  digest/接管/停止/退出恢复/权重生命周期这些**语义契约**，具体实现以对应源文件为准。
- 速度三段是**用户口径的直译**（含 160 处的刻意跳变），不是从任何理论推导出的最优形状；
  若后续实测发现「贴着 160 开最稳但 161 立刻重罚」造成策略在 159-160 附近抖动，
  调整分界/宽度时必须**同时**改 Swift 与 Python 两边 + 两边黄金值断言，一处都不能漏。
- 碰撞保护不启用是**当前阶段的刻意决策**（用户明确选择），不是遗漏；文档与代码注释
  两处都写明，防止后续读者「顺手补上」。
