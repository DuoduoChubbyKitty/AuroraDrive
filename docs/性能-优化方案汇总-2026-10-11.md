## 2. 被排除的方案（违反铁律 或 净收益为负）

### 2.1 🔴 违反用户铁律（**一律不做**）

| **降分辨率 1280×832 → 更低** | — | 违反铁律；用户明确否决 |

## 5. 下一步建议

### 5.1 先做哪一条？→ **分两阶段**

**阶段 1（诊断，最高优先）**：**确认 ENGINE 侧 vImage 缩放的分项占比**
P5 已给出 #1 热点（vImage 1405 采样），但**三处缩放各自的占比未知**。先 `sample` 细分，才能决定改哪一处：
- YOLO 640×640（`CaptureEngine.swift:978`）
- UI 480×312（`CaptureEngine.swift:1024`）
- YOLOPX letterbox 640（`YolopxEngine.swift:1615`）

**为什么先诊断**：三处**同源但目标不同**（640 拉伸 / 480 等比 / 640 letterbox 语义不同），**不能盲目合并**——先搞清楚谁最贵，再动手。

**阶段 2（动手）**：**Top 1（消除 `inferFast` 重复拷贝）**

**理由**：
1. **收益明确**：省 70.3 MB/s = 自动驾驶总拷贝的 **42%**（P1 确定性计算，基于代码常量）；P5 实测 `_platform_memmove` **286 采样**佐证（排 #3）
2. **改动极小**：去掉一次 `copyPixelBuffer`（P1 §3 收益1 给了具体改法）
3. **风险可控**：风险点是"CoreML 是否同步持有 pixelBuffer" —— 这是**可验证的**（加引用计数断言），且 `isInferencing` 防重叠 + 池深度≥4 已提供缓解

**但必须先做验证**（P1 明确标注为最大未验证项）：
```swift
// 验证思路（伪码，非实际改动）：推理期间缓冲引用计数应 > 0

```

### 5.1b ⚠️ Top 4 已撤销（P5 核实后发现会破坏功能）

原 Top 4 建议「`onYoloFrame` 门禁 = `yoloEngine.enabled`」—— **经 P5 + 源码核实，这会断掉光流**：
`AuroraDriveApp.swift:7013` 的 `runOpticalFlow(on: yoloFrame)` **每帧执行、不受 `detectGateB` 门控**，
它消费的正是 `onYoloFrame` 产出的 640×640 帧。关掉缩放 = 光流断流 = **功能破坏**（风险从"低"改为"高"）。
**`onNativeFrame` 门禁仍可做**（收益 0.74 MB/s，极小）。

### 5.2 关于「5 倍目标」的诚实判断

**任务要求**：「如果报告里**没有任何"不降质量也能显著优化"的方案，如实说**」

**如实回答**：
- ✅ **有**"不降质量"的方案（Top 5 全部不违反铁律）
- ❌ **但没有一条是"显著"（5 倍量级）的**：
  - Top 1 省 42% 的**拷贝带宽** —— 但拷贝带宽（167 MB/s）本身只是抓屏（183 MB/s）的 91%，**省它不等于帧率提升**
  - **★ P5 实测确认瓶颈在 CPU**（+84.9pp）而 **GPU 只 +8.5pp** —— 所以"在 GPU 上优化"这条线**整体不可行**
  - Top 1b/1c/2/6 的收益**均未实测**（P3 §7.4 / P5 §8 明确标注）
  - Top 5 收益**量级小**（P2 说"需实测验证"）
  - **P2 明确结论**：「当前配置（1280×832@45fps + 32BGRA + queueDepth 3）**已接近"不降帧率/分辨率"前提下的最优**」
  - 原 Top 3（CIContext）**已被实施**，不再算"待做优化"

**⟹ 结论：靠"减少浪费"拿不到 5 倍。** 需要换思路（三个方向，**均需用户决策**）：
1. **换机器**（更强 CPU —— P5 证明瓶颈在 CPU 侧图像处理，不是 GPU/ANE）
2. **接受质量与性能的权衡**（如允许降帧率 —— 但违反当前铁律，须用户明确改口）
3. **继续定位真机 2.6-3.0 Hz 塌陷的根因**

**★ P5 对根因的贡献（比 P4 更进一步）**：
P4 排除了"推理抢 GPU"但**根因未定**；**P5 用真机 sample 定位了方向**：
```
engine 进程驾驶时 CPU 85~107%，热点排序：
  #1 vImage 缩放族 1405 采样   ← 1280×832 → 各下游尺寸
  #2 extractMask   465 采样   ← 车道线掩码提取
  #3 memmove       286 采样   ← inferFast 的重复拷贝（Top 1 目标）
  #4 vConvert_ARGB8888toPlanarF 223 ← 格式转换喂模型
  libBNNS 推理仅 241+176      ← 推理本身不是大头
```
**⟹ 瓶颈是「CPU 图像处理管线」（缩放+转换+掩码提取），不是推理、不是 GPU。**
P5 §10 建议：优先优化 engine 进程 CPU、查 UI 侧 vImage 格式转换能否在引擎侧一次做完、**不要在 GPU 上做优化**。

> **⚠️ 与 P4 的关系**：P4 的 5 个可疑方向中，第 1 个（CIContext GPU）**已被修复**；
