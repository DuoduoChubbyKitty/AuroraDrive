## 1. 帧尺寸：640×360 → 训练端 resize 到 320×180

### 1.1 录制端（实测）

**代码常量**：`RecordEngine.swift:31`
```swift
/// 输出帧尺寸（16:9 横屏，与 m9_mono 输入 180×320 同比例；训练端 MonoClipsDataset 等比缩放）
let targetSize = CGSize(width: 640, height: 360)
```

**实测（PIL 读真实文件）**：
```
$ ./.venv-yolo26/bin/python3 -c "…PIL…"
  data/raw_clips/clip_20260825_182145/frames/000000.jpg: 640x360 mode=RGB
  data/raw_clips/clip_20261010_133453/frames/000000.jpg: 640x360 mode=RGB
尺寸分布: {((640, 360), 'JPEG'): 220}
```
⟹ **实测 220 帧全部 640×360 JPEG**，与代码常量一致 ✅

### 1.2 ⚠️ 一处**注释错误**（不影响功能，但会误导后人）

`RecordEngine.swift:31` 注释原文称 **「与 m9_mono 输入 180×320 同比例」** —— **不准确**：
- `640×360` 是 **16:9 横屏**
- `180×320` 是 **9:16 竖屏**
- 两者**比例互为倒数**，并非"同比例"

**但实际链路是正确的**：训练端 resize 目标不是 `180×320`，而是 `(W,H) = (320,180)`（见 §1.3），
`640×360 → 320×180` 保持 16:9 **无失真**。所以功能正确、仅注释措辞有误。

### 1.3 训练端 resize（关键证据）

`dataset_v2.py:810-813`：
```python
with Image.open(img_path) as im:
    im = im.convert("RGB").resize(
        (self.image_size[1], self.image_size[0]), Image.BILINEAR)
    img = np.asarray(im, dtype=np.float32) / 255.0
```
`image_size = (H, W) = (180, 320)`（`dataset_v2.py:693/708`）→ resize 到 `(W,H) = (320, 180)`。

`model_v2.py:264-266`：
```python
IMG_H: int = 180
IMG_W: int = 320
```
⟹ **最终送入模型的是 `[3, 180, 320]`（H=180, W=320）**，与 resize 结果一致 ✅

**结论**：**尺寸链路正确，无比例失真，无需修改**。resize 用 `Image.BILINEAR`（抗锯齿一般但速度好），对车道线这类细结构**有一定模糊**，但这是既有设计（640→320 只降一半，损失可接受）。

## 2. JPEG 质量：0.9

`RecordEngine.swift:483-486`：
```swift
// 位图表示 → JPEG（训练端 mono_dataset 读 .jpg，质量 0.9 平衡清晰度/体积）
let bitmapRep = NSBitmapImageRep(cgImage: outImage)
return bitmapRep.representation(using: .jpeg,
                                 properties: [NSBitmapImageRep.PropertyKey.compressionFactor: 0.9])
```
⟹ **quality = 0.9** ✅ 合理（0.9 是"平衡清晰度/体积"的常用取值；再低会在车道线边缘产生块效应）。

**体积参考**（实测）：`data/raw_clips/` 6 clip / 220 帧 / 9.4MB ⟹ **约 43KB/帧**（640×360@0.9）。

⚠️ **一个值得注意的点**：JPEG 是**有损**压缩，车道线（细、高对比边缘）与速度表数字（OCR 依赖）是**最易受损**的内容类型。
- 项目已有实证：`tools/yolopx/export_yolopx_coreml.py:58-64` 记录过"细目标被量化打掉 10×"的教训（虽那是 INT8 量化，不是 JPEG，但同属"细结构易失"）
- **本审计未做量化评估**（需对比原始帧 vs JPEG 帧的车道线像素差）→ 标注 **未验证**
- 建议：若训练后车道线分支表现差，应排查 JPEG 质量是否为因素之一

### 3.3 训练端认什么

`dataset_v2.py:221-232`（**逐字**）：
```python
def _clip_view(clip_dir: Path) -> Optional[str]:
    """从 view.txt 或 clip.json 读取整体视角标签；无法判断返回 None。"""
    vt = clip_dir / "view.txt"
    if vt.exists():
        raw = vt.read_text().strip().upper()          # ← 纯文本读，不是 json.loads
        if raw in ("TPV", "FPV", "MENU"):
            return raw
    cj = clip_dir / "clip.json"                        # ← json.loads 是给 clip.json 的
    if cj.exists():
        try:
            v = str(json.loads(cj.read_text()).get("view", "")).strip().upper()
            if v in ("TPV", "FPV", "MENU"):
                return v
        except (json.JSONDecodeError, KeyError, TypeError, OSError):
            pass
    return None
```

**⚠️ 更正任务描述的一处误读**：任务描述说「`dataset_v2.py`（约 231 行 `json.loads(cj.read_text()).get("view","")`）认 `third` 还是 `TPV`」——
**`:231` 的 `json.loads` 读的是 `clip.json`，不是 `view.txt`**。
`view.txt` 走的是 `:225` 的 `read_text().strip().upper()`（**纯文本 + 转大写**）。
（好在 `clip.json` 那条路径也是 `.upper()` 后比 `"TPV"`，两条路径口径一致。）

⟹ **训练端认的是 `"TPV"` / `"FPV"`（大写）**，与录制端 `viewLabel` **完全一致** ✅

```python
def _frame_path(clip_dir: Path, fmt: str, frame_no: int) -> Optional[Path]:
    """…**两种命名约定都尝试**（顺序：cam00_ 优先 = 前向相机）：
         v2_new: cam00_000000.jpg      v1_old: 000000.jpg
       这样即使 controls.csv 表头与实际帧命名不一致（混合 clip）也不会整 clip 丢帧。"""
    stems = (f"cam00_{frame_no:06d}", f"{frame_no:06d}") if fmt == "v2_new" \
            else (f"{frame_no:06d}", f"cam00_{frame_no:06d}")
    for stem in stems:
        for ext in (".jpg", ".jpeg", ".png"):
            p = frames_dir / f"{stem}{ext}"
            if p.exists():
                return p
    return None
```

⟹ **两种命名都试、三种扩展名都试** ✅ **完全兼容** `000000.jpg`。

**结论**：帧命名**无阻塞**。

## 6. 🔴 新发现：view_filter 默认 None = 不筛视角（混训风险）

`dataset_v2.py:696/711`：
```python
def __init__(self, …, view_filter: Optional[str] = None, …):
    self.view_filter = view_filter
```
`:732-735`：
```python
if view_filter:
    clips = [c for c in clips if _clip_view(c) == view_filter]
    if not clips:
        raise RuntimeError(f"没有 view={view_filter} 的 clip")
```
`train_v2.py:203/1669`：`view_filter=None`（**默认**）

⟹ **默认训练会把 FPV 与 TPV 的 clip 一起训**。
而 `model_v2.py:15/154` 明确写模型输入是**「第三视角截图」**。

**风险**：若数据集里混有 FPV 帧，模型会在两种视角上学同一个 steer 映射 →
- 第一视角：画面中心是消失点
- 第三视角：能看到自己的车，消失点不在中心

**同一 steer 标签对应两种完全不同的画面几何** ⟹ 模型学到的映射会被污染。
（项目文档 `docs/主驾驶模型换代-需求与方案-2026-10-08.md:29` 已指出「标签是录制器自己填的常量，不是从画面判定的」。）

**建议**：
1. **录制时确保全部 TPV**（用户需求），这样即使不筛也不会混
2. **训练时显式传 `view_filter="TPV"`**（防御性；且能快速发现"录成了 FPV"）
3. 若将来需要 FPV 数据，**必须分视角训练或加视角条件输入**，不能混

**注意**：`_clip_view` 对**没有 view.txt 也没有 clip.json** 的 clip 返回 `None` →
`view_filter="TPV"` 时**这类 clip 会被过滤掉**（`None != "TPV"`）。这是**正确且安全**的行为
（宁可少用数据，也不用视角未知的数据）。
