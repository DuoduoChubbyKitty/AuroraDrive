## 0. 摘要（TL;DR）

抓屏 **1280×832 @45fps**（192 MB/s 像素流）每帧被 **5 条下游链路**消费。审计结论：

| 链路 | 门禁 | 门禁在拷贝前？ | 必要性 | 可跳过？ |
|---|---|---|---|---|
| ① `onNativeFrame`（速度表 ROI） | **无门禁**（仅 `if let`） | — | OCR 读速 + 字模录制 | ⚠️ **可加门禁**（见 §3.1） |
| ② `onUpscaleFrame`（全分辨率） | `isUpscaleWanted()` | ✅ **是**（`:940`） | 插帧/超分 | ✅ 已优化 |
| ③ `onYoloFrame`（640×640） | 无门禁（仅 `if let`） | — | YOLO 检测 | ⚠️ **可加门禁**（见 §3.2） |
| ④ UI 帧（480px 缩略） | **无门禁** | — | UI 显示 / 录制 / 推流 | 🔴 **最大的可跳过项**（见 §3.3） |
| ⑤ `currentFrame` / `currentFrameCG` | 无（是 ④ 的产物） | — | 工具/自检/AI 面板按需读 | ✅ 无额外成本 |

**三个最重要的发现**：
1. 🔴 **UI 帧（480px vImage 缩放 + CGImage + NSImage）无条件每帧生成** —— 即使 UI 面板不可见、不录制、不推流（`§3.3`）
2. ⚠️ **`onNativeFrame`（速度表 ROI）无门禁** —— 不录字模、OCR 不需要时仍每帧拷贝（`§3.1`）
3. 🔴 **训练/推理宽高比不一致**（**新发现，非任务要求但影响模型正确性**）：源 1280×832（3:2）被拉伸到 320×180（16:9），而训练数据是 640×360（16:9）等比缩放 —— **推理时横向被压缩 13.5%**（`§4`）

## 2. 门禁审计（"门禁关了但拷贝已做"的浪费）

### 2.1 ✅ 正确：`onUpscaleFrame`（唯一门禁在拷贝前的）
`CaptureEngine.swift:940-943`：
```swift
// 门禁先于拷贝求值：插帧/清晰画面关闭时连全分辨率拷贝都不做
if let onUpscaleFrame, isUpscaleWanted(),
   let upscaleCopy = copyUpscaleFrame(from: pixelBuffer) {
    onUpscaleFrame(upscaleCopy)
}
```
**顺序正确**：`isUpscaleWanted()`（闭包，纳秒级）在 `copyUpscaleFrame`（全分辨率拷贝，1280×832×4 ≈ **4.3MB**）**之前**求值 ✅
**门禁来源**：`EngineMain.swift:791`（引擎侧 `wantFullFrame`）/ `AuroraDriveApp.swift:6026`（UI 侧 `upscaleEnabled`）。

### 2.2 ⚠️ `onNativeFrame` 无门禁
`:932-934`：
```swift
if let onNativeFrame, let nativeCopy = copyNativeFrame(from: pixelBuffer) {
    onNativeFrame(nativeCopy)
}
```
**只有 `if let`（回调是否注册），没有"要不要"的门禁**。
**浪费场景**：不录字模（`glyphMode == false`）且 OCR 不需要该帧时，仍每帧做 ROI 拷贝。
**成本**：速度表 ROI 区域（取决于 `nativeROI` 配置），比全帧小但仍是逐行 memcpy。

### 2.3 ⚠️ `onYoloFrame` 无门禁
`:947-983`：`if let onYoloFrame { … vImageScale_ARGB8888 … onYoloFrame(yb) }`
**只有 `if let`**。每帧都做 **vImage 缩放到 640×640**（CPU 双线性）。
**浪费场景**：YOLO 检测被停用（`yoloEngine.enabled = false`）时仍每帧缩放。

### 2.4 🔴 UI 帧（④）无门禁 —— 最大项
`:995-1061`（**无条件执行**）：
```swift
let maxWidth: CGFloat = 480
let uiScale = min(1.0, maxWidth / sw)
...
vImageScale_ARGB8888(&srcBuf, &dstBuf, nil, kvImage_Flags(kvImageNoFlags))   // 缩放
...
let provider = CGDataProvider(...)      // 零拷贝包装
guard let cgImage = CGImage(...) else { … }
let nsImage = NSImage(cgImage: cgImage, size: NSSize(width: dW, height: dH))
currentFrame = nsImage
onFrame?(nsImage, cgImage)
```
**每帧无条件做**：
- `vImageScale_ARGB8888`：1280×832 → 480×312（**CPU 缩放，约 1.6M 像素**）
- `CGImage` 创建（零拷贝，但仍需分配对象 + 校验）
- `NSImage` 创建
- `CVPixelBufferPool` 取缓冲

**为什么这是最大项**：即使
- UI 面板**不可见**（用户在游戏全屏，Aurora 面板收起）
- **不录制**
- **不推流**（`isStreaming == false`）
- 甚至**不在驾驶**（待机）

…这 4 件事仍每帧发生。

## 3. 可跳过项（按收益排序，**均不违反"不降帧率/分辨率"铁律**）

> ⚠️ 以下为**审计建议**，未实施（本任务只读）。每条都注明"为什么不算降质量"。

### 3.1 🔴 最高收益：UI 帧按需生成（门禁化 ④）

**现状**：480px 缩放 + CGImage + NSImage **无条件每帧**。

**建议**：加门禁，仅在**至少一个消费者需要**时生成：
```swift
// 伪代码（示意）
let needUIFrame = onFrame != nil && (
       state.isPanelVisible          // UI 显示
    || state.isRecording             // 录制
    || state.isStreaming             // 推流
    || state.isDriving               // 驾驶（推理需要 currentFrameCG）
    || state.toolsMayNeedFrame       // 工具/自检按需
)
```
**为什么不算降质量**：
- **帧率不变**（只是不生成没人看的缩略图）
- **分辨率不变**（需要时仍是 480px）
- UI 面板不可见时，那张图**没有任何消费者**

**风险**：需确认"工具/自检/AI 面板"按需读 `currentFrame` 时能触发一次生成（否则会拿到 nil）。
**建议实现方式**：不是"完全不生成"，而是"**按需生成**"——即消费者请求时才做，或用一个"下次 tick 需要"的标志。

**预估收益**（未实测，需 V 系列验证）：省掉每帧 1280×832→480×312 的 vImage 缩放 + CGImage/NSImage 对象创建。

### 3.2 ⚠️ 中收益：`onNativeFrame` / `onYoloFrame` 加门禁

**`onNativeFrame`**：门禁条件建议 `glyphMode || speedOCRNeedsFrame`
**`onYoloFrame`**：门禁条件建议 `yoloEngine.enabled`

**为什么不算降质量**：消费者关闭时不生成，开启时照常。
**风险**：OCR 是持续需求（车速一直在读），故 `onNativeFrame` 的门禁收益可能有限 —— **需实测 OCR 是否真的每帧都需要**（若 OCR 自身有降频逻辑，可对齐）。

### 3.3 ✅ 已优化：`onUpscaleFrame`
门禁已在拷贝前（`:940`），无需改动。

### 3.4 不建议动的
- **`currentFrame` / `currentFrameCG`**：是 ④ 的副产品，无独立成本
- **YOLO 的 640×640 vImage 缩放**：这是**消除 GPU 排队卡顿**的有意设计（`:956-957` 注释：改用 CPU vImage 消除游戏占满 GPU 时 CIContext 排队导致的 40ms 卡顿），不能回退到 GPU

## 4. 🔴 新发现（超出任务范围，但影响模型正确性）

### 4.1 训练/推理的宽高比不一致

| 环节 | 源尺寸 | 宽高比 | 目标 | 方式 | 变形？ |
|---|---|---|---|---|---|
| **训练**（`dataset_v2.py:810-812`） | 640×360 | 1.778:1 | 320×180 | `Image.BILINEAR` resize | ✅ **等比，不变形** |
| **推理**（`InferenceEngineV2.swift:3023`） | **480×312** | **1.538:1** | 320×180 | `context.draw(cgImage, in: CGRect(0,0,320,180))` | ❌ **拉伸，横向压缩** |

**证据**：
```swift
// InferenceEngineV2.swift:3023（旧引擎 InferenceEngine.swift:464 同）
context.draw(cgImage, in: CGRect(x: 0, y: 0, width: width, height: height))
```
`context.draw(in:)` 是**强制填充矩形**，不保持宽高比。

**根因**：抓屏源是 **1280×832**（`:439-440` 按屏幕 3:2 宽高比计算），而模型输入 320×180 是 16:9。

**量化**：1.538 → 1.778，**横向压缩约 13.5%**。

**为什么这是问题**：
- 训练时模型看到的是**等比**的车道线几何（640×360 → 320×180）
- 推理时看到的是**横向压扁**的几何
- ⟹ 车道线斜率、曲率、横向偏移的**视觉特征分布不一致** → 模型学到的映射在推理时偏移

**注**：这**不是**本次改动引入的（旧引擎 `InferenceEngine.swift:464` 同样处理），是**既有问题**。
**建议**：转给模型侧/训练侧评估——要么推理改成 letterbox 保持比例，要么训练也按 1280×832 的 3:2 比例做数据增强。

**⚠️ 本发现需独立验证**：本审计只做了**代码级推断 + 算术**，**未实测**（未跑模型对比训练/推理的输入分布）。建议 V 系列验证。

### 4.2 重复缩放审计（任务点 5）

**任务问**：「有没有重复缩放（YOLO 缩到 640×640，模型又缩到 180×320）？」

**答案：没有重复缩放同一份数据，但存在"多次独立缩放同一源帧"**：

| 链路 | 从源（1280×832）缩到 | 方式 | 独立？ |
|---|---|---|---|
| YOLO | 640×640 | vImage（CPU） | 独立缩放 #1 |
| UI 帧 | 480×312 | vImage（CPU） | 独立缩放 #2 |
| V2 模型 | 480×312 → 320×180 | CGContext.draw | 从 **UI 帧**再缩（#3，**基于 #2 的产物**） |

**关键点**：V2 模型**不是从源直接缩**，而是**从 UI 帧（480×312）二次缩放** → 意味着
- 多一次缩放（480→320）
- 且**继承了 UI 帧的尺寸约束**（480px 是为 UI 显示选的，不是为模型选的）

**建议**：若要让模型拿到最佳质量，应从**源帧直接缩放**到 320×180（而非经 480px 中转）。但这会增加一次独立缩放的成本 —— **需权衡**。

## 6. 录制链路审计（任务点 4）

**`RecordEngine.appendFrame`**（`:464`）：
- **拿到的 `image` 是 `currentScreenImage`**（`AuroraDriveApp.swift:7768`）——即 **UI 帧（480×312）**，**不是全分辨率**
- 内部 `resizeAndEncodeJPEG`（`:483-486`）再缩到 `targetSize = 640×360` 并编码 JPEG quality 0.9

**⚠️ 注意**：480×312 **放大**到 640×360（**上采样**）→ 损失细节。
这是"为省 UI 帧成本（480px）而牺牲录制质量"的**既有权衡**。
（若录制质量重要，可考虑录制走独立的全分辨率路径——但会增加成本，**需权衡**。）
