## 1. ★ 真白干：assistEngine.infer() 在 e2e 模式下每帧推理（item ⑥）

### 1.1 证据链（逐行读源码，非推测）

**调用点**：`AuroraDriveApp.swift:7151`
```swift
assistEngine.infer(image: cg, speedKmh: effectiveSpeed, speedLimitKmh: speedLimit)  // 第二套驾驶模型
```
**位置**：在 `if !forceRuleMode`（:7104）的 **if 块内**，但 **V2 与旧 M9 互斥分支之后**——也就是说，无论走 V2 还是走旧 M9，`assistEngine.infer()` **都执行**。

**输出消费点**：`:7230` `let assistCommand = commandOf(assistEngine)`
- `:7496` `case .yolo: if currentCommand != assistCommand { currentCommand = assistCommand }` —— **只在 `.yolo` 模式才消费**
- `:7330` `let healthCommand = (mode == .e2e) ? m9Command : assistCommand` —— **e2e 模式下用 m9Command，不用 assistCommand**

**含义**：当 `mode == .e2e`（**默认主驾模式**，V2/M9 开车），`assistEngine.infer()` 每帧推理 ~8ms，但**输出不被任何人消费**——纯白干。

### 1.2 量级估算

- `assistEngine` 是 `InferenceEngine`（旧 M9 架构），单帧推理 ~8-16ms（按 P4 实测的旧 M9 CPU 路径）
- 假设取 p50 ≈ 8ms，20Hz tick → **每秒白干 ~160ms CPU**（约占一核的 16%）
- **降级链绝大多数时间停在 `.e2e`**（模型正常时不会降级）→ 这个白干是**常态**

### 1.3 为什么这是"白干"而非"必要预热"

项目的档位注释（`:7163`）写：
> 「M9 / assist 两个驾驶模型**不降频** —— 它们是"每帧出一个控制量的主司机"」

**这个理由对 M9（主驾）成立，对 assistEngine 不成立**：
- M9 在 `.e2e` 模式下**就是主司机**，输出被消费 → 不降频正确
- assistEngine 在 `.e2e` 模式下**不是主司机**，输出不被消费 → 不降频 = 白干

**降级链的辩护**：若跳过 assistEngine.infer()，从 `.e2e` 降级到 `.yolo` 时会有**1 帧冷启动**（assistEngine 用上一帧的旧输出）。但：
- 降级是**低频事件**（模型挂了才触发），1 帧间隔（50ms@20Hz）在驾驶语义上可忽略
- 而白干是**每帧常态**（除非用户主动切 `.yolo` 档）

### 1.4 建议方案（供 Lead 决策，不在本任务范围）

```swift
// 方案 A：只在 .yolo 模式或即将降级时跑 assistEngine
if mode == .yolo || (confidence < degradeThreshold * 1.5) {
    assistEngine.infer(...)
}
// 代价：降级时第 1 帧用旧输出（可接受）
// 收益：e2e 模式下每秒省 ~160ms CPU
```

⚠️ **需 W1/W3 评估降级链时序**：assistEngine 从跳过到首次推理有冷启动（模型已加载，非 MLModel 加载，只是首帧 inference ~8ms）。

| 模型 | 早退门 | 证据 |

**结论**：模型常驻内存、首次加载后不重复加载、不卸载 ✅。每帧调 `loadIfNeeded()` 有廉价早退（一个 Bool guard）。

### 2.2 推理队列空转（item ②）

`grep -rn "makeTimerSource|Timer.scheduled|DispatchSource.makeTimer" Sources/AuroraDrive/Inference/` → **0 命中**。

推理队列（`inferenceQueue`）是串行 DispatchQueue，只在 `infer()` 的 `.async` 投递时工作，无定时器空转 ✅。

### 2.3 V2/world_model 每帧调用（item ③）

- `loadIfNeeded()` 每 tick 调用（`:7113`），但开头有 `guard !isLoaded else { return }`（:1709）→ 模型已加载时**零开销 return**
- `worldModelURL` 是 computed property（每次访问构造 URL + `fileExists`），但被 `if !worldModelLoaded, let wmURL =` 保护：首次加载成功后 `worldModelLoaded=true` → **不进 body → 不求值** ✅
- `runWorldModel` 有 `if let wm = self.worldModel` 门禁（:2232/:2309/:2393）→ world_model 缺失时 nil → **跳过** ✅

### 2.4 光流 ayolom 档白跑（item ④）

`AuroraDriveApp.swift:7029`：
```swift
if !Self.opticalFlowDisabled, perceptionMode.needsOpticalFlow {
    runOpticalFlow(on: yoloFrame)
}
```
- `PerceptionMode.ayolom.needsOpticalFlow = false`（`YolopxEngine.swift:247`）→ **ayolom 档不跑光流** ✅
- 注释（`:7008`）明确记录：`needsOpticalFlow` 此前全仓只被 3 处读、**全是显示/断言**，**没有行为分支**——现已提升为实际门禁 ✅

### 2.5 OCR 高频空转（item ⑤）

`SpeedOCRReader.infer()`（`:531`）开头：
```swift
func infer(nativePixelBuffer: CVPixelBuffer) {
    ensureModelsLoaded()          // ← 在 15Hz 节流闸之前
    // ...
    guard ... >= Self.inferInterval else { return }  // 闸 1：15Hz 节流
    guard !isInferencing else { return }              // 闸 2：防重叠
```

`ensureModelsLoaded()`（`:318`）：
```swift
private func ensureModelsLoaded() {
    guard !modelsLoadFinished else { return }   // ← 首次加载后直接 return
    modelLoadQueue.sync { }
    // ...
}
```

**结论**：首次加载完成后 `modelsLoadFinished=true`，每帧调 `ensureModelsLoaded()` 只是**一个 Bool guard + return**（零开销）✅。15Hz 节流闸在它之后，也不受影响。

**但**：OCR 在**画面无速度表**时是否仍跑？—— 15Hz 节流只按**时间**节流，不按**画面内容**判断。即"画面没有速度表 → OCR 仍每 1/15s 跑一次 → 识别失败 → 返回 -1"。这是**轻微白干**（OCR 单帧 ~2ms × 15/s = 30ms/s），但量级远小于 assistEngine 的 160ms/s。且判断"画面有无速度表"本身需要画面分析（不划算）。

### 2.6 pixelBufferPool 深度 4（item ⑦）

`CaptureEngine.swift:1249`：`[kCVPixelBufferPoolMinimumBufferCountKey: 4]`

- 这是 **MINIMUM**（预分配 4 个），不是 **MAXIMUM**
- 注释（`:346`）：「全部在途时 `CVPixelBufferPoolCreatePixelBuffer` 会**自行扩容**」
- `autoreleasepool` 覆盖：`CaptureEngine.swift:1076`（整帧处理逻辑包进 autoreleasepool，帧末统一释放）
- 20Hz 下：生产 20/s、消费 ~40-100/s（推理 10-26ms < 50ms 间隔）→ **不积压** ✅
- **风险**：若主线程阻塞 >200ms（4 帧缓冲耗尽），pool 会扩容 → 内存缓涨。但 autoreleasepool 在帧末释放，**正常情况下不会持续增长** ✅
