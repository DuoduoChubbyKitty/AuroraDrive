## 2. 代码改动逐条（文件:行 + 根因 + 修法）

### 2.1 ✅ 已修：`YoloEngine.swift:77` maxDetections 20 → 300

- **文件:行**：`Sources/AuroraDrive/Inference/YoloEngine.swift:77`
- **根因**：`YoloEngine` 实际加载的 `models/yolo26s.mlmodelc` 是 **NMS-free 端到端**模型，
  输出张量 `[1,300,6]`（coremltools 读 spec 实测），**网络自身已定死上限 300**。
  运行时代码却又砍到 20 —— 这是 FastestV2 时代的历史遗留值。
  该截断使框数在**到达 `AutoRoadCondition.condition()` 之前**就被压到 ≤20，
  于是 `medium(>30)/busy(>50)/extreme(>70)` 三档在类型上就不可达。
- **修法**：改为 `300` = **不额外截断**，让模型全部输出进入路况判定与 UI。
  选择 300 而非其他值，是因为它与模型输出上限、以及 `YolopxEngine.swift:167`（同批已设 300）
  **三处对齐**，不留任意数字。
- **注释**：已在原位写明「为什么是 300」+ 实测数据 + 明确指出「本改动在现有素材上暂无可见行为差异，
  意义是解除截断、让三档具备可达性」——**不夸大修复效果**。

### 2.2 ⛔ 未改：`ControlWiring.swift` 5 个阈值（70/50/30/20/10）保持原值

- **文件:行**：`Sources/AuroraDrive/App/ControlWiring.swift:448-452`（5 个阈值数字，**一行未动**）
- **修法**：**只加注释，不动数字**。在 `AutoRoadCondition` 枚举上方（`:421-443`）新增「标定状态」段，
  如实记录：实测分布（129 帧 P50=7 / P100=7；yolo26s 恒 2；4 张行车图 2–16）、
  各档命中率（4 个 0/129 + 1 个 129/129）、根因（数字来自 COCO-80 时代数量级）、
  以及**不改的理由（数据不足）**，并留「改动前请先读本段」的警告。
- **为什么值得单独强调**：这段注释是**反误导**装置 —— 没有它，后来者看到
  `extremeThreshold = 70` 会以为它被标定过。现在它自带「未标定」标记与证据链。

### 2.3 未改：`YolopxEngine.swift:167`（已为 300）

核对确认与 `YoloEngine` 现已一致，无需改动。

## 3. 「数据不足」声明（为什么 §2.2 不改阈值）

要重标定 5 个分位阈值，素材必须**覆盖从稀疏到密集的连续车流**。现有素材的实情：

| 素材 | 帧数 | 实际内容 | 能否用于标定 |
|---|---|---|---|
| `tools/yolopx/inference/image/*.jpg` | 4 张 | BDD100K 风格**真实道路**，但这是**域外**（本项目跑游戏画面）；框数 2–16 | ❌ 域外 + n=4 |
| `data/raw_clips/*/frames/*.jpg` | 129 帧 | **本域**，但拆开看是 **5 个片段、合计 6.14 秒** | ❌ 见下 |

**129 帧的真实成色（关键）**：

```
clip_20260825_182145: 23帧 0.85s 640x360   steer/throttle/brake 全为 0
clip_20260825_182147: 12帧 0.40s 640x360   steer/throttle/brake 全为 0
clip_20260922_003025:  2帧 1.88s 640x360   steer/throttle/brake 全为 0
clip_20260922_003027: 22帧 0.68s 640x360   steer/throttle/brake 全为 0
clip_20260922_003029: 70帧 2.33s 640x360   steer/throttle/brake 全为 0
─────────────────────────────────────────
合计 129 帧 / 6.14 秒，视角 FPV，**控制量自始至终为 0**
```

「129 帧」听起来像大样本，实际是**6 秒静止画面**，且 YOLOPX 后 90+ 帧框数**恒为 7**
（序列 `[…,7,7,7,7,7,…]`）—— 高度冗余，**有效独立样本远少于 129**。

**因此**：
- 这 6 秒静止素材**无法**区分「简单」与「极度复杂」——它连一辆车的变化都没有；
- 用它拟合 5 个阈值，等于**用常数分布去定 5 个分位数**，数学上无意义；
- 结论：**数据不足，阈值保持原值。** 这符合任务书第 ③ 条（「若 4 张图数据量不足以标定，
  明确说明数据不足，只修死档位问题，不要瞎调阈值」）。

**建议的取材方向（交给后续任务，本任务不做）**：需要**本域、行驶中、车流有稀疏→密集变化**的
连续录制（≥几分钟，控制量非 0），采样后按帧统计框数分布，再定 5 个分位。

## 5. 局限与未验证（诚实清单）

1. **cap=20 是否会影响未来真实车流，未验证。** 实测只说「在现有 133 帧上截断从未生效」，
   **不能**推断「以后的密集车流也永远不会超 20」。若将来密集车流让框数升至 30+，
   原 20 会静默吃掉框并压制路况 —— 本修复正是为此提前解除闸门。
2. **YOLOPX 在 YOLOPX→UI 链路里的实际框数未在真机验证。** 本报告是**离线**用 Python +
   coremltools 复算，与 Swift 运行期可能存在差异（如预处理实现细节）。
   本报告的框数是**离线口径**，不等于运行时读数。
3. **两组口径差异（0.30 vs 0.25）未统一。** 我按「以运行期为准」记录，但**没有**去改官方
   脚本或运行期参数（不在 in-scope，且改它会牵动精度验收）。
4. **游戏内车流场景未覆盖。** 6 秒静止 FPV 不代表实际对局。
5. **129 帧的有效独立样本数未量化。** 只说「远少于 129」（后 90+ 帧框数恒 7），未做帧间去相关分析。
