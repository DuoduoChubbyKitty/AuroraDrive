## 一、大地图缺陷：根因是「地图浏览」与「自车定位」被绑成了一件事

### 1.1 现象
- 点小地图的「打开大地图」→ 弹层打开，但底图**永远钉在同一处**
- 无法放大缩小
- 游戏未启动时尤为明显，观感"一坨屎"

### 1.2 根因（代码级）

`Sources/AuroraDrive/App/MapWiring.swift:34-42`：

```swift
var mapPixelX: Double {
    guard locatorFound else { return MapTileImage.mapPixels / 2 }   // ← 退回地图正中心
    return Self.worldToMapPixelX(locatorX, locatorY)
}
var mapPixelY: Double {
    guard locatorFound else { return MapTileImage.mapPixels / 2 }
    return Self.worldToMapPixelY(locatorX, locatorY)
}
```

**`locatorFound` 是唯一开关**，而它只在游戏运行、抓到 30031 包时才为真。

| 游戏状态 | `locatorFound` | `mapPixelX/Y` | 大地图表现 |
|---|---|---|---|
| 运行中 | true | 真实自车位置 | 跟随自车 |
| **未启动** | **false** | **恒为 6528（13056/2）** | **钉死地图正中心** |

**所以不是"打不开"，是"打开了但永远卡在地图正中心"。**

### 1.3 缩放的真相：从来没写过

`Sources/AuroraDrive/App/MissionConsole.swift:2031`：

```swift
private let spanMeters: Double = 1200   // ← 硬编码常量，不是 @State
```

全项目 grep `MagnifyGesture` / `zoom` / `scaleEffect` 于地图组件——**零结果**。

**结论：缩放功能不存在，不是坏了。** `spanMeters` 是 `let` 常量，没有任何可变入口。

### 1.4 两个地图的耦合关系（关键）

两处渲染共用同一套 `mapPixelX/Y`：

| 位置 | 组件 | 用的坐标 |
|---|---|---|
| `MissionConsole.swift:967` | `MiniMapCard`（小地图） | `state.mapPixelX/Y` |
| `MissionConsole.swift:2045` | `LargeMapCanvas`（大地图） | `cx/cy` ← 来自 `state.mapPixelX/Y` |

**两者都挂在同一个 `locatorFound` 上。**

### 1.5 设计判断：这是架构错误

| 地图 | 应有语义 | 当前实现 |
|---|---|---|
| 小地图 | 跟随自车（"我周围有什么"）→ **依赖定位合理** | ✅ 符合，未定位时显示"游戏未运行·无定位数据源"覆盖层 |
| 大地图 | 自由浏览（"世界长什么样"）→ **不应依赖定位** | ❌ 错误地绑在 `locatorFound` 上 |

**大地图本质是「地图浏览器」，不是「自车仪表」。** 它的视角中心应当：
1. 有自己的独立状态（`@State`），不是派生的 `let`
2. 初始值：有定位时取自车位置，无定位时取地图中心
3. 之后**完全由用户手势控制**（拖拽平移 + 滚轮/双指缩放）
4. 定位只负责画"我在哪"的图标，**不控制视角**

### 1.6 修复方案（已实施，2026-09-23 00:20 部署验证）

```
MapViewport（新，@State 状态）
├─ centerX / centerY   视角中心（地图像素）
├─ spanMeters          视野范围（可变，替代硬编码 let）
├─ 手势：DragGesture → 平移；MagnifyGesture + 滚轮 → 缩放
└─ 「回到自车」按钮：有定位时一键归位

MiniMapCard   继续用 state.mapPixelX/Y（跟随自车，语义不变）
LargeMapCanvas 改用 MapViewport（自由浏览）
```

#### 实际落地的改动清单

| 文件 | 改动 |
|---|---|
| `MissionConsole.swift` | 新增 `@Observable final class MapViewport`（centerX/Y、spanMeters、userMoved、spanRange 120…12000、zoom/setSpan/pan/recenter） |
| 同上 | `LargeMapCanvas` 改用 `vp.centerX/Y` + `vp.spanMeters`，不再读 `state.mapPixelX/Y` |
| 同上 | 自车图标/导航线改用 `worldToMapPixelX/Y` 再按视口换算（原先混用 `normMapXLarge` 导致平移后漂移） |
| 同上 | 右上角新增 `+` / `−` / 归位 三个 `MapCtrlBtn` |
| 同上 | 新增 `DragGesture` 平移（锚点式，避免累积误差）+ `MagnifyGesture` 缩放 |
| 同上 | 新增 `MapScrollZoom`（NSViewRepresentable）接管滚轮 |
| 同上 | `MiniMapCanvas` 的**自车蓝点与底图改为 `locatorFound` 才画**（原先无条件画，游戏没开也显示假蓝点） |

#### 三个必须记下来的坑

**坑 1：`MagnifyGesture` 的 `magnification` 是相对手势起点的累计倍数，不是帧增量。**
逐帧 `span /= magnification` 会复利放大误差（捏一下视野直接飞到 12000m 上限）。
正解：`onChanged` 第一次记下起始 span，之后每帧 `setSpan(起始 span / magnification)`。

**坑 2：滚轮缩放不能靠 `hitTest`。**
- `hitTest` 返回 `nil` → AppKit 找不到 `scrollWheel` 接收者，事件直接穿过，缩放永远收不到。
- `hitTest` 返回 `self` → 整层盖住地图，`mouseDown` 全被吃掉，拖拽平移和按钮点击全废。

两条路都是死路。正解：`hitTest` 保持 `nil`（完全不参与命中测试，点击/拖拽照常给 SwiftUI），
滚轮改用 `NSEvent.addLocalMonitorForEvents(matching: .scrollWheel)` 按坐标接管。

**坑 3：`ImageRenderer` 渲染不了 `NSViewRepresentable`。**
离屏自检夹具里只要挂了 `MapScrollZoom`，整块地图会被渲染成系统占位图（黄底红禁止符），
夹具验的是占位符而不是真地图，等于白测。
正解：`LargeMapCanvas` 加 `interactive: Bool = true` 参数，夹具传 `false`。

#### 验证方式（可复现）

新增一次性夹具 `--mc-map-offline`，把"游戏未启动"这条路径固化下来：

```bash
./AuroraDrive --mc-map-offline   # 无定位场景 → /tmp/aurora_mc_map_offline.png
./AuroraDrive --mc-map           # 有定位场景 → /tmp/aurora_mc_map_online.png
```

实测结果（2026-09-23 00:20）：离线夹具渲染出真实地图底图 + 5,677 个标记，
底栏读数 `视角 6528,6528 · 未定位（可自由浏览）`、`视野 1,200 m`，
右上角三个缩放按钮齐备。真机小地图显示「游戏未运行·无定位数据源」且**无蓝点**。

## 二、加速度：数据已在包里，只是被丢弃了（已接通，2026-09-23）

> ⚠️ **勘误**：本文初版把解析位置写成 `NetworkLocator.swift:127`。
> 后续核实该文件里的 `UE5PacketDecoder` / `NetworkLocator` / `DualModeLocator`
> **全部是死代码**（全项目无任何实例化，仅 `LocateContext` 留了个 `NetworkLocator?` 字段但从不赋值）。
> **真正在跑的路径是 `Capture/CoordinateCapture.swift` 里的 `UE5Decoder`**，
> 由 `DriveState.runNetworkLocateStep()` 经 `cc.read()` 消费。下文已按实际活跃代码更正。

### 2.1 发现位置（活跃路径）

`Sources/AuroraDrive/Capture/CoordinateCapture.swift`：

```swift
// findCandidates 里（约 307 行）—— 加速度其实已经解析出来了
guard let (accel, cursor, accelBits, accelScaled) =
    ue5Vector(payload, offset: offset + 32, scale: 10) else { continue }
...
output.append(Candidate(clientTime: ..., offset: offset,
                        acceleration: accel, location: location))   // ← 存进了 Candidate

// decode 里（约 280 行）—— 但取出来时用 _ 丢掉了
guard let (_, cursor1, _, _) = ue5Vector(payload, offset: bitOffset + 32, scale: 10) else { return nil }
//          ↑ 这里丢的
```

**加速度一直躺在 `Candidate` 结构里，只是 decode 时没用。**

### 2.2 30031 包的实际结构（已解析部分）

| 偏移 | 字段 | 缩放 | 现状 |
|---|---|---|---|
| `offset` | clientTime (float32) | — | ✅ 用（时间对齐） |
| `offset+32` | **acceleration**（3 分量） | ÷10 | ✅ **已接通**（2026-09-23） |
| `offset+64` | location（3 分量） | ÷100 | ✅ 用（定位） |
| `locationEnd` | rotation（pitch/yaw, 16bit each） | ×360/65536 | ✅ 用（朝向） |

### 2.3 接通方式（已实施）

**拿加速度不需要改解析逻辑、不需要新抓包** —— 数据本来就在包里，同包同源。

```swift
// UE5Decoder.decode：把 accel 留档
lastAcceleration = accel
lastAccelerationAt = timestamp

// UE5Decoder：对外读取（带新鲜度门，过期返回 nil，不拿旧值当实时值）
func acceleration(maxAge: Double = 0.5) -> Vec3?

// CoordinateCapture：透传
func readAcceleration(maxAge: Double = 0.5) -> Vec3?

// DriveState.runNetworkLocateStep：写入 state（÷100 转 m/s²）
state.locatorAccelX / locatorAccelY / locatorAccelZ
```

UI 上在「系统状态」里显示为一行「定位加速度」：**有真实数据才显示数值，没有显示 `—`**（不编数）。
控制逻辑**一行都没接** —— 在坐标系确认前不碰。

### 2.4 ⚠️ 仍未验证项（必须实测，不能假设）

**坐标系未知。** 该加速度可能是：
- 世界坐标系 → 需用 `heading` 旋转到车体系，才得到纵向 `accel_z`
- 车体坐标系 → 可直接用

**这一点必须等游戏运行、抓到真实包之后才能确认。** 不可假设。
判定方法（游戏跑起来后）：直线加速时看三分量——若只有某一轴单调变化、另两轴近零，
且该轴与 `heading` 无关 → 车体系；若三分量随转向同步旋转 → 世界系。

**单位也待确认**：推测与位置同源为 cm/s²（代码里 ÷100 转 m/s²），
需用「速度变化率 ≈ 加速度」交叉验证（速度来自 SpeedOCR，可做闭环校验）。

## 三、换模型调研（一手证据）

### 3.1 现状：M9 为什么烂（实锤）

`InferenceEngine.swift:341-345` 的 `vehicle_state` 6 维实际填充：

| 维度 | 实际值 | 状态 |
|---|---|---|
| `[0]` | `speed/120` | ✅ 真实（SpeedOCR） |
| `[1]` | `0.0` | ❌ 占位符（注释原文「无遥测→0」） |
| `[2]` | 占位 | ❌ |
| `[3]` | 占位 | ❌ |
| `[4]` | `speedLimit/120` | ⚠️ 疑似占位 |
| `[5]` | 占位 | ❌ |

**6 维里只有 1 维是真信号。** 且 `m9_mono.onnx` 仅 126KB + 32MB data，确系手搓。

### 3.2 FH6 模型（`Ayin1412/ForzaHorizon6-VisionAI`）

**许可**：代码 Apache-2.0（**架构可自由复用**）；权重/标定 CC BY-NC 4.0（禁商用）。
→ 结论：**借架构，不借权重**。跨游戏权重本来也不通用。

#### 架构（源码 `scripts/model.py`，109 行）

```
3帧堆叠 [3, 3, 180, 320] @0.1s（0.2s 历史）
        ↓  ResNet-18（conv1 扩到 3×frame_stack 通道）
   AdaptiveAvgPool(4,4) → fc1(256)
        ├─ 早期分叉（fc1 alone，不看车速）
        │    line(3)      车道偏移：now / +0.5s / +1.0s
        │    wp(9×2)      9 个航点，弧长 8/12/17/23/30/40/52/66/85 m
        └─ 晚期分叉（fc1 + state，融合车速）
             wpspeed(9)  各弧长处速度（以当前速度为锚的残差）
             slip(6)     轮胎滑移 front/rear × {0, 0.25, 0.5}s
             steer/throttle  直接 BC 头 —— 仅塑形表示，**不用于驾驶**
        ↓
   geom = cat([line*3.0, wp, wpspeed, slip])   ← **全部 .detach()**
        ↓
   ctrl_steer    = tanh(ctrl_steer_mlp(cat([geom, speed])) + line_to_steer(line))
   ctrl_throttle = tanh(ctrl_throttle_mlp(cat([geom, speed])))
        ↓
   【部署用这两个输出】
```

#### 推理时的真实输入（`scripts/drive.py` 原文）

```python
state_t  = torch.tensor([[speed / speed_norm, accel_z_n, prev_throttle]])
action_t = torch.tensor([[prev_steer, prev_throttle]])
pred = model(image_t, state_t, action=action_t)
```

**只有三样**：画面（3 帧堆叠）+ state + action。

**关键结论：推理时不用任何遥测。** 几何量（line/waypoint/slip）全部由模型自己从画面预测，遥测的 `NormalizedDrivingLine` **只在训练时作监督真值**。

| 阶段 | 用遥测吗 |
|---|---|
| 训练 | ✅ 用（监督几何头） |
| **推理（开车）** | ❌ **完全不用** |

→ **这解除了「《异环》没有遥测 → 模型跑不了」的顾虑：跑的时候本来就不需要遥测。**

#### 状态输入契约（`data/models/meta.json` 原文）

| 维度 | 来源 | 归一化 | 本项目可得性 |
|---|---|---|---|
| `speed_norm` | 车速 | ÷100 | ✅ SpeedOCR 实测 99.8% |
| `accel_z_norm` | 纵向加速度 | ÷20 | ✅ **30031 包里已有**（见 §二） |
| `prev_throttle` | 上一帧自身输出 | — | ✅ 天然可得 |

**位置、朝向：FH6 根本不用**（grep `pos/head/yaw/gps/loc/coord` 于 meta.json → 零结果）。

#### 为什么必须走几何接口（论文 §5 消融，HUD 关闭时）

| 配置 | HUD 开 | HUD 关 | 变化 |
|---|---|---|---|
| `full`（几何量喂控制头） | 29.7 m/s | **27.1** | **−9%** |
| `abl_a`（视觉特征喂控制头） | 30.2 m/s | **5.4** | **−82%** |
| `abl_b` | 31.3 m/s | **3.3** | **−89%** |

且 `abl_a` 的**道路感知完好**（79.5 → 75.1 m）——**只有控制崩了**。

**机制**：控制头能直接看视觉特征时会走捷径（记住「HUD 长这样 → 这样打方向」），HUD 一变即废。强制走几何量 = 逼它真的理解「路在哪」才能输出转向。

论文原话：**「几何接口的价值不在于获得道路理解，而在于强迫控制器通过它来行动。」**

### 3.3 另一条路：`talontownsend/ziggy-racer`（FH6 纯控制论方案）

- **完全不用视觉**，读 FH6 UDP 遥测（71Hz，324 字节，含位置/速度/偏航/**每轮滑移率**/悬挂负载/路面倾角）
- 纯控制理论：Frenet 坐标 + 五次多项式规划 + 摩擦圆限幅；numpy 实现，**每 tick < 1ms**
- 成绩：**28.36s** vs 游戏内置 AI 27.29s vs 人类 25.68s（Shimanoyama Circuit）

**⚠️ 本项目不可用**：30031 只能解析出**位姿**（位置 + pitch/yaw），**没有速度、没有轮速、没有抓地力**。遥测路线在《异环》堵死。

### 3.4 YOLOPv2：车道线兜底候选（比 YOLOP 强得多）

| 模型 | 检测 mAP@0.5 | 可行驶 mIoU | 车道线 Accuracy | 参数量 | 速度 |
|---|---|---|---|---|---|
| YOLOP (2021) | 76.5 | 91.5 | 70.5 | 7.9M | 49 fps |
| HybridNets | 77.3 | 90.5 | **85.4** | 12.8M | 28 fps |
| **YOLOPv2 (2022)** | **83.4** | **93.2** | **87.3** | 38.9M | **91 fps** |

- **单模型三输出**：目标检测 + 可行驶区域 + 车道线
- 许可 **MIT**（比 FH6 权重的 CC BY-NC 干净）
- 权重公开：`CAIC-AD/YOLOPv2` releases `yolopv2.pt`
- 输入 **640×640** —— 与本项目现有 YOLO26s 完全一致，**采集链路无需改动**
- 参考：`hustvl/YOLOP`（MIT，640×640，41 fps）为上一代

**注意**：车道线 IoU 一栏 YOLOPv2(27.2) 反低于 HybridNets(31.6)，但 Accuracy 87.3 vs 85.4 是 YOLOPv2 胜。IoU 对极细目标天然吃亏，**勿被该数字误导**。

#### ⚠️ 领域不匹配风险（必须正视）

YOLOPv2 训练于 **BDD100K 真实道路**（高速/城市/昼夜）。本项目是**游戏画面**：第三人称追车 + 卡通渲染 + 青蓝色发光辅助线。

**分布不同 → 直接跑可能检不出或检错。** 两条路：
- **A**：直接跑先看效果（零成本，值得一试）
- **B**：以 YOLOPv2 权重初始化，用自录游戏帧微调（工作量中等，**这才是可靠的兜底**）

**兜底系统的可靠性不能建立在未验证的迁移上。**

### 3.5 可行驶区域 / 世界模型：单目游戏画面下不成立

FH6 方案中**没有**可行驶区域模型——它靠 waypoint 隐式表达「路在哪」。

真正的 occupancy/BEV 模型（TPVFormer、OccNet 等）输入是**环视相机 + 激光雷达**，属真实道路学术项目，**单目游戏画面无法喂入**。硬做等于从头训一个无监督信号的分割网。

→ **建议放弃**，用 waypoint 表达。

### 3.6 导航路线方案的致命缺口：没有路网

**用户设想**：用游戏内导航 + 任务追踪同步那条线，配合已有地图与自车位置，实时规划路线。

**家底核查**：

| 资产 | 状态 |
|---|---|
| 5677 标记点（含 100 waypoints / 444 任务点） | ✅ 有 |
| 7 个区域多边形（`imap_map_areas_1.json` 有 `geometry`） | ✅ 有 |
| 13056×13056 真实地图 | ✅ 有 |
| 位置 + 朝向（精度 0.22） | ✅ 有 |
| **路网（道路中心线 / 拓扑图）** | ❌ **没有** |

全库 grep `road / edge / node / graph / route / polyline` → **只有散点与区域边界，无任何道路网络**。

**这是决定性缺口**：导航 = 「A 到 B 走哪条路」，需要道路网络。散点连不成路——中间是墙、楼、水。

**可能出路**（按可行性排序）：
1. **从 13056 大地图做道路分割** → 用 YOLOPv2 可行驶区域头（mIoU 93.2）跑大地图，分出「路 vs 非路」，再骨架化为可路由图
2. 从游戏内地图瓦片提取（当前仅 z1 的 4 张瓦片，太粗，需补采）
3. **放弃显式规划**，纯 BC 让模型隐式学路

### 3.7 几何真值从哪来（无遥测下的替代方案）

| 几何量 | FH6 来源 | 本项目替代 |
|---|---|---|
| `line`（车道偏移） | 遥测 | ✅ **画面里那条青蓝辅助线**（Hue 200.2°±2.9°，180×320 下 11px 宽、跨 90 行） |
| `waypoint`（8~85m 弧长） | 遥测 | ✅ **位置差分**：连续帧 (x,y,θ) → 位移投影到车体系 → lat/fwd |
| `slip`（轮胎滑移） | 遥测 | ❌ 拿不到 |
| `wpspeed` | 遥测 | ❌ 拿不到 |

**关于辅助线提取的已知坑**（`tools/extract_driving_line.py`）：
- 实测整体命中率 **12–20%**，但**数据源是视频网站快照帧（480×270）**——分辨率低、压缩伪影重、镜头乱晃、含转场
- 项目文档已明确：**真正数据源必须是自录 1080p+ 标准驾驶画面**
- **→ 1080p 下的命中率尚未验证**，不可用 12–20% 这个数字下结论

**其他已知坑**：自车银/蓝车漆误检（已加 `ego_mask()`）、天空误检（已加 `ROI_TOP=0.40`）、夜景色偏、逆行变红需加红色分支。

### 3.8 控制标签：全自动，无需手工标注

- **控制标签** = 专家模式下用户自己的按键记录（按住时长换算，已实现）
- **waypoint 真值** = 位置差分自动算
- **line 真值** = 辅助线自动分割（可选，仅值 9%）

→ **零手工标注。**
