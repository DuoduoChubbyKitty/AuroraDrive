## 一、定位失效：BPF 设备权限 + 检测逻辑双重错误

### 1.1 现象与日志证据

用户描述：「一直显示游戏未运行 → 跑着跑着突然显示已抓包等待定位数据 → 但死活不显示地图」。

抓包日志（`/tmp/aurora_pcap.log`）给出了铁证：

```
2026-09-22 04:42:46  包=3446  c2s送解=3016  候选包=207  样本=98   ← 正常（≈230包/秒）
2026-09-22 04:43:05  包=2400  c2s送解=2165  候选包=74   样本=32   ← 开始掉
2026-09-22 04:43:31  包=6     c2s送解=3     候选包=0    样本=0    ← 断崖
2026-09-23 12:27     包=5     c2s送解=2     候选包=0    样本=0    ← 至今未恢复
```

**包数差 700 倍。** 关键推论：
- 解码器本身没问题（历史上 `样本=159/160` 是常态，`候选包` 也正常）
- 问题在**抓包管道收不到包**，不在解码

### 1.2 根因一：`isBPFAvailable()` 只探测 `/dev/bpf0`

`Core/BPFSetup.swift:12`（修复前）：

```swift
static func isBPFAvailable() -> Bool {
    return "/dev/bpf0".withCString { access($0, Int32(O_RDWR)) } == 0
}
```

实测本机 BPF 设备权限：

```
crw-rw-rw-  /dev/bpf0   ← 666，永远可读写 → 函数恒返回 true
crw-rw-rw-  /dev/bpf1
crw-rw-rw-  /dev/bpf2
crw-rw-rw-  /dev/bpf3
crw-------  /dev/bpf4   ← 只有 root！而 pcap 恰恰分配到了它
```

**两个后果：**
1. UI 判定「已授权」→ **密码弹窗永远不弹**（用户说的「小药丸弹不出来」）
2. 实际要用的 `/dev/bpf4` 是 `crw-------` → **抓包开不了**

### 1.3 根因二：BPF 设备是**动态创建**的，`RunAtLoad` 覆盖不到

`/dev/bpfN` 由内核**按需创建**（本机 `/dev/bpf4` 时间戳是 9-16，明显晚于开机）。
而旧的 LaunchDaemon 是：

```xml
<key>RunAtLoad</key><true/>   ← 只在开机跑一次 chmod 666 /dev/bpf*
```

**开机时 `/dev/bpf4` 还不存在，所以 chmod 不到它。** 这解释了「有时能抓有时不能」的随机性。

### 1.4 修复

**① 检测改为动态枚举**（`Core/BPFSetup.swift`）：

```swift
static func firstWritableBPFDevice() -> String? {
    for i in 0..<64 {
        let path = "/dev/bpf\(i)"
        guard FileManager.default.fileExists(atPath: path) else {
            if i > 8 { break }   // 编号连续，但留几个空位容错
            continue
        }
        if path.withCString({ access($0, Int32(O_RDWR)) }) == 0 { return path }
    }
    return nil
}
```

**② 守护改为常驻轮询**（不再是一次性 chmod）：

```bash
while true; do
    for dev in /dev/bpf*; do
        [ -e "$dev" ] || continue
        # 只在权限不足时才 chmod，避免每秒无谓系统调用
        if [ ! -r "$dev" ] || [ ! -w "$dev" ]; then
            chmod 666 "$dev" 2>/dev/null || true
        fi
    done
    sleep 3
done
```

配 `KeepAlive=true` + `ProcessType=Background` + `Nice=10`（守护本身要轻，不能反过来抢游戏 CPU）。

## 二、游戏变卡：768MB `mlock` 硬占

### 2.1 实测数据

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 主进程 RSS | **825 MB** | **153 MB** |
| 其中被 mlock 锁死 | 768 MB | 0 |
| swap 峰值 | 11.85 GB / 12.29 GB | — |

`AuroraDriveApp.swift:215`（修复前）：

```swift
let allocSize = 768 * 1024 * 1024  // 768MB
...
if mlock(buf, allocSize) == 0 { ... }   // 锁死在物理 RAM，不可换出、不可压缩
```

**16GB 机器上等于永久少 4.8% 可用内存**，且 mlock 的页**不可压缩**（连内存压缩都救不了）。
游戏要内存时只能把别的换出去 → 卡顿。

### 2.2 为什么这个机制是冗余的

原注释写「让系统认为本进程是重资源进程不敢冻结」，但这属于**民间偏方**。
防冻结实际已由三重正规手段覆盖：

| 机制 | 层级 | 说明 |
|---|---|---|
| `IOPMAssertion` | Power Management | 最权威，系统官方 API |
| `CGEventTap` | 事件系统 | 系统必须保持有 event tap 的进程响应 |
| `beginActivity(.latencyCritical)` | App Nap | 官方防 App Nap |

### 2.3 修复

改为默认关闭（`freezeGuardBytes = 0`），保留开关以便需要极限防冻结时改回：

```swift
private static let freezeGuardBytes: Int = 0   // 0 = 关闭（默认）
```

实测 RSS **825MB → 153MB（-81%）**。

## 三、权限机制：小药丸 + 彻底移除原生授权

### 3.1 用户明确要求

> 「我们早就试过原神授权穿了 macOS，每次很烦，导致直接给我们写差了。虽然我们是开源项目，
> 但必须在应用内集成一个小药丸，**千万不要用原生授权**，不然我们这个就废了。」

> 「发布成软件版本，别人没办法自定义密码知道吗？」

### 3.2 修复前的问题（三处）

**① 密码硬编码**（`AuroraDriveApp.swift:2947 / 3048`）：

```swift
@State private var password = "123456"   // ← 写死在源码里
```

发布版必废：别人的密码当然不是 123456；且等于把本机管理员密码写进仓库。

**② 密码明文进 argv**（`BPFSetup.swift:140` / `PrioritySetup.swift:116`）：

```swift
let appleScript = "do shell script \"bash \(scriptPath)\" password \"\(escapedPwd)\" with administrator privileges"
```

密码拼进 osascript 参数 → `ps` 可见 → 安全隐患。

**③ 原生授权弹窗**（`DaemonSetup.swift:104`）：

```swift
let appleScript = "do shell script \"/bin/sh \(quotedPath)\" with administrator privileges"
```

会弹 macOS 系统框 —— 用户明确禁止。

### 3.3 修复：应用内 `PrivilegePill`

新增 `Core/PrivilegePill.swift`，技术路线 **`sudo -S`（密码走 stdin）**：

```swift
task.arguments = ["-S", "-p", "", "/bin/bash", "-c", command]
// 密码写进 stdin，不进 argv、不出现在 ps 里
inPipe.fileHandleForWriting.write((password + "\n").data(using: .utf8)!)
```

**安全边界（如实说明）**：
- 密码只在内存存在，用完随作用域回收；不落盘、**不写日志**
- 提权动作严格限定为「安装两个 LaunchDaemon」这一件事
- 不做任何其它 root 操作

**状态判定同时看两件事**（避免假绿）：

```swift
var isFullyAuthorized: Bool {
    BPFSetupManager.isBPFAvailable() && PrioritySetupManager.isDaemonRunning()
}
```

**三处旧原生授权函数已全部停用**，改为明确报错，防止以后误用：

```swift
@available(*, deprecated, message: "已改用 PrivilegePill.shared.install(password:)")
static func install(password: String) -> (success: Bool, message: String) {
    _ = password
    return (false, "此路径已停用：请使用应用内提权（PrivilegePill），不要调用原生授权")
}
```

涉及文件：`BPFSetup.swift`、`PrioritySetup.swift`、`DaemonSetup.swift`。

### 3.4 UI：顶栏常驻小药丸

`MissionConsole.swift` 新增 `PermissionPill`，挂在 `TopBar` 右侧（模型名左边）：

| 状态 | 灯色 | 文案 | 行为 |
|---|---|---|---|
| 全部就绪 | 绿 `ok` | 权限就绪 | 悬停看明细 |
| 待授权 | 黄 `amber` | 授权 | 点击 → 应用内密码弹窗 |

视觉沿用 `PillStat` 同款玻璃胶囊，颜色全部取自既有 `Aurora` 色板，未新造颜色。

### 关于「已抓包，等待定位数据」

这个提示本身是**准确的**：`hasRecentTraffic()` 为真（端口有包）但解码出 0 个候选。
修复后若仍出现，说明包内容不符合解码器预期（不是权限问题），
需要用真实包做一次离线解析对比 —— 那时应把原始 payload 落盘取样。
