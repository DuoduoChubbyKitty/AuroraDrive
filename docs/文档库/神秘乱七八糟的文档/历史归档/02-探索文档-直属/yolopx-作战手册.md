### 3.1 模型与精度

> ⚠️ **下表「速度」列的口径说明（2026-09-29 复核补注）**：
> 本表的速度值是**当时的 min（最优值）**，**不是常态**。
> M1 冻结基线（`yolopx-性能基线与测速协议.md`，112 样本/条件）给出的**median 常态**如下：
>
> | 模型 | 本表（min） | **冻结基线 median** | 8 核满载 median |
> |---|---|---|---|
> | `yolopx3_pal8_detfp` | 63.5ms | **97.7ms** | 212.7ms |
> | `yolopx3_w8a16` | ~70ms | **86.7ms** | 199.8ms |
> | `yolopx3_fp16` | ~85-91ms | **92.0ms** | 197.9ms |
> | `yolo26s_int8`（现役基线） | 5.3~8.1ms | **9.3ms** | **12.0ms** ✅ |
>
> **引用本表数值时请注明是 min**，否则会低估差距（详见上方 §0 后的追记）。

| 模型 | 精度 | 速度 |
|---|---|---|
| `yolopx3_pal8_detfp` | **det 100%** / da IoU 0.9930 / ll P/R 99.28%·98.15% | **63.5ms**（min） |
| `yolopx3_w8a16` | det **85%**（框数膨胀 7→12、15→29） | ~70ms（min） |
| `yolopx3_int8` | ll recall **3.98%**（架构性失败） | — |
| `yolopx3_fp16` | det 100% / da IoU 0.9924 | ~85-91ms（min） |
| `yolo26s_int8`（现役基线） | — | **5.3~8.1ms** |

- 模型 **1727 个算子**（yolo26s 仅 1148 个）；`conv` 165 个、`silu` **148 个**（**conv+silu = 81.4%**，见 §3.7）
- 效率标尺：yolo26s = 2.65 GFLOPs/ms
- ✅ **【2026-09-27 关键更正 · 这条决定优化方向】**
  - ❌ 旧表述「YOLOPX 官方标称 47 GFLOPs，同效率理论只需 17.7ms」**已作废**（47G 是论文标称，与实测口径不符）
  - ✅ 实测口径（t5 融合后）：**148.11 GFLOPs / 823.9 MB / AI=179.8**
  - 🔴 **决定性发现：这块 ANE 完全跑得动 YOLOPX，瓶颈不是算力，是 CPU 胶水。**

    | 对象 | FLOPs | 实测 | 有效吞吐 |
    |---|---|---|---|
    | ANE 对照模型（纯 ANE、零 CPU 税、tensor 输入） | **150.99 G** | **27.531 ms** | **5.48 TFLOPS** |
    | YOLOPX（同量级） | 148.11 G | 97.66 ms | 1.52 TFLOPS |

    → **若 YOLOPX 达到对照模型同等 ANE 效率 = 27.0ms（quiet），效率差距在 CPU 侧而非 ANE 算力。**
    → 实测 97.66ms 与 27.0ms 的**差距 70.7ms 全部来自 CPU 侧**（调度/同步/回读），**不是 ANE 算力不够**。
  - **结论：优化目标不是「让 ANE 算得更快」，而是「把 CPU 侧那 ~70ms 干掉」。** ANE 本身极能打，是接入方式吃掉了它的成果。
  - 🔴 **但必须成对引用满载数字（否则会得出过强结论）**：同一个纯 ANE 对照模型在 8 核满载下是
    **27.531ms → 44.186ms（1.605×）**，且**零 CPU 算子时每帧仍烧 13.3ms CPU**（cpu/wall=0.484）
    —— 即 CoreML 每帧 submit/sync 存在约 **13ms 的不可约 CPU 地板**。
    → **「重干扰下 ≤33ms」即使把模型优化到纯 ANE 完美状态也无法达成（满载 ≈44ms）**。
    → 正确表述：**quiet 下 33ms 有希望；满载下不可达**，除非同时消除 submit/sync 惩罚。
    ⚠️ **纪律：引用任何 quiet 数字时必须与同口径的 loaded 数字成对出现**，禁止只报 quiet。

  - 这也解释了为什么 yolo26s（22.53G / 实测 9.30ms ≈ 其带宽下界 9.22ms，达成 **101%**）没有这个缺口——它精确地跑在自己访存天花板上。

### 3.6 性能基线（2026-09-26 M1 冻结 · **优化方向的唯一依据**）

**结论一：用户的「跑在 ANE 上就不怕游戏抢 CPU」假设已被证伪。**
yolopx3 全部版本在 8 核满载下中位慢 **2.2 倍**（97.7 → 212.7ms），14/14 配对块全为正；**2 核就开始掉速**。

**结论二：根因不是 ANE 算力被抢，是 CoreML 的 CPU 侧胶水。**
自建纯 conv 对照模型（`MLComputePlan` 确认 20/20 算子全在 NeuralEngine、CPU 算子 0、交替 0 次）在同样负载下**仍慢 1.6 倍**（1.662/1.650/1.668）。→ ANE 算力扛得住，**被抢的是每帧必走的 submit/sync 那条 CPU 路**。这是工程问题，可解。

**结论三：33ms 对 yolopx3 不可达，且不是差一点。**

| 模型 | quiet min | quiet 中位 | loaded 中位 | 抗干扰倍率 | 33ms |
|---|---|---|---|---|---|
| yolo26s_int8（现役） | 5.1 | 9.3 | 12.0 | 1.29 | **PASS** |
| yolopx3_pal8_detfp | **63.6** | 97.7 | **212.7** | 2.18 | FAIL |
| yolopx3_w8a16 | 64.5 | 86.6 | 199.8 | 2.31 | FAIL |
| yolopx3_fp16 | 71.1 | 92.0 | 197.9 | 2.15 | FAIL |
| yolopx3_int8 | 82.4 | 99.8 | 123.3 | **1.24** | FAIL |

**结论四（最有价值 · 优化的总方向）：把算子从 CPU 搬走 = 同时买到抗干扰性。**
- yolopx3 每帧烧 **63~70ms CPU 时间**，图被切成 **11 处 CPU↔ANE 交替**；yolo26s 只烧 4.7ms、交替 2 处，r(CPU税, 负载倍率)=**0.939**
- `yolopx3_int8` CPU 税只 **26ms**、交替 **7 处** → 抗干扰倍率只 **1.24×**（pal8 是 2.18×）
- → **降 CPU 税与提升抗干扰性本质是同一件事**，这条已被实测反证，不是空想。**不要求「让 ANE 算得更快」，要求「把算子从 CPU 搬走」。**

**pal8_detfp 的 CPU 算子清单**（16 CPU / 411 ANE / 129 unreported）：
```
ios16.softmax     × 4   ← PSA 注意力，位于图纵深中部把图切碎，主嫌疑
ios16.reduce_sum  × 4   ← 同上
ios16.mul         × 若干
ios16.max_pool    × 2
ios16.cast        （image_to_fp16）
image__scaled__
```

**⚠️ 三个必须知道的坑（踩过）**
1. `MLComputePlan` 的 `device_cost_share` 报 CPU 仅 **0.0446**，但实测 CPU 时间占墙钟 **72%** —— 静态权重与真实耗时脱钩，**只能信算子计数**。
2. 计算单元档位：`CPU_AND_NE` 会让 yolopx3_int8 退化到 **617ms**；`CPU_ONLY` / `CPU_AND_GPU` 触发 MPSGraph 断言直接 **SIGABRT**（须子进程隔离）。
3. **块状测量设计在本机失效**——「先全测无负载、再全测有负载」的 quiet 阶段自身从 31ms 飘到 86ms，比 loaded 还慢，对比全废。**任何性能对比必须走 ABBA 交错**，用 `bench_protocol.py compare`。

**⚠️ 本基线的性质**：全部是 Python/CoreML 侧数字，**不含 Swift letterbox 与 det/da/ll 后处理 → 是实机下界**；且"满载"只到整机 CPU 68~88%，真实游戏满载只会更糟。

### 3.7 算子剖析结论（2026-09-26 t3 冻结）

**🔴 最重要的一条：只能信这份剖析的「算子清单」，不能信它的「时间占比」。**
静态 cost 表说 CPU 只占 **3.9%**，但 M1 实测 CPU 烧 **63~70ms = 墙钟 72%**，**差 18 倍**。
原因：那 63ms 主要是 **CPU↔ANE 的调度/同步开销**，这些开销**没有对应算子**，自然不进 cost 表。
✅ 好消息：静态设备普查与 M1 运行时分解**两个独立方法指认了同一批算子**（PSA 的 softmax×4 + reduce_sum×4），清单部分交叉验证成立。

**算子构成**（pal8_detfp：1727 个算子 = const 1171 + 属性 1 + **真实计算 555**）

| 算子 | 个数 | cost 占比 | 设备分布 |
|---|---|---|---|
| `ios16.conv` | 165 | **49.4%** | ANE=165 |
| `ios16.silu` | 148 | **32.0%** | ANE=148 |
| `ios16.mul` | 12 | 4.5% | ANE=7 CPU=5 |
| `concat` | 31 | 4.2% | ANE=31 |
| `ios16.add` | 4 | 3.0% | ANE=4 |
| `ios16.max_pool` | 8 | 2.4% | ANE=6 CPU=2 |
| `ios16.softmax` | 4 | 0.1% | **CPU=4** |
| `ios16.reduce_sum` | 4 | 0.4% | **CPU=4** |

→ **conv + silu = 81.4%**（早期估计「约 30%」**已证伪**，差近三倍）

**层定位**（PyTorch `forward_hook` 执行序 ↔ MIL 拓扑序对齐；conv 计数双向验证 **41+52+24+19+29 = 165 = 165 全吻合**）
`backbone` **38.14%** → `ll_branch` 15.14% → `neck` 10.92% → `det` 8.98% → `da` 7.77%
单点最贵：**`conv#136` = 8.89%**（`model.18.conv`，ll 支路入口）

**设备普查**：ANE **96.1%** / CPU 3.9% / **GPU 0 个**
（⚠️ **此结论仅对 `CPU_AND_NE` 档成立** —— 见下方 t4 更正）

**⚠️ 更正（2026-09-26 t4 实测，档位口径不同导致）**：
- t3 的「GPU 0 个 / supported 含 GPU 也是 0/556」**只对 `CPU_AND_NE` 档成立**。
- **在 `ALL` 档（App 实际使用的档位）下**：`supported` 含 GPU = **427/427**，`preferred=GPU` = **19 个**；
  且 **int8 在 `ALL` 档下有 870 个算子走 GPU**（不是 ANE）。
- → **不能说「没有 GPU 兜底路径」**；GPU 是可用的第二落点。
- ⚠️ **纪律：今后所有设备统计一律标注计算单元档位**（`ALL` / `CPU_AND_NE`），跨档位数字不可拼接。

**⚠️ 另一处口径更正（t4 实测）**：手册早期写的「**11 处 CPU↔ANE 交替**」是 `CPU_AND_NE` 口径（t4 复现出完全相同的 11 次 ✓），
但 **M1 的性能数字取自 `ALL` 档，该档是 9 次 / 4 个 CPU 段**。两者拼接数值上不严格对应（结论方向仍成立）。

**⚠️ 隐藏问题：23.2% 的算子完全不在 cost 表里**
129 个 `constexpr_lut_to_dense`（pal8 的**反量化查表步**），cost 覆盖仅 **76.8%**。
→ **已由 t4 结案**：这 129 个**不落 CPU**，是「设备未上报」而非「回落」。三条硬证据：① 类型单一（129/129 同一算子）；
② fp16 变体 unreported=0 但两者的 CPU 算子清单**逐位相同**；③ **同进程 ABBA 实测 fp16（0 个 lut）89.26ms vs pal8（129 个 lut）82.16ms**
→ 129 个 lut 对 CPU 税的贡献 **≈ 0**。**「pal8 比 fp16 慢」不能用这个解释**，别再往这个方向查。

**ROI 靶子排序（按真实 ROI 排，不是按 cost 大小排）**
1. 🥇 **silu 148 个（32%）** —— 最易融合，但**必须先做 A/B 消融**：silu 是访存密集型，cost 权重可能高估其真实耗时，**别直接按 32% 立项目标**
2. 🥈 **backbone 38%** —— 结构性，集中高分辨率段（640²/320²/160²）。输入 640 是红线，但 **backbone 内部下采样策略不在红线内**，属可动区（改结构需走精度验证）
3. 🥉 **CPU 侧 15 个算子** —— 静态仅 3.9% 但实测对应 **72% 墙钟** → **真实 ROI 最高**，且是唯一能**同时改善延迟与抗干扰性**的方向（M1 int8 反证支持）
4. 🏅 **conv#136 单点 8.89%** —— 靶点明确，适合独立小实验

**口径提示**：t3 报 CPU 算子数 **15**（只统计 555 个真实计算算子），M1 报 **16**（统计全部 1727 个，多算一个 `ios16.cast`）。两者指认同一批核心算子，交叉验证成立，差异属口径不同，**不影响结论**。

## 4. 判定线（硬性）

| 指标 | 阈值 |
|---|---|
| det 匹配率 | **>99%** |
| da IoU | **>0.99** |
| ll 下游偏差 | **<0.006** |
| ll P/R | **>0.97** |
| 单帧延迟 | **≤33ms**（重干扰下） |

**精度与速度冲突时，精度优先**（"不能变瞎" 优先于 "慢"）。

### 4.1 判据口径纪律（2026-09-26 由 M2 冻结，全队必须遵守）

判据的唯一可执行实现：**`tools/yolopx/metrics_spec.py`**（1014 行，`--selftest` 11 项全绿）。
所有对拍一律调用它，**不得自造判据**。

**① det 匹配率必须用双向口径**：`match_rate = min(recall, precision)`，并附带 `count_ratio` 哨兵（>1.5 或 <0.67 直接可疑）。
⚠️ 旧的 `verify_yolopx_coreml.match_count()` 是**单向**的（只算 recall/len(ref)），对「多吐框」完全不设防——框数从 7 膨胀到 12、15→29 时照样报 **100%**。任何引用了单向口径得出的历史结论（尤其「w8a16 det 85%」）**都必须用双向口径重测后才能采信**。

**② ll 下游偏差必须在 640 口径下裁决**：实测同一张图、同一模型，仅换 640/160 口径就差 **0.0005~0.0214**，即阈值的 0.1~3.6 倍。且 160 网格一格 = 0.00625 **已大于阈值 0.006 本身**，该阈值在运行时口径下**无分辨力**。
→ 规则：`<0.006` 只对「**同口径**下产物 vs 基准之差」有效；**跨口径数字一律无效**。裁决统一在 **640 口径**。
