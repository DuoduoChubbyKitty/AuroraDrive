### 1.1 为什么 silu 是"最便宜的攻击面"

- **148 个 silu 吃掉 32.0% 成本**，是第二大项，且**纯逐元素激活**——不改变张量形状，理论上可被融合进前一个 conv 的 epilogue
- 与 conv 相比：165 个 conv 吃 49.4%，即**平均每个 conv 0.30%**，而**平均每个 silu 0.22%**
- **silu 密度极高**：148 个 silu 对 165 个 conv，比例接近 1:1.1 —— 说明网络是 `conv→silu` 成对堆叠（ELAN 结构的特征）

> ⚠️ **重要限制**：`MLComputePlanCost.weight` 是**同图内相对权重**，不是毫秒。
> 它对 silu 报 32% 不代表 silu 真的花 32% 的时间——尤其 silu 是**访存密集**型
> （读+写整张特征图），在 ANE 上实际耗时可能显著低于其 cost 权重。
> 要定 silu 的真实收益，必须做 **A/B 消融实测**（把 silu 换成恒等，测 ms 差），不能只看这个表。

## 2. 表②：网络层定位

### 2.1 ⚠️ 任务给的 `net_model_N_` 前缀法**不可用**（实测证伪）

任务描述假设可以"按 `net_model_N_` 前缀聚合定位到具体网络层"。实测：

```
net_model_N_  命中    38 / 1727   ← 只覆盖 net_model_2 / net_model_23 / net_model_28
model_N       命中     0 / 1727
input_N       命中  1113 / 1727
const_N       命中   292 / 1727
```

**原因**：coremltools 转 MIL 后，绝大多数输出名退化成拓扑序号（`input_17_cast_fp16`），
**PyTorch 的语义层名已经丢失**，没有保留到 CoreML 图里。

**证据 A — PyTorch 执行序 hook**
给所有 165 个 `Conv2d` 挂 `forward_hook`，跑一次前向记录调用顺序与所属模块。

**证据 B — MIL 拓扑序**
MIL 图是拓扑序的；按 conv 出现顺序编号 `conv#0..164`。

**验证**：按「块索引 → 语义模块」分组后，两侧的 **conv 计数完全吻合**：

## 3. 表③：按设备聚合

| 设备 | 算子数 | 占比 | **cost 占比** | 主要算子 |
|---|---|---|---|---|
| **NeuralEngine** | 411 | 74.1% | **96.1%** | conv×165 silu×148 concat×31 reshape×13 sigmoid×12 |
| **CPU** | 15 | 2.7% | **3.9%** | **mul×5 softmax×4 reduce_sum×4 max_pool×2** |
| **unreported** | 129 | 23.2% | 0.0% | constexpr_lut_to_dense×129 |
| **GPU** | **0** | **0.0%** | **0.0%** | — |

### 3.1 GPU 完全缺席（重要）

```
preferred = GPU 的算子:        0
supported 含 GPU 的算子:       0 / 556
  411 个算子  支持设备 = ['CPU', 'NeuralEngine']
  129 个算子  支持设备 = []          ← palettize 反量化步，MIL 未上报
   16 个算子  支持设备 = ['CPU']
```

**推论**：
1. 这个模型**不可能**靠 GPU 兜底 —— 若 ANE 接不住某算子，它只能掉到 CPU（没有 GPU 中间档）
2. 这解释了 M1 §5.4 的实测：`yolopx3_int8` 在 `CPU_AND_NE` 档退化到 **617ms**（vs `ALL` 71.6ms）
   —— 因为"关掉 GPU"在这张图上等于没有任何兜底
3. **`--compute-units CPU_AND_GPU` 对这个模型没有意义**（实测也确实触发了 MPSGraph 断言 SIGABRT）

### 3.2 ⚠️ 静态 cost 与实测 CPU 税的**严重背离**（必读）

| 指标 | 静态 cost 说 | M1 实测 |
|---|---|---|
| CPU 承担量 | **3.9%** | **63~70ms / 帧，占墙钟 72%** |

**这是本报告最重要的警告**：

> `MLComputePlan` 报 CPU 只占 3.9% 的"成本"，但 M1 实测每帧在 CPU 上烧 **63~70ms CPU 时间**。
> 两者差 **18 倍**。

**原因**：`cost.weight` 只统计**算子的计算量**，而 CPU 的 63~70ms 主要来自：
- CPU↔ANE 之间的**调度/同步/数据搬运**（11 处交替，每处一个同步点）
- 这些开销**根本没有对应的算子**，自然不在任何算子的 cost 里

→ **决策规则：绝不能用静态 cost 判断 CPU 侧该不该优化。**
静态 cost 只能回答"哪个算子的算术量大"，不能回答"时间花在哪"。

### 3.3 CPU 上的 15 个算子（M1 已锁定为根因嫌疑）

| 算子 | 个数 | 语义位置 |
|---|---|---|
| `ios16.mul` | 5 | `image__scaled__`（输入归一化）+ PSA 的 4 个 `var_*_cast_fp16` |
| **`ios16.softmax`** | 4 | **PSA 注意力**（`context_mask` / `ctx2`）|
| **`ios16.reduce_sum`** | 4 | **PSA 注意力** |
| `ios16.max_pool` | 2 | backbone 池化 |

**与 M1 的发现完全一致**：M1 独立地从 CPU 时间分解出发，指认了同样的 `softmax`×4 + `reduce_sum`×4。
两个独立方法（静态设备普查 vs 运行时 CPU 时间分解）指向同一批算子 —— **交叉验证成立**。

## 4. 无法估算的算子占比

| 项 | 值 |
|---|---|
| 全图算子 | 1727 |
| const（常量） | 1171 |
| 属性张量（conv 的 pad/strides/dilations/…） | 1 |
| **真实计算算子** | **555** |
| cost 可估算 | 426 |
| **cost 覆盖率** | **76.8%** |
| **不可估算** | **129（23.2%）** |

**不可估算的全部是 `ios16.constexpr_lut_to_dense`** —— palettize（8bit 调色板）的**反量化查表步**，
每个量化权重配一个。MIL 把它们标为 `unreported`，`get_estimated_cost_for_mlprogram_operation()`
拿不到权重。

**影响**：
- 本报告所有 cost 百分比都是**在剩下 76.8% 上归一化**的，不是全图占比
- 这 129 个反量化步**有真实耗时**（每次 conv 前都要查表还原权重），但**完全没进 cost 表**
- 它们也可能正是 M1 测到的 CPU 税的一部分（若被调度到 CPU）
- ⚠️ **这是 pal8 量化引入的额外代价**：fp16 版本没有这些算子。M1 实测 pal8_detfp
  (97.7ms) 确实没有比 fp16 (92.0ms) 快多少 —— 反量化开销可能是原因之一

## 5. 优化靶子（按 ROI 排序）

排序依据：**静态 cost × M1 实测的负载敏感度 × 可操作性**（三者必须同时看）。

### 🥇 靶子 1：silu 的 148 个实例（cost 32.0%，全在 ANE）

- **为什么**：第二大成本项，且是**纯逐元素激活**，结构上最容易被融合/替换
- **预期**：若能融合进 conv epilogue 或换成等价低成本激活，理论上限 32%
- **⚠️ 但必须先做消融实测**：silu 是访存密集的，cost 权重可能高估其真实耗时。
  **不要直接按 32% 立项目标**
- **建议实验（S 线）**：导出 `conv→silu` 换成 `conv→(identity)` 的对照模型，
  只测 ms 差。**这一步成本极低，应最先做**（它决定后面所有 silu 相关工作的上限）

### 🥈 靶子 2：backbone 的 38.1%（结构性）

- **为什么**：单一模块吃掉 38%，且最贵的 10 个 conv 里 6 个在这
- **特征**：都在**高分辨率段**（640²/320²/160²），成本与特征图面积成正比
- **可操作点**：输入 640 是红线（禁改输出分辨率），但**backbone 内部的下采样策略**
  不在红线范围内 —— 若能把高分辨率段的通道数/层数做结构性削减，
  可直接砍掉成本（**但这是改模型结构，会影响精度，必须走精度验证流程**）
- **建议实验（Q 线）**：先做「backbone 各 stage 的 cost 分布」细分，找出最贵的 stage

### 🥉 靶子 3：CPU 侧 15 个算子（静态只 3.9%，**实测 63~70ms → 最高真实 ROI**）

- **为什么**：静态 cost 严重低估（§3.2）。M1 实测这 15 个算子背后是 **72% 的墙钟时间**
  和 **2.2× 的负载敏感度**
- **可操作点**：`softmax`×4 + `reduce_sum`×4 位于 PSA（`model.23`/`model.28`），
  而 PSA 属于 **ll 支路**。若能改写成 ANE 友好形式（如用 matmul 表达注意力），
  可同时降低 CPU 税与 CPU↔ANE 交替数
- **反证支持**：M1 实测 `yolopx3_int8`（CPU 税仅 26ms、交替仅 7 处）负载倍率只 **1.24×**，
  远低于 pal8 的 2.18× —— **"降 CPU 税 = 换抗干扰性"已被实测验证**
- **建议实验（S 线主力）**：PSA 重写。这是**唯一同时改善延迟 + 抗干扰性**的方向

### 🏅 靶子 4：`conv#136`（单点 8.89%）

- **为什么**：全图**单点最大**，位于 `model.18`（ll 支路入口 1×1 投影）
- **可操作点**：检查是否有冗余通道/可合并的相邻投影
- **建议**：成本低、靶点明确，适合作为一个独立小实验

### ⚠️ 靶子 5：129 个反量化步（23.2% 算子，cost 未知）

- **为什么**：pal8 独有的额外开销，完全不在 cost 表里
- **可操作点**：对比 pal8 与 fp16 的实测差异（M1: 97.7 vs 92.0ms，pal8 反而**更慢**）
- **建议**：这是个**负面信号**——8bit 量化没换来速度。需要查清反量化步的实际开销，
  或考虑换量化方案（如 w8a16 的线性量化）

## 6. 与 M1 实测的交叉验证汇总

| 项 | 本报告（静态） | M1（实测） | 一致性 |
|---|---|---|---|
| CPU 算子清单 | `softmax`×4 + `reduce_sum`×4 + `mul`×5 + `max_pool`×2 | 独立指认 `softmax`×4 + `reduce_sum`×4（PSA） | ✅ **完全一致** |
| ANE/CPU 分工 | ANE 96.1% / CPU 3.9% | ANE 计算扛得住，CPU 胶水是瓶颈 | ⚠️ **静态严重低估 CPU** |
| GPU | 0 个算子支持 | `CPU_AND_NE` 让 int8 退化到 617ms；`CPU_AND_GPU` 触发 SIGABRT | ✅ 一致（无 GPU 兜底） |
| 算子总数 | 1727（真实 555） | 1727（同上） | ✅ |
| conv/silu | 165 / 148 | 165 / 148 | ✅ |

**结论**：静态剖析在**算子清单**上可信（与实测完全对齐），在**时间归因**上**不可信**（低估 CPU 18 倍）。
**用它的"清单"，不要用它的"占比"。**

## 7. 给 S 线 / Q 线的具体建议

| 线 | 该做什么 | 依据 |
|---|---|---|
| **S 线（优化）** | 主攻 **PSA 的 softmax/reduce_sum 重写**（靶子 3）—— 唯一同时改善延迟与抗干扰性 | §5 靶子 3 + M1 反证 |
| **S 线（快速验证）** | 先做 **silu 消融 A/B**（靶子 1），成本极低、决定上限 | §5 靶子 1 |
| **Q 线（结构）** | 细分 **backbone 各 stage 的 cost**，找可削减的高分辨率段（靶子 2） | §5 靶子 2 |
| **Q 线（量化）** | 查清 **129 个反量化步**的开销，解释"pal8 没比 fp16 快"（靶子 5） | §4 + M1 |
| **全线红线** | **别用本报告的百分比做时间预算** —— 它漏了 23% 的算子，且 CPU 项低估 18 倍 | §3.2 |

## 8. 已知局限

| # | 局限 | 影响 |
|---|---|---|
| 1 | `cost.weight` 是**相对权重不是毫秒** | 所有百分比只能做**排序**，不能做时间预算 |
| 2 | 23.2% 算子不可估算 | 归一化基数偏小，真实占比会被稀释 |
| 3 | **层定位靠执行序对齐**，非语义名（MIL 丢名） | 计数已验证吻合（165/165 分模块一致），但**边界处可能有 ±1 偏移** |
| 4 | `net_model_N_` 前缀法**不可用**（只覆盖 38/1727） | 任务描述里的这个方法已被证伪，改用执行序对齐 |
| 5 | 只测了 `pal8_detfp` 一个产物 | 其他量化版本（w8a16/fp16/int8）的算子分布未测 |
| 6 | 静态分析不含 CPU↔ANE 切换开销 | 这是 M1 实测的**主要瓶颈**，静态图里完全看不到 |
| 7 | `silu` 的 32% 未经实测验证 | 访存密集型算子可能被 cost 高估，**必须做 A/B 消融** |

## 9. 一句话交接

> **conv 49.4% + silu 32.0% = 81.4%**（不是任务里说的 30%）；**backbone 独吃 38.1%**；
> **GPU 完全缺席**（0 个算子）；**23.2% 的算子（129 个反量化步）根本不在 cost 表里**。
>
> 但最关键的警告是：**静态 cost 说 CPU 只占 3.9%，实测却是 72% 的墙钟时间** ——
> 差 18 倍。**用这份报告的"算子清单"，别用它的"时间占比"。**
