# 第十部分：限速与路况系统（设计定稿 + 实现细节）

## 系统架构（谁干什么）
- **速度检测**：SpeedOCR 模型实时读车速（99.8% 准确率）
- **限速来源**：用户手动滑块（横滑，最右=不限速）+ 路况自动档位（按 YOLO 检测窗口数）
- **刹车执行**：独立函数 `applySpeedLimitBrake()`——不经过 `applyCommand`（模型输出通道），放在 tick 里**所有档位决策之前 return**（完全不用模型）
- **优先级链**：不限速 > 自动速度 > 手动路况。恢复限速的唯一入口是用户自己拉滑块

## 三级刹车（解决"空格+Shift 失控"）
根因：持续按住手刹 = 后轮锁死 = 高速甩尾 = 车头打转。

| 级别 | 时机 | 动作 |
|---|---|---|
| ① 松油门 | 超速 0-0.6s | 只松 W + Shift，发动机制动，完全不碰手刹 |
| ② 点刹 | 0.6-2.5s | 脉冲手刹：按 0.18s / 松 0.22s（占空比 43.9-45.5%，轮胎周期性恢复抓地） |
| ③ 持续刹 | 超速 2.5s+ | 才持续按住空格 |

界面显示当前在哪一级。多数情况在 ① 就降下来了。

## 修掉的三个真缺陷（复查时发现）
1. **手刹永久卡住**（最严重）：applyCommand 只管 W/S/A/D 从不碰 handbrake，刹车退出后没人松空格，refreshHeldKeys 还每帧重发按下——车从此动不了。加 latched 标志在退出边沿释放
2. **专家模式下 AI 偷踩刹车**：刹车代码在 return 前的执行顺序问题
3. **不限速被自动逻辑偷偷改回**：tick 自动判定没排除不限速——拉到底选不限速，几秒后界面自己跳回 120。三处全修（tick 判定 / applyRoadCondition / setAutoSpeed）

## 路况 6 档（按 YOLO 检测窗口数）
| 框数 | 档位 | 限速 |
|---|---|---|
| >70 | 极度复杂 | 20（红字+整层红色光圈） |
| 51-70 | 繁忙 | 60 |
| 31-50 | 中等 | 100 |
| 21-30 | 轻松 | 150 |
| 11-20 | 保持 | 不变 |
| ≤10 | 不限速 | 滑块拉到底 |

# 第十一部分：FH6-VisionAI 完整调研档案（主驾模型路线的依据）

## 模型架构（读源码验证，非文档转述）
- **视觉输入**：[3帧堆叠, 3通道, 180, 320]——三帧间隔 0.1s 覆盖 0.2s 历史；ResNet-18 的 conv1 改吃 9 通道（3×frame_stack），权重用 repeat(1,frame_stack,1,1)/frame_stack 初始化
- **状态输入仅 3 维**（meta.json 原文）：

| 维度 | 来源 | 归一化 |
|---|---|---|
| speed_norm | 车速 | ÷100 |
| accel_z_norm | 纵向加速度 | ÷20 |
| prev_throttle | 上一帧自己的油门输出 | 闭环自反馈 |

- **推理时（drive.py 原文）**：`pred = model(image_t, state_t, action=action_t)`，action=[prev_steer, prev_throttle]。**遥测的 line/waypoint/slip 全部不出现在推理里**——由模型从画面预测后 `.detach()` 送控制头。遥测只在训练时当监督真值

## 防捷径设计（论文核心）
- 控制头只看**几何量+车速**，不看原始视觉特征
- 几何接口：line(3) + wp(9×2) + wpspeed(9) + slip(6)
- 消融证据：HUD 关掉 -9%；几何喂控制头 -9%；**视觉特征直接喂控制头 -82~-89%**——证明模型学的是几何不是记路

## 《异环》落地难点
- 遥测没有 → 几何真值拿不到：辅助线（青蓝色）命中率仅 12-20%；waypoint（8~85m 弧长）单目画面拿不到
- 两条路：A) 几何头不监督 → 退化成普通瓶颈层（防捷径打折）；B) 从画面提真值（命中率太低）
- **用户定的路线**：专家模式录制（游戏自动打标）自建数据集 → 自己微调 → INT8 量化
- accel_z 的坐标系系数未标定（世界系 vs 车体系）——用之前必须标定

## 为什么不是 YOLOPv2 / 为什么先 YOLOPX
- YOLOPv2（2022）是 YOLOP 升级版：一个模型三输出（检测+可行驶区+车道线），全面优于原版——但用户嫌"太老太烂"
- YOLOPX 更新更强（指标见第十部分），MIT 许可，社区活跃
- 检测头 nc=1：只有车辆一类（从模型规格确认）

# 第十二部分：30031 协议逆向完整档案（09-25 晚大突破全程）

## 排查历程（每一步都有实验支撑）

1. **现象**：部署后包进来了（62 包/15s、c2s 送解 2）但候选包=0、样本=0——小地图无坐标
2. **48 字节包排查**：抓到的 c2s 48 字节包内容是心跳/握手（MaaNTE 原版解码器跑它也返回 None）——不是移动包
3. **大包排查**：移动时出现 1400/1076/304 字节大包，内容是 protobuf + UTF-16（food_material_0032、StoreBrandIncome、ereal_0027）——业务数据，也不是移动包
4. **错误结论被自己纠正**：我一度根据 /tmp/aurora_pcap.log 空白推断"从没成功过"——错在那是运行时日志（重启重建、只在有包时打印），142 小时稳定运行证明链路本质是通的
5. **突破口**：我自己用电脑操作（W 键）让角色移动 → 移动瞬间出现新数据
6. **扫描器迭代**：文本解析 pcap 只出 1 个 payload → 改二进制 pcap 解析（struct.unpack pcap global header 24 字节 + 每包 16 字节 record header）；函数名对齐 MaaNTE 原版（_bits/_vector 不是 _ue5_vector）；含 ValueError 语义
7. **假阳性识别**：off=452 的"候选"是固定字节巧合命中（98 包只出 1 个重复值）
8. **决定性发现**：s2c 包（服务器→客户端）在 bit=498/509 有稳定 float，且**随角色移动单调变化**

## 最终协议结构（实测确认）

- 移动同步包：**76 字节 s2c**（服务器批量下发预测轨迹，同一秒连发一串）
- **双记录结构**：rec1 @ bit498(X)+bit509(Z)，rec2 @ bit562(X')+bit573(Z')，offset 差 64 位
- 两个记录是同一坐标序列的不同时间点（当前位置 + 上一位置），C-A = -2145.77 恒定
- 固定字段：字节 64-67 与 72-75 是时间戳对（f91adf08/3c1bdf08，相差 67 = 同时刻包序列号）
- 静止对照：角色静止时单值恒定（-24424.34，无抖动）→ 确认是主角坐标
- 移动验证：X 每包 -1.118 匀速（角色匀速移动），大幅移动后 -24391→-24408（方向跟随）
- 地图换算：13056×13056（map-2026-08 扩图版），世界坐标 ×100 缩放；轴序最终确认 X=bit498, Z=bit509, Y=bit562（早期 Y 误设 bit562 落在黑暗弯道，用游戏内小地图十字路口 pattern 对照修正）

## Swift 生产化落地

1. 新协议解码路径接入 UE5Decoder（在旧 findCandidates 之前优先尝试）
2. 发现并修掉**s2c 丢弃断点**：生产代码里 `if direction == "s2c" || direction == "unknown" { return }` —— 而新协议移动包全是 s2c，解码器永远收不到
3. `--proto-selftest` 自检：用固化真实样本验证 Swift 解码器（与 Python 提取器同源对照）——14 项全绿
4. 部署实测：`[STATS] 包=6 s2c=1 c2s送解=2 解码调用=2 候选包=1/峰=1 样本=1 新协议=2` —— 新协议计数持续增长，**项目第一次从网络包解出真实坐标（协议变更后）**
5. 游戏失焦会停流（游戏后台化就暂停同步）——测试时要保持游戏前台

## 遗留与工具
- 坐标提取器：tcpdump 写文件 + 轮询解析（scapy 本机不可用）；固化样本已存项目
- 老解码路径（findCandidates/UE5 位流）保留为回退
- accel_z（FH6 需要）的坐标系数未标定

# 第十三部分：自适应网卡完整档案（09-25 傍晚诞生记）

## 诞生背景（问题链）
小地图"游戏未运行"→ 逐层排查 → **ap1 网卡 bug**：CoordinateCapture 的 start() 用"第一个能打开的网卡"，ap1（macOS 热点接口，inactive、累计 0 包）在 pcap 枚举排最前抢先被选中 → 抓空气 → 即使游戏启动也抓不到。BPF 权限时序（守护开机跑一次，bpf4 后创建）加剧随机性。

## 方案演进（两版）
- 初版"多通道并行"：所有候选网卡同时开 pcap 通道+探针线程，谁有包谁当选——**被用户否决（太重，"太美秒这么多次探测"）**
- 终版"**探测式状态机**"（用户口述设计）：平时定位正常不探测（零开销）；需要时（启动/断流）每 2 秒唤醒逐卡探测，谁有真实 30031 包锁谁；失流立即重探

## 实现要点
- 单线程统管状态机：探测 → 锁定监听 → 失流重探
- 删旧 captureLoop、activeInterface 改存储属性、close() 停主循环、lastGoodInterface 加锁
- 探测窗口分级：默认网卡 500ms / 默认路由接口（高嫌疑）2500ms——依据实测包率
- 失流窗口 3s → **12s**（突发静默期 6-9 秒会误判横跳）
- DriveState.hasRecentTraffic(window: 3.0) 同步改 12s 口径；坐标 read maxAge 1.0 同步适配

## 途中挖出的额外 bug
- **route 路径错误**：硬编码 /usr/sbin/route 不存在（真身 /sbin/route）→ "默认路由优选"从第一天起静默失效返回 nil。修成多候选路径 + sysctl 路由表查询（纯 C，无子进程）
- 双默认路由（en8 主 + en0 备用）需要正确选择逻辑

## 自检设计（--nic-autotest，真实流量不造假）
- 阶段 A：游戏没开 → 探测轮推进、不误锁
- 阶段 B：向网关 IP:30031 发真实 UDP → 2 秒内命中锁定
- 阶段 C：停发 4 秒（超失流窗口）→ 判停流重探
- 阶段 D：再发包 → 再次锁定
- ck() 断言 + PASS/FAIL 输出，11 项全绿

## 部署实测（游戏开着）
```
[10:20:35] 主循环启动（探测 高嫌疑2500ms/其余500ms / 重探2s / 失流12s）
[10:21:58] ✓ 探测命中：en8 有真实 30031 流量 → 锁定监听
[10:22:20] [STATS] 21s: 包=68
[10:22:38] ⟳ en8 停流（连续 12s 无 30031 包）→ 重新探测
```
三个状态全部按设计工作。

## TCC 大坑（部署必然代价）
- run.sh 重签 → CDHash 变 → 屏幕录制/辅助功能授权失效 → 引擎 fail-fast（ax=false screen=false）回退本地模式
- 用户手动重新授权（必须物理操作+Touch ID，AI 代不了）后：已运行进程不刷新缓存，**新启动进程才读到新值**
- **TCC 挂在裸可执行 AuroraDriveUI 条目**，bundle 是另一条目——run.sh 用 open bundle 启动拿不到权限；裸可执行直跑全链路通（用户判断正确："我从没想过给 App 任何权限"）
- 引擎是子进程，TCC 靠继承链——UI 裸可执行启动 → 引擎 --engine 继承成功

5. **机械截断压缩**——用户明确禁止：代码截断出来的摘要"模型会表现跟傻子一样"，必须人工通读手写

## 流程错误类
6. **没部署就说修好了**——修复只在 .build/scratch/ 里，在跑的是旧二进制。部署与修复是两件事
7. **部署不确认**——磁盘满导致部署一半失败，产物是旧的；要用 MD5 对比确认部署成功（strings 抓不到中文常量不是证据）
8. **会话内直接生成 32K"交接文档"**——DSH 会话里的模型做不到（生成垃圾+答非所问+骂战）。交接文档必须由外部 AI（WorkBuddy）读取会话日志后手写
9. **一输入就卡的会话里继续打字**——每个按键排队一个 O(会话大小) 任务，越堆越死
10. **pkill 后立刻 launch**——必须清 SingletonLock/Socket/Cookie 三件套，否则新实例静默转发给死实例

## 沟通错误类
11. **抢答没听完**——用户说"你先去搜，先不要告诉我，先不要干活"，就是要纯调研
12. **解释英文报错给用户**——用户看不懂英文，要给中文结论
13. **用户骂"你好蠢"时**——通常是事实判断错了（如"沙滩排球没数据"其实拍了），要用视觉能力重新看，别嘴硬
14. **插件出问题就删插件**——用户需要那个插件，删了等于毁工作。要修到能用

## 验证纪律（从对拍学到的）
15. **光看形状对没用**——int8 输出形状全对但像素塌 10 倍；必须跑像素级对照
16. **IoU 阈值不达先别改阈值**——先判断是"导出错"还是"指标不适用"（细线边界效应）；终极判据是下游消费量
17. **假设必须实验**——"游戏同步几十 Hz"的错误假设导致探测 100 轮全失败；实测包率 0.2-0.4/秒突发式
