## 二、卡顿归因（"一开自动驾驶就卡"）

### 2.1 实测的 CPU 增量

游戏运行中，用 `ps -o time=` 取 10 秒 CPU 时间增量：

```
自动驾驶【关】:  引擎   1.1%    UI 19.5%   游戏 136.3%   合计 156.9%
自动驾驶【开】:  引擎  96.8%    UI 23.1%   游戏 107.1%   合计 227.0%
                 ─────────────────────────────────────────────────
增量:            引擎 +95.7% 核        游戏 −29.2% 核
```

**游戏少了 29.2 个点的 CPU —— 这就是"卡"的直接来源。**

### 2.2 YOLOPX 的真实耗时分布

从引擎日志解析 **1705 个 `耗时=` 样本**：

```
min=46.5   p25=106.3   p50=171.8   p75=358.9   max=581.5  (ms)
```

- **空载**（游戏退出）：`--yolopx-selftest` 报 45.7 / 42.4 / 49.1 ms
- **游戏运行**：中位 171.8 ms

→ **YOLOPX 的耗时 100% 是争抢驱动的**，代码本身不慢。

### 2.3 瓶颈定位（`sample` 栈采样，258 样本）

```
YolopxEngine.infer(image:)                    295 samples
  └─ YolopxEngine.swift:620  modelRef.prediction   287
     └─ MLE5ExecutionStream._executeStream
        └─ E5RT::ExecutionStreamImpl::ExecuteStreamSync   258
           ├─ BnnsCpuInferenceOperation::ExecuteSync    162  (62.8%)  ← CPU!
           │     └─ BNNSGraphContextExecute_v2 (libBNNS)
           └─ AneInferenceOperationImplUsingAnefAPIs   145  (37.2%)  ← ANE
              └─ ANEServicesProgramProcessRequestDirect
```

**`BnnsCpuInferenceOperation` 是最大单项消费者，超过 ANE 路径。**

### 2.4 已实测**否决**的优化方向

> 这些都是真跑过、有数字的，**不要再试**。

| 方向 | 实测结果 | 判定 |
|---|---|---|
| 档位 `.all` → `.cpuAndNeuralEngine` | 空载 183.0 vs 204.6 ms；满载 191.4 vs 199.1 ms（ABBA 交替，各 12 轮） | ❌ `.all` 更快，**已回退** |
| 档位 `.cpuAndGPU` | 278.5 ms（真游戏运行时测） | ❌ 慢 60% |
| 拆 softmax 为 exp/max/mean | CPU 算子 **10 → 21** | ❌ 证伪 |
| matmul 化折叠除法 | CPU 算子 **10 → 24** | ❌ 证伪 |
| 去掉 PSA 模块 | 只省 **10.0 ms（4%）**；CPU 算子 10→4 | ❌ 非瓶颈 |
| NMS 优化 | 阈值 0.25 下真实候选只有 **16 个**（不是 6274） | ❌ 无收益 |
| 量化变体 int8 / w8a16 | 真游戏下：pal8 189.6 / int8 186.0 / w8a16 190.6 ms | ❌ 差 2%，噪声内 |
| 输出端压缩（砍掉两张掩码） | 83.3 → 95.3 ms（**没变快**） | ❌ 瓶颈是主干卷积，不是 ANE→CPU 搬运 |
| `letterbox` CGContext → vImage | 10.540 → 2.309 ms（**快 4.57×**），但**检测框 9 → 6 个** | ❌ **精度回退，不可接受** |
| 灰度转换改 vImage | 0.462 vs 标量 0.326 ms | ❌ 更慢 |
| `kvImageDoNotTile` | 省 1.1%（ABBA 12 轮） | ❌ 噪声内 |
| 预分配 tempBuffer | **慢 20%** | ❌ 证伪 |
| 两级降采样（2560→640→480） | **慢 25%** | ❌ 证伪 |

### 2.5b 【决定性】四个模型的真实单次耗时（本轮实测）

用**各模型自己的真实输入格式**分别测（此前误用统一 `{'image': img}`，
导致 m9/assist 报 `RuntimeError: value type not convertible` ——
它们的输入规格根本不同）：

| 模型 | 输入规格 | 单独耗时 | 并发耗时 | 拖慢 |
|---|---|---|---|---|
| `game_assist_control` | `image[1,3,180,320]` + `vehicle_state[1,6]` | **0.9 ms** | 0.9 ms | 1.06× |
| `yolo26s` | `Image(640×640)` | **6.5 ms** | 7.4 ms | 1.13× |
| `yolopx` | `Image(640×640)` | **68.9 ms** | 75.7 ms | 1.10× |
| **合计** | | **76.3 ms** | **84.0 ms** | **1.10×** |

**三个结论（都推翻了之前的推断）：**

1. **`game_assist_control` 只要 0.9 ms** —— 它的输入是 180×320 的小图，
   完全不是瓶颈。之前推算的「~12 ms」是错的。
2. **ANE 争抢不是主因** —— 三模型并发只让彼此慢 **1.10×**。
   之前推测的「ANE 单队列导致严重排队」**不成立**。
3. **`yolopx` 占了 82%**（68.9 / 84.0）—— 它是唯一的成本中心。

**由此可推出引擎 CPU 的构成：**

    引擎实测 121~131% 核
      └─ yolopx 持续占满约 1 个核  （68.9ms 推理 / 68.9ms 周期 = 100%）
      └─ 其余（tick + 其他模型 + 光流）约 20~30%

**`yolopx` 之所以吃满一个核，是因为它「永远在推理」**：
`isInferencing` 门只挡住重叠提交，不改变「一次接一次连续跑」的事实。

### 2.6 关键结构性事实

**4 个模型共享 ANE（单队列硬件），必须排队：**

```
m9_mono (M9端到端主驾)     ~15 ms
game_assist_control        ~12 ms
yolo26s                      6.2 ms
yolopx                      69.2 ms   ← 空载实测
────────────────────────────────────
合计（若串行）              ~102 ms   vs tick 预算 33.3 ms
```

**超支 3.1 倍** —— 每个模型都被拖慢，引擎持续满载。

**三个推理队列全部是 `.userInteractive`（最高优先级），与游戏主线程（PRI=46T）抢同样的 4 个 P 核。**

## 三、小地图定位根因

### 3.1 坐标链路的真实时序（本轮新增埋点测得）

在 `CoordinateCapture` 加了 `[SAMPLE] 坐标落地 间隔=...` 埋点后测得：

```
间隔=15.02s   世界=(-76993.2, 31865.4)
间隔=15.00s   世界=(-76997.6, 31865.4)
间隔=15.01s   世界=(-77002.1, 31865.4)
间隔=15.01s   世界=(-77006.6, 31865.4)
间隔=15.01s   世界=(-77011.1, 31865.4)
```

**游戏固定每 15.01 秒下发一个坐标包**（每周期世界坐标推进约 4.5 单位 ≈ 4.5cm）。

**且约 6% 的周期整轮不发**：17 个统计周期中 1 次 `s2c=0`、`候选包=0`。

### 3.2 阈值判据的断崖式失败（蒙特卡洛验证，6% 断档率）

| 窗口 | 定位可用率 |
|---|---|
| 18s | 94.6% |
| 25s | 94.6% |
| 30s | 94.6% |
| **35s** | **99.7%** |

**没有中间地带** —— 要么闪断，要么让出 23 秒的幽灵定位。

**实机日志直击**（修复 `dlog` 可写性后才第一次看到）：
```
[LOCATE] 定位中断 —— 累计包=72 有样本=true 样本年龄=15.0s 窗口=15s ← 有样本但已过期
```
**样本年龄与窗口分毫不差地撞在一起。**

### 3.3 根治方案：分级新鲜度

新增 `CoordinateCapture.PoseRead`：

```swift
enum PoseRead {
    case unavailable                      // 从未收到过
    case fresh(Pose)                      // 新鲜
    case stale(Pose, ageSeconds: Double)  // 陈旧，但【仍返回位置】
}
```

**关键差异：**
```
旧 read():              超窗 → nil    → 地图清空 → 闪断
新 readWithFreshness(): 超窗 → stale  → 位置照常 → 不闪断
```

UI 新增 `stale` 态文案「网络定位 · 数据稍旧」，`networkLocateScore` 减半。

### 3.4 窗口值调整（保留层级）

```
streamLostWindow   = 22.0s   （网卡失流判据，最后放弃）
trafficFreshWindow = 20.0s   （流量新鲜判据）
poseFreshWindow    = 18.0s   （坐标新鲜判据 = 15.01s 周期 + 3s 余量）
```

**必须满足**：`traffic ≥ pose`、`streamLost > traffic`，
否则出现「流量新鲜但坐标过期」的中间态，定位诊断无法收敛。

### 3.5 另一处 BUG：`worldMetersPerMap` 错 1.639 倍

```swift
// 旧（注释自相矛盾："13056px 地图对应 13.056km" = 断言 1px = 1m）
static let worldMetersPerMap: Double = 13_056
```

**由标定参数推导：**
```
kCalibA = 0.016394586684750773     世界单位(cm) → 地图像素
⟹ 1 像素 = 1/kCalibA = 60.9957 cm = 0.609957 米
⟹ 13056 像素 = 7963.6 米   （不是 13056 米）
```

**可信度佐证**：`kCalibA/B/TX/TY` 与 MaaNTE 上游 `coordinate_position.py`
的 `_CALIBRATION_*` **逐位相同**；用真实样本反算自车像素与自检报告
**只差 1 像素**（世界 (-24424.34, 31854.1) → 地图 (6126.0, 5732.9)，自检报 (6127.0, 5732.9)）。

**影响（`pxPerMeter = mapPixels / worldMetersPerMap` → `spanPx` → `normMapX/Y`）：**

| 真实距离 | 修复前显示在 | 误差 |
|---|---|---|
| 50 米 | 82.0 米 | +32 米 |
| 100 米 | 163.9 米 | +64 米 |
| 160 米 | 262.3 米 | +102 米 |

**自车位置不受影响**（`worldToMapPixel` 不用此常量）→ 症状是
「我人在对的地方，但周围标记全偏」。

**修法**（消除漂移，而非改数字）：
```swift
static let worldMetersPerMap: Double = 13_056.0 / (kCalibA * 100.0)
```

### 3.6 标定参数本身是**正确**的（已验证）

```
世界坐标 X: -76760.26 → -76885.73   变化 -125.47
地图像素 X:   5268.0  →   5266.0    变化   -2.00
由标定预测: -125.47 × 0.016394587 = -2.0570 像素
误差: 0.06 像素   ✅
```

## 五、日志可写性：定位无法诊断的真正原因

### 5.1 现场铁证

```
-rw-r--r--@ 1 root  wheel  105  Sep 26 10:31  /tmp/aurora_debug.log
```

**文件属主是 `root`**（历史遗留），而 UI 以普通用户 `dupi` 运行 →
`FileHandle(forWritingTo:)` 抛权限错误。

### 5.2 原实现（静默吞掉）

```swift
if let h = try? FileHandle(forWritingTo: url) { ... }   // 失败 = 什么都不做
else { try? data.write(to: url) }                       // 同样被 try? 吞掉
```

**两条路径都是 `try?`** → 写失败静默无痕。
「文件存在但内容是 3 天前的」会一直被误判成「代码没走到」。

### 5.3 修法（三处同样的缺陷）

`DriveState.dlog` / `AgentSkillCenter.dlog` / `CoordinateCapture.pcapLog`
全部加可写回退链：

```
/tmp/aurora_debug.log  →  ~/Library/Logs/aurora_debug.log  →  /tmp/aurora_debug_ui.log  →  stderr
```

**保留 `/tmp` 首选 → 对能正常写的环境零行为变化。**

**已验证**：
```
✗ 不可写: /tmp/aurora_debug.log          （root:wheel）
✓ 写入成功: ~/Library/Logs/aurora_debug.log
```

## 六、测量方法论备注

> 这一轮最大的教训：**只有 ABBA 交错测量可信。**

失误记录：
- 单次测得"两次 vImage 缩放要 14~18 ms"，ABBA 复测实际 **3.59 ms**（10.9% 预算）
- 单次测得"NMS 要 84 ms"，真实候选只有 **16 个**（84 ms 是合成最坏情况）
- 用 8 个 busy loop 模拟游戏负载测档位，结论与**真游戏运行时相反**
- `extractMask` 独立微基准在不同轮次报出 39.6 / 35.0 / 11.1 / 3.98 ms —— 同一份工作
- 并发基准污染：`swift build` 与基准同时跑，产生过 `CPU_AND_NE = 1225.4 ms` 的假数据

**环境注意**：
- macOS 无 `timeout` 命令（用 `perl -e 'alarm shift; exec @ARGV'`）
- `ps` 不支持 GNU `--sort`
- `strings` 对中文 UTF-8 不可靠（用 `grep -a` 或 `LC_ALL=C grep`）

## 六点五、本轮修复的真实 Bug（都不是性能问题，而是功能被阻断）

> 这三个是**功能级**缺陷，与「卡」无关，但都直接阻断用户要的能力。

### 6.5.1 `CGEventTap` 失败导致 `applicationDidFinishLaunching` 提前返回

**位置**：`AuroraDriveApp.swift`（原 `guard let eventTap = ... else { print(...); return }`）

**症状**：辅助功能权限未授权时，**该函数后续约 200 行全部被静默跳过**。

**实测证据**（`AURORA_UI_LOCAL=1 ./AuroraDriveUI --auto-login`）：

    修复前：日志 15 行，`--auto-login` 的 fputs **完全没出现**
    修复后：日志 29 行，`[AUTO-LOGIN] 收到 --auto-login` 正常打印

**被跳过的功能**（逐个核实）：

| 行 | 功能 |
|---|---|
| `:454` | `--auto-login` 启动即自动登录 |
| `:465` | `--agent-command` AI 发布指令 CLI |
| `:469` | `AgentSkillCenter.requestCommandOnStartup` |
| `:478-480` | 命令模式判定 + `ControlEngine()` / `CaptureEngine()` 构造 |
| `:482` | `AgentSkillCenter.configure(control:capture:)` 技能引擎注入 |

**为什么原写法错**：event tap 的用途只是「让系统视本进程为实时响应进程」
（抗 Game Mode 冻结的**可选增强**），与「解析 CLI 参数 / 构造引擎」零依赖。
用可选增强的失败终止整条初始化链 = 把降级误当致命错误。

**修法**：`guard ... return` → `if let ... { } else { 如实记录并继续 }`。
权限正常时路径与原来逐字节相同。

### 6.5.2 辅助功能权限**只查询、从不请求**

**位置**：`ControlEngine.checkPermission()` + 两个调用点

**症状**：程序**从未出现在**「系统设置 → 隐私与安全性 → 辅助功能」列表里，
用户想授权都找不到条目。

**原因**：全项目只有 `AXIsProcessTrustedWithOptions(nil)` ——
传 `nil` 时该 API **只查询、绝不弹窗**（原注释里「首次调用会自动弹系统授权提示」是错的）。
`openAccessibilitySettings()` 只是打开了一个空面板。

**修法**：拆成两个方法（职责不能合并）：

    checkPermission()                → 纯查询，不弹窗
                                       用于 press/hold 的每帧重试路径
    requestAccessibilityPermission() → 弹窗 + 登记进列表
                                       只在初始化时机调用（启动检查 / configure）

### 6.5.3 主线程编译 CoreML 模型

**位置**：`SpeedOCRReader.loadCNNModel()` / `loadPPOCRModel()`

**症状**：`open AuroraDriveUI.app`（LaunchServices）启动时进程**永久空转**
（4 线程 / 0.0% CPU / 70MB，CPU 时间 30 秒零增长，不写日志、不建窗口）。

**栈证据**（`sample` 三次采样一致）：

    ContentView.init → DriveState.init → SpeedOCRReader.init
      → loadCNNModel → MLModel.compileModel(at:)
        → ModelPackage 构造 → fopen → open()      ← 阻塞

**Apple 官方 Fault**（unified log，CoreML 子系统）：

    This method should not be called on the main thread
    as it may lead to UI unresponsiveness.

**修法**：用 Xcode 工具链的 `coremlcompiler` **预编译**为 `.mlmodelc`，
与 `.mlpackage` 并列存放；运行期优先命中 `.mlmodelc`（直接加载、零编译），
找不到才回退原路径。**行为零变更** —— `.mlmodelc` 就是 `compileModel` 本会产出的东西。

**验证**（独立 Swift 程序实测四个文件）：

    ppocrv6   .mlmodelc  371.6 ms   |  .mlpackage  366.2 ms
    speed_cnn .mlmodelc   96.7 ms   |  .mlpackage  123.5 ms   ← 快 27ms
    输入签名一致：image / digit_input

**效果**：CoreML Fault 从「每次启动必报」降为 **0**。

**遗留**：`open` 路径仍空转，但卡点已转移到
`_handleAEOpenEvent → NSPersistentUIRestorer`（窗口状态恢复）。

## 六点六、TCC 权限责任链（为什么「授权了还是不行」）

**tccd 日志实证**：

    shell 启动:  responsible = io.dsh.desktop.helper        ← DSH 无权限 → Aurora 拿不到
    open  启动:  accessing   = com.aurora.driveui           ← 责任方是自己 → 可授予

**机制**：macOS TCC 看「责任方」（responsible process）。
从 DSH（本会话宿主）启动的进程，责任方被算到 DSH Helper 头上；
而 DSH Helper 的授权记录是：

    132 次  kTCCServiceAccessibility  → Failed to match existing code requirement
     28 次  kTCCServiceScreenCapture  → Failed to match existing code requirement

**后果**：Aurora 的键鼠注入被系统静默丢弃
（表现为 `[Agent] ❌ 辅助功能权限未授权，无法注入鼠标`）。

**解法**：
- **A（推荐）** 用户从 Finder 双击 → 责任方是 Aurora 自己 → 可授权
  （但需先解决 `open` 的空转，见 6.5.3 遗留）
- **B** 给 DSH Desktop 授辅助功能权限 → 从 shell 启动的一切都继承
- **C** 以 root 运行（项目已有 `/usr/local/bin/aurora-drive-daemon`，LaunchDaemon）

## 六点七、★★★ 卡顿的真正根因（本轮最终定位并修复）★★★

> 本轮之前所有工作都在排查「哪个模型慢」「ANE 争抢」——**全部不是主因**。
> 真正的卡顿来自一个 SwiftUI 反模式，与模型推理零关系。

### 6.7.1 `@State` 默认值表达式 → 每帧重建整套引擎

**位置**：`MissionConsole.swift` `struct ContentView` 首行

    // 修复前
    @State private var state = DriveState()

**机制**：`@State` 的默认值表达式是**视图结构体的存储属性初始化**。
SwiftUI 的 View 是值类型，**视图树每次重建都会构造一个新的 ContentView 实例** ——
于是这个表达式被反复求值。SwiftUI 随后丢弃新对象、沿用首次建立的
`@State` 存储，**但构造副作用已经真实发生了**。

**`DriveState.init()` 的副作用清单**（逐项核实）：

| 动作 | 开销 |
|---|---|
| `upscaleHost.prepare()` → `GooseUpscaler.make()` + `configureInterpolation()` | 建 Metal 引擎 + 运行时编译插帧着色器 |
| `gameHUD.install()` | **新建 NSWindow** |
| `FileManager.removeItem('/tmp/aurora_debug.log')` | 删文件 |
| 构造 `captureEngine` / `yoloEngine` / `yolopxEngine` / `speedOCR` / `motionPredictor` / `fallbackGuard` … | 十余个推理与采集组件 |

**实测量级**（`AURORA_UI_LOCAL=1 ./AuroraDriveUI --auto-login`，69 秒窗口）：

| 指标 | 修复前 | 修复后 | 倍数 |
|---|---|---|---|
| `[upscale] 引擎初始化` | **349 次** | **1 次** | **349×** |
| `[network] 定位引擎初始化完成` | **349 次** | **1 次** | **349×** |
| 日志总行数 | 1041 | 119 | 8.7× |
| `[WindowDiag]` | 278 条 | 6 条 | 46× |

（同一秒内连续爆发多次 ⟹ 与「视图求值频率」完全吻合，而非重启循环。）

**修法**：`DriveState.shared` 惰性单例 + `ContentView` 改为
`@State private var state = DriveState.shared`。

**为什么语义等价**：
- 全进程本来就只需一个 DriveState（它代表唯一一份驾驶状态机）；
- 原写法在任一进程里的**有效结果**同样是「只有一个实例被真正使用」，
  本改动只是不再构造那几百个立刻被丢弃的副本；
- 单例是**每进程一个**（非全局）—— 引擎进程（`--engine`）与 UI 进程
  各自持有自己的实例，互不影响。

### 6.7.2 `MapDatabase.ensureLoaded()` 在 body 求值里读 7.2 MB JSON

**位置**：`MapWiring.swift` `MapDatabase.ensureLoaded()`

**症状**：`open`/双击启动时主线程卡死在启动阶段。

**栈证据**：

    ContentView.body.getter
      → MapDatabase.ensureLoaded()
        → NSData(contentsOfFile:) → readBytesFromFile → open()

`ensureLoaded()` 在**三处**被调用，其中 `MissionConsole.swift:2853` 就在
`ContentView.body.getter` 的求值路径上。而 body 求值发生在主线程 layout 提交期
（`NSHostingView.layout` → `ViewGraphRootValueUpdater.render`），
在这里读 7.2 MB（`models/FINAL_complete_map_database.json`，5677 标记点）
会把窗口构建与事件循环一起拖住。

**修法**：读盘 + JSON 解析整体移到 `DispatchQueue.global(qos: .utility)`，
结果回主线程一次性落状态（`markers` / `markerCount` / `loaded`）。
`isLoading` 做并发保护，`didLoad` 仍表示「已完成」。
**调用方零改动**，`ensureLoaded()` 仍是幂等的，只是变成「发起加载」。

**验证**：`[MAPDB] 已加载 … markers=5677` 正常，计数与坐标系不变。

### 6.7.3 `SpeedOCRReader.init()` 同步做 CoreML 模型 I/O（`open` 死锁的直接原因）

`modelsReady` / `modelsLoading` 供 UI 如实显示。
新增 `loadModelsOnBackground()` / `applyLoadedModels()` / `loadOneModel()` /
`modelCandidates()` 四个纯函数式实现，旧的 `loadCNNModel()` /
`loadPPOCRModel()` 保留为兼容壳（委托到统一实现）。

**验证**（`open` 启动，修复后）：

### 6.8.1 一个字段，两种坐标系

**位置**：`AuroraDriveApp.swift:2750` 写入端 / `MapWiring.swift:36` 等 5 处读取端

拿「像素 − 世界坐标」相减，量纲彻底错乱。统一到世界坐标可让两侧同时正确。

**同步修正**：`MissionConsole` 两处离屏夹具的假坐标

### 6.8.5 附带修复：离屏夹具 vs 异步加载

## 六点十、本轮追加修复：`regionLabel` 每帧遍历 5677 个标记

### 6.10.1 问题

**位置**：`AuroraDriveApp.swift` `DriveState.regionLabel`

    // 原写法（计算属性，UI body 里每次求值都执行）
    var regionLabel: String {
        guard locatorFound else { return "未知区域" }
        return MapDatabase.regionName(atMapX: mapPixelX, mapY: mapPixelY) ?? "未知区域"
    }

`regionName` 内部要**遍历全部 5677 个标记点**找最近的一个：

    for m in markers {                        // 5677 次
        let d = (px-mx)² + (py-my)²
        if best == nil || d < best!.0 { best = (d, m.region) }
    }

**为什么既有格缓存只挡住了一部分**：`regionName` 里确有一层
「100px 格缓存」（同格直接返回上次结果），但它挡不住两种情况：

1. **跨格瞬间**：缓存按 `Int(mx/100)` 分格，一旦自车跨过格边界，
   就重新全量遍历 5677 个标记。120km/h 下每秒跨格十几次。
2. **`locatorFound` 刚变为 true 的那一刻之前的每次求值**：
   区域名要等第一次定位才有值，而 body 在那之前也在反复求值。

更关键的是**职责错配**：`regionLabel` 是**计算属性**，被放在 UI body 里，
于是「反查区域」这件与渲染无关的事，被绑到了**渲染频率**上
（每秒数次~数十次），而不是**定位更新频率**（每 15 秒一次）。
两者相差两个数量级 —— 即便每次只是缓存命中，函数调用、格坐标计算、
`MapDatabase.markers` 的 empty 检查等开销也全在主线程上白烧。

**修法**：把「反查区域」从**每次 body 求值**降到**定位更新时一次**：

    private var regionCache: String = "未知区域"

    func refreshRegionCache() {          // 由定位回调每 15s 调一次
        guard locatorFound else { ... }
        let name = MapDatabase.regionName(...) ?? "未知区域"
        if name != regionCache { regionCache = name }
    }

    var regionLabel: String { regionCache }   // body 安全：纯值读取

**结果逐字一致**：同一套 regionName 反查、同一份数据库、同一个「未知区域」兜底。

### 6.10.2 附带修复：离屏夹具的调用顺序

`regionLabel` 改缓存后，离屏夹具（`--mc-map` / TopBar 截图）不走定位回调，
必须显式调 `refreshRegionCache()`。**且顺序不可颠倒** —— 该函数要遍历
`MapDatabase.markers`，必须在 `ensureLoadedSyncLegacy()` **之后**调用，
否则 markers 为空、只会缓存成「未知区域」。

**实测踩坑与修复**：

    第一次：夹具里 refreshRegionCache() 在 ensureLoadedSyncLegacy() 之前
            → 左上角显示「未知区域」（错）
    修正后 → 显示「新赫兰」（对）

## 六点十一、AttributeGraph cycle 的定性（不是卡顿源）

### 6.11.1 现象

新版启动后 stdout 出现大量：

    === AttributeGraph: cycle detected through attribute 105296 ===

各版本对比（同一条命令，25~30 秒窗口）：

| 版本 | cycle 数 | 日志行数 | 说明 |
|---|---|---|---|
| 备份 `bak-20260929-2317` | **0** | 14 | **14 行就停了** —— `CGEventTap` 的 `return` bug 让它卡在初始化，**根本没走到 ContentView** |
| 新版（本轮修复后） | 90~98 | 119~129 | 跑完初始化 → ContentView 构建 → cycle 出现 |

⟹ **cycle 不是本轮改动引入的，而是「跑得更远」后才暴露的既有现象。**
   旧版不是没问题，是它**根本没跑到出问题的地方**。

### 6.11.2 是否影响性能：实测无

**主线程采样**（`sample` 5 秒，3498 个样本）：

    mach_msg（空闲等待事件）          2838  = 81.1%
    _CFRunLoopRunSpecificWithOptions  3495  = 99.9%

**收敛性**（同一进程连续观察）：

    30 秒前 cycle 数: 98
    30 秒后 cycle 数: 98
    增长: 0 次  ⟹ 启动后即收敛，不是持续循环

**全进程热点分布**（总样本 2237）：

| 占比 | 符号 |
|---|---|
| 2.9% | `DisplayList.ViewUpdater.updateInheritedView` |
| 2.2% | `DisplayList.ViewUpdater.ViewCache.update` |
| 2.1% | `_findAnySubviewNeedingAutoLayoutEngine` |
| … | 其余均 < 2% |

⟹ 热点高度分散、无单一支配项；主线程 81% 空闲。
   **cycle 是 SwiftUI 在首次构建视图树时的内部依赖环警告，之后收敛，不构成卡顿。**

### 6.11.3 唯一实际影响与判定

**实际影响**：cycle 由系统框架用 `print` 直接写 stdout，
会**淹没 CLI 夹具的输出**（实测 `--yolo-bench` 的真实结果被 cycle 刷掉，
需 `grep -v AttributeGraph` 才能看到）。

**未能定位到具体 attribute**：id（如 105296）是 AttributeGraph 运行期分配的，
不直接对应源码行。已排除的方向：
- 不是 `GameHUDWindow`（它是纯 AppKit `NSTextField` + `Timer(0.5s)`，不走 SwiftUI）
- 不是 `--auto-drive`（不带该参数同样有 90 次）
- 不是项目代码打印（全仓库无 `AttributeGraph` 字样，是系统框架输出）

**判定**：**不作为卡顿处理**。理由是量化的：
主线程 81% 空闲 + cycle 30 秒零增长 + 热点无支配项。
真正的卡顿（`DriveState` 每帧重建 349 次）已在前文修复并验证。

## 六点十二、TCC 责任链的最终实证（授权路径已确认可用）

### 6.12.1 两种启动方式的 attribution 对比

同一台机器、同一个二进制、同一时刻，仅启动方式不同：

**shell 启动**（`AURORA_UI_LOCAL=1 ./AuroraDriveUI --auto-login`）：

    AUTHREQ_ATTRIBUTION: attribution={
        accessing   = { identifier=AuroraDrive,        binary_path=…/AuroraDriveUI }
        responsible = { identifier=io.dsh.desktop.helper,
                        responsible_path=/Applications/DSH Desktop.app/Contents/Frameworks/… }
    }

**`open` / Finder 双击启动**（`open AuroraDriveUI.app --args --auto-login`）：

    AUTHREQ_ATTRIBUTION: attribution={
        accessing   = { identifier=com.aurora.driveui }
        （无 responsible 字段 ⟹ 责任方即 accessing 自己）
    }

### 6.12.2 为什么这决定了成败

macOS TCC 判定权限时看的是 **`responsible`（责任进程）**，不是 `accessing`：

| 启动方式 | responsible | 结果 |
|---|---|---|
| shell（经 DSH） | `io.dsh.desktop.helper` | DSH 无辅助功能授权 → **Aurora 永远拿不到** |
| `open` / 双击 | （自己） | 可被授予 → **能出现在系统设置列表里** |

DSH Helper 的授权记录实测（本项目早前测量）：

    132 次  kTCCServiceAccessibility  → Failed to match existing code requirement
     28 次  kTCCServiceScreenCapture  → Failed to match existing code requirement

⟹ 从 shell 启动的一切都继承这条被拒的链。

### 6.12.3 与「鼠标注入被丢弃」的实测闭环

自写 CoreGraphics 探针（独立程序，非推测）：

    注入前光标 (735.0, 494.0) → 注入后 (735.0, 494.0)    位移 dx=0.0
    CGEventTap 可创建，但 post 到 .cghidEventTap 无效
    AXIsProcessTrusted() = false
    CGPreflightScreenCaptureAccess() = false

**权限是硬前提，绕不过去** —— 但 `open` 路径（本轮已修复死锁）提供了可授予的身份。

### 6.12.4 授权步骤（给用户）

1. **从 Finder 双击** `AuroraDriveUI.app`（**不要**从终端启动，否则责任方是 DSH）
2. 打开「系统设置 → 隐私与安全性 → 辅助功能」
3. 把 **AuroraDrive** 勾上（若不在列表里，点 `+` 手动添加该 .app）
4. 同样在「屏幕录制」里勾上（引擎进程需要它抓帧）

**当前 CDHash（授权按此指纹识别）**：

    CDHash     = （见下方"当前部署指纹"一节，每次重新编译都会变）
    Identifier = com.aurora.driveui
    Signature  = adhoc（无 TeamIdentifier）

⚠️ **授权完成后不要重新编译** —— 重新编译会改变 CDHash，
   系统会视为「另一个程序」，已有授权失效。

### 6.12.5 顺带澄清：两处 `failed to find an Application URL` 不是本项目的

`log show` 里能看到：

    handle_TCCAccessCopyInformation(): failed to find an Application URL
      for bundle ID: com.aurora.AuroraDrive
    handle_TCCAccessCopyInformation(): failed to find an Application URL
      for bundle ID: com.aurora.drive

**这两个 bundle ID 与 AuroraDrive 无关**：本项目的真实 ID 是 `com.aurora.driveui`
（`Info.plist` 的 `CFBundleIdentifier` 与 `codesign` 的 `Identifier` 一致）。
同一批报错里还有 `com.openai.codex`、`cn.trae.app`、`com.qoder.ide`、
`com.aliyun.lingma.ide` 等 —— 是**其它 IDE/工具扫描系统里注册过的 bundle ID**
时留下的查询，不是 Aurora 的失败。

## 六点十三、授权为什么是「自己操作游戏」的硬前提（因果链闭合）

### 6.13.1 `startDriving()` 的第一道门就是权限

**位置**：`AuroraDriveApp.swift` `DriveState.startDriving()`

    func startDriving() {
        // 引擎模式：命令转发给后台引擎（不走下面）
        if EngineClient.shared.isActive { … return }

        // ⚠️ 权限检查：按键注入需要辅助功能权限
        guard controlEngine.requestAccessibilityPermission() else {
            controlPermissionDenied = true
            controlEngine.openAccessibilitySettings()
            return                    // ← 无权限就直接返回
        }
        controlPermissionDenied = false
        controlEngine.releaseAll()
        isDriving = true              // ← 永远到不了这里
        keyboardMonitor.start()
        captureEngine.start()
        …
    }

⟹ **没有辅助功能权限 ⟹ `isDriving` 恒为 false ⟹ 自动驾驶不启动。**

这不是「按键被丢弃」这么局部的问题，而是**整条驾驶链路的入口守卫**。
也解释了 `--auto-drive` 为何看起来「没生效」：它确实调了
`state.startDriving()`（日志有 `[AUTO] --auto-drive 收到`），
但被守卫挡回，于是 `tick` 的诊断分支（`guard isDriving else { … return }`）
从不执行，日志里自然一行 `tick:` 都没有。

### 6.13.2 权限请求确实发出了，但责任方不对

实测（shell 启动的实例，pid=89602）：

    REQUEST: sender_pid=89602, function=TCCAccessRequest, msgID=89602.5
    ...attempted to call TCCAccessRequest for kTCCServiceAccessibility without the
       recommended com.apple.private.tcc.manager.check-by-audit-token entitlement
    AUTHREQ_ATTRIBUTION: attribution={
        responsible = { identifier=io.dsh.desktop.helper, pid=12089,
                        responsible_path=/Applications/DSH Desktop.app/Contents/Frameworks/… }
        accessing   = { identifier=AuroraDrive, pid=89602,
                        binary_path=…/自动驾驶系统/AuroraDriveUI }
        requesting  = { identifier=AuroraDrive, … }
    }

**请求发出了（本轮 `checkPermission()` → `requestAccessibilityPermission()` 的修复生效），
但 TCC 把责任方算在 `io.dsh.desktop.helper` 头上**，而后者没有授权记录
⟹ 请求被拒，程序也进不了授权列表。

### 6.13.3 三段证据的完整闭环

| 环节 | 证据 | 结论 |
|---|---|---|
| ① 无权限时能否注入 | 自写 CoreGraphics 探针：光标注入前后 `(735.0,494.0)` 不变，`dx=0.0`；`AXIsProcessTrusted()=false` | **不能，硬阻断** |
| ② 无权限时能否驾驶 | `startDriving()` 的 `guard … else { return }` + 日志无 `tick:` 行 | **不能，入口就被挡** |
| ③ 为什么 shell 启动拿不到 | `responsible=io.dsh.desktop.helper`（无授权记录） | **责任方错** |
| ④ `open` 启动能否拿到 | `accessing=com.aurora.driveui`，无 `responsible` 字段；TCC 成功解析 `staticCode … at …/AuroraDriveUI.app` | **可授权 ✓** |

### 6.13.4 因此：唯一出路是让用户从 Finder 授权一次

代码侧已无剩余可做项 ——
`open` 路径的死锁（6.7.3）、权限只查不请求（6.5.2）、
`CGEventTap` 提前 return（6.5.1）三处阻断都已在前面几轮修掉并验证。
剩下的这一步**必须由用户在系统 UI 里完成**（TCC 设计如此，任何程序都无法代劳）。

## 六点十四、决定性测量：卡顿的主因不是 Aurora（A/B 对照）

### 6.14.1 测量方法

同一时刻、同一台机器，唯一变量是 **Aurora 是否运行**。
用 `ps -o time=` 前后差（CPU 时间累加值）而非 `ps -o %cpu=`（那是进程
生命周期均值，会随运行时长稀释，不可用于短窗口比较）。

    measure() {
      a=$(ps -o time= -p <PID>)          # 起点 CPU 时间
      sleep 12
      b=$(ps -o time= -p <PID>)          # 终点 CPU 时间
      cpu% = (b - a) / 12 * 100
    }

### 6.14.2 结果（先单次，后修正为 3 轮 ABBA）

**首次单次测量**（n=1，**结论被后续推翻，保留以示过程**）：

| 组别 | WindowServer | 游戏进程 |
|---|---|---|
| A：Aurora 运行中 | 37.9% | 78.9% |
| B：Aurora 已关闭 | 41.0% | 79.7% |
| A − B | −3.1% | −0.8% |

⚠️ **这个单次结果不可靠**：同一配置下 WindowServer 的自然波动就有 ±3%，
单次测量落在噪声里。**因此做了 3 轮 ABBA 重复。**

**3 轮 ABBA 重复测量**（关→开→关→开→关→开）：

| 轮次 | Aurora 关 | Aurora 开 |
|---|---|---|
| 1 | 41.4% | 44.2% |
| 2 | 40.9% | 44.7% |
| 3 | 41.4% | 44.7% |
| **中位** | **41.4%** | **44.7%** |

⟹ **Aurora 对 WindowServer 的真实增量 = +3.2%**（三组样本各自极稳定，
关组离散度 0.5%、开组 0.5%，组间差异远大于组内波动）。

**修正后的结论：Aurora 确实带来约 3.2% 的合成器开销**（它有个
0.5 秒刷新的 GameHUD 悬浮窗 + 主窗口），但**这个量级（3.2%）与
游戏自身的 75~81% 相比可以忽略** —— 见 6.14.3 的排序。

### 6.14.3 结论：卡顿的三个 CPU 大户排序

同一时刻 `top -o cpu` 的实测快照：

| PID | 进程 | %CPU | 说明 |
|---|---|---|---|
| 81772 | **异环（游戏本体）** | **62.0** | 已在登录页停了 6 小时 27 分，64 线程，**什么也没做** |
| 459 | WindowServer | 39.8 | 系统合成器 |
| 0 | kernel_task | 17.1 | 内核 |
| 3069 | **AuroraDriveUI** | **12.1** | 本应用 |
| 466 | coreaudiod | 10.4 | |
| 960 | Mio Island | 9.2 | 游戏的另一个进程 |

**游戏本体 62% + Mio Island 9.2% ≈ 71%**，是 Aurora（12.1%）的**约 6 倍**。
（ABBA 复测中游戏稳定在 **75~81%**，且 **Aurora 开关对此几乎无影响**：
开 74.8~75.6%、关 80.5~81.2% —— 中间的差异来自游戏自身渲染波动的相位，
不是 Aurora 造成的。）

⟹ **「一打开就卡得离谱」的主因是游戏自己停在登录页持续空转**
   （6.5 小时、64 线程、无用户输入、未进世界），不是 Aurora 的开销。
   本轮的 A/B 对照把这一点量化到了 ±3% 的误差带内。

### 6.14.4 本轮据此做的两处优化（仍然值得，但量级明确）

即便主因不在 Aurora，下面两处仍是**真实的空转**，已修：

**（1）`runNetworkLocateStep()` 的 `no_data` 分支缺「先比后写」守卫**

该函数由 10Hz 定时器驱动。同一函数上方的 `game_not_running` 分支
**早已有**守卫（并附注释「每秒 10 次强制 SwiftUI 重算布局 + WindowServer
重合成，纯属白烧 CPU」），但 `no_data` 这条漏了 —— 而游戏没开时
走的正是这条无守卫路径，每 100ms 无条件投递主线程一次。

修法：`if networkLocateMode != "no_data" { DispatchQueue.main.async { … } }`
（与上方同构，语义等价，score 恒为 0）。

**（2）`[LOCATE] 定位中断` 日志降频（10Hz → 0.5Hz）**

`dlog` 内部是 `FileHandle(forWritingTo:)` + write + `print` ——
**每次都打开/写入/关闭文件**。原实现无条件调用 = 每秒 10 次磁盘 I/O。
现改为「2 秒最多一行」（新增 `lastLocateDiagLog`，标 `@ObservationIgnored`，
与 `lastTickLog` / `lastUpscaleLiveLog` 同一约定）。**打印内容逐字不变。**

**（3）`CoordinateCapture.supervisorLoop()` 空闲指数退避**

原实现每轮探测无果后固定睡 2 秒就重来；而**一轮探测本身就要
2.5s（首选网卡）+ 0.5s × 其余网卡**，本机有多张网卡 ⟹ 游戏没开时
该线程几乎从不休息，每轮都要对每张网卡 `pcap_open_live` + 挂过滤器 +
轮询 + `pcap_close`。

修法：「连续无果」计数 `probeFailStreak`，间隔按 2 的幂放大
（2→4→8→…→封顶 30s），**一旦某轮命中立刻复位回 2s**。
最坏发现延迟 30s，而游戏从启动到进世界至少几十秒 —— 可接受；
进世界后行为与原实现逐字一致。

### 6.14.5 诚实标注：这三处修完 CPU 没有可测下降

修复后复测：**18.0% → 18.0%（无可测变化）**。

原因已在 6.14.3 说清：Aurora 的 12~18% 里，主要部分是
**常驻组件的固有开销**（Metal/CoreML/音频/抓包线程的常驻），
而不是可以靠「少投递几次主线程」消掉的部分。这三处修复减少的是
**无效工作**（白烧的磁盘 I/O、无意义的主线程投递、空转的网卡探测），
在 CPU 数字上体现不出来，但方向正确且无副作用 —— 保留。

**不夸大：本轮没有把 Aurora 的 CPU 显著降下来，因为 Aurora 本来就不是瓶颈。**

## 六点十五、游戏的「历史平均 CPU」—— 卡顿归因的最后一块拼图

### 6.15.1 决定性数据

`ps -o etime` 与 `ps -o time` 一起读，可以得到**进程整个生命周期的平均 CPU**，
这是比任何瞬时采样都稳的指标（不受采样相位影响）：

| 指标 | 值 |
|---|---|
| 游戏运行时长（`etime`） | **06:30:18** |
| 游戏累计 CPU 时间（`time`） | **370:02 → 370:14**（分钟:秒） |
| ⟹ **生命周期平均占用** | **≈ 95% 单核** |
| 当前瞬时占用 | 79 ~ 81% |
| 线程数 | 64 |
| RSS | 552 MB |
| 窗口 | `Mio Island` 1470×750 @(0,0)，**可见** |

**96 分钟的差值（390 分钟墙钟 vs 370 分钟 CPU）几乎全是启动加载。**
换句话说：**这台机器上，游戏从启动那一刻起就在满负荷烧一个核，
持续 6.5 小时，期间没有任何用户输入、没有进世界、停在登录页。**

### 6.15.2 三者的量级对比（同一时刻）

| 进程 | 占用 | 对「卡顿」的贡献 |
|---|---|---|
| 游戏本体（异环） | **75~81%** | **主因** |
| WindowServer | 41.4%（无 Aurora）/ 44.7%（有 Aurora） | 系统合成器，其中 **3.2% 归 Aurora** |
| AuroraDriveUI | **12~18%** | **次要**，且如上所述其中大部分是常驻组件固有开销 |

**游戏 : Aurora ≈ 5 ~ 6 : 1。**

### 6.15.3 归因结论（诚实版）

用户描述「一打开（自动驾驶）就卡得离谱」。实测不支持「Aurora 是主因」：

1. **Aurora 开关对游戏自身的 CPU 无影响**（ABBA：开 74.8~75.6%，
   关 80.5~81.2% —— 都在游戏自身的波动带内，且关的时候反而更高）。
2. **Aurora 对 WindowServer 的增量只有 +3.2%**（三组样本离散度 0.5%，
   这个 +3.2% 是可信的真实增量，但相对游戏的 75~81% 可忽略）。
3. **游戏自己就占掉约 0.95 个核**，从启动起持续 6.5 小时。

**「卡」的主体是游戏本体在登录页的持续满载。** Aurora 的开销
（12~18%，其中主窗口 + 0.5s 刷新的 GameHUD 悬浮窗贡献了那 3.2%）
是叠加在这个已经饱和的基础上的**边际负担** —— 在游戏已经把
一个核吃满的机器上，任何额外 15% 都会被用户明显感知到。

### 6.15.4 因此本轮的优化方向仍然正确（降边际负担）

虽然动不了游戏，但把 Aurora 自身的无效工作削掉，等于**降低边际负担**：

| # | 修复 | 性质 |
|---|---|---|
| ① | `@State` 默认值每帧重建整套引擎（349 次 → 1 次） | **真 bug，数量级** |
| ② | `MapDatabase` 7.2 MB JSON 在 `body` 求值路径里同步读 | **真 bug** |
| ③ | `locatorX/Y` 坐标系混用（864 米偏差） | **真 bug，功能** |
| ④ | `regionLabel` 每帧遍历 5677 标记 | **真 bug** |
| ⑤ | `upscaleLive`/`upscaleEngineError` 每帧赋值零读取方 | 无效工作 |
| ⑥ | `lastDecided` 每帧赋值（值长期不变） | 无效工作 |
| ⑦ | `no_data` 分支 10Hz 无条件主线程投递 | 无效工作 |
| ⑧ | `[LOCATE]` 日志 10Hz 文件 I/O | 无效工作 |
| ⑨ | 抓包探测循环空闲不退避 | 无效工作 |

①②③④ 是数量级/功能性缺陷（已量化验证）；
⑤~⑨ 是无效工作消除（CPU 数字上不可测，但方向正确、无副作用）。

### 6.16.2 真 bug：`lastPacketWall` 的初值让诊断日志自相矛盾

**症状**（修复前反复出现的日志行）：

    [LOCATE] 定位中断 —— 累计包=0 有流量=true 有样本=false 样本年龄=从未有过s …

`累计包=0` 与 `有流量=true` **同时成立** —— 两个字段互相打架。

**根因**（`CoordinateCapture.swift`）：

    // 修复前
    private var lastPacketWall = Date().timeIntervalSince1970   // ← 对象构造时刻

    func hasRecentTraffic(window: Double = trafficFreshWindow) -> Bool {
        let now = Date().timeIntervalSince1970
        return (now - lastPacketWall) <= window      // 构造后 20 秒内恒为 true
    }

对象构造时把 `lastPacketWall` 设成「现在」，于是**抓包启动后的头 20 秒
（= `trafficFreshWindow`）内 `hasRecentTraffic` 恒返回 true，哪怕一个包都没收到**。

**危害**：这条日志是本项目定位问题的主要线索，而它把排查方向
**误导**到「网卡选错 / 权限不足」，真相却是「根本还没收到任何包」。
本项目已在定位问题上消耗多轮，这条假线索是原因之一。

**修法**：

    private var lastPacketWall: Double = 0        // 0 = 「从未收到过包」哨兵

    func hasRecentTraffic(window: Double = trafficFreshWindow) -> Bool {
        guard lastPacketWall > 0 else { return false }   // 显式守卫
        let now = Date().timeIntervalSince1970
        return (now - lastPacketWall) <= window
    }

**安全性论证**（这是关键，因为 `lastPacketWall` 还有第二个读取方）：

`listenLocked` 里用 `lastPacketWall` 做失流判定：

    let last = lastPacketWall
    if Date().timeIntervalSince1970 - last >= Self.streamLostWindow { return }

若初值改 0 而该值又从未被设置，这里会**立即返回**（误判失流）。
**但这个路径不可能在未收到包时到达** —— 已逐行核实调用链：

    supervisorLoop
      └─ probe(interface:window:)          ← 内部 while 循环调 pcap_next_ex
           └─ result == 1 → got = true
                          → processPacket(...)   ← 在这里设置 lastPacketWall
           └─ return (handle, got)
      └─ if got { locked = (handle, name); break }
      └─ guard let locked else { … continue }    ← got=false 在这里就 continue 了
      └─ listenLocked(handle:…)                  ← 只有 got=true 才到这

⟹ **进入 `listenLocked` 时 `lastPacketWall` 必然已被 `processPacket` 设置过（> 0）。**
   初值改 0 对失流判定**零影响**。

**可观察变化（唯一）**：程序启动后的头 20 秒内若无包，现在如实报
`有流量=false`，而不再误报 `true`。这正是我们要的。

## 六点十七、本轮实测到的两个确凿量化改善

前面几轮修了不少东西，但多数落在「CPU 数字上看不出来」的类别里。
本轮**有两项拿到了可测量的证据**，如实记录如下。

### 6.17.1 改善一：抓包探测频率降低约 4 倍（已实测）

见 6.16.1 的完整时间线。摘要：

    退避前（推算）：每轮 = 2s 退避 + 约 6.5s 探测 ≈ 8.5 秒一轮
    退避后（实测）：每轮 = 30s 退避 + 约 6.5s 探测 ≈ 37 秒一轮

**降幅约 4 倍。** 证据是 `~/Library/Logs/aurora_pcap.log` 里连续 4 轮
稳定在 36~37 秒的间隔（22:48:42 / 22:49:19 / 22:49:55 / 22:50:32）。

### 6.17.2 改善二：日志写入量从 3.0 行/秒 降到 0 行/秒（已实测）

**测量方法**：同一二进制、同一启动参数（`--auto-login`，游戏停在登录页、
无 30031 流量 —— 即「空闲」这一最坏情形），统计 `~/Library/Logs/aurora_debug.log`
在固定窗口内的行数增长。

| | 修复前 | 修复后 |
|---|---|---|
| 观察窗口 | 40 秒（启动期） | 60 秒 |
| 日志行数 | **121 行** | **5 行**（全部是启动期的一次性行） |
| 增长速率 | **约 3.0 行/秒** | **0 行/秒** |

**60 秒窗口内零增长**，且同时确认进程健康存活（14 线程、CPU 时间正常累加
`0:58.01 → 0:59.76`），排除「进程卡死所以没日志」这一解释。

**为什么这重要**：`dlog` 的每次调用都是 `FileHandle(forWritingTo:)` +
write + `print` —— 即**一次完整的文件打开/写入/关闭**。
3.0 行/秒 = 每秒 3 次文件 I/O，在空闲状态下纯属白烧；
且日志文件会被无意义地撑大（修复前 40 秒 121 行，长时间运行会持续增长）。

**这一项是本轮唯一「修完就归零」的改善** —— 因为它修的是**纯浪费**
（状态恒定时无条件打印），而不是任何必要工作。

### 6.17.3 归因：为什么大多数修复在 CPU 数字上看不出来

诚实结论（承接 6.14 的 A/B 对照）：

1. **Aurora 的 12~18% CPU 主要是常驻组件固有开销** ——
   Metal/CoreML 运行库、音频子系统（`coreaudiod` 侧）、抓包线程常驻、
   WindowServer 侧那 3.2%。这些不是「少投递几次主线程」能消掉的。
2. **真正的瓶颈是游戏本体**（生命周期平均 95% 单核，见 6.15），
   而它不受 Aurora 控制。
3. 因此本轮的 7 处修复里，只有**消除纯浪费**的那两处（探测退避、
   日志限流）能给出可见数字；其余（先比后写、`@ObservationIgnored`）
   消除的是**每次调用都很小、但原本每帧都发生**的无效通知 ——
   方向正确、无副作用，但在已经饱和的机器上测不出差值。

**这个分类比「修了很多」更有价值**：它说明后续若还要降 Aurora 开销，
该往「常驻组件的启动成本」而非「tick 路径的每次开销」上找。

## 六点十八、部署校验的正确方法（哈希比对会误报）

### 6.18.1 现象

同步 `.app` 内二进制后，三个副本的 SHA-256 不一致：

    .build/scratch/release/AuroraDrive                  9226040 bytes
    ./AuroraDriveUI                            （与 .build 同哈希）
    ./AuroraDriveUI.app/Contents/MacOS/AuroraDriveUI   9190560 bytes  ← 差 35480 字节

### 6.18.2 原因（不是 bug）

`codesign --force --deep --sign -` 会把**已有的（旧）签名数据剥离**
再写入新签名 —— 这个过程的产物与输入**必然不同字节**。
哈希不同只说明「经过了一次重签」，**不代表内容陈旧**。

### 6.18.3 正确的校验方法：行为验证

**不要用哈希比对 .app 内二进制。** 改用「新版本独有的可观察行为」验证：

本轮实测（把 `.app` 内二进制单独跑 50 秒，检查新版独有的退避日志）：

    「空闲退避」出现次数: 3
      22:53:27  空闲退避：连续 1 轮无流量 → 下次探测间隔 2s
      22:53:36  空闲退避：连续 2 轮无流量 → 下次探测间隔 4s
      22:53:47  空闲退避：连续 3 轮无流量 → 下次探测间隔 8s

**该日志字符串只存在于本轮新增的代码里** ⟹ `.app` 内二进制确为最新版本。

同时 `codesign --verify --deep --strict AuroraDriveUI.app` 通过 ⟹ 签名有效。

### 6.18.4 写进操作手册的结论

| 副本 | 校验方式 |
|---|---|
| `.build/scratch/release/AuroraDrive` ↔ `./AuroraDriveUI` | **SHA-256 相等**（纯 cp，无签名介入） |
| `./AuroraDriveUI.app/Contents/MacOS/AuroraDriveUI` | **行为验证**（跑一个只有新版才有的日志/自检） |

## 六点十九、【已被 6.21 更正】关于游戏窗口 onscreen 标志的观察

### 6.19.1 关键测量：游戏窗口 onscreen=false

用 `CGWindowListCopyWindowInfo(.optionAll)` 枚举游戏进程（pid=81772）的全部窗口：

    pid=81772 owner=异环 title=(无标题) layer=0  onscreen=false  bounds={X:0, Y:33, W:1470, H:923}   ← 主窗口
    pid=81772 owner=异环 title=(无标题) layer=0  onscreen=false  bounds={X:0, Y:0,  W:1470, H:33}
    pid=81772 owner=异环 title=(无标题) layer=26 onscreen=false  bounds={X:0, Y:0,  W:1470, H:33}
    pid=81772 owner=异环 title=(无标题) layer=0  onscreen=false  bounds={X:-1200, Y:-244, W:1200, H:30}  ← 屏外
    …

**全部 `onscreen=false`** —— 包括那个 1470×923 的主窗口。

对照：`kCGWindowListOptionOnScreenOnly` 的结果里**根本没有游戏**，
可见的窗口是 `Mio Island`（1470×750 @(0,0)）、AuroraDriveUI、控制中心。

### 6.19.2 但它在满速渲染

同一个进程的 CPU 数据（见 6.15）：

    累计 CPU 370 分钟 / 墙钟 6 小时 30 分  ⟹  生命周期平均 ≈ 95% 单核
    当前瞬时 75~81%
    线程数 64

**窗口不可见 + 满载渲染 = 典型的「窗口被遮挡/最小化但仍以全速跑渲染循环」。**
通常 macOS 会对完全被遮挡的窗口降频（occlusion-driven throttling），
但**该优化对全屏/独占模式的游戏常不生效** —— 游戏自己控制了
渲染节奏，不理会系统的遮挡通知。

### 6.19.3 另一条线索：`Mio Island` 的窗口覆盖全屏

    /Applications/Mio Island.app   (com.codeisland.app, v3.1.3)
    pid=960, PPID=1, 已运行 3 天 20 小时, 占 8.3% CPU
    窗口: L27, 1470×750 @(0,0)   ← **正好铺满整个游戏区域，且可见**

`Mio Island` 是一个第三方「灵动岛/刘海扩展」类常驻应用。
它的窗口与游戏主窗口**位置尺寸完全重合**（都是 @(0,0) 1470×…），
层级 L27 高于游戏的 L0。

**这解释了「游戏窗口 onscreen=false」**：游戏主窗口被这个更高层级的
全屏窗口盖住，于是被 WindowServer 判为不在屏幕上。

### 6.19.4 ⚠️ 本节因果链已被推翻 —— 见 6.21

**原推断（错误，保留以示过程）**：

    ① 游戏启动 → 加载 → 停在登录页
    ② Mio Island 的全屏窗口（L27）覆盖其上
    ③ 游戏主窗口被判 onscreen=false（被遮挡）
    ④ 游戏不理会遮挡节流，继续满速渲染
    ⑤ 结果：一个「看不见的窗口」持续烧掉 ≈95% 单核

**为什么错**：`onscreen=false` 是**所有后台应用窗口的常态**
（DSH Desktop / ego lite / Safari / Parallels Desktop 全是 false），
不是「被遮挡」的特例。6.21 的实验进一步证明：把游戏切到**前台**
（`onscreen` 变 true）后，它的 CPU **反而下降 13.9%**（79.1% → 65.2%），
与「遮挡导致浪费」方向相反。

⟹ **正确结论见 6.21.3：卡顿主因是游戏自身的渲染开销，与遮挡无关。**

### 6.19.5 可操作建议（已按 6.21 更正）

1. **退出游戏**（若不再玩）：直接消除那 ≈94% 单核。这是收益最大的一步。
2. **`Mio Island` 可关但不急**：它占 7~9% CPU，是**独立**的额外负担；
   但 **它不是「游戏变卡」的原因**（6.21.2 已证）。
3. **让游戏真正进入世界**：登录页的渲染循环没有产出，进世界后
   这 95% 至少是在做有用的事。
4. **Aurora 侧已无更多空间**：A/B 对照确认 Aurora 对 WindowServer
   的增量只有 +3.2%（6.14），自身 12~18% 主要是常驻组件固有开销（6.17.3）。

**诚实说明**：本条是**归因**，不是修复 —— 游戏和 Mio Island 都不由
本项目控制。但它把「卡」的来源定位到了一个具体的、可操作的对象上，
比继续在 Aurora 内部找百分比更有价值。

## 六点二十、屏幕上一直挂着一个等待你点击的授权弹窗

### 6.20.1 发现

用 `CGWindowListCopyWindowInfo(.optionOnScreenOnly)` 枚举**仅在屏**窗口
（过滤掉所有离屏窗口后，只剩 45 个），其中这一条是决定性的：

    pid=975  layer=0  onscreen=true  owner=universalAccessAuthWarn
    bounds={X:504, Y:219, Width:461, Height:181}

进程路径：

    /System/Library/PrivateFrameworks/UniversalAccess.framework/Versions/A/
      Resources/universalAccessAuthWarn.app/Contents/MacOS/universalAccessAuthWarn

**`universalAccessAuthWarn` 是 macOS 专门用来弹「辅助功能授权警告」的系统组件** ——
即那个「"XXX" 想要控制这台电脑」的对话框。

### 6.20.2 它意味着什么

这颗弹窗说明：**授权请求确实发出去了、系统确实认可了请求方的身份、
弹窗也确实渲染出来了并停留在屏幕上** —— 它只是在**等用户点「打开系统设置」
或「拒绝」**，在那之前它会一直挂着。

这解释了本轮反复观察到的现象：

1. 从 shell 启动时，`requestAccessibilityPermission()` 走到了、请求也发了，
   但责任方是 `io.dsh.desktop.helper`（见 6.12），弹窗内容指向的是 DSH。
2. 从 `open` 启动时，责任方是 `com.aurora.driveui` 自己（6.12.1），
   这才是应该被授权的那一条。

### 6.20.3 与本轮 `checkPermission()` → `requestAccessibilityPermission()` 修复的闭环

前几轮把这处从「只查询、从不请求」改成「发出请求 + 登记进列表」。
当时的推断是「这样用户才能在系统设置里找到条目」。

**本轮拿到了这条推断的直接实证**：弹窗真的出现了（`universalAccessAuthWarn`

## 六点二十一、【更正 6.19】「游戏被 Mio Island 遮挡」是误读

### 6.21.1 我上一轮错在哪

6.19 节我根据「游戏主窗口 `onscreen=false`」推断

**反证**（同一份窗口枚举，看非游戏进程）：

|---|---|---|

| B：**切到前台** | **65.2%** | **true** |
| **B − A** | **−13.9%** | |

**切到前台后游戏 CPU 降低了 13.9%** —— 与「遮挡导致浪费」的假设**方向相反**。
（合理解释：窗口被遮挡时游戏仍在跑完整渲染循环但拿不到 vsync 节流；
前台时反而受显示器刷新率约束。）

### 6.21.3 结论修正：卡顿归因收敛到「游戏自身」

删去「Mio Island 遮挡」这个错误中间环节后，6.19 的因果链简化为：

    ① 游戏停在登录页，持续跑渲染循环
    ② 生命周期平均 ≈ 94% 单核（6.15 实测：381.8 分钟 / 6.76 小时）
    ③ 无论前台（65%）、后台（79%），都在大量消耗 CPU
    ④ Aurora 侧对 WindowServer 的增量仅 +3.2%（6.14，3 轮 ABBA）

⟹ **「卡」的主因就是游戏自己的渲染开销**，与遮挡无关、与 Mio Island 无关。
   `Mio Island` 自身占 7~9% CPU 是**独立**的额外负担（它已运行 3 天 20 小时），
   可以关，但它不是「游戏变卡」的原因。

### 6.21.4 保留下来的有效结论

6.19 里唯一仍然成立的是**实测数据本身**（`onscreen=false` 是事实），
被推翻的是**对它的解释**。已按此更正 6.19 的标题与结论段。

教训记录：**「窗口标志异常」这类观察，必须先确认它在正常进程上的取值**，
再判断是否异常 —— 否则会把框架常态误读成 bug。
本轮靠「枚举全部窗口做对照」发现了这一点。

## 六点二十三、突破：无权限下跑通完整驾驶链路（观测模式）

### 6.23.1 找到的接缝：`startDriving()` 的引擎分支在权限守卫之前

**位置**：`AuroraDriveApp.swift` `DriveState.startDriving()`

    func startDriving() {
        // ── 引擎模式：命令转发给后台引擎 ──
        if EngineClient.shared.isActive {
            EngineClient.shared.sendCommand("start")
            isDriving = true            // ← 直接置位
            return                      // ← 在权限守卫之前就 return 了
        }
        // ↓ 权限守卫（只有本地模式才会走到）
        guard controlEngine.requestAccessibilityPermission() else { … return }
        isDriving = true
        …
    }

⟹ **引擎模式下 `isDriving` 可以被置为 true，绕过权限守卫。**

### 6.23.2 但实测发现引擎侧被同一道守卫挡回

本轮实测（引擎 + UI 联调）：

    UI 侧：  [UI-CLIENT] 共享内存已映射 72 MB
             [UI-CLIENT] ✅ 引擎模式已激活（socket + 共享内存就绪）
             [引擎模式] 已发送 start 命令给后台引擎
    引擎侧： [ENGINE] 收到命令: start
             [ENGINE] startDriving → isDriving=false      ← 被挡回
             [ENGINE] 统计: … driving=false …

**原因**：`handleCommand("start")` 调的是**引擎进程内**的
`EngineGlobals.state?.startDriving()` —— 那是**另一个 DriveState 实例**，
它自己也有同一道权限守卫。命令送达了，但引擎侧同样 `return` 了。

### 6.23.3 修复：新增观测模式旁路 `AURORA_OBSERVE_ONLY=1`

**语义**（这是关键的安全设计）：

| 项目 | 行为 |
|---|---|
| `controlDisabled` | **被强制置为 true** |
| 按键注入 | **全路径关闭** |
| 截屏 / YOLO / YOLOPX / E2E 推理 | 照常 |
| 定位 / 小地图 / 检测框渲染 / 日志 | 照常 |
| **默认** | **不开启**（不设变量则行为与修复前逐字一致） |

`controlDisabled` 之所以能作为安全保证，是因为它在 `tick()` 里同时 gate 住
**全部两条注入路径**（已逐行核实调用点）：

    · :4713  主注入      if expertMode || controlDisabled { releaseAll() } else { applyCommand(...) }
    · :4557  限速刹车    let mayInjectKeys = isDriving && !expertMode && !controlDisabled

**纵深防御（额外核实）**：即使这两个 gate 都失效，
`ControlEngine.hold()`（`ControlEngine.swift:176`）**自身也带权限 gate**：

    func hold(_ action: Action) {
        guard hasAccessibilityPermission else { _ = checkPermission(); return }
        …
    }

无权限时它提前 return ⟹ `heldKeys` 永远为空 ⟹ `release()` 全部 no-op
（`:191` `guard heldKeys.contains(keyCode) else { return }`）。
即**三层独立保护**，无权限时不可能注入任何按键。

另核实：第二条注入通道 `holdGameKey` / `releaseGameKey`（`:356`/`:364`）
**全仓库零调用方**，不构成风险。

**为什么用环境变量而非 UI 开关**：用户红线「不能加任何东西」。
环境变量不改变任何既有 UI 与行为，与既有 9 处诊断开关
（`AURORA_UI_LOCAL` / `AURORA_ENGINE_DIAG_SKIP_TCC` /
`AURORA_DISABLE_OPTICAL_FLOW` / `AURORA_SKIP_MODEL_LOAD` …）同一约定。

## 六点二十五、【重大修复】转向指示的参考系混用（错误率 58.3% → 1.0%）

### 6.25.1 这很可能就是用户说的「地图定位永远是偏差错误的」

用户原话：「**小地图无法定位**…**地图定位永远是偏差错误的**」。

前几轮修的是**位置**（`locatorX/Y` 坐标系混用导致 864 米偏差）。
但「永远是偏差错误」还有第二层含义 —— **位置对了，方向不对**。
本轮找到了它。

### 6.25.2 根因：两个角度用不同参考系，却直接相减

**位置**：`MissionConsole.swift` `NavGuidance.derive(from:)`

    let bearing = atan2(dy, dx) * 180 / .pi          // ← 数学极角
    var rel = bearing - s.locatorHeading             // ← 罗盘角，参考系不同！
    … else if rel > 0 { action = "米后右转" }

两个量的参考系：

| 量 | 来源 | 0° 指向 | 旋向 | 范围 |
|---|---|---|---|---|
| `locatorHeading` | `toPose()` 的 `atan2(east, north)`，负值 +360 | **正北** | **顺时针**（罗盘） | [0, 360) |
| `bearing` | `atan2(dy, dx)` | **正东** | **逆时针**（数学） | (−180, 180] |

**原点差 90°、旋向相反** ⟹ `bearing - locatorHeading` 毫无几何意义。

### 6.25.3 量化影响：扫描 5184 个组合，错误 58.3%

对「目标罗盘方位 × 自车罗盘朝向」各以 5° 为步长做全组合扫描：

**修复前**：

    组合数: 5184
    转向指示错误: 3021  (58.3%)

典型反例（这些是**必然发生**的错，不是边界抖动）：

    目标在正北、车头朝正北          → 应「直行」，原实现显示「右转」
    目标在正北、车头朝北偏东 20°    → 应「左转」，原实现显示「右转」
    目标在正北、车头朝北偏东 35°    → 应「左转」，原实现显示「右转」

### 6.25.4 修法

把目标方位统一换算成**罗盘角**再相减。走既有的、已实测正确的地图投影
（`worldToMapPixelX/Y`），而不是在世界系手算：

    let egoPx = DriveState.worldToMapPixelX(s.locatorX, s.locatorY)
    let egoPy = DriveState.worldToMapPixelY(s.locatorX, s.locatorY)
    let tgtPx = DriveState.worldToMapPixelX(Double(t.x), Double(t.y))
    let tgtPy = DriveState.worldToMapPixelY(Double(t.x), Double(t.y))
    // 罗盘方位角 = atan2(东 = +Δx, 北 = −Δy)
    let bearingCompass = atan2(tgtPx - egoPx, -(tgtPy - egoPy)) * 180 / .pi
    var rel = bearingCompass - s.locatorHeading

`−ΔmapY` 的依据（已核对）：

    · 地图像素 y 轴向下（屏幕系）
    · 地图北朝上（`kNorth ≈ (0, −0.9999, 0)` ⟹ 世界 −Y 为北）
    · `worldToMapPixelY = kCalibA·wy + kCalibTY`（wy 增大 → 像素 y 增大 → 屏幕向下）
    ⟹ 像素 −Δy 即「向北的分量」

**为什么不在世界系手算**：世界系里「北」是 `kNorth = (−0.0138, −0.9999, 0)`
这个**非轴向**向量（含 0.79° 倾角），要正确投影必须用它；而 `kNorth`/`kEast`
是 `CoordinateCapture.swift` 的 file-private 常量，从 `MissionConsole.swift` 拿不到。
走地图像素系既避开可见性问题，**又顺带把标定矩阵里的微小倾角 `kCalibB`
一并算对** —— 原实现把这个倾斜完全忽略了。

### 6.25.5 修复后验证

**全组合扫描**：

    组合数: 5184
    修复后转向指示错误: 52  (1.0%)
    ⟹ 相比修复前的 3021 (58.3%)，**改善 98.3%**

（剩余 1% 是 20° 判定阈值边界的舍入，非逻辑错误。）

**真实夹具数据复核**（自车 `(-77000, 31865)` → 目标 `(-76500, 32200)`）：

    世界位移：dx=+500（东） dy=+335
    地图像素：Δx=+8.2  Δy=+5.5
    目标罗盘方位 = 123.8°（东南偏东）
    ⟹ 与像素位移方向完全自洽（+Δx 为东、+Δy 为南）

**同时核对了另一个读取方**：地图上自车箭头的朝向
（`:2294` `.rotationEffect(.degrees(state.locatorHeading))`）——
`.offset(y: -13)` 使箭头默认朝上（屏幕北），SwiftUI 的 `rotationEffect`
顺时针为正 ⟹ **罗盘角与它天然匹配，这一处原本就是对的**，未改动。

### 6.25.6 这一条的意义

用户的三项诉求里，「小地图偏差」现在有两层修复：

## 六点二十六、【重大修复】导航线目标点缺一次坐标变换

### 6.26.1 发现途径：截图视觉复核

6.25 修完转向指示后重新生成 `--mc-map` 离屏截图做视觉复核，
在图上看到**一条从自车斜穿整个屏幕到左下角的长线**：

    自车（画面中央，冰蓝色圆点）──────────────→ 左下角

而夹具数据里目标就在自车**右下方 6.9 像素**处，**本不该出现可见的线**。

### 6.26.2 根因：目标点与世界坐标/像素混算（对称遗漏）

**位置**：`MissionConsole.swift` `LargeMapCanvas` 的导航路径绘制

    let ePx = DriveState.worldToMapPixelX(state.locatorX, state.locatorY)  // ← 自车已转换
    let ePy = DriveState.worldToMapPixelY(state.locatorX, state.locatorY)
    let ex = min(0.97, max(0.03, (ePx - cx) / spanPx + 0.5))
    let ey = min(0.97, max(0.03, (ePy - cy) / spanPx + 0.5))
    let tx = min(0.97, max(0.03, (t.x - cx) / spanPx + 0.5))   // ← t.x 是世界坐标！
    let ty = min(0.97, max(0.03, (t.y - cy) / spanPx + 0.5))

`locatorTarget` 存的是**世界坐标**（UE5 厘米）—— 这一点由 `:1398` 的
`(t.x - locatorX) / 100.0` 定义（两者相减再除 100 得米，必须同坐标系）。
而 `cx`/`cy` 是**地图像素**。

**世界坐标 − 地图像素 = 量纲不符**：

    夹具：t.x = −76500（世界）  cx = 5264.1（像素）
    (t.x − cx) / spanPx + 0.5 = (−76500 − 5264.1) / 1967 + 0.5 = −41.06
    被 max(0.03, …) 夹到 → 0.030        ← 目标被**钉死在画面左边缘 3%**

y 同理被夹到 0.970（下边缘）⟹ **目标永远画在左下角**，
导航线因此斜穿全屏。**与地图实际内容完全无关，是纯粹的坐标系错误。**

### 6.26.3 为什么之前没发现 —— 典型的对称遗漏

前几轮修 `locatorX/Y` 坐标系混用时，处理的是**自车**一侧
（`ePx/ePy` 一直是正确经过 `worldToMapPixel` 转换的），
**漏掉了与它配对的「目标」一侧**。

同一个文件里 `:2265` 的目标距离计算用的是 `s.locatorX` 与 `t.x`
—— 两者**同为世界坐标**因而正确；唯独本处把世界坐标和像素混算。

### 6.26.4 修法（与自车完全对称）

    let tPx = DriveState.worldToMapPixelX(Double(t.x), Double(t.y))
    let tPy = DriveState.worldToMapPixelY(Double(t.x), Double(t.y))
    let tx = min(0.97, max(0.03, (tPx - cx) / spanPx + 0.5))
    let ty = min(0.97, max(0.03, (tPy - cy) / spanPx + 0.5))

### 6.26.5 验证（数学 + 视觉双重）

**数学**：

| | 目标屏幕位置 | 说明 |
|---|---|---|
| 修复前 | `(0.030, 0.970)` | 被钉死在**左下角**（原始值 −41.06 被夹取） |
| 修复后 | `(0.504, 0.503)` | 正确落在画面中央偏右，自车 6.9px 外 |

**视觉**（`--mc-map` 离屏截图，`/tmp/aurora_mc_map_online.png`）：

    · 修复前：一条冰蓝色长线从自车斜穿全屏到左下角
    · 修复后：**该线消失** —— 因为目标本就距自车 6.9 像素，
      两点几乎重合，符合夹具数据的真实几何

### 6.26.6 与 6.25 的关系：同一类错误的两个表现

| # | 位置 | 错误 | 后果 |
|---|---|---|---|
| 1 | `NavGuidance.derive` 转向指示 | 罗盘角 − 数学极角 | 转向指示 58.3% 错误 |
| 2 | `LargeMapCanvas` 导航线 | 世界坐标 − 地图像素 | 导航线目标点钉死在屏幕角落 |

**两者都是「坐标系混用」**，且都在小地图这条链路上。
用户说的「小地图无法定位 / 地图定位永远是偏差错误的」，
实际上是**三个独立 bug 的叠加**：

    ① locatorX/Y 写像素读世界坐标  → 位置偏 864 米（前几轮已修）
    ② 转向指示参考系混用            → 方向 58.3% 错误（6.25 修）
    ③ 导航线目标点缺变换            → 目标被钉在屏幕角落（本轮修）

## 六点二十八、【根因修复】屏幕录制权限从未被申请过（对称遗漏）

### 6.28.1 「权限勾不上」的真正原因

长期现象：`--tcc-selftest` 恒为 `ax=false screen=false`，
且**从来没有出现过屏幕录制的授权弹窗**，用户在系统设置里也找不到本 App。

全库扫描找到了原因 —— **只有查询，没有申请**：

| API | 出现位置 | 作用 |
|---|---|---|
| `CGPreflightScreenCaptureAccess()` | `EngineMain.swift:632`、`AuroraDriveApp.swift:158` | **纯查询**，按设计不弹窗、不注册 |
| `CGRequestScreenCaptureAccess()` | **全项目 0 处** | 才是弹出授权框 + 把 App 登记进 TCC 列表的那个 |
| 打开「屏幕录制」设置面板 | **全项目 0 处** | 从未实现 |

`CaptureEngine.swift:161` 的注释寄望于
「`try await SCShareableContent.current` 会触发权限弹窗」，
但那只是**枚举失败时的被动行为**，**不负责把 App 注册进 TCC 列表**。
未注册的 App 在「屏幕录制」列表里**不可见** —— 用户想手动勾选都无从下手。

**这与辅助功能是同一类遗漏的对称位置**：辅助功能那一路已在上一个阶段修好
（`checkPermission()` → `requestAccessibilityPermission()`，屏幕上出现的
`universalAccessAuthWarn` 弹窗即其证据），**当时只补了一半。**

### 6.28.2 修复（两处）

**① 新增申请与引导 API**（`ControlEngine.swift`，紧接辅助功能那组之后，
保持同一职责相邻、便于对照维护）：

    @discardableResult
    func requestScreenRecordingPermission() -> Bool {
        let granted = CGRequestScreenCaptureAccess()
        if !granted { openScreenRecordingSettings() }
        return granted
    }
    func openScreenRecordingSettings() {
        // x-apple.systempreferences:com.apple.preference.security?Privacy_ScreenCapture
    }

**② 在权限被拒的回调里真正调用它**（`AuroraDriveApp.swift` 的
`captureEngine.onStatusChange` `.permissionDenied` 分支）：
原来该分支**只置一个布尔标志位**，没有任何申请动作。现在补上申请调用。

**③ 顺带补上缺失的诊断**（同一分支）：
`.stopped, .error` 分支此前**完全不打印任何日志** ——
这正是 `img=false` / `native=0x0` 长期无人能解释的原因
（实测 `[capture]` 前缀在日志里 **0 次**输出）。现在如实打印状态。

### 6.28.3 修复生效的直接证据

补上诊断后，失败原因**第一次在日志里显形**：

    [CAPTURE] ❌ 画面流失败: 获取屏幕内容失败（可能未授权）:
              用户拒绝了应用程序、窗口、显示的访问

同时系统设置被自动打开（`openScreenRecordingSettings()` 生效，
实测 `System Settings` pid 67871 被拉起）。

**TCC 系统日志证明申请请求确实发出了**：

    AUTHREQ_CTX: msgID=… function=<private>, service=kTCCServiceScreenCapture, preflight=yes

（这条 `kTCCServiceScreenCapture` 请求在修复前**从未出现过**。）

### 6.28.4 关键约束：必须用 `open` 启动

对照两种启动方式的 TCC 日志：

**`open` 启动（TCC 可识别）**：

    -[TCCDAccessIdentity staticCode]: static code for: identifier com.aurora.driveui, type: 0: 0x8c6de8f0
    AUTHREQ_ATTRIBUTION: attribution={accessing={TCCDProcess: identifier=com.aurora.driveui…

## 六点二十九、【重大修复】「一打开就卡得离谱」= 权限药丸每帧扫 64 个设备节点

### 6.29.1 用 sample 抓到了真凶

对运行中的 UI 进程做 `sample`（6 秒、1ms 粒度、3725 样本），主线程调用树：

    100.0%  NSApplicationMain → _DPSNextEvent
     82.6%  __CFRunLoopDoObservers
     82.5%  ViewGraphRootValueUpdater.updateGraph
     81.6%  DynamicBody.updateValue
     81.4%  **PermissionPill.body.getter**      ← 一个小药丸占主线程 81%
     45.4%  mach_msg（空闲）

对照之下 `mach_msg`（真正的空闲）只有 45.4% —— 也就是说
**主线程超过一半的时间在重算这个「权限药丸」的 body**。

### 6.29.2 根因链条

**① 它在热路径上。** `PermissionPill`（`MissionConsole.swift:269`）位于
`TopBar`（`:95`），而 `TopBar` 读 `state` —— 于是 30Hz 的 `tick()`
每写一次 `@Observable` 属性，都让 `TopBar` 子树失效、重算 body。

**② body 里读了昂贵的派生属性。** `PermissionPill.body` 两处读
`PrivilegePill.shared.statusDetail`：
`.help(ready ? …statusDetail : "…")` 与按钮 action 里的赋值。

**③ `statusDetail` 每次都扫文件系统与进程表**：

    var statusDetail: String {
        let bpf = BPFSetupManager.isBPFAvailable()        // ← 循环 0..<64
        let pri = PrioritySetupManager.isDaemonRunning()  // ← 进程/文件检查
        …
    }

其中 `firstWritableBPFDevice()`（`BPFSetup.swift:26`）循环 `0..<64`，
每轮做 `FileManager.default.fileExists(atPath:)` + `access(2)` **两次系统调用**；
未就绪时 `lockedBPFDevices()` 还要再来一轮。

**合起来：每秒 30 次 × 最多 64 次系统调用 ≈ 2000 次/秒，全部砸在 UI 主线程上。**

### 6.29.3 修法：在属性内部加 2 秒记忆化

    private var cachedStatusDetail: (value: String, at: Date)?

    var statusDetail: String {
        if let c = cachedStatusDetail, Date().timeIntervalSince(c.at) < 2.0 {
            return c.value
        }
        let v = computeStatusDetail()
        cachedStatusDetail = (v, Date())
        return v
    }

原逻辑逐字搬进 `computeStatusDetail()` —— **缓存只改变「多久算一次」，
不改变算出来的值**。

**为什么在属性内部缓存而不是改调用点**：`statusDetail` 有多个调用方
（药丸 tooltip、密码弹窗、状态展示），在属性内部缓存能一次性覆盖全部，
比逐个改调用点更不易遗漏 —— 本类此前反复踩的正是「只补一处、
漏掉对称位置」的坑。

**为什么是 2 秒**：权限状态是**人手操作才会变**的量（用户去装 BPF/启动守护），
不需要 30Hz 精度。2 秒的陈旧度完全够用，把系统调用量从 ~2000 次/秒
降到 ~0.5 次/秒。

**配套**：新增 `invalidateStatusCache()`，在 `install(password:)` 的
**三个成功返回点**都调用 —— 保证用户装完立刻看到新状态，
而不是等最多 2 秒（那种「点了没反应」的观感正是要避免的）。

### 6.29.4 验证：主线程空闲率 45% → 70%

**修复前**：

    mach_msg（空闲）        45.4%
    PermissionPill.body     81.4%   ← 主线程被它吃满

**修复后**（同样 6 秒采样、3779 样本）：

    mach_msg（空闲）        69.6%
    PermissionPill.body     **已掉出排行榜**（占比 < 4%）

**主线程空闲率从 45.4% 提升到 69.6%** —— 这就是「一打开就卡」的直接改善。

### 6.29.5 本轮同时修掉的另一处对称遗漏

`lastDecided` 在限速刹车分支（`:4681`）是**无条件赋值**，而主路径
（`:4740`）上一轮已改成「先比后写」。原因：该分支**提前 return**，
永远走不到主路径那行 —— 又是典型的对称遗漏。本轮一并对齐。

同一处理也应用到 `switch decided` 的四个分支（`currentCommand`）：
`ControlCommand: Equatable`，四个分支原本都是无条件赋值，30Hz 下
每秒 30 次无效通知（其 UI 读取方只有 `MissionConsole.swift:504` 一处）。
现全部改为 `if currentCommand != X { currentCommand = X }`。

### 6.30.2 发现：角色站桩时坐标有**系统性匀速漂移**

对 60 个连续样本（跨度 3353 秒）做线性回归：

    X: -83802.4 → -82803.0 cm，漂移率 **-0.298 cm/s = -10.73 m/h**

**每 15 秒的 X 增量高度一致**：

    0s → 241s：稳定 -4.40 / -4.50 cm（18 个样本，仅 1 个是 -4.80）
    中间两次抓包空档后的"跳跃"：
      t=241→1638（23 分钟）：-416.40 cm
      t=1743→2149（6.8 分钟）：-121.00 cm

**关键判据**：两次跳跃量恰好等于「空档时间 ÷ 15 秒 × 4.5 cm」：

    23 分钟 / 15s = 92 个周期 × 4.5 = 414 cm  ≈ 实测 416.40 ✓
    6.8 分钟 / 15s = 27 个周期 × 4.5 = 121 cm  ≈ 实测 121.00 ✓

⟹ **漂移是游戏服务器按固定速率累加的**，与我方抓包/解码无关
（我方空档期间只是没记录，游戏照常漂）。
量级 `-0.3 cm/s`（约 10.8 m/h）符合「游戏内角色站桩时的微小滑移」，
**属游戏自身行为，非本项目 bug**。

### 6.30.3 但它的**长期累积**不可忽略

    1 分钟        漂移    18 cm  = 地图   0.30 像素
    10 分钟       漂移   180 cm  = 地图   2.95 像素
    1 小时        漂移  1080 cm  = 地图  17.7  像素
    8 小时        漂移  8640 cm  = 地图 141.6  像素   ← 视野的 54%！

小地图视野 160 米 = 262.3 像素。**8 小时会漂掉半个视野。**

（本轮曾一度误算成「8 小时才 2.6 像素」—— 那是把 `pxPerCm` 用反了。
此处以修正后的数字为准。）

**这是否构成「定位偏差」的实际来源？** 需要区分两种情形：

    · 若角色**一直在动**：每 15 秒的新坐标会覆盖漂移，漂移无影响。
    · 若角色**长时间静止**（挂机）：漂移会持续累积，8 小时后确实可见。

用户描述的「永远是偏差错误的」更符合**恒定偏移**特征，
已由 6.5 的 864 米坐标系 bug 解释；本节的漂移是**缓慢累积型**，
两者不是同一问题。但挂机场景下值得后续观察。

### 6.30.4 本节的意义

这是**第一次用真实游戏数据反向验证地图投影链路**：

    30031 抓包 → 解码 → 世界坐标 → worldToMapPixel → 地图像素 → 地图内容

四个环节全部自洽（裁出的地图内容与「城市边缘」的预期相符、
周边地标密度合理、最近地标 14.3 米属正常量级）。

## 六点三十一、【重大发现 + 自我更正】「一打开就卡」的真实机制是 WindowServer +26%

### 6.31.1 先更正两个此前测量错误

**错误一：Aurora 稳态 CPU 不是 20~31%，而是 1.2%。**

前几轮报过「Aurora 占 20~31% 单核」，那是 **`ps -o %cpu` 的
生命周期均值**被启动期（模型加载 + Metal/CoreML 初始化）拉高的结果。
用 CPU 时间增量法（`ps -o time=` 差值）测真实稳态：

    ps 生命周期均值:  0.3%     ← 无参考价值
    20 秒实测增量:    1.2% 单核 ← 真实稳态（观测模式，无帧）

**错误二：Aurora 对游戏 CPU 的影响可忽略（此前报的 −48% 是测错）。**

（此条已在 6.27 更正，此处再次确认。）

### 6.31.2 真正的问题：WindowServer 负载 +25.9 个百分点

用 ABBA 法（三组，每组 25 秒 CPU 时间增量，间隔 40 秒等启动期过去）：

**Aurora 关闭（基线）**

    基线 1    56.1%

    轮 1      78.4%
    轮 2      79.2%
    轮 3      79.8%
    中位      79.2%
    Δ vs 基线 **+25.9 个百分点**

**组内极差 <1%（78.4/79.2/79.8），高度可复现。**

WindowServer 位于**所有渲染的关键路径**上 —— 它的负载接近翻倍，
就是用户所述「一打开就卡得离谱」最合理的机制。
（相比之下 Aurora 自身只占 1.2%，游戏 CPU 也不受影响 ——
问题不在「谁抢了 CPU」，而在**WindowServer 的合成负担**。）

    ─────────────────────────
    HUD 的净代价    : **+1.2 个百分点**

**⟹ HUD 不是主因**（虽然它确实有成本，但只占增量的 5%）。

## 六点三十二、WindowServer +30% 的因子分解（关键实验）

### 6.32.1 三分组对照实验

为区分「进程存在」与「窗口可见」各自的贡献，设计三组实验
（每组 20 秒 CPU 时间增量，间隔 40 秒跨过启动期）：

    组别                                      WindowServer
    [A] Aurora 完全关闭                        51.1%
    [B] Aurora 开 · 所有窗口 orderOut（隐藏）   71.2%    Δ vs A = **+20.1%**
    [C] Aurora 开 · 窗口正常可见               81.8%    Δ vs A = **+30.7%**

**组 [B] 是怎么做到的**：用既有的 `--agent-command` 启动模式 ——
其 `ContentView.onAppear` 里有「命令模式：遍历 `NSApp.windows` 全部
`orderOut(nil)`」的分支（`AuroraDriveApp.swift:993-999`）。该模式下
**进程照常运行**（抓包/定位/推理/模型加载全在，实测进程存活），
只是没有任何窗口显示。

### 6.32.2 分解结论

    +20.1%  ← 「Aurora 进程存在」本身引起（**与窗口无关**）
    +10.6%  ← 「窗口可见」额外引起（A/B 之差）

**主因不是窗口渲染** —— 一个窗口都不显示时，增量已达总量的 2/3。

### 6.32.3 已排除的候选

| 候选 | 排除依据 |
|---|---|
| 帧率 HUD（`level=.screenSaver`，压在全屏游戏之上） | 新增 `AURORA_DISABLE_HUD=1` 对照：HUD 开 79.6% / HUD 关 78.4%，**净代价仅 +1.2%** |
| 显示器刷新率被拉高 | `CGDisplayCopyDisplayMode` 实测主屏与副屏均 **60.0 Hz**，未变 |
| 窗口数量泄漏 | 连续 4 次枚举（间隔 15s）恒为 **10 个窗口**，不增长 |
| 主窗口非不透明 | 主窗口已 `isOpaque = true`（`AuroraDriveApp.swift:2186`），走快路径 |
| `CGEventTap` | 创建于 `.cgSessionEventTap`，但**辅助功能权限缺失时创建失败**（`:285` 分支），当前未生效 |
| 主线程自身开销 | 稳态采样：主线程仅 **14%** 在做 CoreAnimation 提交，其余空闲 |

### 6.32.4 剩余嫌疑（交下一轮）

[A]→[B] 那 **+20%** 发生在「无任何窗口」情况下，说明来源在
**进程与 WindowServer 的非窗口交互**上。剩余嫌疑：

    · `beginActivity(.latencyCritical, .userInteractive, .idleSystemSleepDisabled)`
      —— macOS 最强的「不要节流我」声明，可能系统性提升相关合成节奏
    · `setpriority(PRIO_PROCESS, 0, -20)` —— 最高进程优先级
      （⚠️ 用户红线「不能降 nice=-20」，需**非侵入式**验证：先只读对比，
        不做持久修改）
    · `IOPMAssertion`（Power Management 层断言）
    · `GameModeDefender` 每 3s 重新主张 nice/activity/音频
    · 10 个窗口里 8 个是 `onscreen=false` 的残留（1200×30 与 1470×33 各 4 份），
      虽不可见但仍在窗口树内

**验证方法**（下一轮）：为上述各项各加一个 `AURORA_DISABLE_*` 诊断开关
（遵循既有 9 个开关的约定，不设则行为逐字不变），逐个做 ABBA 对照，
定位那 +20% 的确切归属。

### 6.32.5 这一节的意义

「一打开就卡得离谱」此前一直是**归因猜测**（游戏自身负载 /
Aurora 抢 CPU / 窗口遮挡…），本节第一次把它**量化并分解**：

    总增量 +30.7%
      ├─ +20.1%  进程存在本身（非窗口）
      └─ +10.6%  窗口可见性

且明确了 **Aurora 自身只占 1.2% CPU、游戏 CPU 完全不受影响** ——
问题的本质是 **WindowServer 的合成负担**，而不是 CPU 争抢。
这解释了为什么此前所有「降 CPU」的努力方向都不对。

## 六点三十三、WindowServer +30% 的最终定位：**UI 渲染本身**

### 6.33.1 决定性分解实验

在 6.32 三组实验基础上，再加一组「只开 UI、不抓屏不跑模型」，
把「UI 窗口」与「推理/抓屏」彻底分开：

    组别                                       WindowServer    Δ vs A
    [A] Aurora 完全关闭                         51.3%            —
    [B] 仅 UI（不带 --auto-drive）              77.4%          **+26.1%**
        —— 不启动抓屏、不加载任何模型、不进 tick 推理
    [C] 完整（--auto-drive，窗口可见）           81.7%          **+30.4%**

**结论：+30.4% 里有 +26.1%（86%）仅仅来自「把 UI 窗口显示出来」。**
抓屏 + 四个模型的加载与运行合计只占剩余的 **+4.3%**。

### 6.33.2 这与 6.32 的「窗口隐藏仍 +20%」并不矛盾

两组实验共同指向同一件事：**增量来自「Aurora 的 UI 存在」这一事实**，
而不是某个具体窗口的可见性、也不是推理负载。差别在于：

    · `--agent-command`（6.32 组 B）：窗口被 `orderOut`，
      但 SwiftUI 视图树**仍在构建与维护**（`ContentView` 照常求值），
      WindowServer 仍持有其图层 → +20.1%
    · `orderOut` 后仍有一部分合成/布局开销无法消除，
      完全可见时再加上真正的绘制 → 合计 +30.4%

### 6.33.3 完整的因子分解表

| 因子 | 贡献 | 依据 |
|---|---|---|
| **Aurora UI 存在且可见** | **+26.1%** | 组 [B]（不抓屏不跑模型） |
| 抓屏 + 四模型 + tick 推理 | **+4.3%** | 组 [C] − [B] |
| 其中：帧率 HUD（`level=.screenSaver`） | +1.2% | `AURORA_DISABLE_HUD` 对照（6.31.3） |
| 其中：静音音频（`coreaudiod`） | +0.6% | 实测 11.5% → 12.2% |
| 合计 | **+30.4%** | |

### 6.33.4 已排除的全部候选

| 候选 | 排除依据 |
|---|---|
| 帧率 HUD | 净代价仅 +1.2% |
| 显示器刷新率被拉高 | 主/副屏均实测 **60.0 Hz**，未变 |
| 窗口数量泄漏 | 连续 4 次枚举恒为 10 个，不增长 |
| 主窗口非不透明 | 已 `isOpaque = true`，走快路径 |
| `CGEventTap` | 辅助功能权限缺失时创建失败，当前未生效 |
| 抓屏失败重试 | 60 秒内仅 **2 次** `[CAPTURE]` 记录，无重试循环 |
| 静音音频 | `coreaudiod` 仅 +0.6% |
| 主线程自身开销 | 稳态采样主线程仅 **14%** 在做 CA 提交 |
| 推理/模型负载 | 本组 [B] 完全不加载模型，仍有 +26.1% |

### 6.33.5 这意味着什么

「一打开就卡得离谱」的根因是 **Aurora 的 SwiftUI 界面本身让
WindowServer 的合成负担增加了约 26 个百分点**（在总负载 ~51% 的基础上，
相当于让 WindowServer 多干一半的活）。

**这与「降 CPU」「降 nice」等方向完全无关** ——
Aurora 自身只占 1.2% CPU、游戏 CPU 不受影响（6.27），
问题纯粹在**合成管线**上。

**下一步的修复方向**（需用户确认，因涉及「不能降品」红线）：

    · 主窗口 1200×760 的 SwiftUI 视图树包含大量自定义绘制
      （地图、标记点、状态向量、日志卡片等），每次失效都触发大范围重绘
    · 可考虑的重绘隔离手段：把静态子树（TopBar / HardwareBank /
      RunLogCard 等）拆成独立 `Equatable` 视图，让 @Observable 变化
      只失效真正依赖它的子树 —— **不改变任何视觉呈现，纯性能优化**，
      符合「不能降品」

## 六点三十四、【根因确认】「一打开就卡得离谱」= 背景 60px 动态高斯模糊

### 6.34.1 决定性实验：单因子对照

新增诊断开关 `AURORA_DISABLE_BG_DRIFT=1`（只让背景光斑静止，
不做任何其它改动），做单因子对照：

    [基线] Aurora 完全关闭                       WS = 51.2%
    背景漂移 开（现状）                          WS = 81.9%    Δ = **+30.7%**
    背景漂移 关（AURORA_DISABLE_BG_DRIFT=1）     WS = 51.9%    Δ = **+0.7%**

**停掉背景漂移后，WindowServer 完全回到基线。**

⟹ **「一打开就卡得离谱」100% 由这一处引起。**
其余所有因子（抓屏、四模型、HUD、静音音频、nice=-20、event tap）
合计只占 0.7 个百分点。

### 6.34.2 根因代码

`AuroraTheme.swift` 的 `AuroraLightField`（`ContentView` 的背景装饰）：

    ZStack {
        blob(color: condition.color, size: max(w,h)*0.78, …)   // 三个光斑
        blob(color: .white, size: max(w,h)*0.60, …)
        blob(color: .white, size: max(w,h)*0.48, …)
    }
    .blur(radius: 60)                                          // ★ 60px 高斯核
    .offset(x: drift ? 22 : -22, y: drift ? 18 : -18)          // ★ 每帧在动
    .animation(.easeInOut(duration: 26).repeatForever(autoreverses: true), value: drift)
    .onAppear { drift = true }                                 // ★ 永不停止

**机理**（该段代码上方注释其实早已写明，只是从未量化）：

    · 三个 blob 的总面积 ≈ 窗口的 **1.9 倍**
    · `.offset` 每帧改变位置 ⟹ 模糊结果**无法被 Core Animation 缓存**
    · 于是**每一帧都要对近两倍窗口面积重做一次 60px 大核高斯卷积**
    · 该动画 `repeatForever`，**只要 App 开着就永不停止**

WindowServer 的负载正比于「被重绘的像素面积 × 模糊核大小 × 频率」，
本处三项全部拉满。

### 6.34.3 为什么之前没找到

排查过程中走过三条弯路，都在本轮被证伪：

    ① 「游戏自身负载」     → 6.27 实测游戏 CPU 不受 Aurora 影响（±1.7%）
    ② 「Aurora 抢 CPU」    → 6.31 实测 Aurora 稳态仅 **1.2%** 单核
    ③ 「帧率 HUD 压顶」    → 6.31.3 实测 HUD 净代价仅 **+1.2%**

真正的线索来自 6.32/6.33 的两步分解：

    6.32  orderOut 所有窗口仍 +20.1%  ⟹ 不是「某个窗口可见」的问题
    6.33  仅开 UI、不抓屏不跑模型 +26.1%  ⟹ 锁定在 **UI 渲染本身**
    6.34  单因子关掉背景漂移 → **回到基线**  ⟹ **精确定位**

**方法论教训**：`sample` 抓主线程堆栈看不到这个 —— 它是 **GPU/合成侧**
的开销，主线程只负责提交（实测主线程仅 14% 在做 CA 提交，看似健康）。
必须用 **WindowServer 的 CPU 时间增量** 才能观测到。
6.28 曾加过 `.drawingGroup()` 想缓存模糊，结果**更卡**
（注释 `:330-355` 有完整回退记录）—— 因为 `.offset` 让离屏纹理每帧重建。

### 6.34.4 当前状态与后续

**本轮只加了诊断开关，未改变默认行为** —— 用户红线「不能降品」，
背景光斑漂移是既有视觉设计的一部分，是否改为默认静止需**用户确认**。

可选的正式优化（按代价从低到高）：

    a) 让漂移动画在窗口不可见/游戏全屏时暂停（视觉零损失）
    b) 降低 blur 半径（60 → 30），视觉略变
    c) 去掉漂移，保留静态光斑（视觉几乎无差异，性能收益 30 个百分点）
    d) 用预渲染的静态图片替代实时模糊（需改资产）

**推荐 (c)**：`81.9% → 51.9%` 的收益极大，而 26 秒往复 44px 的
缓慢漂移在观感上几乎察觉不到。但**须由用户拍板**，不自行更改默认值。

## 六点三十六、【根因确认并修复】系统代理场景下抓包失效

### 6.36.1 背景

用户提示「我有开系统代理」。这一句解释了一个长期矛盾 ——
抓包看起来在工作，但定位数据始终对不上。

### 6.36.2 系统代理改变了流量路径

开启 Clash 类系统代理后，游戏的流量路径变为：

    游戏 ──[明文私有协议]──→ 127.0.0.1:12450 ──[TLS 密文]──→ 外网服务器
           ↑ 只有这一段可解                      ↑ 抓了也解不开

实测证据（`lsof`）：

    游戏 pid 94812:
      · 127.0.0.1:56415 → 127.0.0.1:12450   （走系统代理）
      · 192.168.1.3:54815 → 43.144.211.30:30031 （直连，15秒一次）
    代理 core pid 3316:
      · 192.168.1.3:56329 → 39.173.180.138:20046（39.35 Hz，TLS 密文）

物理网卡上 `20046` 那条 39 Hz 的流**首字节是 `16 03 03` / `17 03 03`**
—— 标准 TLS 记录头，无论字节级还是位级扫描都解不出坐标。
**明文只在回环（lo0）上。**

### 6.36.3 两个叠加的代码缺陷

**缺陷 ①：`lo` 被列入跳过表**

    private static let skipPrefixes = ["lo", "pdp", "utun", ...]
                                              ↑ 回环被整个放弃

回环是代理场景下**唯一的明文链路**。跳过它 = 主动放弃可解数据。

**缺陷 ②：链路层头长硬编码 14 字节**

    guard data.count > 14 else { return }
    var offset = 14                    // 假定「链路层 = 以太网」

链路层类型随网卡而变：

| 网卡 | pcap DLT | 头长 |
|---|---|---|
| en0 / en8 | `DLT_EN10MB` (1) | **14** |
| **lo0** | **`DLT_NULL` (0)** | **4** |
| OpenBSD lo | `DLT_LOOP` (108) | 4 |

`tcpdump -i lo0 -L` 实测确认回环是 `NULL (BSD loopback encapsulation)`。

**两个缺陷叠加的后果**：即使把 `lo0` 加进探测列表，按 14 字节跳会切进
IP 头中间 → `ipVersion` 读到非 4 → 立即 `return` → **一个坐标都解不出**，
且完全静默、无任何日志。这就是「抓包看起来在跑，定位却永远不对」的机理。

### 6.36.4 对照实验（铁证）

构造真实的 `127.0.0.1:30031` UDP 包，用两种偏移各解析一次：

    回环包前 8 字节: 02 00 00 00 45 00 00 68
                     └─ NULL 头 4B ─┘└─ IP 头起点 ─┘

    旧代码（偏移 14）: 首字节=0x00  版本=0   ✗ 错位 → 直接 return
    新代码（偏移  4）: 首字节=0x45  版本=4   ✓ 正确解析
                       协议=17  端口 30031→30031
                       payload 偏移60 float32 = -88363.81  ← 坐标完整读出

⟹ **系统代理场景下旧代码 100% 解析失败，新代码可完整读出坐标。**

### 6.36.5 修复内容

    a) 新增 pcap_datalink 绑定，在 openWithFilter 成功后记录该网卡的
       实际 DLT 类型（currentDataLinkType 成员，默认值 = 以太网，
       保证既有物理网卡路径逐字不变）
    b) 新增 linkLayerHeaderLength(forDLT:)：DLT_NULL/DLT_LOOP → 4，
       其余 → 14（回退原行为，不引入新行为）
    c) processPacket 改用 linkLayerHeaderLength 决定偏移
    d) `lo` 从 skipPrefixes 移出，改为 loopbackNames，
       **排在所有物理网卡之后**探测：
       物理网卡能探到 30031 时（绝大多数情况）行为完全不变；
       只有物理网卡全部探不到时才去回环找（= 代理场景）

### 6.36.6 顺带修掉的测试缺陷

`--nic-autotest` 阶段 C 恒为 FAIL，原因不是抓包逻辑，而是**测试假设脱离现实**：

    测试等 8 秒就断言「应已失流」
    但 streamLostWindow = 22.0 秒（必须覆盖游戏 15.01 秒的坐标周期）

改为按真实窗口（22s + 5s 余量）等待。

### 6.36.7 验证结果

    回归：--proto-selftest PASS   --motion-selftest PASS
          --yolopx-selftest 检测框 9 / 可行驶 26.19% / 车道线 8.042%

## 六点三十七、【根因确认并修复】探测窗口与坐标周期不匹配 → 有流量却锁不上

### 6.37.1 症状：游戏在跑、网卡有流量，抓包却空转

现场实测（`~/Library/Logs/aurora_pcap.log`）三方证据同时成立：

    · 游戏进程存活，CPU 121%
    · lsof 显示 30031 ESTABLISHED
    · tcpdump -i en8 port 30031 能抓到 76 字节坐标包

但抓包模块却在 10 张网卡之间空转：

    选中网卡: en8 → en0 → llw0 → vmenet0 → vmenet1 → en3 → ...
    第 5 轮探测：10 张网卡均无 30031 流量（游戏未启动/未进游戏）
    空闲退避：连续 5 轮无流量 → 下次探测间隔 30s

⟹ **「网卡上明明有流量，探测却报无流量」** —— 这是纯粹的探测窗口 bug。

### 6.37.2 根因：2.5 秒窗口去接 15 秒周期的包

    probeWindowPrimary = 2.5 秒          ← 高嫌疑网卡（默认路由）的探测窗口
    实测坐标包周期      = 15.01 秒        ← 四个样本 74/74 个包间隔完全一致

**2.5 秒窗口落在 15 秒周期的任意位置，命中概率仅 2.5 / 15.01 ≈ 17%。**

更糟的是失败模式：en8 作为高嫌疑网卡只被给 2.5 秒，错过即判「无流量」，
接着必须等整轮 10 张网卡扫完（9 张各 0.5s + en8 的 2.5s）才轮到下一次 ——
而下次**依然只有 2.5 秒**。多次独立小概率事件连败是常态，
于是表现为「长时间空转、偶尔才侥幸锁定」。

### 6.37.3 原注释为何过时

`probeWindowPrimary` 上方的注释写着：

    「实测数据（tcpdump 30 秒采样）：30031 是突发式流量——
      一阵连发（1 秒内 5-6 包）后静默 6-9 秒」

那是 **2026-09-25 用 30 秒采样**得到的结论。而 2026-09-30 用四个独立样本
（idle / move2 / move_burst / turn）复测（见 6.30 节）发现：坐标包**严格
每 15.00 秒一个**，74 个包间隔完全一致。2.5 秒这个值建立在一个已被推翻的
「突发式」假设上，故必然失效。

### 6.37.4 修复

高嫌疑网卡（默认路由接口 / 上次命中的网卡）的探测窗口：

    probeWindowPrimary(2.5s)  →  probeWindowPrimaryForKnownCadence = 16.0 秒

16 秒 ≥ 实测周期 15.01 秒 + 余量 ⟹ **单次探测即必中**（只要该网卡确实承载流量）。

其余 8 张低嫌疑网卡仍用 `probeWindowOther = 0.5 秒`（它们绝大多数是零流量的
虚拟接口，不值得久等）。一轮总耗时 ≈ 16s + 9×0.5s ≈ 20.5 秒。

**代价与权衡**：高分网卡每轮多等约 13.5 秒。但「多等一轮」远优于「永远锁不上」，
且仅在**探测阶段**（未锁定）付出，锁定后完全不涉及。

## 六点三十八、【根因修复】定位彻底错误 —— 三个叠加缺陷，MaaNTE 方案移植验证

### 6.38.0 用户报告（原文要点）

> 「绝对不是真实定位，绝对抓错东西了。传送了四五次都保持在那里，肯定有问题。
>  为什么是15秒每次？我特意查了事件，并不是15秒每次，而是每秒有好几次，
>  只要能移动立马就发数据包。」

用户三个观察**全部正确**，且都指向同一根因。

### 6.38.1 完整证据链（89.4MB 实战抓包，用户实玩 7 分钟）

抓包全量保存于 `/tmp/play/en8.pcap0` + `lo0.pcap0`（152,293 包）：

**缺陷 ①：方向反了。** 真实位置在 **C2S**（客户端→服务器的移动上报，
UDP 30212，~8Hz，站立也发、位置恒定）。旧代码只把 **S2C** 送解码器。
MaaNTE 上游 `nte_coordinate_api.py:454` 对 S2C 一律 `return` —— 只解 C2S。

**缺陷 ②：字段是微秒时钟，不是坐标。** 旧 `decodeProtoMove` 匹配 S2C 30031
的 76 字节心跳（每 15.00s 恒定一个），读 bit498/509/562/573 —— 实测这些位
落在心跳包**唯一变化的区域**（字节 56~63/68~71）：

    u32@56: 1323822037 → 1338821708 → 1354822707 → …
    Δ 恒为 +15,000,000（每 15 秒）= **每秒 +1,000,000 的微秒时钟**

所以「X 每 15s 漂 -4.47」= 时钟走字的位模式被当 float；「Y 恒 31866.77」=
固定字节 `da 1e df 08` 的位模式。**传送当然不会改变时钟** → 定位纹丝不动。
2026-09-25 的「物理自洽性」判据（ΔX=−2145.77 像 21.5m 移动）被时钟的
匀速走字骗过 —— 时钟恰好「像匀速移动」。

**缺陷 ③：过滤器漏了 UDP。** 旧过滤器 `(tcp|udp) port 30031` 把 C2S UDP
30212 移动包全部挡在内核层 —— S2C 30031 上只有心跳（TCP）与元数据推送
（物品/生成记录：`PropBox_Item_*`、`PrivateSpawnInfoRecord` 等明文，重组后
类型 ID 0x000a/0x0666/0x0667/0x0669），全都不含玩家实时位置。

**用户「15秒」之惑的解答：** 15.00s 是 S2C 心跳周期；移动包是 ~8Hz ——
用户观察「每秒好几次、移动立马发」与 C2S UDP 8Hz 完全吻合。

### 6.38.2 MaaNTE 上游方案（nte_coordinate_api.py，API_VERSION 1.3.0）

    抓包过滤器: tcp port 30031 or udp    （裸 UDP，靠解码器甄别杂包）
    解码方向:   仅 C2S
    候选扫描:   bit 偏移 [190, min(512, len*8-60))
      · float32 client_time ∈ [0, 100000)
      · UE压缩向量 scale=10  → 加速度（必须 scaled，宽 1~16，|v|<50000）
      · UE压缩向量 scale=100 → 位置（必须 scaled，宽 20~32，|v|≤2e6 cm）
      · 位置后紧接合法 FRotator（yaw 有、roll 无、|pitch|≤90）
    锁定: 时间连续性(±0.5s) + 空间惩罚(距²/5000²) + 新 flow 双包确认
    朝向: _NORTH/_EAST 点积 → 罗盘角 [0,360)

项目内 `UE5Decoder`（2026-09-13 移植）的 findCandidates/状态机与上游一致且
完好 —— **问题从来不在移植本身，而在它被缺陷①③饿死、被缺陷②抢答**。

## 6.40 车道保持（纯规则主驾）—— 视觉 + 地图混合 · 地图打点与三段式转向（2026-09-30 晚）

### 6.40.0 用户需求原文（确立本节的验收标准）

> 「一旦车道线丢失，绝对不会硬开，而是通过可行驶区域加上地图来转弯，反正转向全都用地图，
>   除非有车道线；如果没有车道线就直接用地图。」
>
> 「那个直走他会自己通过车道线……一些非常危险的弯道，那是他那些识别出现了弯道或者混杂的，
>   那么他就直接查地图……我想要是那种正常的、非常微小的弯道，就比如说高速公路上
>   也有那种很小的弯道，只要把方向盘往外面打一丢丢的那种弯道，然后那个是给模型自己拟合，
>   但是一旦出现真正需要路口有急弯的时候直接调地图。」
>
> 「你那个一整条弯道，过弯完新地方比较大的都得打一个点 —— 因为要是他不从你这个方向开呢？
>   还有，有一个路断了你都没发现吗？还准心是对的？……这条大直道上打还有十字路口那里，
>   如果他是从另一边过呢？你只打一个点，你要打很多个点好吗？……他要是从另一个方向过，
>   他走过了都不知道。」
>
> 交接判据：「在那条道路里，而且已经向前行驶一段距离，而且都能拟合在道路里，
>   并且模型已经能正常识别到车道线，才能算成功。」

**归纳成设计约束**：
1. 微弯（常态）→ 纯视觉线性拟合，方向只打一丢丢；
2. 急弯/路口/车道线失效 → **地图先验接管转向**；
3. 打点必须**密集**（一整条弯道多点）且**双向**（两个进入方向都记）；
4. 拐过去后**必须回正**，四条件齐备才交回视觉；
5. 执行机构只有 WASD —— 转向是**开关量**（`steer>0.1` 按 D / `<-0.1` 按 A），不是角度。

### 6.40.1 三轮返工：先修离线产物，再谈算法（★本节最重要）

本节最初直接开写打点算法，结果被用户当场抓出三处硬伤。**根因全在离线底图，不在算法**。
若不做下面三项修正，后面所有转向逻辑都建立在错数据上。

#### 修正 1 —— 灰度阈值错（45 → 70）：多抓了 16.1% 的等高线

早先在**一个 900×900 局部块**上测直方图，得出"背景 10~30 / 道路 80~90，双峰零重叠，
阈值不敏感"的结论 —— 那个块恰好偏亮，结论是错的。全图 13056² 实测：

| 灰度档 | 占比 | 实际是什么 |
|---|---|---|
| 0 ~ 8 | 47.6% | 纯黑（地图外/海） |
| 16 ~ 24 | 45.0% | 暗背景（空地） |
| 24 ~ 56 | 4.8% | 建筑纹理 + **等高线** |
| **80 ~ 88** | **1.95%** | **真·道路（唯一）** |

阈值 45 比 70 多出 **677,265 像素（16.1%）** —— 全是等高线/建筑噪声。
后果：打点 83% 落在非路面（图像验证 6 个点里 5 个在建筑上）。

连通性对照（2048 网格，最大连通块占全部道路像素）：

| 阈值 | 道路占比 | 最大连通块 | 判定 |
|---|---|---|---|
| 45 | 4.01% | 86.3% | 混入噪声 |
| **70** | **2.91%** | **98.6%** | ✅ 干净 |
| 80 | — | 37.1% | 道路断裂 |

新位图 `models/road_prior_2048_t70.png` 是旧版的**严格子集**（`new & ~old == 0`），
证明只去噪、未伤真路。生成脚本：`models/tools/make_road_prior_t70.py`。

#### 修正 2 —— 缩放 bug：整除截断丢了 468 米地图

```swift
H // GRID == 13056 // 2048 == 6        // ✗ 整除截断
GRID * 6 == 12288 < 13056              // ✗ 地图最后 768px 被丢弃
13056 / 2048 == 6.375                  // ✓ 真实比例
```

旧代码每格按 **6px** 池化，却按 **6.375px/格** 换算坐标 —— 双重错误导致**坐标系统性偏移**，
且地图最右/最下 768px（**468 m**）整块丢失。量化结果：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 打点到真路面距离（中位） | 609 m（找不到） | **0.0 m** |
| ≤1.8 m | 13.0% | **94.3%** |
| ≤9.8 m | 21.5% | **100%** |
| >24 m | **66.6%** | 0% |

修复：改用 PIL `BOX` 滤波直接缩放到 2048（覆盖全幅、精确 6.375 px/格，
等效 max-pooling，格内任何路面像素都保留）。

#### 修正 3 —— 路网断裂：斑马线把路"切断"了 837 处

用户指出「有一个路断了你都没发现」。检测：横向扫描原图找"两侧都有路、中间是深色窄条"
的位置 —— 发现 **837 处**，缝内灰度 **17~68**（真路面 80~88）⟹ **斑马线/路标**。

后果：射线打到缝里就"断"，路网不连通，曲率与分支判断全部失真。

修复：形态学闭运算（半径 16px，先膨胀后腐蚀）填窄缝，断裂 **837 → 49 处（减少 64%）**，
连通性恢复 98.6%。产物 `models/road_prior_2048_t70_fixed.png`。

### 6.40.2 打点 v2：密集 + 双向（用户三点要求的落实）

| 用户指出的问题 | v1 实况 | v2 修正 |
|---|---|---|
| 「一个弯道只打一个点」 | 362 点，聚类后一个弯道 1 点 | **952 个位置**，最近邻中位间距 **23 m** |
| 「他从另一个方向过呢」 | 只记一个进入方向 | **双向 1904 条**（952×2），覆盖 **96%** |
| 「路断了你都没发现」 | 底图有 837 处断裂 | 闭运算填缝，断裂减少 64% |
| 「十字路口那里」 | 未记录 | 路口 **2191 条**（含各分支方向），转向暂不覆盖但留数据 |

**双向的意义**：同一位置两条记录，`headingIn` 相差 105°~155°（= 180° − 弯度），
`turnSign` 一正一负。车反向驶来时匹配反向那条 → 左右自动相反，不会打反方向。
自检验证：正向 `turnSign=1`、反向 `turnSign=-1` ✓

产物：`models/road_corners_v2.json`（4095 条，100% 落在路面像素上）；
脚本：`models/tools/make_road_corners_v2.py`。

**方法**：射线峰值法 —— 每 6 格取种子点，向 36 个方向（每 10°）发射射线量"连续可达长度"，
局部极大即分支；2 分支 = 弯道（弯度 = 两分支夹角偏离 180°），≥3 分支 = 路口。
曲率半径 ≈ `跨度 / 弧度`。

**LaneFallback 升级要点**（回应"微弯只打一丢丢"）：

### 6.40.4 自检闭环探针抓出的两个真缺陷（★值得记的教训）

自检最初只验"能加载 + 试查 5 个已知点"，结果 5 个探针**全部返回"无适用"** —— 那是
**假绿**：只证明文件读进来了，没验证任何决策逻辑。为此加了**闭环探针**（从打点集自身取一个点，
把车放在它后方 35 m、朝向 = 进入方向，必然命中），随即抓出两个真问题：

1. **转向目标选错（已修）**：`steerForCorner` 原直接拿 `headingOut`（出弯方向）当目标 ——
   但车还在弯道点后方几十米时，出弯方向与车头可能差 120°，会输出"还没到弯就掰 120°"的荒谬指令。
   修为**两阶段**：距点 >25 m 时目标 = 朝弯道点开（`compassBearing`）；≤25 m 才目标 = 出弯方向。
2. **候选点选了侧前方（已修）**：打点密集时，仅按"最近"选会选中**侧方 63°** 的另一个点，
   跟着它打方向会把车带下路。新增**前方锥约束**（`aheadConeDeg=75°`，
   候选点方位与车头夹角超此值不采纳），自检闭环随即只命中前方 26 m 的点。

另有一处**断言写错**（非代码缺陷）：原断言要求正/反向进入方向差 >120°，
但弯道两分支夹角 = 180° − 弯度，实际差 105°~155°，正确阈值是 >90°。

**结论**：自检必须能构造"必然成功"的场景，否则"PASS"只是文件读到了而已。

#### nic-autotest 从 FAIL(4) → PASS 的根因（同一类型的坑）

失败现象：阶段 B/D 注入真包后**不锁定**（`active=无`、`lockCount=0`）。

根因：注入目标是**默认网关**（`192.168.1.1`）。`isLocalishAddress` 把 `192.168/10/172.16-31`
全判为"本地"，于是 `src=本机、dst=网关` 被 `packetDirection` 算成 **s2c**（服务器下发方向）。
而本轮修复方向反转时在解码入口新增了 `if direction == "s2c" { return }`（真实移动包只在 C2S）
—— 注入包在入口即被丢弃，与过滤器、探测窗口都无关。

修复：注入目标改为**真实游戏服务器地址**（`49.232.46.87`，非私有 → 正确判为 c2s；
可用 `AURORA_NIC_TEST_TARGET` 覆盖）。修复后 7 项断言全绿。

**教训**：`isLocalishAddress` 把私有网段一律当"本地"，是**方向判定**的隐含前提；
任何"往内网地址发包来模拟外网流量"的测试都会被它误判。测试用的地址必须与生产同性质。

### 6.41.3 ★ 离线全量验证抓出的方向性 bug（本节最重要）

对 1211 个路口 × 每条来路（共 6690 个情形）复现 Swift 侧选路逻辑，结果**完全不对**：

| 指标 | 首轮实测 | 设计预期 |
|---|---|---|
| 直行（≤20°） | **0.0%** | ~63.5% |
| 掉头级（>120°） | **11.5%** | 0.1% |
| 主路判据使用率 | **0%** | ~19% |

**根因**：「排除来路」判据方向搞反了。

```swift
// ✗ 原写法：用车→路口的方位（bearingToJunction）作为来路
let bearingToJunction = compassBearing(from: 自车, to: 路口)
filter { headingDiff(branch.deg, bearingToJunction) > excludeInDeg }
//  车在来路上朝路口开时，bearingToJunction ≈ 车头方向
//  ⟹ 这行把"与车头同向的支路"全部排除 —— 恰好排掉了直行该走的那条

// ✓ 正确：来路 = 车头的反方向
let incomingHeading = (headingDeg + 180) % 360
filter { headingDiff(branch.deg, incomingHeading) > excludeInDeg }
```

修正后（同一份数据全量重跑）：

| 指标 | 修正前 | 修正后 | 预估 |
|---|---|---|---|
| 直行（≤20°） | 0.0% | **68.7%** | 63.5% |
| 顺路转弯（20~60°） | 61.1% | **23.7%** | 27.1% |
| 大转弯（60~120°） | 27.4% | **7.5%** | 9.2% |
| 掉头级（>120°） | 11.5% | **0.1%** | 0.1% |
| 主路判据使用率 | 0% | **19%** | ~12.8% |

需转向角中位 20°、均值 23°、最大 160°；置信度中位 0.60。

**教训**：这类"几何方向"的 bug **不容易靠读代码发现**（两种写法看起来都合理），
但**全量离线验证一跑就露馅** —— 因为它会体现在分布上（直行 0% 显然荒谬）。
凡是能用离线数据全量跑的逻辑，就不要只做单元级验证。

### 6.41.4 转向规则（三层，全部纯几何）

```
① 排除来路：来路 = 车头反方向（heading + 180）± excludeInDeg(35°) 内那条
② 选去向：剩余支路里挑与车头夹角最小的
③ Y 形岔路（12.8%）：多条都在 forkTolDeg(25°) 内 → 主路判据
     先比射线长度（触顶按 0.95 折；差超 reachRatio=1.2 才算明显主路）
     不明确 → 再比宽度（仅 widthValid 的）
     都不明确 → 取较长者，置信度降到 0.5
```

**两阶段输出**（与弯道同构）：距路口 >25m 做预对准（强度按置信度打折）；
≤25m 真正转向出口方向。转向量上限 0.5、置信度低于 1 时按比例衰减。

**兜底保障**：支路不足 / 选不出出口 → **不输出转向**（保持航向）+ 限速 30 km/h，
绝不随机拐一条。大转弯（>90°）置信度自动乘 0.6。

### 6.42.3 ★ 自检自身踩过的两个坑（值得记）

写完后第一次运行**完全测不出东西**（推理计数=0、频率全是 25Hz），根因两个：

**坑 1：`Thread.sleep` 阻塞主线程 → 推理结果永远回不来**
- 推理在 `inferenceQueue` 上跑，完成后要 `DispatchQueue.main.async` 回写
  （掩码/检测框/latency）。主线程若被 `sleep` 睡死，回写永远排不上队 →
  `isInferencing` 停在 `true` → 后续提交全被"防重叠"门挡掉。
- **修法**：改用 `RunLoop.current.run(until:)` —— 与生产 tick 一致（生产 tick 本就跑在 RunLoop 上）。

**坑 2：频率测错了对象**
- 原先"我调了 `infer()` 就打一个点" —— 那只反映**提交频率**（恒等于 tick 频率 24~25Hz），
  而 R1 红线关心的是**推理真正完成**的频率（yolopx 应 ~12Hz 而非 24Hz）。
- **修法**：用各引擎自增的 `inferenceCount` 变化打点，只有计数涨了才记一次。

**教训**：测量工具本身也会骗人 —— 它的输出必须**先与已知事实对上**（见下节：
yolopx 12Hz 与 68.9ms 推算的 14.5Hz 吻合）才算可信。

### 6.42.5 ★★ 基线直接坐实了缺陷①（本轮最重要的发现）★★

```
yolopx 提交 241 次（每个 tick 都提交 = 24Hz）
yolopx 完成 120 次（= 12Hz）
⟹ 一半的提交被 isInferencing 门白扔了（121 次无效调用）
```

**结构性问题**：
```
tick(24~30Hz) 每帧调 yolopxEngine.infer()
   └─ isInferencing 门：只挡重叠提交，不改变"一次接一次连续跑"
   └─ yolopx 单次 68.9ms > tick 预算 33.3ms → 永远跑不完
   ⟹ yolopx 线程 = 永久占满一个核 + 每 33ms 被唤醒抢一次 P 核
```

**关键洞察（不降频也能省的根据）**：
yolopx **本来就只跑到 12Hz**（实测）—— "每 tick 触发"**没有让它更快**，
只是让它在两次结果之间**白抢 CPU**、并产生 121 次无效函数调用。

**另一个新发现（缺陷②）**：
```
YolopxEngine.swift:609-617 —— letterbox 在**主线程**绘制
   「主线程准备输入缓冲（letterbox 绘制），再交给推理队列」
   实测该 letterbox = 10.540ms（文档 §2.4）
   × 12Hz = 126ms/秒 全花在主线程上
   ⟹ 这是纯白工：同样的算法挪到推理队列即可，一个字都不用改
```

### 6.42.8 测量方法学备注

- **不用平均值**：卡顿是长尾问题，故一律 p50/p95/p99 + max
- **测试图不用纯色**：纯色会让缩放/卷积类优化"假快"，故造斜向梯度 + 棋盘格 + 亮线

- **环境一致**：空载数字同样可用于回归对比，只要前后两次环境一致
  （游戏满载数字需游戏在跑，现场测）

#### A2：letterbox 移出主线程 —— **主线程成本降 3.9×**

| 指标 | 优化前（A组） | 优化后（B组） | 提升 |
|---|---|---|---|
| `submit.yolopx` p50 | **0.158 ms** | **0.041 ms** | **3.9×** |

**为什么 CPU% 没降**：工作只是从主线程**挪到**推理线程，总功不变 ——
本项的收益是**主线程腾空**（那才是卡顿感的来源），不是省 CPU。
省下的 10.540ms letterbox 现在由推理线程承担；主线程每帧只剩一次 guard 检查。

**为什么算法没变**：仍是同一个 `drawLetterbox`（内部 CGContext 快路径，vImage 分支保持关闭）。
文档实测"letterbox 改 vImage"会让检测框 9→6（精度回退，已否决）——
故 A2 只改**在哪执行**，绝不改**怎么算**。R2 复验：检测框仍 **9 个** ✓

#### A1：yolopx 节拍 —— ★ **被实测否决（默认关闭）**

**初衷**：基线显示 yolopx **提交 241 次 / 完成 120 次** —— 一半提交被 `isInferencing` 门白扔。

**实测结果（ABBA，三组）**：

| 配置 | yolopx 频率 | 判定 |
|---|---|---|
| 优化前 | 12.75 Hz | 基准 |
| 优化后（节拍关闭，默认） | **12.82 Hz** | ✅ 未降 |
| 优化后 + 节拍 90ms | **5.02 Hz** | ❌ **掉 61%，违反 R1** |

**根因**：节拍是"距上次完成 ≥ 90ms 才启动"的**固定间隔**。而空载推理比游戏里快得多，
固定间隔反而成了**额外瓶颈** —— 把"能跑多快"硬压到"间隔多大"。

**处置**：**默认关闭**（`minInferenceIntervalMs = 0`），并把教训写进代码注释。
若要启用，值必须**小于典型单次推理耗时**（如 30ms），作用只是"别在推理未完成时白准备输入"。

**更优的天然保护**：A2 之后，无效提交的成本已从 10.5ms（主线程 letterbox）降到 **~0.04ms**
（只剩一次 guard 检查）—— 所以"每 tick 提交"现在几乎免费，**不需要节拍**。

#### B/F：空间索引 —— ★ **测量方法本身被修正**

**首轮测量（错误）**：`cornerAhead` 显示 **31.4 ms**、`isOnRoad` 显示 **14.3 ms**。

**根因**：只调用了 1 次（n=1），测到的是**懒加载的一次性成本**
（2048² PNG 解码 + 420 万次 buffer 映射），不是稳态热路径成本。

**修正后（预热 + 120 次采样）**：

```
map.isOnRoad         p50=0.000  p95=0.000  max=0.001
map.nearestRoad      p50=0.000  p95=0.000  max=0.001
map.cornerAhead      p50=0.001  p95=0.001  max=0.001
map.junctionAhead    p50=0.003  p95=0.003  max=0.005
→ 一帧地图查询合计: p50 0.004 ms / p95 0.004 ms（tick 预算 33.3ms）
```

**仍然做的优化（空间索引）**：`cornerAhead` 原为**纯线性扫描 1904 条**（×3 次
`headingDiff` + `compassBearing` 的 atan2 ≈ 8000 次浮点三角运算）。
改为**网格空间索引**（128m/格，查 3×3 邻格）。

**等价性证明（必做）**：索引是"加"出来的优化，一旦格边界/前瞻量关系搞错会静默漏判
（安全性问题）。故保留 `cornerAheadLinearReference()` 作为**全量扫描基准**，
自检里用 200 个散布全图的探针**逐点对拍**：

```
索引对拍: 探针命中 91 次，不一致 0 次 ✓ 与线性扫描等价
```

**为什么本机看不出速度差异**：空载时 4 核全空闲，8000 次三角运算 ≈ 0.001ms。
**但游戏满载时 CPU 被抢占**，运算量的差别会体现 —— 这是"为满载场景做的优化"，
其价值只能在游戏运行时验证（现场测）。

### 6.43.1 E3 —— `dlog` 缓冲批量刷（本批收益最大）

**优化前实测代价**：每次 `dlog` 走 **6 次 syscall**
```
fileExists(stat) → attributesOfItem(stat) → open → seek → write → close
```
而 `dlog` 被**三个线程并发**调用（主线程 30Hz tick / 推理回调 / 读包线程 10Hz+）
⟹ 每秒数百次 syscall + 反复 open/close，全落在**主线程 tick 路径**上。

**优化后**：新增 `LogSink`（`AuroraDriveApp.swift` 文件末）
- 路径解析一次 + FileHandle 常驻（不再每次 open/close）
- 内存缓冲累积，满 8KB 或每 200ms 落盘
- 独立串行队列（`.utility`）刷盘，调用线程只做一次数组 append
- `atexit` 前 flush；缓冲超 512KB 时丢弃较早日志并插入提示行

**ABBA 实测（各 300 次采样）**：

| 指标 | 优化前（`AURORA_LOG_SYNC=1`） | 优化后（缓冲） | 提升 |
|---|---|---|---|
| `dlog` 热路径 p50 | **0.065 ms** | **0.000 ms** | ≈ 消除 |
| `dlog` p95 | 0.121 ms | **0.000 ms** | |
| `dlog` p99 | 0.235 ms | **0.005 ms** | **47×** |
| `dlog` max | 0.663 ms | 1.295 ms | 首次触发刷盘（一次性） |
| `flushNow`（每 300 行一次） | 0 ms（无缓冲） | 0.091 ms | — |

**为什么这不是"省一点"**：三线程并发 × 每秒数百次 × 0.065ms ⟹ **每秒省下数十毫秒的主线程时间**。

**硬约束（全部守住）**：
- **不丢日志**：`atexit` flush + 缓冲满主动刷 + 超时刷；全候选不可写 → 落 stderr（与优化前一致）
- **格式逐字不变**：`"时间 消息"` 未改
- **10MB 封顶保留**：`writeOnce` 沿用原逻辑
- **可写回退链保留**：`/tmp/aurora_debug.log` → `~/Library/Logs/` → `/tmp/aurora_debug_ui.log`
- **回退开关**：`AURORA_LOG_SYNC=1` → 逐行同步写（与优化前逐字一致）

**未采用**：信号 handler 里 flush。原因：信号上下文做 I/O 不安全，且会干扰既有崩溃报告链路；
改由 `atexit`（覆盖正常退出）+ 主动刷（覆盖长运行）承担，最坏丢 8KB 或 200ms。

### 6.43.3 E2 —— 小地图源图转换缓存

**问题**：`MapTileCache.tile(from image: NSImage, ...)` 内部调
`image.cgImage(forProposedRect: nil, context: nil, hints: nil)`。
视野缓存（4px 量化键）设计正确，但**转换发生在取视野缓存之前**（要拿到 `src` 才能裁），
所以即使视野没变、走了缓存命中，**转换也已经做掉了**。

**改法**：新增 `cachedCGImage(from:)`，按**源图身份**缓存转换结果：
```swift
private var srcImageID: ObjectIdentifier?   // NSImage 是引用类型，可稳定标识
private var srcImageSize: CGSize = .zero    // 防御"同实例换内容"
private var srcCGImage: CGImage?
```
同一张源图只转一次；换图才重转。

**不降品**：小地图刷新率**不变**（`MapTileCache.shared.tile` 调用点数量未变），
只是同一张源图不重复做格式转换。**R5 守住**。

### 6.43.4 G —— 定位分级新鲜度（★ 本批含安全性修正）

**先查到的现状**：`readWithFreshness` 已有两级（`.fresh` / `.stale` / `.unavailable`），
文档 §3.3 已提出"分级"思想 —— 但**消费者不分级**，且发现一个**实际缺陷**：

```
写入端: self?.locatorScore = poseIsStale ? 0.5 : 1.0
决策门槛: guard locatorScore >= 0.4 else { return nil }
⟹ 陈旧定位（0.5）**大于门槛 0.4，照样能驱动驾驶** ← 缺陷
```

**改法两层**：

**层 1：数据层三级 tier**（`CoordinateCapture.swift`）
```swift
enum PoseTier {
    case live      // ≤18s（= 现有 poseFreshWindow）：全功能
    case recent    // ≤40s（≈2.6 个周期）：UI 正常显示，决策不采信
    case stale     // ≤90s（≈6 个周期）：UI 标"陈旧"
    case lost      // >90s：UI 标"无定位"
}
static let poseRecentWindow: Double = 40.0
static let poseStaleWindow: Double  = 90.0
func readWithTier(...) -> (tier, pose?, ageSeconds?)
```
⚠️ `.live` 阈值**严格等于**原 `poseFreshWindow = 18.0` —— 既有行为逐字不变。

**层 2：决策侧按档位给分**（`AuroraDriveApp.swift`）
```swift
private func locatorScoreForTier(_ tier: String) -> Double {
    case "live":   return 1.0    // ≤18s：正常
    case "recent": return 0.3    // 低于 0.4 门槛 → 不驱动驾驶
    case "stale":  return 0.1
    default:       return 0.0
}
```

**验算**：

| 档位 | 分数 | 过决策门槛(0.4)? |
|---|---|---|
| live (≤18s) | 1.0 | ✓ 可驾驶 |
| recent (18~40s) | 0.3 | ✗ 不驱动驾驶 |
| stale (40~90s) | 0.1 | ✗ 不驱动驾驶 |
| lost (>90s) | 0.0 | ✗ 不驱动驾驶 |

**为什么这样能治 6% 断档**：蒙特卡洛显示单一阈值是"断崖式"的
（18/25/30s 可用率全为 94.6%，35s 才跳到 99.7%，无中间地带）。
分级后 UI 层 `live+recent` 都正常显示（不闪断），而"幽灵定位"也不会回来
（`lost` 明确标注 + `hasRecentTraffic` 前置门仍在）。

**不提高任何频率**：定位更新仍由游戏 15.01s 突发决定（客户端改不了），
本项只是把同一份数据按年龄分成四档。**未新增抓包、未新增截图、未新增周期任务。**

**安全性方向**：与旧行为相比**更保守** —— 陈旧定位不再参与驾驶。
这是安全修正，不是性能妥协。

## 6.45 光流接线 —— 完整径向模型（2026-10-01 · 路线2）

### 6.45.0 缘起与用户决策

§6.44.5 提出光流裁决三选项（A 默认关闭 / B 接线让它真正有用 / C 降频）。
**用户选择 B**，原话要点：

> 「降频我是绝对不允许，一旦降品我会直接把模型换掉」

⟹ 路线 B 的性质是「**只加不减**」：光流照常每帧算，额外增加消费端。
这不是优化项，是**功能补全**（把预留接口接上）。

**后续追问确认的两个设计选择**：
1. **路线**：用户选 **路线2（完整径向模型）**，而非"只校验横向平移"的保守版
2. **异常行为**：用户选 **降级为「不预测」，只做位置平滑**

### 6.45.1 为什么必须用径向模型（几何论证）

`MotionPredictor` 的速度来自 α-β 滤波对**检测框差分**的更新。它有个天生弱点：
**目标静止、自车在动**时，会把"自己的运动"误算成"目标在动"。

直觉上拿光流的 `dx/dy`（全局中位平移）去减即可 —— **但那是错的**：

| 自车运动 | 画面上静止目标如何移动 | `dx/dy` 能描述吗 |
|---|---|---|
| **横移** | 整体平移 | ✓ |
| **前进** | 向消失点**径向扩散** | ✗ |

前进时画面中央几乎不动、边缘向外飞 —— 这是**径向扩张场**，正是
`divergence` 所度量的量（C 层注释：「3×3 分块平均流的径向外向分量」）。
故必须建径向模型，而不是平移相减。

### 6.45.2 关键几何事实（本项目比常规标定简单）

`CaptureEngine.swift:349` 明确注释：直通帧是「**非等比拉伸到 640×640
（与训练/慢路径一致，不保持宽高比）**」。

⟹ 推论：
- x/y 两方向焦距**不同**（`fx ≠ fy`）
- 但**消失点恒在画面中心** (320, 320) —— 拉伸不改变中心

这是本项目标定比常规相机简单的地方：只需 2 个参数（中心已定）。
本次先取中心 (320,320)、`pitch = 0` 作为**保守初值**，真机标定留待实测。

### 6.45.3 实现（新增 1 文件 + 改 1 文件）

**新增 `Sources/AuroraDrive/Inference/EgoMotionModel.swift`**（纯新文件）
- `EgoMotionEstimate`：`forwardRate`（前向率，来自 `divergence`）、
  `lateralRate`（横向率，来自 `dx`）、`confidence`、`isUsable`
- `EgoVerdict`：观测位移 / 自车预测位移 / 残差 / **残差比** / `blocksPrediction`
- `estimate(from:dt:)` —— **数据不可信时返回 nil**
- `predictedImageShift(for:ego:)` —— 径向位移场预测
- `verdict(for:observedVelocity:ego:)` —— 判定

**修改 `MotionPredictor.swift`（全部为增量插入）**
- `updateEgoMotion` 从「只存值」→「存值 + 中转光流」，**调用方 tick 无需改动**
- `applyObservation` 末尾追加判定（**不改** `velocityX/Y`、**不改** `consistentVelocityFrames`）
- `predict()` 外推条件追加第 4 项 `&& !egoBlocked` ← **单点生效，好回退**
- `reset()` / `pruneIfNeeded()` 追加 `egoVerdicts` 清理（防内存泄漏 + 防跨会话串味）

### 6.45.4 fail-open 纪律（本设计最重要的安全约束）

| 情形 | 行为 |
|---|---|
| 光流 nil（首帧 / 尺寸不符 / C 层 valid=0） | `estimate` → nil → **不拦截** |
| 光流幅值过大（转场/闪烁） | `estimate` → nil → **不拦截** |
| `dt` 非法（≤0 或 >0.5s） | `estimate` → nil → **不拦截** |
| 置信度低于阈值 | `verdict` → nil → **不拦截** |
| 观测位移过小（噪声级） | `verdict` → nil（模型"不发表意见"） |

**特别强调**：绝不能把"没有数据"当成"数据说没问题"，更不能当成"自车静止"——
后者会让预测器把运动中的目标**冻住**，是安全事故。
故所有不确定性一律**倾向于不拦截**。

另：漏检帧**不清除**既有判定（沿用上次结论）—— 漏检恰恰最需要拦截，
若每帧重算，拦截会在漏检帧之间反复抖动。

### 6.47.1 ★ 根因：`bpf7` 权限漏配导致定位引擎全程不可用（已修）

**症状**：`--tcc-selftest` 报 `权限状态: ready=false — BPF 设备无读写权限：/dev/bpf0...bpf6`。

**矛盾点**（这是破案的关键）：App 报 bpf0~6 都不可读写，但**手工 `ls -l` 看它们全是 `crw-rw-rw-`（666）**。

**真根因**：
- `/dev/bpfN` 由**内核按需创建**，每被打开一个就新建下一个；
- 守护脚本 `/usr/local/bin/aurora-bpf-setup.sh` 只处理**当时已存在**的设备；
- 实测：`bpf0~6` = 666 ✅，但 **`bpf7` = `crw-------`** ❌
- App 内 `BPFSetupManager.firstWritableBPFDevice()`（`BPFSetup.swift:29`）**逐个探测 0..<64，遇到第一个不可读写的就继续往后找**——逻辑本身是对的，但**当时 bpf7 之后没有可用的**，于是返回 nil ⟹ `ready=false`。

**更关键的第二层**：守护进程虽然 `launchctl list` 显示存在，但**实测已卡死**（PID 45965 活着却不干活，所以新出现的 bpf7 一直停在 `crw-------`）。

**修复动作**：
```bash
sudo launchctl kickstart -k system/com.aurora.bpf-setup   # 重启卡死的守护
```
**修复后实测**：`bpf0~8` 全部 `crw-rw-rw-`，App 报 **`ready=true — 网络权限 + 性能提权 均已就绪`** ✅

**⟹ 影响面**：在这之前所有"真机定位"数据都是**在定位引擎不可用状态下采的**。

## §6.48 2026-10-02 删除全部自动脱困/自动刹车（真机 bug 根因取证与修复）

> **用户原话**：「脱困的代码根本没删掉……疯狂脱困……托管中一直跟我抢……必须删掉所有托管代码
> 不能留任何脱困措施，脱困只能请求人工介入了」。
>
> **结论：用户判断正确。** 之前记录的「`.recover` 已整体删除」**只对了表象**——
> 档位枚举确实删了，但**自动刹车的执行链一直在跑**，只是不叫「脱困」。

### 6.48.1 ★ 真根因：第三视角下自车被当成障碍框 → 几何兜底误判碰撞

**用户自己定位的**（本节只做取证确认）：
> 「那个死模型我做的是第三视角自动驾驶……他妈的会把那个我自己当成障碍物」

**日志铁证**（`/tmp/aurora_debug.log`，2026-10-02 17:42–17:44，**3 分钟 27 次，每 2 秒一次**）：

```
几何兜底(框叠加): 框叠加碰撞（IoU/中心距超限）→ 紧急避让
  ego=(0.50,0.69,0.08,0.24)  other=(0.50,0.65,0.08,0.25)
  ↑ 两框中心同在 x=0.50（画面正中）、尺寸几乎相同 ⟹ 同一个自车被检测了两遍
  转向 -0.04→+0.19  油门 0.94→0.20  刹车 0.06→0.80
```

**为什么是"疯狂脱困"**：本游戏里 **`brake` 唯一的物理含义是按 S 键，而 S 键兼作倒车**
（`ControlEngine.KeyMap`：`brake = 1 = S`）。故 `brake 0.06→0.80` = **AI 自动挂倒挡**。

**为什么"一直抢"**：`FallbackGuard` 的施加点**不限定驾驶档位**（旧注释自称
「不限定 decided 状态」）。真机 tick 日志证明**连 `.e2e` 端到端主驾档也照劫不误**：

```
tick: mode=端到端主驾 m9Live=true assistLive=true conf=1.00
      cmd=(s=-0.26 t=0.20 b=0.80)   ← 模型完全健康，刹车仍被强行拉到 0.8
```
与正常帧 `cmd=(s=-0.03 t=0.94 b=0.06)` 交替出现 ⟹ **1~2 秒一次的方波**。

### 6.48.3 新增：卡死 30 秒 → 拉横幅请求人工介入（不自动脱困）

用户指定：
> 「如果那个发现那个连续 30 秒钟速度都为零，那么就直接拉横幅，但是**不要语音**」

  - 必须 `isDriving`，**等红灯不计时**。

- **UI**：`MissionConsole.StuckWarn`（新组件）→ `ViewportPanel` 顶部横幅，
  文案「车辆已卡住 Ns · 请人工介入接管」。**只显示，不发声**。
  与既有 `RCWarn` 互斥（卡死优先）。**符号已验证编入二进制**（`nm` 可见 `AA9StuckWarnV`）。
- 🚨 **纪律**：`needsManualIntervention` **只是提示位，绝不驱动任何控制量**。
  置位后 AI 不会刹车/倒车/脱困 —— 脱困的唯一途径是用户自己接管。
