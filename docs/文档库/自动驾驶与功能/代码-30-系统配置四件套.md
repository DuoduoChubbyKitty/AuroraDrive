## 一、PrivilegePill 应用内提权（「小药丸」，PrivilegePill.swift 全文 302 行）

**设计约束（文件头 9–27 行注释，用户 2026-09-23 明确要求）**：

- ❌ **绝对不用 macOS 原生授权弹窗**（`do shell script ... with administrator privileges`）——原生框每次都要手动输系统密码体验割裂；且一旦被系统判定「反复索要授权」会被 macOS 记为可疑行为，对开源项目声誉有害
- ✅ **必须应用内输入密码 → 后台静默提权**——用户看到 AuroraDrive 自己的玻璃弹窗，密码由用户自己填，**绝不硬编码**（旧实现写死 "123456"，发布版必然失效且是安全隐患）
- **技术路线 `sudo -S`**（密码从 stdin 读）——不写进 argv：`ps` 看不到；旧实现把密码拼进 AppleScript 字符串等于明文暴露在进程参数里
- **安全边界（如实说明，不粉饰）**：密码只在内存里存在，用完立即清空，不落盘、不写日志；提权动作严格限定为「安装一个 LaunchDaemon 脚本」这一件事；不做任何其它 root 操作

**`PrivilegeResult`（struct，31–34 行）**：`success: Bool + message: String`——安装结果如实回传。

**`PrivilegePill`（@MainActor final class，40–44 行）**：单例 `shared`。**「小药丸」的由来（38–39 行注释）**：顶栏那颗常驻胶囊按钮，绿=已授权、黄=待授权、红=授权失效；点它才弹密码框，不主动打扰用户。

**状态判定（46–70 行）：**

- **`isFullyAuthorized: Bool`（54–56 行）**——权限是否真的可用（不是「装过就算」）。判定依据分两层，**必须都满足**：① `BPFSetupManager.isBPFAvailable()`（抓包前提）② `PrioritySetupManager.isDaemonRunning()`（防冻结前提）。**只看其中一条会出现「界面显示已授权但功能不可用」的假绿状态**
- **`statusDetail: String`（59–70 行）**——授权状态描述（给 UI 显示真实原因，不显示笼统的「未授权」）：都就绪 → "网络权限 + 性能提权 均已就绪"；都不行 → "网络权限与性能提权均未就绪"；只 BPF 不行 → 进一步用 `lockedBPFDevices()` 列出具体锁死的设备（空 → "BPF 设备尚未创建（游戏未启动时属正常）"）；只提权不行 → "性能提权守护未运行"

**`install(password:) -> PrivilegeResult`（78–120 行）——提权安装主入口：**

1. `guard !password.isEmpty`——空密码直接拒绝
2. **一次性安装脚本写到 `/tmp/aurora_privilege_install.sh`（0o700）+ defer 删除**——⚠️ 关键设计：脚本里不写死任何密码，密码只用于 sudo 认证本身
3. `runSudo(password:, command: "/bin/bash \(tmpPath)")`
4. **失败分类（101–110 行）**：输出含 "incorrect password"/"sorry, try again" → "密码错误，请重新输入"；含 "not in the sudoers" → "当前账户不在管理员组，无法提权"；否则前 160 字符原文回传
5. **复核（112–119 行，不能只听脚本退出码）**：`isFullyAuthorized` → "权限已就绪，重启后自动生效"；BPF 可用 → "网络权限已就绪；性能提权守护稍后自启"；否则 → "已安装，请重启电脑后生效"

**`selfHeal() -> Bool`（124–133 行）——无需密码的自愈**：守护已装但当前未生效时直接 `launchctl kickstart -k system/com.aurora.bpf-setup` + `system/com.aurora.priority`（kickstart 不需要 root，守护本身以 root 注册在 system 域），用于「装过一次，但重启后新创建的 BPF 设备没被 chmod 到」场景。

**`runSudo(password:command:)`（138–168 行）——sudo -S 封装**：`/usr/bin/sudo -S -p "" /bin/bash -c <command>`（-S 从 stdin 读密码；-p "" 抑制提示串避免混进输出）→ 密码 + 换行写入 stdin 后立即关闭写端 → **输出读取放在 waitUntilExit 之前（避免管道写满死锁）** → 返回 (terminationStatus, output)。

**`installScript`（static let，198–301 行）——一次性安装脚本，装两个守护：**

**① BPF 权限守护（205–248 行）**——`/usr/local/bin/aurora-bpf-setup.sh` + `/Library/LaunchDaemons/com.aurora.bpf-setup.plist`：

- **为什么是常驻轮询而不是 RunAtLoad 一次性（193–197 行注释，关键设计）**：`/dev/bpfN` 是**内核按需动态创建**的，开机时往往还不存在（本机 /dev/bpf4 就是开机很久后才出现）。旧实现只在 RunAtLoad 跑一次 chmod，结果新创建的设备永远是 `crw-------`，抓包时好时坏——这正是「有时候能定位、有时候死活定位不到」的根因
- 脚本：`while true` → 遍历 `/dev/bpf*` → **只在权限不足时才 chmod 666**（避免每秒无谓的系统调用）→ sleep 3
- plist：Label com.aurora.bpf-setup + RunAtLoad + KeepAlive（崩溃自动拉起）+ ProcessType=Background + Nice=10；root:wheel 644

**② 性能提权守护（250–286 行）**——`/usr/local/bin/aurora-priority.sh` + `/Library/LaunchDaemons/com.aurora.priority.plist`：

- 脚本：`while true` → `ps -axo pid=,comm=` 精确匹配 `/AuroraDriveUI$`（**用 comm 而不是 pgrep -f——后者会误伤任何命令行含 "AuroraDriveUI" 的无关进程**）→ `renice -n -20 -p` → sleep 5
- plist：Label com.aurora.priority + RunAtLoad + KeepAlive + **ProcessType=Interactive + Nice=-20**（守护进程出生即最高）；root:wheel 644

**③ 加载（288–294 行）**：`launchctl bootout`（清旧，容错）→ `bootstrap system`（装新，现代 API——旧 load 在新系统已废弃）→ `kickstart -k`（立即跑）

**④ 立即生效一次（296–297 行）**：`chmod 666 /dev/bpf*`（不等守护的下个轮询周期）→ echo AURORA_PRIVILEGE_INSTALLED

## 二、DaemonSetupManager 权限服务编排器（DaemonSetup.swift 全文 114 行，9-23 大简化）

**背景（9–18 行注释）**："原「用户会话 XPC Agent」方案**已废弃**——实测 launchd 拉起的后台进程拿不到 TCC 权限（ax=false、screen=false），驾驶引擎改为由主程序 spawn 的子进程承担（沿进程链继承权限）。因此本文件只保留与驾驶无关的 BPF 权限服务（root LaunchDaemon），以及若干兼容旧调用点的空壳入口"。

**空壳入口（21–54 行）**：`isRunningAsDaemon()` 恒 false、`isDaemonInstalled()` 恒 false（Agent 方案废弃）、`needsInstall()` = `!isBPFAvailable()`、`install(password:currentExecutablePath:)` 保留 password 参数**但不读取**（兼容旧 UI）、`uninstall(password:)` 恒 (true, "无需卸载")、`currentExecutablePath()` 标准化路径。

**⚠️ `installBPFWithSystemAuthorization()` 已停用（58–65 行）**：原为 `do shell script ... with administrator privileges` 原生授权路径，用户明确要求不要原生授权，**现直接返回失败**："此路径已停用：请使用应用内提权（PrivilegePill），不要调用原生授权"。

**遗留工具（67–113 行）**：`shellQuote`（单引号转义）、`CommandResult` + `run(_:allowFailure:timeout:)`（带超时命令执行器）、`SetupError`（当前未被使用）——保留供参考，无活跃调用。

## 三、BPFSetupManager（BPFSetup.swift 全文 134 行）

**文件头（6–7 行）**：BPF 权限自动安装器——首次启动检测 BPF 权限，通过 App 内密码输入安装开机自启 LaunchDaemon；用户只需输一次密码，之后每次重启自动 chmod 666 /dev/bpf\*，永久无需再输。

**检测方法（2026-09-23 大修后）**：

| 方法 | 实现 | 说明 |
|---|---|---|
| `isBPFAvailable()` | `firstWritableBPFDevice() != nil` | **⚠️ 2026-09-23 修复（「小药丸弹不出来」的根因）**：旧实现只探测 `/dev/bpf0`，而它长期 666 → 恒返回 true → 上层判定「已授权」→ 密码弹窗永远不弹；但真正要用的设备（pcap 按需分配，可能是 bpf4/bpf5…）却是 `crw-------` →「界面显示已授权，实际抓不到包」。**正解：逐个探测所有已存在的 bpf 设备**，必须与 pcap 的真实分配行为对齐 |
| `firstWritableBPFDevice()` | for i in 0..<64，`access(O_RDWR)==0` 即命中 | **动态枚举**（pcap 内核按需创建，数量不固定，不能写死 0..3）；编号连续创建——遇到不存在的多扫 8 个再停（防中间空洞） |
| `lockedBPFDevices()` | 同上但收集不可读写项 | **诊断用**：让 UI 能如实说明卡在哪个设备（PrivilegePill.statusDetail 消费） |
| `isLaunchDaemonInstalled()` | plist 文件存在 | — |
| `isLaunchDaemonLoaded()` | `launchctl list \| grep` | ⚠️ 零调用（预留） |
| `needsInstall()` | `!isBPFAvailable() && !isLaunchDaemonInstalled()` | — |
| `needsLoad()` | `isLaunchDaemonInstalled() && !isLaunchDaemonLoaded()` | ⚠️ 零调用（预留） |

**⚠️ `install(password:)` 已停用（87–101 行）**：原为 AppleScript 密码经参数传的安装路径——两个致命问题：① 密码硬编码/明文进 argv（ps 可见）；② 走 macOS 原生授权弹窗（用户明确禁止）。**deprecated，调用即返回失败**："此路径已停用：请使用应用内提权（PrivilegePill）"。

**`tryImmediateChmod()`（104–115 行）**：`launchctl start com.aurora.bpf-setup` + sleep 1 + 验证——已装未 chmod 时补救（不需要密码）。

**`loadDaemonIfNeeded()`（118–133 行)**：已安装未加载时 `launchctl load + start`——⚠️ 零调用（预留）。

## 四、PrioritySetupManager（PrioritySetup.swift 全文 74 行，大幅简化）

**背景（4–19 行注释）**："游戏开 Game Mode 后同为 userInteractive QoS，**同级竞争时系统偏心前台游戏**，AuroraDrive 的推理线程被挤到效率核 → 卡顿。用户态 QoS 已拉满（userInteractive 是天花板），要再高只能走 root nice -20"。机制说明保留（安装的脚本内容现在由 PrivilegePill.installScript 承担）。安全性："只 renice 自己名字的进程，不碰其他任何进程"。

**现存接口（25–73 行）**：

| 成员 | 说明 |
|---|---|
| `scriptPath/plistPath/serviceLabel` | `/usr/local/bin/aurora-priority.sh`、`/Library/LaunchDaemons/com.aurora.priority.plist`、`com.aurora.priority` |

| `isRunning()` | `pgrep -f aurora-priority.sh`——**实测进程存在（plist 装过 ≠ 守护在跑）** |

## 五、GameModeDefender 持久战（GameModeDefender.swift 全文 178 行，9-25 复核无变化）

**引用关系**：`GameModeDefender.shared.start()` 两个调用方——EngineMain:493（引擎侧）+ AuroraDriveApp（UI 侧，applicationDidFinishLaunching）。

**文件头（4–24 行）**：对抗 Game Mode 压制。背景（2026-09-13 实测）：游戏全屏 Game Mode 后辅助帧率维持 30fps 约 40 秒，随后被 gamepolicyd 压过去（掉个位数）→ **教训：一次性设防不够，会被逐步压制**。两条互补措施：

1. **静音音频（audible 维度）**：App Nap 判定条件之一是「it isn't audible」→ 播音频是独立豁免项；**CoreAudio 音频线程是实时优先级且不需要 root**（绕过「设实时线程要 root」的门）；AudioQueue 零采样循环，不需要 NSApplication（引擎进程也可用）
2. **持续重新主张**：每 3 秒复查 nice/activity token/音频队列，被改动就立刻设回并落盘日志

**日志**：`/tmp/aurora_defender.log`（无封顶，A/B 对比需要完整历史）。

**`start()`（70–75 行，幂等）** → startSilentAudio + startReassertLoop：

- **静音音频（87–126 行）**：44100Hz LinearPCM signed/packed 2ch×16bit → AudioQueueNewOutput → **两块 0.25s（11025 帧）零填充静音 buffer**（memset = 绝对无声）→ callback 重新入队形成无限循环（C 回调不捕获上下文）→ AudioQueueStart
- **重新主张循环（130–177 行）**：3s 定时器（leeway 200ms）→ `reassert()`：① `getpriority != -20` → setpriority 设回；② napToken 被释放 → 重新 beginActivity；③ 音频队列被停（`kAudioQueueProperty_IsRunning == 0`）→ AudioQueueStart 重启 / 未启动 → 补启。日志节流：有修复才记，无修复每分钟（第 21/41/61…次）记一条"稳态"
