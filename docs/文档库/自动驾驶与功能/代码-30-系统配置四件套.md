## 二、BPFSetupManager（BPFSetup.swift 全文 162 行）

**引用关系（grep 实测）**：`needsInstall/isBPFAvailable/isLaunchDaemonInstalled/tryImmediateChmod` 调用方 = ContentView.onAppear:2248–2259 + DaemonSetupManager（三处：29/40/109）；`install(password:)` 唯一调用方 = BPFPasswordSheet:2767；**`isLaunchDaemonLoaded()/needsLoad()/loadDaemonIfNeeded()` 零调用**（预留）。

**文件头（6–7 行）**：**BPF 权限自动安装器：首次启动检测 BPF 权限，通过 App 内密码输入安装开机自启 LaunchDaemon。用户只需输入一次密码，之后每次重启自动 chmod 666 /dev/bpf\*，永久无需再输**。

**检测方法（第 10–42 行）：**

| 方法 | 实现 | 说明 |
|---|---|---|
| `isBPFAvailable()` | `"/dev/bpf0".withCString { access($0, O_RDWR) } == 0` | **BPF 是否可读写**（纯系统调用，零子进程） |
| `isLaunchDaemonInstalled()` | `FileManager.fileExists("/Library/LaunchDaemons/com.aurora.bpf-setup.plist")` | LaunchDaemon 是否已安装 |
| `isLaunchDaemonLoaded()` | `sh -c "launchctl list \| grep -q com.aurora.bpf-setup"` | **LaunchDaemon 是否已加载（真正运行）**——⚠️ 零调用 |
| `needsInstall()` | `!isBPFAvailable() && !isLaunchDaemonInstalled()` | 需要安装吗？（BPF 不可用 且 未装） |
| `needsLoad()` | `isLaunchDaemonInstalled() && !isLaunchDaemonLoaded()` | 需要启动吗？（已安装但未加载）——⚠️ 零调用 |

**`install(password:)`（第 47–129 行）——写 setup 脚本到 /tmp，然后用 AppleScript 以管理员权限运行**：

1. **内嵌脚本（49–83 行）**：`/usr/local/bin/aurora-bpf-setup.sh`（**内层只做 `chmod 666 /dev/bpf*`**，755）+ `/Library/LaunchDaemons/com.aurora.bpf-setup.plist`（**Label com.aurora.bpf-setup + ProgramArguments [/bin/sh, /usr/local/bin/aurora-bpf-setup.sh] + RunAtLoad=true**，root:wheel 644）+ `launchctl load` + 立即 chmod + `echo "BPF_SETUP_DONE"`
2. **脚本写入（85–92 行）**：`/tmp/aurora_bpf_setup.sh`（atomic 写 + 0o755）；失败 → "写脚本失败"
3. **授权执行（94–101 行）**：**用 AppleScript 以管理员权限运行 setup 脚本（不弹系统弹窗，密码通过参数传）**——`do shell script "bash /tmp/aurora_bpf_setup.sh" password "密码" with administrator privileges`（**escapedPwd：反斜杠+双引号转义**）→ `/usr/bin/osascript -e` + Pipe
4. **结果（111–125 行）**：status == 0 → isBPFAvailable ? "BPF 权限已安装，开机自动生效" : **"LaunchDaemon 已安装，请重启电脑后生效"**（双分支：立即生效 vs 重启生效）；非 0 → errMsg 含 "Authentication"/"password" → **"密码错误"**；否则 "安装失败: …"
- catch → "执行失败"

**⚠️ 安全性标注（诚实）**：**密码经 AppleScript argv 参数传递**——argv 在进程列表里对同机其他用户进程可见（ps -ef），**不如 DaemonSetup 的系统原生授权对话框安全**；且脚本里 `password "\(escapedPwd)"` 写进 osascript 参数串。这是当前 UI 实际走的路径（BPFPasswordSheet）。

**`tryImmediateChmod()`（第 132–143 行）——尝试立即 chmod BPF（不需要密码，如果 LaunchDaemon 已装但 BPF 还没 chmod）**：

- `sh -c "launchctl start com.aurora.bpf-setup 2>/dev/null; sleep 1; test -r /dev/bpf0"`——**kickstart 服务 + 等 1s + 验证可读**
- 返回 `terminationStatus == 0 && isBPFAvailable()`——**双条件：服务启动成功 + BPF 实际可读**
- **调用方 = ContentView.onAppear:2258**（isLaunchDaemonInstalled 分支：已装未 chmod 时补救）

**`loadDaemonIfNeeded()`（第 146–161 行）——启动 LaunchDaemon（如果已安装但未加载）**：

- `guard isLaunchDaemonInstalled` + `guard !isLaunchDaemonLoaded`
- `sh -c "launchctl load … 2>/dev/null; launchctl start … 2>/dev/null"` → `terminationStatus == 0 && isLaunchDaemonLoaded()`
- **⚠️ 零调用**——needsLoad/isLaunchDaemonLoaded 同样零调用（预留：若 UI 加"启动服务"按钮可用）

## 三、PrioritySetupManager（PrioritySetup.swift 全文 157 行）

**引用关系（grep 实测）**：`isLaunchDaemonInstalled` 调用方 = ContentView.onAppear:2248/2252（与 BPF 合并首条件）；`install(password:)` 唯一调用方 = BPFPasswordSheet:2769（**同一密码顺带装性能提权，无需额外按钮**）；`isRunning()/currentNice(pid:)` **零调用**（诊断预留）。

**文件头（4–19 行）——AuroraDrive 性能提权器（root 级 renice 守护）**：

- **背景（7–9 行注释）**："游戏开 Game Mode 后同为 userInteractive QoS，**同级竞争时系统偏心前台游戏，AuroraDrive 的推理线程被挤到效率核 → 卡顿。用户态 QoS 已拉满（userInteractive 是天花板），要再高只能走 root nice -20**"
- **机制（11–16 行）**："（与 BPFSetup 相同的密码模式）：用户输入一次管理员密码 → 1) 安装 /usr/local/bin/aurora-priority.sh（root 常驻循环）**每 5 秒把 AuroraDriveUI（含 --engine 引擎子进程）renice 到 -20——比游戏（nice 0）高一头，内核调度永远优先喂我们**；2) 安装 /Library/LaunchDaemons/com.aurora.priority.plist（**RunAtLoad + KeepAlive：开机自启、崩溃自动拉起、新进程 5 秒内自动跟随**）"
- **安全性（18 行）**："**只 renice 自己名字的进程，不碰其他任何进程**"

**常量与检测（第 25–46 行）：**

| 成员 | 值 | 说明 |
|---|---|---|
| `scriptPath` | `/usr/local/bin/aurora-priority.sh` | 常驻 renice 守护脚本 |
| `plistPath` | `/Library/LaunchDaemons/com.aurora.priority.plist` | LaunchDaemon 配置 |

| `isRunning()` | `sh -c "pgrep -f aurora-priority.sh >/dev/null"` | **守护进程是否正在运行**——⚠️ 零调用（install 内部用它做验证） |

**`install(password:)`（第 49–142 行）——安装（需要管理员密码）。模式与 BPFSetupManager.install 完全一致**：

1. **内嵌脚本（51–100 行）**：
   - **aurora-priority.sh（56–66 行）**：`while true` 常驻循环——**用 ps comm（可执行文件路径）精确匹配，不用 pgrep -f——后者会误伤任何命令行含 "AuroraDriveUI" 的无关进程（终端/编辑器/诊断命令）**：`for pid in $(ps -axo pid=,comm= \| awk '$2 ~ /\\/AuroraDriveUI$/ {print $1}')` → `renice -n -20 -p "$pid"` → sleep 5
   - **plist（70–92 行）**：Label com.aurora.priority + ProgramArguments [/bin/bash, aurora-priority.sh] + **RunAtLoad + KeepAlive + ProcessType=Interactive + Nice=-20**（**plist 自身 Nice=-20：守护进程出生即最高**）——root:wheel 644
   - **卸旧加载新（96–99 行）**：launchctl unload（容错）→ `load -w` → echo PRIORITY_INSTALLED
2. **脚本写入（101–107 行）**：`/tmp/aurora_priority_setup.sh`（0o755）；失败 → "写脚本失败"
3. **授权执行（109–121 行）**：同 BPFSetup——`do shell script "bash …" password "…" with administrator privileges`（密码经参数传）→ osascript + Pipe
4. **结果（126–138 行）**：status == 0 → isRunning() ? **"性能提权已生效：AuroraDrive 全家已锁定 nice -20（重启后自动跟随）"** : "LaunchDaemon 已安装（重启电脑后自动生效）"；密码错 → "密码错误"；失败 → "安装失败"
- catch → "执行失败"

## 四、GameModeDefender 持久战（GameModeDefender.swift 全文 178 行）

**引用关系（grep 实测）**：`GameModeDefender.shared.start()` 两个调用方——EngineMain:469（引擎侧）+ AuroraDriveApp:184（UI 侧，applicationDidFinishLaunching）；单例 `static let shared`（32 行）。

**文件头（4–24 行）——对抗 Game Mode 压制的「持久战」组件**：

- **背景（7–9 行注释，2026-09-13 实测）**："游戏全屏进入 Game Mode 后，AuroraDrive 的辅助帧率能维持 30fps 约 40 秒，随后被 gamepolicyd 压过去（掉到个位数）→ **教训：一次性设防（启动时设 nice / 拿 activity）不够，会被逐步压制**"
- **两条互补措施（11–21 行）**：
  1. **静音音频（audible 维度）**："Apple 文档：App Nap 判定条件之一是「it isn't audible」→ 播音频是独立豁免项；Game Mode 很可能沿用同类评估维度。**CoreAudio 的音频线程是实时优先级且不需要 root——这绕过了我们此前卡住的「设实时线程要 root」那道门。用 AudioQueue 输出零采样循环，不需要 NSApplication（引擎进程也可用）**"
  2. **持续重新主张（打持久战）**："每 3 秒复查：本进程 nice 是否仍是 -20、activity token 是否仍持有，被改动就立刻设回去并落盘日志。**对「40 秒后被压过去」这类渐进压制，这是最对症的手段**"
- **日志（23 行）**：`/tmp/aurora_defender.log`（**便于 A/B 对比与事后取证**）

**状态（第 37–48 行）**：logPath / audioQueue: AudioQueueRef? / audioBuffers: [AudioQueueBufferRef] / timer（DispatchSourceTimer）/ napToken / reassertCount / audioActive；**`role`（计算属性）**："ENGINE" / "UI"（日志前缀——CommandLine.arguments 判定）。

**`log(_:)` + `ts()`（第 50–65 行）**：追加写（FileHandle seekToEnd / 文件不存在 createFile）——**`[ENGINE]/[UI]` + `[HH:mm:ss.SSS]` 前缀**；**注意：此日志无 10MB 封顶（DriveState.dlog 有）——持久战日志靠人工清（A/B 对比需要完整历史，未封顶是有意取舍）**。

**`start()`（第 70–75 行）——启动全部对抗措施（幂等）**：`guard timer == nil`（防重复启动）→ log"─ 持久战启动：静音音频 + 每 3s 重新主张 ─" → **startSilentAudio() + startReassertLoop()**。

**措施 1：静音音频（第 77–126 行）——AudioQueue，不依赖 NSApplication：**

- **`audioCallback`（static let，C 回调，81–85 行）**："**用全局函数指针（C 回调不能捕获上下文），通过 inUserData 拿回自身**"——**重新入队同一块已清零的 buffer → 持续「正在播放」状态**：`AudioQueueEnqueueBuffer(queue, buffer, 0, nil)`
- **`startSilentAudio()`（87–126 行）**：
  - **格式（88–97 行）**：44100Hz + LinearPCM + **signed integer | packed + 2ch × 16bit（mBytesPerFrame=4）**——标准双声道
  - `AudioQueueNewOutput(&format, callback, nil, nil, nil, 0, &queue)`——失败 → log"✗ 静音音频启动失败（status=N）" + return
  - **两块 0.25 秒的静音 buffer（106–117 行）**：`framesPerBuffer = 11025`（44100/4）→ 循环 2 次——AudioQueueAllocateBuffer + **memset 零填充（= 绝对无声）** + AudioQueueEnqueueBuffer；成功入 audioBuffers
  - `AudioQueueStart(q, nil)`——成功 → audioQueue/audioActive + log"✓ 静音音频已启动（AudioQueue 2×11025 帧零采样循环；**audible=活跃 + CoreAudio 实时线程**）"；失败 → log"✗"

**措施 2：持续重新主张（第 128–177 行）：**

- **`startReassertLoop()`（130–137 行）**：DispatchQueue（"aurora.defender", .userInteractive）+ DispatchSourceTimer（**3s 间隔，leeway 200ms**——低精度容差让系统合并唤醒）→ reassert()
- **`reassert()`（139–177 行）——复查并重新主张所有可被系统改动的防护项**：
  - **① nice（144–149 行）**：`getpriority(PRIO_PROCESS, 0)` != -20 → `setpriority(-20)` → fixes.append("nice N → -20")
  - **② activity token（152–157 行）**：napToken == nil（被释放）→ `beginActivity([.latencyCritical, .userInteractive, .idleSystemSleepDisabled], reason: "AuroraDrive Game Mode 对抗：重新主张防冻结")` → fixes.append("重新取得 activity token")
  - **③ 静音音频（160–169 行）**：队列存在且 audioActive → **`AudioQueueGetProperty(kAudioQueueProperty_IsRunning)` == 0 时 AudioQueueStart 重启**（fixes.append"静音音频被停 → 已重启"）；**`!audioActive` 时 startSilentAudio 补启**（fixes.append"静音音频补启"）
  - **日志节流（171–176 行）**：reassertCount += 1；有修复 → log"⚔ 重新主张：…（第 N 次复查）"；无修复 → **`reassertCount % 20 == 1` 每分钟记一次"稳态"**——"稳态：nice=N audio=true 复查第 N 次"
