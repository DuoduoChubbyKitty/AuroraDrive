## 一、PrivilegePill 应用内提权（「小药丸」，PrivilegePill.swift 全文件）

**设计约束（文件头与类注释，用户 2026-09-23 明确要求）**：

- ❌ **绝对不用 macOS 原生授权弹窗**（`do shell script ... with administrator privileges`）——原生框每次都要手动输系统密码体验割裂；且一旦被系统判定「反复索要授权」会被 macOS 记为可疑行为，对开源项目声誉有害
- ✅ **必须应用内输入密码 → 后台静默提权**——用户看到 AuroraDrive 自己的玻璃弹窗，密码由用户自己填，**绝不硬编码**
- **技术路线 `sudo -S`**（密码从 stdin 读）——不写进 argv：`ps` 看不到；旧实现把密码拼进 AppleScript 字符串等于明文暴露在进程参数里
- **安全边界（如实说明，不粉饰）**：密码只在内存里存在，用完立即清空，不落盘、不写日志；提权动作严格限定为「安装两个 LaunchDaemon 脚本」这一件事；不做任何其它 root 操作

**`PrivilegeResult`（struct，Sendable）**：`success: Bool` + `message: String`——安装结果如实回传。

**`PrivilegePill`（`final class PrivilegePill: Sendable`）**：单例 `static let shared` + `private init()`。**「小药丸」的由来**：顶栏那颗常驻胶囊按钮，绿=已授权、黄=待授权、红=授权失效；点它才弹密码框，不主动打扰用户。

**状态判定：**

- **`isFullyAuthorized: Bool`**——权限是否真的可用（不是「装过就算」）。判定依据分两层，**必须都满足**：① `BPFSetupManager.isBPFAvailable()`（抓包前提）② `PrioritySetupManager.isDaemonRunning()`（防冻结前提）。**只看其中一条会出现「界面显示已授权但功能不可用」的假绿状态**
- **`statusDetail: String`**——授权状态描述（给 UI 显示真实原因，不显示笼统的「未授权」）。内部走 `cachedStatusDetail`（`OSAllocatedUnfairLock`，2 秒记忆化）→ 过期才调 `computeStatusDetail()`；`invalidateStatusCache()` 在安装/自愈后立即作废缓存（避免「点了没反应」的观感）。`computeStatusDetail()` 的分支：BPF 不可用 → 用 `BPFSetupManager.lockedBPFDevices()` 列出具体锁死设备；为空 → 「BPF 设备尚未创建（游戏未启动时属正常）」；含 `EPERM` → 「系统策略拒绝 BPF 读写（EPERM）…请从未受沙盒限制的 macOS 终端启动 AuroraDrive」；否则「BPF 设备无读写权限：<paths>」。BPF 可用时再看 `PrioritySetupManager.isDaemonRunning()`：就绪 → 「网络权限 + 性能提权 均已就绪」，否则 「性能提权守护未运行」
- **为什么加 2 秒缓存（类注释完整记录）**：`PermissionPill.body` 每 tick 重算，原先每秒 30 次 × 最多 64 次系统调用（`fileExists` + `access`）≈ 2000 次/秒砸在 UI 主线程 → 「一打开就卡得离谱」。`sample` 实测主线程 81.4% 耗在这颗药丸的 body。权限状态是「人手操作才会变」的量，2 秒陈旧度足够，系统调用降到 ~1 次/2 秒

**`install(password: String) -> PrivilegeResult`——提权安装主入口：**

1. `guard !password.isEmpty`——空密码直接返回「请输入管理员密码」
2. 在 `Self.processQueue`（私有串行队列，`qos: .utility`）上执行，`defer { invalidateStatusCache() }`
3. `runSudo(password:)` 执行 `Self.installScript`（脚本本身不写死任何密码，密码只用于 sudo 认证）
4. **失败分类**（按 stderr 小写匹配）：含 "incorrect password"/"sorry, try again" → 「密码错误，请重新输入」；含 "not in the sudoers" → 「当前账户不在管理员组，无法提权」；含 "effective uid is not 0"/"no new privileges" → 「当前启动环境限制 sudo 提权。请从未受沙盒限制的 macOS 终端启动 AuroraDrive」；否则「提权失败（退出码 N）：<输出前 200 字符>」（**输出里的密码会被替换成 `•••`** 再回传）
5. **复核（不能只听脚本退出码）**：RunAtLoad 由 launchd 异步启动，`install` 给守护一个最多 2 秒的就绪窗口（`systemUptime + 2.0`，每 0.1s 复查 `isFullyAuthorized`）；就绪 → 「系统服务安装成功，网络权限和性能提权已就绪」；超时 → 「权限复核失败。<computeStatusDetail()>」

**`selfHeal() -> Bool`——无需密码的自愈**（`@discardableResult`）：守护已装但当前未生效时，`run("/bin/launchctl", ["kickstart", "-k", "system/com.aurora.bpf-setup"], timeout: 8)` + 同样方式拉起 `com.aurora.priority`，最后返回 `isFullyAuthorized`（kickstart 不需要 root，守护本身以 root 注册在 system 域）。用于「装过一次，但重启后新创建的 BPF 设备没被 chmod 到」场景。

**`selfHealAsync() async -> Bool`（P-4 修复新增）**：把两次 kickstart 整段挪到 `processQueue` 上跑（`withCheckedContinuation`），完成后 `invalidateStatusCache()` 并读一次 `isFullyAuthorized`。为什么需要它：`selfHeal()` 是同步的，调用方（`MissionConsole` 的 `Task { @MainActor in ... }`）在主线程调它就仍会被占住，最坏 16 秒。

**`runSudo(password: String) -> (status: Int32, output: String)`——sudo -S 封装**：`/usr/bin/sudo` + `["-S", "-k", "-p", "", "--", "/bin/bash", "-c", Self.installScript]`（-S 从 stdin 读密码；-p "" 抑制提示串避免混进输出）→ 对 stdin 设 `F_SETNOSIGPIPE`（sudo 可能在读密码前退出，写入失败时保留它的错误输出）→ 密码 + 换行写入 stdin 后立即关闭写端 → **输出读取放在 `waitUntilExit()` 之前（避免管道写满死锁）** → 返回 (terminationStatus, 去首尾空白的输出)。

**子进程执行体（P-4 重写）**：

- `run(_ path: String, _ args: [String], timeout: TimeInterval) -> Int32`：只负责「切到 `processQueue`」，实现只有一份（`runOnQueue`）——避免 `selfHeal()` 与 `selfHealAsync()` 各写一份逻辑迟早分叉
- `runOnQueue(_:_:timeout:) -> Int32`：**事件驱动，不忙等**——`task.terminationHandler` + `DispatchGroup`，超时用 `asyncAfter` 投递「到点强杀」的 `DispatchWorkItem`（不占线程、零 CPU）。原实现是 50ms 一轮 `usleep` 自旋，最坏 16 秒主线程被占（用户感知为「卡死」）。注意该方法**不自己** `processQueue.sync`（`selfHealAsync` 已在队列上，再 sync 会同队列重入死锁）

**`installScript`（private static let，多行 bash 脚本）——一次性安装脚本，装两个守护：**

1. `set -euo pipefail` + 固定 `PATH`；`stage_dir=$(mktemp -d /private/var/run/aurora-install.XXXXXXXX)` + `trap 'rm -rf "$stage_dir"' EXIT` 暂存并保证清理
2. **① BPF 权限守护**：写 `aurora-bpf-setup.sh` 与 `com.aurora.bpf-setup.plist`——脚本 `while true` 遍历 `/dev/bpf*`，**用 `stat -f '%Lp'` 读八进制权限位、非 `666` 才 `chmod 666`**（源码注释：本脚本以 root 运行，root 对 `crw-------` 永远可读写，用 `test -r/-w` 判断恒为假 → 一次 chmod 都不会执行，这是「小地图又没法用了」的第二层根因），`sleep 3` 常驻轮询（RunAtLoad 一次性 chmod 覆盖不到后来由内核创建的设备）。plist：Label `com.aurora.bpf-setup` + RunAtLoad + KeepAlive + ProcessType=Background + Nice=10
3. **② 性能提权守护**：写 `aurora-priority.sh` 与 `com.aurora.priority.plist`——脚本 `while true` 用 `ps -axo pid=,comm=` + `awk '$2 ~ /\/AuroraDriveUI$/ {print $1}'` 精确匹配（**用 comm 而不是 `pgrep -f`——后者会误伤任何命令行含 "AuroraDriveUI" 的无关进程**）→ `renice -n -20 -p` → `sleep 5`。plist：Label `com.aurora.priority` + RunAtLoad + KeepAlive + **ProcessType=Interactive + Nice=-20**（守护进程出生即最高）
4. **③ 校验与落盘**：`plutil -lint "$stage_dir/"*.plist` → `mkdir -p /usr/local/bin /Library/LaunchDaemons` → `install -o root -g wheel -m 755 ...sh /usr/local/bin/`、`install -o root -g wheel -m 644 ...plist /Library/LaunchDaemons/`
5. **④ 加载**：对两个 service 循环——`launchctl print "system/$service"` 成功则先 `launchctl bootout "system/$service"`（清旧，容错）→ `launchctl bootstrap system "/Library/LaunchDaemons/$service.plist"`（现代 API，旧 `load` 已废弃）
6. **⑤ 立即生效一次**：遍历 `/dev/bpf*`，`[[ -c "$dev" ]]` 时 `chmod 666`（不等守护的下个轮询周期）

## 二、DaemonSetupManager 权限服务状态入口（DaemonSetup.swift 全文件）

**`struct DaemonSetupManager` 现有三个静态入口**：

| 入口 | 实现 | 说明 |
|---|---|---|
| `isRunningAsDaemon()` | `false` | 旧 UI 兼容：引擎架构已不再有 daemon 模式 |
| `isDaemonInstalled()` | `BPFSetupManager.isLaunchDaemonInstalled() && PrioritySetupManager.isLaunchDaemonInstalled()` | 两个 LaunchDaemon 都装才算装 |
| `needsInstall()` | `!isDaemonInstalled() \|\| !PrivilegePill.shared.isFullyAuthorized` | 未装，或装了但权限实际不可用 |

## 三、BPFSetupManager（BPFSetup.swift 全文件）

**文件头**：BPF 权限自动安装器——首次启动检测 BPF 权限，通过 App 内密码输入安装开机自启 LaunchDaemon；用户只需输一次密码，之后每次重启自动 chmod 666 `/dev/bpf*`，永久无需再输。

**检测与查询入口（全部为 `static func`）：**

| 方法 | 实现 | 说明 |
|---|---|---|
| `isBPFAvailable()` | `firstWritableBPFDevice() != nil` | **⚠️ 2026-09-23 修复（「小药丸弹不出来」的根因）**：旧实现只探测 `/dev/bpf0`，而它长期 666 → 恒返回 true → 上层判定「已授权」→ 密码弹窗永远不弹；但真正要用的设备（pcap 按需分配，可能是 bpf4/bpf5…）却是 `crw-------` →「界面显示已授权，实际抓不到包」。**正解：逐个探测所有已存在的 bpf 设备** |
| `firstWritableBPFDevice() -> String?` | `for i in 0..<64`，`fileExists` + `access($0, O_RDWR) == 0` 即命中 | **动态枚举**（pcap 内核按需创建，数量不固定，不能写死 0..3）；编号连续创建——遇到不存在的多扫 8 个再停（`if i > 8 { break }`，防中间空洞） |
| `lockedBPFDevices() -> [(path: String, error: Int32)]` | 同上但收集不可读写项的 errno | **诊断用**：让 UI 能如实说明卡在哪个设备（`PrivilegePill.computeStatusDetail()` 消费，EPERM 有专门文案） |
| `isLaunchDaemonInstalled()` | `/Library/LaunchDaemons/com.aurora.bpf-setup.plist` 存在 | — |
| `isLaunchDaemonLoaded()` | `sh -c "launchctl list \| grep -q com.aurora.bpf-setup"` | ⚠️ 零调用（预留） |
| `needsInstall()` | `!isBPFAvailable() && !isLaunchDaemonInstalled()` | — |
| `needsLoad()` | `isLaunchDaemonInstalled() && !isLaunchDaemonLoaded()` | ⚠️ 零调用（预留） |
| `tryImmediateChmod()` | `launchctl start com.aurora.bpf-setup` + `sleep 1` + `test -r /dev/bpf0`，再复查 `isBPFAvailable()` | 已装未 chmod 时补救（不需要密码） |
| `loadDaemonIfNeeded()` | 未装返回 false、已加载返回 true；否则 `launchctl load` + `launchctl start` 后复查 `isLaunchDaemonLoaded()` | ⚠️ 零调用（预留） |

> ⚠️ 本文件**已无** `install(password:)`——原安装入口随提权收口到 `PrivilegePill` 一并删除（全仓 grep 零命中），不是 deprecated 占位。

## 四、PrioritySetupManager（PrioritySetup.swift 全文件）

**背景（文件头注释）**：游戏开 Game Mode 后同为 userInteractive QoS，**同级竞争时系统偏心前台游戏**，AuroraDrive 的推理线程被挤到效率核 → 卡顿。用户态 QoS 已拉满（userInteractive 是天花板），要再高只能走 root nice -20。机制说明保留（安装的脚本内容现在由 `PrivilegePill.installScript` 承担）。安全性：「只 renice 自己名字的进程，不碰其他任何进程」。

**`enum PrioritySetupManager` 现存接口：**

| 成员 | 说明 |
|---|---|
| `scriptPath/plistPath/serviceLabel`（static let） | `/usr/local/bin/aurora-priority.sh`、`/Library/LaunchDaemons/com.aurora.priority.plist`、`com.aurora.priority` |
| `isLaunchDaemonInstalled()` | plist 存在 |
| `isRunning()` | 跑 `/bin/launchctl print system/<serviceLabel>` 并解析输出中是否存在 `state = running` ——**实测服务状态（plist 装过 ≠ 守护在跑）**；stderr 丢弃到 `FileHandle.nullDevice` |
| `isDaemonRunning()` | `isRunning()` 的**语义化别名**（供 `PrivilegePill.isFullyAuthorized` 双条件判定用） |
| `currentNice(pid:) -> Int32?` | `sysctl(CTL_KERN, KERN_PROC, KERN_PROC_PID)` → `kinfo.kp_proc.p_nice`（诊断用；-20 = 提权生效） |

> ⚠️ 本文件**已无** `install(password:)`（同 BPFSetupManager：安装统一走 `PrivilegePill`），且 `isRunning()` 已从 `pgrep -f aurora-priority.sh` 改为 `launchctl print` 判据。

## 五、GameModeDefender 持久战（GameModeDefender.swift 全文件）

**引用关系**：`GameModeDefender.shared.start()` 两个调用方——`EngineMain.run()`（引擎侧）+ `AuroraDriveApp`（UI 侧，applicationDidFinishLaunching）。`final class GameModeDefender` + `static let shared` + `private init()`。

**文件头**：对抗 Game Mode 压制。背景（2026-09-13 实测）：游戏全屏 Game Mode 后辅助帧率维持 30fps 约 40 秒，随后被 gamepolicyd 压过去（掉个位数）→ **教训：一次性设防不够，会被逐步压制**。两条互补措施：

1. **静音音频（audible 维度）**：App Nap 判定条件之一是「it isn't audible」→ 播音频是独立豁免项；**CoreAudio 音频线程是实时优先级且不需要 root**（绕过「设实时线程要 root」的门）；AudioQueue 零采样循环，不需要 NSApplication（引擎进程也可用）
2. **持续重新主张**：每 3 秒复查 nice/activity token/音频队列，被改动就立刻设回并落盘日志

**日志**：`logPath = "/tmp/aurora_defender.log"`，行前缀 `[ENGINE]`/`[UI]`（`role` 按 `CommandLine.arguments.contains("--engine")` 判定）+ `HH:mm:ss.SSS`（`Self.ts()`）。**新增轮转**：`logMaxBytes = 8MB`，超限把当前文件挪 `.1`（覆盖旧备份）后重建——与 `CoordinateCapture.pcapLog` 同策略（24/7 挂机下「纯追加无上限」会无限增长）；本类写入频率极低，故每次写前检查、不做节流。

**`start()`（幂等，`guard timer == nil`）** → `startSilentAudio()` + `startReassertLoop()`：

- **`startSilentAudio()`**：`AudioStreamBasicDescription`（44100Hz / `kAudioFormatLinearPCM` / signed+packed / 2ch×16bit）→ `AudioQueueNewOutput`（回调 `Self.audioCallback`：C 回调不能捕获上下文，通过 `inUserData` 拿回自身，播完再次 `AudioQueueEnqueueBuffer` 形成无限循环）→ **两块 0.25s（11025 帧）零填充静音 buffer**（`memset` = 绝对无声）→ `AudioQueueStart`；成功置 `audioQueue`/`audioActive`
- **`startReassertLoop()`**：`DispatchSource.makeTimerSource`（queue `aurora.defender`，`qos: .userInteractive`）+ `schedule(deadline: .now() + 3, repeating: 3.0, leeway: .milliseconds(200))` → `reassert()`
- **`reassert()`**：① `getpriority(PRIO_PROCESS, 0) != -20` → `setpriority` 设回；② `napToken == nil` → 重新 `beginActivity(options: [.latencyCritical, .userInteractive, .idleSystemSleepDisabled], reason: ...)`；③ 音频队列被停（`AudioQueueGetProperty(q, kAudioQueueProperty_IsRunning, ...)` 得 0）→ `AudioQueueStart` 重启，未启动（`!audioActive`）→ 补启。日志节流：`fixes` 非空才记「⚔ 重新主张…（第 N 次复查）」；无修复时只在观测快照（`lastSteadySnapshot`）变化时追加一行「稳态」（2026-10-04 改，旧实现是每分钟固定写一行完全相同的内容）
