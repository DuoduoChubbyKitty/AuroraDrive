## 一、结论摘要（先看这个）

### 最终方案

```
数据采集:  游戏内设追踪路点 → 专家模式 → 一键录制 → 正常开车
           （采集 100% 自动，控制标签由「按住时长换算」自动生成）

模型架构:  照搬 FH6 VisionAI 的「几何接口」设计
           主干 ResNet-18 + 三帧堆叠 → fc1(256) →
             ├─ 早期分叉(不看车速): line(3) + waypoint(9×2)   ← 路线几何
             └─ 晚期分叉(融合车速): wpspeed(9) + slip(6)
           控制头 ctrl 只吃「解耦后的物理量 + 车速」，不碰原始视觉特征

速度输入:  SpeedOCRReader（已有，实测 99.8%）→ speed_norm
           + 速度差分 → accel_z_norm
           + 上一帧输出 → prev_throttle
           共 3 维，全部本地可得，无需任何游戏接口

不做的事:  ❌ 强化学习（实时游戏无法加速，见 §七）
           ❌ 虚构路网（游戏自己规划，见 §六）
           ❌ 提高输入分辨率（180×320 够用，见 §五）
           ❌ 手工标注辅助线（只值 9%，见 §四）
```

### 一句话

**《异环》没有遥测接口，但路线信息画在画面里（in-world driving line）——而控制标签来自用户自己的驾驶操作。两者叠加，构成一个不需要任何游戏接口的完整模仿学习闭环。**

## 三、目标架构：FH6 VisionAI 的「几何接口」

### 3.1 来源与许可

- 仓库：`Ayin1412/ForzaHorizon6-VisionAI`
- 论文：《Seeing Is Not Driving: Geometry as a Control Interface in a High-Speed Racing Game》（18 页，已读取全文）
- **许可**：代码 Apache-2.0（**架构可自由复用**）；权重与标定 CC BY-NC 4.0（**禁止商用**），且派生自游戏画面
- **对本项目的意义**：**借架构，不借权重**。重训可完全规避许可风险，且跨游戏权重本来也不通用

### 3.2 核心设计：几何中间量 + 解耦控制头

```
                    三帧堆叠 [3, 3, 180, 320] @0.1s（0.2s 历史）
                              ↓
                    ResNet-18（conv1 扩到 3×frame_stack 通道）
                              ↓
                        AdaptiveAvgPool(4,4)
                              ↓
                          fc1 (256)
                    ┌─────────┴─────────┐
              早期分叉（不看车速）    晚期分叉（融合车速）
                    │                   │
       ┌────────────┼───────┐     ┌─────┴─────┐
     line(3)    wp(9×2)  slip(6) wpspeed(9)  直接 steer/throttle
       │           │              │           （仅塑形表示，不用于驾驶）
       └───────────┴──────────────┘
                    ↓
          geom = cat([line*3.0, wp, wpspeed, slip])   ← 全部 .detach()
                    ↓
          ctrl_steer = tanh(ctrl_steer_mlp(cat([geom, speed])) + line_to_steer(line))
          ctrl_throttle = sigmoid(ctrl_throttle_mlp(cat([geom, speed])))
                    ↓
              【部署用这两个输出】
```

### 3.3 为什么「解耦」是关键（论文实测支撑）

论文 §5 消融，**HUD 关闭时**的表现：

| 配置 | HUD 开 | HUD 关 | 变化 |
|---|---|---|---|
| `full`（几何量喂控制头） | 29.7 m/s | **27.1 m/s** | **−9%** |
| `abl_a`（视觉特征喂控制头） | 30.2 m/s | **5.4 m/s** | **−82%** |
| `abl_b` | 31.3 m/s | **3.3 m/s** | **−89%** |

**且 `abl_a` 的道路感知完好**（79.5 → 75.1 m）——**只有控制崩了**。

**机制解释**：控制头只见物理量，所以它必须真的「理解路在哪」才能输出转向；若控制头能直接看视觉特征，它会走捷径（记住「HUD 长这样 → 这样打方向」），HUD 一变就废。

### 3.4 三条防捷径措施（论文 §3.4 原文）

1. **弧长航点**：waypoint 按固定弧长（8/12/17/23/30/40/52/66/85 m）而非时间采样 → 解耦几何标签与实际车速
2. **随机化 `prev_throttle` / `accel_z`**：降低对本体感觉线索的复制（对应 Causal Confusion 论文）
3. **几何驱动的速度目标**：让刹车成为「预测速度曲线」的函数，而非「HUD 外观」的函数

> 论文自评：只有第 3 条有直接闭环对照证据，前两条是「采纳的设计选择，非独立消融结论」。

## 四、辅助线（driving line）：能自动提取，但只值 9%

### 4.1 一手证据：辅助线确实存在且贴地

| 证据 | 内容 |
|---|---|
| **Mod** | `Disable Driving Line`（GameBanana，32 likes）——「Disables the **in-world driving lines** that appear when setting a waypoint」 |
| **触发条件** | 设置追踪路点后出现 |
| **形态** | 贴路面的发光条带（**in-world**，非 HUD 贴片） |
| **颜色** | 青蓝色，实测 Hue **200.2° ± 2.9°**、Sat 0.47 ± 0.11、Val 0.82 ± 0.14、RGB(115,178,210) |
| **纹理** | 横向/斜向条纹（阶梯状光带） |
| **红色变体** | 逆行/禁止状态时变红（用户确认） |

### 4.2 分辨率实测：180×320 下信号充足

对真实帧逐级降采样，测线的像素宽度：

| 分辨率 | 线最宽 | 中位宽 | 有效行 | 评估 |
|---|---|---|---|---|
| 1920×1080 | 285 px | 62 px | 565 | 极好 |
| 1280×720 | 190 px | 42 px | 374 | 极好 |
| 640×360 | 95 px | 21 px | 184 | 极好 |
| **320×180** | **47 px** | **11 px** | **90** | **充足** |
| 256×144 | 38 px | 9 px | 72 | 勉强 |

**结论**：**180×320 下这条线是 11px 宽、跨 90 行的光带，不是 1–2px 细线。信噪比充足，不需要提高分辨率。**

### 4.3 但它的价值有限

论文消融显示：**line 只贡献约 9%**（29.7 → 27.1 m/s），主驱动是**纯视觉 waypoint**。

**因此本方案的决定**：
- **辅助线不是必需项**。可作为可选辅助头加入（从画面自动分割，零人工标注），成本极低
- **绝不把辅助线当主监督信号**。主监督是「路线几何 + 用户操作」

### 4.4 自动提取的已知坑（实测 1300+ 帧发现）

工具 `tools/extract_driving_line.py` 的实测结果：整体命中率约 **12–20%**，原因是**数据源问题，非算法问题**：

| 坑 | 说明 | 对策 |
|---|---|---|
| 大部分视频帧没设路点 | 线只在追踪目标时出现 | 录制时全程设路点 |
| **自车车漆误检** | 银/蓝车漆与线同色系 | 已加 `ego_mask()`（中央±30%、下方38% 区域） |
| 天空误检 | 蓝天 Hue 同样落在 200° 附近 | 已加 `ROI_TOP = 0.40` |
| 夜景/雨天色偏 | 发光材质强度变化 | 阈值需按场景调 |
| 逆行变红 | 颜色变了 | 需加红色分支 |

> ⚠️ **重要教训**：视频网站快照帧（480×270）不是合格数据源——分辨率低、压缩伪影重、镜头乱晃、含转场。**真正的数据源必须是用户自己录制的 1080p+ 标准驾驶画面。**

## 六、地图/定位/路网：不需要虚构，但已有完整基础设施

### 6.1 用户原始疑问与结论

> 「怎么和游戏同步数据？在大地图设个目标，规划出路线让模型开……是不是需要虚拟出一个路网？」

**答案：不需要。** 因为——

```
用户在游戏地图设目标 → 【游戏自己】算出路线 → 【游戏自己】在路上画出辅助线
                                                    ↓
                                          这条线就是路线，就在画面里
```

**游戏已经完成了路径规划，模型只需学会「跟着眼前的路开」。**

### 6.2 三个方案的复杂度对比

| 方案 | 需要什么 | 复杂度 |
|---|---|---|
| A. 地图定位 + 自算路线 | 抓包 + 地图匹配 + 路径规划 + 坐标变换 | 🔴 极高 |
| **B. 只用画面里的辅助线** | 无（线是像素） | 🟢 **极低** |

**本方案选 B。**

## 七、强化学习：为什么不做

### 7.1 用户疑问

> 「强化学习该怎么强化？他怎么判断自己撞到墙？」

### 7.2 奖励信号的三条路

| 来源 | 可行性 | 说明 |
|---|---|---|
| 游戏 API 告知碰撞 | ❌ | 无接口（FH6 有遥测，GT Sophy 有索尼内部 API） |
| 从画面判断 | ⚠️ | 撞车瞬间画面剧变 + 速度骤降 |
| **从速度判断** | ✅ | SpeedOCR 已能读速度 |
| **用辅助线当奖励** | ✅ | 离线越近奖励越高（**这才是「自监督」该在的位置**） |

### 7.3 但物理上不可行

| 障碍 | 数字/说明 |
|---|---|
| **无法加速** | 真实游戏 30 fps，RL 需 10⁶–10⁷ 次交互 → 按 30fps 需**连续跑数周至数月** |
| **撞车需重置** | 手动重开、重跑回赛道，无法自动化 |
| **初期必撞** | 训练初期模型开不好，需人工盯守 |
| **游戏内代价** | 撞车有真实惩罚（车损、任务失败） |
| **多目标奖励** | 「开得好」= 快 + 不撞 + 在车道 + 不违规，需精心设计 |

**参照系**：
- **GT Sophy**（索尼）：专用分布式训练集群 + 游戏内部完整状态访问权
- **FH6 那个模型**：论文原文 `Training is pure BC, with no DAgger or RL fine-tuning`（**连有遥测的都没做 RL**）

### 7.4 正确替代：BC + DAgger（项目已实现）

`Sources/AuroraDrive/App/AuroraDriveApp.swift:905-907` 原文注释：

```swift
/// 专家模式：录制时控制量来源切到真人物理键（模仿学习的专家演示），
/// 而非 AI 决策（currentCommand）。关 → 录 AI 决策（DAgger 自训练）。
var expertMode = false
```

| 轮次 | 模式 | 作用 |
|---|---|---|
| 第 1 轮 | 专家模式**开** | BC：模型学用户开车 |
| 第 2 轮+ | 专家模式**关** | DAgger：模型自己开，出错时用户接管纠正 |

**DAgger 就是 RL 的实用替代品**——用「人工纠正」代替「奖励信号」，成本低几个数量级。项目里 `tools/dagr_to_h5.py` 已存在。

## 八、数据采集：专家模式 + 一键录制

### 8.1 自动标签机制（已实现）

`Sources/AuroraDrive/App/AuroraDriveApp.swift:849-882` 的 `RecordLabelMapper`：

```swift
/// 把物理按键的「按住时长」换算成连续控制标签
static let fullScaleDuration: TimeInterval = 0.6   // 满刻度时长

static func steer(leftHeld:, rightHeld:) -> Double   // D比例 − A比例
static func throttle(wHeld:) -> Double                // W按住比例
static func brake(sHeld:, spaceHeld:) -> Double       // S/空格 取较大者
```

**设计意图**（代码注释）：
> 让模型学到「打得越满 → 按住越久」的连续映射，替代二值标签带来的顿挫。

### 8.2 录制产物格式

`Sources/AuroraDrive/Capture/RecordEngine.swift`：

```

  ├── frames/          # 画面帧（默认 640×360，16:9）
  ├── controls.csv     # t_sec,frame,steer,throttle,brake
  ├── meta.json        # duration / perspective / target_w/h / capture_interval_ms
  └── view.txt         # 视角标记（FPV / 第三人称）
```

### 8.3 用户操作清单（周末执行）

```
1. 开游戏，第三人称视角，固定画质设置
2. 地图上设一个追踪路点（辅助线出现）
```

## 九、本方案与被证伪的假设（防止重复踩坑）

### 9.1 已被证伪

| 假设 | 证伪依据 | 结论 |
|---|---|---|
| 「FH6 模型是自监督」 | 论文 §3.6 原文：`teacher forcing at probability 0.5`，几何量真值来自**遥测** | ❌ **是特权监督（privileged distillation），不是自监督** |
| 「FH6 模型是第一人称」 | 提取 GIF 帧确认为**第三人称追车视角**（车体完整可见） | ❌ |
| 「地平线 = 地平线机器人」 | 用户澄清为《极限竞速：地平线6》 | ❌ |
| 「抖动是 OOD 问题」 | 用户说明：**抖动一直在训练数据里** | ❌ 属 in-distribution，不是 OOD |
| 「1080p 输入会挤爆 GPU」 | 代码 `computeUnits = .all` **优先 ANE**，GPU 全留给游戏 | ❌ **ANE 独立单元，不抢 GPU** |
| 「先提高分辨率再说」 | 降采样实测：180×320 下线宽 11px、90 有效行 | ❌ 分辨率不是瓶颈 |
| 「用视频网站快照当数据源」 | 实测标签几乎不压在真实线上（含天空/挖掘机/隧道误检） | ❌ **必须用自己录的 1080p 标准驾驶数据** |
| 「辅助线是主监督信号」 | 论文消融：line 只值 **9%** | ❌ 是可选加分项，非必需 |
| 「控制量可以自监督」 | 画面不含「该打多少方向」这一信息 | ❌ **物理上不可得，必须人工演示** |

### 9.2 核心教训

1. **不要把工具输出当事实转述**（源于 `run.sh` 的 libpcap 误报事件）
2. **不要混淆「脚本能分割」与「模型能学会」**——红点图是给人看的调试可视化，不是模型输入
3. **不要优化不该优化的指标**（命中率 ≠ 驾驶质量）
4. **不要为了数据而去找数据**——正确的数据源是「自己按标准流程录制」

## 附录 A：FH6 论文关键数据速查

### A.1 训练数据

- 842,592 帧 / 33 个录制会话（另有 10 个会话因路径标签不可靠被丢弃）
- 69.4% 游戏 AI（Anna）+ 30.6% 人类手柄
- 车辆构成：CarOrdinal 3123 占 83.5%，3773 占 8.9%，412 占 7.6%
- 验证集：每个录制的最后 15%，前留 2% 时间间隔防泄漏

### A.2 训练协议

- Adam，lr 1e-4，ReduceLROnPlateau（factor 0.5, patience 3）
- teacher forcing 概率 0.5（几何输入随机替换为真值）
- 纯 BC，无 DAgger / RL
- 每头加权 L1 损失；掩膜 `line_mask` / `wp_mask` / `slip_mask` / `steer_mask`

### A.3 steer_map（两个专家单位对齐）

- Anna 的转向像物理轮角，人类手柄指令经过游戏转向曲线
- 按曲率拟合增益比 ρ(v) = g_user(v) / g_anna(v)
- **30 m/s 时 ρ ≈ 9.98**，速度域内从 3.2 到 10.5（3.3 倍浮动）→ 单一常数不可用
- 对齐后可解锁 **69.4% 帧**的转向监督（原本没有人类转向标签的 Anna 帧）

### A.4 跨车泛化

- 三辆车、三种驱动形式（含未见过的 AWD），无逐车适配
- 达到游戏 AI 均速的 **84–92%**

### A.5 被推翻的假设（论文 §6）

| 假设 | 实测结果 |
|---|---|
| 航点振幅太小，放大有帮助 | 三次重训后闭环**都更差** |
| 近距航点误差是梯度饥饿 | 重平衡损失后 a* 仍约 1.7，无改善 |
| 入弯后应复用入弯前预测 | 误差随预测视界单调上升；oracle 只挽回 4.6% |
| 高滑移帧的转向饱和是映射过度 | 人类 48.3% vs 映射后 Anna 47.5%，基本一致 |
| 消融版油门是纯反应式 | 前瞻探针显示两族都会提前松油，差异在绝对速度 |

### A.6 论文自陈局限

1. 全程低于专家配速；纯 BC，无 DAgger / RL 微调
2. **每个变体只跑一个种子一次**，无重复、无误差棒、无种子扫描
3. 验证集是同路线内的时间切分，离线指标偏乐观
4. 跨车证据仅 n=3，每车一次配对运行，无误差棒
5. **未训练字面意义的 PilotNet 变体**（即驾驶头无梯度回传到卷积层），因此未直接测经典端到端 BC
6. 手写控制基线是单一最小配置，未调参
7. 完成度判定依赖人类观察者，非自动判据

### A.7 注意力图定性发现（论文附录 C）

- 横向航点头：注意力在**前方道路 + 赛道线标记**，不在天空/桥梁/植被
- 航点速度头（快速直道）：注意力延伸更远并沿走廊铺开
- 论文声明：**「报告中没有任何断言依赖于此」**

### A.8 KITTI 零样本（论文附录 D）

几何头能在真实道路图像（KITTI）上给出合理的路径——**说明学到的不是纯游戏特定的道路表示**。但该检查是**定性、单帧**的。

## 十二、部署时没有辅助线怎么办（关键问题）

### 12.1 问题本质

端到端模型要**全自动完成任务**，但：

```
问题: 模型训练数据全是「有辅助线」的画面，
      部署时却不可能每次都手动打开地图设路点 → 没有辅助线 → 模型没见过 → 崩
```

**这是本方案最重要的风险点。**

### 12.2 被否定的方案：从画面里"擦除"辅助线

**设想**：训练时随机把辅助线抹掉，让模型学会不依赖它。

**实测结论：❌ 不可行**，两条原因：

**① 技术层面——分割不可靠**
- 线的实际像素色：Hue **213.1° ± 1.5°**、Sat **0.70**、Val **0.22**（暗部）
- 自车车漆：Hue **212.1° ± 3.1°**、Sat 0.57、Val 0.43
- **两者 Hue 几乎重合**，仅靠颜色无法分离

**② 更根本——擦除解决不了问题**
- 擦除只是「让模型别依赖线」，但**模型仍然不知道往哪开**
- 擦除后的画面里没有任何路线信息，模型只能瞎猜

**③ 我的实测失败记录（诚实记录）**
- 首次测试脚本报告「残留率 5.2%」，但**视觉对比图显示线完好无损**
- 根因：**线本身落在自车掩膜区域内**（中央下方），掩膜把线一起挖掉 → 统计为"已擦除"，实际未改动
- **教训**：统计指标必须与视觉验证交叉核对，不能单信脚本输出

### 12.3 正确方案：**有线 + 无线 混合录制**

```
录制批次 1: 设追踪路点 + 专家模式 + 开 10min   →  有线数据
录制批次 2: 不设路点   + 专家模式 + 开 10min   →  无线数据  ★关键
录制批次 3: 设路点走不同路线 + 10min           →  多样性
```

**为什么这样可行**：

| 场景 | 训练时见过？ | 部署表现 |
|---|---|---|
| 有辅助线 | ✅ 批次 1 | 正常 |
| **无辅助线** | ✅ **批次 2** | **正常（关键）** |

**模型学的是「看路开」，辅助线只是额外参考。** 批次 2 让它学会在无线条件下也开得好。

> **对比 FH6**：论文消融显示 line 只贡献 **9%**（29.7 → 27.1 m/s），主驱动是纯视觉 waypoint。**线本来就是可选加分项，不是必需品。**

### 12.4 另一条路：自己的路线规划（App 侧）

用户提出的方向（**正确**）：**不依赖游戏画线，App 自己规划路线。**

```
层级 1  路线规划（App 侧，不依赖游戏）
        地图数据库(5677标记) + 抓包定位(CoordinateCapture)
        → 规划路径点序列 → PID 转向建议
层级 2  端到端视觉驾驶（负责"怎么开"）
        画面 → 模型 → 油门/刹车/转向微调
```

**已有可复用资产**：

| 组件 | 位置 | 说明 |
|---|---|---|
| 路线数据格式 | `MaaNTE/assets/resource/routes/*.json` | `{version, routes:[{id,name,segments}]}` |
| 现成路线 | 同上 | `test.json` / `FishNavigation.json` / `WitchDivinatNavigation.json` / `penquan.json` |
| PID 转向 | `MaaNTE/.../waypoint_navigator.py` | `kp=0.85 ki=0.04 kd=0.10`，含死区、限幅 |
| 路线状态机 | `MaaNTE/.../route_model.py` | `RouteSession`：路径点 + 索引 + `advance()` |
| 世界坐标 | `Sources/.../CoordinateCapture.swift` | libpcap 抓包 → `Pose(x,y,z,pitch,heading)` |
| 坐标转换 | `CoordinateCapture.swift:629` | `worldToMapPixel()` → 地图像素 + heading |

**结论**：**两条路都留着**。近期用「有线+无线混合录制」（简单、已验证），远期接「自规划路线」（全自动、需开发）。

### 13.2 可行性已验证（原型已跑通）

**脚本**：`tools/route3d_view_proto.py`
**效果图**：`docs/文档库/探索文档/生成图/3D路线导航原型-2026-09-21.png`

原型做的事：
1. 读真实地图数据库（5677 标记）
2. 用标准 **look-at 投影矩阵**（`forward`/`right`/`up` 三轴）把 3D 世界点投到 2D
3. 相机参数可调：`CAM_H=10.0`、`CAM_BACK=16.0`、`FOV=58.0°`
4. 绘制：地面网格 → 道路带 → 三层发光路线 → 标记柱 → 自车三角 → HUD

**投影核心代码**（已验证正确）：
```python
Fw = (target - cam); Fw /= norm(Fw)       # 前向
Rt = cross(Fw, UP);  Rt /= norm(Rt)       # 右向
Up = cross(Rt, Fw)                        # 上向（正交化）
def proj(p):
    d = p - cam
    x, y, z = d@Rt, d@Fw, d@Up           # 相机空间
    if y <= 0.3: return None              # 背面剔除
    return (W/2 + f*x/y, H/2 - f*z/y)     # 透视除法
```

### 13.5 结论：对我们的影响

```
✅ 有影响，但只影响「投射到游戏画面」方案
❌ 不影响「投射到预览框」方案
```

**因为**：预览框用的是**我们自己的相机**（自己定 `CAM_H`/`CAM_BACK`/`FOV`），**与游戏相机完全无关**。

**唯一残留影响**：如果要在预览框里**对照游戏画面**（比如把游戏帧当背景），游戏相机的动态变化会让对照不精确。但**独立的 3D 导航面板不受影响**。
