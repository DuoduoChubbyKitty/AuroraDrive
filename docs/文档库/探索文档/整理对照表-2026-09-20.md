## 二、根因：为什么会有 20436 个 unhandled

⚠️ **`exclude` 数组里只有 `.build`（SwiftPM 自己的构建目录），缺了项目自己的 `build/`（2.1GB / 20427 文件）**。

### 七之三、`run.sh` 的 libpcap 误报（已修正）

**用户指出**：「之前抓包是真的验证过成功了，怎么又未安装了？」——核查后确认**用户正确，我的转述错误**。

#### 证据：libpcap 完全正常

```
① 库在 dyld 共享缓存中（现代 macOS 系统库不再以实体文件存在于 /usr/lib）
   $ dyld_info -exports /usr/lib/libpcap.A.dylib
     /usr/lib/libpcap.A.dylib [arm64e]:  _bpf_dump  _bpf_filter …

② 二进制确实导入并使用它（8 个函数）
   $ nm -u AuroraDriveUI | grep pcap
     _pcap_open_live  _pcap_next_ex  _pcap_setfilter  _pcap_compile
     _pcap_findalldevs  _pcap_breakloop  _pcap_close  _pcap_freealldevs

③ BPF 设备真实可读写（抓包的功能性依赖）
   $ ls -la /dev/bpf*
     crw-rw-rw-  /dev/bpf0 …（程序自报「BPF可读写 ✓」）
```

#### 根因：旧判据自 macOS 11 起恒为假

```sh
# 旧写法（必然误报）
if ls /usr/lib/libpcap* >/dev/null 2>&1 || brew list libpcap >/dev/null 2>&1; then
```
- `ls /usr/lib/libpcap*` → 系统库已全部移入 dyld 共享缓存，磁盘上不存在实体文件（本机 `/usr/lib` 仅剩 32 个条目）→ **恒失败**
- `brew list libpcap` → libpcap 是 **macOS 自带库**，从不经 brew 安装 → **恒失败**

⚠️ 该 glob 未匹配时的 `No such file` 报错被 `2>&1` 吞掉，故看不出异常——**这行检查自 macOS 11 起就一直是误报**。

#### 修正（`run.sh` 26–38 行，仅改此段，其余未动）

```sh
if { [ -f "$BIN_SRC" ] && /usr/bin/dyld_info -linked_dylibs "$BIN_SRC" 2>/dev/null | grep -q libpcap; } \
   || /usr/bin/dyld_info -exports /usr/lib/libpcap.A.dylib >/dev/null 2>&1 \
   || ls /usr/lib/libpcap* >/dev/null 2>&1; then
    echo "  libpcap: ✓ 已安装 (dyld 共享缓存)"
```

**为何三段式**（用户给的判据只含前两段，实测有边界缺陷）：
- **判据①**（检查产物链接）需 `$BIN_SRC` 存在，但本检查在 `[1/4] 环境检查`（第 27 行），而编译在第 58 行且会 `rm -rf .build` → **首次运行时产物不存在，判据① 必然落空**
- **判据②**（`dyld_info -exports` 穿透共享缓存）**不依赖构建产物**，兜住首次运行场景 ← 实测验证的关键补充
- **判据③**（原 `ls`）保留作为极老系统兜底

#### 验证

```

./run.sh --status（产物存在）          → libpcap: ✓ 已安装 (dyld 共享缓存)
```

**不要把工具的输出当成事实转述。** `run.sh` 打印 ✗，我就跟着说「未安装」，还把它归为「与本次整理无关的本机环境状态」——这恰好是用户反复警告的那类错误。**检查脚本本身也可能是错的**，尤其是涉及 macOS 版本演进（系统库迁移至 dyld 共享缓存）的判据。
