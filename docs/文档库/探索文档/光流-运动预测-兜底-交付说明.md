# 光流 ↔ 运动预测 ↔ 双结构兜底 —— 交付与运维说明

**日期**：2026-09-27
**状态**：已实现并自检通过（3 个自检 0 失败）；**尚未真机跑过驾驶**

## 一、这套东西解决什么问题

YOLOPX 单帧实测约 **60ms**（148.11 GFLOPs；ANE 实测峰值 9.26 TFLOPS，
所以物理地板 16ms，当前效率约 26%），**跑不到 30Hz**。

但主循环是 30Hz。如果每帧只读"最近一次检测结果"，那么在两次推理之间
检测框是**完全静止**的 —— 目标在动、框不动，决策层会按过期位置开车。

用户给的解法（原话整理）：
> 「通过持续递增率检测加跟踪，然后通过滤波算法和一些光流算法预测出
> 车辆到底是怎么走的那种……把他的车道线还有各种可行驶区域继续延伸下去，
> 再加上双结构兜底」

落地成三段：
1. **光流**：帧间运动估计（30Hz，实测 p95 1.7ms）
2. **运动预测**：α-β 滤波维护 (位置, 速度)，真值校正 + 缺席外推
3. **双结构兜底**：纯几何判据，不依赖模型置信度

## 三、实测数据（全部本机同批测得）

### 3.1 光流方案选型 —— 为什么是 OpenCV

用户红线：**光流 ≤5ms**。

| 方案 | 640×640 p95 | 判定 |
|---|---|---|
| Apple `VTOpticalFlow`（VideoToolbox 硬件） | 10.28 ms | ✗ |
| Vision `VNGenerateOpticalFlow` | 27.43 ms | ✗ |
| **OpenCV `DISOpticalFlow` PRESET_ULTRAFAST** | **1.91 ms** | ✓ |
| 同上，只留 1 核 | 3.78 ms | ✓ |

DIS = CVPR 2016 论文算法（Dense Inverse Search），OpenCV 官方 `video` 模块，
**非自研手搓**。精度实测误差 **0.07px**（dx=1.930 对真值 2.000）。

### 3.2 生产配置（两处关键调优，勿改）

**① 4:1 抽样求中位数**（`flow_bridge.cpp` 的 `kMedianSampleStep`）

| 实现 | p50 | p95 | p99 |
|---|---|---|---|
| 全量 409600 点 | 4.57 | 4.95 | 5.32 ← 卡红线 |
| **4:1 抽样 16384 点** | **1.47** | **1.91** | **2.07** |

精度几乎不变（光流场高度平滑，中位数对抽样不敏感）。

**② OpenCV 线程数 = 2**（`flow_bridge.cpp` 的 `kOpenCVThreads`）

线程多 ≠ 快。默认（用满 8 核）在 7 路背景负载下 p95 达 20.9ms：

| nt | 空载 p95 | 7 路背景负载 p95 |
|---|---|---|
| 默认(8) | 2.26 | 20.86 ✗ |
| 1 | 3.07 | 6.01 ✗ |
| **2** | 2.21 | **3.53 ✓** |
| 4 | 2.30 | 4.07 ✓（尾延迟更差） |

### 3.3 极端工况的边界（重要，别误读）

用户要求「CPU 只留一个核心、极端工况下维持」。实测到的**适用条件**：

| 场景 | p95 | 判定 |
|---|---|---|
| 空载 | 1.7 ms | ✓ |
| 7 路负载 @ **UTILITY**（模拟游戏/后台） | **3.7 ms** | ✓ **生产即如此** |
| 7 路负载 @ **与光流同优先级**（把 8 核占死） | ~9 ms | ✗ |

生产 tick 由 `DispatchQueue(qos: .userInteractive)` 驱动（`MissionConsole.swift:2876`），
游戏是普通优先级 → 属于第二行。第三行在真实场景不存在：真有 7 个
userInteractive 满载线程，整个 App 的 30Hz 早就先崩了。

**自检里已显式提升线程优先级**（`OpticalFlowBridge.elevateCurrentThreadPriority()`），
否则自检跑在主线程（默认 QoS）会测出假超标。

### 3.3b 真实行车画面验证（不只是合成图）

合成图能验精度，但真实纹理才是生产条件。用仓库里已有的真实录制帧
（`data/raw_clips/clip_20260922_003025/frames/`，640×360 letterbox 到 640×640）：

**① 静止场景不产生假运动（关键安全属性）**

那两帧是油门为 0 的静止录制（像素平均绝对差 0.087，仅 0.19% 像素有差异）。
光流输出 **dx=0.000 dy=0.000** —— 正确。它没有在静止画面上编造运动。
（反过来才可怕：静止却报"车在动"，预测器会把框推着走。）

**② 真实纹理上的位移精度**

| 真值 | 测得 dx | 测得 dy | 误差 | 判定 |
|---|---|---|---|---|
| (6, 3) | 5.688 | 2.731 | (0.312, 0.269) | ✓ |
| (12, 5) | 11.877 | 4.666 | (0.123, 0.334) | ✓ |

真实行车纹理上误差 0.12~0.33px，**在 0.5px 红线内**。
延迟 p50=1.872 / p95=2.378 ms，达标。

## C.1 最要命的发现：掩码可见性从未被验证过

无法区分是 ①模型没输出 ②引擎没跑 ③掩码没传 ④UI 没画。

街道 + 车道线 + 前方 3 辆车）跑完整推理：

```

  ✓ 测试图加载成功  — 1280×720
  ✓ 推理产出结果  — 耗时 52.2 ms
    检测框 9 个 / 可行驶占比 26.19% / 车道线占比 8.042%

  ✓ 车道线掩码非空  — 1158 格
```

**结论：模型完全正常，da/ll 都出得好好的**（车道线 1158 格）。
问题在显示层 —— 见 C.2。

## C.2 车道线看不见的真因：降级「连坐」

`YolopxEngine` 原本用**单一** `isDegraded` 同时管两层掩码：

```swift
isDegraded = (laneRatio < lanePositiveFloor)      // 0.002
    || (drivableRatio < drivablePositiveFloor)    // 0.02
    || (laneRatio > lanePositiveCeil)
    || (drivableRatio > drivablePositiveCeil)
```

而车道线是**细目标**，前景占比天然只有 1.3~2.6%（贴近下限）。一旦它塌陷：

```
isDegraded = true → MaskOverlay 的 dim = 0.35
→ 可行驶区透明度 0.18 × 0.35 = 0.063  ← 几乎不可见
```

**即「车道线的问题把可行驶区一起带暗了」，二者本无因果关系。**
这就是「只能看到检测框」的直接机制。

### 修复：分层塌陷，显示层解耦

- `YolopxEngine` 新增 `laneDegraded` / `drivableDegraded` 两个独立标志
- `MaskOverlay` 分别调暗（`daDim` / `llDim`）
- **决策层继续用合并后的 `isDegraded`，语义完全不变**
- 协议 v3 flags 加 bit2（车道线塌陷）/ bit3（可行驶区塌陷）
- 旧引擎不发这两位 → 恒为 0 → 两层都不压暗（**安全的降级方向**：偏亮而非偏暗）

## C.3 预览框卡顿：实测逐项归因

| 项 | 改前 | 改后 | 说明 |
|---|---|---|---|
| `convertToGray` | 0.639 ms | **0.040 ms** | 见下 |
| 光流 DIS | 1.700 ms | 0（移出） | 移到 captureQueue |
| 掩码绘制 | 1.192 ms | **0.375 ms** | 行跨度合并 |
| 检测框绘制 | 0.300 ms | 0.300 ms | 未动 |
| **主线程合计** | **3.831 ms** | **0.675 ms** | **降 82%** |
| 占 33.33ms 预算 | 11.5% | **2.0%** | |
| 光斑 blur60（GPU） | 2.13~4.20 ms | 待复测 | 见下 |

### 真凶 1：每像素整数除法（`convertToGray`）

原实现在**内层循环**逐像素算 `x * srcW / dstW`。生产路径是
640×640（YOLO 直通帧）→ 640×640（workingSize），即 **srcW == dstW**，
那个除法**恒等于 x** —— 却对每帧 40.96 万像素各做一次。

实测（M3，640×640，n=40）：

| 写法 | p50 |
|---|---|
| 逐像素除法 | 0.639 ms |
| **同尺寸直接步进** | **0.040 ms** ← 快 16 倍 |
| 预计算列偏移表 | 0.264 ms ← 仍有表访问开销 |

修复：加 `sameSize` 快路径（1:1 时无缩放无除法）；非同尺寸时保留完整
最近邻语义，但列映射提到行循环外预计算。**数学等价，非近似。**

### 真凶 2：光流在主线程

`runOpticalFlow` 原本在 `tick()`（主线程，`DispatchQueue.main.async` 驱动）里
同步执行。用户实测 `tickGap` 已飙到 45ms（>33.3ms 即掉拍）。

**移到 `captureEngine.onYoloFrame` 回调**（captureQueue 后台线程）：
- 那里才是"帧的生产点"，池化缓冲的 use-after-recycle 约束天然满足
- 不新增捕获路径、不额外拷贝（与 yoloEngine 复用同一份 640×640 帧）
- 相关成员改 `nonisolated(unsafe)`（同 `pendingYoloFrame` 既有手法）

⚠️ **不可改成"存引用、稍后算"**：直通帧是池化私有缓冲，`inferFast` 拷完即归还，
下一帧可能拿到同一块 IOSurface 被覆写 → use-after-recycle。

### 真凶 3（已量未改）：光斑 blur

`AuroraTheme.swift` 的 `AuroraLightField` 代码注释自述「UI 侧最贵的一处 GPU 开销」，
但**此前从未被量过**。本次用 CIGaussianBlur（SwiftUI `.blur` 同底层）实测：

| 视口 | p50 | p95 | 占 33.33ms |
|---|---|---|---|
| 800×450 | 2.13 ms | 143 ms ⚠️ | 6.4% |
| 1200×675 | 2.93 ms | 5.25 ms | 8.8% |
| 1470×956（设计稿） | **4.20 ms** | 6.90 ms | **12.6%** |

**确认属实：预览框里单项最贵的绘制。**

修复选择**零视觉改动**方案：`.drawingGroup()` 把 blob+blur 栅格化成离屏纹理，
之后 `.offset` 只是平移纹理，Core Animation 可复用缓存。
半径 60、三个 blob 的尺寸/位置/透明度/动画曲线**全部不变**。

不用「降半径 / 删 blob / 移出预览框」的原因：光斑是用户明确要求的视觉语言
（空间感光斑、高对比玻璃拟态），属功能而非装饰，按项目纪律不得缩减。

### 真凶 4：掩码逐格 addRect

原实现每前景格一次 `path.addRect`。改为**行跨度合并**（每行连续前景格合成一个矩形）。
实测：

| 覆盖率 | 逐格 | 行跨度合并 |
|---|---|---|
| 可行驶区 14.73% | 0.961 ms | **0.216 ms** |
| 车道线 4.52% | 0.231 ms | **0.092 ms** |
| 车道线 + 新增描边 | — | 0.159 ms |

**几何等价性已验证**：7 种形态（全亮/棋盘/纵线/散点/全灭/随机10%/整行）在
CGContext 里逐像素比对 alpha 通道，覆盖面积**完全一致**。

顺带增强：车道线在填充之上加 0.8pt 同色描边（`Aurora.iceHi`），
提高边缘对比度 —— 车道线在 160 网格下只有 1~2 格宽，容易被画面亮部吃掉。
不扩大实际覆盖范围，只让已有车道线更醒目。
