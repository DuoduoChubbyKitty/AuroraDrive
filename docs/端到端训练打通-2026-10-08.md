## 1. 三方契约差异表（任务 1）

### 1.1 契约对照

| 字段 | M2 `model_v2.py` 声明 | M3 `dataset_v2.py` 产出 | 是否一致 |
|---|---|---|---|
| `image` | `[B,3,180,320]` | `[B,3,180,320]` | ✅ |
| `lane_mask` | `[B,1,160,160]`（MaskGrid） | `[B,1,180,320]` → 修复后 `[B,1,160,160]` | 🔴 修复前不符 |
| `dets` / `det_boxes` | `[B,20,12]`（合并 12 维） | `[B,20,4]` + `det_scores[20]` + `det_classes[20]` | 🔴 **格式不同** |
| `det_mask` | `[B,20]` | `[B,20]` | ✅ |

### 1.2 ★ 实测：把 M3 原始输出直喂 M2 会怎样

不是读代码推断，是真喂进去看报错：


**三路里两路硬炸、一路静默**。静默那路最危险——见 §5。

### 1.4 ⚠️ 遗留隐患：参数名 `state` vs `vehicle_state`

- `build_m2_inputs` 返回键是 **`state`**
- `M2Model.forward` 形参是 **`vehicle_state`**（因为 coremltools 8.3 会把名为 `state` 的输入静默改名为 `state_workaround`）

后果：`m(**inputs)` 直接展开会炸
```
TypeError: M2Model.forward() got an unexpected keyword argument 'state'
```
必须走 `call_model()`（按形参名过滤）才能工作。

**建议**：给 `build_m2_inputs` 的返回值加一个 `vehicle_state` 别名键，消除这个陷阱。

## 5. 🔴 车道线掩码几何口径 bug（本次最隐蔽的发现）

### 5.1 问题

`lane_mask` 的 **shape 两侧都是 160×160，但几何口径完全不同**：

| | 运行时 Swift `MaskGrid` | 修复前训练侧 |
|---|---|---|
| 来源 | yolopx `ll` 头 → **letterbox 640×640** → stride 4 下采样 | 录制帧 → resize 180×320 → interpolate 160×160 |
| 内容位置 | **只占行 35..125**（56.2%），上下各 35 行是**灰边(114 填充)** | **填满 0..160**，无灰边 |
| 纵横比 | 保持（等比） | **破坏**：横向压缩 4.0×、纵向 2.25×，差 **1.78×** |

### 5.2 源码依据（运行时侧亲口承认）

```
Sources/AuroraDrive/Inference/YolopxEngine.swift:40
  「二值掩码网格（letterbox 640 坐标系，按 gridStride 下采样后存储）」
Sources/AuroraDrive/Inference/YolopxEngine.swift:374
  「车道线掩码（letterbox 640 坐标系，下采样后）」
Sources/AuroraDrive/Inference/InferenceEngineV2.swift:124
  「掩码是 letterbox 640 坐标系的俯视图投影」
```

而训练侧 `train_v2.py` 原注释自己都在怀疑：
> 「M2 声明 lane_mask 为 [B,1,160,160]；M3 给的是 image_size 分辨率。**两者语义不同（疑为俯视栅格 vs 相机空间）**，默认按 M2 声明缩放。」

### 5.3 量化后果

同一物理像素在 160 网格中的行坐标（640×360 源图）：

| 画面 y | 运行时 letterbox | 训练侧拉伸 | 偏差 |
|---|---|---|---|
| 0 px | 35.0 | 0.0 | **−35.0 格** |
| 90 px | 57.5 | 40.0 | −17.5 格 |
| 180 px | 80.0 | 80.0 | ±0.0 格（仅中心重合） |
| 270 px | 102.5 | 120.0 | +17.5 格 |
| 360 px | 125.0 | 160.0 | **+35.0 格** |

**最大偏差 35 格 = 网格高度的 21.9%，且上下反向拉伸。**

### 5.3b ★ Lead 实测铁证：几何错位让 steer 偏半量程

Lead 用**真权重**（`checkpoints/m9_v2/best_model.pt`）+ 同一张图，只改车道线几何口径：

| 车道线输入 | 模型输出 steer |
|---|---|
| **正确口径**（letterbox 160 网格） | **+0.0710** |
| **错位口径**（interpolate 拉伸填满） | **−0.4331** |
| 全零（不给车道线） | +0.0448 |

- **正确 vs 错位差 = 0.504 —— 半个量程！**
- ⟹ 这个几何 bug 就是用户说「**直接开出车道线**」的技术根因之一
- ⟹ 本修复是本次换代**最重要的修复之一**

**同时暴露第二层问题**：正确车道线 vs 全零只差 0.026 → **车道分支还没学会用车道线**（因为 `lane_coverage=0.0`，车道分支从未被监督）。

### 5.4 为什么这个 bug 特别危险

`LaneMaskEncoder` 开头是：
```python
self.downsample = nn.MaxPool2d(kernel_size=2, stride=2)
...
self.global_pool = nn.AdaptiveAvgPool2d((1, 1))
```
**任何输入尺寸都能吃下去不报错**（实测 180×320 直喂也不炸）。
⟹ shape 对齐给人「已经对齐了」的**假安全感**；这类 bug 不崩、不告警，只会让模型上车即失效。

### 5.5 修复（方案 1：统一到运行时口径）

**新建 `src/lane_geometry.py`** —— 训练侧唯一真值实现，逐行复刻 Swift：

| 函数 | 复刻对象 |
|---|---|
| `letterbox_metrics()` | `YolopxEngine.swift:150-166` `LetterboxMetrics.calculate()` |
| `logits_to_grid()` | `YolopxEngine.swift:1263-1341` `extractMask()` |
| `valid_region_in_grid()` | `extractMask()` 的 valid 区域计算 |

**核心语义**（与 Swift 逐位一致）：
```
1) 在 640 上算 (ch1 > ch0)
2) 对每个 4×4 块做多数表决：positive * 2 >= stride² → 160×160
```

**改动清单**：
1. `dataset_v2.py::_load_lane_mask` —— **删掉 `resize`**，改为按 letterbox 口径归一（640 → 4×4 多数表决 → 160）
2. `dataset_v2.py::backfill_lane_masks` —— 改为**直接产出 160×160 letterbox 口径**（原来存 640 全分辨率、由加载器 resize）
3. `train_v2.py::build_m2_inputs` —— **删掉 `F.interpolate`**，尺寸不符时**抛错/拒绝**，绝不静默 resize
4. 新增参数 `lane_grid` / `strict_lane_geometry`

### 5.6 ★ 验证：与 Swift 真跑逐位对拍（不是读代码推断）

系统有 `swiftc`，因此**真编译并运行 Swift 代码**做对拍：

```

    （发现：Python round(2.5)=2 而 Swift=3 → 必须自实现 _swift_round）
[2] letterbox 参数 vs Swift      ✓ 15 组源尺寸全部逐位一致
[3] extractMask 逐位对拍         ✓ 25600 像素 0 差异（正像素 16456）
[4] 几何常量                     ✓ padY=140 newH=360 ratio=1.0；valid 行 [35,125)
[5] fail-fast 契约               ✓ 拒绝 180×320 / 128×128 / 100×160 / 非0-1取值
[6] 几何口径诊断                 ✓ letterbox 口径 (35,125)；错误拉伸口径 (0,160) 可识别
[7] dataset/train 接线           ✓ 输出 [1,160,160]；错误口径被拒；正确口径原样透传
```

**回归测试已固化**：`tools/verify_lane_geometry_contract.py`（退出码 0/1，可接 CI）

| **w8a16**（本次实测） | `linear_quantize_weights` only，激活保持 fp16 | ✅ `yolopx3_w8a16` 在用 |
| **palette + 关键头保 fp16** | `palettize_weights` + `op_name_configs={...: None}` | ✅ **`ayolom_n_int8` 在用，用户实测"挺准"** |
| **W8A8 全量化** | weights + `linear_quantize_activations` | ❌ 车道线掉 10×，**已证伪** |

**本次测的是 w8a16 与 palette，都不是被证伪的全量化。** 项目里"INT8 打掉车道线 10×"那句结论**不适用于本次路径**。

### 6.3 ★ 三方对照（★ 分布内 vs 分布外两种口径，务必区分）

> **判据说明（采纳 w1-backend + lead 的方法论）**：量化误差的**绝对差值没有意义**，
> 要看「误差 / 模型自身输出跨度」，且**必须用部署分布（真实截图）来测**。
> 用 `torch.rand` 随机图测的是**分布外伪输入**，其 steer 会把模型推到全量程两端、
> 且大量落在 0 点附近，微小的量化误差自然容易符号翻转 —— **这种翻转真实运行不会出现**。

**分布内（70 帧真实截图 + 全零 lane/dets/state，即训练集真实口径）**：

| 方案 | 翻转率 | maxΔ | 体积 |
|---|---|---|---|
| fp16 | **0/70 = 0%** | 2.40e-03 | 5.796 MB |
| **palette** | **0/70 = 0%** | 3.68e-03 | 2.963 MB |
| w8a16 | 0/70 = 0% | 1.54e-02 | 2.963 MB |

**分布外（120 组 torch.rand 随机图，仅供看"最坏情况"，不代表真实）**：

| 方案 | mean | p95 | p99 | max | 翻转率 |
|---|---|---|---|---|---|
| fp16 | 1.356e-02 | 6.28e-02 | 9.97e-02 | 1.400e-01 | 0.0% |
| w8a16 | 5.599e-02 | 2.018e-01 | 4.860e-01 | 4.976e-01 | **2.5%** |
| palette | 6.150e-02 | 2.275e-01 | 2.882e-01 | 3.025e-01 | **1.7%** |

**为什么分布内/外差异如此巨大**：
```
真实截图 steer 跨度  = 0.00144   （模型学完只输出接近常数的值）
torch.rand 跨度       = 1.9999    （把模型推到全量程两端）
```
差 **1388 倍**。像素分布也印证：真实截图 mean≈[0.13,0.17,0.20]（深色），
torch.rand mean=[0.50,0.50,0.50]（均匀）。

**⚠️ 分布外翻转率不可外推**：1.7%/2.5% 的翻转只发生在 torch.rand 伪输入上；
**分布内（真实截图）palette 与 fp16 都是 0 翻转**。

**跨度归一化（误差 / 模型自身跨度，全样本口径）**：
```
no_dets 专项（跨度 = 1.16397）：
  fp16     6.37e-03 = 0.55%
  palette  1.22e-02 = 1.05%
  w8a16    8.46e-02 = 7.27%
```

**符号翻转样例（最危险 —— 左转变右转）**：
```
seed= 12  fp32=-0.0934  w8a16=+0.0693  palette=+0.0320
seed= 21  fp32=-0.3897  w8a16=+0.1078   ← |Δ|=0.4976，近半个量程
seed= 22  fp32=-0.1522  w8a16=+0.2854  palette=+0.0136
```

### 6.4 ★ 训练分布内复测（最诚实的口径）

用真实训练数据口径（`lane`/`dets`/`state` 全零）复测 12 组（绝对误差）：

| 方案 | 平均 \|Δsteer\| |
|---|---|
| fp16 | **9.42e-04** |
| w8a16 | 1.21e-02 |
| **palette** | **1.71e-03** |

⟹ **分布内 palette 比 w8a16 好 7.1×**（绝对口径）/ **4 倍**（跨度归一化口径）。

这**解释了用户的经验**：用户测 yolopx 说"INT8 挺准"，那用的是 **palette 配方 + 真实游戏画面（分布内）**。随机输入扫描（分布外）会放大差异，使两者整体数字接近；一旦回到分布内，palette 的优势就显现。**用户没错。**

### 6.5 归因（区分"量化导致" vs "模型本身"）

三方对照（PyTorch fp32 / CoreML fp16 / CoreML w8a16）：
```
              fp16 Δ      w8a16 Δ     放大
mean        1.356e-02    5.599e-02    4.1×
p99         9.966e-02    4.860e-01    4.9×
max         1.400e-01    4.976e-01    3.6×
```
fp16 与 w8a16 差 3~5×，**误差主体来自权重量化，不是后端**。

### 6.6 ⚠️ 建议（供决策）—— ★ 定案

| 方案 | 分布内翻转 | 分布内误差 | 体积 | 建议 |
|---|---|---|---|---|
| **palette gs=1** | **0%** | max 3.68e-03 | 2.963 MB | ✅ **首选**（用户明确要 INT8；palette 是项目量产配方，用户实测"挺准"） |
| fp16 | 0% | max 2.40e-03 | 5.796 MB | 🛡️ **兜底开关**（最稳，万一 palette 真机发现问题一键切回） |
| w8a16 | 0%（分布内） | max 1.54e-02 | 2.963 MB | ❌ 不推荐（palette 同体积，但误差是 palette 的 4.2×） |

**定案理由**：
1. **分布内（真实截图）palette 0 翻转** —— 与 w1 独立复现一致，翻转只出现在分布外随机图
2. palette 误差 3.68e-03 可接受，是 w8a16 的 **1/4.2**
3. 体积 2.963 MB 远低于 10MB 硬约束
4. **启发线索**：当年 yolopx 里"INT8 掉 10×"是被证伪的**全量化**；palette + 关键头保 fp16 是**另一回事**，已验证可用

### 6.7 本节的诚实限定

> **两个必须写清的边界**：
> 1. 本仓库**没有真实游戏画面**（129 帧全是桌面截图），所以上面"分布内"= 桌面截图，
>    **不是真正的驾驶画面**。真正的分布内（游戏画面 + 真实车道线 + 检测框）翻转率仍未测，
>    要等重新录制后才能定案。
> 2. 全是**单帧独立误差**，**没测帧间时序抖动**。
> 3. 训练集 lane/dets 全零、模型这两路从未被监督，故**绝对误差幅度不能外推为真实驾驶精度**。
>    但「palette < w8a16 < fp16（误差递增）」的**相对排序是稳的**。

```python
mlpackage = out.with_suffix(".mlpackage")   # 若 out 已是 .mlpackage，两者同一路径

mlmodelc = out
```

⟹ **静默假报成功**。建议：检测 `mlpackage == mlmodelc` 时直接报错，并在 `save()` 后校验文件存在。
