## 2 · 错开正确性（源码层验证，不靠跑）

### 2.1 门判定源码（`AuroraDriveApp.swift:6571-6586`）

```
adaptiveFrameCounter &+= 1
let parityEven = adaptiveFrameCounter % 2 == 0
let decimateFallback = Self.detectDecimate == 1
let detectGateA = decimateFallback || parityEven    // yolopx：偶数帧
let detectGateB = decimateFallback || !parityEven   // yolo26s：奇数帧
```

### 2.2 门实际门控的三处提交点

| 提交点 | 门 | 网络 | 行号 |
|---|---|---|---|
| 直通 `inferFast`（待机/驾驶都跑） | `detectGateB` | yolo26s（奇数帧） | 6634-6641 |
| 驾驶分支慢路径 `yoloEngine.infer` | `detectGateB` | yolo26s（奇数帧） | 6836-6839 |
| 驾驶分支 `yolopxEngine.infer`（三合一 ll/da/det） | `detectGateA` | yolopx（偶数帧） | 6845-6847 |

**判定**：✅ **错开正确，非同相**。三处提交点全部按「yolopx 偶数帧 / yolo26s 奇数帧」错开，每帧至少一网出检测框真值，不再有「真空帧」。`AURORA_DETECT_DECIMATE=1` 可一键回退两门恒真（恢复每帧都跑）。

```

`LaneBridge()` 便捷构造（`LaneBridge.swift:92-97`）现已**直接绑定真实 E2**：

```
车道线消费点从「读冻结的 `yolopxEngine.laneMask`」改为「读外推后的 `extrapolatedLaneMask`」，链路已接。

### 3.2 🔴 架构矛盾：默认 A-YOLOM 档下外推退化为「快照回退」

源码级确定、不依赖编译，六步链路：

| 步 | 事实 | 位置 |
|---|---|---|
| 1 | 默认档 `perceptionMode = .ayolom` | App:5301 |
| 2 | `.ayolom.needsOpticalFlow == false` | YolopxEngine:242-247 |
| 3 | 光流唯一调用点被 `perceptionMode.needsOpticalFlow` 门控 → A 档**不跑** | App:6756-6757 |
| 4 | `lastOpticalFlow` 唯一写入在 `runOpticalFlow` 内 → A 档恒 nil | App:6373 |
| 5 | 外推实参 `flow:` 就传这个 `lastOpticalFlow` | App:6440 |
| 6 | 门③ `flow == nil` → `return lastLaneSnapshot`（快照回退，**不调 E2**） | LaneBridge:145-147 |

**根因**：A2 注释（App:6742-6746）假设「A-YOLOM 每帧都有真值→不需要光流」；该前提被 E4 错开**打破**——yolopx（含 A-YOLOM 族 `ayolom_n_int8`）被 `detectGateA` 门控只在偶数帧 15Hz 跑，A 档真值从「每帧」掉到「偶数帧」。于是 E2/E5 想在奇数帧补光流外推，但光流在 A 档被 A2 关死，`flow` 恒 nil → 只回退快照。

**结果**：默认档（用户绝大多数场景）下，奇数帧车道线仍是「上一帧冻结旧掩码」，恰好就是 E2/E5 要消除的「车在动、线不动」问题**没有真正解决**；真正光流外推只在 `legacy` 档（26S+光流+YOLOPX）可能发生。

**判定**：🔴 **代码问题（跨任务 E4 × E2/E5 × A2 集成矛盾）**，非环境噪声。候选修复：
- (a) A 档也允许跑光流（为外推提供 flow 可用）；
- (b) 外推改依赖别的信源；
- (c) 若 Lead 明确「默认档就是快照回退」，需在文档/UI 诚实标注「车道线外推仅 legacy 档生效」，避免误导验收。
（已上报父代理，等 Lead 决断）。
