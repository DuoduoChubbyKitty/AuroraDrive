# 骨干网络候选清单 — 2026-10-08

> **Lead 亲自挖掘**（B1 代理未及启动，名额被 M1-M8 占满）
> 硬约束：**模型 ≤ 10MB** + 必须收「图像/车道线/检测框/状态」+ M3 上 30Hz

---

## 0. 大小换算基准（先算清楚 10MB 能装什么）

| 精度 | 每参数字节 | **10MB 能装** |
|---|---|---|
| FP32 | 4 B | ≈ 2.5M 参数 |
| **FP16** | 2 B | **≈ 5M 参数** |
| **INT8** | 1 B | **≈ 10M 参数** |

**参照物（本项目实测）**：
- 现有 M9 主驾驶模型 = **15MB**（超了！）
- `game_assist_control` = **7.6MB**（合规）
- M2 新写的 `model_v2.py` = **FP16 ≈ 6.2MB**（2,759,000 参数，合规 ✅）

## 3. 多模态融合结构（关键——本项目必须自己搭）

| 结构 | 用途 | 参数量 |
|---|---|---|
| **PointNet** | 变长集合编码（→ **检测框分支**） | 极小（几层 MLP，<0.1M） |
| 小 CNN | 车道线掩码编码 | 极小（3 层卷积，<0.5M） |
| MLP | 状态向量编码 | 可忽略（<0.01M） |

**为什么这些够用**：检测框是"几个框"、车道线是"160×160 二值图"、状态是"4 个数"——**信息量远小于图像**，不需要大网络。

---

## 4. ★ 推荐 Top 3（针对 ≤10MB + 多模态 + 30Hz + 自己训练）

### 🥇 方案 A：ShuffleNetV2 0.5x + 多分支头（**最省空间**）
- 图像骨干：ShuffleNetV2 0.5x（**2.28M / 4.73MB**）
- 车道线分支：3 层小 CNN（≈0.3M）
- 检测框分支：PointNet 风格 MLP（≈0.1M）
- 状态分支：MLP（≈0.01M）
- 融合头：FC（≈1M）
- **合计 ≈ 3.7M 参数 → FP16 ≈ 7.4MB** ✅ 留 2.6MB 余量
- **优点**：最小、有 ImageNet 预训练可用、CoreML 友好
- **缺点**：表达力弱于 RepVGG

### 🥈 方案 B：M2 已实现的 RepVGG-A0 轻量变体（**已落地**）
- 图像骨干：RepVGG-A0 瘦身版（**2.76M / 6.2MB**）
- + 车道线 / 检测框 / 状态分支
- **实测 FP16 ≈ 6.2MB** ✅
- **优点**：**已写好**（`src/model_v2.py`）、与项目现有风格一致、训练时可重参数化
- **缺点**：比 ShuffleNet 略大

### 🥉 方案 C：MobileNetV3-Small + 多分支头（**最稳**）
- 图像骨干：MobileNetV3-Small（**2.5M / 5.0MB**）
- + 多模态分支
- **合计 ≈ 3.9M → FP16 ≈ 7.8MB** ✅
- **优点**：有官方预训练、NAS 搜索过、[论文实测用于轻量任务](https://arxiv.org/html/2505.03303v1)
- **缺点**：hard-swish 激活在 CoreML 上可能略慢

---

## 5. 核心结论

1. **10MB 完全够用** —— 上述三方案都在 6-8MB，有 20-40% 余量
2. **不要用原版 RepVGG-A0**（8.0M / 16MB **超了**）—— 这就是 M9 有 15MB 的原因
3. **自动驾驶专用网络不能直接用**（都超 10MB + 输入不匹配），但可借鉴其**多模态融合思想**
4. **多模态分支本身很轻**（PointNet + 小 CNN + MLP 合计 <0.5M）—— 瓶颈在图像骨干
5. **M2 的 `model_v2.py` 已符合约束**（6.2MB / 五路输入）—— 可直接用，或换更小的 ShuffleNetV2 骨干再省 1.5MB

## 6. 未验证项（诚实标注）

- FastViT / MobileOne 具体参数量（未查）

## 7. 下一步建议

1. **优先用 M2 已实现的 model_v2**（已合规），先跑通训练流程
2. 若训练后发现精度不够 → 换 ShuffleNetV2 0.5x 骨干再试（省 1.5MB，可用于加深融合头）
3. **实测三个骨干在 M3 上的推理耗时**（`--perf-selftest` 同口径），再定最终选型
