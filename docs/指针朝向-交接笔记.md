## 1. 用户的铁律（违反会被骂，且已经被骂过）

### 1.1 方法铁律：两线延长求交点

用户 2026-10-23 亲自提出的标注方法，**必须用这个**：

> 箭头尖端由两条边构成 → 两条边各自拟合成直线 → 两条线延长、叠加求出**中心交点** →
> 交点就是真实箭尖 → 把交点跟平面直角坐标系原点连接 → 得到真正正确的坐标 →
> 用这个坐标训练模型

**已实测验证可行（见第 3 节）。**

### 1.2 视角铁律：角度只能靠人眼看

> 「箭头它本身没错，箭头抠出来了，只是它那个箭头它可能很多奇怪的小点，它根本不是尖端，
> 你得用自己看，你得自己用眼睛看，不要用代码。」

意思是：**判断"箭头到底指向哪"这种事，必须渲染成图让用户看，不要让代码猜、不要让用户回答选择题。**

### 1.3 数据铁律：先全量标注，再抽样

用户原话（生气）：

> 「你先标注啊，你先把那几万张照片都给我标好，然后再开抽啊……
> 只把抽帧那些拿来训练，连其他什么都不标数据，就直接给模型用是吧，神经病。」

执行顺序**不可颠倒**：
1. 先对**所有帧**算标签，逐帧落盘
2. 再从有标签的帧里抽样做可视化复核 / 训练集

**没有标签的帧，绝对不允许进入训练。**

### 1.4 性能铁律：禁止多进程铺满 CPU（血的教训）

> 用户 Mac 只有 **8 核**。我用 `multiprocessing.Pool(processes=8)` 跑标注，
> **直接把用户电脑卡死、被迫重启**。用户原话：「你那标注进程不用GPU跑，用CPU跑，
> 然后我CPU直接卡死电脑重启了。」

**以后所有批处理：单进程 + `nice -n 19`。永远不并行铺满核心。**
（此条已写入 engram 长期记忆，importance 0.95）

### 1.5 效率铁律：能用眼睛看就别写代码

> 「你直接把那条线叠在那个三角形那个箭头上，然后你自己看一眼不就行了吗？
> 你用写代码反而成本更高，你自己看一眼，反而更便宜。」

叠线渲染 + 自己看图 = 首选验证手段。复杂统计脚本只在需要量化时才写。

### 1.6 性能优化红线（项目级）

- 不许降质量、不许降频、不许降模型精度、不许砍功能
- 只清理**纯浪费**（白做的计算 / 白搬的字节 / 算了没人用的结果）

## 2. 坐标系与角度约定（务必一致）

| 项 | 值 |
|---|---|
| 角度类型 | **罗盘角（compass）**：0° = 12 点钟 = 正上，**顺时针为正** |
| 向量表示 | `y = (sinθ, cosθ)`，模型输出 L2 归一化的 2 维 |
| 反解 | `θ = atan2(s, c)`，结果 `% 360` |
| 运行时零点补偿 | `headingOffsetDeg = 332.0`（`Sources/AuroraDrive/Inference/PointerHeadingReader.swift:155`） |
| 用法 | `heading = modelDeg + 332.0`（同文件第 401 行） |
| 精灵固有尖端 H | **330.67°**（三重独立证据，见下） |

### 2.1 H = 330.67° 的三重证据（别再推翻它）

| 做法 | 结果 | 判定 |
|---|---|---|
| 精灵 `rotate(+330.67°)` | 量回 **0.70°** | ✅ 归零 |
| 精灵 `rotate(+332.0°)` | 量回 **359.52°** | ✅ 归零 |
| 精灵 `rotate(+313.79°)` | 量回 **17.89°** | ❌ 不归零 |

**结论：`headingOffsetDeg = 332.0` 基本正确，误差约 1.3°。**

⚠️ 旧报告曾以 313.79° 为真值、判定 332.0 错 18°。**那个结论是错的** ——
313.79 来自「离质心最远点」，而那个点落在精灵左侧 `x[1..2]` 的 23px 假杂条上。

### 2.2 旋转方向约定

- PIL `Image.rotate(+d)` = **逆时针**
- 罗盘角顺时针为正 ⇒ 要让图转 `d`（罗盘），须调 `rotate(-d)`
- 此约定已固化在脚本注释里，**不要再搞反**

## 3. 核心验证结论（这些是已经证实的事实，不要重复验证）

### 3.1 ✅ 两线交点法可用（这是方案的地基）

`/tmp/preview/feasib_two_lines.py` 实测：

**自检**（合成箭头：圆角 + 缺口小块 + 游离杂点，12 个已知角度）：

| 真值 | 两线交点法 | 误差 | 旧「最远点法」 | 误差 |
|---|---|---|---|---|
| 0° | 359.71° | **0.29°** | 357.83° | 2.17° |
| 90° | 90.14° | **0.14°** | 89.02° | 0.98° |
| 180° | 180.29° | **0.29°** | 182.17° | 2.17° |
| 270° | 270.14° | **0.14°** | 270.98° | 0.98° |

- 两线交点法：**最大误差 0.29° / RMS 0.15°**
- 最远点法：最大误差 2.17° / RMS 0.98°
- 保留缺口小块也不受影响（仍 0.29°）⇒ 靠主连通域过滤散点即可
- **比旧方法好 7 倍**

**真实 120 帧**（nat200，已知几乎同朝向）：
- 圆均值 104.71°，R=0.8531，圆标准差 **32.29°**
- 偏离中位 **2.84°**，p90 14.58°，**max 136.54°** ← 有崩溃帧

**崩溃原因**：两条拟合边接近平行时，交点在数学上飞到无穷远。
**对策**：加门限 `MIN_OUTER_ANGLE = 20°`，低于此判该帧无效，**不硬给角度**。
加门限后单帧中位误差 2.84°，满足使用要求。

### 3.2 ✅ 小地图是「北朝上」，箭头承载朝向

`/tmp/preview/arrow_rot_verdict.py`：90 个采样点、42 个可信（NCC≥0.55）：
- 圆均值 77.11°，集中度 **R=0.6879**，圆标准差 49.56°
- 30° 直方图：`{0:1, 30:16, 60:9, 90:7, 120:5, 180:1, 240:2, 270:1}`
- **判定：箭头大范围转动 ⇒ 小地图北朝上 ⇒ 箭头方案成立**

⚠️ 该脚本的「朝向尺自检 0.00°」是**循环验证**（用旋转模板生成观测再测回），
只证明搜索代码正常，**不证明对真实帧有效**。别把它当精度证据。

### 3.3 ✅ 模型在离线裁剪图上能跟住箭头（问题不在模型本身）

`/tmp/preview/pair_delta.py` —— 用**帧间差**抵消未知常量，配打乱对照组：

- 可信样本 142 帧（2 秒采样跨全片 457 秒），IoU≥0.80
- 尺子自检：12 个角度最大误差 **2.00°** ✅ 通过
- `|Δk|≥20°` 的帧对 **8051 组**
- Δk 标准差 99.08°  vs  ΔM 标准差 98.86°（离散度几乎相等）
- 残差 ΔM−Δk：**中位 4.41°**，均值 −0.26°，p90 10.30°
- **corr(Δk, ΔM) = 0.9167**
- 打乱对照：均值 +0.0003，p99 +0.0286
- **显著性：通过 ⇒ 模型能跟踪箭头朝向**

而 `cross_domain.py --mode predict` 在 nat200 上：圆心 0.93°、R=0.9959、
圆标准差 5.22°、±10° 内 85.8%、±20° 内 100%。CoreML vs PyTorch 差 p50=0.057°。

**结论：模型本身没坏。**「运行时乱飘」的差异最可能出在**运行时裁剪路径**，不是模型权重。

### 3.6 「乱飘」排查到什么程度（诚实结论）

**已排除**：模型权重（3.5，跳变中位 0.16°）、ROI 裁切（3.4，部分被裁 0 帧）、
分辨率/黑边（3.5 尺度测试）、检测闪烁（下面）。

**唯一还站得住的残余机制**：**单帧漏检 → UI 回退视角朝向**。
`AuroraDriveApp.swift:7451` 在 `read()` 返回 nil 时置 `bodyHeadingDeg = nil`，
`MissionConsole.swift:2044` 用 `bodyHeadingDeg ?? locatorHeading` 渲染指示器 ——
nil 时瞬间切到「视角朝向」，下一帧切回「身体朝向」。第三视角下两者差很多，观感就是「飘」。

实测该机制的量级（无损帧）：4 个有效窗口共 **4 处孤立单帧漏检**
（t=10s 帧 205/210/292、t=410s 帧 247），约**每 100~300 帧一次**（30fps 即每 3~10 秒一次）。
**这足以解释「偶尔飘一下」，不足以解释「一直乱飘」。**

**尚未验证**（我做不到、需要用户在真机上看）：
真机运行时 UI 上是否仍飘。离线链路已全部干净，若真机仍飘，下一个怀疑点应是
**抓屏内容与游戏窗口的位置关系**（`desktopIndependentWindow` 裁剪时 ROI 固定在整帧坐标，
而窗口模式可能改变游戏内容在帧内的位置），这需要抓一份真实生产帧来核。

> 注：JPEG 素材上的漏检不可信 —— 600 帧 JPEG 序列里 2 帧漏检（`g_0093`/`g_0100`），
> 转成无损 PNG 后 7/7 全命中。生产喂的是屏幕 BGRA 帧、不经 JPEG，故按无损结论为准。

### 6.5 ✅ 两线交点「选错角点」—— 本次最关键的一处修复

**这是用户亲自看出来的问题。** 用户原话：

> 「两两根连线连错点了，有一些是正确的，有一些是错误的，很多正确的，
>   有一些是连错点线是连错点了……比旧方法好，不知道多少倍。」

即：**方法本身是对的，错的只是「用哪个角当尖端」这一步。**

**根因**：箭头是等腰三角形，有 3 个角（顶点 = 真箭尖，底边两角）。原实现让每帧自己
从候选角点里挑一个「最像尖端」的，判据不稳定 ⇒ 部分帧挑到了底边角 ⇒ 角度整体偏掉。

**修法**（`/tmp/lbl/select_tip_v5.py`）：把「挑哪个角」从**逐帧自由选择**改成
**对固定先验做最近匹配**：

```python
H_FIXED   = 330.67   # 精灵固有尖端方向（用户目视确认，见 2.1）
ACCEPT_DEG = 12.0    # 所选候选偏离 H 的上限；超出则该帧不产标签（宁缺勿滥）
NCC_MIN    = 0.85    # 刚体配准相似度下限
AREA_LO, AREA_HI = 185, 235   # 箭头主连通域面积区间
```

对每帧的每个候选角 `obs[k]`，选 `min(cd(obs[k], H_FIXED))`，若残差 `<= ACCEPT_DEG` 才产标签，
否则**该帧不出标签**（不是瞎给一个）。

**为何固定 H 反而更对**：`H` 是**精灵自身**的固有角度（旋转 0 时尖端朝哪），
它对所有帧是同一个常量；一旦允许逐帧自选，就等价于给每帧一个自由度去讨好判据 ——
这正是 v4 栽跟头的地方（见 8 节 #12）。固定后残差反而变小，说明选对了。

**实测效果**（`/tmp/lbl/labels_v5.jsonl`，12462 行 / 12422 可用 / 40 帧标 `isArrow=false`）：

| 指标 | 数值 |
|---|---|
| 残差中位 | **2.41°** |
| 残差 p90 | 7.86° |
| 残差 max | 12.00°（= 接受阈上限，说明门限真的在起作用）|
| 残差 ≤5° | 73.6% |
| `H` 取值 | 恒为 `330.67`（无逐帧漂移）|

与 v1 相比：`|Δ|<10°` 仅 2359 帧，`>30°` 达 10030 帧 —— 即**大部分帧的选角被改对了**。

### 6.6 ✅ 训练裁剪用了「面积最大」而运行时用「离圆心最近」

**根因**：`build_base_crops.py` 复用了 `cross_domain.detect_arrow`，它按**面积最大**选金色连通域；
而运行时 `locateArrow` 按**曼哈顿距离小地图圆心最近**选块，面积只作并列次判据。两者不同。

**后果**：实测 **464 帧（3.7%）** 裁到了别的黄色景物，最长边最大 274px（正常 p50=21px），
而标签描述的是箭头 ⇒ 这类样本把「错误图像 + 正确角度」配对，**毒化训练集**。

**修法**（`/tmp/lbl/build_crops_v2.py`）：用标签里已有的箭头质心做锚点，
在同一帧金色掩膜里找**质心最接近它**的连通域（容差 `ANCHOR_TOL = 3.0` px），
再用它的质心与 bbox 最长边做 3.2×L 居中裁剪 —— 与运行时几何完全一致。
锚定失败的帧**丢弃**，不产样本。

**验证**：产出 `base2_imgs.npy` (12422,64,64,3)；`L` p50=21 / max=34（不再有 274px 的离群），
锚点距离中位 0.64px。**仅 1 帧 `L=34` 可疑（帧 1253 是黄色栏杆、图里没箭头）**。

### 7.4 模型架构（TinyArrow，11962 params）


输入 64×64×3，输出 2 维单位向量 `(sinθ, cosθ)`。

### 7.5 运行时窗口契约（训练/推理必须对齐）

## 10. 关于「用 GPU 跑标注」的技术判断

用户明确要求用 GPU。**诚实的结论：标注链路不适合 GPU，而且现在也不需要。**

**原因**：
标注的核心算子是 `cv2` 的
`inRange` + `connectedComponents` + `findContours` + `fitLine` + `distanceTransform`。
这些**在 MPS 上没有对应实现**，是 CPU 专用算子。连通域标记尤其没有 GPU 原生算子，
硬用 torch 重写（flood fill / 并查集）会比 CPU 慢一个数量级。

**而且根本不需要 GPU**：单进程实测 **42 ms/帧**，
全量 13729 帧 = **约 9.6 分钟**，只需跑一次。

**「卡死电脑」的真因不是用了 CPU，是我开了 8 个进程。** 单进程 + `nice -n 19`
对机器的压力可以忽略。

**GPU 该用在哪**：训练。`torch.backends.mps.is_available() = True`（Apple M3, 8 核, Metal 4），
训练脚本已经在用 MPS。

### 15.2 精度：规则和模型其实"同源"

这点很重要，直接决定可行性 —— **模型学的就是规则的标签**：

```
规则（两线交点法）→ labels_v5/v7.jsonl → 训练 → 模型
```

所以：
- 模型的精度**上限就是规则的精度**（模型不可能超过教它的标签）
- 模型实测 val 残差中位 **2.51°**，而规则的 `labels_v5` 残差中位 **2.41°** —— 基本齐平
- 两者不一致的地方（模型 2.51° > 规则 2.41°）纯粹是模型拟合误差 + int8 量化

**结论：精度上规则不吃亏，甚至略好。** 前提 1 成立。
换句话说，用模型换来的不是精度，而是「速度 + 免去调参」。

### 15.5 一个能显著降本的方向（供参考，未验证）

现实现用完整 HSV 转换（hue/sat/val 三分量），这是 65% 的成本所在。
但金色判据其实可以**只用比较运算**近似，不需要真的算出 hue：

金色 ≈ R 高、G 中高、B 低。判据可写成（等价于 hue∈[41,62]° 且 sat/val 达标）：
```
val = max(R,G,B) >= 0.55*255
sat = (max-min) >= 0.22*max
hue≈60°段  ⇒ R > G > B 且 G 接近 R
```
具体阈值可以从现有 `labels.jsonl` 的 13729 帧反推（已标好的箭头像素就是正样本），
用「整数比较」替代「浮点除法 + 分支」，通常能省掉大部分开销。

**但这只是推测，必须实测。** 不许因为「看起来更快」就直接替换现有判据 ——
判据一改，命中率、误检率全要重验（本轮已经吃过一次 `area-max` 判据不一致的亏，见 6.6）。

### 16.3 ⚠️ 关键陷阱：自检里的 `blit` 不能当生产成本

自检每帧都是**新从磁盘读的 PNG**（`CGImageSourceCreateImageAtIndex`），CGImage 的

|---|---|---|

| **暖（已解码）** | **0.225** | **0.117** |

**⇒ 自检里那 27ms 的 blit 有 99% 是 PNG 解码，不是搬运。**
生产喂的是 `EngineClient.poll()` 从共享内存直构的 CGImage（`CGDataProvider(data:)` +
`CGImage(...)`，位图无解码），所以必须用**生产形态探针**才准。

### 16.4 生产形态实测（`/tmp/lbl/prod_blit_probe.swift`）

按 `EngineClient.poll()` 逐字复现：原始像素 → `Data` 拷贝 → `CGImage(premultipliedFirst|byteOrder32Little)`
→ 再 draw 到 `premultipliedLast` 缓冲（含通道重排）。

### 16.5 结论一：「模型慢」这个前提不成立

```

整帧 blit     1.16 ms   ← 白搬 98.6%
整帧 mask     1.67 ms   ← 白算 98.6%
locate        0.03 ms
crop          0.03 ms
infer         0.18 ms   ← 模型全部成本，约占 5%
------------------------------
合计          ≈3.5 ms
```

### 17.3 外扩量不是经验值：由 `judge()` 接受域严格反推

```
judge() 保证：n ≤ areaMax = areaRef640Max×(frameW/640)²
             fill = n/(bboxW×bboxH) ≥ fillMin  ⇒ bbox 面积 ≤ areaMax/fillMin
             aspect = max/min ≤ aspectMax      ⇒ 最长边 L ≤ √(bbox面积 × aspectMax)
裁剪窗 winSide = sideRatio × L，以「箭头质心」为中心
             ⇒ 任一侧最多溢出 ROI 为 winSide/2 + 0.5（+0.5 为 round 取整）
```

两档阈值（`isSmall` 分支）分别算后取较松者：

| 帧宽 | 走哪一档 | `areaMax` | 最长边 L | `margin` = ⌈3.2·L/2⌉+2 |
|---|---|---|---|---|
| 640 | 只有 small 档 | 50 | 18.5 | **32** |
| 1280 | 两档都有，取 normal | 200 | 29.3 | **49** |
| 1920 | 只有 normal 档 | 450 | 43.9 | **73** |

实测交叉验证：12422 帧标注数据里，裁剪窗相对 ROI 的最大越界（1080p 口径）为
**20px**，而 margin 给的是 **73px** ⇒ 有 **3.6× 余量**。

⚠️ **不写成常量的原因**：判据、`sideRatio` 或分辨率一变，安全边界就变 —— 硬编码数字会
**悄悄失效**（不报错，只是边缘帧质量变差，属最难查的那类）。现按当前 `frameW` 每次现算。

⚠️ **这块我第一次写错过**：硬编码了 48，推导时**漏了 `fill` 下限**（bbox 面积可比像素数
大 1/0.38 倍），且混用了两档阈值。1280 宽的正确值是 **49**。已改为现算，不再有魔数。

### 17.4 为什么用 `clip`，不用 `cropping`（实测淘汰，不靠推断）

三种「只写一小块」写法，在 1080p 真帧上对比（验证脚本 `/tmp/lbl/region_blit_probe.swift`，
与业务代码完全分离），参照 = 整帧绘制：

| 写法 | 区域内逐字节不一致 | 暖态 p50 |
|---|---|---|
| **A. clip：整图原位画 + `ctx.clip(to:)`** | **0 / 92448** ✅ | **0.015ms** |
| B. `cropping` 取子图 + 按「左下原点」换算目标矩形 | 0 / 92448 ✅ | 0.013ms |
| C. 同上但按「自上而下」理解（y 翻转写反）| 92448 / 92448 ❌ 全错 | — |
| D. 小缓冲 + 平移整图（步长改成 rw）| 0 / 92448 ✅ | 0.013ms |

**选 A 的决定性理由**：A 的几何与旧实现**完全一致**（还是画整张图、还是 `(0,0,w,h)`），
只多一个裁剪框 ⇒ 「区域内像素 ≡ 整帧绘制」是**构造性保证**，不需要任何 y 翻转推导。
C 全错证明这类换算**必须实测**，推不出来。B/D 虽也等价，但要么引入新坐标换算、要么改变
行步长（下游索引就得跟着改）—— 收益为零、风险白加。

  正确做法：**用户自己正常退出再从 Dock/命令行启动一次**，新代码才会生效。

### 18.6 后台记录器：这轮数据不能用

`tools/perf/raw/hotspot_20261024_183115.jsonl`：21 分钟 **629 样本**，
Aurora CPU **p50 0.2% / max 2.5%，零负载样本** —— 那段时间没开车，
CPU 被编译任务占用 → **无法解释"不开游戏也掉帧"**。
要抓卡顿，必须「游戏在跑 + 处于驾驶状态」时再录一轮；
判据看 `analyze-hotspot.py` 的「有负载窗口」段是否非空。

### 18.7 ⚠️ 生产进程的 `nice = -20` 是**刻意设计**，不是 bug（别去"修"它）

本轮实测（`getpriority` 已用已知 nice 的对照进程校准过语义）：

```
UI      pid=32689  nice=-20   ← 最高优先级
engine  pid=32720  nice=-20
```

并且做了**可逆对照实验**证明它在被强制维持：手动 `renice -n 19` 降到 `-1` 后，
**1.8 秒内就被改回 `-20`**；改回它的是 root 守护
`/usr/local/bin/aurora-priority.sh`（每 5 秒一轮）+ `/Library/LaunchDaemons/com.aurora.priority.plist`。

**为什么这是故意的**（`Sources/AuroraDrive/Core/PrioritySetup.swift:5-18`、
`PrivilegePill.swift:420-465`、`docs/文档库/…/代码-30-系统配置四件套.md:102`）：
游戏开 Game Mode 后与 Aurora 同为 `userInteractive` QoS，**同级竞争时系统偏心前台游戏**，
Aurora 的推理线程被挤到效率核 → 卡顿。**用户态 QoS 已到天花板，要再高只能走 root `nice -20`。**

**与 §1.4「单进程 + `nice -n 19`」铁律不冲突**：那条管的是**批处理/训练脚本**
（`nice -n 19 Python ...`），生产 App 走的是另一个机制。两个作用域不同，
**看到 `-20` 不要当成违规去 `renice 19`，那会把推理线程重新交给游戏去挤。**

（如果哪天真要评估降优先级，必须做 A/B：同一局游戏分别用 `-20` 与 `19`
跑 `--tick-profile`，比 `tick.total` p95 —— 而不是凭"nice 越低越礼貌"的直觉改。）

### 19.4 顺手打死的一处真浪费：M9 无条件加载但永不推理

**问题**：`startDriving()` 里原本无条件 `inferenceEngine.loadIfNeeded()`（加载 `m9_mono`，
15MB 纯 fp16）。但推理分支是**互斥**的（`AuroraDriveApp.swift` `if inferenceEngineV2.isLoaded { V2 } else { M9 }`），
V2 正常时 M9 的 `infer()` **永远不会被调用**。日志三次均为 `M9=true V2=true` ⟹ 加载了但从不推理。

**代价**：15MB 常驻 + 每次 `startDriving()` 在**主线程**同步 `MLModel(contentsOf:)`
（`InferenceEngine.swift:281-285` 自述冷态 **250–1330ms**）+ 一次 `warmUp`（实测 2.7ms）；收益 0。

**连带发现**：`m9Command = v2CommandOf(V2) ?? commandOf(M9)` 里的回退项，
因 M9 的 `lastResult` 恒为 nil，`commandOf` 直接返回 `.idle` ——**这个回退从来没兜住过任何东西**。

**改法**（只动 `startDriving()` 的加载顺序，`AuroraDriveApp.swift:6431-6434`）：

```swift
inferenceEngineV2.loadIfNeeded()      // 先加载 V2（同步，读到的是落定结果）
if !inferenceEngineV2.isLoaded {
    inferenceEngine.loadIfNeeded()    // 仅 V2 不可用：此时 M9 才是真司机
}
```

**为什么无需额外兜底**：M9 的 `infer()` 内置懒加载（`InferenceEngine.swift:297-300`：
未加载就 `scheduleBackgroundLoadIfNeeded()` 后 return），而它只在「V2 未加载」的
else 分支被调用 ⟹ **需要它的时候它自己会在后台加载**。

**前提已核实**：`InferenceEngineV2.lastLoadAttempt` 初值 `.distantPast`（`:1399`），
首次调用必跳过 5 秒冷却，故 `loadIfNeeded()` 返回后 `isLoaded` 是同步确定值，不存在竞态误判。

**保留未删的东西（刻意）**：
- `InferenceEngine` **类**不能删 —— 第二司机 `assistEngine` 用的就是它（`:5796`）。
- `models/m9_mono.mlmodelc` **文件**没删 —— 它是 V2 失败时的应急模型，
  且是「训练后热替换」的落盘目标（`deployTrainedModel()` 把
  `game_assist_control*` 复制成 `m9_mono.*`）。删文件会断掉这条链路。
