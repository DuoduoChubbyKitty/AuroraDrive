## 5. 字段语义与断言前提（重要发现）

### 5.1 🔴 `frames` ≠ 抓屏帧数（task-63 断言前提有误）

| 项 | 事实 |
|---|---|
| `state.frames` 来源 | `st.recordEngine.frameCount`（`EngineMain.swift:1072`） |
| 语义 | **录制帧计数**，只在 `recording == true` 时递增 |
| 实测 | 未录制：`frames=0`（15s / 67 次轮询不动）；开录制后：**涨到 91** |
| 真正的"抓屏活着"证据 | `hasFrame: true` + `publishedSeq` 1130→1783→1800 + `fps≈29` + 日志 `📥 帧到达 #1200 status=valid` |

**判定**：task-63 把 `frames` 当作"抓屏帧数"来断言 —— **前提不成立**；但**抓屏本身是活的**（多条独立证据）。
**建议**：`state` 增加 `captureFrames`（真正的抓屏计数），或断言改用 `publishedSeq`。

### 5.2 🔴 未捕获时 `capture` 不校验窗口（谎报成功）

见 §3.10(b)：`ok=true` 但窗口不存在。**根因**：早退分支不设 `lastModeError`。

### 5.3 ⚠️ `ok=false` 时 `data.captureMode` 与实际不符

**实测**（捕获中反证后立刻查 state）：
```
ack 返回:  data.captureMode = "只录窗口 #999999999"   ← 请求的模式
           detail            = "…仍保持「录全屏」"     ← 实际结果（正确）
真实 state: captureMode = '录全屏'                    ← 实际生效的模式
```
**判定**：`detail` 正确，但 **`data.captureMode` 用了「请求的模式」而非「实际生效的模式」** →
调用方若只读 `data.captureMode`（不看 detail）会**误以为切换成功**。
**建议**：`ok=false` 时 `data.captureMode` 应回**当前实际生效**的模式。
