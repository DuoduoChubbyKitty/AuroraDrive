# 优化 · GPU 深挖实测（OPT-G2 · 2026-10-11）

> **任务**：task-101 · **类型**：只读实测（**未编译、未跑 app、未跑自检**）
> **方法**：`ioreg` / `system_profiler` / `ps` / `lsof` / 读 8 份已有报告
> **结论**：**GPU 从 AuroraDrive 侧已无显著可省空间。** 基线 63% GPU 是系统合成器 + 其他 App
> 撑起来的，AuroraDrive 只贡献 +8.5pp（且其中抓屏本身不可省）。P2 说的"配置已最优"成立。

## 0. 一句话结论

**GPU 没得省了——从 AuroraDrive 侧。**

当前 GPU 63% 基线里，AuroraDrive **根本没在跑**——这 63% 是 WindowServer（48.7% CPU 合成所有窗口）
+ DeepSeek Harness Renderer（25% CPU）+ 一堆 Electron 渲染进程撑起来的。
AuroraDrive 开抓屏只加 8.5pp（P5 实测），且其中 SCStream 抓屏是系统级 GPU 推流（P6 证实不可省）、
推理不碰 GPU（P4 证实）、CIContext 已改 CPU（源码已含 `useSoftwareRenderer: true`）。

**→ 在"不降帧率/不降分辨率"铁律下，GPU 侧已无优化空间。**

## 2. ★ 谁在吃这 63% GPU？（WindowServer + 渲染进程分析）

**命令**：`ps -eo %cpu,comm | grep -iE "Renderer|GPU|WindowServer|Metal"`

| 进程 | CPU% | 说明 |
|---|---|---|
| **WindowServer** | **48.7%** | 系统窗口合成器（管理所有窗口的 GPU 合成） |
| DeepSeek Harness Helper (Renderer) | **25.0%** | DSH 的 Electron 渲染进程（本工具自己） |
| ego Helper (Renderer) | 2.2 + 0.7 + 0.1... | ego lite 浏览器的多个渲染进程 |
| QQ Helper (Renderer) | 0.9 | QQ Electron 渲染 |
| WebKit.GPU | 0.0 | Safari 的 GPU XPC（空闲） |
| **总和** | **75.5%** | — |

**→ GPU 的 63% 基线由 WindowServer（合成两块显示器 + 所有窗口）+ DSH Renderer + Electron 一族撑起。**
AuroraDrive **不在其中**（未运行）。

### WindowServer 48.7% CPU 正常吗？

**正常偏高**。WindowServer 管两块显示器：
- 内置 LCD 2560×1664 Retina
- 外接 DELL U2412M 1200×1920（旋转 90°）

旋转显示器 + Retina 缩放 = 合成负担比单屏重。加上开着 ego lite（多个渲染进程）、
QQ、DSH（Electron 全家桶），WindowServer 要合成大量图层。
**这不是 AuroraDrive 能控制的——是用户的系统环境。**

## 5. ★ 明确判断：GPU 还有可省空间吗？

### AuroraDrive 的 GPU 占用构成（全部已知项）

| GPU 占用源 | 占比（估算） | 可省？ | 依据 |
|---|---|---|---|
| SCStream 抓屏本身 | ~8.5pp 的大部分 | ❌ **不可省** | P6：推流模式，系统级 GPU 采集，只有 `.idle` 能省 |
| CoreML 推理 | 0 | — | P4：6 组件全 0 GPU 算子 |
| CIContext 图像预处理 | 0（已改 CPU） | — | 源码已含 `useSoftwareRenderer: true` |
| vImage 缩放 | 0（CPU 而非 GPU） | — | P3：有意用 CPU 绕开 GPU 排队 |
| MetalGoose 插帧 | 未测 | ⚠️ 可能有用 GPU | P1 标注"超范围"；本次未测（**不跑 app**） |

### 结论

**在"不降帧率/不降分辨率"铁律下，GPU 从 AuroraDrive 侧已无显著可省空间。**

理由（三条，全部有实测/源码支撑）：
1. **推理不碰 GPU**（P4，6 组件全 0）→ 没有推理 GPU 可省
2. **CIContext 已改 CPU**（源码 `useSoftwareRenderer: true`）→ 唯一曾用 GPU 的预处理已消除
3. **SCStream 抓屏是系统级推流**（P6），**不可省**——帧已经采完送达 CPU 才能判断"有没有变化"，GPU 工作已经做完了

**剩下的 +8.5pp 就是 SCStream 抓屏本身的 GPU 成本，无法在不降帧率/分辨率的前提下消除。**

### 唯一未排除项

**MetalGoose 插帧引擎**：P1 标注"GPU 侧成本未测（超范围）"。MetalGoose 用 MTKView 渲染，
理论上会用 GPU。但本次**不跑 app**（铁律），无法实测。
→ **标注为"未验证"，不编数据。** 若要验证，需在 P5 同等条件下单独测 MetalGoose 开/关的 GPU 差值。

## 6. 为什么 63% 基线这么高？（系统环境分析）

**这不是 AuroraDrive 的问题，是用户的系统环境**：

| 因素 | 影响 | AuroraDrive 能控制？ |
|---|---|---|
| 双显示器（2560×1664 + 1200×1920 旋转） | WindowServer 合成负担翻倍 | ❌ |
| 旋转显示器 | 合成需要额外变换 | ❌ |
| Electron 全家桶（ego lite 多进程 + QQ + DSH） | 每个都有 Renderer 进程吃 GPU | ❌ |
| WindowServer 48.7% CPU | 合成所有窗口图层 | ❌ |

**→ 如果用户想降 GPU 基线，关掉不用的 Electron App / 拔掉旋转显示器，比优化 AuroraDrive 有效得多。**
但这是用户的系统使用习惯，不是代码能改的。
