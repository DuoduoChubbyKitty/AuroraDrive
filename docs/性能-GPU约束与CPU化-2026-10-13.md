## 1. 「推理不碰 GPU」约束的落实情况

### 1.1 CIContext 使用点清单（全仓库）

| 文件 | 行号 | 性质 | 是否热路径 |
|---|---|---|---|
| `ConfidenceEstimator.swift` | 228 | `brightnessContext`（`useSoftwareRenderer:true`） | 热路径，**但默认不走**（见 §2 已移除） |
| `SpeedOCRReader.swift` | 806 | `ciContext`（`useSoftwareRenderer:true`） | 15Hz，**默认不走**（`AURORA_OCR_CI=1` 才走，`SpeedOCRReader.swift:941`） |
| `CaptureEngine.swift` | 1123, 1157 | 仅注释引用血案；实际用 `vImageScale_ARGB8888`（CPU） | 热路径，**已无 CIContext 调用** |
| `RecordEngine.swift` | 600 | 注释明示「无 CIContext、无方向翻转」 | 录制路径 |

热路径上**真正还在调 CIContext 的代码已为零**：两处 `CIContext(options:)` 实例仅作回退路径保留，默认分支全部改走纯 CPU。

### 1.2 各推理引擎 computeUnits 设置

| 引擎 | 文件:行号 | computeUnits | 是否硬保证零 GPU |
|---|---|---|---|
| InferenceEngineV2 世界模型 | `InferenceEngineV2.swift:1693` | `.cpuOnly` | ✅ 硬保证 |
| InferenceEngineV2 multi_split enc | `:1734` | `.cpuAndNeuralEngine` | ✅（ANE 不含 GPU） |
| InferenceEngineV2 multi_split tf/chunk1~6/head | `:1738,1744,1748,1799,1802` | `.cpuOnly` | ✅ 硬保证 |
| InferenceEngineV2 主模型（同步/后台兜底） | `:1714,1862` | `.all` | ❌ 依赖 CoreML 调度 |
| InferenceEngine（M9） | `InferenceEngine.swift:164,206` | `.all` | ❌ 依赖调度，注释「优先 ANE」 |
| YoloEngine（YOLO26S） | `YoloEngine.swift:180` | `.all` | ❌ 依赖调度 |
| YolopxEngine（A-YOLOM/legacy） | `YolopxEngine.swift:734` | `.all` | ❌ 依赖调度 |

**结论**：硬保证零 GPU 的是 V2 的世界模型与 multi_split 子模型（CPU/ANE）；主驾驶模型族（M9/YOLO/YOLOPX）统一用 `.all`，交给 CoreML 内部按算子 `supported_compute_devices` 选 ANE/CPU，**不主动指定 GPU**。`YolopxEngine.swift:720-734` 实测说明 `.all` 是让 CoreML 自选最优，人工指定 `.cpuOnly` 反而慢（548ms+）。

## 2. 已做的 CPU 化改造

### 2.1 ConfidenceEstimator.averageBrightnessViaCPU（像素指针抽样）
`ConfidenceEstimator.swift:274`。从 `cgImage.dataProvider` 拿字节指针（`279-281`），按步长抽样约 4096 点（`290 step = max(1, total/4096)`）；按 `bitmapInfo.byteOrder32Little` 判定 BGRA/ARGB（`295-301`），直接读 `base[offset+bIdx/gIdx/rIdx]`（`312-314`），Rec.601 加权（`323`）。开销约 0.05ms（注释 `260`）。血案调用栈见 `244-247`：679 采样点全卡在 `CIContext.render → CI::MetalContext::readback_bitmap → _MTLCommandBuffer waitUntilCompleted`。

### 2.2 SpeedOCRReader.cgImageFromPixelBuffer（CVPixelBuffer memcpy）
`SpeedOCRReader.swift:823`。`CVPixelBufferLockBaseAddress`（`838`）→ 取 `base`（`840`）→ 预分配 `dst` 数组（`844`）→ 逐行 `memcpy`（`847-850`）→ `CGContext.makeImage()`（`855-862`）。小 ROI（102×42）拷贝量约 17KB。替代原 `ciContext.createCGImage`（`944`，仅 `AURORA_OCR_CI=1` 走）。

### 2.3 InferenceEngineV2.preprocessPixelBuffer（预分配）
`InferenceEngineV2.swift:3012`（`nonisolated(unsafe) static var`）。`preprocessImage`（`3026` 注释「原实现每帧 `var pixelData = [UInt8](...)`」）改为懒重建（`3033` 仅在 `count != needed` 时重建）→ `withUnsafeMutableBufferPointer` 复用（`3039`）→ 三平面写入（`3073-3075`）。提交 `a5f7a3a perf: preprocessImage预分配——省4.6MB/s堆分配`。

## 3. CIContext 在 Apple Silicon 的问题

根因证据：`ConfidenceEstimator.swift:251-255` 与 `SpeedOCRReader.swift:813-815` 同引官方头文件 `CIContext.h:184` 原文：

> Note: This option has no effect if the platform does not support OpenCL.

**Apple Silicon 无 OpenCL** → `.useSoftwareRenderer` 被系统静默忽略 → 照样走 Metal（GPU）。结论：**只要用 CIContext 就无法保证不碰 GPU，唯一可靠做法是不用 CIContext**（`ConfidenceEstimator.swift:255`、`SpeedOCRReader.swift:933`）。`CaptureEngine.swift:1123` 的 vImage 缩放即为绕开 GPU CIContext 才改。

## 4. 进程优先级对抗

### 4.1 GameModeDefender（用户态，无需 root）
`GameModeDefender.swift`。
- **nice=-20**：`166-169`，`getpriority` 不等 -20 则 `setpriority(PRIO_PROCESS,0,-20)`。
- **beginActivity**：`175-178`，options=`[.latencyCritical,.userInteractive,.idleSystemSleepDisabled]`。
- **静音音频**：`109-148`，`AudioQueueNewOutput`（`122`）+ 两块 11025 帧零填充 buffer（`129-139`）。理由（`12-17`）：CoreAudio 线程实时优先级且不需 root，且 audible 是 App Nap 独立豁免项。
- **复查周期**：`152-158`，`DispatchSource` 定时器 `repeating: 3.0, leeway: .milliseconds(200)`。每 3 秒复查 nice / activity token / 静音音频，被改动立刻设回（`162-191`）。

### 4.2 PrioritySetup（root 级 renice 守护）
`PrioritySetup.swift`。
- 机制（`12-16`）：安装 `/usr/local/bin/aurora-priority.sh`（`25`）root 常驻循环，每 5 秒把 `AuroraDriveUI`（含 `--engine` 子进程）renice 到 -20。
- LaunchDaemon：`/Library/LaunchDaemons/com.aurora.priority.plist`（`26`），`RunAtLoad+KeepAlive` 开机自启、崩溃拉起。
- 实际 renice 命令见 `PrivilegePill.swift:425`：`renice -n -20 -p "$pid"`。
- 诊断：`currentNice(pid:)`（`62-73`）经 `sysctl KERN_PROC` 读 `kp_proc.p_nice`。

## 6. 抓屏帧率与推理 tick 的对齐关系（含 45→20 改动）

### 6.1 历史与最新定档
- 提交链：`b552c0c feat: 20Hz定档` → `69bf409 perf: 抓屏频率对齐推理 20Hz + 应急爆发联动`。
- 踩坑记录（`EngineMain.swift:614-619`）：曾把 tick 一起改成 45 → 45Hz 预算 22.2ms，单帧实际 36.9ms → 游戏掉到 1-2 帧。
- 最终定档（`EngineMain.swift:647-649`）：两档推理 **20Hz**；区别只在抓屏帧率与模型大小。

### 6.2 当前映射函数（代码现状）
`EngineMain.swift`：
- `tickHz(forPerceptionMode:)`（`759-765`）：`ayolom`→20 / `legacy`→20。
- `captureHz(forPerceptionMode:)`（`770-776`）：`ayolom`→20 / `legacy`→20。
- `baseCaptureHz`（`674`）= `20.0`；`lastAppliedCaptureHz`（`667`）= `20.0`。

> 注：`:789`、`:647-648` 注释仍残留「ayolom 抓屏 45fps」旧表述，系 69bf409 改 capture 为 20 后注释未同步；**以代码函数体为准**。

### 6.3 抓屏配置落点
`CaptureEngine.swift:597-598`：`let tscale = max(1, Int(safeHz.rounded()))`；`config.minimumFrameInterval = CMTime(value: 1, timescale: CMTimeScale(tscale))`。`setCaptureHz(_:)`（`~632`）热切换，但 `:632` 注释标注 `minimumFrameInterval` 热更是否生效**未验证**。

### 6.4 应急爆发联动
`EngineMain.swift:1185-1210`。`wantCapHz = EmergencyTakeover.shared.sprinting ? EmergencyTakeover.sprintHz : EngineMain.baseCaptureHz`（`1205-1206`）。状态对应（`1196-1199`）：
- cruise：tick 20 / 抓屏 20（对齐不浪费）
- sprint：tick 45 / 抓屏 45（一起冲，抗系统）
- yield（用户接管）：tick 5 / 抓屏 20

`sprintHz = 45.0`（`EmergencyTakeover.swift:56`）。只在值真变时触发一次 `setCaptureHz`（`1207-1210`），避免每帧派发 Task。
