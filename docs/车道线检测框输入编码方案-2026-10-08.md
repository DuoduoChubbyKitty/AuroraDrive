# 车道线 + 检测框 → 神经网络 · 输入编码方案（M6 产出）

> **日期**：2026-10-08
> **作者**：M6 输入编码设计员（蓝色大肥鱼）
> **定位**：**M2 模型架构的输入规格依据**。本文只定义「怎么把现有数据结构编码成张量」，不含模型结构、不含训练、不改任何代码。
> **上游事实源**：[车道线外推-坐标契约-2026-10-07.md](车道线外推-坐标契约-2026-10-07.md)、[性能优化总结-2026-10-07.md](性能优化总结-2026-10-07.md)
> **一句话结论**：**裁掉 letterbox 灰边 → 64×64 软降采样车道线 + 16 槽位检测框向量 + 20 维自车状态，三路 concat 融合**。编码总开销 ≤0.20ms，为 M2 前向留下 ≤3ms 预算。

---

## 0. 先钉死三条事实（后面所有设计都从这儿推）

### 事实 1：三套输入的数据结构（已核实，非推测）

| 输入 | 类型 | 定义位置 | 关键字段 |
|---|---|---|---|
| 车道线 | `MaskGrid` | [`YolopxEngine.swift:45-76`](../Sources/AuroraDrive/Inference/YolopxEngine.swift) | `width`/`height`/`cells:[UInt8]`（行优先，0=背景 1=前景），`index = y*width + x` |
| 检测框 | `Detection` | [`RuleController.swift:29-55`](../Sources/AuroraDrive/Agent/RuleController.swift) | `x/y/width/height`（**归一化 [0,1]**）、`label: Label`（car/pedestrian/sign/obstacle）、`confidence`、`rawName` |
| 光流 | `OpticalFlowReading` | [`OpticalFlowBridge.swift:45-67`](../Sources/AuroraDrive/Inference/OpticalFlowBridge.swift) | `dx`/`dy`（**640 像素**，非归一化）、`divergence`、`timestamp`、`magnitude` |
| 自车运动 | `EgoMotionEstimate` | [`EgoMotionModel.swift:63-85`](../Sources/AuroraDrive/Inference/EgoMotionModel.swift) | `forwardRate`、`lateralRate`（**归一化/秒**）、`dt`、`confidence`、`isUsable` |

**空值语义**：`MaskGrid.empty = MaskGrid(width:0, height:0, cells:[])`（[`YolopxEngine.swift:82`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)）。检测框 0 个 = `[]`，合法常态而非异常。

### 事实 2：★ 坐标系不匹配 —— 本方案最重要的一条

| 数据 | 实际坐标系 |
|---|---|
| `MaskGrid` | **letterbox 640 空间**，含灰边。`(gx,gy) → 640px (4gx, 4gy)`，stride = `640/160 = 4`（[`YolopxEngine.swift:262-263`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)、[`LaneExtrapolator.swift:43-48`](../Sources/AuroraDrive/Perception/LaneExtrapolator.swift)） |
| `Detection` | **原帧归一化**，已剔除灰边。`nx = (px - padX)/ratio/srcW`（[`YolopxEngine.swift:115-119`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)） |

**把两者直接 concat 会错位最多 46 个格（184 px）**，这是必须处理的硬伤。

**★ 但这里有个免费的好消息**：因为 `newW = round(srcW × ratio)`，所以

```
nx = (px − padX) / ratio / srcW  ≡  (px − padX) / newW  ≡  有效内容区内的归一化坐标
```

即 **`Detection.x/y/w/h` 本身就是「裁掉灰边后的有效区归一化坐标」**。只要把 `MaskGrid` 裁到有效区再降采样，检测框**零换算**直接可用。这是本方案选择「裁剪」而非「补零对齐」的决定性理由。

**灰边有多大（实测推算）**：

| 源分辨率 | ratio | newW×newH | padY(640) | 灰边占 160 网格 |
|---|---|---|---|---|
| 1280×720 | 0.5 | 640×360 | 140 | 70/160 行 = **43.8%** |
| 1920×1080 | 0.3333 | 640×360 | 140 | 70/160 行 = **43.8%** |
| 1280×800 | 0.5 | 640×400 | 120 | 60/160 行 = 37.5% |
| 2560×1080 | 0.25 | 640×270 | 185 | 92/160 行 = **57.8%** |

⟹ **最多 57.8% 的网格是恒定零填充**。喂进去 = 白烧算力 + 给网络一个恒定的无信息边框。裁剪是零成本的净收益。

### 事实 3：时间预算（33ms @30Hz）已被现有链路吃掉大半

| 阶段 | p50 实测（基线→优化后） | 出处 |
|---|---|---|
| `infer.yolopx` | 22.647 → **19.245ms** | [性能优化总结](性能优化总结-2026-10-07.md):22 |
| `infer.yolo26s` | 14.065 → **11.874ms** | 同上:23 |
| `opticalflow` | 6.171 → **1.001ms** | 同上:20 |
| `tick.loop` | 6.275 → **1.074ms** | 同上:21 |
| `infer.m9`（现有 e2e） | 4.099 → **3.268ms** | 同上:24 |

**推论**：
1. 检测网与车道线网都已被 P1 降频到 **15Hz**（`detectDecimate = 2`，[`AuroraDriveApp.swift:5395-5400`](../Sources/AuroraDrive/App/AuroraDriveApp.swift)）——即**每 2 个 30Hz tick 才产出一份新真值**。M2 若沿用同一档位，其编码与前向也只需在真值帧上跑一次，中间帧由 `LaneExtrapolator` 外推补足（[`LaneExtrapolator.swift:30-38`](../Sources/AuroraDrive/Perception/LaneExtrapolator.swift)）。**这是本方案把预算定得较宽的前提，M2 若要求 30Hz 逐帧提交则需重新核算。**
2. M2 自己的前向预算**必须 ≤3ms**（对齐现有 `infer.m9` 的 3.268ms 量级），编码开销**必须 ≤0.20ms**（见 §5.4）。
3. 这是**否决 attention 类融合的量化依据**（见 §4）。

## 1. 车道线编码：3 个备选

### 备选 a) 直接 `[1,160,160]` 过小 CNN

**做法**：`cells:[UInt8]` 逐元素转 Float32 → `[1,1,160,160]`（或 `[1,160,160]`）。

**优点**
- 零信息损失，无手工特征。`cells` 是行优先连续数组，直接 `memcpy` 级转换（[`YolopxEngine.swift:49`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)）。
- 空输入天然安全：`.empty` → 全零张量。

**缺点**
- **37.5%~57.8% 的网格行是 letterbox 灰边**（事实 2），纯浪费且引入无信息常量边框。
- 与 `Detection` 坐标系不一致，必须额外做框→网格映射，且映射里要带 `padY` 偏移（易错点）。
- **时间冗余**：车道线真值只有 15Hz（`detectDecimate=2`），中间帧是 `LaneExtrapolator` 用光流平移出来的近似（[`LaneExtrapolator.swift:30-38`](../Sources/AuroraDrive/Perception/LaneExtrapolator.swift)），30Hz 喂同一份信息没有新增信息量。
- **信噪比极差**：`laneRatio` 健康区间是 **[0.002, 0.25]**（[`YolopxEngine.swift:288/336`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)）。1280×720 时有效区 160×90 = 14400 格，取健康下限 0.002 → 只有约 **29 个前景格**，占有效区 0.2%。

**判定**：❌ 不作为 M2 主输入。**但它是正确的预处理源**。

> ⚠️ 澄清一个常见误判：**算力不是否决 a 的理由**。按 stride-2 stem + 3 个卷积块估算，160×160 输入的小 CNN 前向仅约 **16 MFLOPs**（stem 只占 0.92 MFLOPs），在 M3 ANE 上是亚毫秒级。否决 a 的真实理由是**灰边浪费 + 稀疏信噪比 + 时间冗余**，不是速度。

---

### 备选 b) 裁剪 + 降采样 `[1,64,64]` 或 `[1,40,40]`　★ 推荐

**做法**（4 步，全在 Swift 侧，纯函数）：
1. **裁剪**：用 `yolopxEngine.metrics`（[`YolopxEngine.swift:378`](../Sources/AuroraDrive/Inference/YolopxEngine.swift) 已公开 `private(set) var metrics`）算出有效网格区
   `vx0 = padX/4, vy0 = padY/4, vx1 = ceil((padX+newW)/4), vy1 = ceil((padY+newH)/4)`
   —— 与 `extractMask` 内部算 `validTotal` 用的是**同一组公式**（[`YolopxEngine.swift:1306-1312`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)），复用即不会错位。
2. **降采样**：**面积平均（soft），不做二值化**。160×90 → 64×64（16:9 时）。
3. **归一化**：除以 4×4 块的格数得到 `[0,1]` 浮点。
4. **输出** `[1, 1, 64, 64]` Float32，CHW 排布，与现有 `image [1,3,H,W]` 约定一致（[`InferenceEngine.swift:10`](../Sources/AuroraDrive/Inference/InferenceEngine.swift)）。

**★ 为什么必须「面积平均 + 不二值化」而不是「多数表决」**：
现有的 640→160 用 4×4 多数表决（`if positive*2 >= stride*stride`，[`YolopxEngine.swift:1335-1338`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)），因为 640 空间里车道线有 4~8px 宽，多数表决能活。**但 160→40 再做一次多数表决会让车道线整条消失**：160 空间里车道线只剩 1~2 格宽，在 4×4 块里最多 8/16 票，**永远达不到多数**。面积平均保留亚格证据（4/16 正 → 0.25），网络仍看得见。

**★ 为什么选 64 而不是 40（量化依据）**：
`laneRatio` 的分母是**有效区格数**而非全网格（`validTotal`，[`YolopxEngine.swift:1311-1313/1345`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)），1280×720 时有效区 = 160×90 = **14400 格**。取 `lanePositiveFloor = 0.002` 的最坏健康帧 → 约 **29 个前景格**。降到目标分辨率后：

| 目标 | 总格数 | 前景格（估算） | 判定 |
|---|---|---|---|
| **40×40** | 1600 | **≈3 格** | ❌ 严重混叠，帧间抖动会让 3 格变 1 格或 5 格 |
| **64×64** | 4096 | **≈8 格** | ✅ 可辨认（推荐） |
| 80×80 | 6400 | ≈13 格 | 更稳，但收益递减、成本 ×1.56 |

（1280×800 / 2560×1080 因有效区更小，绝对值略低，40×40 下同样是 3 格量级 —— 结论不随分辨率翻转。）

**优点**
- 消除 37.5%~57.8% 灰边浪费；**检测框坐标零换算直接可用**（事实 2）。
- 数据量 25600 → 4096（**6.25×**），编码耗时 ~0.1ms（vImage 单次 `vImageScale_Planar8`）。
- 软值天然表达「亚格置信」，与 `LaneFallback` 的连续帧确认纪律（[`LaneFallback.swift:19`](../Sources/AuroraDrive/Inference/LaneFallback.swift)）同精神。
- 空输入 → 全零，且尺寸恒定，**永不触发 shape 变化**。

**缺点**
- 裁剪依赖 `metrics` 正确；`metrics == .zero` 时（模型未加载）必须走空输入分支（已在 §5 护栏表覆盖）。
- 非等比缩放引入纵横比畸变（源分辨率变化时畸变率变化）→ 用 `ego_state[9] aspect` 维度让网络可条件化（见 §3）。

**判定**：✅ **推荐**。理由汇总：裁掉灰边（推算最多 57.8%）+ 检测框零换算对齐（事实 2 的恒等式）+ 保住稀疏下限（`lanePositiveFloor` 量化）+ 编码 ≤0.1ms。

### 备选 c) 参数化（多项式系数 / 消失点 + 每行中心偏移）

**做法**：对 `MaskGrid` 逐行求左右车道线中心 → 拟合 2 条三次多项式 → 输出 `[a0..a3]×2 + 消失点 (vx,vy) + valid 标志`，约 10~14 维。

**优点**
- 极紧凑，MLP 成本可忽略；可解释、可直接监督（与 `ControlCommand.steer` 有物理对应）。
- 天然抗噪：拟合平均掉了单格抖动。

**缺点（对现有数据结构的硬冲突）**
- **空/单线/多线都要处理**：`MaskGrid.empty` 是合法值，1 条线是常态（只看到一侧车道线），车道分叉时会出 3+ 条。参数化格式必须为每种情况定义槽位，失败模式复杂。
- **失败方向危险**：拟合失败或拟合到噪声 → **凭空造出一条车道线**。这与项目的显式红线冲突 —— `LaneExtrapolator` 明写「畸形掩码 → 返回 `.empty`，**绝不造车道线**」（[`LaneExtrapolator.swift:57-59`](../Sources/AuroraDrive/Perception/LaneExtrapolator.swift)），`LaneFallback` 的 fail-open 原则是「绝不猜一个方向」（[`LaneFallback.swift:12`](../Sources/AuroraDrive/Inference/LaneFallback.swift)）。参数化会把「猜」固化进输入编码。
- **引入第二事实源**：`RuleController` / `LaneFallback` 现在直接消费 `MaskGrid` 本身。参数化等于在输入侧再拟合一遍，两边口径可能不一致。
- **额外耗时**：逐行扫描 160×160 = 25600 次读 + 拟合，估计 0.2~0.5ms，是备选 b 的 2~5 倍，而信息量更少。

**判定**：❌ 不作为主输入。**但采纳其精神**：把 3 个廉价标量摘要（近端/远端车道中心偏移、航向误差）放进状态向量（§3 的 `ego_state[10..12]`）——它们只是**附加证据**，坏了就由 `lane_valid` 门控置零，不会替代掩码、不会造假。

## 2. 检测框编码：3 个备选

### 备选 a) 固定 N 槽位 × `[x,y,w,h,label,valid]` → MLP　★ 推荐

**做法**：按**紧迫度降序**排序，取前 N=16，不足补零，每槽 12 维：

| 槽内 idx | 字段 | 来源 | 归一化 |
|---|---|---|---|
| 0 | `x` | `Detection.x` | 已 [0,1]（事实 2：即有效区归一化） |
| 1 | `y` | `Detection.y` | 已 [0,1] |
| 2 | `w` | `Detection.width` | 已 [0,1] |
| 3 | `h` | `Detection.height` | 已 [0,1] |
| 4 | `conf` | `Detection.confidence` | 已 [0,1] |
| 5 | `urgency` | `Detection.urgency` | 已 [0,1]（[`RuleController.swift:65-69`](../Sources/AuroraDrive/Agent/RuleController.swift)） |
| 6 | `is_car` | `label == .car` | one-hot |
| 7 | `is_pedestrian` | `label == .pedestrian` | one-hot |
| 8 | `is_sign` | `label == .sign` | one-hot |
| 9 | `is_obstacle` | `label == .obstacle` | one-hot |
| 10 | `valid` | 该槽有框 ? 1 : 0 | {0,1} |
| 11 | `reserved` | 0 | 预留给 v2（如 track id / 帧间速度） |

输出 `[1, 16, 12]`。

**★ 排序键为什么用 `urgency` 而不是 `confidence`**：
`Detection.urgency = clamp(w·h·8·(1 − |x−0.5|·2), 0, 1)` 已经把「大（近）+ 居中」编码进去（[`RuleController.swift:65-69`](../Sources/AuroraDrive/Agent/RuleController.swift)），正是控制决策关心的量。`RuleController.decide` 自己也是按 urgency 取 `max`（[`RuleController.swift:120`](../Sources/AuroraDrive/Agent/RuleController.swift)）。按 urgency 截断 ⟹ **截断只会丢掉控制上最不相关的框**。用 confidence 截断则可能丢掉一个「低置信但正堵在车头」的框 —— 方向错误。

**优点**
- **定长、可静态声明 shape**，CoreML 编译期就能定死，ANE 友好。
- **0 个框天然安全**：全部槽 `valid=0`、其余位 0，不需要特判（这是空输入最好处理的一档）。
- 排序保证**确定性顺序**，消除了变长列表的置换歧义；并列时按 `(urgency, conf, x, y)` 稳定 tie-break。
- 成本可忽略：16×12 = 192 个 float。

**缺点**
- N 截断会丢框。缓解：`maxDetections = 300`（[`YolopxEngine.swift:278`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)）是硬上限，但实际行车场景（BDD100K 类）远达不到 16 个高紧迫框；且排序键已保证丢的是最不相关的。

**判定**：✅ **推荐**。

### 备选 b) PointNet 风格（每框 MLP + max pool）

**做法**：每框过共享 MLP（12→64→64），对所有框做 max pool → 全局框嵌入。

**优点**
- 真正的置换不变；理论支持无界 N；是处理点集的标准做法。

**缺点（对这个仓库是决定性否决）**
- **「天然变长」的优势已被现有代码消灭**：`maxDetections = 300` 是硬上限（[`YolopxEngine.swift:278`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)、[`YoloEngine.swift:77`](../Sources/AuroraDrive/Inference/YoloEngine.swift)），且 `parse` 结尾就是 `dets.sorted{...}.prefix(maxDetections)`（[`YoloEngine.swift:790`](../Sources/AuroraDrive/Inference/YoloEngine.swift)）。既然**输入本来就已被截断成定长**，PointNet 还要再 pad 到 N_max —— 那就是备选 a 再加一层池化。
- **max pool 丢信息**：池化后只剩「最强的那个框」，丢掉框数量与多目标共存结构。而「前方几辆车、各在哪」对控制是关键的。
- **CoreML 侧无收益**：可变 N 要么用 flexible shape（ANE 掉到 CPU 的风险），要么还是 pad。两条路都不比 a 好。
- 成本高于 a（每框 64 维 MLP + 池化），换来的是 a 已经具备的性质。

**判定**：❌ 否决。理由：**优势被 `maxDetections` 的既有限幅抵消，代价却是实打实的**。
> 折中采纳：在备选 a 的融合头里对 16 个槽做一次**带 `valid` 掩码的 max/mean pool**（§4），用极小代价拿到置换容忍性，同时保留逐槽向量。

---

### 备选 c) 转热力图 `[1, 4, 64, 64]`

**做法**：把每个框栅格化成 blob，按 label 分 4 通道，`confidence` 作为强度。

**优点**
- **与车道线张量空间对齐** → 可与车道线通道 concat，共享同一个 CNN 主干，融合「免费」。
- N 不变，0 框天然安全（全零）。
- 保留了「哪里有什么」的空间关系。

**缺点**
- **坐标必须换算**：`Detection` 是原帧归一化，掩码（若未裁剪）是 letterbox 空间。**若先执行 §1 的裁剪，则框坐标零换算**（事实 2）—— 这一条缺点在本方案里被 §1 的裁剪消掉了。
- **细框混叠**：归一化后远处行人的框可能只有 0.02×0.06 → 在 64×64 上仅 **1.3×3.8 格**；栅格化后塌成 1~2 格，**形状信息全丢**，且帧间会闪烁。
- **置信度与几何被混为一谈**：强度同时编码「多确定」和「框多大」，网络难以解耦。
- **精度损失**：控制需要「前车距离」这类度量信息，热力图把连续几何量化到 1/64 分辨率，比向量编码粗得多。
- **每帧多一次栅格化开销**（N 个框 × blob 填充）。

**判定**：⚠️ **不作为主编码，但作为 v2 的可选辅助通道**。它的「空间对齐 + 融合免费」优点是真的，代价是精度。推荐路线：v1 只用备选 a；若 M2 实测出现「框与车道线的空间关联学不会」的具体失败模式，再加 `[1,4,64,64]` 热力图通道。

## 3. 状态向量 `ego_state`：20 维

**设计依据**：现有 `InferenceEngine` 已有 `vehicle_state [1,6]` 的先例（[`InferenceEngine.swift:11-12`](../Sources/AuroraDrive/Inference/InferenceEngine.swift)、[`tools/convert_e2e_to_coreml.py:11`](../tools/convert_e2e_to_coreml.py)），其 6 维定义为：

```
[speed_norm, curvature*5, sin(heading), cos(heading), speed_limit_norm, reserved]
```

实现见 [`InferenceEngine.swift:431-436`](../Sources/AuroraDrive/Inference/InferenceEngine.swift)。**关键观察：第 1/2/3 维现在被硬编码为 `0.0 / 0.0 / 1.0`，注释写明「无遥测→0」。** 这既是沿用格式的理由，也是 M2 的真实增量机会 —— 航向/曲率可以从车道线掩码本身估出来（§3 的 10~12 维）。

| idx | 名称 | 定义 | 数据来源 | 归一化 / 范围 |
|---|---|---|---|---|
| 0 | `speed_norm` | 有效车速 | `DriveState.effectiveSpeed`（km/h，[`AuroraDriveApp.swift:5027`](../Sources/AuroraDrive/App/AuroraDriveApp.swift)） | `clamp(v/120, 0, 1)`（**沿用现有 120 上限**） |
| 1 | `speed_valid` | 速度是否新鲜可信 | `DriveState.speedValid`（OCR 新鲜：`lastResultTime<0.5s && conf>0.3`） | {0, 1} |
| 2 | `speed_limit_norm` | 限速 | `DriveState.speedLimit`（默认 120） | `clamp(v/120, 0, 1)` |
| 3 | `accel_norm` | 纵向加速度 | 由 `effectiveSpeed` 差分 + EMA 平滑导出 | `clamp(a/10, -1, 1)`（10 m/s² ≈ 1g） |
| 4 | `lateral_rate` | 横向运动率 | `EgoMotionEstimate.lateralRate`（归一化/秒） | `clamp(r/2.0, -1, 1)`（**2.0 是模型自己的越界阈值**，[`EgoMotionModel.swift:262`](../Sources/AuroraDrive/Inference/EgoMotionModel.swift)） |
| 5 | `forward_rate` | 前向运动率 | `EgoMotionEstimate.forwardRate` | `clamp(r/0.5, -1, 1)`（**0.5 = `maxForwardRate` 默认值**，[`AuroraFlags.swift:238`](../Sources/AuroraDrive/Core/AuroraFlags.swift)） |
| 6 | `ego_conf` | 自车运动置信度 | `EgoMotionEstimate.confidence` | 已 [0,1] |
| 7 | `lane_ratio` | 车道线前景占比 | `yolopxEngine.laneRatio` | `clamp(r/0.25, 0, 1)`（**0.25 = `lanePositiveCeil`**，[`YolopxEngine.swift:336`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)） |
| 8 | `lane_valid` | 车道线可信度（**分级**） | 0=空/畸形；0.5=外推帧；1=真值帧 | {0, 0.5, 1} |
| 9 | `aspect` | 有效区纵横比 | `metrics.newW / metrics.newH` | `clamp(ar/2.0, 0, 1)`（16:9→0.89，4:3→0.67） |
| 10 | `lane_offset_near` | 近端车道中心横向偏移 | 由 `MaskGrid` 在近端行（裁剪区 y≈0.90）求前景质心 | `clamp((c−0.5)·2, -1, 1)` |
| 11 | `lane_offset_far` | 远端车道中心横向偏移 | 同上，远端行（y≈0.55） | `clamp((c−0.5)·2, -1, 1)` |
| 12 | `heading_err` | 车道走向 vs 自车航向 | `atan((off_near − off_far)·k)`，k 由两行间距定 | `clamp(θ/(π/4), -1, 1)` |
| 13 | `box_count_norm` | 有效框数量 | `min(detections.count, 16)/16` | [0, 1] |
| 14 | `prev_steer` | 上一帧转向 | `ControlCommand.steer`（左负右正） | 已 [-1, 1] |
| 15 | `prev_throttle` | 上一帧油门 | `ControlCommand.throttle` | 已 [0, 1] |
| 16 | `prev_brake` | 上一帧刹车 | `ControlCommand.brake` | 已 [0, 1] |
| 17 | `is_degraded` | 感知降级标志 | `yolopxEngine.isDegraded`（[`YolopxEngine.swift:1095`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)） | {0, 1} |
| 18-19 | `reserved` | 预留 | 0 | 加维不换 shape |

**设计说明（每条都对应一个现有事实）**
- **0/2 维沿用 120 上限**，与 `InferenceEngine` 现有口径一字不改，避免 M2 与 m9 之间出现两套速度语义。
- **4/5 维的除数直接取自模型自己的阈值**（2.0 / 0.5），不是拍脑袋 —— 这样「越界」在归一化后恰好落在 ±1 边界外，网络看到的饱和点与 `EgoMotionModel` 的判废点一致。
- **7 维用 `lanePositiveCeil = 0.25` 做分母**，因为 `laneRatio` 高于 0.25 即判为「车道线头异常膨胀」并置 `isDegraded`（[`YolopxEngine.swift:1091-1092`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)），所以 0.25 是真实的语义满量程。
- **8 维做成 0/0.5/1 三档而非布尔**：`LaneBridge` 明确区分「真值帧」与「外推帧」并记录 `lastGroundTruthTime`（[`LaneBridge.swift:69-78`](../Sources/AuroraDrive/Perception/LaneBridge.swift)），M2 应当知道当前车道线是**测出来的还是推出来的**，因为外推误差会累积。
- **10~12 维是备选 c 的「廉价版」**：只在 2 行上求质心（2×160 次读，<0.05ms），不拟合多项式、不生成第二事实源；`lane_valid == 0` 时强制置 0。
- **14~16 维是时序平滑的必要输入**：项目现状是「规则/模型每帧独立出 `ControlCommand`」，M2 若不带上一帧动作，转向极易在 15Hz 感知下抖动。这是 openpilot 类端到端模型的标配输入。
- **18~19 维 reserved**：镜像现有 `vehicle_state[5] = reserved` 的先例（[`InferenceEngine.swift:436`](../Sources/AuroraDrive/Inference/InferenceEngine.swift)）。CoreML 的输入 shape 变更 = 重新导出 + 重新训练，留 2 维是极便宜的保险。
- **3 维 accel 标注为低置信**：速度来自 15Hz OCR，量化步长 ±1~2 km/h（[`SpeedOCRReader.swift:112`](../Sources/AuroraDrive/Inference/SpeedOCRReader.swift)），差分后噪声大，必须 EMA 平滑；且 `speedValid == 0` 时置 0。

## 4. 融合方式：**concat（早融合 + 语义融合双层）** ★ 推荐

### 候选与裁决

| 方案 | 成本 | 裁决 |
|---|---|---|
| **concat** | 极低（一个 128→64 MLP，微秒级） | ✅ **推荐** |
| attention（自注意力） | 中 | ❌ 见下 |
| cross-attention（框 ↔ 车道线） | 中高 | ❌ v1 不用，留作 v3 |

### ★ 为什么否决 attention —— 本项目有硬证据

本仓库已有实测结论：`yolopx` 模型里 **PSA 模块的 `softmax×4 + reduce_sum×4` 在静态 cost 表里只占 3.9%，但实测烧掉 63~70ms，占墙钟 72%**，差 18 倍，是「真实 ROI 最高、且是唯一能同时改善延迟与抗干扰性的方向」（[yolopx-作战手册](../docs/文档库/神秘乱七八糟的文档/历史归档/02-探索文档-直属/yolopx-作战手册.md):260-262、:305）。

⟹ **在这个项目里，`softmax`/`reduce` 是已被实测钉死的 CPU 侧性能杀手**。而 attention 的核心算子就是 `softmax(QKᵀ/√d)·V`。在 33ms 总预算、`yolopx` 已占 19ms 的前提下，为一个**输入维度本来就低**（车道线 1 通道 + 16 个框 + 20 维状态）的问题引入 attention，是拿确定的性能风险换不确定的精度收益。

### 为什么 concat 在**精度上也不亏**

attention 的价值在于「在长序列里找远程依赖」。本问题的输入是：
- 车道线：**1 个空间张量**，不是序列；
- 检测框：**16 个已按紧迫度排序**的向量；
- 状态：**20 维标量**。

三者都低维、且**已经空间对齐**（事实 2：裁剪后框坐标与掩码同系）。没有「需要注意力去匹配的长程 token 对」。而「哪个框压在哪条车道上」这类空间关系，**用空间 concat 就让 CNN 免费学到**，不需要显式注意力。

### 推荐结构（只定义输入侧，不含主干细节）

```
lane   [1,1,64,64] ──→ 轻量 CNN 编码器(3 个 stride-2 块) ──→ GAP ──→ lane_emb  [64]
boxes  [1,16,12]   ──→ 逐槽共享 MLP(12→32→32) ──→ valid 掩码 mean-pool ──→ box_emb [32]
ego_state [1,20]   ──→ MLP(20→32) ──────────────────────────────────→ ego_emb [32]
                                                                          │
                            concat ────────────────────────────────────────┘
                              ↓ [128]
                          MLP(128→64→3)
                              ↓
        steer = tanh(·) ∈ [-1,1] · throttle = sigmoid(·) ∈ [0,1] · brake = sigmoid(·) ∈ [0,1]
```

**输出契约与现有 `m9_mono` 完全一致**（[`InferenceEngine.swift:13-15`](../Sources/AuroraDrive/Inference/InferenceEngine.swift)）：`steer` 用 `tanh`、`throttle`/`brake` 用 `sigmoid`。沿用现有契约的理由是**零成本兼容** —— 上层 `ControlCommand`（[`EscapeController.swift:28-46`](../Sources/AuroraDrive/Control/EscapeController.swift)）、`DegradeStateMachine`、`RuleController` 全部不用改。

**box 池化用「带 `valid` 掩码的 mean-pool」而非裸 max-pool**：
- 0 个框时：`sum = 0`，但除数也是 0 → 必须显式 `if n_valid == 0 { emb = zeros }`，**否则 NaN 会污染整条链路**。这是空输入最容易被忽略的崩溃点。
- mean 而非 max：保留「多个目标」的整体态势；`box_count_norm`（state[13]）另行提供数量。

**v3 备选**：若 M2 实测出现「框与车道线的交互学不会」的具体失败模式，再上 cross-attention（lane token ↔ box token），并且**必须先量它在该 ANE 上的实际 softmax 开销**，不得凭直觉引入。

### 5.3 尺寸选择的量化依据（速查）

| 参数 | 取值 | 依据 |
|---|---|---|
| 车道线 64×64 | 而非 160 或 40 | `lanePositiveFloor=0.002` → 最坏健康帧约 29 格（有效区 14400）：40×40 只剩 ≈3 格（混叠），64×64 剩 ≈8 格（可辨），160×160 有 37.5~57.8% 是灰边 |
| 槽位 N = 16 | 而非 8 或 32 | 实际高紧迫框远少于 16；`maxDetections=300` 是硬上限但非典型值；16 槽 × 12 维 = 192 float 成本可忽略 |
| 状态 20 维 | 而非 6 | 沿用 `vehicle_state` 前 6 维语义，但**现有实现里 idx1/2/5 恒为 0、idx3 恒为 1**（[`InferenceEngine.swift:431-436`](../Sources/AuroraDrive/Inference/InferenceEngine.swift)），等于 6 维只用了 2 维；M2 把这几位真正填上，再加车道几何 + 上帧动作 + 降级标志 + 2 维预留 |
| 融合 concat | 而非 attention | softmax/reduce 在本仓库实测占 72% 墙钟（作战手册:260） |

### 5.4 耗时预算

| 项 | 预算 | 依据 |
|---|---|---|
| 裁剪 + 降采样（25600 格 → 4096 格） | **≤0.10ms** | vImage 单次缩放，与 `drawLetterbox` 同级操作 |
| 检测框编码（16 槽 × 12 维） | **≤0.02ms** | 192 次浮点写 |
| 状态向量（20 维 + 2 行质心扫描） | **≤0.05ms** | 2×160 次读 |
| **编码合计** | **≤0.20ms** | 占 33ms 预算 0.6% |
| M2 前向 | **≤3.0ms** | 对齐现有 `infer.m9` p50 = 3.268ms（性能优化总结:24） |
| **新增合计** | **≤3.2ms** | 剩余 ~29ms 留给已有链路 |

**必须遵守**：编码器**不得每帧分配内存**。沿用 `InferenceEngine` 的 `reusableImageBuffer` / `reusableStateBuffer` 先例（[`InferenceEngine.swift:114-120`](../Sources/AuroraDrive/Inference/InferenceEngine.swift)）—— 尺寸不变时复用 `MLMultiArray`。

## 6. 空输入 / 畸形输入护栏（硬性要求）

这是本仓库有**血泪史**的地方，必须逐条覆盖。

| 场景 | 判定条件 | 编码行为 |
|---|---|---|
| **车道线为空** | `mask.width == 0`（即 `.empty`） | `lane` 全零；`lane_valid=0`；`lane_ratio=0`；`lane_offset_*=0`；`heading_err=0` |
| **车道线畸形** | `cells.count != width*height` | **同上按空处理**。⚠️ [`YolopxEngine.swift:53-70`](../Sources/AuroraDrive/Inference/YolopxEngine.swift) 记录过：畸形 `MaskGrid` 流入 `LaneFallback` 会触发 Swift 数组越界 **SIGTRAP（EXIT=133）→ 整个驾驶进程死亡**。编码器必须把这道防线扩到输入侧 |
| **尺寸不是 160×160** | `width != maskGridSize \|\| height != maskGridSize` | **按空处理并置 `lane_valid=0`**。⚠️ 不要「宽容地」接受 80×80：`LaneFallback` 明确**拒绝**它，注释写「自洽但非生产尺寸，**历史事故来源**」（[`AuroraDriveApp.swift:2645-2650`](../Sources/AuroraDrive/App/AuroraDriveApp.swift)、[`LaneFallback.swift:167`](../Sources/AuroraDrive/Inference/LaneFallback.swift)）。编码器必须与 `LaneFallback` **同一口径**，否则会出现「编码器喂了、兜底不认」的静默不一致 |
| **`metrics == .zero`**（模型未加载） | `ratio <= 0 \|\| newW <= 0 \|\| newH <= 0` | `lane` 全零 + `lane_valid=0`；**不得做除法**（`toNormalized` 的 `guard ratio > 0` 先例，[`YolopxEngine.swift:116`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)） |
| **检测框 0 个** | `detections.isEmpty` | 16 槽全零 + `valid=0`；`box_count_norm=0`；**池化必须显式返回零向量**（防 0/0 = NaN） |
| **检测框 > 16 个** | `count > 16` | 按 urgency 降序取前 16；丢弃数量写日志（不静默） |
| **检测框含 NaN/Inf** | `!x.isFinite \|\| ...` | **整框丢弃**。先例：[`YolopxEngine.swift:1190-1193`](../Sources/AuroraDrive/Inference/YolopxEngine.swift) 的「非有限值一律跳过（NaN/Inf 进 Int() 会 runtime trap 崩全车）」 |
| **检测框越界** | `x/y/w/h ∉ [0,1]` | `clamp` 到 [0,1]（与 [`YolopxEngine.swift:1233-1236`](../Sources/AuroraDrive/Inference/YolopxEngine.swift) 的 clamp 口径一致） |
| **光流不可用** | `!ego.isUsable` 或 `flow == nil` | `lateral_rate=0`、`forward_rate=0`、`ego_conf=0`（**不是保留上次值**，避免陈旧运动信息污染） |
| **速度不可信** | `speedValid == false` | `speed_norm=0`、`speed_valid=0`、`accel_norm=0`。⚠️ 注意 `SpeedOCRReader.speedKmh` 未读到时是 **-1**（[`SpeedOCRReader.swift:157`](../Sources/AuroraDrive/Inference/SpeedOCRReader.swift)），**必须先判 `speedValid` 再归一化**，否则 `-1/120` 会变成负速度 |
| **上帧无动作** | 首帧 | `prev_*=0` |
| **车道线是外推帧** | 非真值帧 | `lane_valid=0.5`（**仍喂掩码**，但降权），依据 `LaneBridge.lastGroundTruthTime` 新鲜度 |

**总原则（与项目 fail-open 纪律一致）**：**空输入永远产生「全零 + valid=0」的合法张量，绝不产生 NaN、绝不改变 shape、绝不抛异常**。`LaneFallback` 的原话是「任何一个输入不可信，立即返回 nil，调用方维持原决策，绝不猜一个方向」（[`LaneFallback.swift:12`](../Sources/AuroraDrive/Inference/LaneFallback.swift)）—— 输入编码层同理：**不可信就明说不可信（valid=0），不要伪造一个看起来像数据的零**。

## 7. 给 M2 的交接清单

1. **输入 shape 按 §5.1 静态声明**，三个输入 + 三个输出，不要用 flexible shape。
2. **输出激活沿用 `tanh`/`sigmoid`**，与 `m9_mono` 一致，上层零改动。
3. **裁剪公式必须复用 `metrics`**，且与 `extractMask` 的 `vx0/vy0/vx1/vy1`（[`YolopxEngine.swift:1306-1312`](../Sources/AuroraDrive/Inference/YolopxEngine.swift)）同源，否则会与 `laneRatio` 的统计口径打架。
4. **检测框零坐标换算**是建立在「先裁剪」的前提上的；**若 M2 选择不裁剪**，则必须补上 `gx = (x·newW + padX)/4` 的映射，否则会引入最多 46 格的系统性偏移。
5. **训练数据要能复现同一套编码**：训练侧（Python）必须实现逐位一致的裁剪/降采样/归一化，包括 §6 的每一条护栏。建议直接以本文件 §5 为契约写一个共享的编码函数，Swift 与 Python 各一份实现 + 交叉校验用例。
6. **待验证项（本文件未实测，不得当作已确认）**：
   - M2 前向 ≤3ms 是**预算目标**，未在 M3 上实测。
   - 编码 ≤0.20ms 是**估算**，未实测。
   - `lane_offset_near/far` 的两行位置（0.90 / 0.55）是**初值**，需真机标定。
   - `accel_norm` 在 15Hz OCR 速度下的噪声水平未测。
   - 备选 b 的 64×64 是否足够（vs 80×80）需在真实 `laneRatio` 分布上验证。

## 8. 一页速查

```
┌─ I1 lane      [1, 1, 64, 64]  ← MaskGrid 裁剪有效区 + 面积平均降采样（软值）
├─ I2 boxes     [1, 16, 12]     ← Detection 按 urgency 排序，零填充，valid 标志
├─ I3 ego_state [1, 20]         ← 速度/运动/车道几何/上帧动作/降级标志
│
├─ 融合：concat（CNN 空间融合 + 向量语义融合），不用 attention
│        理由：softmax/reduce 在本仓库实测占 72% 墙钟（作战手册:260）
│
└─ O1 steer [1,1] tanh  O2 throttle [1,1] sigmoid  O3 brake [1,1] sigmoid
   编码开销 ≤0.20ms ｜ M2 前向预算 ≤3.0ms ｜ 空输入 → 全零 + valid=0
```

**三个最关键的结论**
1. **必须先裁剪 letterbox 灰边**：推算最多 **57.8%** 的 160×160 网格是零填充；裁剪后 **`Detection.x/y` 天然就是同一坐标系**，零换算对齐。
2. **车道线降到 64×64 且用面积平均、不二值化**：多数表决会让 1~2 格宽的车道线整条消失（`lanePositiveFloor=0.002` 量化论证）。
3. **融合用 concat**：本项目对 `softmax`/`reduce` 的 CPU 代价有实测血案，attention 是拿确定风险换不确定收益。
