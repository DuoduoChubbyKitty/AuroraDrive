## 3. 导出与量化命令（原文保留）

### 3.1 A-YOLOM INT8（生产档）

```bash
# INT8（生产）—— palette 8 位 kmeans + det 头保 fp16
PYTHONPATH=/tmp/ayolom_sklearn tools/ayolom/.venv/bin/python \
  tools/ayolom/export_ayolom_coreml.py --weights models/ayolom/v4.pt \
  --out models/ayolom/ayolom_n_int8.mlpackage --quantize int8

# 编译成 .mlmodelc（免运行时编译）
xcrun coremlcompiler compile models/ayolom/ayolom_n_int8.mlpackage /tmp/c8
cp -R /tmp/c8/ayolom_n_int8.mlmodelc models/ayolom/
```

导出日期 **2026-10-02**，coremltools 源框架 `torch==2.14.1`。

**两处关键修订**（`models/ayolom/NOTICE.md:50-62`）：

- **修订① 输入类型 `TensorType` → `ImageType`**：`TensorType` 要 `MLMultiArray`，而 `YolopxEngine.swift` 喂的是 `MLFeatureValue(pixelBuffer:)`（`CVPixelBuffer`）——类型对不上会直接加载/推理失败。归一化搬进图内（`scale=1/255`、`bias=[0,0,0]`、RGB）。
- **修订② int8 量化方式 `linear_quantize_weights` → palette（kmeans 8 位）+ det 头保 fp16**：配方来自 `tools/yolopx/exp_quant_palette.py`。`metadata.json` 显示存储精度 `Mixed (Float16, Palettized (8 bits))`。

### 3.2 接口契约（Swift 侧按此读取）

```
输入  image   ImageType  RGB  scale=1/255  bias=[0,0,0]   640×640
输出  det     [1, 5, 8400]   cx, cy, w, h, cls_conf
                            ⚠️ 与 yolopx 的 [1,8400,6] 不同：无 obj_conf，且是列优先
      da      [1, 2, 640, 640]   可行驶区 logits（与 yolopx 逐位相同）
      ll      [1, 2, 640, 640]   车道线 logits（与 yolopx 逐位相同）
```

### 3.3 INT8 等价性实测（200 帧真游戏画面，ANE）

| 指标 | 值 |
|---|---|
| 可行驶区 da 掩码 IoU（vs fp16） | **0.9942** |
| 车道线 ll 掩码 IoU（vs fp16） | **0.9749** |
| 检测召回（vs fp16，IoU>0.5） | **99.1%** |
| 推理 p50 / p99 | **10.4 / 13.1 ms** → 95.9 Hz |
| 30Hz 预算占用 | 31% |

**A-YOLOM(n) 10.4ms vs YOLOPX 118ms ≈ 11 倍差距** —— 这就是 `.ayolom` 被设为默认档的原因（`models/ayolom/NOTICE.md:77`）。

### 4.3 为什么它被架构限制在「仅显示层」

这是**有意设计的隔离**，不是偶然：

1. **数据流方向单向、无决策回写**。`Capture/Control` 与 `Inference` 链路完全不碰 MetalGoose：
   - `CaptureEngine.swift:1102-1109` 的 `onUpscaleFrame` 注释：*「插帧/超分直通：把全分辨率帧送给 MetalGoose 引擎。必须复制到带 IOSurface 的私有缓冲，否则下游 CGImage 创建会崩（MG-ENG-001）。门禁先于拷贝求值：插帧/清晰画面关闭时连全分辨率拷贝都不做」*
   - 引擎进程只把帧**写给共享内存 / MetalGoose**（`Core/EngineMain.swift:1043-1050`），**不从 MetalGoose 读回任何结果**。
   - 换言之：MetalGoose **只吃像素、只吐像素**，永远接触不到 `ControlCommand`、检测结果、坐标。
2. **门禁默认关闭**。`isUpscaleWanted` 默认 `false`（`CaptureEngine.swift:138`），UI 侧默认 `upscaleEnabled == false`。**默认路径下 MetalGoose 根本不参与**。
3. **不修改上游**。`NOTICE.md` 明确「None. The files are kept byte-for-byte as published ... so that AuroraDrive remains a faithful GPL v3.0 derivative.」——原文保留，不引入「部分 GPL / 部分闭源」的灰色解释。

**但要注意**：上述隔离**降低的是工程风险，不是法律风险**。法律上只要二进制里链了 GPL 代码，整体就是 GPL。

## 5. OpenCVFlow 桥接设计

### 5.1 它是什么（README 原文）

> 一层薄 C 桥，把 OpenCV 的 `cv::DISOpticalFlow`（稠密光流）暴露成纯 C 接口给 Swift 用。Swift 不能直接 `import` C++，所以必须有这一层。
>
> **它只做一件事**：喂两帧灰度图，回传「自车运动摘要」（全局位移 + 散度）。不回传稠密流场 —— 640×640×2×4B = 3.3MB，跨语言搬运比光流计算本身还贵。

### 5.2 为什么不用 Apple 官方（实测数据仍在 README:15-25）

> 用户红线：**光流延迟 ≤5ms**。本机 640×640 同批实测：
>
> | 方案 | p95 | 判定 |
> |---|---|
> | Apple `VTOpticalFlow`（VideoToolbox，macOS 15.4+） | 10.28 ms | ✗ |
> | Vision `VNGenerateOpticalFlow` | 27.43 ms | ✗ |
> | `VNGenerateOpticalFlowRequest` @160×160 | 27.43 ms | ✗ |
> | **OpenCV `DISOpticalFlow` PRESET_ULTRAFAST** | **1.91 ms** | ✓ |
> | 同上，**只留 1 核**（极端工况） | **3.78 ms** | ✓ |
>
> 官方硬件路径慢 5～14 倍，所以选 OpenCV。
>
> `DISOpticalFlow` 是 **CVPR 2016 的正式算法**（Dense Inverse Search），OpenCV 官方 `video` 模块内建，**非自研手搓**。

**核实结论**：✅ 这段实测数据**仍然写在 `Vendor/OpenCVFlow/README.md:13-28`**，未过期。精度：位移估计误差 **0.07 px**（实测 dx=1.930，真值 2.000，自然纹理图）。

### 5.3 性能关键：4:1 抽样（勿删，README:90-104）

| 实现 | p50 | p95 | p99 |
|---|---|---|---|
| 全量 409600 点 | 4.57 ms | 4.95 ms | **5.32 ms** |
| **4:1 抽样 16384 点** | **1.47 ms** | **1.91 ms** | **2.07 ms** |

全量版卡在 5ms 红线上抖动（p99 超标）。抽样把 `nth_element` 规模降 16 倍，精度几乎不变（dx 都是 1.930）——因为行车画面光流场高度平滑。**若将来改回全量，先确认能过 5ms。**

### 5.6 线程安全与接口（README:106-121）

> **`ad_dis_compute` 不是线程安全的。** 同一个 ctx 不能被并发调用。调用方（Swift 侧 `OpticalFlowBridge`）负责串行化。

```c
void *ad_dis_create(int preset);        // 创建（长期持有，别每帧建）
void  ad_dis_destroy(void *ctx);        // 销毁
AD_FlowResult ad_dis_compute(...);      // 算两帧间运动
```
失败一律返回 `valid = 0`，不抛异常、不崩溃。

**YOLOPX 三档对拍结论**（`models/yolopx/NOTICE.md:39-48`）：

| 档位 | det 准确率 | da IoU | ll P/R | 单帧耗时 | 结论 |
|---|---|---|---|---|---|
| `fp16` | 100% | 0.9924 | 99.2% / 98.4% | 147 ms | 用户否决（太慢） |
| `w8a16` | 85% | 0.9919 | 98.9% / 98.1% | **118 ms** | 基座 |
