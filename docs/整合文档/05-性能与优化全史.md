## ② 抓屏与拷贝链路

### 2.1 数据流全貌（源码直读，2026-10-18）

```
ScreenCaptureKit（SCStream，1280×832 @ 20fps，32BGRA，queueDepth=3）
  └─ stream(_:didOutputSampleBuffer:of:)   CaptureEngine.swift:1060  （captureQueue，autoreleasepool 包裹）
       ├─ onNativeFrame  :1098   原生分辨率直通（逐行 memcpy 仅 speedROINorm 区域，≈16.7KB/帧）
       ├─ onUpscaleFrame :1106   全分辨率 → 带 IOSurface 私有池（≈4.06 MB/帧）★ 有门禁
       ├─ onYoloFrame    :1113   vImage CPU 缩放 → 640×640 池（≈1.56 MB/帧）
       └─ onFrame        :1227   vImage CPU 缩放 → 480px 宽（≈0.57 MB/帧）→ CGDataProvider 零拷贝
                                 → CGImage → NSImage → currentFrame + onFrame?(nsImage, cgImage)
```

**四个 `CVPixelBufferPool`** 都是「`MinimumBufferCount = 4` + 惰性创建 + 尺寸匹配复用」：
`CaptureEngine.swift:1249`（YOLO）、`:1274`（UI）、`:1349`（native）、`:1409`（upscale）。
池耗尽时 `CVPixelBufferPoolCreatePixelBuffer` 会**自行扩容**（非 MAX 上限）——正常情况下 `autoreleasepool` 帧末释放，不持续增长。

### 2.2.1 感知档位对 tick 成本的影响（2026-10-20 00:01 tick-bench 实测 · 最终版）

**本项目第一次「同进程、背靠背、唯一变量是感知档位」的干净对照**——用 `--tick-bench` headless 夹具驱动**真实 `DriveState.tick()`**（`AURORA_UI_LOCAL=1`，不注入按键、不起 GUI、安全断言全过），只改 `perceptionMode`。产物 `23:58:49`，全量自检 26 绿 + 2 既有 FAIL、0 新增 FAIL：

| 指标 | `.ayolom` 档（A 模型档） | `.legacy` 档（三件套） |
|---|---|---|
| `tick.total` p50 / p95 / p99 | **0.012 ms** / 0.030 ms / 0.099 ms | 0.255 ms / 0.405 ms |
| `tick.yoloFast`（yolo26s 推理） | **n=0**（一次都没跑） | n=102，p50=0.044 ms |
| `tick.opticalflow`（DIS 光流） | **n=0**（一次都没跑） | n=204，p50=0.228 ms |

机器可读：`tick.total.p50=0.0122 / p95=0.0300 / p99=0.0994 / tick.opticalflow.p50=0.0000 / tick.consumeFrame.p50=0.0012`。

**这组数据的双重意义**（它同时是功能证据与性能证据）：

1. **功能实证（硬判据是样本数 n，不是毫秒数）**：`tick.yoloFast n=0` 是「A 模型档不加载/不推理 yolo26s」（goal-3279b59b 需求 1）的**运行时证据**——不是 grep 代码推出来的，是真跑出来的。改动前的旧产物在 `.ayolom` 档是 **n=54**（照样每两帧推理一次），这正是本次要修的问题。同理 `tick.opticalflow n=0` 是「A 模型档停光流」（需求 9）的运行时证据。三轮 A/B 复跑结论一致。
2. **性能基线（仅供同口径横向比）**：`.legacy` 档的 tick 成本里，光流（0.228 ms）远大于 26S 推理（0.044 ms）——**光流才是 legacy 档的大头**，不是 26S。这与 task-5 风险评估「光流是三大消费者共同依赖、不能轻动」的结论互相印证。

> ⚠️ **口径一：这是主线程 tick 段，不是整机帧预算**。`--tick-bench` 的 `tick.total` 只覆盖 `DriveState.tick()` 在主线程的整圈（门控求值 + 各消费段），**不含抓屏、不含后台推理队列、不含按键注入**。主线程每帧 0.255 ms → 0.012 ms（省 95.2%），**别写成"整机省 95%"或"整机省 99%"**。
> ⚠️ **口径二：绝对毫秒数不可跨时段比**。项目自己的警告见 `PerfSelfTest.swift:867-873`——同一二进制在数小时前后可差 2~2.5 倍。三轮 p50 在 0.004~0.025 ms 间波动属正常，**引用时不要拿本轮 0.012 ms 与历史任何绝对值比大小**，唯一硬判据是样本数 n（A 档 n=0 vs legacy n=102/204）。
> ⚠️ **口径三：本夹具不覆盖 motion 消费者**。夹具 `isDriving=false`，故 `updateMotionPipeline` 零样本。**不能说"实测证明 MotionPredictor / LaneBridge 不受影响"**——那条只有代码级论证（见 task-5 风险评估结论）。
> ⚠️ **复现命令**：`AURORA_UI_LOCAL=1 --tick-bench --seconds 4`，产物须含档位门控（`AuroraDriveApp.swift:7072-7073` detectGateB 判据）。

## ③ GPU / CPU 归属

### 3.1 结论

> **推理不碰 GPU（模型层已硬保证）；CIContext 已全部 CPU 化；抓屏的 GPU 成本是 SCStream 系统级行为，不可省；瓶颈在 CPU 侧图像处理管线。**

### 6.2 抓屏侧的否决/未采纳项

| 方案 | 结论 | 原因 |
|---|---|---|
| `pixelFormat` 换 YUV 420v/420f | ⛔ 净收益为负 | 理论省 62.5%（192→72 MB/s），但 vImage **无 420 双平面缩放函数** + 全链路 12+ 处依赖 32BGRA；每帧加一次全帧 CPU 转换 ≈190 MB/s 读写，倒贴 |
| `SCStreamConfiguration.Preset` | ⛔ 不用 | 5 个 preset **全是 HDR 相关**，项目是 SDR + BGRA，用了带宽翻倍 |
| `captureResolution = nominal` | ⛔ 违规 | 官方语义 = 降分辨率，违反铁律 |
| `SCStream` 直出 640×416 | ⛔ 违规 | = 降分辨率；且三处 vImage 缩放都依赖全帧源做超采样降噪 |
| 自实现逐像素变化检测 | ⛔ 净收益为负 | 全帧比对实测 6.81 ms/帧，占 45Hz 预算 22.2ms 的 **30.7%**，为省 CPU 先花三成预算 |
| 「2-3 秒刷新一次」 | 🔴 高危且违规 | 横向 1.0 m/s 时 2s 偏 2.0m（车道宽仅 3.5m）；等价降帧率到 0.33~0.5 Hz |
| `SCScreenshotManager` 按需拉帧替代推流 | ⛔ 不推荐 | 丢失 45fps 推流稳定性，时序抖动 |
| `queueDepth` 3 → 8 | ⛔ 不改 | 官方上限 8，但 8 帧 = 178ms @45fps 延迟，对实时决策是负收益 |
| `showsCursor = false` | ⛔ 不改 | 省微秒级光标合成，代价是录制里看不到鼠标 |
| `ignoreShadowsSingleWindow` + `shouldBeOpaque` | 🟡 窗口模式可试，未实测 | 收益量级小 |
| `.idle` 信号接入（`SCFrameStatusIdle`） | ⚠️ 价值有限 | **项目至今未读这个信号**（`grep SCFrameStatus Sources/` 零命中）；它只在画面完全静止（菜单/暂停）触发，游戏运行时无效 |

### 6.3 模型侧的否决/未采纳项

| 方案 | 结论 | 原因 |
|---|---|---|
| 重叠执行流水线（enc ∥ ctl 双队列） | ⛔ 已否决 | enc 与 ctl **都在 ANE 上**（单一硬件单元），并发只抢时间片；6 次复跑收益 −22.8% ~ +33.1% 乱跳（均值≈0），代价确定：端到端延迟 **+1 帧 = +33.3 ms** |
| GRU 隐状态续算（O(N)→O(1)） | ⛔ 已否决 | 语义变更非等价：窗口语义要求 `GRU(x_1..x_8)`，续算得 `GRU(x_0..x_8)`，maxdiff ≈4.6e-2（两次复跑均在 4e-2 量级）。GRU 门控非线性复合，**精确 O(1) 滑动窗口不存在** |
| 死子图去冗余（删 refiner + temporal） | ⚠️ 「当前无损」非永远无损 | 依赖 checkpoint 缺权重（出口投影零初始化）；checkpoint 训练完整后不可删。**未采纳** |
| 光流 warp 特征外推复用 | ⛔ 证伪 | 线性外推误差 2.202e-01（20.4%），端到端 maxdiff 5.308e-02 超差 |
| 早期帧降精度（前 7 帧 fp16/int8） | ⚠️ 未采纳 | fp16 满足 <1e-3，但收益不如算子修复（已不需要） |
| 跑两次 batch=4 替代 batch=8 | ⛔ 更慢 | 4.99 vs 4.07 ms |
| `deduplicate_weights` | ⚠️ API 不存在（非"试过没用"） | coremltools 8.3.0 / 9.0.0 均无此符号；且实测 4KB 粒度重复块仅 3.5%（全是全零块），CoreML 编译期自动 `const_deduplication` |
| 降分辨率换延迟（90×160 / 45×80） | ⛔ 违规 | 虽有收益（面积 1/4 → 耗时约 1/2），违反红线 |

### 6.4 其他被推翻的因果链（留痕，勿重复排查）

| 曾经的判断 | 实际 |
|---|---|
| 「卡顿是 ANE 争抢 / 模型推理占 GPU」 | 三模型并发只彼此慢 1.10×；CoreML 推理 6 组件 GPU 算子全 0 |

| 「卡顿主因是 Aurora」 | A/B 对照：游戏历史平均 CPU 才是大户 |
| 「`--perf-selftest` 的频率 = 出结果频率」 | 23.86 Hz 是**提交率**（`DispatchQueue.async`），不是完成率 |
