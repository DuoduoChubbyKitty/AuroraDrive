## 1. 坐标系与标定

### 1.1 三套单位的世界观

项目里同时存在三套坐标，**混用即出 bug**（历史上已出过多次）：

| 坐标系 | 单位 | 用途 | 唯一出处 |
|---|---|---|---|
| **世界坐标** | UE5 厘米（cm） | 网络定位、任务目标点、弯道打点 | `CoordinateCapture` / `quest_index.json` / `road_corners_*.json` |
| **地图像素** | px（13056²） | 路网图、底图裁切、路线折线、标记点 | `route_graph.json` / `MapLayers` / `worldToMapPixel` |
| **米** | m | 视野 span、距离显示、弯道提前量 | `MapViewport.spanMeters` / `RoutePlan.distanceMeters` |

### 1.2 世界 → 地图像素：kCalib 四件套

`Sources/AuroraDrive/Capture/CoordinateCapture.swift:112-115`（已核对逐字一致）：

```swift
let kCalibA:  Double = 0.016394586684750773
let kCalibB:  Double = 5.693519256055879e-08
let kCalibTX: Double = 6526.474380746091
let kCalibTY: Double = 5210.664390686138
```

正向变换（`CoordinateCapture.swift:1786-1787`）：

```swift
let mapX = kCalibA * wx + kCalibB * wy + kCalibTX
let mapY = kCalibA * wy - kCalibB * wx + kCalibTY
```

- 底图坐标系为 **map-2026-08**（MaaNTE-Map **13056×13056** 扩图版，2026-09-13 升级），旧帧 map-2026-06 为 11264，A/B 不变、仅 TX/TY 平移 (+233, +1738)（`CoordinateCapture.swift:106-110`）。
- **反向变换**（像素 → 世界）在 `MapWiring.mapPixelToWorldX/Y`，是上面这个式的严格逆（`--route-selftest` 已验往返误差 < 1e-12 px）。

### 1.3 米 ↔ 像素：0.61 的来历（**已验证**）

`metersPerPixel = 0.61` **不是**拍脑袋，而是从 kCalibA 反推：

- `kCalibA = 0.0163946` 是「世界 cm → 地图像素」的比例 ⟹ 1 像素 = `1/kCalibA = 60.9957` 世界单位 = **0.609957 米**（取整写作 0.61）。
- 因此 `pxPerMeter = kCalibA × 100 = 1.63946`（即 1.6395），全图 13056 px = 13056 × 0.609957 = **7963.6 m**。

代码里的三处落点（全部一致）：

| 位置 | 写法 |
|---|---|
| `RouteGraph.swift:294` | `let mPerPx = (meta["m_per_px"] as? NSNumber)?.doubleValue ?? 0.61` |
| `models/route_graph.json` `meta.m_per_px` | `0.61`（实测） |
| `MissionConsole.swift:2968` | `static let worldMetersPerMap: Double = 13_056.0 / (kCalibA * 100.0)` |

> ⚠️ **一个被修掉的历史错误值得记住**：`worldMetersPerMap` 曾硬编码 `13056`（把像素数当米数），导致视野 spanPx 少算 1.64 倍 —— 用户反馈「地图定位永远是偏差错误的」。现已改为由 kCalibA 推导（`MissionConsole.swift:2940-2968` 有完整事故记录）。

**缺陷 1：修复引入了 26 条零长度自环（原 7 条已被删）**

| | 修复前 | 修复后 |
|---|---:|---:|
| 自环条数 | **7**（node 86/417/461/484/514/580/597，len 1.2~1.5 m） | **26**（node **612~660**，len 全部 = 0） |

**缺陷 2：`len_m` 与 poly 实测长度系统性不符**

932 条边里：

- `poly_len × 0.61 < 0.9 × len_m` 且差 >1 m 的有 **154 条**（例：edge 6→7 `len_m=5.5` 而 poly 只有 5px=3.05 m；edge 43→42 `len_m=28.8` 而 poly 25.69 m）。

A\* 用的是 `e.len`（`RouteGraph.swift:495`），所以**距离显示会偏大约 7%**；渲染用的是 poly，两者不同源。根因疑似修复脚本的 `poly_len` 重算只覆盖被改过的边，未全量重刷。**本次未修**（不属本次范围，且改动会影响冻结基线），仅登记。

## 3. 寻路算法

### 3.1 状态定义：半边（half-edge）

只用节点建图**算不出拐弯** —— 到路口时不知道从哪条路拐进来。故状态 = `(edgeIndex, dirFlag)`，`dirFlag 0 = a→b, 1 = b→a`，共 `2 × edges.count = 1864` 个状态（`RouteGraph.swift:21-27`、`:141` `stateID`）。

代价函数（`RouteGraph.swift:402`、`:490-495`）：

```swift
cost = 边长 + W × (转向角 / 90°)
```

- 转向角 = `acos(arriveDir · leaveDir)`，`arriveDir` 是进入方向的取反（`RouteGraph.swift:161-169`）。
- `turnThresholdDeg = 25°`：超过才算一次「拐弯」（`:389`）。
- **默认 W = 200**（`:393-397`，可用 `AURORA_ROUTE_TURN_W` 覆盖）。原注释称「实测最优：与字典序同解」，但 `AuroraDriveApp.swift:2236-2246` 已自我修正：那个等式在 24→36 上**只是巧合**，Python 独立复算 120 对随机起终点，修复后仍有 51/120 对不一致 ⟹ 断言已改为「字典序拐弯数 ≤ W=200」（数学必然）。

### 3.2 启发式可采纳性

`h(u) = hypot(Δx, Δy) × metersPerPixel`（`:417-421`）。直线最短而实际要沿路绕行 ⟹ h 恒 ≤ 真实剩余代价 ⟹ 不破坏最优性（`:29-33`）。

### 4.2 三层缓存 + 一个「数据世代」

| 缓存 | 键 | 关键点 |
|---|---|---|
| 底图瓦片 `MapTileCache.tile` | 量化后 `(cx,cy,spanPx,outSize)` | 量化粒度 **4px**；`MapTileStore` 544² PNG，LRU 48 张 / 64MB |
| 路网叠加层 `RoadOverlayCache.overlay` | `(cx,cy,spanPx,outSize,flags,gen)` | **必须含数据世代 gen**（`:77-80`） |
| 视野窗口 `ViewportWindow` | 单份，中心随拖动迁移 | 换窗才解全图 |

**`gen` 的存在理由是一次真实事故**（`MapLayers.swift:71-80`）：图层数据异步加载，第一帧 `roads == nil` 画出一张**空图**并按视口缓存；12.5 ms 后数据到位但**视口没变 → 命中缓存 → 永远返回空图**，路网再也不出现。`--mc-map` 夹具是同步加载所以从未暴露。

**量化规则只有一份实现**（`MapLayerViewport.quantized`，`:62-66`）：底图按量化后的视野裁，叠加层若按未量化视野渲染就会差半格。历史上「底图按 4px 跳、标记连续滑」的错位就是这么来的。

### 4.3 一次真实的坐标系 bug：Y 轴翻转

`MapLayers.swift:294-315` 记录：拖动时路网和底图一起动但**永远对不上**。根因是两套坐标系 Y 方向相反 —— 底图走 `ctx.draw(cg,in:)`（图像第 0 行落在上下文 y 最大处），而折线用地图像素 y（向下增大）。修法是先平移到 y=side 再用负缩放翻 Y。实测判据：线像素落在亮路面（top12%）上的比例，翻转前 20.2%（随机基线 12%），翻转后应 >60%。

## 5. 目的地来源

### 5.1 结论本身（**仍成立，且已被产品化**）

原文结论：「游戏包里不存在目的地字段，路径必须由客户端自己算」。

今天的代码状态**比原文更进一步** —— 目的地已经从「只能用户/AI 指定」扩展到「OCR 任务面板自动识别」：

```
CaptureEngine 帧 → 裁 questROI → Vision OCR(zh-Hans)
  → 过滤提示行 → 多行拼查询 → 投票缓冲（连续 3 次相同才确认）
  → 四路匹配 exact → substr → core → fuzzy（+ byname 兜底）
  → verdict(ok/ambiguous/low/miss) → ambiguous 走 NextQuests 链消歧
  → state.setLocatorTarget(x:y:) + state.questName
```

`QuestPanelReader.swift:9-23` 有完整链路；`AuroraDriveApp.swift:5901-5912` 是接线点（`onConfirmed` 回调，默认开启，`AuroraFlags.questOCR` 默认 true）。

**红线（源码注释明确）**：`quest_index.json` 的 x/y 是**世界坐标（UE5 厘米）**，`locatorTarget` 也是，**直接传、一个转换都不做**（`QuestPanelReader.swift:27-41`）。`--quest-selftest` 有专测：「条目坐标与索引原始值逐位相同（无任何换算）」。

### 5.3 导航指引链路（MissionConsole）

`NavGuidance.derive`（`MissionConsole.swift:3089-3175`）：

- 距离：`locatorTarget` 与自车同为世界坐标，`÷100` 得米。
- 转向指示：**2026-09-30 修过参考系混用 bug** —— 原来把罗盘角 `locatorHeading` 与数学极角 `atan2(dy,dx)` 直接相减（原点差 90°、旋向相反），扫描 5184 个组合发现 **58.3% 的转向指示是错的**。修法：自车与目标都投影到地图像素系，再取 `atan2(ΔmapX, −ΔmapY)`（顺带把 kCalibB 的微小倾角也算对）。
- 拿不到目标/未定位 → 如实显示「未设目标 / 定位中」，**绝不编地名与时间**。

路线绘制：默认走**沿路网折线的真实路线**（`state.routePlan`）；`AURORA_ROUTE_STRAIGHT=1` 切回旧的「自车→目标」直线（仅作 A/B）。规划入口 `planRouteToMapPixel` / `planRouteFromMapPixel`（`AuroraDriveApp.swift:4431-4493`），起点取自车定位（未定位则退回 `routeStartPx` 或报错）。

### 5.4 协议结论的边界（**一条重要修正**）

原文 §3.5 说「`decodeProtoMove` 读的正是 bit 498/509，与实测一致 —— 现有定位链路没有读错字段」。

**这条已被源码推翻**。`CoordinateCapture.swift:298-320` 明确记录：2026-09-30 实测发现那些 bit 解出的**是 S2C 心跳包里的微秒时钟**（u32@56 每 15 秒恒定 +15,000,000 = 每秒 +1e6 微秒），「ΔX 像移动」是时钟走字的巧合；用户传送 4~5 次该值纹丝不动。真实移动包在 **C2S UDP 30212**（8Hz），而过滤器 `port 30031` 把它全挡在门外。

当前状态：`decodeProtoMove` 函数体**保留不停用**（铁律：不删既有代码），但入口默认关闭，仅 `AURORA_LEGACY_PROTO=1` 时启用（仅诊断，勿用于定位）。定位一律走 `findCandidates`（MaaNTE 上游同款 UE5 位流扫描 + 连续性锁定）。

⟹ 「四个偏移已固化在 CoordinateCapture」这句**只对常量本身成立**，对「定位链路在读这些位」**不成立**。

### 5.5 驾驶侧的地图用途（不是导航，是「路往哪拐」）

地图先验在**控制回路**里的用途与「去某地」无关，而是补视觉的盲区（车道线在路口/弯道必然丢失）：

| `RoadCornerGuide` | `road_corners_v3b.json`（3135 条打点） | 「前方多远有个弯、往哪拐、要不要减速」 |
| `DriveSegmentController` | 上面两者 | 「现在该用地图还是该用视觉」 |

**安全边界（源码反复强调）**：`RoadMapPrior` **只提供航向、绝不提供横向偏差**（地图是玩家标注版，与实景有米级偏差，拿它做横向会直接带偏方向，`RoadMapPrior.swift:10-12`）。所有地图建议只做方向 + 强度，最终仍走 `applyLaneAdvice` + `applyCommand` 的限幅与死区。
