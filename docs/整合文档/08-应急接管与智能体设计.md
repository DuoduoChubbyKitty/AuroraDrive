## 2. 让位 / 冲刺 / 巡航语义

### 2.1 让位（yield）的完整实现链

跨进程架构是本节的核心：**引擎进程收不到物理按键**（ET-6 实测确认：`dispatchMain()` 不 spin NSRunLoop + 项目从未申请 Input Monitoring），所以按键必须由 UI 进程经 socket 转发。

```
用户按下受控键（UI 进程）
  └─ KeyboardMonitor 全局监听（NSEvent.addGlobalMonitorForEvents）
     └─ controlledKeyCodes 过滤（KeyboardMonitor.swift:52，18+ 键镜像表）
        └─ onUserKeyDown 回调（AuroraDriveApp.swift:6277-6279）
           └─ EngineClient.sendCommand("config", extra: ["takeover": true])
              └─ socket → 引擎进程 EngineMain case "config"（:1698-1749）
                 └─ EmergencyTakeover.shared.noteUserKeyDown()   ← 内部 guard sprinting
                    └─ enterYield()：hz=5, userHoldingKey=true, sprinting=false
                       └─ tickOnce 读到 effectiveTickHz=5 → setTickHz(5)（:1201-1204）
                       └─ 抓屏保持 baseCaptureHz=20（:1223-1229，sprinting 已 false）
                       └─ tick() 注入分支：`else if userHoldingKey { controlEngine.releaseAll() }`
                          （AuroraDriveApp.swift:7751-7765）← 持续抑制 applyCommand
松手（UI 进程）
  └─ onUserKeyUp → sendCommand("config", ["takeover": false])
     └─ 引擎 noteUserKeyUp() → enterCruise()：hz=20，全部归零
```

**ET-6 的两个关键结论（源码仍成立）**：

1. **一次性 `releaseAll()` 不够**——下一帧 tick 会 `applyCommand` 重新按下去。故实现是「一次 `releaseAll()` + 每帧持续抑制」（`AuroraDriveApp.swift:7758-7764` 的 `else if` 分支）。
2. **让位 = 让出控制权，不是让出 CPU 语义**——5Hz 注释「把算力让给用户」；且 `releaseAll()` 对 6 个映射键发**全局** keyUp（`ControlEngine.releaseAll`），会对用户正按着的键也发释放——这正是让位语义（AI 不再控制，用户重新按即可），风险可控。

**⚠️ 设计取舍（Lead 裁决，源码注释 `AuroraDriveApp.swift:6273-6276`）**：UI 侧回调**不门控 `takeoverActive`**——回调轻量（一条 socket JSON），且引擎侧 `noteUserKeyDown` 只在 sprinting 态生效，平时无害。加门控反而要跨进程同步 `takeoverActive`（复杂且有时隙 gap）。

| 触发 | 条件 | 源码 |
|---|---|---|
| 掉拍 | 连续 **10 帧** `tickGap > 80ms` | `EmergencyTakeover.swift:123-127` |
| 模型降级 | `isDegraded` **false→true 边沿** | `:148-156` |

**退出**（三条，全部在 `noteTickGap` 内）：

|---|---|---|
| 用户接管 | `noteUserKeyDown`（仅冲刺态）→ 让位 | `:159-164` |

**喂信号的接线（ET-4）**：`AuroraDriveApp.swift:6895-6900`，位于 `tick()` 最前、`isActive` 早退**之前**：
```swift
if !EngineClient.shared.isActive {
    EmergencyTakeover.shared.noteTickGap(tickGapMs)
    if yolopxEngine.isLoaded {
        EmergencyTakeover.shared.noteModelDegraded(yolopxEngine.isDegraded)
    }
}
```
- `tickGapMs` 在 `tick()` 最前无条件赋值（`:6866-6868`），不受任何 guard 影响 → 两进程都喂（ET-6 §1 结论）。
- `yolopxEngine.isLoaded` 门控的原因（`:6878-6879`）：未加载时 `isDegraded` 默认 true（`YolopxEngine.swift:382`），那不是"运行中退化"，不该触发应急。

**⚠️ ET-9b 的关键修复（2026-10-12，交叉验证 §2.5 的 P1 已被修掉）**：
`AuroraDriveApp.swift:6880-6894` 记录了「引擎模式下 UI 进程不能本地喂信号」的修法。原风险链：UI 进程 `:6286` 无条件 `yolopxEngine.loadIfNeeded()` → UI 的 yolopx 也 loaded → ayolom 档 `isDegraded` 恒 true → UI 实例本地 `enterSprint()` → 而引擎 heartbeat 回传 false → `syncFromEngine` 写回 false → **横幅一开一关闪烁**。
修法：`if !EngineClient.shared.isActive { ... }` —— 引擎模式下 UI 实例**只做显示镜像**；UI-local 模式（引擎未连）才本地喂信号。
→ 交叉验证报告 §0 表 7 / §6 表 #3「UI 进程仍本地喂 noteModelDegraded（P1）」**已过期，已修复**。该报告 §2.5 的「关键未知：UI 进程是否加载 yolopx」也已被 `:6286` 的回答终结：**会加载**，所以这个门控不是可选项而是必需。

### 2.3 巡航（cruise）与状态归零

`enterCruise()`（`:224-232`）重置 **6 个字段**：`sprinting` / `takeoverActive` / `userHoldingKey` / `sprintStart` / `consecutiveMisses` / `effectiveTickHz`。交叉验证 §5.4 确认「无残留」。

**⚠️ 让位态没有超时出口（真实缺口，两处代码佐证）**：
`noteTickGap` 第一行 `if userHoldingKey { return }`（`:109`）→ 让位态下 35s 超时检查（在 `if sprinting` 分支内，`:112-120`）**被跳过**。
→ 若用户按键的 keyUp 事件丢失（跨进程经 socket 下发，任何一环断掉都会丢），状态**永久停在 5Hz**，只能重启引擎恢复。
交叉验证 §5.3 也独立发现了这条，判「P1 但可接受」；**本篇判为需修复的安全缺口**（§5-S2），理由：它不是"用户主动选择一直 5Hz"，而是"事件丢失导致无法退出"，且没有任何提示告知用户系统已卡在让位态。

### 3.4 跨进程状态同步（ET-9，原 P0 已修）

这是本篇最重要的一条链路，因为它修掉的是「安全功能完全失效」级别的缺陷。

## 5. 已知安全缺口

> 判定标准：**会影响用户游戏内角色/账号安全**，或**会让安全功能静默失效**。

### S1. 巡航态按 WASD 不触发接管（设计如此，但需文档明示）

- 源码：`EmergencyTakeover.noteUserKeyDown` :159-164 `if sprinting { enterYield() }` —— 巡航态（无触发）用户按键**被静默忽略**。
- 交叉验证 §3.2 判定「⚠️ 设计如此（巡航态无需让位）」。
- **风险面**：用户以为「我按住 W 系统就会让位」，实际不会。若同时 AI 也在注 W，两者不冲突（同键），但用户对"谁在控制"的认知可能与现实不符。
- 建议：UI 上明示「应急接管只在系统检测到掉拍/降级后生效」。

### S2. 让位态没有超时出口（真实缺口，需修复）

- 源码：`noteTickGap` :109 `if userHoldingKey { return }` → 35s 超时检查（在 `if sprinting` 分支 :112-120）被跳过。
- 触发条件：keyUp 事件丢失（跨进程经 socket 下发，UI 回调 / socket / 引擎解析任一环断掉都会丢）。
- 后果：**永久停在 5Hz**，无提示、无自愈，只能重启引擎。`takeoverActive` 仍为 true → 横幅一直显示「✅ 已接管」。
- 交叉验证 §5.3 独立发现，判「P1 但可接受」；§6 表 #10 标 P2「需文档说明」。
- **本篇判定：应修复**。最小修法：让位态也检查一个更长的兜底超时（如 `userHoldingSince` + 300s），或至少打一次警告日志。

### S3. 跨进程按键时序（按了没反应，且无提示）

- 源码链路：UI `KeyboardMonitor` 回调 → socket → 引擎 `noteUserKeyDown`。
- 场景：用户按键时引擎**尚未**进入 sprinting（如掉拍检测刚累计到第 2 帧）→ `noteUserKeyDown` 被 guard 静默丢弃 → 用户按了但没让位 → **无任何提示**。
- 交叉验证 §3.3 判 P1。
- 建议：引擎侧在丢弃时 `engineLog` 一次（有据可查），或 UI 侧在 `takeoverActive=false` 时给一次轻提示。

### S4. F1–F12 在 schema 排除了，但执行面仍可注入

- 源码：`ToolRegistry.gameKeyNames` :934-943 从 schema enum 排除 F1–F12（保留 "F"）；但 `resolveGameKey` :888-892 走 `gameKeyAliases` :950-962，该表由 `ControlEngine.GameKey.allCases` **全量**构建，包含 `.f1/.f2/.f4`。
- 后果：模型猜 "F1" 会被**接受并真实注入**。自检只断言 enum 不含 F 键（`LLMSelfTest.swift:1432-1438`），没有断言 resolver 拒绝。
- 风险：macOS 上 F1–F12 是系统功能键（亮度/调度中心/聚焦/听写/音量），发过去只会触发系统动作、游戏收不到——对用户是「屏幕亮度突然乱跳」。
- 建议：`gameKeyAliases` 与 `gameKeyNames` 用同一个过滤函数生成。

### S5. 引擎模式 ack `ok:false` 语义未区分「失败」与「暂缓」

- 源码：`EngineMain.applyPerceptionMode` :772-776 应急中返回 `(false, "应急接管进行中…结束后自动恢复")`；:786-790 录制中返回 `(false, "录制中…已挂起，停止录制后自动生效")`。
- 风险：UI 若把 `ok:false` 当「配置失败」（而非「暂缓」），可能弹错误提示或回滚开关 → 用户看到「切档失败」的误导信息。
- 交叉验证 §4.3 判 P2；W8 报告记录了同文件的 P1 修复（原 ack 硬编码 `ok: true`）——那个已修，但 `ok:false` 的**语义歧义**仍在。
- 建议：ack 增 `pending: true` 字段，或 detail 前缀统一用「⏸ 暂缓：」。

### S6. tick 停摆时 35s 超时不触发

- 源码：超时检查只在 `noteTickGap` 内，而 `noteTickGap` 只在 tick 跑时喂。
- 场景：引擎卡死到 tick 完全停摆 → `noteTickGap` 不被调用 → 超时永不触发 → 卡在 45Hz。
- 交叉验证 §5.2 判 P2（极端场景）。本篇维持 P2，但记录：它与 S2 是同一类「依赖被喂入才检查」的模式。

### S7. `controlledKeyCodes` 是镜像副本，有漂移风险

- 源码：`KeyboardMonitor.swift:52` 起，注释自承「`ControlEngine.gameKeyToKeyCode` 是 private static，本类访问不到，故镜像一份」。
- 风险：ControlEngine 新增 GameKey 而忘记同步 → 新键的接管回调失效（用户按新键不让位）。
- 交叉验证 §1 末尾判 P2。建议：把 `gameKeyToKeyCode` 提为 internal，或加一条自检比对两个集合。
