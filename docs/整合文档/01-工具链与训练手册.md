## ② 构建与部署

### 2.1 构建锁：为什么要它（scripts/README.md:8-23，实测支撑）

SwiftPM 是**全模块编译**：多人并发改文件 + 并发 `swift build` 会
① 互相打断（`error: input file '...' was modified during the build`）；
② 一个人写坏，全组 `swift build` 全红；
③ 更隐蔽的：并发基准让 `loadavg` 冲高，**耗时类数字全部不可比**。

**实测数据**（scripts/README.md:20-22 注记，测量日期未在原文标出，**未重测**）：
3 个 agent 同时 `--mc-map-bench --iters 200`，各占 ~85% CPU，
`loadavg` 冲到 **5.15 / 8 核** —— 此时任何耗时类数字不可比。

`build-lock.sh` 设计要点（源码 `build-lock.sh:35-146` 逐行核对）：
- `LOCK = ${AURORA_BUILD_LOCK:-${TMPDIR:-/tmp}/aurora-build.lock}`（:37），
  `STALE_MIN = ${AURORA_BUILD_LOCK_STALE_MIN:-15}`（:38）
- `mkdir` 原子锁 —— bash 3.2 无 `flock`（:30 注释）
- owner 文件写 6 个字段：`pid / time / host / user / reason / cwd`（:64-71）
- 残留锁 ≥15 分钟 → **只提示不自动删**（:91-94）
- 持锁进程已死 → 提示 `rm -rf`，**仍不自动删**（:87-90，保守）
- `release` 时校验 owner pid，不是自己拿的锁**拒绝释放**（:102-106）
- `run "原因" -- <命令>` = 自动 acquire → 跑 → release，透传退出码（:129-138）

**哪些脚本会自动取锁**（源码确认）：
`perf-snapshot.sh:57-66`、`regression-gate.sh:56-63`、`paired-ab.sh:226`（`exit 3`）。

**两个必须记住的踩坑**（源码注释即原文）：
1. **为什么原子替换**（run.sh:99-104）：旧的 `cp` 原地覆盖同一 inode，进程按需分页会读到新旧混合页，
   CDHash 校验失败 → 内核 SIGKILL（Taskgated Invalid Signature，2026-09-12 见 9/10 DiagnosticReports）。
2. **Metal 预编译的 cache 路径**（run.sh:117-121）：`-fmodules-cache-path` 指到 workspace 内，
   因为默认写 `/var/folders/`，在受限环境下 `Operation not permitted` → 预编译静默失败。

**签名 ≠ TCC 授权**（重要区别）：
- `codesign -` 只是 ad-hoc 签名，让进程能起、不被 CDHash 杀；
