## 1 · 录制双模式：raw_clips vs glyph_clips

### 1.1 两种模式的产物差异（源码核实）

| 维度 | 训练录制（raw_clips） | 字模录制（glyph_clips） |
|---|---|---|
| 根目录 | `data/raw_clips/`（`RecordEngine.swift:177`） | `data/glyph_clips/`（`RecordEngine.swift:87`） |
| 目录名 | `clip_<yyyyMMdd_HHmmss>/`（`:260`） | 同名（`:247`） |
| frames/ | 640×360 JPEG，命名 `%06ld.jpg`（`:509`） | **原生分辨率速度表区域 PNG**（`:5` 注释 + `:242`） |
| controls.csv | **写**（9 列，`:288-289`） | **不写**（`:244` 注释「字模只关心画面」） |
| view.txt | **写**（`:273`） | **不写** |
| meta.json | 写（10 字段，`:375-396`） | **不写**（字模分支 `:243-257` 提前 return） |
| 触发开关 | `glyphMode = false` | `glyphMode = true`（`EngineMain.swift:1617` 同步） |

**结论**：两模式在**同一份代码内分流**（`start()` 的 `:242` 提前 return），不是两套引擎。`pruneOldClips` 对两个根目录**都生效**（`:238`）——字模 clip 也占磁盘配额。

### 1.3 ⚠️ 文档与代码不符 #1：targetFps 24 vs 20

- 文档《录制端契约确认-2026-10-08》`:34` 称「录制目标帧率 24 Hz（targetFps）」，并据此推算 `capture_interval_ms = 41`（`:37`）。
- 源码现值 **20**（`:36`，注释「2026-10-11 用户定档：推理 20Hz，故录制也 20」），`capture_interval_ms` 应为 **50**。
- 但磁盘实测（`data/raw_clips/clip_20261011_020359/meta.json`）仍是 `capture_interval_ms: 41`——**因为该 clip 录于 20Hz 定档前**。最新代码写 50。
- **影响**：`meta.json` 的 interval 只用于诊断；训练端 dt 由 CSV 的 `t_sec` 实算（`dataset_v2.py:378-384`），故**不影响训练正确性**。

### 1.4 ⚠️ 文档与代码不符 #2：maxClipsPerKind 10 vs 200

- 《录制链路修复-2026-10-08》`:44-49` 记载「原硬编码 10 → 改为 AURORA_MAX_CLIPS > 覆盖 > 默认 10」。
- 源码现在默认 **200**（`:60-62`），注释记录了 2026-10-10 的上调理由：用户说「只能录一次，错了就完了」，默认 10 会在第 11 段静默删第 1 段。
- 《录制验证-D2》`:92` 也提到「clip 保留上限 10 → 200」，与代码一致。
- **判定**：文档描述的是中间态，**最新代码是 200**。

## 3 · 标签换算：专家模式 vs AI 模式

### 3.1 单一分流点（源码核实）

`recordFrameIfNeeded()` 里只有一处 `if expertMode`（`AuroraDriveApp.swift:7906-7921`）：

```swift
if expertMode {
    recSteer    = RecordLabelMapper.steer(leftHeld: holdDuration(keyCode: 0),
                                          rightHeld: holdDuration(keyCode: 2))
    recThrottle = RecordLabelMapper.throttle(wHeld: holdDuration(keyCode: 13))
    recBrake    = RecordLabelMapper.brake(sHeld: holdDuration(keyCode: 1),
                                          spaceHeld: holdDuration(keyCode: 49))
} else {
    recSteer   = currentCommand.steer      // AI 输出直通
    recThrottle = currentCommand.throttle
    recBrake   = currentCommand.brake
}
```

**关键语义**：`expertMode` **只切换标签来源，不关感知**。《录制前检查-G》`:231-251` 已核实：OCR / 定位 / 检测 / 推理四条链路在专家模式下**照常运行**，因此 `speed_kmh` / `heading` / `speed_limit` 三列在专家模式下**照样有值**。

### 3.2 RecordLabelMapper 数学契约（源码逐字）

`AuroraDriveApp.swift:4121-4146`：

| 函数 | 公式 | 值域 |
|---|---|---|
| `holdRatio(d)` | `min(1, max(0, d / 0.6))` | [0,1] |
| `steer(l, r)` | `clamp(holdRatio(r) − holdRatio(l), -1, 1)` | [-1,1]，**右正左负** |
| `throttle(w)` | `holdRatio(w)` | [0,1] |
| `brake(s, sp)` | `max(holdRatio(s), holdRatio(sp))` | [0,1] |

`fullScaleDuration = 0.6`（`:4125`，注释写「30Hz 下约 18 帧」——⚠️ 20Hz 下是 12 帧）。

**键码映射**（`:7909-7918`）：A=0 左转 / D=2 右转 / W=13 油门 / S=1 刹车 / Space=49 手刹。

### 3.3 与推理端的一致性（《录制前检查-B》结论，源码复核仍成立）

| 项 | 标签端 | 推理端（`applyCommand`） | 判定 |
|---|---|---|---|
| 值域 | steer∈[-1,1]、thr/brk∈[0,1] | 同 | ✅ |
| steer 方向 | D−A，右正 | steer>0.1 → steerRight | ✅ |
| brake 合成 | max(S, Space) | brake>0.3 或手刹 | ✅ |
| **死区** | **连续，无死区** | \|steer\|≤0.1 不转向；thr/brk≤0.3 不给 | ⚠️ **错配** |

**⚠️ 已知错配 #1（文档问题 2，源码复核仍存在）**：标签连续，推理端有 0.1/0.3 死区。模型会学到 [0, 0.1] 区间的「微小转向」标签，而这些值在推理端被当 0 丢弃。**修复建议（文档 P2，未实施）**：录制端加同款死区。

**⚠️ 已知缺口 #2（文档问题 3，源码复核仍存在）**：Shift（boost，keyCode 56）**未录**。专家模式下真人按 Shift 加速的意图完全没进标签。

### 3.5 专家模式标签有效性的实测证伪（重要方法论留痕）

《录制验证-D2-专家模式键盘-实测证伪》用 `clip_20261010_235425` 证明了"引擎进程收不到键盘"这个 **P0 风险不成立**：

**方法论两个教训**（值得保留）：

2. 探针程序必须先在 TCC 授权列表里，否则"探针收到 0"是仪器无效，不是被测对象失效。

**源码侧的防线**（2026-10-10 新增，`RecordEngine.swift:350-366`）：`stop()` 时若 `expertMode && totalFrames >= 30 && labeledFrameCount == 0` → 打印 🚨 全零告警。这是**可观测性防线**，不是修 bug。

### 4.4 view_filter：训练端仍需显式传

《录制前检查-C》`:289-322` 发现的「默认 None = 不筛视角」**至今仍是有效风险点**（源码复核）：

- `dataset_v2.py:697` `view_filter: str = "auto"`… 实际默认 `None`，不筛
- 若数据集混有 FPV clip，同一 steer 标签对应两种画面几何 → 映射污染
- 建议：训练时显式 `view_filter="TPV"`
