## ① 项目架构速写

### 1.1 一句话

**macOS 上的《异环》(NTE) 第三人称「视觉 → 操控」闭环**：
SCStream 抓屏 → 神经网感知 → 三档决策梯子 → CGEvent 注入按键 → 游戏。
（来源：`笔记-2026-10-18-代码深度勘察总报告.md:45-69`）

### 1.2 主链路（按数据流）

```
屏幕（SCStream 1280×832 @20fps，BGRA 4.26MB/帧）
   ↓ 四条回调分发（各自独立缓冲池）
   ├─ onNativeFrame  速度表 ROI   102×42   ≈17KB
   ├─ onUpscaleFrame 整帧         1280×832 ≈4.26MB（门禁开才拷）
   ├─ onYoloFrame    YOLO 输入    640×640  ≈1.64MB
   └─ onFrame        UI 显示      480×312  ≈0.60MB
   ↓
感知层（三条腿并行）
   ├─ yolopx 三合一（检测+车道线+可行驶区）偶数帧 @10Hz
   ├─ yolo26s（纯检测框）奇数帧 @10Hz —— **仅 legacy 三件套档**；A 模型档（ayolom）不加载、不推理（2026-10-19 改，见 AuroraDriveApp.swift:7049-7073 detectGateB 档位门；回退开关 AURORA_FORCE_YOLO26S=1）
   └─ 光流 DIS（仅 legacy 档；ayolom 档按档位门跳过）
   ↓
决策层（三档梯子，纯内存状态机）
   .e2e（M9/M9-V2 端到端，直接出 steer/throttle/brake）
   → .yolo（第二套神经网接管）
   → .rule（YOLO 框 + 手写规则，最后防线）
   ↓ 叠加：限速硬闸（最高优先）→ 车道保持/车道线兜底 → 驾驶分段（地图打点）
   ↓
控制层（CGEvent 注入 W/A/S/D/Space/Shift）
   ↓
游戏
```

> ⚠️ 注意雷达图与实际不符的一点：`DriveMode` **只有 3 个 case**（`.recover` 已于 2026-09-30 删除）。
> 所有写「四档」「recover+rule」的文档都已过期 —— 见 ⑤.2。

### 1.3 两条独立支线

| 支线 | 做什么 | 现状 |
|---|---|---|
| **网络定位** | libpcap 抓 UE5 同步包（tcp/30031）→ 位流解世界坐标 + 罗盘朝向 → 映射到 13056² 大地图 | ⚠️ 主类 `NetworkLocator` / `VisualLocator` **全仓零实例化 = 死代码**（见 ②.4） |

### 1.4 进程模型

UI 进程（SwiftUI）+ 可选 `--engine` 后台引擎进程。
**两者跑同一份 `DriveState.tick()`**，经 unix socket 传命令、经共享内存（72MB 像素区）回传帧与检测结果。
（详见 `代码-33-进程模式与CLI参数全解.md`）

### 4.2 YOLOPX 的定位与文档叙事相反 —— 决策级结论

> 来源：`笔记-00-工作区总览与过期清单.md:821-860`（+ `笔记-探索文档-根目录.md` 554 行）

| 维度 | 实测事实 |
|---|---|
| **精度** | YOLOPX `det` 头 **100%**（精度冠军） |
| **延迟** | ⚠️ **严格口径**：min **63.6ms** / **median 97.7ms**（常态）/ 满载 median **212.7ms**。按常态算 = 33ms 预算的 **2.96 倍**，满载 **6.4 倍**（→ **不可达**）。**不要把 min 当常态** |
| **实际跑在链路里的** | **`yolo26s`** —— 唯一满足 33ms 预算的检测器 |
| **瓶颈位置** | **不在 ANE 算力**，而在 **CoreML 的 CPU 侧胶水**：每帧 63~70ms CPU 税 + 11 处 CPU↔ANE 交替（r=0.939） |

> **★ 由此推出的架构结论（建议正式采纳）**：
> YOLOPX 的合理用途是提供 `da`/`ll`（可行驶区/车道线）给 `LaneFallback` 与掩码叠加，
> **而非作为主检测源**。

**两件常被混谈的事（务必分开）**：
1. **33ms 红线至今未达标** —— 末次实测 ~84ms（2.5×）
2. **但主循环 ≤4.4ms 是安全的** —— 因为 YOLOPX 跑在**后台队列**

即：**「YOLOPX 超标」与「主循环卡顿」是两个独立问题**，多篇文档把它们混着说。

> ⚠️ **该结论的时效性**：这是 2026-09-29 的测量。10-18 后又出现了
> A-YOLOM（`ayolom_n_int8`，p50 10.4ms）作为**默认档**，YOLOPX 退为 legacy 档。
> 所以「YOLOPX 是效率输家」这个结论**方向上更强化了**（现在连默认档都不是它），
> 但具体的 63.6/97.7/212.7ms 数字**需重测才能引用**。
