## 1. 逐字段审计

### 1.1 `speed_kmh` —— ✅ 有值（两个候选源，需选一）

**两个字段的区别**（`AuroraDriveApp.swift:5108 / 5122`）：

```swift
5108:  var effectiveSpeed: Double = 0                    // ← EMA 滤波后的"有效速度"
5122:  var speedKmh: Double {                             // ← 计算属性
           EngineClient.shared.isActive ? remoteSpeedKmh : speedOCR.speedKmh
       }
```

| 字段 | 语义 | 来源 | 特点 |
|---|---|---|---|
| `speedOCR.speedKmh` | **OCR 原始读数** | SpeedOCR 认速度表 | 真实但会跳变；读不到时为 **-1**（无效哨兵） |
| `effectiveSpeed` | **EMA 滤波值** | `effectiveSpeed += (speedOCR.speedKmh - effectiveSpeed) * 0.7`（`:7235`） | 平滑但有滞后；读不到时向 0 衰减 |
| `speedKmh`（属性） | 引擎模式走 `remoteSpeedKmh`，否则走 OCR | — | **录制时应取这个或 `speedOCR.speedKmh`** |

**OCR 何时更新**（`:7228-7235`）：
```swift
let ocrFresh = speedOCR.speedKmh >= 0
    && speedOCR.confidence > 0.3
    && (speedOCR.lastResultTime.map { Date().timeIntervalSince($0) < 0.5 } ?? false)
if ocrFresh {
    effectiveSpeed += (speedOCR.speedKmh - effectiveSpeed) * 0.7   // 快跟踪
} else {
    effectiveSpeed *= 0.9                                          // 向 0 衰减
    if effectiveSpeed < 0.5 { effectiveSpeed = 0 }
}
```

**✅ 录制建议**：写 **`speedOCR.speedKmh`（原始读数）**，而不是 `effectiveSpeed`。
- 理由：训练标签应尽量接近真值；`effectiveSpeed` 是给控制用的滤波量，含滞后与衰减（读不到时会**伪造性衰减到 0**，等于把"读不到"写成"速度 0"，**引入假标签**）。
- **但要处理哨兵值**：`speedOCR.speedKmh == -1` 表示"读不到"，应写 `NaN`/空 或配合 `speedConfidence` 写 mask，**不能写 -1**（`dataset_v2.py` 会把 -1 当真实速度归一化）。
- 建议同时写 `speed_confidence`（`speedConfidence` 属性已存在，`:5123`）。

**专家模式影响**：❌ **无**。`speedOCR.infer(nativePixelBuffer:)`（`:7018`）在 tick 内**没有 expert 门控**（见 §2）。

### 1.2 `heading` —— ✅ 有值（**关键澄清：不依赖已移除的 networkLocator**）

**写入链**（`AuroraDriveApp.swift`）：

```swift
4768:  self?.locatorHeading = hdg                     // ← 写入 DriveState
```

**数据源**：`coordinateCapture`（`CoordinateCapture` 实例）→ `readWithTier()` → `worldToMapPixel(pose).heading`。
**不是** `networkLocator`（那个才是被注释的）。

**两处"已移除"的对象不同**（这是误解的来源）：

但 `coordinateCapture`（`CoordinateCapture`）是**另一条链路**，它在 `runNetworkLocateStep()` 里**懒初始化并常驻运行**：
```swift

4541:     if coordinateCapture == nil {
```

**驱动频率**（`MissionConsole.swift:6101-6112`）：

✅ **录制时 `state.isRecording == true` → `busy == true` → 定时器保持 10Hz** → **heading 有值**。

### ⚠️⚠️ 但必须知道：**定位不是 30fps 连续更新的，是游戏 15.01s 突发驱动的**

这是**最影响录制质量的一条**，来自代码注释原文（`AuroraDriveApp.swift:4595-4622`）：

> 定位更新仍由**游戏 15.01s 突发**决定。
> 窗口≈1 个周期(18s) → 每次断档都闪断；窗口≈2 个周期(35s) → 不闪了，但游戏关了还显示旧位置（幽灵定位）
> 蒙特卡洛（6% 断档）显示可用率是**断崖式**的：18/25/30s 全为 94.6%，35s 才跳到 99.7%

**四级新鲜度**（同注释，`readWithTier()`）：

| tier | 年龄 | UI 显示 | 决策层 | 控制层 |
|---|---|---|---|---|
| `live` | ≤18s | 正常 | **采信** | **采信** |
| `recent` | ≤40s | 正常（不闪断） | 不采信 | 不采信 |
| `stale` | ≤90s | 标"陈旧" | 不采信 | 不采信 |
| `lost` | >90s | 标"无定位" | 不采信 | 不采信 |

**⟹ 对录制的实质影响**（关键结论）：

| 问题 | 说明 |
|---|---|
| **heading 在 30fps 录制下会大量重复** | 游戏 15.01s 才推一次定位；30fps × 15s = **约 450 帧共用同一个 heading 值** |
| **`locatorHeading` 在两次突发之间是「旧值」** | 它不是"当前帧车头朝向"，而是"最近一次突发的车头朝向" |
| **`live` 窗口仅 18s，而突发周期 15s** | 大部分时间落在 live 内，但**间隙处会掉到 recent/stale** → 这些帧的 heading 不可信 |

✅ **录制建议（据此修正 §1.2）**：
- **必须同时写 `locatorScore`**（`locatorScoreForTier` 产出），**用 tier 做 mask** —— 建议**只采信 live 档**的 heading
- 或写 `heading_age_seconds`，让训练侧自行决定是否使用
- **不要把 450 个重复值当成 450 个独立标签**（会造成 heading 维度过度加权）

> ⚠️ **如果训练需要逐帧车头朝向**，`locatorHeading` **不是合适的数据源**（频率不匹配）。
> 替代方案：从**运动方向**估计（如 `NetworkLocator.motionHeading` 的思路——相邻位置差分），
> 但同样受"15s 突发"限制。**真正逐帧的朝向需要另一个数据源**（如游戏内视角/方向盘数据），当前不存在。

**⚠️ 另有两条重要限制**：

| # | 限制 | 证据 | 影响 |
|---|---|---|---|
| H1 | **需要 pcap 权限且游戏在跑** | `cc.start()` 返回 false → `networkReady=false` → `locateSource() == .packetError`（`:4532`） | 没抓到包 → `locatorHeading` 保持 0 |
| H2 | **有新鲜度门槛** | `readWithTier()` 分 live/recent/stale/lost；**只有 live 才可用于驾驶**（`:4651`） | 包稀疏时 heading 是**旧值**（stale），会写进 CSV 造成"错位标签" |
| H3 | **单位是「度」[0,360)** | `dataset_v2.py:78` 明确写：CoordinateCapture 产出 heading 是**度**；而模型契约要**弧度** | **必须显式转换 + 指定 `heading_unit`** |

**✅ 录制建议**：
- 写 `locatorHeading`，但**同时写 `locatorScore`**（现有字段，`:4363` 附近）作为**有效性 mask**
- **单位统一**：写入端**转弧度**（`heading_rad = deg * π/180`），并显式写 `heading_unit="rad"`（`dataset_v2.py` 支持该参数，`:74-79`）
- **注意 0/360 环绕**：`dataset_v2.py:71` 有 `heading_wrapped`（wrap_to_pi）用于消除 sin/cos 二义性 → 建议直接写弧度原值，让 dataset 侧 wrap

### 1.3 `curvature` —— ⚠️ 运行时**未暴露**，但**可自己算**

**审计结果**（`grep -rn curvature Sources/ --include=*.swift` 共 **38** 处命中）：

| 位置 | 有没有 |
|---|---|
| `DriveState`（`AuroraDriveApp.swift`） | ❌ **无 curvature 字段**（grep 空） |
| `InferenceEngine.swift:402-432`（旧 M9） | ⚠️ 有占位，但写死 `arr[1] = 0.0`（"无遥测→0"） |
| `InferenceEngineV2.swift:437` | ✅ `LaneGeometry.curvature` —— **真算了** |
| `InferenceEngineV2.swift:678-684` | ✅ 计算处：`kappaPx / config.curvatureReference` → `clampUnit` |

**V2 里怎么算的**（`:492 / :678`）：
```
拟合车道线 → 系数 → ⑤ 导出 heading / curvature / lateralOffset
let curvatureNorm = kappaPx / config.curvatureReference   // :678
result.curvature = clampUnit(curvatureNorm)               // :684 → [-1, 1]
```

**⚠️ 关键问题：V2 的 curvature 是「归一化 [-1,1]」，不是物理 1/m**
`InferenceEngineV2.swift:313-323` 注释原文：
> 训练侧的 curvature 归一化是**物理量**：`src/dataset_v2.py:64  curvature_x5 = clip(curvature * 5, -1, 1)`
> 即参考基准 = 0.2 **米⁻¹**（curvature 是 1/米）。
> ⚠️ 而本文件的 `curvatureReference` 是**像素⁻¹** 量纲下的参考值，
> **像素↔米标定之前，curvature 这一维的绝对大小不可信，只有「符号」可信**

⟹ **V2 内部的 `curvature` 与训练侧期望的「物理 1/m」不同量纲**，直接写会**引入量纲错误**。

**✅ 但有可行路径**：`laneMask` 在 `DriveState` 可读（`yolopxEngine.laneMask`），且估计器是**可直接调用的 static 方法**：
```swift
// InferenceEngineV2.swift:498-505（非 private，可跨模块调用）
enum LaneGeometryEstimator {
    static func estimate(mask: LaneMaskSnapshot, config: V2Config = .default) -> LaneGeometry
}
```
**三种可选做法（按推荐度）**：

| 方案 | 做法 | 代价 | 产出 |
|---|---|---|---|
| **A（推荐）** | 录制时调 `LaneGeometryEstimator.estimate(...)` 拿 `curvature`（归一化），**同时写入 `curvature_raw_unsupported=true` 标记** | 小（一次静态调用） | 可训练，但**只有符号可信**，需后续标定像素↔米 |
| **B** | 把 `yolopxEngine.laneMask` 随帧**一起存下来**，离线用 Python 补算物理 curvature | 中（存掩码，体积增大） | 最干净：离线可反复调参、可标定 |
| **C** | 先**不写** curvature，`dataset_v2` 侧 mask 置 0（现状） | 零 | 该维度学不到东西（现状） |

**⚠️ 无论哪种方案，都必须解决「像素↔米」标定**，否则写进去的 curvature 是**无量纲的相对量**，模型学到的与推理端一致（都是相对量）→ **训练/推理自洽但物理意义不明**。项目文档已承认这一点（`InferenceEngineV2.swift:323`）。

**✅ 录制建议**：**方案 A**（先写归一化值 + 显式标注"未标定"），后续做方案 B 补标定。**不要**把 V2 的归一化值直接当物理 1/m 写。

- `speed_kmh` —— 从 `speedOCR.speedKmh`（专家模式无门控）

- `speed_limit` —— 从 `DriveState.speedLimit`（默认 120，恒有值）

### ⚠️ 录制时**需要额外工作**（1 个）
- `curvature` —— 需在录制路径调 `LaneGeometryEstimator.estimate(mask:)`（**可做到**，但产出的归一化值**量纲未标定**）

### ❌ 录制时**拿不到**（0 个）
**没有"无论如何都写不了"的字段** —— 4 个**全部有可行路径**。

### ⛔ 三个**前置条件 / 质量陷阱**（不满足则 heading 无值或不可信）
1. **pcap 抓包权限**（`cc.start()` 必须成功）
2. **游戏在跑**（端口有流量，`hasRecentTraffic`）
3. **⚠️ heading 频率不匹配**：底层由游戏 **15.01s 突发**驱动 → 30fps 录制下 ~450 帧共用同一值；
   且 `live` 窗口仅 18s，间隙处掉到 `recent`/`stale`（**决策层不采信**）。
   → **必须用 `locatorScore` 做 mask，或只采信 live 档**
