## 修复：TRAE/WorkBuddy 经 12451 代理报 `Parse(Version)` (4028)
**报错**：`WebSocket error ... url: "http://127.0.0.1:8792/v1/chat/completions" ... hyper::Error(Parse(Version))`。

**根因（关键）**：客户端被设了出站代理 `127.0.0.1:12451`，发的是**绝对 URL 请求**（`POST http://127.0.0.1:8792/v1/chat/completions`）。
旧 `port_forward_12451.py` 把首包原样转发给 8792，8792 的 `BaseHTTPRequestHandler` 收到绝对 URL 后把 `http://127.0.0.1:8792` 当成**要代理的上游**，于是把请求发到 NIM 公网（awselb ELB）且 Host 错 → 返回 `server: awselb/2.0` + `404`，客户端收到非 `HTTP/` 首行 → hyper `Parse(Version)` 炸。
（之前误判为 keep-alive 半截字节，实际是绝对 URL 未还原。）

**修复**：`port_forward_12451.py` 新增 `strip_absolute_url()`，普通代理分支转发前把请求行 `METHOD http://host:port/path HTTP/x` 还原成 `METHOD /path HTTP/x`（相对路径），8792 收到标准请求即正常。验证：经 12451 打 8792 不再出现 awselb，返回 8792 自身响应（无 key 时 401 / 有 key 时 200+SSE）。

**附带清理**：重启 8792 代理与 12451 桥接时，发现 `nvidia_watchdog.sh`(45341) 和 `watchdog.sh`(72136) 仍在跑会拉起旧进程；用 `kill -9` + 精确 `lsof -tiTCP:12451/-8792` 清理后干净重启（8792=47752, 12451=47920）。

## 教训
- 代理桥接器转发**普通代理请求（带绝对 URL）**时，必须还原成相对路径再发给下游 HTTP 服务器，否则下游 BaseHTTP 会把绝对 URL 的 host 当上游 → 打到公网。
- 排查 `Parse(Version)`：不是 keep-alive 就是响应首行非 `HTTP/`，优先抓原始响应首字节（`repr`）看是不是 awselb/代理链错位。
- 重启代理类进程前，先 `lsof -tiTCP:<port> -sTCP:LISTEN` 找 PID 精准 kill，避免 watchdog 拉起旧进程导致"改了代码不生效"。

## 二次修复 IncompleteMessage（前一轮修完客户端仍报）— 根因是 httpx 读环境死代理 + 200头过早发

## 三次修复 IncompleteMessage（客户端仍报，根因：httpx 响应被二次 iter_raw 读空）
**现象**：上一轮 10/10 通过后客户端仍间歇报 `IncompleteMessage`。查 `nvidia_proxy.log` 发现 22 次 `Attempted to read or stream some content, but the content has already been streamed` + 13 次 `headers sent but 0 bytes written`。

**真正根因**：上一轮"延迟发 200 头 + 预读首块"的修复里，`do_POST` 第 599 行 `next(resp.iter_raw())` 预读消费了响应的**第一个 chunk**，随后第 638 行 `_stream_one(resp, ...)` 内部又 `for raw_chunk in resp.iter_raw()` 对同一 `resp` 二次迭代 → httpx 抛 "content has already been streamed"（响应只能消费一次）→ 200 头已发、但 body 一个字节都写不出 → 客户端收空流 → `IncompleteMessage`。只要上游首块稍慢（必触发预读），100% 空流。

**修复**：
- `_stream_one` 签名由 `resp` 改为接收**外部传入的一次性迭代器** `raw_iter`，内部绝不再对 `resp` 调 `iter_raw`。
- `do_POST` 改为：`_raw_iter = resp.iter_raw()`（**全生命周期只调这一次**），`_first_chunk = next(_raw_iter)` 预读首块，再 `_stream_one(_raw_iter, ..., prepend_chunk=_first_chunk)` 从该迭代器继续读。彻底消除二次迭代。
- 附带修双 DONE：NIM 偶发 503 overloaded 时以 `200 + SSE error 事件 + data:[DONE]` 形式返回，下游 `_stream_one` 收尾又补一个 `[DONE]` → 双 DONE。改为基于「已转发的原始字节 `_raw_seen` 是否含 `[DONE]`」决定是否补发，零双 DONE。

**验证**：经 12451→8792 带 key **10 连发**，全部 200 + 非空真实 SSE 内容 + DONE 收尾 + 零双 DONE + 零空流 ✅。日志里 `has-been-streamed`/`0-bytes-written` 计数不再新增。

**铁律（记死）**：httpx `resp.iter_raw()` / `iter_text()` 等流式迭代器**只能消费一次**。任何"预读 + 转发"模式，必须把迭代器当一次性对象传递，绝不对同一 `resp` 调第二次迭代方法，否则必现 "content has already been streamed" 空流。

## 修复：TRAE 经 12451 反复报 `SSE stream error: error decoding response body (4028)`
**现象**：模型名修正后，TRAE 频繁报 `Stream error: SSE stream error: Transport error: error decoding response body (origin: downstream) (4028)`，反复出现非偶发。但本地 curl 经 12451 与直连 8891 各 5/5 长流全 OK（假象）。

**真因（关键，已复现）**：`port_forward_12451.py` 的 `socket.create_connection((host,port), timeout=15)` 的 `timeout=15` 会**继承为 socket 全局超时**，使后续 `upstream.recv(65536)` 也有 15 秒上限。SSE 流式响应在两次 chunk 之间若静默超过 15 秒（LLM 首 token 延迟大/生成间隙），`relay()` 的 `recv` 抛 `socket.timeout` → 被 `except pass` 吞掉 → 关闭连接 → 客户端收到**半截 `data:` 块** → TRAE(reqwest 流式 SSE 解码)在中途崩：`error decoding response body`。curl 用 `-N` 收完或容忍截断所以不报错，掩盖了问题。

**复现手段**：写 `sse_strict_probe.py` 严格模拟 TRAE 流式消费（逐块 4096 读 + 严格 SSE 解析校验 + 并发），修复前经 12451 **6/6 全 `IncompleteRead`/`RemoteDisconnected`**（仅读 246~1927 字节就断），直连 8891 **6/6 全 OK** → 锁定 12451 层。

**修复**：`create_connection` 之后显式 `upstream.settimeout(None)` + `client.settimeout(None)`（改回阻塞模式，仅在连接真正断开时退出），消除静默超时误杀。

**验证**：修复后重跑——经 12451 **8/8 OK** → 混合直连+经12451 **12/12 OK** → 经12451 单独 **10/10 OK**（均 events 250~750、done=True、bad_chunk=False）。根除。

**铁律（记死）**：裸 socket 桥接器里 `socket.create_connection(..., timeout=N)` 的 timeout 会污染后续 recv；凡做长连接/TCP 流式转发，建连后必须 `settimeout(None)` 改回阻塞，否则流式响应静默超 15s 必被掐断导致客户端半截流。

**交付状态**：12451 桥接器已 `launchctl unload/load` 重载修复后代码（进程 64066）。TRAE 侧配置不变（仍经 12451 或直连 8891 均可），重发即可正常流式。Base URL `http://127.0.0.1:8891/v1` / Key `sk-lm-8891-7c4f2a9e1b6d5038` / 主名 `nemimax-3-Uling-119B-1.95T/Ultra-chimera` 不变。

## 修复：TRAE 经 12451 报 `Invalid HTTP request received. (400) (4028)`
**现象**：404 修好后，TRAE 又报 `Invalid HTTP request received. (HTTP Status: 400) (4028)`。

**真因（关键，已复现）**：两层叠加，都在 `strip_absolute_url` / `peek_target`：
1. **peek_target 只读到第一个 `\n` 就停**（旧逻辑 `while b"\r\n" not in buf`），`first` 只含请求行、不含后续 header。当 TCP 分片让首包只送达一行时，`first` 残缺 → 转发给上游的请求头缺 Content-Length 等 → 上游 400/超时。
2. 上一轮修 404 时写的 `strip_absolute_url` 用 `old_line` 正则把**整个头部块截断成只剩请求行**（`method + path + version`），把 Host/Content-Length/Content-Type 等所有 header **全丢了** → 上游收无 Content-Length 请求 → 一直等 body → 超时/400。用 echo 服务器抓转发字节实锤：上游只收到 `POST /v1/chat/completions HTTP/1.1\n\n`（空头部）。

**TRAE 实际发的是「编码绝对 URL」请求行**（`http%3A//127.0.0.1%3A8891/...`），curl 发明文所以之前测不出——必须用编码形式复现。

**修复**：
- `peek_target`：停止条件改为读到**完整头块**（`\r\n\r\n` 或 `\n\n`），`first` 成为完整 HTTP 头部（含所有 header）；目标解析前先 `%3A→:` `%2F→/` 解码覆盖编码形式。
- `strip_absolute_url`：只改**第一行**的绝对 URL 为相对路径 `/path`，`lines[0]` 替换后 `b"\n".join(lines)` 重组，**其余所有 header 行原样保留**。

**验证**：单元测试 3 例（编码/明文/GET）header 全保留；echo 服务器抓到转发字节含完整 Host/Content-Length/body；编码绝对URL 经12451 打真实 8891 非流式 `200 OK` + 流式 `200`+单DONE。launchd 常驻（进程 68384）。

**铁律（记死）**：裸 socket 代理桥接器转发「普通代理绝对 URL 请求」时：①`peek_target` 必须读到 `\r\n\r\n` 头块结束才算首包读全，不能只读第一行；②`strip_absolute_url` 只替换请求行的绝对 URL 部分，**绝不能丢掉其他 header 行**（否则上游缺 Content-Length → 400/超时）；③客户端可能发百分号编码绝对 URL，解析目标与还原路径都要先解码 `%3A/%2F`。

**交付状态**：12451 已重载修复代码（进程 68384，launchd KeepAlive）。TRAE 配置不变，重发即可。Base URL `http://127.0.0.1:8891/v1` / Key `sk-lm-8891-7c4f2a9e1b6d5038` / 主名 `nemimax-3-Uling-119B-1.95T/Ultra-chimera` 不变。

## 修复：TRAE 经 12451 报 `{"detail":"Not Found"}` 404 (4028)
**现象**：SSE 断流修好后，TRAE 又报 `{"detail":"Not Found"} (HTTP Status: 404) (4028)`。

## 【22:25 修复：8891/12451 上 `/v1/models` 返回 404 + 兜底函数失效】

**用户报**：`GET http://127.0.0.1:8891/v1/models` → 404。

**根因**：embedded 代理两个端口的路由是硬编码的白名单——`handle_llm`（LLM 端口 8891 等）第 178 行只认 `POST /v1/chat/completions`，其他路径一律 404；`handle_proxy`（12451）也只在 `b"/v1/chat/completions" in first` 时处理，别的 close。所以 `/v1/models` 任何端口都不支持。

**修复（已落地重载）**：
1. 新增 `_exposed_models()`（从 `litellm_config.yaml` 的 `model_list[].model_name` 去重收集对外名）+ `_handle_models(client)`（返回 OpenAI 兼容 `{"object":"list","data":[{"id":...,"object":"model",...}]}`）。
2. `handle_llm` 路由加：`GET /v1/models` → `_handle_models`；`handle_proxy` 加同样分支。
3. 实测：8891 / 12451 两个端口 `GET /v1/models` 均 200，返回 15 个对外名（含 gseek-v9-pro、Ultra-chimera 等）。

**顺带发现的真 bug（重要）**：上一轮（22:13）加的 `_patch_empty_content` **实际没生效**——它用 `getattr(msg,"reasoning_content")` 读 LiteLLM 的 `ModelResponse` 对象，但 LiteLLM Message 上该字段 `getattr` 拿不到（序列化时才填进 dict），导致 GLM 思考吞 content 时空回复没被兜底。验证复现：短 `max_tokens=128` 打 gseek-v9-pro，GLM 返回 `content=''`、`finish=length`、但不触发兜底。
**修复**：`_patch_empty_content` 改为先 `resp.model_dump()` 成 dict 再读 `message.reasoning_content` 回填 content；调用方（handle_llm 非流式 + _handle_proxy_llm 非流式两处）改为拿到 dict 后 `json.dumps` 返回（不再 `model_dump_json()`）。
**复测**：短 max_tokens 逼 GLM 空 content，6/6 全部 content 有字、`finish=stop`、标注 `[思考已折叠·代理兜底]`，客户端永远收到内容。

## 【22:55 DSH 报 "Connection error" + 重试延迟 7948ms 根因与修复】

**现象**：用户在 DSH（浏览器壳，跑在 localhost:3080）里打模型报 `Connection error`、`重试延迟 7948ms`；但本机 curl 直打 8891 完全正常（7s 返回）。

**根因（CORS 预检被拒）**：DSH 是浏览器跨源网页（localhost:3080 → 127.0.0.1:8891），浏览器发请求前必发 `OPTIONS` 预检。原 `handle_llm` 路由判断 `method != "POST"` → 直接 404 + `client.close()` 断连接。浏览器收到非 2xx 预检响应 → 判定 CORS 失败 → 报 Connection error，DSH 自带重试（即那个 7948ms 延迟）。curl 不发 OPTIONS（同机无 CORS 概念）所以正常——这解释了"本地能通、DSH 不能"。

**修复（`port_forward_embedded.py`）**：
1. `send_response` 默认带 `Access-Control-Allow-Origin: *` + `Allow-Methods` + `Allow-Headers`（所有响应都加）。
2. `handle_llm` 开头：若 `method == "OPTIONS"` → 返回 204 + CORS 头，不断连接。
3. `handle_proxy`（12451）同样加 OPTIONS 预检放行。

**验证**：模拟 DSH 跨源（`Origin: http://localhost:3080`）→ OPTIONS 预检返回 204 + CORS 头；带 Origin 的跨源 POST `gseek-flash-lite` 正常返回 content。launchd 重启（PID 73643）。

**教训**：任何浏览器壳（DSH/网页端）接入本机裸 HTTP 代理，都必须处理 CORS 预检 + 回 `Access-Control-Allow-Origin`，否则必然 Connection error。

## 【23:04 DSH 真因：畸形路径 /v1/models/chat/completions】

**关键排查手段**：在 `handle_llm` + `handle_proxy` 加临时 debug 日志（`/tmp/dsh_debug.log`，PEEK 首行），让用户触发一次 DSH 请求 → 看到 DSH 真实发出的请求。

**DSH 真实行为（日志铁证）**：
- DSH 实际连的是 **12451**（不是用户以为的 8891）。
- 它先做 `GET /v1/models` 探测（12451 已支持 → OK）。
- 然后发 **`POST /v1/models/chat/completions`** —— DSH 把 `/v1/models` 当 base URL 再拼 `/chat/completions`，拼出畸形路径（标准应是 `/v1/chat/completions`）。
- 该路径在 12451 被 `if b"/v1/chat/completions" in first` 误匹配进 `_handle_proxy_llm`，但内部异常 → **静默关闭连接（无响应）** → DSH 报 Connection error + 每秒重试（日志里 23:03:18~57 疯狂重发）。8891 则直接 404。

**修复**：两个端口路由都兼容畸形路径——把 `/v1/models/chat/completions` 当 `/v1/chat/completions` 处理（8891 的 path 白名单 + 12451 的 `in` 判断都加上该路径）。
**验证**：畸形路径打 8891/12451 均返回 HTTP 200 + content。launchd 重启（PID 75011）。

**第二个真因（上一轮已修但非主因）**：原 `send_response` 没发 `Content-Length` 头（裸 HTTP/1.1 200 + body 靠关连接结束），严格客户端可能判不完整。已补 `Content-Length` + `Connection: close`。

**结论**：DSH 报 Connection error 的根因是**畸形路径被静默关闭**，不是 CORS（CORS 已在上轮修好，但非主因）。修好后 DSH 应正常。
