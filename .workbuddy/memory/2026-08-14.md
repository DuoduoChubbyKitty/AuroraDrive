## 速度 OCR 字模方案推进（2026-08-14 深夜）
- **App 录制（RecordEngine）不可用于字模**：它写死 `targetSize=224×224`（训练缩略图，非等比压扁）。实测 1222 帧跑 RealSpeedometer 流程：轮廓数 1-10 乱跳、数字仅 ~20px 高，无法分离 0-9。且字形压扁与运行时原生帧不一致。
- **运行时 OCR 读的是原生帧**（CaptureEngine onNativeFrame 的 CVPixelBuffer，2940×1912），故字模必须原生分辨率抠。
- **槽位坐标已锁定**（从 `档案留存/` 9 张原生截图程序化定位）：速度表右下，3 数字槽空心字，归一化 x 中心≈0.459/0.490/0.521（槽宽~0.031），y≈0.859-0.912。数字空心（左右竖+上下弧），亮度 135-200 非纯白，上半部比下半部暗（Otsu 只勾出下半部——已知坑）。
- **算法蓝本**：RealSpeedometer（github banujan59，FH5 速度表识别，无 LICENSE 只借鉴思路）。核心：灰度→阈值→轮廓分离→数字 resize 25×45→与模板**减影**→**5×5 侵蚀 1 次**→残差≤10 命中；"1"残差≤100 特殊。训练=视频逐帧分离→人工标注→pickle。参数 DATASET 90×50、阈值170、h≤30 过滤、x<10 去重。
- **GitHub 调研**：异环自动化工具 BetterNTE(GPL-3.0/Rust)、MaaNTE(AGPL-3.0/Py,2672star)、ok-nte(GPL-3.0/Py) 均**无速度表功能**且 Windows 专属。7 段数码管方案(SegoDec/SSOCR)不适用（异环是空心字非数码管）。赛车游戏速度 OCR 主流=Tesseract(PSM7+whitelist，Apache 许可)。**结论：GitHub 无现成异环字模，字模必须从游戏画面抠**。

## ✅ CaptureEngine 输出分辨率修复（2026-08-15 中午，字模分辨率根因）
- **根因**：SCDisplay.width 实测返回点值/中间值（~1485），SCStream 输出低分辨率 → 速度表数字仅 ~18px → 用户录的字模切片 119×48（235×96 的一半）→ Otsu 后 1-9 样本全是噪点，聚类只能认出「0」（C0=1374/1800 样本，C1-C3 全是噪点碎片）。用户飙车 0→200 确实录到了 1-9，但分辨率低到认不出。
- **修复**：`CaptureEngine.startStream` 改为 `NSScreen.deviceDescription["NSScreenNumber"]` 匹配 SCDisplay.displayID → `config.width/height = frame(点) × backingScaleFactor`。实测屏0 = 1470×956 点 × 2 = **2940×1912 像素** ✓（副屏 1200×1920 scale=1 不受影响）。
- **附带修复**：`RecordEngine.cropAndEncodePNG` 改用 `largestCGImage`（遍历 representations 取最大像素，Retina 2x 优先），并埋 `[glyph]` 尺寸日志；`CaptureEngine` 埋 `[capture] display` 日志。
- **结论**：修复后字模切片应为 235×96（数字 ~95px），与运行时同源。用户游戏更新完录一次 0→200 即可建全 0-9 字模。
- **用户铁律**：只用 App 不敲命令行；讨厌反复折腾（"害怕你了"）——每次修改必须验证到位再交付。
