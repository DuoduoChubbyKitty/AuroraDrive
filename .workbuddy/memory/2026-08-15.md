- OCR(YOLO/M9) 走 `onNativeFrame`(全分辨率像素缓冲) / `onYoloFrame`(源头 GPU 缩放) 直通，与此全分辨率 CGImage 无关，降分辨率不影响它们。

## GPU→CPU 缩放：根治 40ms（2026-08-16 00:3x，用户实测"四十几毫秒"）
- **根因**：CaptureEngine `ciContext = CIContext(.useSoftwareRenderer:false)` **强制 GPU**，每帧 2 次 GPU 缩放（YOLO 640 render + UI 480 createCGImage）。游戏占满 GPU → 排队 → capWork 飙到 40ms。全盘优化时审查者估的是"GPU 空闲 1-2ms"，漏算了"游戏占 GPU 时排队"——正是用户早先点破的"别走 GPU，游戏占满会排队"。
- **修复**：删 ciContext(GPU)，YOLO 640 + UI 480 全改 `vImageScale_ARGB8888`(CPU 双线性，32BGRA 字节序匹配、top-down 不翻转、YOLO 非等比/UI 等比)；UI 用 `CGDataProvider(releaseData: retain uiBuf)` 零拷贝建 CGImage（修 use-after-recycle 花帧）；删 copyYoloFrame/yoloBuffers 改池化直缩放(省 1.6MB 冗余拷贝)；config.pixelFormat 显式 32BGRA。
- **关键教训（必记）**：① 编译验证**绝不能只看 `| tail` 的 exit 0**——tail 的 exit 会掩盖 swift build 失败。必须 `swift build ...; echo "exit=$?"` 看真实 exit。之前"池上限"加 `kCVPixelBufferPoolMaximumBufferCountKey`（**SDK 不存在的常量**，只有 MinimumBufferCountKey/MaximumBufferAgeKey）导致编译静默失败、部署了旧产物，是用户测 40ms 的隐藏原因。② CGDataProvider 的 passRetained/releaseData 引用计数：provider 失败手动 release、cgImage 失败靠 provider ARC（拆分 guard 防 over-release）。
- **流程**：架构师→工程师1(GPU→CPU)→工程师2(复查揪出 use-after-recycle + 冗余拷贝)→QA→双模型比对(2 轮)，终审"极好"。
